# 5. Data model

## Audit columns — on every table, and the join-table exception

Every table spreads `...auditColumns`: `created_at`, `created_by`, `updated_at`, `updated_by`, `deleted_at`, `deleted_by` (`src/db/audit.ts`). The six-column set is the four stamp columns (`auditStampColumns`) plus the two delete columns, so it has one definition. Two join tables, `ingredient_categories` and `spell_categories`, spread the four stamps only and are hard-deleted. `spell_steps` is a join table that carries the full set: a layer taken out of a spell is a tombstone.

**Why those two and only those two.** A pair is a pairing, not content. It holds nothing of its own — no locator, no position, no typed text — so a pair removed is restored by toggling the chip again, and a tombstone keeps nothing a restore could return. Every category chip toggled off is a write to one of them, so a soft delete would fill the highest-churn tables with tombstones nothing reads, and each would need a surrogate key and a partial unique index so the same pair could be re-added. `spell_steps` is different: a layer is part of a recipe that keeps what went into its jar, where categories are a classification, corrected rather than kept. The v2 history trigger records a `DELETE` as readily as an `UPDATE`, the actor beside it in `app.current_user_id`, so nothing is lost to history. The four stamp columns stay on both: `created_by` on a join row answers who added the link. `workspace_members` and `ingredient_folk_names` keep the full six (claude-docs/db/hard-delete-join-tables.md, "Hard delete on two join tables").

**Four enforcement rules, because audit columns rot the moment one path skips them:**

1. **`*_by` never comes from a request body.** All writes go through `withAudit(session, fn)`, which injects them. A lint rule bans importing `db` outside `src/db/repository/`.
2. **`updated_at` is a database trigger**, so a manual `psql` fix still stamps it.
3. **Soft-delete filtering is the repository's** (CLAUDE.md rule 4). No exported query can forget `deleted_at IS NULL`: `findMany`/`findOne` apply it where the column exists and read a join table that has none, deciding on the table's own shape rather than on a flag a caller passes. The writer holds the same line: every update and soft delete skips a deleted row, so a tombstone is never rewritten and a second delete never overwrites who made the first. The way back to a deleted row is v2's restore (§13, "Edit history"). **The named exceptions**, each a finder whose name ends `…IncludingSoftDeleted` that skips one filter and no other (claude-docs/db/soft-delete.md, "Soft-delete filtering and the partial-index convention"):
   - a spell keeps reaching an ingredient soft-deleted after it went into the jar (`spell_steps`, below);
   - a substitute keeps reaching a deleted ingredient it links, to show its last name (`ingredient_substitutes`, below);
   - a member reads the name of anyone who has shared a coven with them, a removed member and a deleted user included (`design-decisions/auth.md`, "A deleted co-member reads under their last name");
   - a coven whose cupboard names a compendium entry the curators have retired keeps reading it, its forms, children and jars, keeps annotating it, may make it its own or remove it, and may add, change and remove jars of its forms. It keeps listing it on the same condition, through the hatch-named `workspaceListScopeIncludingSoftDeleted`, while the public compendium, the picker and the add flow stay live-only (`design-decisions/ingredients.md`, "A retired entry stays readable to the covens that use it");
   - one writer, `reviveMembership`, reaches a soft-deleted row, a removed member's, because the pair `(workspace_id, user_id)` is the primary key and an invitation accepted by someone removed earlier cannot insert it again. It reaches deleted rows only, clears the deletion, sets the invited role and restarts `joinedAt`.
4. **The hard delete is a named method, not a flag.** `write.delete(table, match)` removes rows outright and is typed to reject any table carrying `deletedAt` at compile time; `softDelete` demands one. It names its rows by column value (a list matches by `IN`) rather than by an `SQL` predicate, which a service may not build (MB.33).

Every write transaction publishes the acting user as a transaction-local setting, `app.current_user_id`, with `select set_config('app.current_user_id', $1, true)`: `SET LOCAL` accepts no bind parameters, so writing it literally would mean interpolating a user id into SQL text. One v1 trigger reads it, `record_privilege_change()`, as the actor of a `user_privilege_changes` row. Beyond that it is there for the v2 history trigger (§13) and the policies deferred to the public launch (§8), so either becomes one migration rather than a re-audit of every write path. A write that changes a privilege column on `users` also declares its route and an optional note (`app.privilege_route`, `app.privilege_note`), and the trigger refuses a privilege change whose route is empty (claude-docs/db/write-path.md, "The write path — `withAudit`").

**Partial indexes only, on every table that has a `deleted_at`.** Without the `WHERE deleted_at IS NULL`, deleting a record permanently blocks reusing its name. The two hard-deleted join tables need none: their composite primary key has no tombstone to dodge. The one named exception is a unique index that is the target of composite foreign keys, which a partial index cannot be (`ingredient_variants`, below).

## Naming note: `workspaces` vs `/coven/`

The schema entity is `workspaces`; the URL prefix is `/coven/`. The divergence is deliberate. `/w/` is unreadable, and nesting workspaces under `/compendium/` would make that word mean two things. Code, schema and prose use _workspace_; the URL segment and every label, heading, notice and dialog title on the screens say _coven_.

## Tables

Column lists are given where a column carries a rule; the schema files in `src/modules/*/schema/` are the full list.

**`users`** — `id`, `email`, `emailVerified`, `name`, `image`, `role` (`user` | `curator` | `admin`), `canCreateWorkspace` (boolean, default `false`), `verificationSentAt` (nullable; when the last verification mail went out, so the next is at least a minute away), `agreedTermsVersion`, `agreedDisclaimerVersion`, `agreedEthicsVersion` (nullable integers), `termsAcceptedAt`, + audit.

- `name` and `image` (not `displayName`/`avatarUrl`) are Better Auth's own core `User` field names (§2, §8); renaming them would need a `user.fields` mapping in `src/lib/auth.ts` for no real benefit.
- `emailVerified` is true when Google or Discord reported the address verified or when the user followed our own verification mail; Facebook and Microsoft profiles arrive unverified whatever they report. A provider that does not vouch is never matched to an existing row by its address: it is added to an account only by an explicit link from a signed-in session on `/account`, after which its sign-in resolves by the provider account id and never by the address. An unverified account is provisional and lapses one verification window after its last mail, and three hours after sign-up at most, which is how an address squatted by an unverified sign-up returns to its owner. An address changes only at verification: asking for a new one mails it a change link and writes nothing to the row, so an established account never becomes provisional.
- The three `agreed…Version` numbers are the Terms of Use, Disclaimer and Code of Ethics versions the account last agreed to, all three at once; null means none. They read as one joint version, `terms.disclaimer.ethics` (`design-decisions/support.md`, "Agreeing to the terms covers the disclaimer and the code of ethics").

`role` is a column, not a table; v1 needs no granular platform permissions. Its three values (`design-decisions/auth.md`, "A third site role, `curator`"):

- A **curator** curates and does nothing else on the site: they may use every curation screen a keeper can and reach nothing on the people page. A keeper may curate too. The people page is the user list, one user's details and covens, role changes, granting and revoking coven creation, impersonation, admin invitations, the pause and the privilege ledger, and it is the keeper's alone. A coven's invitations stay its stewards': a curator invites to the covens they own and to no other. The component workshop and the privilege ledger stay admin-only, and a curator can be impersonated like any non-keeper.
- Two checks hold the line (CLAUDE.md rule 5): `assertCurator` passes a curator or a keeper and returns a `Curator` proof; `assertSiteAdmin` passes a keeper only and returns a `SiteAdmin`, which is a `Curator` with a second brand, so every keeper proof is a curator proof and never the reverse.
- Keepers and curators write the global compendium (including showing or hiding an entry: a hidden entry is excluded in SQL from every public surface and still seen by admin screens, the audit queue and a coven whose cupboard names it), global categories, the ingredient form vocabulary, the two group vocabularies that organise them (`category_groups`, `ingredient_form_groups`), the celestial body and zodiac vocabularies (`celestial_bodies`, `zodiac_signs`), and the deity vocabulary with its traditions (`deities`, `deity_traditions`), and **nothing else**: neither has any access to any workspace's ingredients or grimoire. A keeper or curator account is still an ordinary member of whatever workspaces it belongs to; the site role and the workspace roles are independent, and `/coven/[slug]` is a 404 to them as a non-member.
- The **primary keeper** is the live keeper whose email matches the `ADMIN_BOOTSTRAP_EMAIL` env var. It is promoted at a Google or Discord sign-in that reports the address verified (the two providers whose verification can be trusted), or on verifying the address through our own mail from a session holding the row; the address cannot be registered any other way. It cannot be revoked or deleted by anyone, itself included. Changing who it is means changing the variable and redeploying, and the previous primary keeper stays an ordinary admin.
- Every other keeper is granted and revoked by an existing keeper from `/keepers/users`, which is also where a keeper gives and takes away the curator role (one Change Role dialog offering every role but the one held; moving a keeper to curator or user is a revoke of admin, so the primary-admin and last-admin refusals apply). Every change is recorded in the `user_privilege_changes` ledger by a trigger on `users`. A revoke that would leave zero keepers is refused, as a fallback for the gap between changing the variable and the new address signing in. The primary keeper can pause granting and revoking for every other keeper, itself exempt, through the `admin_role_change_pauses` ledger; the pause covers approving and revoking coven creation too (claude-docs/auth/admin-bootstrap.md, claude-docs/auth/admin-users.md).

`canCreateWorkspace` defaults to `false`. Signing in by any method (a registered provider, a password or a passkey) earns an account and an observer seat in the demo coven (below), and nothing more; the seat does not touch the flag. The flag turns `true` by one of two routes, accepting a workspace invitation or a keeper granting it, and stays `true` until a keeper revokes it, so an established user can create as many workspaces as they like. Revoking stops new workspaces and leaves the ones already created, of which they remain stewards; a keeper's or a curator's flag cannot be revoked while they hold the role, and nothing automatic clears it (`design-decisions/auth.md`, "Revoking workspace creation, and its ledger"). Nothing in the OAuth flow sets it. Being made keeper or curator sets it `true` in the same write, and a CHECK on `users`, `users_privileged_can_create_workspace` (`role = 'user' or can_create_workspace`), refuses any row that is not a plain user and lacks it, so the gate reads the flag alone, never `role`. Moving between curator and keeper keeps it, and so does losing either role: a former keeper or curator keeps the flag, as the grant was a vouching too (`design-decisions/auth.md`, "Every admin holds `canCreateWorkspace`").

**`admin_role_change_pauses`** — `id`, `endedAt` (nullable), `endedBy` (nullable), + audit. The primary keeper's pause on every other admin's grants and revokes of admin and of coven creation, one row per pause: `created_by` is who paused and `created_at` when, the ended pair who resumed and when. Keeper changes are paused while a live row has no `endedAt`; a unique index on a constant, partial on that, allows one such row at most, and a CHECK keeps the ended pair together. Nothing is seeded. Reached only through the open-pause finder and the writer's named pause and resume, each under the `SiteAdmin` proof (the finder also under a site-tier invitation, whose accept reads the pause from a session holding no proof); the generic insert, updates and deletes refuse the table at compile time (`design-decisions/auth.md`, "The admin-role-change pause is a ledger, not a settings row").

**`user_privilege_changes`** — `id`, `userId`, `privilege` (`admin` | `curator` | `create_workspace`), `change` (`grant` | `revoke`), `via` (`bootstrap` | `admin` | `invitation` | `manual`), `note` (nullable), + audit; each set a closed enum. The one privilege ledger: one row per change to a privilege column on `users`, because the next update to a user's row overwrites its `updated_by`. `created_by` is who made the change and `created_at` when. `via` is how it came about: `bootstrap` the primary keeper's promotion by `ADMIN_BOOTSTRAP_EMAIL`, `admin` a keeper's act on `/keepers/users`, `invitation` an acceptance, `manual` a `psql` fix that declared itself. Append-only by the database: a `forbid_rewrite()` trigger refuses every update and delete from any client. `record_privilege_change()`, a trigger on `users`, fills it: one row per changed privilege (curator to admin writes a curator revoke and a keeper grant at one instant; user to curator writes a curator grant and a `create_workspace` grant), its actor `app.current_user_id` or else the row's own `updated_by`, its route and note those the writer declared to `withAudit`, and a change declaring no route refused. Nothing in the application inserts into it. A third privilege is a value in the enum and a line in that trigger, not a table. It is a privilege's account, not §13's edit history (`design-decisions/auth.md`, "One privilege ledger, written by the database").

**`support_requests`** — `id`, `about` (`accessibility` | `bug` | `account` | `compendium` | `privacy` | `feedback` | `question`), `subject` (1–120 characters), `message` (1–4,000), `path`, `errorCode` (nullable integer; the HTTP status of the error page it was sent from), `status` (`open` | `waiting_on_sender` | `resolved` | `closed`), `assignedTo` (nullable user), `curatorVisible` (boolean, default `false`), `issueUrl` (nullable; an issue on the project's repository), `resolvedBy`, `resolvedAt`, `lastSenderActivityAt`, `lastStaffActivityAt`, `closedAt` (each nullable), `closingNoticeSentAt` (nullable; when the closing-soon notice for the current resolution was taken by the mail transport, cleared by a reopen), `linkedFrom` (nullable request: the closed request this one follows up), `errorReference` (nullable; the digest Next gives an error page), `senderEmail` (nullable), + audit. Soft-deleted; resolved and closed rows are kept, and a request closed twelve months is anonymised rather than deleted. Owned by the `support` module. A message a signed-in, verified account sends to whoever runs the site (`design-decisions/support.md`, "A support form, reviewed by keepers").

- No workspace id: a request is the account's, and the sender is `created_by`, so the sender's finder ANDs `created_by`. A curator reads a request only when `curatorVisible` or `assignedTo` them, filtered in SQL. An account may send ten in 24 hours, counted from this table.
- `path` is the page it was sent from, as the address, coven slug included. A curator reads it with the segment after `/coven/` redacted; a keeper and the sender read it as stored. An invitation token in it is replaced and a query string dropped on write (`design-decisions/support.md`, "A support request keeps the coven in its page"). A curator is never shown a sender's email, neither a signed-out visitor's `senderEmail` nor an account's address; a keeper is shown both.
- `senderEmail` is the address of a signed-out visitor, in which case `created_by` is the seeded signed-out sender account and a CHECK ties the two together (`design-decisions/support.md`, "The support feature, revised after review").
- **Retention.** A resolved request closes seven days after resolving, with `closedAt` set to `resolvedAt` plus seven days, and readers treat a lapsed resolved row as closed from that moment, before the job writes it. Twelve calendar months after `closedAt`, the job sets `subject` to the fixed "Anonymised support request.", empties `message`, `path` and every reply's `body`, sets `senderEmail` null, and passes `created_by` (and a sender's `resolvedBy`, and a sender-authored reply's `created_by`) to the System account. `about`, `status`, `errorCode`, the dates, the staff ids and `issueUrl` stay, so counts per topic and month do not change.
- A request whose `created_by` is the System account is shown with no Sender: the server sends no sender and no System name, and the screens drop the Sender cell, the From fact and the sender's messages. Nothing on it can be changed: the service refuses a note, a reply, an assignee, curator visibility and an issue link on it, and the dialog offers none of them (`design-decisions/support.md`, "A resolved request closes on its own, and a closed one is anonymised").

**`support_replies`** — `id`, `requestId`, `body` (1–4,000 characters), `authorRole` (`sender` | `staff`, default `staff`), `visibility` (`public` | `internal`, default `public`), `noticeSentAt` (nullable; when the mail telling the sender of this staff reply was taken by the mail transport, set by the job step that sent it), + audit; soft-deleted. One message on a request; the author is `created_by`. An internal note is staff-only, and any curator who can read a request may add one to it, assigned to them or not. The sender reads a reply on `/account/support`, and a mailed notice says one is waiting without carrying its text; a signed-out sender, who has no such page, is mailed the reply whole.

**`support_send_counts`** — `id`, `kind` (`address` | `client`), `key` (an HMAC of the normalised address under `BETTER_AUTH_SECRET`, never the address), `windowStart`, `count`, + audit; one live row per kind and key. The running count of requests a signed-out visitor has sent in the current 24 hours, written as the seeded signed-out sender.

**`support_timeouts`** — `id`, `userId` (nullable: null on a time-out set on a signed-out request, which binds the address alone), `addressKey` (nullable: the HMAC key of the address the sender wrote from, never the address; a CHECK requires `userId` or `addressKey`), `until` (nullable: null is a time-out with no end date), `note` (required, a CHECK refusing a blank one), `liftedAt` (nullable), + audit; kept as history and never deleted by the app. A verified claim of the address moves an address-only time-out to the claiming account. A keeper's sanction on a sender: it stands while `liftedAt IS NULL` and `until` is null or in the future, and while it stands `sendSupportRequest` refuses with an error naming the end, or saying the sender is timed out with no end date. Every time-out says why in its note, which staff alone read. The keeper who set it is `created_by`; a curator may not set or lift one (`design-decisions/support.md`, "The support feature, revised after review").

**`user_access_pauses`** — `id`, `userId`, `until` (nullable; null means no end date), `note` (required, never blank: a CHECK refuses one with no character but whitespace), `liftedAt` and `liftedBy` (nullable), + audit; kept as history, never deleted, except that a hard-deleted provisional account takes its pauses with it (`userId` cascades). A site admin's pause on a user's access to the site, one row per pause: `created_by` is the keeper who set it, the note why, the lifted pair who lifted it and when; a CHECK keeps the pair together. A row is _live_ while it has no `liftedAt` and no `deletedAt`, and a unique index on `userId`, partial on that, allows one live row per user. A pause _stands_ while it is live and its `until` is null or still ahead. Once `until` passes, the pause ends by itself with no write and its row stays live: `now()` is not immutable, so it cannot sit in the index predicate. Setting a pause therefore lifts the user's live row first, standing or run out, stamping the lifted pair from the session, then inserts the new row. A lifted row whose `until` is earlier than its `liftedAt` had run out on its own before it was lifted; lifting reaches a standing pause only, so a run-out pause is never recorded as a keeper's lift. Owned by the `identity` module and reached only through the standing-pause finder (no proof: every signed-in request reads it to decide what its session may reach), the finder for every pause on a user, and the writer's named set and lift (the last three under `SiteAdmin`); the generic insert, updates and deletes refuse the table at compile time (claude-docs/db/identity-model.md, claude-docs/db/write-path.md, "Pausing a user's site access").

**`documents`** — `id`, `key` (`privacy` | `disclaimer` | `code-of-ethics` | `terms`), `title`, `lede`, `seedKey` (nullable), + audit. One row per site document (`design-decisions/support.md`, "A keeper editor for the site's documents"). A partial unique index on `key`, and one on `seedKey`. The set is fixed by the seed: a keeper edits a document and never creates or deletes one, because each has its own public route and footer link in code. Owned by the `documents` module; `updateDocument` is the writer's named edit of the title and lede, under `SiteAdmin`, and the generic writes refuse the table at compile time.

**`document_versions`** — `id`, `documentId`, `number` (a whole number per document, 1, 2, 3), `body` (markdown), `status` (`draft` | `published`), `publishedAt` (nullable), `revision` (the optimistic-concurrency counter, `revisionColumn()`), + audit. A partial unique index on `(documentId, number)`, and one on `documentId` where `status = 'draft'`, so a document has at most one open draft; a CHECK sets `publishedAt` exactly when `status` is `published`. A published row is never written again: a change opens a new draft, copied from the latest published body, with the next number (a number once used is never reused, deleted rows included). Saving and publishing a draft carry the expected revision and refuse a stale one with `StaleWrite`. Owned by the `documents` module; the finders for the current, a numbered and a page of published versions take no proof because the public pages read them, and the draft finder and the named writes take `SiteAdmin`.

**`document_mailings`** — `id`, `documentVersionId` (nullable), `summary` (nullable), `status` (`sending` | `paused` | `sent` | `replaced`), `recipientCount`, `finishedAt` (nullable), + audit. The record of one email to every account about every document changed since the last email. The documents it covers are its `document_mailing_items`. `documentVersionId` and `summary` are legacy, nullable and empty in a new mailing; the partial unique index on `documentVersionId` stays with them. A keeper starts a mailing, never a publish, and starting takes `SiteAdmin`: it covers every pending document (each newest live published version past version 1 that no `sent` mailing holds), with a written summary for each, and replaces every `sending` or `paused` mailing. A transaction-scoped advisory lock, taken before pending is read, stops two keepers starting two mailings at once. Finishing one runs in the job as the System account, and only a `sending` mailing finishes. A `paused` mailing stopped on the provider's monthly allowance and sends again only when a keeper resumes it. "Queued" and "waiting" are not stored: the panel on `/keepers/documents` works them out from which mailing is oldest and how many have gone out today. Owned by the `documents` module.

**`document_mailing_items`** — `id`, `mailingId`, `documentVersionId`, `summary`, + audit. One document a mailing covers: the published version it announces and the keeper's summary of what changed. A partial unique index on `(mailingId, documentVersionId)`. The email lists every item, and asks the reader to agree again only when the terms, the disclaimer or the code of ethics is among them. Owned by the `documents` module.

**`document_mailing_recipients`** — `id`, `mailingId`, `userId` (cascades with a hard-deleted provisional account), `sentAt` (nullable until sent), `skippedAt` (nullable; set instead of `sentAt` for an account that is gone or whose address the provider refused for good; a CHECK allows at most one of the two), + audit. A unique index on `(mailingId, userId)`, so a retried batch never mails an account twice. Read a page at a time, the ones with neither set. The day's send count and the reached count read `sentAt` alone, so a skipped account uses none of the allowance. Owned by the `documents` module.

**`help_articles`** — `id`, `kind` (`faq` | `article` | `guide` | `term`), `audience` (`public` | `staff` | `keeper`, default `public`; a `term` is always `public`), `title`, `slug`, `summary`, `body` (Markdown), `position`, `seedKey` (nullable), `parentId` (nullable), `searchVector` (generated `tsvector`, `english`: title weight A, summary B, body C; GIN index), + audit. One row per FAQ entry, help article, guide or glossary term (`design-decisions/support.md`, "Help and FAQ articles, and a glossary, as rows a keeper edits"; §10, "Help and FAQ articles"). Owned by the `help` module; the public finders take no proof because the public pages read them, and every write takes `SiteAdmin`.

- `slug` comes from `src/lib/slugify.ts`. It is unique among live rows on a partial index, across every kind, so a term's anchor and an article's address never share a slug. The slug `glossary` is reserved: the service refuses it, because `/help/glossary` is the glossary page.
- `position` is the FAQ's order. A `term` does not use it.
- `parentId` points at a row of kind `guide`, for sub pages. Only a guide holds sub pages, a sub page is always an `article`, and a guide has no parent, so help is one level deep. A CHECK allows a parent only on an `article`; that the parent is a live `guide` needs a look at a second row, so the service enforces it and a test asserts it. A guide with live children cannot be deleted until its children are moved or deleted.
- `kind` changes only between `article` and `guide`: a top-level article becomes a guide, a sub page does not, and a guide becomes an article only while it holds no live sub page. The service refuses the rest.

**`workspace_member_pauses`** — `id`, `workspaceId`, `userId`, `until` (nullable; null means no end date), `note` (nullable), `liftedAt` and `liftedBy` (nullable), + audit; kept as history, never deleted, except that a hard-deleted provisional account takes its pauses with it (`userId` cascades). A coven steward's pause on one practitioner's or observer's access to that coven, one row per pause, read the way `user_access_pauses` is: `created_by` is who set it, a CHECK keeps the lifted pair together, a row is _live_ while it has no `liftedAt` and no `deletedAt`, and a unique index on `(workspaceId, userId)`, partial on that, allows one live row per member per coven. A pause _stands_ while it is live and its `until` is null or still ahead, and ends by itself with no write once `until` passes. Setting a pause lifts the member's live row in that coven first, standing or run out, and lifting reaches a standing pause only. The paused user keeps their seat, and a pause in one coven touches no other. Owned by the `coven` module. Its two finders (the standing pause on one member, and a page of the coven's pauses) and the writer's named set and lift each take a `Membership` and AND its `workspaceId`, so a proof for one coven can neither read nor lift a pause in another. Which permission that proof must carry is the service's to check. The generic workspace insert, updates and deletes refuse the table at compile time.

`assertMembership` has to refuse a paused user before any `Membership` exists, so it cannot use the standing-pause finder, which takes one. The check sits inside the membership lookup's own query: `findWorkspaceSeat`, the one workspace-scoped read that takes no proof because it mints one, reads the role and the standing pause in one statement, a left join on `workspace_member_pauses`. This keeps one query per render under the existing `cache()` and keeps the read narrow: a role and a pause's end, never rows. It answers with the pause rather than dropping the role, so a caller can tell a paused member, refused with `AccessPaused` and shown a page saying their access is paused, from a non-member, refused with a bare `Forbidden` and given a 404. `findWorkspaceRole` is the role alone, read through `findWorkspaceSeat`, for callers that ask whether a seat is taken: a paused member still holds the seat (claude-docs/db/membership-proof.md).

**`workspaces`** — `id`, `name`, `slug`, `demo`, + audit. `demo` is true on the one demo coven (a partial unique index on `demo WHERE demo AND deleted_at IS NULL` allows at most one live row), which is seeded on every environment under the fixed id `DEMO_WORKSPACE_ID`; code finds it by the column, never the constant. Every account is seated in it as an observer (`viewer`), the bootstrap system user and every site keeper hold a steward (`owner`) seat, a user may leave it and is never re-added, and it cannot be deleted. It is a flag and not a `kind`: the row is still a workspace that takes members (`design-decisions/auth.md`, "One demo coven on every environment").

There is no `kind` column and no automatically created workspace. Every workspace behaves identically: it can take members and be deleted by a steward. A newly signed-in user has no workspace until they accept an invitation or, holding creation rights, make one.

**`workspace_members`** — `workspaceId`, `userId`, `role`, `joinedAt`, `invitedBy` (nullable), + audit. PK on the pair. `invitedBy` is the sender of the invitation that seated the person, written once at acceptance and overwritten if they are removed and invited back; it is not `created_by`, which is whoever accepted. A coven's creator keeps null. No address is stored here: a steward sees each member's `email` read off their `users` row when the members page is drawn, so a changed address shows at once, and no other role sees it. No verified state is shown beside it, since every member's address is verified: a seat is taken only by accepting an invitation, which matches a verified address, or by creating a coven, which an unverified account cannot reach.

**`workspace_slugs`** — `workspaceId` (foreign key to `workspaces`, `ON DELETE CASCADE`), `slug`, + audit. A coven's current address and at most one old one, the address it held before its latest rename, so a link to that old address still finds the coven. The unique index `workspace_slugs_slug_unique` is partial on `deleted_at IS NULL`: an address belongs to one live coven at a time, and a deleted coven's rows are soft-deleted with it, freeing its addresses. The foreign key cascades because tests hard-delete covens. Writes are named (`insertWorkspaceSlug`, `updateWorkspaceName`), not the generic ones. The migration backfills one row per live coven from `workspaces.slug`, and the standard and demo-coven seeds write the same row. A rename records the previous and the new address and soft-deletes the coven's other rows; renaming back swaps the two and reuses the row. A new address gets a number only when another live coven's current address or a reserved word is that address. Another coven's old address is free to take: the claim soft-deletes that row in the same transaction, and its redirect ends. A deleted coven's addresses are free.

| Role                    | Can                                                                                     |
| ----------------------- | --------------------------------------------------------------------------------------- |
| Steward (`owner`)       | Everything, plus manage members and delete the workspace                                |
| Practitioner (`member`) | Read and write ingredients and grimoire, and see who else is in the workspace           |
| Observer (`viewer`)     | Read only. With notes deferred to v2 there is no exception — an observer writes nothing |

At least one steward (`owner`) per workspace, enforced on demotion and removal.

**`invitations`** — `id`, `workspaceId` (nullable), `email` (nullable), `role` (nullable), `siteRole` (nullable), `tokenHash`, `expiresAt`, `acceptedAt`, `acceptedBy`, `declinedAt` (nullable), `revokedAt`, `note` (nullable), `kind`, `batchId` (nullable), `position` (nullable), + audit. Every invitation, in two tiers as `ingredients` is. Owned by `coven`, since it mostly names a workspace; the admin tier reaches it as admin curation reaches `ingredients`. It is marked `namedWrites`, so only its named insert, accept, accept by id, decline and revoke write it. Full rules: claude-docs/db/invitations.md, "Invitations" (`design-decisions/auth.md`, "Workspace and admin invitations are one two-tier table").

- A row naming a workspace and a role invites into that coven. A row with neither is a **site-tier** invitation, which grants the site role its `siteRole` names, `curator` or `admin`. A CHECK pairs the two, `(workspace_id IS NULL) = (role IS NULL)`, and `role IS NULL OR role IN ('viewer', 'member')` makes `owner` invitable on neither tier. `invitations_site_role_tier`, `(workspace_id IS NULL) = (site_role IS NOT NULL)`, and `invitations_site_role_invitable` (admits `curator` and `admin`, never `user`) do the same for the site role.
- `role` accepts `viewer` (Observer) or `member` (Practitioner) only; steward is deliberately not invitable, so no future code path can widen it by accident. The Steward role is granted afterwards by an existing steward on the members page.
- An invitation never lowers a role: one is not sent to an address already holding its role or a higher one, and accepting one that an account has since outgrown stamps it and grants nothing.
- An invitation is **pending** until it is accepted, declined or revoked, or its `expiresAt` passes. **Declined** is the invitee's no, stamped from the account page; the decliner is the address the invitation was sent to, so there is no `declinedBy`. A declined invitation stays on the steward's list, marked declined whatever its expiry, until a steward removes it, which stamps `revokedAt` as Revoke does. `invitations_declined_coven`: only a coven invitation can be declined, since a keeper invitation is never listed to its invitee. `invitations_answered_once`: never both accepted and declined.
- `kind = 'card'` is a printed code bound to no address, coven or site role: `invitations_kind_shape` requires a card's `email`, `workspaceId`, `role` and `siteRole` to be null and an `address` row's `email` to be set; `invitations_kind_known` admits the two kinds; the two tier checks apply to address rows only. `batchId` groups the cards of one mint. A card's token is returned once, at minting, to the keeper who mints it, and is in no later response (`design-decisions/auth.md`, "An invitation card is a third shape of `invitations`"). One unique index on `token_hash` spans all three shapes, partial as every one is.
- Only the hash is stored, and the token is generated with a CSPRNG (`crypto.randomBytes`, never `Math.random`). The link is mailed to the invited address and appears in no response and no query. It is accepted only by a signed-in account whose verified email matches the invitation's. A coven invitation is also listed on the account page (`/account`, its Invitations section) to that same verified account and accepted there by id, under the same address match, ANDed in SQL, with `/coven` and the account menu linking to it; a keeper invitation is accepted by its link alone. Accepting also sets `canCreateWorkspace` on the accepting user, audited: someone vouched for by an existing member is an established user. Accepting a site-tier invitation is a grant through the admin role service, so it writes the ledger row, sets `canCreateWorkspace`, and is refused while keeper changes are paused.
- Each insert and revoke is scoped by the proof it is handed, a `Membership` filling and ANDing its workspace, a `SiteAdmin` writing and ANDing the null pair. The accept and the token read take no proof and match either tier. Each tier's pending list is read under its own proof, the coven's also holding the declined ones not yet removed. An invitee's own pending coven invitations, with the accept or decline of one by id, take no proof and match only while the session's user holds the invited address, verified. Policy stays in two services (who may invite, the pause, what accepting grants and where it lands), while the token, the expiry, the pending predicate, the accept and the revoke exist once.

**`card_invitation_attempts`** — `id`, `invitationId`, `userId`, `reason` (CHECK: `revoked`, `expired`, `accepted`), `attempts` (≥ 1), `lastAttemptedAt`, + audit. One live row per card, account and reason, counting a signed-in account's refused opens of a card link; owned by `coven` and marked `namedWrites`. Full rules: claude-docs/db/invitations.md, "Card attempts".

**`ingredients`** — `id`, `workspaceId` (nullable), `name`, `slug`, `canonicalName`, `nomenclature`, `identityKey` (generated), `description`, `elements[]`, `celestialBodies[]`, `zodiacSigns[]`, `colors[]`, `safetyNotes`, `toxic`, `seedKey`, `revision` (the counter `spells` carries, raised by one on every update, `integer NOT NULL DEFAULT 1`), + audit. An ingredient holds what every form of it shares, and each form it comes in is a row of `ingredient_variants` beneath it (below): Rosemary the herb and Rosemary the oil are one ingredient with two variants, not two ingredients each repeating the plant's description and correspondences. Folk names, substitutes and deities are child tables (`ingredient_folk_names`, `ingredient_substitutes`, `ingredient_deities`), not array columns. Folk names and deities belong to the ingredient and never to a variant, since a practice names and dedicates the plant, not a preparation of it. The row has no `form`, `form_id` or `canonical_key`.

`slug` is `slugify` of `name` and `canonicalName` where declared, joined by a space (`ingredientSlug` in `src/lib/slugify.ts`), unique per scope on partial indexes (`(slug) WHERE workspace_id IS NULL`, `(workspace_id, slug)`, both `AND deleted_at IS NULL`). It is a compendium entry's public address, `/compendium/ingredients/[slug]` (§9). The form is not in the slug, since one page shows every form: Rosemary is `rosemary-salvia-rosmarinus`. The slug follows a relabel and a change of formal name, and a compendium entry's old slug goes to `retired_ingredient_slugs`.

One table, two tiers, so `spell_steps` (and v2's `notes`) point at a single kind of thing:

- `workspaceId IS NULL` — the global compendium. Everyone reads; only keepers and curators write. Every entry declares a `nomenclature`, and one naming a system carries a `canonicalName`.
- `workspaceId` set — local to that workspace. Stewards and practitioners there write it. Invisible elsewhere. A formal name is optional here, so story 29's one-field stub still saves.
- No user path promotes local to global. That is v2's suggestion flow.

`name` is the display label and nothing more; identity is the formal name alone (below). A variant's `form` is free text drawn from a keeper-curated vocabulary (`ingredient_forms`), not an enum, and its `formId` records the curated row a member picked, when one was.

**Correspondence lists.** `elements[]` is an array of the closed enum `ingredient_element` (earth, air, fire, water, spirit). `celestialBodies[]`, `zodiacSigns[]` and an ingredient's deities are lists of free text drawn from keeper-curated vocabularies (`celestial_bodies`, `zodiac_signs`, `deities`), not closed sets: the project serves a wide range of practices and any closed list refuses some (modern practice reads Uranus, Neptune and Pluto beside the traditional seven; others read Earth, Chiron, the asteroid goddesses or the lunar nodes; sidereal practice adds Ophiuchus; no list of gods covers every practice that names one). The entry form offers the curated values as autofill, and on a coven's ingredient a value off the list is written as readily as one on it. A picked deity records its curated row beside its name (`ingredient_deities`); a celestial body or sign records its text alone. `colors[]` is free text with no vocabulary and no suggestions.

Each of the four lists follows one set of rules:

- An ingredient carries as many entries as its practice gives it: a herb ruled by Venus and the Moon carries both.
- Each entry is trimmed and a blank entry dropped. A repeat but for case and spacing is refused at the repeat; for `elements` the repeat is refused rather than dropped, since the form offers only the elements not yet chosen, so a repeat comes from another caller and refusing it says so.
- A list left with no entries is an absence, stored as null rather than `{}`, and an edit replaces a list whole.
- **Each list keeps the order entered.** A practice that names a ruling planet beside a lesser one writes the ruler first, a Postgres array keeps its order for nothing, and nothing in the app sorts an entry list. The form lets a member move an entry by pointer or keyboard alone.
- The field names are `celestialBodies`, `zodiacSigns`, `colors` and `elements` in the database, the shared schema, GraphQL and the form: `zodiacSigns` because one entry is a sign and the zodiac is all of them (as the vocabulary is `zodiac_signs`); `colors` as `colorDark` is, since code says _color_ and prose _colour_.

**`ingredient_variants`** — `id`, `ingredientId`, `form`, `formId` (nullable), `description`, `elements[]`, `celestialBodies[]`, `zodiacSigns[]`, `colors[]`, `safetyNotes`, `toxic`, + audit. One form an ingredient comes in, carrying what is particular to that form: Rosemary's oil variant holds the oil's own description and safety note, while the plant's description, correspondences, folk names and deities stay on the ingredient. `form` is never blank (`CHECK (btrim(form) <> '')`), and `formId` is the curated `ingredient_forms` row a member picked for it. A variant owns its own references, substitutes and categories, through a variant column on `reference_links`, `ingredient_substitutes` and `ingredient_categories`. It carries no `workspace_id`: it takes its ingredient's tier, as every child of an ingredient does, and is read only beneath its parent, never by a bare id (CLAUDE.md rule 5).

**A variant is unique per ingredient and folded form**: a partial unique index on `(ingredient_id, lower(btrim(form)))`, so `Oil` and `oil` are one, and two ingredients may each have an Oil. A second unique index on `(id, ingredient_id)` is the target of the composite foreign keys below, which a partial index cannot be; it is the one named exception to "every unique index is partial" (CLAUDE.md rule 4) and reserves nothing the primary key does not. A partial index on `form_id` serves the vocabulary's reads of which entries pick a form, and a trigram index on the unaccented `form` and `description` serves the search's reach into a variant (§9).

**Inheritance is a union: a variant adds to its ingredient and never removes.** A reader of one form sees the ingredient's correspondences, categories, substitutes and references plus that variant's own. Nothing on a variant overrides or hides the ingredient's, so no read merges two values and no list needs an "explicitly none" flag. When a property is not true of every form — a safety note only the oil carries, an element only the root is worked with — the curator moves it off the ingredient onto the forms it is true of. Rosemary keeps `Fire` and its folk names on the ingredient; "dilute before it touches the skin" sits on the oil variant alone.

**The toxic flag is the one exception: it does not union.** `ingredients.toxic` and `ingredient_variants.toxic` are each a yes/no, default no, and each says only what its own row says: the ingredient's is on when any part of it is poisonous, to people or to pets, and a form's when that form is. To whom, and how, is the safety notes' to say. A preparation toxic when the plant is not (an essential oil, say) flags its form, and whether the ingredient takes the flag too is the curator's call. Turning either flag leaves the other as it was. A reader of one form reads the form's flag, never the ingredient's in its place; the only read that combines the two is the search's toxic filter, which reads both to choose which entries to list (`design-decisions/ingredients.md`, "Search facets take lists and a toxic setting").

**An ingredient with no variant is information only.** It can be read, searched, and linked as a substitute, but nothing is held or laid in a jar without a form: a stock row and a linked spell layer each name a variant. An entry with no form is flagged on the keeper's to-do list on the compendium page, and the entry form asks for at least one.

**A variant's children name both ids.** `inventory_items`, `spell_steps`, `ingredient_categories` and `ingredient_substitutes` reach a variant through a composite foreign key `(variant_id, ingredient_id) → ingredient_variants (id, ingredient_id)`, so a row cannot name one ingredient beside another ingredient's variant. The key is `MATCH SIMPLE`, which skips the check when either column is null, so a table whose `ingredient_id` may be null beside a variant pairs the two with a CHECK. `reference_links` names a variant through its own column instead, as it names every sourced row.

**Variants are written inside the ingredient's save**, never by mutations of their own. The input is the whole entry, its variants and their children included, and one `withAudit` transaction writes it: a variant the input names by id, or else by its folded form, keeps its row, so a form can be respelt in place; one no longer sent is soft-deleted, its children left for a restore; a new one is inserted. Separate variant mutations would need a second tier check, a second collision mapper and a cache expiry per variant, and a save would take several round trips (`design-decisions/ingredients.md`, "An ingredient and its forms").

**`ingredient_folk_names`** — `id`, `ingredientId`, `name`, + audit. The regional and common names an ingredient also answers to. A partial unique index on `(ingredient_id, lower(name))` and a trigram index on `name`. Uniqueness is per ingredient, **deliberately not global**: several unrelated plants claiming "Cat's Claw" is precisely the thing being documented. A child table rather than an array column because `array_to_string` is `STABLE` on Postgres 18, so is legal in neither an expression index nor a generated column. GraphQL exposes them flattened as `folkNames: [String!]!` (§7).

**`retired_ingredient_slugs`** — `id`, `ingredientId`, `workspaceId` (nullable, the ingredient's scope), `slug`, `retiredAt`, `expiresAt` (generated: the UTC calendar date of `retiredAt` plus 180 days, at 00:00 UTC), + audit. A slug a compendium entry has moved off. While unexpired, and while no entry holds the slug, it answers a 308 to the entry's current slug. Another entry may take it (the admin confirms ending the redirect first) and the page then at the address links to the entry that moved until the window closes; the entry itself may take its own old slug back at once. Expiry is a predicate on `expiresAt`, so the redirect ends at midnight UTC with nothing scheduled, and a lapsed row is hard-deleted by the next compendium write. A coven ingredient's slug follows its name and retires nothing, since no route reads it (`design-decisions/graphql.md`, "The compendium is public and search-indexable", `design-decisions/data.md`, "A taker ends a retired slug's redirect, once confirmed").

**`ingredient_substitutes`** — `id`, `ingredientId`, `variantId` (nullable), `substituteId` (nullable), `substituteVariantId` (nullable), `name` (nullable), + audit. What an ingredient may be replaced with, one row per entry: a link to another ingredient or a name typed for one that is not entered, never both and never neither.

- `CHECK (num_nonnulls(substitute_id, name) = 1)` holds the exclusive-or, and `name` is non-blank. A substitute typed without picking an ingredient is stored as its text, without a warning, and is never resolved into a link behind the member's back.
- A CHECK keeps a row from substituting for itself, refusing only the same ingredient _and_ the same variant (`substitute_id = ingredient_id AND substitute_variant_id IS NOT DISTINCT FROM variant_id`), so Rosemary's leaves may stand in for its stems.
- **An ingredient lists a substitute once**: the same ingredient linked twice, or the same name typed twice in any case, is refused. Two partial unique indexes carry it, in the shapes `spell_steps` gives its links and custom names (`(ingredient_id, substitute_id)` where `substitute_id` is set; `(ingredient_id, lower(name))` where `name` is set), each split by `variant_id IS NULL`, so a form lists a substitute once and the ingredient as a whole once. The shared schema refuses the repeat first, at its position. A typed name equal to a linked ingredient's label is not a repeat: one is text and the other a link. A plain partial index on `ingredient_id`, and one on `variant_id`, serve the reads by parent and by form.
- **A substitute is for a form, and a form's link names a form.** `variantId` names the variant a row is a substitute _for_, null on a substitute for the ingredient as a whole; `substituteVariantId` names the form of the linked ingredient, held to it by the composite key and to a link by `CHECK (substitute_variant_id IS NULL OR substitute_id IS NOT NULL)`. Any variant of any ingredient may substitute for a form, and a form's linked substitute always names one (a name needs none); the ingredient's own list may still link an ingredient whole (`design-decisions/ingredients.md`, "A form's linked substitute names a form"). A form may be stood in for by leaves for stems, or a different plant altogether, because the substitution lists the sources give are organised by use, not by form. A matching form is therefore a ranking, not a rule: the picker lists an entry holding the same form first, then one holding a form of the same form group, then the rest.
- **A substitute links only what its ingredient's readers may read.** A compendium entry's substitute links another compendium entry and nothing else; a coven ingredient's links a compendium entry or an ingredient of its own coven, never another coven's. The compendium is public and indexable, so a link from an entry to a coven's ingredient would publish that ingredient's name, and that it exists, to every reader, where a coven's contents are private (§8). A CHECK cannot read another row, so the service holds the rule: the linked id must be one the writer's own scope reads (the compendium and the proof's coven for a coven write, the compendium alone for a keeper's), and anything else is refused as a field error pathed to the entry, asserted by direct id. The read ANDs the same rule.
- **A link to a deleted ingredient is kept, and shown by its last name.** When the linked ingredient is soft-deleted, by its coven or, for a compendium entry, by a keeper, the row stays a link and reads as plain text under the name the ingredient was deleted with, with nothing to follow. Turning the row to text at the delete would make a keeper deleting a compendium entry rewrite rows in every coven that linked it (access to a coven's ingredients a keeper never has, asserted by test), and v2's restore (§13) could not bring the link back; dropping the link would make a recorded substitute vanish without a word. The cost is a named finder that reaches a soft-deleted ingredient, which skips the linked ingredient's `deleted_at` and no other filter, pinned by `tests/guards/soft-delete-finder-guard.test.ts` (CLAUDE.md rule 4). As with a spell layer, a link already reaching a deleted ingredient survives a save of its parent, and a new link cannot reach one. Nothing reads from a linked ingredient back to the rows linking it, and an ingredient is never hard-deleted, so no index leads on `substituteId`.
- **The rows carry the full audit spread and are soft-deleted**, as `ingredient_folk_names` does, rather than the four stamps and a hard delete. A substitute is content, a member's text or claim about a practice, not a link between two curated rows: nothing joins _through_ the table to another, and a tombstone is what v2's history and trash view restore. The table adds its own `set_updated_at` trigger line. A save brings the live rows to the list sent: an entry still listed keeps its row, one no longer listed is soft-deleted, a new one is inserted, and a save that changes nothing writes nothing.
- **Substitutes read alphabetically, by the name each shows** (the linked ingredient's label, its last once deleted, or the typed text), as folk names do, not in the order entered as the correspondence lists are. The read sorts; nothing stores an order.
- **The picker searches with `ingredientSuggestions`** (§7): the live ingredients of the compendium and the current coven, exactly what a coven's substitute may link, matched as the compendium search matches, best first. `commonNameSuggestions` answers with names, not ids; `possibleDuplicates` compares whole names at 0.4, so a prefix finds nothing; `workspaceIngredients` lists only what a coven holds. A compendium entry's form reads `compendium(query)`, which holds what its substitutes may link and nothing else.

**`ingredient_deities`** — `id`, `ingredientId`, `deityId` (nullable), `name`, `position`, + audit. The deities an ingredient corresponds to, one row per entry: a name, and, when the member picked a curated row, a link to it beside the name.

- `name` is held on a linked row as well, in the curated row's spelling, so a link whose deity is soft-deleted still reads as its name: the repository's filter drops the deity and nothing else, so it needs no named finder (CLAUDE.md rule 4). `CHECK (btrim(name) <> '')`. A deity typed without a pick is stored as its text and never resolved into a link. Two live deities may share a name (Greek and Roman Hecate), and the link tells a pick of one from the other, which the text alone could not.
- **A save brings the live rows to the list sent.** An entry is a curated deity's id or a typed name, exactly one. A pick made anew must name a curated deity, live and under a live tradition, and its name is written in that deity's spelling, refreshed on a later save if the deity is renamed. A row still listed keeps its row and takes its new `position`, one dropped is soft-deleted, and a new one is inserted. **A held pick is kept**, as a substitute's link is: once its deity or tradition is retired it reads as its name, and a save sending back that name, or the deity's id, keeps the row, its link and its name, rather than tombstoning it for an unlinked twin (`design-decisions/ingredients.md`, "Reading and writing the picked form and deities").
- **Deities keep the order entered**, unlike substitutes: a deity is a correspondence beside celestial bodies, zodiac signs and colours, which keep theirs. The order is `position`, unique among an ingredient's live rows (a partial unique index on `(ingredient_id, position)`, which also serves the read by parent in order, as `spell_steps_spell_id_position_unique` reads a jar). It is checked per row, so a reorder moves the live rows through a scratch offset, as a spell's layers do.
- **An ingredient lists a deity once**, by two partial unique indexes in the shapes substitutes have (`(ingredient_id, deity_id)` where linked; `(ingredient_id, lower(name))` where `deity_id IS NULL`). The shared schema refuses the repeat first, at its position. Links to two same-named deities are not a repeat, nor is a typed name equal to a linked deity's.
- The rows carry the full audit spread and are soft-deleted, as substitutes are and for their reason, with their own `set_updated_at` trigger line.

## References — where a row's information came from

Every compendium entry, and every curated vocabulary row whose content was drawn from somewhere (a deity's filing and spellings, a celestial body's rulerships), records its sources as `references` rows linked to it. A correspondence is a claim about a practice and a safety note a claim about a plant; the compendium is public and indexable, read by people who cannot ask whose claim it is, so an entry carries its sources the way a reference work does (`design-decisions/ingredients.md`, "A reference is one source, kept once, rendered in Chicago form").

- A reference is one source (a book, a chapter, an article, a web page) kept **once** and linked from every row it supports, so a book fifty herbs cite is one row edited in one place. A row's references read as a bibliography in **Chicago Manual of Style, bibliography form**, because the works this compendium draws on are humanities works written in it and a reader can take a citation from here to a library. The style is a rendering of stored fields, never a stored string.
- **Two tiers, as ingredients are.** `references.workspace_id` is nullable: a compendium reference is admin-written and public, a coven's its own. A row links only what its readers may read, so a compendium entry or vocabulary row links compendium references alone and a coven's ingredient the compendium's or its own coven's.
- **A compendium entry may save with none.** An unsourced entry is the admin's second to-do list beside the `unknown` nomenclature: requiring a source would block the quick entry story 29 protects and hang a fixture on every seeded entry, where a filter makes the gap visible without refusing the row.
- **A curated seed list records its sources in its seed doc first**, in the same form (the astrology and deity docs do), and the seed writes them as rows. A vocabulary that is the project's own design, the categories and the forms, cites nothing.

**`references`** — `id`, `workspaceId` (nullable), `kind`, `authors`, `title`, `container`, `contributors`, `edition`, `volume`, `issue`, `series`, `place`, `publisher`, `published`, `pages`, `host`, `url`, `modified`, `accessed`, `note`, `seedKey`, + audit. One source per row, in the `ingredients` module.

- `kind` is the enum `reference_kind` (`book`, `chapter`, `article`, `entry`, `web_page`) and decides which rendering the row gets, so the renderer is total over every row the table admits: `chapter`, `article` and `entry` require a `container` (the book, the journal, the reference work), `web_page` requires `url` and `accessed`, `accessed` needs a `url`, and `url` is absolute http(s). `title` is the one required text.
- Every other column is text as Chicago prints it (`authors` with the first inverted and any role, "Smith, William, ed."; `volume` a number on an article and a statement on a book, "2 vols."; `published` at whatever precision the work gives, "Summer/Autumn 2013") except `modified` and `accessed`, which are `date`s. `note` is a short annotation rendered after the citation in parentheses. Nothing is structured further: a name grammar would invert "Snorri Sturluson", and a date column would refuse a season.
- Every text column has a non-blank CHECK. There is no unique index on its fields: nothing short of a librarian identifies a source, and an index on any subset would refuse a legitimate second edition. The seed recognises its own rows by `seedKey`, the citation it rendered at insert.
- What is typed is tidied as it is parsed, and a date with no year, a non-numeric page, an address with no named host and a day not yet come are refused beside their fields, in the shared schema the form and the service both run (claude-docs/db/references.md, "Formatting and checks").

**`reference_links`** — `id`, `referenceId`, `ingredientId`, `ingredientVariantId`, `deityId`, `deityTraditionId`, `celestialBodyId`, `zodiacSignId` (each sourced column nullable), `locator`, + audit. One link from one source to one sourced row: `CHECK (num_nonnulls(ingredient_id, ingredient_variant_id, deity_id, deity_tradition_id, celestial_body_id, zodiac_sign_id) = 1)`. A new sourced table costs a column, an index and the widened CHECK (a `DROP CONSTRAINT` under its sidecar), where a join table per entity costs a table, a trigger line and a finder each time.

- A variant is a sourced row too, so a form's own sources (a monograph on the essential oil, say) link the oil variant and not the plant. A reader of the page sees them as notes numbered in page order, the ingredient's first and then each form's own, and one bibliography of every source once. The categories and the form vocabulary are the project's own design and are not sourced.
- `locator` is the one thing a link carries ("p. 112", "chap. 13"): free text, nullable and non-blank. A source cited at several places in one row names them all in its one locator, "pp. 12–19, 40; chap. 3". A bibliography entry names the work, so the renderer leaves the locator out and the page shows it in the note that cites the work.
- Full audit spread and soft-deleted, as a substitute is: a link is content, and v2's history restores it. One live link per reference per row, held by a partial unique index per sourced column, each leading on the sourced id so it also serves the read by row, so no plain parent index is built. None leads on `referenceId`: nothing in v1 reads from a reference back to its links, and a reference is never hard-deleted.
- **A link names only what its row's readers may read**, the tier rule substitutes follow, held in the service since a CHECK cannot read the reference's row: a compendium entry's or a vocabulary row's link names a compendium reference, a coven ingredient's the compendium's or its own coven's, and anything else is a field error pathed to the entry. A compendium reference is written under the `SiteAdmin` proof alone and a coven's under its `Membership`, whoever links it: a member who links a compendium reference reads it and cannot change it. An edit reaches every row linking the reference, and a compendium-tier edit revalidates the `compendium` tag.
- **References read alphabetically by the rendered citation**, as a bibliography does, so nothing stores an order. The key is the plain citation less a leading quotation mark and an initial _A_, _An_ or _The_, compared case- and accent-insensitively; the citation exists only in TypeScript, so the service sorts, as `folkNamesOf` does. The picker's search, `referenceSuggestions` (§7), matches `authors`, `title` and `container` as the compendium search matches names, scoped to the compendium and the current coven (rule 7 filters in SQL, which cannot match a rendered citation).
- **Nothing deletes a reference in v1.** The writers are the ingredient form (`createReference`, `updateReference`, and the links inside the ingredient's own save, brought to the list sent as folk names are) and the seed; the admin vocabulary pages gain no field. Unlinking soft-deletes the link. A reference whose every link is gone stays live and suggested: a source is reusable, and sweeping it would delete a coven's record, or a keeper's seeded row, behind their back. Should a reference be soft-deleted, its links are untouched and the read joins live references only, so it leaves every bibliography and a restore returns it. This is the opposite of the substitute rule, because a deleted reference is a retracted source where a deleted ingredient is a fact a member recorded, and it needs no cross-tier write and no new rule-4 exception.
- **Owned by `ingredients`, not a sixth module.** The link table keys into `ingredients`, which `vocabulary` may not import, and the links are written inside the ingredient's transaction, which a module above `ingredients` could not be called from without a cycle. A vocabulary row's references are therefore read from `ingredients`, as `User.memberships` is added from `coven`, and the compendium-tier rows join the tier seam's extraction unit (claude-docs/modules.md, "The tier seam").

**The citation is rendered, never stored**, by one pure function, `renderCitation` in `src/lib/citation.ts`, beside `slugify` because the page, the picker, the service's sort and the seed's test all call it and it imports no module. It returns parts, each `{ text, italic }`; `citation` on the wire is the parts joined, plain, and a surface that shows italics renders the parts itself.

- The kind supplies the default italics (a book's title, a chapter's or article's container) and a writer marks any other with `_…_` in `title`, `container` or `note`, under CommonMark's rule that an underscore inside a word is not a mark, so `Greek_Mythology` in a URL is not italic; `url` is never parsed, and a marked span inside a field already italic renders roman. An entry's container and a web page's site are roman unless marked. A test joins the parts back with `_` around the italic ones, which is the seed doc's own Markdown, so the seed's and the page's tests compare strings.
- Optional fields drop cleanly; each part ends in a period it does not already carry, a quoted title takes its period inside the quotes, a date prints "October 6, 2026", and `Place: Publisher, Published` loses each missing piece with its punctuation. Per kind (examples in claude-docs/db/references.md, "The renderer"):
  - **`book`** — Authors. _Title_. Contributors. Edition. Volume. Series. Place: Publisher, Published. Host. Last modified Modified. Accessed Accessed. URL. (Note)
  - **`chapter`** — Authors. "Title." In _Container_, Contributors, Pages. Edition. Volume. Series. Place: Publisher, Published. Host. Last modified Modified. Accessed Accessed. URL. (Note). Contributors print as a chapter prints them, "edited by …", after its book.
  - **`article`** — Authors. "Title." _Container_ Volume, no. Issue (Published): Pages. Host. Last modified Modified. Accessed Accessed. URL. (Note). Without a volume: _Container_, Published, Pages.
  - **`entry`** — Authors. Container, Edition, under "Title." Contributors. Place: Publisher, Published. Host. Last modified Modified. Accessed Accessed. URL. (Note)
  - **`web_page`** — Authors. "Title." Container. Publisher. Published; last modified Modified. Accessed Accessed. URL. (Note). "Last modified" is capitalised when it stands without a published date.

## Vocabularies

**`ingredient_forms`** — `id`, `name`, `slug`, `groupId`, `description`, `seedKey`, + audit. Global only, keeper-curated, shaped like `categories` and managed at `/curator/forms` under the same gate as `/curator/categories`. It is the vocabulary behind a variant's `form`. The groups answer the question `form` asks, _what kind of thing are you holding?_, rather than how it was made: three by source (did it grow, did it come off a creature, was it dug), and three by state for what has lost its source's shape (does it flow, does it hold a shape of its own, or neither). A powdered mineral is therefore a _powder_, and the ingredient's name says what it was. There is no _Other_: a value that fits no form is typed as free text on a coven's ingredient, and is added to the vocabulary before a compendium entry may hold it, where a catch-all row would let it stand unnamed. `description` is required and non-empty, so a curated value explains itself (`rootBark` can say "the bark of the root, not the stem").

The seed's source is the table below, and the seed's test parses it, so the two cannot drift.

| Group     | Forms                                                                                                                                              |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Botanical | herb, root, bark, flower, leaf, seed, fruit, peel, stem, wood, sap, resin, pollen, whole, berry, nut, bud, petal, thorn, moss, mushroom, bulb, pod |
| Animal    | bone, claw, feather, shell, tooth, fur, shed, egg, horn, antler, scale, skin, pearl, coral, specimen                                               |
| Mineral   | crystal, salt, stone, clay, sand, earth, metal, chalk                                                                                              |
| Substance | powder, ash, wax, charcoal, pigment, ointment, soap, incense, paste                                                                                |
| Fluid     | liquid, oil, water, vinegar, spirit, concoction, ink, syrup, honey, perfume                                                                        |
| Curio     | curio, candle, cord, coin, nail, key, charm, bead, bottle, poppet, paper, mirror, bell                                                             |

**Uniqueness on a vocabulary table is on the `slug`, and a display name carries no constraint** (the rule for all four vocabulary tables). On `ingredient_forms` it leaves one gap open deliberately: two live forms may both be called "Wax", one an _animal_ part (the comb as it came from the hive) and one a _substance_ (rendered and set), and since a variant's `form` stores the string, the text alone cannot tell them apart. The autofill resolves it: a suggestion carries its group and is rendered with it ("Wax (animal)", "Wax (substance)"), and the pick is kept as the variant's `formId` beside the text, so the entry form shows its group beside the text until the text is edited away from it. A typed one says no more than its text. A unique index on the name would have decided for the admin that wax is one thing. **So a form's slug is its name and its group** (`formSlug(name, group)` in `src/lib/slugify.ts`, `wax-substance`) and a deity's its name and its tradition's, where every other vocabulary row's is its name: a slug of the name alone would put both "Wax" rows at `wax`. It follows a rename and a regrouping, and a group's rename moves its forms' slugs. The seed takes only the substance sense and leaves the other row for a keeper to add. A schema test asserts the pair of same-named rows is accepted, so the gap stays a decision.

**`ingredient_form_groups`** — `id`, `name`, `slug`, `description`, `seedKey`, `icon` (nullable, enum `form_group_icon`), + audit. Global only, keeper-curated. Seeded with the six above, and open to a seventh without a migration. No colour: form groups section an autofill dropdown, they are not chips. A group carries instead which of six icons stands for it (`botanical`, `animal`, `mineral`, `substance`, `fluid`, `curio`), shown beside every form filed under it wherever forms are listed; NULL means the generic salt spoon. It is an enum rather than a CHECK, so a seventh icon is `ALTER TYPE … ADD VALUE`, expand-only (`design-decisions/ui.md`, "Form icons: on the group, with a generic"). Groups render alphabetically by `name`, so there is no order column. A form's slug names its group, so renaming a group moves the slug of every live form under it, and deleting one first moves its live forms to another live group the admin picks, each re-slugged there; the forms stay curated, so no ingredient's pick is orphaned or rewritten (`design-decisions/ingredients.md`, "The admin group pages: where a deleted group's rows go").

**A variant's `form` is `text`, not a foreign key to this table**, and the whole design rests on that. An FK would make an unlisted value impossible to write; text lets the variant index fold the string and lets a member write `rhizome` before anyone has curated it. To a coven the curated set is a _vocabulary_, not a constraint: the entry form's autofill offers curated values first, each labelled with its group, then in-scope values already in use that are not in it, visibly distinguished. Soft-deleting a vocabulary row rewrites no coven's variant: the value stays on its rows and moves into the in-use bucket.

**A pick is recorded beside the text.** A variant's `form_id` is a nullable foreign key to this table, set only when a member picked a curated row and never resolved from typed text; `form` is `NOT NULL`, so a link never stands without its text. The text stays the value: the variant index folds `form` and not `form_id`, so an uncurated value stays writable and a form is never told apart by an id. A link to a soft-deleted row, or to one whose group is soft-deleted, reads as no link (the repository's filter drops the row), so the variant reads as its text, with no soft-delete exception.

- **A save writes a pick only of a curated form**, live and under a live group, with `form` text folding to its name, written in that name's spelling. A `formId` naming anything else is refused beside it, never a 23503, and text that is not the picked form's name is refused beside `form` rather than overwritten. A save sending no `formId` clears the column and keeps the text, so a pick retired since reads, and saves, as typed text. Two variants of one ingredient, one picked as each Wax, still fold to one form, so the second is refused, since the index stays on the text (`design-decisions/ingredients.md`, "A picked form or deity is recorded beside its text").
- So a vocabulary a member writes is text, with an optional link beside it to the curated row picked; `ingredient_deities` holds the same for deities.

**The compendium is held to the vocabularies.** Each of a compendium entry's variant forms and each of its deities is a pick of a live curated row (a form under a live group, a deity under a live tradition), and its `celestialBodies` and `zodiacSigns`, and each variant's, each name one. The compendium services refuse anything else as a `ValidationError` beside the field (`['variants', i, 'form']`, `['variants', i, 'formId']`, `['celestialBodies', i]`, `['zodiacSigns', i]`, `['deities', i]`). A curated form or deity typed rather than picked is refused as an uncurated one is, and a deity pick the entry already holds is refused once its deity is retired, where a coven's is kept. A celestial body or sign matches as the suggestions fold, `lower(btrim(value)) = lower(name)`, and every value is stored in its row's own spelling. The columns stay text, since a coven writes them freely, so the rule is the service's and not a key's, nor Zod's, since it reads the database. Nothing is lost: the keeper who writes the compendium curates the lists, so a missing value is added there first. It is what makes the autofill headings true ("From Compendium" for a curated value, "From Coven" for one only in use), and why the admin pages carry no curation to-do list of values in use: under it there could be none. Folk names and colours have no curated list and stay free text in both tiers.

**The rule holds after the write as well as at it.** Soft-deleting a curated row a live compendium entry holds is refused, naming the entries, until the keeper edits them, and so is soft-deleting a deity tradition with such a row under it; deleting a form group moves its forms to another live group instead. Renaming a row carries the new spelling onto every live compendium entry holding it, in the same transaction (one set-based statement). A form or a deity is held by the entries that pick it; a celestial body or sign is held by an entry's variants too, and only while it is the last live curated spelling of its value, since two live rows may share a name. A coven's rows never block a delete and are never rewritten (`design-decisions/ingredients.md`, "The compendium holds curated values alone").

**`celestial_bodies`** and **`zodiac_signs`** — each `id`, `name`, `slug`, `description`, `seedKey`, `position` (a nullable integer), + audit. Global only, keeper-curated, managed at `/curator/celestial-bodies` and `/curator/zodiac-signs` under the same gate as `/curator/forms`. People read this vocabulary as Celestial Bodies, since most of its nineteen values are not planets; the table, the code and GraphQL all say celestial bodies (`design-decisions/ingredients.md`, "The planets are Celestial Bodies wherever a person reads them"). They are the vocabularies behind `ingredients.celestial_bodies` and `ingredients.zodiac_signs`, and stand to those columns as `ingredient_forms` stands to `form`, without the recorded pick: the columns stay `text[]` with no foreign key and no link beside them, the tables feed the autofill, a value off the list stays writable on a coven's ingredient, a compendium entry holds curated values alone, and deleting or renaming a row treats the two tiers as a form's does. The seed writes each name in title case as the proper noun it is (`North Node`), its slug derived.

| Vocabulary       | Values                                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Celestial bodies | sun, moon, mercury, venus, earth, mars, jupiter, saturn, uranus, neptune, pluto, chiron, ceres, pallas, juno, vesta, lilith, north node, south node |
| Zodiac signs     | aries, taurus, gemini, cancer, leo, virgo, libra, scorpio, ophiuchus, sagittarius, capricorn, aquarius, pisces                                      |

Earth, Chiron, the lunar nodes and Ophiuchus are listed because practices use them, not because a source gives them herb correspondences: "few sources" is not a reason to refuse a practice. A body a practice reads that is not listed (Eris, Sedna) is typed as free text on a coven's ingredient, and is curated before a compendium entry may name it. The sources are in `claude-docs/compendium/astrology-vocabulary-seed.md`.

- **One tier, not two.** Neither vocabulary has a group (nineteen bodies and thirteen signs section nothing), so there is no group table and no colour, and the seed is a flat helper rather than the two-tier one the forms and categories share. **Two tables rather than one with a `kind` column**: a celestial body query that forgot its `kind` predicate would offer Scorpio for `celestialBody`, and two tables make that query unwritable rather than merely wrong.
- **`description` is required and non-empty**, as on `ingredient_forms`, and it is search surface: the suggestion query matches it as well as the name, and a name match outranks a description match. A description names the words a reader reaches for (Lilith's says _Black Moon_, the nodes' say _Rahu_ and _Ketu_, Ophiuchus's says _Serpentarius_). The same requirement is why a value cannot be curated in one click.
- **`position` orders the search facets, nothing else.** The seed gives the twelve signs their calendar places with Ophiuchus 13, and the Sun, the Moon and the planets their solar-system places, Sun 1 to Pluto 11; every other row is null and sorts after them by name, and a row a curator adds has no position. The admin lists stay alphabetical by `name`, and the autofill ranks by match.
- **The two readers are scoped differently.** A member's autofill offers curated values first, then uncurated values already in use in the compendium and the current workspace. The keeper's reads the compendium tier only (the live entries holding a value, which refuse its delete and take its rename), since a keeper has no access to any workspace's ingredients: a workspace's uncurated `Eris` never reaches `/curator/celestial-bodies`, and a workspace's `Moon` never blocks a delete. A value is uncurated when its trimmed, lower-cased form matches no live row's lower-cased name. A value in use is an entry of a list, so both readers unnest the column first, and a value counts once however many lists hold it.

**`deities`** — `id`, `name`, `slug`, `description`, `traditionId`, `seedKey`, + audit; and **`deity_traditions`** — `id`, `name`, `slug`, `description`, `seedKey`, + audit. Global only, keeper-curated, managed at `/curator/deities` and `/curator/deity-traditions` under the same gate as `/curator/forms`. They are the vocabulary behind an ingredient's deities and stand to them as `ingredient_forms` and `ingredient_form_groups` stand to `form`: each deity stays text with the picked row recorded beside it in `ingredient_deities`, a value off the list stays writable on a coven's ingredient, a compendium entry holds curated deities alone, and deleting or renaming a row treats the two tiers as a form's does. `traditionId` is a key because only a keeper writes it.

- **Grouped by tradition**, one tradition per deity: a suggestion reads "Hecate (Greek)", as a form's reads "Wax (Substance)", because every tradition has its thunder god and its Moon. A god several traditions honour is filed under one, and the description names the others.
- **A tradition is a people or a religion, never a region**: Irish, Welsh, and Gaulish & British rather than Celtic; Taoist, Chinese Buddhist and Chinese folk rather than Chinese; Akan, Igbo and Yoruba rather than African. A member reads the tradition a practice names and no living religion is filed as a region's footnote, at the cost of a few traditions of one or two rows.
- **`description` is required on both**, and on a deity it is search surface: it carries the tradition and the other spellings a reader types (_Hekate_, _Freyja_, _Guanyin_). Traditions list alphabetically and carry no colour.
- The seed is thirty-five traditions and 216 deities, too many rows to be specification: the list, its order and its sources are in `claude-docs/compendium/deity-vocabulary-seed.md`.
- The readers are the celestial bodies' two, scoped the same way. A deity is curated only while its tradition is live, so deleting a tradition first moves its live deities to another live tradition the admin picks, as deleting a form group moves its forms.
- **A deity's slug is its name and its tradition's**, `deitySlug(name, tradition)` (`hecate-greek`), for the reason a form's carries its group: one god honoured under two traditions is two rows. A tradition's rename and a move re-slug its deities as a form group's do its forms (`design-decisions/ingredients.md`, "The admin deity pages: the slug, the tradition's delete, one form").

**`deity_other_names`** — `id`, `deityId`, `name`, + audit. The other names a deity answers to: a spelling or a by-name a source uses, such as Ashtoreth for Astarte or Woden for Odin. It has the shape of `ingredient_folk_names`, is soft-deleted the same way, and is global and keeper-curated as `deities` is. `CHECK (btrim(name) <> '')`; a partial unique index on `(deity_id, lower(name))`; a trigram index on `name` serves the deity picker. A name is an other name only when the vocabulary calls it the same deity: a related but separate figure, such as Luna beside Selene, stays a deity of its own. A site keeper or curator writes the names on the deity form, as a list saved whole. The service refuses one name twice on a deity, or on two live deities of one tradition, naming the deity that holds it, since no constraint can reach the tradition through the deity. The deity picker finds a deity by an other name, the entry page and the admin list show them, the deity seed loads them from `DEITIES[].otherNames`, and a compendium entry file may name a deity by one of them.

**`categories`** — `id`, `name`, `slug`, `description`, `groupId`, `seedKey`, + audit. Global only, keeper-curated. Suggestions in v2. Seed list in §6. `description` is required and non-empty, here and on `category_groups`, as on `ingredient_forms`. **No colour of its own**: a category wears its group's pair of hexes, which is what §6's grouping is for (eight families rather than 63 individually-tinted chips).

**`category_groups`** — `id`, `name`, `slug`, `colorDark`, `colorLight`, `description`, `seedKey`, + audit. Global only, keeper-curated, managed at `/curator/category-groups`. §6 seeds eight; a keeper may add a ninth, and groups render alphabetically by `name`.

- The two colours are the chip colour every category in the group wears, one per theme, stored as hexes on the row rather than looked up from a build-time token, since a group created at runtime cannot have a Sass variable. Two columns rather than one because every seeded group is tuned separately per theme (a dark-theme colour is lifted, a light-theme colour darkened), and one hex cannot clear 4.5:1 on both soot and parchment without being mud on at least one.
- Each is validated on write against its own theme only, and against the harder of that theme's two surfaces: `colorDark` against the dark card, `colorLight` against the light page. An unselected chip's label is the colour itself on whatever surface holds it, a page or a card, so clearing the harder one clears both. The keeper sees both swatches while picking.
- The pair keeps one hue to within 10°, so a chip changes shade with the theme and never family; the admin page fills the second colour from the first.
- Deleting a group first moves its live categories to another live group the admin picks, in the same write, so no category is left under a deleted group.

**`seedKey`, on every table the reference seed writes** — the eight vocabularies above, `references` and `ingredients`. Nullable text, under a partial unique index `(seed_key) WHERE seed_key IS NOT NULL AND deleted_at IS NULL`: the identity the seed gave a row when it wrote it (a vocabulary row's slug at insert, a reference's rendered citation), never changed after, and null on a row a keeper or a member writes. A reseed runs on every deploy that touches a seed file, and recognising its rows by what a keeper can change (a slug that follows the name, a citation that follows its fields) would put the original back beside every row a keeper renamed or edited. No input, service or GraphQL field names it. The scenarios key by fixed id on fresh databases and `reference_links` by two ids, so neither carries one (`design-decisions/data.md`, "A seeded row keeps the key the seed gave it").

**Two group tables, not one with a `kind` column.** A shared table would let `categories.groupId` point at a form group: the failure would be invisible until something rendered, where two tables make it a foreign-key violation. This is the _impossible-versus-absent_ distinction the rest of this document turns on.

**`categories.groupId` and `ingredient_forms.groupId` are foreign keys, unlike a variant's `form`**, deliberately. A variant's `form` stays free text because a _member_ writes it and must be able to write `rhizome` before a keeper has curated it. Only a keeper writes a category or a form, and only a keeper writes the groups they point at, so no one is blocked by a group that does not exist yet, and integrity is worth having since a typo'd group silently empties a chip section. The rule generalises: a vocabulary a member writes is text, a vocabulary only a keeper writes is a foreign key.

## Assignments, stock and the grimoire

**`ingredient_categories`** — `ingredientId`, `variantId` (nullable), `categoryId`, + audit stamps. No `deleted_at`, hard-deleted. A row with no `variantId` files the ingredient as a whole, and one with a `variantId` files that form alone ("for anointing" on the oil) while still carrying the `ingredientId`, so a reader asking what an entry is filed under gets the union of the two for nothing. A result card shows that union: the ingredient's own categories first, then those carried only by its live forms, drawn as the plain chip with a dashed border and a tip naming the form. The share card shows the ingredient's own categories, or its forms' when it has none. Two partial unique indexes carry the key, `(ingredient_id, category_id) WHERE variant_id IS NULL` and `(variant_id, category_id) WHERE variant_id IS NOT NULL`, so a category is filed once on the ingredient and once at most on each form. A second, non-unique index leads on `categoryId` so the pair is readable in both directions ("what is this ingredient tagged with", "what is in this category").

**`spell_categories`** — `spellId`, `categoryId`, + audit stamps. Composite primary key on the pair, no `deleted_at`, hard-deleted. A second, non-unique index leads on `categoryId` ("which spells are tagged for prosperity"; §9's grimoire list is filterable by category). `spell_steps` gets no such index because no v1 feature lists spells by ingredient: which directions are actually queried decides the indexes.

**`inventory_items`** — `id`, `workspaceId`, `ingredientId`, `variantId`, `quantityOnHand`, `unit`, `unitDimension`, `lowStockThreshold`, `source`, `acquiredDate`, + audit.

- A stock row is of one form: `variantId` is `NOT NULL`, since a jar of Rosemary holds the herb or the oil and never the plant in the abstract, and the composite key holds it to the row's ingredient. Unique on `(workspaceId, variantId) WHERE deleted_at IS NULL`, so a coven may hold Rosemary herb and Rosemary oil as two rows, and starting a jar of a form it already holds is refused beside the form, never answered with the held jar or topped up into it.
- Units cover three dimensions, metric and imperial in each: **weight** — mg, g, kg, oz, lb; **volume** — ml, l, tsp, tbsp, fl oz (UK), fl oz (US), cup (the two fluid ounces differ by about four per cent, so both are stored); **count** — piece, drop, pinch. `unitDimension` is stored alongside `unit` rather than derived at each call site, so a query can filter or group by it; a row whose dimension contradicts its unit cannot be written. One shared module owns the unit-to-dimension map, imported by both the Zod schema and the conversion library.
- `lowStockThreshold` is written onto the row at creation with a dimension-appropriate default (3 for count, 10 g for weight, 15 ml for volume, converted into the row's unit), not left null and defaulted at read time (claude-docs/db/stock.md).

**`spells`** — `id`, `workspaceId`, `title`, `intent`, `jarDescription`, `sealWaxColor`, `moonPhase`, `dayOfWeek`, `note`, `status` (`draft` | `complete`), `visibility` (`private` | `workspace`), `revision`, + audit.

- `title` is nullable while the spell is a draft, because it is saved as it is typed before it has a name, and `CHECK (status <> 'complete' OR title IS NOT NULL)` requires it to complete; a draft with no title reads as "Untitled Spell".
- `visibility` has the column default `workspace`, but every write sends it and the builder sends `private` for a new spell: the autosave would otherwise share a draft 3 s after the first keystroke, for good (`design-decisions/grimoire.md`, "A new spell starts private").
- `revision` is a counter, `integer NOT NULL DEFAULT 1`, that the shared trigger function `bump_revision()` raises by one on every update; a write that names the revision it read is refused when the row has moved on, which is how two people editing one spell are told apart (`design-decisions/grimoire.md`, "Long forms autosave, and edits of one row can conflict").
- `note` is a free-text line on the spell as a whole; the ritual itself is its steps, below.

**Visibility.** A `workspace` spell is readable by every practitioner, observers included. A `private` spell is readable only by its author, against stewards too. Stewards and members create and edit; observers create and edit nothing, including private spells.

**A complete spell never goes back to a draft**: `updateSpell` refuses a save naming `draft` on a complete spell with an explaining `Forbidden`, "A complete spell cannot go back to a draft. Duplicate it to get a draft copy.", since reopening would undo the workings and the visibility lock below. A change to a complete spell goes through a copy (`duplicateSpell`, story 82).

**Visibility is one-way once a spell is complete.** A `draft` may be shared and made private again as often as its author likes (`design-decisions/grimoire.md`, "A draft's visibility moves either way; a complete spell's only widens"). A `complete` spell may be widened from `private` to `workspace` and never narrowed back; the rule reads the status the row holds before the write, so the save that completes a shared draft starts the lock. Once a finished spell is part of the shared grimoire the others have read it and may have built on it; hiding it afterwards would retract something they were relying on. Widening is a gift, narrowing is a retraction, so only one is allowed. Enforced in the service and asserted by test (§8, §11), not merely absent from the UI. The rule governs visibility, not existence: a shared spell can still be deleted.

**`spell_steps`** — `id`, `spellId`, `position`, `body` (nullable), `ingredientId` (nullable), `variantId` (nullable), `name`, `form`, `quantity`, `unit`, + audit. A spell's recipe is one ordered list of steps, and a step is an instruction (`body`), an ingredient laid in the jar (a layer), or both (story 80). Soft-deleted, unlike the other two join tables, and so keyed on a surrogate `id`: a removed step's tombstone must not go on holding its place, so `(spellId, position)` is a partial unique index over live rows. A step has no per-ingredient note: `body` is the one text on a step (`design-decisions/grimoire.md`, "The step note is retired (PR #1308)"; `design-decisions/grimoire.md`, "A spell's recipe is one ordered list of steps").

- A layer references the ingredient and the form laid, not the inventory item, so a saved spell survives running out of something. A linked layer names a variant (`CHECK ((ingredient_id IS NULL) = (variant_id IS NULL))`, the composite key holding it to the ingredient), so a jar records which form went in, and the layer's safety notes, categories and correspondences are the ingredient's plus that form's.
- **A spell does not lose an ingredient that is deleted.** A spell is a recipe that keeps what went into its jar, so a layer keeps reaching the ingredient it links after that ingredient is soft-deleted, by a keeper or by its coven: it is shown as it was, its categories still count toward the spell's derived categories, and its safety notes still warn. A layer leaves a spell only when a user removes it, which is a soft delete too. The spell stays editable: a layer already linking a deleted ingredient survives a save, and a new layer cannot link one. History is v2's, where a layer pins the ingredient's exact revision (§13, "Edit history"; `design-decisions/data.md`, "A spell keeps the ingredients it holds, deleted or not").
- **A step names at most one ingredient, linked or custom, and is never empty.** `ingredientId` points at an `ingredients` row; `name`, with an optional free-text `form` (not a foreign key, as a variant's `form` is not), is a one-off ingredient written for this jar alone. `CHECK (num_nonnulls(ingredient_id, name) <= 1)` keeps the two apart and `CHECK (num_nonnulls(ingredient_id, name, body) >= 1)` refuses an empty step (the same `num_nonnulls` idiom `design-decisions/data.md`, "Notes use real foreign keys and one generic history trigger" keeps for the deferred notes model). `quantity` and `unit` describe an ingredient, so a CHECK refuses them on an instruction-only step; `body`, `name` and `form` are checked non-blank; `CHECK (ingredient_id IS NULL OR form IS NULL)` keeps `form` off a linked row, where it would contradict the variant the layer names.
- One partial unique index over live rows carries the one identity that stays unique: `(spellId, lower(name)) WHERE ingredient_id IS NULL`, one custom name per jar. A linked form is not unique: a jar may lay one form in several steps, the oil at two points of the recipe (`design-decisions/grimoire.md`, "A spell may lay one form in several steps"). The coven's supply of a form is judged on the sum of its steps.
- A custom row lives inside its spell and shares its visibility. It is never an `ingredients` row: it does not appear on the workspace's ingredients page, is offered no compendium match, contributes nothing to derived categories, has no safety note to surface and no stock to be held or not held. Reusable is a different thing and already exists: a workspace-local `ingredients` row with only a `name` (story 29). What reads through the table (derived categories, on their way to `ingredient_categories`) reads it by `existsIn`, which filters a removed layer by construction (`design-decisions/grimoire.md`, "A custom, one-off spell ingredient is a row in `spell_ingredients`, not a table of its own").

**Workings.** A spell is the recipe; a working is the record of one time a coven made it (claude-docs/db/grimoire.md, "Workings"). Three tables hold it.

**`spell_workings`** — `id`, `spellId`, `status` (`draft` | `complete`, the `working_status` enum), `workedOn` (a date, when it was made), `completedAt` (null while a draft), `note` (nullable), `visibility` (the `spell_visibility` enum, default `workspace`), + audit, soft-deleted. `createdBy` is who recorded it. Index on `(spell_id, worked_on DESC) WHERE deleted_at IS NULL`. Two CHECKs: a `note` is never blank, and `(status = 'complete') = (completed_at IS NOT NULL)`, so a complete working always says when and a draft never does. `workedOn` may be after today on a draft; completing is refused until it is not, judged against the latest calendar day anywhere (today at UTC+14), so no one is refused on their own today. A working of a deleted spell is unreachable because it is read through its spell's filter (`findManyInSpell`), not because the delete cascades.

**`spell_working_participants`** — `id`, `workingId`, `userId` (nullable), `name` (nullable), `position` (the order entered), + the four audit stamps and no `deleted_at`. `CHECK (num_nonnulls(user_id, name) = 1)`: a participant is a member or a typed name, never both or neither. A name is never blank. Unique on `(working_id, user_id)` and on `(working_id, lower(name))`, plain unique indexes since the table has no `deleted_at`: a removed participant is a deleted row.

**`spell_working_deductions`** — `id`, `workingId`, `spellStepId`, `inventoryItemId`, `quantity`, `unit` (the stock row's unit), `shortfall` (`0` when fully met), + the four audit stamps. Written once at completion and never edited, so it has no `deleted_at`. Index on `working_id`.

**Notes are deferred to v2.** The first-class `notes` model and its `private | workspace | public` visibility are specified in §13. Nothing in v1 writes a note, and no v1 table references one. `notes` is the reason the ingredient detail page (§9) is built to take a section beneath it without restructuring.

## Ingredient identity — the formal name

Common names are regional and ambiguous. "Cat's Claw" is _Uncaria tomentosa_, _Uncaria guianensis_, _Senegalia greggii_, _Dolichandra unguis-cati_ — and a literal claw from a cat. "Snakeroot" is five unrelated plants. A safety note hung on an ambiguous label is the dangerous case, because comfrey and foxglove leaf are confused in the real world: `safetyNotes` is the argument for demanding a formal name in the curated tier. So identity sits on the formal name alone, with each form an ingredient comes in held beneath it as a variant (`ingredient_variants`, above).

Five columns are easy to confuse, so the division is stated once:

| Column          | Answers                                                  | Constrained                                                                                   | Why it is that way                                                                                                                                                                                                                                                                        |
| --------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`          | What is this called **here**?                            | free text; unique per workspace, not unique in the compendium                                 | The display label, freely relabellable                                                                                                                                                                                                                                                    |
| `canonicalName` | What is its **formal name**?                             | free text, no format regex                                                                    | Identity. Required in the compendium, optional in a workspace                                                                                                                                                                                                                             |
| `nomenclature`  | **Which naming system** does that formal name belong to? | enum, `NOT NULL`, no default                                                                  | Separates "no system names this" from "one does and nobody looked it up"; drives rendering, since a scientific name is italicised and a mineral or chemical name is not; makes the compendium requirement enforceable                                                                     |
| `form`          | What kind of thing are you **holding**?                  | free text on a variant, autofilled from `ingredient_forms`; unique per ingredient once folded | Not identity: valerian root and valerian leaf are one ingredient, _Valeriana officinalis_, with two variants, each carrying its own description, safety note and references. Open-ended, so no enum and no foreign key on the text; a pick records its curated row beside it, in `formId` |
| `elements[]`    | Which classical elements does it **correspond to**?      | a list of an enum of five values                                                              | A **correspondence**, beside `celestialBodies[]`, `zodiacSigns[]`, `deities[]` and `colors[]`, not identity. Earth/air/fire/water/spirit is a closed, fixed set: the opposite of `form`                                                                                                   |

**`nomenclature` names which naming system the formal name belongs to, not which rank within it.** `canonicalName` is the most specific accepted name _at the granularity the entry exists at_, written in that system's conventional form. Without that rule the crystal drawer collapses: amethyst, citrine, rose quartz, smoky quartz, agate, carnelian and onyx are all the species _Quartz_, and the compendium could hold exactly one.

| Entry                                | `nomenclature` | `canonicalName`                     |
| ------------------------------------ | -------------- | ----------------------------------- |
| Amethyst                             | `mineral`      | `Quartz var. amethyst`              |
| Selenite                             | `mineral`      | `Gypsum var. selenite`              |
| Lapis lazuli — a rock, not a species | `mineral`      | `Lapis lazuli`                      |
| Hidcote lavender                     | `botanical`    | `Lavandula angustifolia 'Hidcote'`  |
| A cat's claw                         | `zoological`   | `Felis catus`, with `form = 'claw'` |
| Graveyard dirt                       | `none`         | — no system names it                |

Where a system gives two entries the same most-specific name (sea salt and Himalayan pink salt are both `Sodium chloride`), they are one identity and so one entry in a tier; that is the answer, not a bug.

A coven's cupboard names the compendium entries it holds in a row of its own, `workspace_compendium_entries`, rather than guessing from matching names (claude-docs/db/workspace-compendium-entries.md).

**No format regex on `canonicalName`.** Real names include `Artemisia spp.`, `Lavandula angustifolia 'Hidcote'`, `subsp.` and `var.` ranks, and author citations like `Salvia officinalis L.`; a binomial regex rejects valid names, which is the silent guess §11's `unitConvert` rule forbids. There is **no external identifier column** (POWO, IPNI, GBIF, CAS, IMA) in v1: nothing reads one, taxonomic ids churn, and a nullable text column is purely additive later.

`nomenclature` has seven values:

| Value        | Governs                                                                | Examples                                                                                                               |
| ------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `botanical`  | ICN                                                                    | _Uncaria tomentosa_, _Laurus nobilis_, _Artemisia spp._                                                                |
| `fungal`     | ICN — see the note below                                               | _Amanita muscaria_, _Ganoderma lingzhi_                                                                                |
| `zoological` | ICZN                                                                   | _Apis mellifera_ (beeswax), _Felis catus_ (a claw)                                                                     |
| `mineral`    | IMA species and varieties, plus rocks, mineraloids and natural glasses | `Quartz var. amethyst`, `Lapis lazuli`, `Moldavite`                                                                    |
| `chemical`   | IUPAC, or the accepted chemical name                                   | `Sodium chloride`, `Potassium nitrate`, `Sulphur`                                                                      |
| `unknown`    | —                                                                      | There **is** a formal name and its classification is unsettled. `canonicalName` may hold it, unconfirmed, or be null   |
| `none`       | —                                                                      | No system names this: graveyard dirt, moon water, a coffin nail, black salt (a _preparation_). `canonicalName IS NULL` |

**`fungal` splits on organism, not code, deliberately.** Fungi are governed by the ICN alongside plants, so `fungal` is the one value with no nomenclatural code of its own. It is kept because curators shelve mushrooms separately from herbs. Do not "correct" it away.

`unknown` earns its place because `none` is a **positive claim**. Without `unknown`, a keeper's only truthful option for an un-researched plant is to lie into `none`, and `WHERE nomenclature = 'unknown'` is a findable curation to-do list. **An `unknown` entry may carry its formal name**: a member who knows the Latin but not whether a lichen is botanical or fungal records the name and leaves the classification open. Rows on the to-do list then need a classification chosen, and those without a name need the name looked up too; the formal-name column tells them apart, so the list stays one. This is the project's own idiom: `unitConvert` refuses a cross-dimension conversion as an explicit result rather than guessing.

`nomenclature` is `NOT NULL` with no default. `identity_key` is `text NOT NULL GENERATED ALWAYS AS (lower(COALESCE(canonical_name, name))) STORED`; Postgres refuses a direct write and Drizzle omits generated columns from `$inferInsert`, so TypeScript refuses first. Every function in the expression is `IMMUTABLE` and no enum cast is involved, so the column is legal. Two CHECKs hold the coupling:

- `ingredients_nomenclature_declares_canonical_name`: `nomenclature = 'unknown' OR (nomenclature = 'none') = (canonical_name IS NULL)`. A biconditional everywhere but `unknown`, asserted in both directions: `none` carrying a formal name is rejected, any of the five named kinds carrying none is rejected, and `unknown` saves either way.
- `ingredients_canonical_name_not_blank`: `canonical_name IS NULL OR btrim(canonical_name) <> ''`.

The form is not in the key: _Valeriana officinalis_ root and leaf are one identity, one entry with its correspondences held once and two variants. The cat's-claw vine and the literal claw never needed the form to tell them apart, since _Uncaria tomentosa_ and _Felis catus_ are different formal names. A variant's form is folded in its own index, `lower(btrim(form))`, which collapses `Root Bark` onto `root bark`; `rootbark` is left to the autofill, as with folk names.

**The missing default binds code paths, not users.** The workspace-local Zod variant supplies `nomenclature: 'none'` when the formal-name field is blank, and `'unknown'` when a formal name comes without a classification, so story 29 and "saving with only a name succeeds" hold; the compendium variant makes the admin answer. The kind-to-name coupling is enforced in Zod as well as in the database, so the CHECK is never what a user sees.

Three partial unique indexes hold identity and labels:

- `ingredients_compendium_identity_key_unique` on `(identity_key) WHERE workspace_id IS NULL AND deleted_at IS NULL`.
- `ingredients_workspace_identity_key_unique` on `(workspace_id, identity_key) WHERE workspace_id IS NOT NULL AND deleted_at IS NULL`.
- `ingredients_workspace_label_unique` on `(workspace_id, lower(name)) WHERE workspace_id IS NOT NULL AND deleted_at IS NULL`. Label uniqueness exists in the workspace tier only: inside one drawer an ambiguous label is a mistake, not a distinction.

In the compendium four rows may display "Cat's Claw", told apart by their formal names. A unique _constraint_ cannot carry `WHERE deleted_at IS NULL`, and `NULLS NOT DISTINCT` exists only on constraints, so the two tiers stay separate partial indexes. A tier holds one Rosemary, whatever forms it comes in; a second form is a variant of it.

**Relabelling is safe, with one exception:** identity is stable under relabelling only for rows that _carry_ a formal name. A `none` row's key **is** its label, so relabelling it changes its key. Because `COALESCE` merges two namespaces into one key, a `none` entry whose _label_ equals another entry's _formal name_ collides, and the raw error names a column the admin never filled in; the write translates it into a readable message naming the colliding entry, on `name`, which the form shows beside that field.

**Display name: no new column.** `name` remains the display label in both tiers. Choosing a folk name as the display name is a **swap** between `ingredients.name` and one `ingredient_folk_names` row, a two-value exchange in one transaction. Absent a selection, `name` is prefilled from `canonicalName` at write time, matching `lowStockThreshold`'s idiom of writing the default onto the row. A swap on a compendium row is **global**: a workspace cannot hold its own display preference for a shared entry without another table, and the UI says so before the swap.

**A coven's cupboard is what it chose, and nothing hides on a name match.** The cupboard is its own entries plus the compendium entries it names in `workspace_compendium_entries`. A compendium entry is there because the coven added it or stocked a form of it, never because an own entry shares its name. An own entry and a same-named compendium entry are both offered in the picker, each in its own group, and both listed in the coven's list once the cupboard names the compendium one. `createStock` stores a jar on the form the member picked, and a jar of a compendium form puts its entry in the cupboard when it is not there already (`design-decisions/ingredients.md`, "A coven's cupboard names the compendium's entry, rather than hiding it").

The own entry's page shows the compendium entries it may be, as a display only: it offers no way to convert the entry into one, because linking an own entry to the compendium waits for v2 (§13, "Link to the Compendium"). The match is on identity, and on the label only when the own entry declares no formal name, case-insensitively: a local stub has only its label to go on, while an entry that _declared_ an identity is not matched to a differently-identified row for sharing a label. It ignores forms. The match is read in SQL (rule 7), by `findCompendiumMatchesByName` under `compendiumMatchesOf`.

| Own entry (label / formal name) | Compendium                | The own entry's page                                                               |
| ------------------------------- | ------------------------- | ---------------------------------------------------------------------------------- |
| Mugwort / —                     | Mugwort / _A. vulgaris_   | "Similar in the Compendium", listing the entry as one it may be                    |
| Cronewort / _A. vulgaris_       | Mugwort / _A. vulgaris_   | "In the Compendium" — labels differ, identity matches                              |
| Mugwort / _A. vulgaris_         | Mugwort / _A. absinthium_ | nothing — different plants                                                         |
| Graveyard dirt / `none`         | Graveyard dirt / `none`   | "Similar in the Compendium"                                                        |
| Cat's Claw / —                  | Cat's Claw ×5             | "Similar in the Compendium", three then See All — the five the fuzzy warning flags |

A workspace-local ingredient may share a label, and an identity, with a compendium entry. Forbidding the collision would block someone who disagrees with a keeper's correspondences from keeping their own version.

**Entry-time lookups are permission-scoped, and that is a leak rather than a nicety.** When someone types a common name or a form, the field suggests from the compendium and the current workspace only, never another workspace, and both halves are scoped: the suggested **strings** as well as the attribution list of which in-scope ingredients already claim them, each shown with its formal name so the ambiguity is visible at entry. A naive implementation gathers distinct values globally and scopes only the attribution, which reveals that another workspace holds the string. `ingredient_forms` is global and keeper-curated, so its rows need no scoping; the in-use values outside it do. A curated form suggestion is shown with its group, "Wax (substance)", because the vocabulary permits two live rows to share a display name. The common names in use are the display names and folk names of in-scope entries, and a claiming entry with no formal name is shown by its label rather than dropped. Picking a suggestion writes the string into this ingredient's own folk-name row; it links no records.

**A curated form is matched on its description as well as its name.** The vocabulary is deliberately short, one row per kind of thing, so `ointment` covers what a reader may call a salve or a balm. Each row's description carries the words it stands in for, the suggestion query matches them, and the row is offered under its own name. **A name match always outranks a description match**, so typing `wax` offers _Wax_ above _Candle_, and a description match is only ever offered, never filled in automatically. Only the curated vocabulary is searched this way; an in-use uncurated value has no description.

## Two kinds of spell category

`spell.categories` is what you **intend** the spell to do. The union of its ingredients' categories is what it is **composed of**. Conflating them is a bug.

The spell builder shows both side by side, flagging intent categories with no ingredient backing them ("tagged for prosperity but nothing in the jar carries it") and ingredient categories outside the stated intent ("mugwort adds psychic work — intended?"). That comparison is what makes assigned categories worth having.

## Fuzzy duplicate warning

`pg_trgm` is available on Neon, as is `unaccent`, the design's only other extension: it folds the compendium search's accents (§7's `compendium(query:)`) through an `IMMUTABLE` wrapper and expression indexes (claude-docs/db/compendium-read.md, "The compendium read").

One multicolumn index, `CREATE INDEX ON ingredients USING gin (name gin_trgm_ops, canonical_name gin_trgm_ops)`, serves a query on either column alone, plus `ingredient_folk_names`' own trigram index.

Debounced on the create form's name field. Returns compendium and in-workspace matches above 0.4 similarity on `name`, on `canonicalName`, or on any of the ingredient's folk-name rows.

**The threshold is set explicitly, and the match uses the `%` operator.** `similarity(a, b) > 0.4` is a function call the planner cannot answer from a trigram index, so it sequentially scans `ingredients`; only the operators (`%`, `<->`) are indexable. But `%` alone uses `pg_trgm.similarity_threshold`, which defaults to **0.3**, not 0.4. So the threshold is set per transaction and the predicate stays an operator:

```sql
SET LOCAL pg_trgm.similarity_threshold = 0.4;
SELECT … WHERE name % $1 ORDER BY similarity(name, $1) DESC;
```

`%` filters through the index; `similarity()` only ranks what survives.

Every result carries its formal name: "Did you mean Cat's Claw?" is useless when it could mean five things. Nothing refuses the create on the server; the form renders "Did you mean Bay Laurel?" with a link plus a Create Anyway button, and a save is checked against the name it sends and held as an error on the name, focusing Create Anyway, until the warning is set aside. Merge tooling is v2.
