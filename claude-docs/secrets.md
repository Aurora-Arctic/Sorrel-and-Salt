# Secrets and environment variable matrix

Every secret this app needs, where it lives, and which environment reads it, so a deploy never discovers a missing one mid-flight. Nothing here is a value; this doc names variables, not secrets. No credential is needed to run tests locally or in a PR check: they run with the fixed placeholder `local-dev-not-a-real-secret` for `BETTER_AUTH_SECRET` where a production-mode build needs one at all ([`auth/config.md`](auth/config.md)).

**The OAuth variables read as empty in CI's pull, and that is harmless.** `scripts/assert-pulled-env.ts` reports every key a pull returned, with a classification and a length and never a value; the eight OAuth variables show as `empty` on the staging pull. Nothing reads them at build time: `/sign-in` and `/api/auth/[...all]` are dynamic routes, so `configuredProviders()` and `socialProviders()` run against the deployed function's own environment and not the pulled file. The real test is whether staging's sign-in page offers the providers and a real browser completes a sign-in through them.

**A Microsoft sign-in carrying an address that already has an account is refused** with a generic `account_not_linked` error, and that is the guard working. Microsoft sends no `email_verified` claim, so Better Auth treats its address as unverified and will not link it to an existing verified account; if it did, anyone who registered a Microsoft account under someone else's address would get into that account. Verify Microsoft with an address that has no account yet, or sign in another way and add Microsoft under `/account` ([`auth/admin-bootstrap.md`](auth/admin-bootstrap.md), "Linking a second provider").

**The GitHub OAuth App is no longer used.** Its client id and secret are not read by anything; deleting the App is a manual step on GitHub (Settings, Developer settings, OAuth Apps, the app, Delete).

**`ENABLE_IMPERSONATION` must never be set on Production.** It is one of two conditions, the other being Vercel's own `VERCEL_ENV`, so setting it there by mistake still registers nothing; even so, a mis-scoped variable must not be the only thing standing between a keeper and any user's session on the live site. On Preview, setting it turns impersonation on for staging and every hotfix preview at once, since they share the scope. Locally, `ENABLE_IMPERSONATION=true` in `.env.local` turns it on, because `VERCEL_ENV` is unset off Vercel.

**`BETTER_AUTH_SECRET` is one value across both environments**, because CI needs a readable copy of it and one shared secret is one thing to keep in step rather than two. A separate Preview value is safer in general (a leaked preview secret that also signs production sessions is a forged login); revisit this at the public launch.

- **The current value is short and low-entropy.** Better Auth says so in every build log. Regenerating it with `openssl rand -base64 32` invalidates every existing session, which is free before launch and expensive after: do it before the site is public.
- **Regenerating it later is a rotation, not a replacement.** The two-factor secrets and the providers' tokens are encrypted under it, so a new value goes in `BETTER_AUTH_SECRETS` beside the old one, and `BETTER_AUTH_SECRET` keeps the old value until nothing is written under it ([`auth/config.md`](auth/config.md), "Rotating the secret"). While `BETTER_AUTH_SECRETS` is unset it changes nothing.

**`ADMIN_BOOTSTRAP_EMAIL` is required.** Every build fails with `ADMIN_BOOTSTRAP_EMAIL is not set` without it, and `deploy.yml`'s pulled-environment assertion names it before `vercel build` does. Leave it **not Sensitive**: it names an address rather than granting anything, and a Sensitive variable reaches CI's `vercel pull` as the literal `[SENSITIVE]`, which the assertion refuses. Whoever can set it chooses the primary keeper, which is already true of `DATABASE_URL`.

- **Its account becomes admin at either of two events**, new account or existing: its next Google or Discord sign-in with a verified address, or its owner following the verification link our mail sends to it, from a browser signed in to that account. A Microsoft or Facebook sign-in never promotes by itself, so a steward with only those verifies by mail.
- **Changing it** promotes the new address at that address's next qualifying sign-in or verification. The previous primary keeper keeps `role: 'admin'` and simply stops being protected. An address its account has already verified is not verified again, so set it to one that can sign in through Google or Discord, or to an account that has not verified yet, or nobody will be protected.

**The mail variables are each scoped to the one environment that reads them, and none is read at build.** `src/lib/mail.ts` reads them when it sends ([`auth.md`, "First-party email verification and email delivery"](design-decisions/auth.md#first-party-email-verification-and-email-delivery), "Delivery"), so a deployed function takes them from the platform: `deploy.yml`'s pulled-environment assertion does not name them, they may all be Sensitive, and CI keeps no copy. The module refuses any transport but `resend` at `VERCEL_ENV=production` and any but `mailtrap-sandbox` at `preview`, so a variable copied into the wrong environment sends nothing and logs why, rather than mailing a stranger from staging. Local development, the compose `e2e` service and CI's Playwright job send to Mailpit instead, with `MAIL_TRANSPORT=mailpit` and `MAILPIT_URL` set in compose and `playwright.yml`, no secret; Vitest leaves it unset and the message is logged. **The Resend integration adds `RESEND_API_KEY` to every environment**: narrow it to Production, since a key present in Preview is live delivery one edit away.

**There is no `BETTER_AUTH_URL` row.** A single Preview-scoped value cannot be correct for both `staging` (a fixed alias) and a hotfix preview (its own ephemeral `hotfix-<slug>.sorrelandsalt.com` domain per open PR): Vercel's Preview scope applies to both, so staging's URL would leak into every hotfix preview's OAuth `redirect_uri`. `src/lib/auth.ts`'s `baseURL()` instead uses Better Auth's `allowedHosts` (wildcard-capable) to resolve the origin per request, scoped to `NODE_ENV=production`. An unrecognised `Host` header resolves to the production URL and is never reflected into a redirect.

**Hotfix previews cannot complete a real sign-in with any provider.** `allowedHosts` fixes only the URL this app tells a provider to redirect back to. Google, Discord, Facebook and Microsoft each require an exact, pre-registered redirect URI, and none can be registered for a hotfix slug that does not exist yet. A real sign-in works end to end on `staging` and Production only; a hotfix build that needs one exercises it against `staging`'s URL.

**`vercel pull` cannot give CI `DATABASE_URL` or `BETTER_AUTH_SECRET`, by design.** Both are Sensitive in Vercel, and a Sensitive variable cannot be read back: the pull writes `[SENSITIVE]` in place of the value. That is a non-empty string, so a check that asks only whether something is set lets it through, and no `vercel pull` flag changes it. So **CI keeps its own copy of exactly those two**, and nothing else:

| Value                | CI source                                          | Why                                                                 |
| -------------------- | -------------------------------------------------- | ------------------------------------------------------------------- |
| `DATABASE_URL`       | `DATABASE_URL_PRODUCTION` / `DATABASE_URL_STAGING` | Differs per target, so one named secret each                        |
| `BETTER_AUTH_SECRET` | `BETTER_AUTH_SECRET`                               | One value for both environments, so one secret                      |
| a hotfix preview     | the pulled `POSTGRES_URL`                          | Its Neon branch is created per deployment; no static value names it |

- **The runtime is untouched.** Deployed functions take their environment from the Vercel platform, not the pulled file. Only `vercel build` and `drizzle-kit migrate` read that file, and both run in CI, so the Sensitive flag stays on.
- **Named secrets rather than GitHub Environments**: an environment would add an input, an output and two `environment:` keys to the workflows to say what the secret's name already says. How the workflows select between the secrets is [`ci/deploy.md`](ci/deploy.md), "Deploy". `deploy.yml` and `migrate.yml` select between the same two secrets the same way, and must go on doing so.
- **The connection string lives in two places.** Rotating a database credential means changing it in Vercel _and_ in the matching GitHub secret. A drifted copy does not error: it migrates the wrong database silently, while the deployed app queries one that was never migrated and fails on its first query with a missing-column error. No CI step catches it, because CI never connects with Vercel's copy. After a rotation, sign in on staging before trusting it.
- **`--git-branch` stays on the preview pull**: the OAuth secrets exist only as `staging`-branch-scoped rows and are absent from an unscoped pull. The production pull passes no branch and must not, so each workflow pulls through two steps, one per target ([`ci/deploy.md`](ci/deploy.md) has the rejected single-step form).
- **A possible retirement of the CI copy of `DATABASE_URL`**: `GET /projects/{id}/connection_uri?branch_id=…` could give every branch its connection string from Neon directly, and `NEON_API_KEY`/`NEON_PROJECT_ID` are already set. It is not used because the snapshot key can create branches, and this would put it on every deploy's path, staging's included. It would not replace `BETTER_AUTH_SECRET`.

## How to set each row

These steps need your own Vercel, Neon, Google, Discord, Meta, Microsoft, Resend and Mailtrap accounts. The devcontainer has no Vercel CLI, and its `gh` token cannot list or set Actions secrets.

1. **Vercel env vars**: Vercel dashboard → Project → Settings → Environment Variables, or `vercel env add <NAME> production` / `vercel env add <NAME> preview` from a machine with the Vercel CLI linked to this project. `DATABASE_URL` for `staging` takes the branch-scoped form in the table above, not the plain `preview` one.
2. **Neon connection strings**: Neon console → the project → each branch (`main`, `staging`) → Connection Details. **`channel_binding=require` can stay, and is enforced.** The console puts it in by default, and a hotfix's Neon URL is written by Neon's Vercel integration, which rewrites it, so it cannot be deleted by hand. The driver reads it from the URL and refuses to connect unless the server offers channel binding, which Neon does (`src/db/connection-url.ts`; [`ci/deploy.md`](ci/deploy.md), "Deploy", has the failure it gives otherwise). Keep `sslmode=require`: the driver consumes that one, and it is what requests TLS.
3. **Google OAuth client**: Google Cloud Console → APIs & Services → Credentials → Create OAuth client ID (Web application). Authorised redirect URIs, on one client:
   - Local: `http://localhost:8000/api/auth/callback/google`
   - Staging: `https://staging.sorrelandsalt.com/api/auth/callback/google`
   - Production: `https://sorrelandsalt.com/api/auth/callback/google`
4. **Discord OAuth application**: Discord Developer Portal (discord.com/developers/applications) → New Application → OAuth2 → General. Register all three redirect URIs on the same application:
   - Local: `http://localhost:8000/api/auth/callback/discord`
   - Staging: `https://staging.sorrelandsalt.com/api/auth/callback/discord`
   - Production: `https://sorrelandsalt.com/api/auth/callback/discord`

   `DISCORD_CLIENT_ID` is the "Application ID" on the General Information page; `DISCORD_CLIENT_SECRET` is under OAuth2 → Client Secret ("Reset Secret" if none was generated). **Discord returns an email only for an account with a verified one.** For an unverified account the sign-in completes with a placeholder address, and `/account/email` asks for a real one (`src/lib/sign-in.ts`; `src/lib/auth.ts`).

5. **Facebook Login**: Meta for Developers (developers.facebook.com/apps) → Create App → use case "Authenticate and request data from users with Facebook Login" → Facebook Login → Settings, and set "Valid OAuth Redirect URIs":
   - Local: `http://localhost:8000/api/auth/callback/facebook` — Facebook permits plain `http://localhost` for development only; every other redirect URI **must be HTTPS**.
   - Staging: `https://staging.sorrelandsalt.com/api/auth/callback/facebook`
   - Production: `https://sorrelandsalt.com/api/auth/callback/facebook`

   `FACEBOOK_CLIENT_ID` is the App ID and `FACEBOOK_CLIENT_SECRET` is under App Settings → Basic → App Secret. **The app stays in Development Mode until Meta's App Review approves the `email` permission.** Until then only accounts added as testers, developers or admins under App Roles can complete a real sign-in; everyone else sees Facebook's own "app not set up" screen before reaching this app. Submit for review before relying on this provider for anyone outside that list. Facebook can also return no email (the same placeholder case as Discord).

   **Add `email` to the use case, even in Development Mode.** Better Auth always requests `email` and `public_profile`. If `email` has not been added under Use cases → Facebook Login → Customize → Permissions, Meta refuses the whole dialog with "Invalid Scopes: email" before the app role check runs. Adding it needs no review; review only decides whether people without an app role can grant it.

6. **Microsoft identity platform (Entra ID)**: Azure Portal → Microsoft Entra ID → App registrations → New registration.
   - **Supported account types must be "Accounts in any organizational directory and personal Microsoft accounts"**, the multitenant plus personal option. A single-tenant registration (the portal's default) rejects every personal Microsoft account at Microsoft's login screen whatever `tenantId` this app sends (`src/lib/auth.ts` sends `'common'`), so this is the one step that decides whether personal accounts work.
   - Redirect URIs, platform "Web":
     - Local: `http://localhost:8000/api/auth/callback/microsoft`
     - Staging: `https://staging.sorrelandsalt.com/api/auth/callback/microsoft`
     - Production: `https://sorrelandsalt.com/api/auth/callback/microsoft`
   - `MICROSOFT_CLIENT_ID` is the "Application (client) ID" on the registration's Overview page; `MICROSOFT_CLIENT_SECRET` is under Certificates & secrets → Client secrets → New client secret. Pick the longest expiry offered: it still expires and needs rotating before it does. Leave `MICROSOFT_TENANT_ID` unset unless the tenant is to be narrowed from `common`.
7. **GitHub Actions secrets**: this repo's Settings → Secrets and variables → Actions → New repository secret, or `gh secret set <NAME>` from a machine whose `gh` token has the Actions-secrets permission.
8. **Vercel dashboard settings** nothing in this repo drives: deploy previews off (Project → Settings → Git) and the `staging` alias to `staging.sorrelandsalt.com` (→ Domains). `vercel.json`'s `deploymentEnabled: false` stops the Git integration deploying anything itself; the CLI-driven `deploy.yml` is the only path.
9. **Resend (Production mail)**. The Vercel Marketplace integration creates the account and adds `RESEND_API_KEY`; what is left is the domain.
   1. Resend dashboard → Domains → Add Domain → `sorrelandsalt.com`.
   2. At the domain's DNS host, add every record Resend lists, exactly as shown: the DKIM `TXT` at `resend._domainkey`, and the SPF `MX` and `TXT` on the `send` subdomain. A DMARC `TXT` at `_dmarc` (`v=DMARC1; p=none;`) is optional and helps deliverability.
   3. Back in Resend, Verify, and wait for the domain to show Verified. Until it does, Resend refuses a send from that domain, and `src/lib/mail.ts` logs the refusal.
   4. In Vercel, edit `RESEND_API_KEY` down to Production only, and Sensitive.
   5. Add `MAIL_TRANSPORT` = `resend` and `MAIL_FROM` = `Sorrel & Salt <noreply@sorrelandsalt.com>`, both Production only.
10. **Mailtrap Email Sandbox (Preview mail)**. Captures and never delivers; the free plan takes 50 messages a month, shared by staging and every hotfix preview, and a send over the cap fails and is logged.
    1. Mailtrap → Email Sandbox → open the sandbox (create one if none exists). Its numeric id is the number in the page's URL.
    2. Settings → API Tokens → Add Token, with access to that sandbox.
    3. In Vercel, add `MAIL_TRANSPORT` = `mailtrap-sandbox`, `MAILTRAP_SANDBOX_TOKEN` = the token and `MAILTRAP_SANDBOX_ID` = the id, all Preview only, the last two Sensitive.
    4. Read a preview's mail in the sandbox's own inbox in Mailtrap.

## Every variable

The root `.env.example` names every environment variable `src/` and `scripts/` read, with a safe local value or a blank, and one comment line each saying what it is for. `npm run setup` copies it to `.env.local`. `tests/guards/env-example.test.ts` fails when the code reads a variable the file does not name, when the file names one the code never reads, or when a credential in it holds a value. The guard finds a read as `process.env.X` or `env.X`, as `requiredInProduction('X')` (`src/lib/env.ts`), and as a quoted name in `src/lib/social-providers-config.ts`, which reads by a name map; a read by a computed name anywhere else fails it.

Two rules shape the file:

- **Tool-set variables are not keys.** `NODE_ENV`, `PORT`, `CI`, every `VERCEL_*` and every `GITHUB_*` are set by the tool that runs the code (Next, Vercel, GitHub Actions or a test runner), never by a developer, so a key for one would only shadow it. The guard holds them as an allow-list and fails if the file names one.
- **A credential's value is blank.** Every key whose name says it holds a credential (`SECRET`, `TOKEN`, a trailing `_KEY` or `_PAT`) is blank, bar `BETTER_AUTH_SECRET=local-dev-not-a-real-secret`, the documented local value. Variables with no safe local value, such as `MAIL_FROM` and `MAILTRAP_SANDBOX_ID`, are blank too. A blank value reads as unset in every reader, and a value the shell or Docker compose sets wins over the file.
