# Component workshop

Where every standalone component renders in isolation, against the real tokens, without a page routed to it. It is Storybook (`@storybook/nextjs-vite`); what maps to what in the Claude Design sync, which reads the Storybook, is in [`ui.md`, "The component workshop moves from Ladle to Storybook"](design-decisions/ui.md#the-component-workshop-moves-from-ladle-to-storybook).

- **Component stories live at exactly `src/components/<Name>/index.stories.tsx`**, beside `index.tsx`, and mail stories at `src/emails/<name>.stories.tsx`. The `stories` globs in `.storybook/main.ts` also pick up `.storybook/*.stories.tsx`, for workshop-only pages the app never imports.
- **Every component and every email template has its story**, by review; no test guards it. A component that renders nothing has none: `CovenSwitchTargets` only tells the coven switcher which covens a page also opens in, so its story would be an empty frame.
- Stories are CSF3 (Storybook's story file format): a default-exported `meta` with the title, and one named export per story. They carry no test ids, no snapshots and no assertions; behaviour is the test's job, and the test lives at `tests/components/<Name>/index.test.tsx`.
- **A story pins a theme only when the theme is what it shows** (such as the contrast of a chip colour), with `globals: { theme: 'light' }`. Every other story is drawn in whichever theme the toolbar holds, so there is no Dark/Light pair of the same story. The eight group colours were tuned hardest against light, so check that theme first.
- **A story pins a width only when the width is the state it shows**, and there are no `Phone` stories. Narrow any story with the toolbar's viewport menu (375, 382, 600 and 700px), or from a link (below). The one pinned width is `SectionNav`'s `AdminOnAHiddenPage`, whose More-menu state exists only at tablet width: `globals: { viewport: { value: 'w700', isRotated: false } }`.
- **A story that needs `prefers-reduced-motion`** sets `parameters: { reducedMotion: true }` (see ".storybook/" below).
- **A story that opens a modal needs nothing special.** Storybook draws each story in an iframe of its own, so `Modal`'s top layer (`showModal()`) covers the story and not the sidebar.
- **A page component's story renders inside the page's real frame**: the `main` its route draws, with the same classes, such as `<main className="page-frame">` for `NotAuthorized` or `page-frame page-frame--narrow` for a form page. A story that drew the component bare would show a column the app never draws, since the frame sets the width and the spacing. The workshop's own frame is a `<div>` that takes `role="main"` only when the story has no `<main>` inside it (`.storybook/preview.tsx`), so a page holds one main either way. The accessibility checks in `tests/e2e/workshop/` skip `page-has-heading-one` because a component story has no page heading.
- **A story's title is a group, then the piece, both in title case.** Foundations is the one top-level exception: it has no group above it. The sidebar lists the groups in this order (`storySort` in `.storybook/preview.tsx`):
  1. **Foundations** stands alone at the top: the tokens and primitives every piece is drawn from. It is one story that follows the toolbar's theme.
  2. **A piece the app draws in one area goes under that area's group**, in the order a person meets them: **Pages** (a whole page with no area of its own: Welcome, the invitation page, Error Page, Not Authorized), **Sign In** (the panel, the sign-in methods and the provider mark), **Shell** (the bar and what sits in it: the account menu, the context row), **Account** (including `Account / Invitations Received`, `Account / Name Form`), **Coven** (including `Coven / Invitations Sent`, `Coven / Member List`), **Ingredients** (everything about the compendium and a coven's ingredients, in one flat group), **Grimoire** (everything about a coven's spells), **Admin** (`Admin / Invitations`, `Admin / Nav`, `Admin / User List`, `Admin / Group List`) and **Emails**.
  3. **A piece the app draws in more than one area goes under its kind**: **Forms** (fields and the controls inside them, and the Icon Tip; `Forms / Field`), **Feedback** (a notice, a skeleton and its fade, a spinner, and the loading and pending states: Main Body, Navigation Bar, Pending Link), **Layout** (frames, lists, tables, pagers and what every page carries, inside the shell or not: the theme switch and the impersonation banner, which the root layout draws on pages without the bar too; `Layout / Pager`), **Navigation** and **Surfaces** (what says or holds something on the page: a modal, an add icon, click feedback).
  4. **Titles name the piece as the screens do**, so `Coven`, never `Workspace` (`Coven / Leave Coven Button`); the file and component names stay as they are.
  5. **A story is named for its state.** A piece with several states has one story, `States`: a grid of every state for a small piece, or, for a page, a list or a large piece, one story with a `state` dropdown in the Controls panel (see "The `state` dropdown story"). A piece with nothing to merge keeps `Default` for its one story. A state stays a story of its own only when a test needs it isolated. The same state has the same name everywhere: `Empty` (nothing to list), `NoMatches` (a filter found nothing), `Loading` (data on its way), `Pending` (an action on its way), `FirstPage`, `MiddlePage` and `LastPage`, and `Failed`.

  "Draws" is read from the imports under `src/app` and `src/components`, not from a plan: a piece moves to its kind in the PR that makes a second area draw it. Nothing sits loose at the top level. Within a group the sidebar lists a piece's `States` story first, then `Default`, and the rest by name. Storybook builds a story's id from its title and export name in kebab case (`Shell / Account Menu` and `States` give `shell-account-menu--states`), so a title change moves the id, and with it any link to the story.

- `*.stories.tsx` and `.storybook/**/*.ts(x)` are type-checked by `tsc` like any other source: `src/**` already reaches the component stories, and `tsconfig.json` names the dot-directory because a `**` glob skips it. Storybook compiles stories through Vite, which strips types, so `tsc` is what catches a fixture that has drifted from its prop or GraphQL type. A fixture is typed or `satisfies` its real type, never cast. Typed routes make `Route` a union of the static addresses, so a story's dynamic `href` goes through `route()` in `.storybook/route.ts`, the same helper the invitation page uses. `tsconfig` does not reach `scripts/`; Oxlint is the only check covering those files.

## Opening a story at phone width

The viewport is a Storybook global, like the theme, so a link can set both:

```
/?path=/story/<story-id>&globals=theme:light;viewport:w375
```

- `<story-id>` is the kebab-case title and export name above, and `&args=state:Open` picks a state of a `state` dropdown (spaces as `+`). For example `/?path=/story/shell-account-menu--states&args=state:Open&globals=theme:light;viewport:w375` opens the account menu with its links, light, in a 375px preview.
- Globals are separated by `;`, each as `name:value`. `theme` is `dark`, `light` or `auto`. `viewport` is `w375`, `w382`, `w600` or `w700` (`VIEWPORT_WIDTHS` in `.storybook/preview.tsx`). Add `;viewport.isRotated:true` to turn it sideways.
- **It works on the manager link (`/?path=…`) only.** The viewport resizes the preview frame the manager draws. A bare `/iframe.html?id=<story-id>&viewMode=story&globals=theme:light` takes the theme but fills the browser window, so a test that needs a width sets the browser's own viewport (`page.setViewportSize`) and opens that URL.
- A story's own `globals` are its starting setting, and a link's override them.

## `.storybook/`

- **`main.ts`** — the `stories` globs, the framework, and `viteFinal`:
  - `@` aliased to `src/`. Components import `@/modules/...` at runtime, as `tsconfig.json`'s `paths` say, and the framework does not read those paths for stories.
  - Sass pinned to `modern-compiler`, so `@use` resolves as under `next dev`: relative paths, empty load paths.
  - `server.allowedHosts: ['devcontainer']`, for the Playwright browser, which reaches the workshop under the compose service's name. `core.allowedHosts` is `['localhost', 'devcontainer']`: the container listens on every interface (`--host 0.0.0.0`) so the host can reach it, and Storybook 10 then stops at an interactive "host validation disabled" prompt unless told which hosts to accept. `localhost` is the owner's browser, `devcontainer` the e2e remote browser; any other Host header gets 403.
  - `staticDirs` serves `mockServiceWorker.js` (the fake API's worker file) from the root, and `define` sets `WORKSHOP_API_PREFIX` to `/workshop` (see "The fake API").
  - `next/link` and `next/navigation` need no alias: the framework supplies them. Its decorator wraps each story in the App Router's contexts (a router whose calls go nowhere), and `preview.tsx` sets the page it pretends to be on (`/keepers/users`, `parameters.nextjs.navigation.pathname`).
  - No HMR settings: Vite's reload socket shares the HTTP port, so `--base` and a second published port are not needed.
- **`preview.tsx`** — the load-once entry and the **decorator**. It imports `theme.scss` and the three `*-base` sheets below, and holds the viewport presets and `storySort`. The decorator reads the toolbar's `theme` global and re-applies it through `applyTheme()`, the one shared implementation of the `data-theme` + `localStorage` write, also used by the app's `ThemeToggle`; `auto` clears the attribute so `prefers-color-scheme` decides. The default is `dark`, matching the app's dark-first default in `globals.scss`. It wraps the story in `<main className="workshop-story-frame" key={theme}>`, where the `key` forces a remount on theme change so a component that reads `data-theme` only on mount follows the switch, inside the app's `Providers` (`src/app/providers.tsx`) so a component that uses TanStack Query finds the one client the root layout mounts, and the click feedback's status region. A story never mounts a `QueryClientProvider` of its own, which would split the cache.
  - **`storySort` must be self-contained**: Storybook reads it from the source text without running the file, so it can use no type annotation and no name from outside it. The parameters are typed by a `satisfies` on `parameters`, which Storybook strips, not by annotations, which it evaluates and chokes on.
  - **`reducedMotion` parameter.** `prefers-reduced-motion: reduce` is an OS/browser setting with no toolbar control to dispatch, so a story sets `parameters: { reducedMotion: true }` to have it simulated. The decorator patches `window.matchMedia` so the reduced-motion query reports a match (the check `ThemeToggle`'s click handler makes to park a facet immediately when no `transitionend` is coming), and adds `workshop-story-frame--reduced-motion` to the frame, whose rule in `story-frame.scss` zeroes every transition inside it. Both halves are needed: the CSS alone does not touch the click-time check, and the patch alone does not stop a real transition from firing its own `transitionend`. The patch is undone on cleanup so it cannot leak into the next story. The pin does not reach a CSS media query, so to see a story that depends on one (the page bar's pulse), turn on the OS "reduce motion" setting or emulate `prefers-reduced-motion: reduce` in devtools.
- **The typefaces.** `preview.tsx` imports Cormorant Unicase (latin 500, 600 and 700) and Lexend from the `@fontsource` packages (`@fontsource/cormorant-unicase`, `@fontsource-variable/lexend`), so the workshop's type matches the app's; the app self-hosts them through `next/font`, which the workshop has no equivalent of. The build bundles the font files beside its own and links them relative to the page, so they load under `/workshop/` and no workshop page asks Google's font servers (`tests/e2e/workshop/fonts.spec.ts`). `--font-body` and `--font-display` are redefined in `typography.scss`'s `:root` block, because the app defines them only through `next/font`, so there is nothing to import. The override names the families the `@fontsource` stylesheets declare, `'Lexend Variable'` and `'Cormorant Unicase'`, so it changes with the imports in `preview.tsx`, and the weights those imports take agree with `src/app/fonts.ts`.
- **`theme.scss`** — a trimmed copy of `globals.scss`: the three theme blocks and the `body` surface, minus its `@use './typography'`. Importing `globals.scss` whole drags `_typography.scss`'s document-wide element rules (`li::before { content: '◆' }`, …) onto Storybook's own sidebar and list controls. **The three theme blocks are a verbatim copy and must be kept in step with `globals.scss`; they must not grow layout rules of their own.**
- **`story-frame.scss`** — the app-surface frame: `$surface-page` / `$text-primary` so a story needs no per-story setup; `min-height: 100vh`, so the ground fills the window under a short story; `transform`, making the frame the containing block so a `position: fixed` child pins to the story rather than Storybook's chrome; `overflow: hidden` so it clips like a viewport; a 3rem gutter a side, and `space(4)` below 30rem, where 3rem would leave a 375px story 279px. It also holds `.story-guide` and `.story-note` (a story's own "what to try" panel, and the line saying what it stands in for), and the `workshop-story-frame--reduced-motion` rule, a `!important` blanket over every transition in the frame, since the real media feature zeroes transitions app-wide too. The `.workshop-story-frame:has(.app-shell, .public-frame)` rule is for a state that draws the whole app shell or the signed-out frame: it drops the frame's padding, `transform`, clip and background (so the Backdrop, at `z-index: -1`, shows above the body colour as on the site), because a transformed ancestor would otherwise pin the phone's `position: fixed` bottom bar to the end of the page and not the screen. It applies per state, not per story, so a story whose dropdown holds both shell and non-shell states keeps the frame's padding for the latter. `:has()` is Baseline Widely Available, the floor in `package.json`.
- **`typography.scss`, `layout.scss`, `primitives.scss`** — each `@include`s its `src/scss/` `*-base` mixin into `:where(.workshop-story-frame)`, so a story gets the identical prose, document structure and class layer a page does while Storybook's own `<ul>` / `<li>` / `<a>` chrome, outside the frame, stays untouched. **The `:where()` is load-bearing**: it gives the scope no specificity, as `body` has next to nothing in the app. Scoped by a bare class, `.workshop-story-frame p` (0,1,1) outranks every component's own `p` class (0,1,0), so the workshop would draw a notice at body size with the paragraph margin, and a nav's rows with the ◆ bullet the page never shows.
- **`navigation.tsx`** — three wrappers that put a different value in the contexts Next's real hooks read. `WorkshopPathname` sets another address for `usePathname`, so a story can show the current-page marker on another tab. `WorkshopNavigation` is told where `push` and `replace` were asked to go: a `RouteModal` closes by navigating, so without it a story's modal stays mounted as a native modal dialog, invisible once faded and holding the whole page inert. The framework's `useSearchParams` answers an empty query, so a component whose open state is a search parameter (the shell's Add Ingredient button, opening on `?new`) draws closed in a story. `WorkshopSearch` is that query: it follows the story's own `history.pushState`, `replaceState` and Back as the router does, adds its `initial` parameters to the frame's address, and puts the address back when it unmounts.
- **`reopenable.tsx`** — `Reopenable`, what stands in for a modal's owner. The app's stewards close a modal by unmounting it, and a story has no owner. It renders its children while open, hands them a `close`, answers a `RouteModal`'s navigation through `WorkshopNavigation` by closing too, and leaves an Open Again button in place of the modal. A story that draws a `Modal` whose `onClose` would do nothing wraps it in this. `in-modal.tsx`'s `InModal` is a form drawn in the modal the admin pages open it in, with Open Again.
- **`mock-api.ts`** — the workshop's fake API (see "The fake API").
- **`admin-frame.tsx`** and **`shell-frame.tsx`** — the admin area's and the application shell's layouts as markup only (the real layouts are server components that read the session). `AdminFrame` draws the context row ("Admin" and `AdminNav`) and the `.page-column` column inside `.app-shell__main`, with an optional `open` address that decides the nav's current page, and a `shell` flag that draws it inside `ShellFrame`; `AdminTabbedFrame` is a tabbed admin page (heading and tabs from `ADMIN_PAGES`, and an `action`). `ShellFrame` draws the bar, the context row, then the page, with fixture props (`FIXTURE_VIEWER`, `FIXTURE_WORKSPACES`, whose `canReadMembers` is worked out from the role as the layout does); its `area` picks the context row (a coven's, the admin area's, the create page's, or none, as on the account pages), and `signedOut` draws `PublicFrame` in place of the shell.
- **Fixtures** — invented rows the stories of a feature share, so a form's story and its list's story offer the same data: `fixtures.ts` (the admin stories), `grimoire-fixtures.ts` (the grimoire's categories, steps and workings, so the builder, the recipe and the cards draw the same categories in the same colours) and `compendium-fixtures.ts` (`NO_FILTER` and `NO_FACETS`, which the list and card stories start from). `grimoire-workings.tsx` is the Workings section with the recipe page's own controls, shared by the Spell Workings and Spell Recipe stories.
- **`states-grid.tsx`** — `StatesGrid`, every data state of one small component side by side, each under its name (rule 5). A state that needs a canvas of its own (a click, an open dialog, a hanging request, a viewport) stays a story.
- **`press.ts`** — `press(name)` and `usePressOnMount(name)`, for a story that opens on a state a button press reaches, such as a Delete question over its form. `pressLast(name)` presses the last button of that name (a dialog's confirm over a same-named button), `setInputValue(input, value)` types into a field so React hears it, `submitForm(selector)` submits a form as Enter does, and `useSteps(steps, gap)` runs a list of these once the story has mounted, a short wait between each.
- **`navigating.tsx`** — `Navigating` keeps a router call pending for good. The workshop's router goes nowhere, so a press would end its wait at once; `Navigating` suspends the call inside the same transition, under an already-shown boundary, so the page bar's state, the link's `aria-busy` and the body's skeleton stay on screen as in the App Router. "Start Over" remounts the whole thing and is the only way the wait ends. `tests/support/navigating.tsx` does the same with a mocked router.
- **`types.ts`** — the types the workshop's helpers share (`AdminTabbedFrameProps`, `ShellFrameProps`).
- **`foundations.{tsx,scss,stories.tsx}`** — the one reference page under `Foundations`: the palette, tokens, type scale, spacing, radii, buttons, notices, field primitives, the page frame, data table, pager, filter row, page header, provider buttons, group colour chips, badges, a modal and an ingredient card. Every printed value is generated by `foundations.scss` from the real partial's own map, never typed. The data table, filter row and page header are drawn twice, at page width and inside a 375px box (`.fd-phone`), so their container queries show the phone layout at any window size. It lives in `.storybook/` because the app never imports it; `foundations.scss` holds only reference-page chrome, nested under `.fd`. The other workshop-only stories are `main-body.stories.tsx` (the body-swap states: one dropdown of pages inside the shell, the waiting ones opened with their link already pressed), `navigation-bar.stories.tsx` and `pending-link.stories.tsx`.
- **The page bar needs a transformed box.** It is `position: fixed` against the window, but the shell frame pads the shell in from the window's edge. A transformed box (`translateZ(0)`) becomes the bar's containing block, so the bar lands on the global bar's bottom edge as in the app. The box also becomes the skip link's containing block, whose hiding (lifted above the page's top edge) would leave it in view; the clip hides it again, and it still shows on focus.

## Mail templates

- **`src/emails/*.stories.tsx`** is the second story glob in `main.ts`: one story file beside each mail template, titled `Emails / …`. The shared frame in `src/emails/parts/` has none; every template previews it.
- **`EmailPreview.tsx`** renders a template's `Message` and shows the HTML part in an iframe, so the workshop's styles and document never reach the mail, with the plain-text part in a `<details>` beneath. Images and fonts load from the workshop's own origin: Vite serves `public/` in `storybook dev` and Storybook copies it into the build, and on staging `/email/*` is the app's own public prefix.
- **The toolbar's theme reaches the mail by rewriting it.** A framed document's `prefers-color-scheme` follows the browser, not the frame's `color-scheme` (in the Playwright Chromium, a light page left the mail dark). So the preview reads the page's computed `color-scheme` and turns the mail's one `LIGHT_MEDIA` block into `@media all` or `@media not all`: the same rules a client in that scheme applies, nothing re-styled. A story's own theme `globals` win, as for components.

## Review screenshots

`scripts/review-screenshots.mjs` is a design review's camera: it shoots each page a review lists at 375×812 and 412×915, in the dark and the light theme, full page, into the directory it is given (`.reports/<task>-screenshots/` by convention, gitignored). A review reuses it rather than shooting by hand. It is a tool for the agents running a review, not a requirement of the app, and is untested on purpose.

```sh
node scripts/review-screenshots.mjs --out .reports/mb.116-screenshots \
  --pages '[{ "path": "/sign-in", "name": "sign-in" }, { "path": "/", "name": "welcome" }]'
```

- **It drives the remote browser**, `chromium.connect(PLAYWRIGHT_WS_ENDPOINT)`, the same `playwright-server` the e2e runner uses, since no browser is installed in the devcontainer. That browser reaches this container as `devcontainer`, so `--base` defaults to `http://devcontainer:8000`, the dev server.
- **`--pages`** is a JSON list of `{ path, name }`, inline or a file's path; each page is saved as `<name>-<width>-<theme>.png`.
- **The theme is `emulateMedia({ colorScheme })`**: a fresh context has no stored theme, so the app follows `prefers-color-scheme` as a first visit does. A workshop story does not: it opens dark unless the URL carries a theme, so the script adds `globals=theme:light` or `globals=theme:dark` to any `/iframe.html?id=...` path that has no `globals`.
- **`--storage-state <file>`** is a Playwright storage-state file carrying a signed-in session's cookies, for a page behind sign-in.
- **Both widths are touch screens**: every browser context is opened with `hasTouch` and `isMobile`, so the page's `(hover: none)` query holds as it does on a phone. A desktop browser at phone width would otherwise show what no phone does, such as the impersonation banner tucked away until a pointer nears the top, where a touch screen keeps it in the page's flow. A review's phone sign-off is a touch sign-off.

## The fake API

A story whose component asks the server gets an answer from Mock Service Worker (MSW), a library that answers a request in the browser. `.storybook/mock-api.ts` holds the helpers; `preview.tsx` starts the worker with `mswLoader(startMockWorker)`, which also resets the handlers before each story. The handlers in `mock-api.ts` are the defaults every story starts from. Requests nothing handles go to the network, and an unanswered operation gets a 501.

- **A story states its answers in `beforeEach: ({ msw }) => msw.use(...)`.** The helpers are `answerQuery` and `answerMutation` (typed by the generated document, matched by operation name, e.g. `answerMutation(SaveIngredientDocument, () => ({ ... }))`), `answerOperations` (one function for a story with many lookups), `hangOperation` and `hangAllOperations` (a request that never answers, for a loading state), `hangAuth` and `refuseAuth` (the same for `/api/auth`), and `refusal({ message, code, fieldErrors, currentRevision })` (a refusal as the server sends it: HTTP 200, no data, one error with its code; `currentRevision` goes with `STALE_WRITE`, for a story that shows a conflict).
- **`beforeEach` runs once per load.** A story that picks its answer from an arg or a `state` control calls `useMockHandlers(handlers)` in its render instead; it swaps the handlers whenever they change. The two are not mixed in one story: removing `useMockHandlers`' handlers puts the worker back to its defaults and re-adds only its own, so a story using both loses the `beforeEach` ones. Pass it a list that keeps its identity (a module constant or `useMemo`).
- **The prefix.** See "The API prefix". The worker file is found beside the page (`./mockServiceWorker.js`), so it works under `/workshop/` on staging as well as at the root of the dev server.
- **A refused auth request is a failed request.** A GraphQL refusal logs nothing in the browser; an `/api/auth` refusal is a non-OK response and logs "Failed to load resource". A story that does this carries the tag `expects-failed-request`, which the every-story check reads from `index.json`.
- **A request that navigates away is not mocked.** A success that ends in `window.location.assign` (Stop Impersonating) would leave the story, so its story shows the waiting and the refusal only.

### Handlers a story passes

- **Every handler a story passes is `fn()`** (from `storybook/test`), as an arg, so the Actions panel records the call. A bare `() => {}` records nothing and leaves a button that looks dead.
- **Where a click should change what is shown, `useArgs`** (from `storybook/preview-api`) updates an arg the story draws (see `Field` `ActionsInUse`, `IngredientCard` `States`, `Notice` `States`).
- **Where a control cannot work in the workshop, the story says why** in its comment. `TabbedPage` cards loading is one: a tab can only wait with the default table skeleton, because `PageTab` carries no skeleton shape and no tab in the app uses a cards skeleton.

## The `state` dropdown story

A story with a `state` control (rule 5 above) draws a whole page or list, too big to sit beside the others. Its `state` arg is the node it draws: the `argTypes` mapping turns the chosen name into that node, so the story's type is `StoryObj<{ state?: ReactNode }>`. A node keys nothing, so the frame's decorator keys the story by the chosen name (`context.unmappedArgs.state`): a new choice remounts it, and its state, its fake API handlers and its scripted presses start afresh, as they do when the state is opened by its address.

## The every-story check

`npm run workshop:check` loads every story in `index.json` in both themes in a real browser and fails on a page error, a console error, a failed or 4xx/5xx request, Storybook's own error display and an axe violation (the page-level rules a lone story cannot satisfy are off: heading one, region and the landmark rules).

- **It is manual.** It is not in CI, pre-commit or any other test script: its file is `tests/e2e/workshop/every-story.check.ts` (the `.check.ts` name matches no default `testMatch`), and it has its own config, `playwright.workshop-check.config.ts`. `playwright.config.ts` also ignores every `/workshop/` path, and no workflow calls it.
- **Run it against a running workshop at `localhost`**, since a service worker needs a secure origin: `npm run workshop` in one shell, then the check with `WORKSHOP_CHECK_URL` (default `http://localhost:61104`; set it to the port the workshop runs on). The remote browser reaches the container's `localhost` through `PLAYWRIGHT_WS_ENDPOINT` with `exposeNetwork`.
- **Narrowing:** `WORKSHOP_CHECK_ONLY` (a story id substring), `WORKSHOP_CHECK_THEMES` (`light`, `dark` or both) and `WORKSHOP_CHECK_WORKERS` (default 4).
- **A story tagged `expects-failed-request`** is exempt from the failed-request and console-error checks only, never from page errors or axe.
- **A story tagged `shows-low-contrast`** is exempt from the `color-contrast` axe rule only. Use it for a story whose point is a colour pair that fails, such as a colour field showing its too-low ratio; every other rule still runs.

## Commands and gates

- `npm run workshop` / `make workshop` — dev server on **61000**, with Vite HMR and React Fast Refresh, bound to every interface and asking for no sign-in. Only edits to the `.storybook/` config files themselves (`main.ts`, `preview.tsx`) need the dev server restarted. The compose service is in `docker.md`, "workshop".
- `npm run workshop:build` / `make workshop-build` — static build to the gitignored `.reports/workshop/`, or to the directory `--outDir <dir>` names (`deploy.yml` passes `public/workshop`), via `scripts/build-workshop.ts`. It exits non-zero when the build fails. See "The build gate".
- **`workshop:build` is not a render smoke test.** The static build bundles stories without running them, so it cannot catch a story that throws at render time; it catches an unresolvable import or a syntax error.
- **The gate runs in CI, and not in pre-commit.** `workshop:build` runs on `checks.yml`'s `build` leg. Pre-commit is lint, `format:check` and typecheck on the files a commit changes, test-free by decision: a hook that runs tests is a hook people start skipping, and a PR cannot skip CI.

## On staging

Staging serves the workshop at `https://staging.sorrelandsalt.com/workshop`, to keepers only. The local `npm run workshop` asks for no sign-in: local development is the one relaxed environment. Production and hotfix previews never carry the workshop.

- **How it ships.** On a staging deploy alone (the step's `if:` reads `git_branch == 'staging'`), `deploy.yml` runs `npm run workshop:build -- --outDir public/workshop` before `vercel build`. Next then serves the files from `public/` as it serves any static file; `public/workshop` is gitignored. Storybook's static build links its own files relative to the page (`./iframe.html`, `./sb-manager/…`), so it needs no base path; what it needs instead is that every page is served from a URL under `/workshop/`, which the redirect below sees to.
- **How it is gated: in `src/proxy.ts`, and nowhere else can do it.** Next runs the proxy before it serves `public/`, and a static file has no page to call `requireSession()`, so the proxy's usual cookie-only check would admit any signed-in account, and signing in with any provider earns one. For `/workshop` and everything beneath it (`/workshopping` is not beneath it), and only there, the proxy asks Better Auth for the live session through `sessionFromHeaders()` and hands it to `assertWorkshopAccess()` (`src/modules/identity/services/workshop-access.ts`; the rule is a service's, per rule 1). This is the one prefix where the proxy asks the database itself. The lookup module is imported inside the workshop branch only, so no other request loads the database client in the proxy.

  | Request                                  | Answer                                                                 |
  | ---------------------------------------- | ---------------------------------------------------------------------- |
  | No session cookie                        | 307 to `/sign-in?next=<path>`, as any protected route                  |
  | A cookie Better Auth rejects             | The same redirect                                                      |
  | A live session, role `user` or `curator` | 403, plain text                                                        |
  | A live session, role `admin`             | The file, with the workshop's Content Security Policy (below)          |
  | The same keeper, at bare `/workshop`     | 307 to `/workshop/index.html`, query kept, with the same policy header |

  The 403 is plain rather than the styled page `/keepers` shows: it answers requests for scripts and JSON as well as for the page.

- **Bare `/workshop` redirects to `/workshop/index.html`, query kept.** `index.html` is Storybook's manager, the page with the sidebar, and it loads each story from `./iframe.html` in a frame. A relative link resolves against the page's directory, so a manager served at `/workshop` itself would ask for `/iframe.html` and get nothing. A rewrite would keep that URL in the browser, so it does not work. `/workshop/` does not work either: Next's trailing-slash redirect, which runs before the proxy, sends `/workshop/` back to `/workshop`.
- **No application data is reachable through it.** The build is static: no story reaches GraphQL, and `index.json` is the story index. A story whose component asks `/api/graphql` answers it in the page ("The fake API"), so the request never leaves the page and the policy below has nothing to refuse. The workshop's own scripts nonetheless run on the app's origin carrying a keeper's cookie, so every workshop response the gate lets through carries a Content Security Policy (CSP, a header telling the browser what the page may load) of `connect-src <host>/workshop/`, for example `connect-src staging.sorrelandsalt.com/workshop/`. `tests/proxy.test.ts` checks the header against the specification's path-matching rule.
- **Admin only for now.** A role that can open the workshop without admin's other powers is v2 (DESIGN.md §13, "A workshop-viewer role"); when it lands, `assertWorkshopAccess()` is the one line that changes.

### The workshop's Content Security Policy

Scripts may fetch, by `fetch`, XHR (`XMLHttpRequest`) or WebSocket, only files under `/workshop/` on the address the browser used. Storybook's manager and preview fetch their own files (`index.json` and `project.json` among them), so `'none'` would break it. A source whose path ends in `/` matches every path beneath it and no other, so `/api/graphql`, `/api/auth/*` and every page outside `/workshop/` are refused by the browser though the scripts carry a keeper's cookie. `'self'` cannot take a path, which is why the host is written out. Nothing else is restricted: the manager frames its own `iframe.html`, and no header in the proxy, `next.config.ts` or `vercel.json` forbids framing.

- **The host** is the one in the browser's address bar: `x-forwarded-host` (as Next's own Server Actions check reads it), then `Host`, accepted only when it is a plain host and port; any other value falls back to `nextUrl.host`. It is not `nextUrl.host`, the address the server was reached on, which behind a proxy or a container is something like `0.0.0.0:8000`; a policy naming that refuses every one of Storybook's own fetches, and the workshop shows "Failed to fetch".
- **No scheme is written**, so the source takes the page's own, and `https` behind a proxy that ends TLS (Transport Layer Security, the encryption in `https`) still matches.
- **One limit, from the CSP specification itself:** after a redirect the path is no longer checked, only the origin. Nothing under `/workshop/` redirects off it for a keeper; the only redirect is to `/sign-in` once a session has died, which returns the sign-in page and no data.

### The API prefix

`apiPath()` in `src/lib/api-path.ts` (used by `src/lib/graphql-client.ts` and `src/lib/auth-client.ts`) puts an optional prefix in front of the API path; it is empty in the app. The workshop sets `WORKSHOP_API_PREFIX=/workshop` in `main.ts` at build time, so its stories call `/workshop/api/...`: staging's CSP lets a workshop page reach only addresses under `/workshop/`, and refuses the real ones before a service worker can answer. The mock service worker answers there, never the real API; its file is served at `/workshop/mockServiceWorker.js`. The prefix is read at the call site, not at import, so a test can set it before the module under test loads. The name has no `NEXT_PUBLIC_` on purpose: Next builds every `NEXT_PUBLIC_` variable into the live site's browser code, so setting one on Vercel would send the real site's requests to the wrong address. Only the workshop's Vite build replaces this name; in the app's browser code it is undefined.

## The build gate

`scripts/build-workshop.ts` runs `storybook build` and relays its exit code. It exists so `npm run workshop:build` has one place to change: it renames `--outDir` to Storybook's `--output-dir`, builds to `.reports/workshop` when no directory is given, and turns telemetry off. Storybook's static build links its own files relative to the page, so it needs no `--base` to be served under `/workshop/`.

## The library build

`npm run build:components` turns `src/components/` into a library in `dist/`, which is gitignored. It writes one JavaScript module per component folder (named after the folder, such as `dist/Modal.mjs`), a `tokens.mjs` entry, shared chunks, and one stylesheet, `dist/sorrel-and-salt.css`, which holds the global theme tokens from `src/app/globals.scss` and every component's own Sass module. The Claude Design sync reads this build together with the Storybook workshop.

It runs Vite's library mode through `vite.components.config.ts`, not a `tsc` emit, because the components import their Sass from TypeScript and only a bundler compiles that. React, `react-dom`, `next/*`, `react-hook-form`, `downshift` and `zod` stay external: the consumer supplies them. Everything else, including the `@/` paths, is bundled in. The stylesheet needs `scripts/library-tokens.ts` as its entry, because Vite will not take a stylesheet as an entry on its own.
