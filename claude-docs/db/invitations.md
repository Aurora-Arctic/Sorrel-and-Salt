## Invitations

`src/modules/coven/schema/invitations.ts` holds every invitation, in two tiers as `ingredients` is: a row naming a workspace and a role invites into that coven, and a row with neither is a **site-tier** invitation, which grants a site role, as a null workspace is a compendium entry. Why one table, why it is `coven`'s, and what was rejected: [`auth.md`, "Workspace and admin invitations are one two-tier table"](../design-decisions/auth.md#workspace-and-admin-invitations-are-one-two-tier-table).

- `email` is text and **not** a foreign key: an invitee may have no account yet, which is the point of inviting them.
- `note` says why the person is being invited, optional as a privilege change's `note` is in `user_privilege_changes`; either tier may carry one.
- **Cards.** A third shape of the same table: a printed code bound to no address, coven or site role (why a shape of this table: [`auth.md`, "An invitation card is a third shape of `invitations`"](../design-decisions/auth.md#an-invitation-card-is-a-third-shape-of-invitations)).
  - `kind` is `address` (the default) or `card`. `invitations_kind_shape` requires an `address` row's `email` and a `card`'s `email`, `workspace_id`, `role` and `site_role` to be null.
  - `batch_id` (nullable uuid, no table) groups the cards of one mint. `position` is a card's place in its batch, in the order the print PDF lays the fronts out; card rows only.
  - A card's `note` is the keeper's note on the mint, copied onto every card of the batch and held to 500 characters (`invitations_card_note_length`); accepting a card writes it into the privilege ledger like any other invitation's note.
  - A card's token is returned once, at minting, to the keeper who mints it; only its hash is stored.
- **`invitations_tier`**: an address row is in one tier, a workspace and the role it is invited to, or neither; a card is in neither.
- **`invitations_declined_coven`**: only a coven invitation is declined. A keeper invitation is never listed to its invitee, so it is accepted by its link or not at all, and the database says so rather than leaving it to the service.
- **`invitations_answered_once`**: an invitation is accepted or declined, never both. The writers already match a pending row only, so two racing answers cannot both land; the CHECK is what holds if a later path forgets. `revoked_at` is outside it on purpose: the owner's Remove stamps a declined row revoked, so a row may carry a decline and a revoke together.
- **Only the hash is stored.** There is no plaintext column and there must never be one: a leaked database row cannot be redeemed. The token is generated with `crypto.randomBytes`, mailed in the link and in no response, and every later read matches a hash against `token_hash`. The schema test pins the table's exact column set, so a later `invite_token` reddens it.
- **`invitations_role_invitable`**, `role is null or role in ('viewer', 'member')`, is the check DESIGN.md §5 requires. It is written as the allowed set rather than as `role <> 'owner'` deliberately: a role added later would be silently _invitable_ under the negative form and silently refused under this one. Refusing is the safe default for the column that decides what a stranger holding a link may do. It is in the database because a service check can be forgotten by the next code path that writes the table, and a constraint cannot.
- **Expiry defaults to seven days** (`now() + interval '7 days'`), `NOT NULL`: long enough that a link mailed on a Friday survives the weekend, short enough that one found in an old inbox is dead. Omitting one cannot produce an invitation valid forever.
- **`invitations_token_hash_unique`** is the acceptance path's lookup, across both tiers, and unique as well as indexed: one hash must resolve to at most one invitation, or redeeming it is a coin toss between two rows that may grant different things.
- **Five lifecycle columns, not one `status` enum.** `expiresAt` is a clock comparison, `revokedAt` is a steward's or a keeper's act, `acceptedAt`/`acceptedBy` are the redeemer's, and `declinedAt` is the invitee's no. The dead states must be told apart with a deterministic answer when two apply at once; collapsing them is the shape rejected in Better Auth's plugin, which answers every dead link with one `INVITATION_NOT_FOUND` ([`auth.md`, "Better Auth's organization plugin for workspaces and invitations"](../design-decisions/auth.md#better-auths-organization-plugin-for-workspaces-and-invitations)). The acceptance service owns the classification; the table owns keeping the evidence apart.
  - There is no `revokedBy`: revoking is the last write a row takes, so `updated_by` is who revoked.
  - There is no `declinedBy`: who declined is the address the invitation was sent to, which the decline write matched against the session's verified address.
  - No constraint pairs `acceptedAt` with `acceptedBy`, since one named write sets both.

### Site tier

A site-tier row has a null workspace and role, and names the site role it grants, `site_role` (the `user_role` enum), `curator` or `admin`. `invitations_site_role_tier` is `(workspace_id is null) = (site_role is not null)`. `invitations_site_role_invitable` admits only `curator` and `admin`; it compares the column as text, since Postgres refuses a value an enum gained in the same transaction (55P04), and drizzle-kit runs every pending migration in one.

### Written and read by tier

The row is what authorises a membership or a grant, so a generic insert would let any service mint its own user an invitation and accept it. The table is marked `namedWrites` in its schema file, which takes it off every generic writer method ([`write-path.md`](write-path.md#table-marks-mb198), "Table marks"). In their place, in the repository's `invitations.ts`, which `writerFor` spreads into the writer:

- **`revokePendingInvitationsTo(proof, email)`** stamps revoked every pending invitation to the address in the proof's tier: its coven for a `Membership`, the site tier for a `SiteAdmin`, so the two tiers never replace each other. Both create services call it before `insertInvitation`, in the same write.
- **`insertInvitation(membership, values)`** writes a workspace invitation into the proof's workspace with a role the type confines to `viewer` or `member`. **`insertInvitation(admin, values)`**, under the `SiteAdmin` proof, writes the null pair and a site role the type confines to `curator` or `admin`. Either writes the token's hash and nothing else, so a row starts pending, and in the proof's tier, even if a cast smuggled a stamp, a workspace or a role in.
- **`acceptInvitation(token)`** stamps `accepted_at` now and `accepted_by` from the session, on either tier, under no proof, since the invitee holds neither a membership nor the site role yet. It matches only while the session's user holds the invited address, verified, on a live row, compared case-insensitively. The accept service checks the address first so it can say why, pointing an unverified match at `/account/email`; the statement is what holds if a later path forgets. When a coven's accept inserts or revives a membership, it also writes the invitation's `created_by` to `workspace_members.invited_by`; an accept by someone already seated writes no membership.
- **`acceptReceivedInvitation(id)`** and **`declineReceivedInvitation(id)`** stamp a workspace-tier row by id, under no proof, matching only while the session's user holds the invited address, verified, the coven is live and the row is pending. The decline writes only `declined_at`: no `declined_by`, no membership or grant.
- **`revokeInvitation(membership, id)`** stamps `revoked_at` now on an open row in the proof's workspace, and **`revokeInvitation(admin, id)`** on a site-tier row. Open is pending, or declined and not yet removed: Revoke is this write on a pending row, and Remove is the same write on a declined one, so it leaves the owner's list and stays in the table for the audit. It is by id because a steward or a keeper revokes from a list and neither holds the token. Each reaches only its own tier, asserted by direct id.

The accept and decline stamps match a **pending** row only: live, none of accepted, declined and revoked, and unexpired. So no invitation is answered twice, a declined, revoked or expired link cannot be redeemed even by a service that forgot to check, and no stamp overwrites another; a call that matches nothing returns no row. The revoke stamp matches an **open** row instead: not accepted, not revoked, and either declined or unexpired. A declined invitation is an answer for the owner to read, not a link that lapses, so it stays open past its expiry until a steward removes it.

**The token goes in, never the hash.** `hashToken` in the repository's `tokens.ts`, hex SHA-256, is the only place a hash is made, so a caller never holds one: a hash read out of a dumped row and passed where a token goes is hashed again and matches nothing, and the accept by token cannot be reached with an invitation's id, which the lists show. SHA-256 is unsalted rather than a password hash, because a token is `crypto.randomBytes` output with no dictionary to resist. `Math.random()` is predictable from a few outputs, so a token made with it could be guessed.

**One generator makes every token.** `newToken()` in `src/lib/invitation-token.ts` is 32 bytes of `crypto.randomBytes()` as base64url. Both tiers' services call it. It lives in `src/lib/` because a service may not import the repository's internals, and because two modules mint a token, so neither owns it. The service hands the token to `insertInvitation` and then to the mail sender, and to nothing else: no response, no query, and no later read can recover it. A card's token is `newCardToken` in the same file: 16 characters from a 57-symbol alphabet without `0`, `O`, `1`, `l`, `I`; `insertInvitationCards` stores only the hashes.

**`rotateInvitationToken`** gives the pending address invitation a fresh token, storing only its hash; it returns null when the invitation is accepted, declined, revoked, expired, a card, or in a deleted coven. It writes as the System account because the mail step holds the id alone; `tests/guards/invitation-token-rotation.test.ts` holds the only-caller rule ([`auth.md`, "The invitation mail mints its token in the job step"](../design-decisions/auth.md#the-invitation-mail-mints-its-token-in-the-job-step)).

The finders:

- **`findInvitationByToken(token)`** returns the live row the token names, on either tier, under no proof: holding the token is what admits. It returns expired, revoked, accepted and declined rows alike, because the accept service rejects each with its own message and can only tell them apart if it sees them.
- **`findPendingWorkspaceInvitationPage(membership, page)`** is the members page's pending list, which also holds the declined invitations not yet removed. **`findPendingSiteInvitationPage(admin, filter, page)`** is `/keepers/invitations`'. Each tier's pending rows are read under its own proof, newest first, with a matching `...Count` for "Page X of Y".
  - **`findInvitationInWorkspace(membership, id)`** reads one invitation of the proof's workspace in any state, and `undefined` for a missing, deleted or other workspace's id. `revokeInvitation` matches open rows only, so this is how the coven service tells an accepted invitation (point the owner at member removal) from a missing one.
  - The site tier's page is keyed on `created_at` negated as `numeric`, as the privilege ledger is, so the microseconds survive the cursor, and by id among rows of one instant. It reads through `findPageInScope` under `onSiteTier()`, since the exported pagers' types admit no two-tier table and `findPageInTiers` would read the site tier as the compendium. No index serves the order: the pending set is small.
  - `SiteInvitationFilter` ANDs in SQL `email` (a fragment matched case-insensitively by the shared `containsText`, its `%` and `_` read literally) and `expiresWithinHours`, measured against the database's `now()`, the same clock the pending test reads, so the app's clock never decides an expiry.
  - No list of past invitations exists: each pending list is where an invitation is acted on, and the privilege ledger holds every acceptance that granted something.

The site tier is read through `onSiteTier()`, `workspace_id IS NULL` spelled for this table alone rather than through `inCompendium`: a site-tier invitation is no compendium row. The tier-seam guard still lists it, since it reads the spelling ([`modules.md`](../modules.md), "The tier seam").

### Policy, in two services

Who may invite, the pause, what accepting grants and where it lands stay in two services, while the mechanics above exist once: `coven`'s `createInvitation` / `revokeWorkspaceInvitation`, steward only, role chosen, and `identity`'s `createAdminInvitation` / `revokeAdminInvitation`, admin only and refused while keeper changes are paused. One accept service in `identity`, `acceptInvitation(session, token)`, adds the membership and sets `canCreateWorkspace` on a workspace row, and grants the site role on a site row; one route, `/invite/[token]`, lands in the workspace or on `/keepers` by tier (`/i/[token]` is the public short link, in `src/proxy.ts`, rendering the same `InvitationPanel`). The accept reads the open pause under the site-tier invitation itself, since the invitee holds no `SiteAdmin` proof: `findOpenAdminRoleChangePause` takes either. The site tier's half is [`auth/admin-users.md`](../auth/admin-users.md), "Inviting a keeper".

### Inviting into a coven

`createInvitation(session, workspaceId, { email, role }, sender)`, exported from `@/modules/coven`, runs in this order, and the order is the point:

1. **`assertMembership(session, workspaceId, { member: ['invite'] })`**, which only stewards hold. A practitioner, an observer, a steward of another coven and a stranger all get the same `Forbidden`, before the role or the address is looked at, so nothing about the input leaks to a caller who may not invite.
2. **The role** must be `viewer` or `member`. The GraphQL enum `InvitableRole` has no `owner`, but the service refuses it too, as a `ValidationError` on `role` that says ownership is granted afterwards: a direct call is a second path, and the database check is a third, which would only say "check violated".
3. **The address** is trimmed and lower-cased with `normaliseEmail` and checked with `validateEmailAddress`, both from `identity`, exactly as `createAdminInvitation` does.
4. **A live member's address is refused**, in words, by `findMemberByEmail(membership, email)`: one SQL `EXISTS` over `users`, case-insensitive, live rows only, so a removed member can be invited back.
5. **The row** goes to `insertInvitation(membership, { email, role, token })` inside `withAudit`, holding the hash of a `newToken()` that nobody is told, and only then is `sender.invitation(row.id)` called: after the commit, so a mailed link always names a row. The sender starts the secret-link job with the invitation id and the origin alone; its step gives the invitation a fresh token through `rotateInvitationToken`, reads the coven, the role and the inviter's name from the database (the session holds the id alone), and mails the link. Each attempt mints again, so only the newest mailed link works.

**Each sender's mail is limited.** `createInvitation` counts the sender's own coven invitations created in the last hour, revoked or replaced ones included, and refuses the next once there are 20. The refusal is a `ValidationError` with no field that says when the oldest one leaves the window. The count is a SQL read through `findRecentCovenInvitationTimes`, so it holds across server instances and needs no table. The limit and window are `INVITATION_MAIL_LIMIT` and `INVITATION_MAIL_WINDOW_MINUTES` in `src/modules/coven/services/invitations.ts`. The check runs after the input checks and before any write, so a refusal writes and mails nothing. Two requests at the same moment can both read a count under the limit, so a few racing requests can pass it.

**A repeat invitation replaces the pending one.** Inviting an address that already has a pending invitation to the same coven first stamps that one revoked, as the inviter, in the same `withAudit` write that inserts the new one, through `revokePendingInvitationsTo(membership, email)`. So one invitation per address and coven is pending, its link is the newest and its role the one that applies. The address is matched in any case. Only a pending row in this coven is touched. A new invitation that fails its checks revokes nothing.

**A failed send leaves the invitation pending.** The job retries the step, and a step that runs out of attempts logs the invitation id, never the address or the token, so the mutation succeeds and the owner can revoke and re-invite. The row it answers carries no token.

**The mail** is `src/emails/coven-invitation.ts`, rendered twice by `renderParts` as HTML and plain text. The plain-text part carries the `/invite/<token>` link, because the browser flow reads the token from the mailed message. `InvitationSender` (`identity/types.ts`) is one method, `invitation(invitationId)`, for both tiers; the real one is built in `src/lib/invitation-mail.ts`, and the link's origin is Better Auth's, resolved from the request. `invitationLinkPath` (`src/lib/invitation-link.ts`, which holds the key and value once) builds the path: a site invitation's link carries the marker `?for=site` and a coven's carries none. The marker is read on the invite page signed out to put Create Account first ([`invitation-acceptance.md`](../components/invitation-acceptance.md)), and nothing else reads it.

**In GraphQL**, `coven` adds to `Invitation` an `InvitableRole` enum (`viewer`, `member`), `Invitation.role` and `Invitation.workspace`, and the `createInvitation(workspaceId, email, role)` mutation. `workspace` reads through the `membershipsByUser` loader, so it answers a coven the caller belongs to and nothing else, and a site-tier invitation answers none for both. No field carries the token, its hash or a link; the field-list test in `tests/modules/identity/graphql/admin-invitations.test.ts` pins that.

### Listing and revoking in a coven

Services in `@/modules/coven` open with `assertMembership(session, workspaceId, { member: ['invite'] })`, which only stewards hold. Never `member: read`: members hold that, and the pending rows carry the addresses of people who have not joined.

- **`listPendingWorkspaceInvitations`** and **`countPendingWorkspaceInvitations`** read the repository pager above. The members page calls them directly (a server component); there is no GraphQL read.
- **`revokeWorkspaceInvitation(session, workspaceId, id)`** looks the row up with `findInvitationInWorkspace` and then stamps it through `revokeInvitation(membership, id)`, inside `withAudit`. A missing id, a malformed one, another coven's, and a revoked or lapsed invitation are `NotFound`. A **declined** invitation is revoked like a pending one, even past its expiry: that is the owner's Remove. An **accepted** invitation is a `ValidationError` on `id` whose message points to the members list: the person is a member now, and removing them is a membership action. Two tabs revoking at once, or the link lapsing in between, leave nothing pending to stamp. In GraphQL, `revokeInvitation(workspaceId: ID!, id: ID!): Invitation!` goes through the service.
- **A pending invitation outlives its inviter.** Demoting or removing the member who sent it changes nothing about the row; a steward still lists and revokes it.

### Accepting from the account page

An invitation otherwise reaches its person one way, the mailed link, so a mail lost to a spam filter would leave them on `/coven` reading that someone must invite them, when someone had. The account page's Invitations section therefore lists the pending coven invitations addressed to the signed-in account's verified email, each with an Accept and a Decline, and the accept runs by id as well as by token. The `/coven` landing and the account menu say how many wait. The site tier is not listed and cannot be accepted by id: a keeper invitation's link is a bearer token for the site's highest privilege, and the worst case of a coven invitation is one coven's seat ([`auth.md`, "A coven invitation is accepted from the account page as well as from the mail"](../design-decisions/auth.md#a-coven-invitation-is-accepted-from-the-account-page-as-well-as-from-the-mail)).

**The reads.** Five finders in the repository's `invitations.ts` take no proof, for the token read's reason, with the session row in the token's place: each ANDs `heldVerifiedBySession(session)`, the predicate the accept write holds, and the workspace tier.

- `findReceivedInvitationPage(session, page)` and `findReceivedInvitationCount(session, start)` page the pending ones into a live coven, newest first.
- `findReceivedInvitation(session, id)` answers one row in any state, so the service can say accepted, declined, revoked or expired, and nothing for an id the address does not hold.
- `findReceivedInvitationCovens(session, ids)` and `findReceivedInvitationInviters(session, ids)` answer the name and slug of each coven and the name of each inviter, for the page's ids alone, so a page costs three statements whatever its size ([`membership-proof.md`](membership-proof.md), "The reads that take no proof").

**The service.** `acceptInvitationById(session, id)` and `declineInvitationById(session, id)` in `identity`'s `invitation-acceptance.ts` share every check and every effect of `acceptInvitation(session, token)`, the row read by id instead of by token: the seat or the revived seat, `invited_by`, the `canCreateWorkspace` grant declared `via: 'invitation'`, and the recheck after a race. An id the address does not hold, an unverified match, a site-tier id, a deleted row or coven and a malformed id are `NotFound` alike, so an id read off a steward's list tells a stranger nothing; an accepted, declined, revoked or expired row is `Forbidden` in the link's own words. A decline stamps the row inside `withAudit` and grants and seats nothing; if the stamp matches no row, because an accept or a revoke committed since the checks, it reads the row again and reports why. `listReceivedInvitations(session, page)` and `countReceivedInvitations(session, start)`, in `received-invitations.ts`, shape the rows for the account page, which calls them directly (the count also goes to `viewerOf`, once per shell page, for the menu and the landing's notice); there is no GraphQL read. The mutations are `acceptInvitationById(id: ID!): Invitation!` and `declineInvitationById(id: ID!): Invitation!`, open to any signed-in account with the service deciding; `Invitation.declinedAt` is exposed ([`components/received-invitations.md`](../components/received-invitations.md), [`components/pending-invitations.md`](../components/pending-invitations.md)).

**What the link still proves that the list does not.** A verified address proves the mailbox was the person's when it was verified; the link proves it still is at invitation time. An address passed on since could accept a coven invitation meant for its new holder, which the site-tier exclusion bounds to one coven.

**Declined is final.** To join after a decline, the person asks the owner to invite them again, which writes a new row with its own token. The pending filter excludes declined rows, so the account page's list and the shell's count drop it at once; the steward's list uses the open filter, so it keeps the row, marked declined, past its expiry until they remove it.

### Card attempts

`card_invitation_attempts` (`src/modules/coven/schema/card-invitation-attempts.ts`) holds the refused opens of a card link by signed-in accounts: one live row per card, account and reason, with an `attempts` count and `last_attempted_at`, so a repeat open adds to the count and never to the row list.

- `reason` is a CHECK (`revoked`, `expired`, `accepted`), like `invitations.kind`, rather than a Postgres enum: adding a reason is a one-line constraint change in an ordinary migration.
- The unique index on `(invitation_id, user_id, reason)` is what makes a repeat one row.
- The table is marked `namedWrites`. `recordCardAttempt` (identity service `invitation-acceptance.ts`) is its one writer: an upsert that adds 1 to `attempts` and sets `last_attempted_at`.
- **Recorded:** a signed-in account with a verified address opening a card link that is refused as `revoked`, `expired` or `accepted` by another account. **Not recorded:** no session, an unverified account, an unknown token, a token that is not a card, a card still pending, or the account that accepted the card itself. The service returns quietly for each, so a probe learns nothing.
- `findCardAttemptPage` and `findCardAttemptCount` (site keeper only) list one batch's rows, most recent first; `findCardBatchTotals` sums `attempts` over a batch's cards for the Invitation Cards tab's count.

## Invitation acceptance details

`src/modules/identity/services/invitation-acceptance.ts` is the one accept service for both tiers of `invitations`. Holding the token names the invitation, and the session's verified address is what admits. No message names a workspace, since the reader is not yet a member of it (claude-docs/auth/admin-users.md, "Inviting a keeper").

- **Dead-link order.** A link reports one reason: accepted before declined before revoked before expired, so a link in two states always reports the same one. An act beats the clock, and the invitee's answer beats the owner's Remove that may follow a decline, so a declined link keeps saying "This invitation was declined. If you change your mind, ask whoever sent it for a new one." after a steward clears the row. `InvitationRefusal` has `declined`.
- **Deleted coven.** A link into a deleted coven is refused as `closed`, after the dead-link and address checks, so an accepted invitation into a since-deleted coven still says accepted and a stranger learns nothing of the coven. The repository write's own live-workspace check is the backstop. Workspaces are only soft-deleted, so no live coven means a deleted one and no finder of deleted rows is needed. The account page lists live covens only; only the link names the reason.
- **A card's refusal words.** A card has no email and no sender, so its expired, withdrawn and unmatched-code refusals say "This card has expired.", "This card has been withdrawn." and "That code doesn't match a card. Check the link or the QR code printed on the card and try again.", each with "You can still join by invitation: ask a coven to invite you." A found card is known by `kind`; a token that names nothing is taken for a card when it has a card code's shape (`looksLikeCardToken`: 16 symbols of the card alphabet, where an address invitation's token is 43 characters). The account that accepted a card and opens its link again is refused as `used-by-you`, not `accepted`: "You've already used this card. You can start a coven from your account.", and the panel adds a Start a Coven link to `/coven/new`. Another account still reads `accepted`, and `used-by-you` is never recorded as a refused open. Accepting a card lands on `/coven/new?card=accepted`; the marker only selects a sentence, and the page still reads the right from the row.
- **Pause.** While keeper changes are paused, an invitation is accepted only if the primary keeper sent it. Another admin's waits for the resume, so one a rogue admin sent cannot be redeemed meanwhile.
- **Two ways in.** The link's token and the account page's id share one check body so they cannot drift. An id is not a link, so no message says "open the whole link". The writer's own match is the last word.
- **Site tier.** Accepting grants the named site role (curator or keeper) with the creation flag the users CHECK holds both to, declared `via: 'invitation'` with the invitation's note so the trigger on `users` records it as the accepting user's act; the invitation is stamped in the same transaction. An account already holding that role or a higher one has the invitation stamped and nothing granted, so nothing is recorded: an invitation never lowers a role.
- **Workspace tier.** It seats the person at the invited role. A removed member's row is revived, since `(workspace_id, user_id)` is the key and a second insert would collide; a live member is seated nowhere and the invitation only stamped. It also sets `canCreateWorkspace`, declared the same way, which re-grants it to a person a keeper revoked; one who holds it gets no ledger row. The live seat is read before the transaction. If the row is soft-deleted since the read, the stamp rolls back with it.
- **Card kind.** The accept predicate admits any account whose `users.email_verified` is true and says nothing of the address; it is ANDed with `pendingInvitation`, so the first accept stamps the row and a second matches nothing. `checkInvitation` reports an unverified account as `unverified` (the email page) and a used, expired or revoked card with its own reason, none naming a batch. Accepting sets `canCreateWorkspace` only, with `via: 'card'` in the privilege ledger: no seat and no site role. The by-id path and the received list read address-kind workspace rows only, so a card is never returned by them.
- **Card arrivals.** `findCardArrivalPage` and `findCardArrivalCount` (site keeper only) answer "which accounts arrived by card, when, and from which batch" from accepted card rows ordered by `accepted_at`, newest first. `revokeInvitationCardBatch` touches pending cards only; `findCardBatchPage`, `findCardBatchCount` and `findCardBatchTotals` list one row per batch with its counts, so an accepted card row, the permanent record of an arrival, is never changed.
