## The ingredient identity model

DESIGN.md §5 specifies the tables below. This file describes them as built.

- **`ingredients`** (`src/modules/ingredients/schema/ingredients.ts`) — `id`, `workspaceId` (nullable: `NULL` is the compendium tier, non-null is a workspace's own ingredient), `name`, `slug` (["Ingredient slugs"](ingredient-slugs.md)), `canonicalName`, `nomenclature`, the generated `identityKey` (below), the correspondence columns (`description`, `elements[]`, `celestialBodies[]`, `zodiacSigns[]`, `colors[]`, `safetyNotes`), `toxic` (a yes/no, default no; each form carries its own, which never unions with this one — DESIGN.md §5), `seedKey`, `revision`, + audit.
  - `seedKey` is the key the compendium seed gives an entry it writes, so an entry an admin renames is not seeded again beside itself. It is null on every other row, the `standard` fixture's included (DESIGN.md §5, "`seedKey`").
  - `revision` is `integer NOT NULL DEFAULT 1`, raised by one by the `bump_revision` trigger on every update, the same counter and function `spells` uses (["Revision"](grimoire.md)). One column guards the whole ingredient form, children included.
  - `name` is the display label, what it is called _here_, and stays freely relabellable, because identity sits on the formal name, `canonicalName`, and its `nomenclature`.
  - The row has no form: each form an ingredient comes in is a row of `ingredient_variants` beneath it (below).
  - Of the correspondences only `elements` is constrained: a list of the `ingredient_element` `pgEnum` of `earth`, `air`, `fire`, `water`, `spirit`, closed and fixed. That is the exact opposite of a variant's `form`, and the reason the two are easy to confuse but never interchangeable.
  - `celestialBodies`, `zodiacSigns` and `colors` are native `text[]` columns, one of the things SQLite could not have run (DESIGN.md §14).
  - Eight declared indexes: the three partial unique ones below, the identity pair on `identity_key`, the two on the slug (["Ingredient slugs"](ingredient-slugs.md)), `ingredients_seed_key_unique` on live keyed rows, `ingredients_trgm` (one multicolumn `gin_trgm_ops` index over `name` and `canonical_name`; see ["Fuzzy matching"](fuzzy-matching.md)) and its folded twin `ingredients_unaccent_trgm` (["The compendium read"](compendium-read.md)).
- **`ingredient_folk_names`** (`src/modules/ingredients/schema/ingredient-folk-names.ts`) — `id`, `ingredientId` (FK to `ingredients`), `name`, + audit. Common names, one row each, scoped to the ingredient that claims them. Two indexes: `ingredient_folk_names_unique` over `(ingredient_id, lower(name))`, partial on `deleted_at IS NULL`, and `ingredient_folk_names_trgm`, a plain `gin_trgm_ops` index on `name`, which is what common-name matching reads. The surrogate `id` is not redundant beside that unique index: the index is unique among _live_ rows only and a primary key carries no predicate, and a promotion swaps one named row rather than reconstructing a pair. No locale or region column: DESIGN.md §5 records no regional requirement and nothing renders one.
- **`ingredient_substitutes`** (the model is in DESIGN.md §5) — `id`, `ingredientId`, `substituteId` (nullable FK to `ingredients`), `name` (nullable), + audit. One row per substitute, a link or a typed name: three CHECKs hold exactly one of the two, a non-blank name and no link to its own ingredient. Three indexes, all partial on `deleted_at IS NULL`: the parent's, and two unique ones, one link per ingredient and one name per ingredient case-folded, each over its own kind of row. None leads on `substitute_id`, since nothing reads back from a linked ingredient. It replaced a `substitutes[]` column: the migration copied every entry across as a name, trimmed, blanks skipped, an entry repeated in any case kept once in the spelling it first holds (`0032_ingredient-substitutes.sql`); the later drop copied across any entry with no row yet in any case, live or removed, since by then the table was newer than the list (`0039`).
- **`ingredient_deities`** (`0040_picked-form-and-deities.sql`; the model is in DESIGN.md §5) — `id`, `ingredientId`, `deityId` (nullable FK to `deities`), `name`, `position`, + audit. One row per deity, in the order entered: a name on every row, and a link beside it when the member picked a curated deity. `name` is held on a linked row too, in the curated row's spelling, so a link whose deity is soft-deleted reads as its name under the ordinary filter, and a CHECK holds it non-blank. Three unique indexes, all partial on `deleted_at IS NULL`: one position per ingredient, which is also the parent's index, read in order; one link per ingredient and deity; and one unlinked name per ingredient, case-folded, so links to two same-named deities may sit on one ingredient. It replaced a `deities[]` column (`0041` filled it unlinked in the array's order from position 0; `0048_drop-deities-list` copied across what the deploy before the switch had written to the list since, after each ingredient's rows, then dropped it). Readers and writers: ["Ingredient children"](ingredient-children.md); the decision is [`../design-decisions/mb.165-record-the-picked-vocabulary-row.md`](../design-decisions/mb.165-record-the-picked-vocabulary-row.md).
- **`ingredient_forms`** (`src/modules/vocabulary/schema/ingredient-forms.ts`) — `id`, `name`, `slug`, `groupId`, `description`, + audit. Shaped like `categories`: global, keeper-curated, no workspace scoping. This is the third resource keepers curate globally, alongside the compendium and categories (CLAUDE.md). Its `groupId` points at `ingredient_form_groups`, keeper-curated in turn; see the [categories section](categories.md).

**`nomenclature`** is a seven-value `pgEnum`, `NOT NULL` with no default: `botanical`, `fungal`, `zoological`, `mineral`, `chemical`, `unknown`, `none`. It names _which naming system_ a formal name belongs to, not which rank within that system: `Quartz var. amethyst` and `Lapis lazuli` are both `mineral` even though one is an IMA variety and the other a rock. `unknown` and `none` are both answers, not the absence of one. `unknown` means a formal name exists in some system but which one is not settled; the name may be recorded, unconfirmed, or not yet looked up (§5 says why that earns a value of its own). `none` is the positive claim that no naming system names this thing at all (graveyard dirt, moon water, black salt). A CHECK ties the kind to the name, `nomenclature = 'unknown' OR (nomenclature = 'none') = (canonical_name IS NULL)`, enforced in both directions, so `none` never carries a formal name and a named kind never lacks one, while `unknown` takes either.

**`identity_key`**, the generated identity column, is DESIGN.md §5's `GENERATED ALWAYS AS (lower(coalesce(canonical_name, name))) STORED`: the lower-cased formal name, or the label where there is none, and never the form. Both functions in it, `lower` and `COALESCE`, are IMMUTABLE, which Postgres requires of anything inside a generated column (and of an expression index). That is also why a form was never a `pgEnum` in a key: a cast to an enum type raises an immutability question a plain `text` column does not.

**Two CHECKs hold the table's names**: `ingredients_nomenclature_declares_canonical_name` (the kind-to-name CHECK above) and `ingredients_canonical_name_not_blank`. The non-blank check exists because `btrim(x) <> ''` is what the kind-to-name CHECK cannot say for itself: `canonical_name = '   '` satisfies "not null" while contributing nothing to the identity key. A variant's form has its own, `ingredient_variants_form_not_blank`. The expressions, and the generated column's, are written as literal SQL rather than interpolated Drizzle columns, and transcribe DESIGN.md §5's SQL verbatim. The generated column has no choice: it names columns of the table whose column object is still being built, so there is nothing to interpolate from. Postgres itself would accept a table-qualified self-reference in either place (verified on 18.6); the limitation is Drizzle's.

**How the table is tested.** The worker's `sorrel_test_<n>` clone arrives with every migration applied and the `standard` scenario seeded, re-cloned that way before each test file (`testing/where-tests-live.md`), so `tests/modules/ingredients/schema/ingredients-schema.test.ts` asserts against the real table as production's migrations built it: no DDL is applied or hand-copied in the test, and nothing is dropped afterwards. Its `beforeEach` is `truncate ingredients cascade`, because the seeded compendium has category and folk-name links behind `NO ACTION` foreign keys, so a `delete` would be refused. Its author and workspace are the seed's (`FIXTURE_USERS.A`, workspace W). The shape half of the file needs no database at all and reads `getTableConfig`, the same as `workspaces-schema.test.ts`.

**Three partial unique indexes, not two, and indexes rather than constraints.** `ingredients_compendium_identity_key_unique` on `identity_key` in the compendium tier, and `ingredients_workspace_identity_key_unique` on `(workspace_id, identity_key)` and `ingredients_workspace_label_unique` on `(workspace_id, lower(name))` in the workspace tier. All three carry `WHERE deleted_at IS NULL`, per the [partial-index convention](soft-delete.md): deleting a row must not permanently reserve its identity or its label (CLAUDE.md rule 4). The label index is workspace-tier only. Inside one workspace an ambiguous label is a mistake, but the compendium deliberately allows several rows to display the same label (four unrelated "Cat's Claw" entries) as long as they are different identities; the formal name that keeps them apart is in the slug too (["Ingredient slugs"](ingredient-slugs.md)). They are indexes rather than unique constraints because Drizzle's `nullsNotDistinct()` exists only on constraints, and a constraint cannot carry a `WHERE` predicate at all; since every unique index in this schema must be partial, the constraint form was never on the table. Two indexes over the two tiers rather than one over `(workspace_id, identity_key)` for the same reason: without `NULLS NOT DISTINCT`, every compendium row's null `workspace_id` would be distinct from every other's and a single index would reserve nothing there.

**The predicates are asserted by behaviour, once for every table.** `tests/db/partial-unique-indexes.test.ts` reads each partial unique index from the catalogue and proves a second live row refused and a soft-deleted holder's slot freed, which is what catches a dropped `WHERE deleted_at IS NULL`; `tests/db/schema-drift.test.ts` holds each index's name and partiality to the schema file's. What stays in `tests/modules/ingredients/schema/ingredients-indexes.test.ts` is what each index refuses that the others do not: identity in the compendium, identity and the folded label per workspace, and the slug per tier.

**A variant's `form` is `text`, and deliberately not a foreign key to `ingredient_forms`.** To a coven the curated table is an autofill vocabulary, not a constraint: a foreign key would make an uncurated value like `rhizome` unwritable until a keeper curates it first. `ingredients-schema.test.ts` asserts the ingredient's own foreign keys are its workspace and nothing else, since that is the property the whole free-text design rests on.

**A pick is recorded beside the text.** A variant's `form_id` is a nullable foreign key to `ingredient_forms`, set only when a member picked a curated row, never resolved from typed text. A variant's `form` is `NOT NULL`, so a pick always stands beside its text and needs no CHECK of its own. The pick is outside `ingredient_variants_form_unique`, which folds the text, so two forms of one ingredient, one picked as each Wax, still fold to one form, and a link to a soft-deleted form reads as no link, the text staying. A save writes a pick only of a curated form, live under a live group, beside text folding to its name and written in its spelling; anything else is refused beside the variant's `formId` or `form`, and a save sending no `formId` clears the column and keeps the text. The deities take the same model in `ingredient_deities`, so a vocabulary a member writes is text with an optional link to the curated row picked.

**The compendium tier is held to the vocabularies, by the service.** Each of a compendium entry's forms and each of its deities is a pick of a live curated row (a form under a live group, a deity under a live tradition), so a curated value typed rather than picked is refused as an uncurated one is. Its `celestialBodies` and `zodiacSigns` each name one, matched as the suggestions fold, `lower(btrim(value)) = lower(name)`. Every value is stored in its row's own spelling. `createCompendiumEntry` and `updateCompendiumEntry` enforce it after the parse, the picks through `resolvePicks` and the celestial bodies and signs through `curatedSpellings` in `vocabulary`, and refuse a value as a `ValidationError` at `['variants', i, 'form']` or `['variants', i, 'formId']`, or `['celestialBodies', i]`, `['zodiacSigns', i]` or `['deities', i]` at the entry sent ([`../validation.md`](../validation.md), "The two ingredient variants"). Not Zod, since the check reads the database, and not a key or a CHECK, since the columns are shared with the coven tier, which keeps free text. Deleting a curated row a live entry holds (a form or deity it picks, or a celestial body or sign's last live spelling) is refused, and renaming one carries onto the entries, so the rule holds after the write as well ([`../design-decisions/mb.162-compendium-holds-curated-values.md`](../design-decisions/mb.162-compendium-holds-curated-values.md)). A form rename is carried onto the entry's variants that picked the form and moves no slug, a form being no part of the entry's identity or address.

**Folk names got their own table instead of staying `folkNames text[]` because of one verified fact.** On this repo's live PostgreSQL 18.6, `array_to_string` is **STABLE** (`pg_proc.provolatile = 's'`), not IMMUTABLE, so it is legal in neither a generated column nor an expression index; a trigram index over a `text[]` column would have needed a hand-written IMMUTABLE wrapper. As a normalized table, `ingredient_folk_names` carries a plain `gin_trgm_ops` index on `name` directly, plus a unique index on `(ingredient_id, lower(name))` partial on `deleted_at IS NULL`. Uniqueness is per ingredient, deliberately not global, since several unrelated ingredients claiming the same common name is exactly what is being documented, not an error. `lower`, `btrim`, and `similarity`, by contrast, are all IMMUTABLE and used freely throughout this model.

**Celestial bodies, zodiac signs and colours are lists.** DESIGN.md §5 gives an ingredient several of each, so they are `celestial_bodies`, `zodiac_signs` and `colors`, nullable `text[]` with no default, declared in Drizzle as `celestialBodies`, `zodiacSigns` and `colors`. The shared schema trims each entry, drops a blank one, refuses a repeat but for case and spacing (at the repeat) and turns a list left empty into null ([`../validation.md`](../validation.md), "The two ingredient variants"), so no row holds `{}` or a blank entry, and no CHECK repeats that. An array keeps its order, and each list's order is the member's, so nothing sorts one on write or read.

- **Arrays, not child tables, unlike folk names.** Folk names moved to a table so a trigram index could reach them. No single column carried one (the celestial body and zodiac autofill reads the in-use values of the compendium and one workspace with no index behind them), so a list loses no index, and a table per list would buy three joins for nothing.
- **A new name, by rule 10.** A column cannot turn from `text` to `text[]` under a deployed reader, so the lists sat beside the singles for a deploy: `0030_ingredient-lists` added them and filled each from its single column where one was set; the switch read and wrote the lists and stopped declaring the singles, which stayed in the database undeclared; `0036_drop-ingredient-singles` dropped them, with its `.ack.md` sidecar, once a release carrying the switch had reached production (["Expand/contract"](expand-contract.md)).
- **The switch's migration rederived the lists.** `0031_refill-ingredient-lists` ran before the switch promoted, while only `0030` had written a list, so every list was still its single's. Each was set to its single as one entry, or to null where the single was, for whatever the live deploy wrote after `0030` (a new row, a changed value, a cleared one). Only a row that disagrees was written, so `updated_at` moved on no other. It is `generate --custom`, which copies the last snapshot rather than diffing the schema, so the snapshot kept the undeclared singles and the later `db:generate` still emitted their drop.
- **The drop filled nothing first.** Once the switch promoted it wrote the lists, so a single that disagrees with its list may hold the previous deploy's write between `0031` and the promotion, or the stale value of a list a member has edited since, and the row cannot say which. A fill would overwrite that member's edit to recover a write from a deploy-length window, one the app had not read since the switch went live, so the drop took it (`0036_drop-ingredient-singles.ack.md`, "What is lost").
- **The in-use scan unnests.** Tier 2 of the celestial body and zodiac autofill reads entries rather than a column: `cross join lateral unnest(…)` gives one row per entry before anything trims or folds it, so a value counts once however many lists hold it, or however often one does (["The member's autofill"](member-autofill.md)). The deity autofill reads `ingredient_deities`' live rows.

**Elements are a list.** DESIGN.md §5 gives an ingredient several elements, so `elements` is a nullable `ingredient_element[]` with no default, declared in Drizzle as `ingredientElement('elements').array()`. The set stays the `pgEnum`'s five, so the array's type refuses anything else and no CHECK says it again. The shared schema refuses a repeat and turns a list left empty into null ([`../validation.md`](../validation.md), "The two ingredient variants"), so no row holds `{}` or one element twice. No CHECK repeats either: comparing an array's entries with each other needs a subquery or a hand-written function, and the free-text lists carry no CHECK. The array keeps the order chosen, and nothing sorts it.

- **A new name, by rule 10**, as the lists took one: `0034_element-list` added `elements` and filled it from `element` where one was set, as a one-entry list; the switch stopped declaring `element`, and its migration `0035_refill-element-list` rederived the list from `element` for whatever the live deploy wrote after `0034`, as `0031` did, writing only a row that disagrees; `0037_drop-element` dropped `element` once the switch had deployed, with its `.ack.md` sidecar. The `ingredient_element` type stays, since the list is of it. The seed writes lists, and two of its compendium entries hold more than one element.
- **The drop filled nothing either**, for the lists' reason: a single that disagrees with its list may hold the old deploy's write between `0035` and the promotion, or the stale value of a list a member has edited since, and copying it in would bring back an element that member removed (`0037_drop-element.ack.md`, "What is lost").
- **The filter reads containment.** The element filter matches a row whose list holds the element chosen, among others or alone: Drizzle's `arrayContains`, `@>`, rather than an equality. No index stands behind it, as none stands behind any list; it ANDs onto the compendium read's other predicates over one tier.

**Identity is the formal name alone, and each form is a variant.** DESIGN.md §5 keys an ingredient on `identity_key`, unique per tier, and holds each form it comes in as a row of `ingredient_variants` beneath it, one live row per ingredient and folded form, so Rosemary the herb and Rosemary the oil are one entry with two variants. A variant adds to its ingredient and never overrides it, and carries its own description, safety notes, correspondences, categories, substitutes and references, while deities and folk names stay on the ingredient ([`../design-decisions/mb.215-ingredient-variants.md`](../design-decisions/mb.215-ingredient-variants.md)). Before it, the key had the trimmed, lower-cased form appended after `::`, which let _Valeriana officinalis_ root and leaf exist as two separate identities. A variant's `form` stays text and not a foreign key, for the reason above.

**Fuzzy matching: one index, and a rule every caller is bound by** has a file of its own: [`fuzzy-matching.md`](fuzzy-matching.md).

**Ingredient slugs** has a file of its own: [`ingredient-slugs.md`](ingredient-slugs.md).

**The variants table.** One form of an ingredient is a row of `ingredient_variants` (`src/modules/ingredients/schema/ingredient-variants.ts`, migration `0061_ingredient-variants.sql`): `ingredient_id`, `form` (text, non-blank by `ingredient_variants_form_not_blank`), `form_id` (the curated pick), `description`, `safety_notes`, the four lists, and the six audit columns, with its own `set_updated_at` trigger. It is an ingredient's child, so the unscoped finders refuse it at compile time.

- `ingredient_variants_form_unique` holds one live row per ingredient and `lower(btrim(form))`.
- `ingredient_variants_id_ingredient_id_unique` on `(id, ingredient_id)` is the one unique index on a soft-deleted table that is not partial. It is the target of the composite foreign keys below, which a partial index cannot be, and reserves nothing the primary key does not. `tests/db/partial-unique-indexes.test.ts` names it as rule 4's exception and fails any other.
- `ingredient_variants_form_id_idx` (partial) and `ingredient_variants_unaccent_trgm` (a trigram index over the folded form and description) serve the in-use reads and the search.

`ingredients.identity_key` is built by `identityKeyOf`: the formal name, or the label where there is none, and never the form. Since `0062`, _Valeriana officinalis_ root and leaf are one entry with two variants, and a write of the second as an entry of its own is refused by the identity-key index, which the compendium and coven services map.

**Identity as every reader and writer uses it.** `findCompendiumEntryByIdentity({ name, canonicalName })` and its coven twin, `findWorkspaceIngredientByIdentity` under the proof, compare `identity_key` through `identityKeyOf`, and `IngredientIdentity` carries no form. Both services' `refuseCollision` map the identity-key indexes to `canonicalName`, or to `name` for an entry with no formal name, naming the entry already holding it through `describeEntry` and pointing at adding the form to it. Postgres names the first index it finds broken, and the address index and a coven's label index are older than the identity one, so an oil written under the herb's own label meets one of them first: each of those branches looks for an identity holder before its own message, so the refusal is the formal name's whichever index spoke. `ingredientSlug` takes the label and the formal name.

`0062_ingredient-variants-fill.sql` filled one variant per row with a form, soft-deleted rows included: the trimmed form and its pick, stamped as the row's last editor. The correspondences stayed on the ingredient, since a variant adds to its ingredient and never overrides it. A `DO` block then refused a database holding two live rows of one `identity_key` in a tier, with a hint naming "Merging a group" in [`mb.215-ingredient-variants.md`](../design-decisions/mb.215-ingredient-variants.md), before the two indexes were created. The pre-flight query, which must return no row: `select workspace_id, lower(coalesce(canonical_name, name)), count(*) from ingredients where deleted_at is null group by 1, 2 having count(*) > 1`. The migration's data tests retired once `0062` reached production's journal (`testing/layer-ownership.md`, "What a test may assert", rule 7).

**What names a variant.** Migration `0063_variant-children.sql` gives four tables a `variant_id` held to their `ingredient_id` by a composite foreign key, `(variant_id, ingredient_id) → ingredient_variants (id, ingredient_id)`, declared with Drizzle's `foreignKey` against the non-partial `(id, ingredient_id)` index, so no row pairs one ingredient with another's form. The key is `MATCH SIMPLE`, which skips the check when either column is null, so a CHECK closes the gap wherever the ingredient may be null.

- `inventory_items.variant_id`, NOT NULL; one live row per coven and variant.
- `spell_ingredients.variant_id` (the table is `spell_steps` since the rename), set exactly when `ingredient_id` is; one live layer per jar and variant. `0063` filled every linked layer from its ingredient's one live variant, behind a guard refusing a database where one has none or several.
- `ingredient_categories.variant_id`, nullable: the pair primary key became two unique indexes, one on the parent's pairs and one on a form's ([`ingredient_categories`](categories.md)).
- `ingredient_substitutes.variant_id`, the form a row stands in for, and `substitute_variant_id`, the linked ingredient's form, under its own composite key against `substitute_id` and a CHECK that it has one beside it. `ingredient_substitutes_not_itself` is narrowed to the same ingredient _and_ the same form, so a sibling form may stand in, and the link and name uniqueness split by whether `variant_id` is set.
- `reference_links.ingredient_variant_id`, one entry in the `SOURCED` registry ([References](references.md)).

The stock service writes `variant_id` on stock; the grimoire writes it on layers; the ingredient services write a form's categories, substitutes and references. `tests/db/migrations/0063-variant-children.test.ts` re-runs the fill and the guard, and retires once `0063` is in production's journal (`testing/layer-ownership.md`, "What a test may assert", rule 7).

**The old model's drop.** Migration `0064_drop-form-and-canonical-key.sql` dropped `canonical_key`, `form` and `form_id` from `ingredients`, the indexes `ingredients_compendium_identity_unique`, `ingredients_workspace_identity_unique` and `ingredients_compendium_form_id_idx`, the CHECKs `ingredients_form_not_blank` and `ingredients_form_id_has_form`, and the pick's foreign key `ingredients_form_id_ingredient_forms_id_fk`. `canonical_key` is dropped before `form`, the reverse of the order `db:generate` wrote, since Postgres refuses to drop a column a generated column reads. Nothing is lost: every form has been a variant since `0062` (`0064_drop-form-and-canonical-key.ack.md`).

## Ingredient table details

Notes that used to sit as comments on `src/modules/ingredients/schema/ingredients.ts`.

- **Identity key.** `identityKey` is the formal name, falling back to the label, and never the form. The generated column's expression and the finder's comparison come from one builder, so the key has one spelling. The column names are raw because they name columns of the table still being built; every function in the key is IMMUTABLE and no enum cast is involved, which is what makes a stored generated column legal. The text is the migrations' own, byte for byte, so `db:generate` sees no change. GENERATED ALWAYS means Postgres refuses a direct write, and Drizzle omits generated columns from `$inferInsert`, so TypeScript refuses first.
- **Slug.** The public address is `ingredientSlug` of the label and the formal name (src/lib/slugify.ts), with no form. It has no default: one in SQL would be a second slug rule, so a row written earlier keeps its form in the slug until its next save.
- **Nomenclature.** The database has no default: the workspace-local Zod variant supplies `none` and the compendium variant makes the admin answer. The CHECK has three cases: `none` carries no formal name, a named kind must, and `unknown` takes either. Zod enforces it too, so the CHECK is never what a user sees. A second CHECK stops a blank formal name keying nothing.
- **Toxic flag.** The ingredient's flag is its own and is never read into a form or out of one; each form carries its own (DESIGN.md §5, "The toxic flag is the one exception").
- **Seed hash.** `seedHash` is the sha256 of the seeded fields of the markdown file the entry was last written from, so the seed can tell a changed file from an unchanged one and apply a correction. Null until the seed writes it, and always null on a coven's own entry. It is not a stamp: the trigger leaves `updated_at` alone when only this changes (migration 0081). A hash is 64 lower-case hex characters or nothing, because a truncated or upper-cased one would never equal a file's and would queue a correction forever.
- **Review mark.** `reviewedAt` and `reviewedBy` are set together or both null, since one without the other says nothing a reader can trust. A reviewed entry is one the seed never overwrites. Only the review service writes them, and like the hash they are never a change to the content, so the trigger ignores both.
- **Seed key.** `seedKey` is the key the compendium seed gives the entry it writes, so an entry a keeper renames is not seeded again beside itself. The `standard` fixture keys on identity and writes none.
- **Indexes.** The formal name is unique once per tier whatever the form, as two indexes: a constraint carries no WHERE and `nullsNotDistinct()` exists only on constraints. Label uniqueness is the workspace tier only: inside one drawer an ambiguous label is a mistake, in the compendium it is the point. The slug index for the workspace tier carries no tier predicate, as DESIGN.md §5 writes it, because a null `workspace_id` collides with nothing in a btree.
- **Shown flag.** `shown` says whether the public compendium shows the entry: `true` by default, so every row there already reads as shown. A hidden entry is kept, never deleted, and a coven's own entry is always shown. A curator sets it through one service, the seed sets it only when it first lands an entry (hidden when neither the entry nor any of its forms names a category), and every public read excludes `shown = false` in SQL, while admin screens and a coven's cupboard still see the entry. Migration `0109` applied that same rule once to the rows already there, since nobody could have chosen Show or Hide before it, and migration `0117` hid once every live shown entry with no live category (the category and its group live, the pair on the entry or on a live form). `ingredients_tier_shown`, on `(workspace_id, shown)` where `deleted_at IS NULL`, serves that read.
- **Trigram indexes.** One multicolumn `gin_trgm_ops` index serves a predicate on either column alone (asserted by EXPLAIN in ingredients-trigram.test.ts). It is not partial. A match must be written `name % $1` under a per-transaction `pg_trgm.similarity_threshold`, never `similarity(name, $1) > 0.4`, which no trigram index can answer. The folded twin goes through `unaccent_immutable` (migration 0026) for the compendium search's accent-insensitive `<%`; only an expression index lets a fold reach a trigram index. It sits beside the raw one because the fuzzy finders still match the raw columns.

### Workspaces and membership

`src/modules/coven/schema/workspaces.ts` holds DESIGN.md §5's two workspace tables and the `workspace_role` enum (`viewer`, `member`, `owner`). The declaration order reads as a hierarchy and is not one: each role has its own permission statements, so nothing compares two roles (see ["The Membership proof"](membership-proof.md)). `0004_black_slyde.sql` is the migration.

- **`workspaces`** — `id`, `name`, `slug`, + audit, and **nothing else**. There is no `kind` column and no automatically created workspace: every workspace behaves identically, taking members and being deleted by a steward. `workspaces-schema.test.ts` pins the whole column set rather than asserting the absence of one name, so a later `kind`/`type`/`personal` column turns it red instead of going unnoticed. The entity is `workspaces` even though it routes under `/coven/[slug]`; only the URL segment says coven (§5's naming note).
- **`workspaces_slug_unique`** is partial on `deleted_at IS NULL`, per the [partial-index convention](soft-delete.md): the slug is what `/coven/[slug]` routes on, so a plain unique constraint would let a deleted workspace hold a name hostage forever.
- **`workspace_members`** — `workspaceId`, `userId`, `role`, `joinedAt`, `invitedBy` (nullable), + audit, with a composite primary key on the pair and no surrogate `id`. The pair _is_ the membership's identity: a surrogate key would let the same user join the same workspace twice, with two rows disagreeing about their role.
  - `joinedAt` is deliberately distinct from `created_at`: a role change rewrites the row without changing when the person joined.
  - `invitedBy` references `users.id` and holds the sender of the invitation that seated the person. It is not `created_by`, which is the person who accepted, since acceptance runs under their session. It is written at the moment of seating, not worked out later from `invitations`: a person removed and invited back has several accepted invitations, and the database clock (`accepted_at`) and the app clock (`joined_at`) need not order them the same way. Revival overwrites it, a role change leaves it, a creator has null, and the name resolves through the co-member finder, which still names someone removed since.
- **`owner` is a role here but not an invitable one.** That narrowing lives on `invitations`, whose check constraint rejects it; see ["Invitations"](invitations.md). The Steward role is granted afterwards by an existing steward on the members page.
- Both tables carry the full six-column audit spread, and every `*_by` column references `users.id`. `workspace_members` keeps all six despite being a join table: two other join tables hard-delete, and this is not one of them, because who removed whom, and when, is worth keeping.

### The provisional-account delete

`deleteLapsedProvisionalUser(userId, lifetimeSeconds, capSeconds)` is the one hard delete of a table carrying `deleted_at`, and it is a named export rather than a loosening of `write.delete`'s type. It removes the one `users` row named, if it is unverified, holds at least one `accounts` row, and has an `updated_at` older than `now()` minus the lifetime or a `created_at` older than `now()` minus the cap, and answers whether it did. Both cutoffs are the database's clock, as the columns are. The `EXISTS` over `accounts` is `existsIn`'s, so the delete builds no read of its own.

`accounts` and `sessions` follow by their `ON DELETE CASCADE`, as do the account's rows in `user_access_pauses`, `workspace_member_pauses` and `support_timeouts`, whose `user_id` cascades too (`support_timeouts.user_id` was a plain foreign key until migration 0120 re-added it with `ON DELETE CASCADE`). A pause or a support time-out sanctions the account it names and records nothing else, so unlike the privilege ledger below it neither keeps the account nor blocks the delete.

`provisionalSecondsLeft(userId, ...)` is its read-only partner: how long until the row lapses, or null when it will not (it is verified, vouched for, has no provider account, or is gone). The expiry job's step calls the two in turn.

It skips a row holding any `user_privilege_changes` row, as `not(existsIn(...))`, the negation `citesNothing` uses. Such an account is one a keeper has vouched for, and the ledger references it with a plain foreign key, so deleting it would fail. The rows are not deleted with it either: `forbid_rewrite` refuses that, and the ledger is the history.

It is hard for a reason outside this layer: Better Auth reads `users` by address with no `deleted_at` filter, so a tombstone would keep refusing the owner's sign-in. It runs outside `withAudit` because no surviving row is left to stamp, though its caller is a job whose other writes would run as the System actor. Two partial indexes serve it, one per half of the `OR`: `users_provisional_updated_at_idx` and `users_provisional_created_at_idx`, each `WHERE email_verified = false`. The rest is [`auth/admin-bootstrap.md`](../auth/admin-bootstrap.md), "Provisional accounts".
