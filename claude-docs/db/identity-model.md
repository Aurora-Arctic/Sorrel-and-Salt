## The ingredient identity model

DESIGN.md §5 specifies the tables below. This file holds the rules and constraints behind them; the column lists are the schema files'.

- **`ingredients`** (`src/modules/ingredients/schema/ingredients.ts`): `workspaceId` is nullable (`NULL` is the compendium tier, non-null a workspace's own ingredient). `name` is the display label, what it is called _here_, and stays freely relabellable, because identity sits on the formal name, `canonicalName`, and its `nomenclature`. The generated `identityKey` is below. `toxic` is a yes/no, default no; each form carries its own, which never unions with this one and is never read into a form or out of one (DESIGN.md §5, "The toxic flag is the one exception"). The row has no form: each form an ingredient comes in is a row of `ingredient_variants` beneath it.
  - `slug`: see ["Ingredient slugs"](ingredient-slugs.md). It has no SQL default, because one would be a second slug rule.
  - `seedKey` is the key the compendium seed gives an entry it writes, so an entry an admin renames is not seeded again beside itself. It is null on every other row, the `standard` fixture's included (DESIGN.md §5, "`seedKey`").
  - `seedHash` is the sha256 of the seeded fields of the markdown file the entry was last written from, so the seed can tell a changed file from an unchanged one. Null until the seed writes it, and always null on a coven's own entry. It is not a stamp: the trigger leaves `updated_at` alone when only this changes. A hash is 64 lower-case hex characters or nothing, because a truncated or upper-cased one would never equal a file's and would queue a correction forever.
  - `reviewedAt` and `reviewedBy` are set together or both null, since one without the other says nothing a reader can trust. A reviewed entry is one the seed never overwrites. Only the review service writes them, and like the hash they are never a change to the content, so the trigger ignores both.
  - `shown` says whether the public compendium shows the entry: `true` by default. A hidden entry is kept, never deleted, and a coven's own entry is always shown. A curator sets it through one service, the seed sets it only when it first lands an entry (hidden when neither the entry nor any of its forms names a category), and every public read excludes `shown = false` in SQL, while admin screens and a coven's cupboard still see the entry. `ingredients_tier_shown` on `(workspace_id, shown)` where `deleted_at IS NULL` serves that read.
  - `revision` is `integer NOT NULL DEFAULT 1`, raised by the `bump_revision` trigger on every update, the same counter and function `spells` uses (["Revision"](grimoire.md)). One column guards the whole ingredient form, children included.
  - Of the correspondences only `elements` is constrained: a list of the `ingredient_element` `pgEnum` (`earth`, `air`, `fire`, `water`, `spirit`), closed and fixed. That is the opposite of a variant's `form`, and the two are never interchangeable.
  - Indexes: the three partial unique ones below, the identity pair on `identity_key`, the two on the slug, `ingredients_seed_key_unique` on live keyed rows, `ingredients_trgm` and its folded twin `ingredients_unaccent_trgm` (below).
- **`ingredient_folk_names`** (`src/modules/ingredients/schema/ingredient-folk-names.ts`): common names, one row each, scoped to the ingredient that claims them. `ingredient_folk_names_unique` over `(ingredient_id, lower(name))` is partial on `deleted_at IS NULL`, and `ingredient_folk_names_trgm`, a plain `gin_trgm_ops` index on `name`, is what common-name matching reads. The surrogate `id` is not redundant beside the unique index: the index is unique among _live_ rows only and a primary key carries no predicate, and a promotion swaps one named row rather than reconstructing a pair. No locale or region column: DESIGN.md §5 records no regional requirement.
- **`ingredient_substitutes`** (DESIGN.md §5): one row per substitute, a link (`substituteId`, nullable FK to `ingredients`) or a typed `name` (nullable). Three CHECKs hold exactly one of the two, a non-blank name and no link to its own ingredient. Three indexes, all partial on `deleted_at IS NULL`: the parent's, and two unique ones, one link per ingredient and one name per ingredient case-folded, each over its own kind of row. None leads on `substitute_id`, since nothing reads back from a linked ingredient.
- **`ingredient_deities`** (DESIGN.md §5): one row per deity, in the order entered (`position`): a `name` on every row, and a `deityId` link beside it when the member picked a curated deity. `name` is held on a linked row too, in the curated row's spelling, so a link whose deity is soft-deleted reads as its name under the ordinary filter, and a CHECK holds it non-blank. Three unique indexes, all partial on `deleted_at IS NULL`: one position per ingredient (also the parent's index, read in order); one link per ingredient and deity; and one unlinked name per ingredient, case-folded, so links to two same-named deities may sit on one ingredient. Readers and writers: ["Ingredient children"](ingredient-children.md); the decision is [`ingredients.md`, "A picked form or deity is recorded beside its text"](../design-decisions/ingredients.md#a-picked-form-or-deity-is-recorded-beside-its-text).
- **`ingredient_forms`** (`src/modules/vocabulary/schema/ingredient-forms.ts`): shaped like `categories`: global, keeper-curated, no workspace scoping, the third resource keepers curate globally beside the compendium and categories (CLAUDE.md). Its `groupId` points at `ingredient_form_groups`, keeper-curated in turn ([categories](categories.md)).

**`nomenclature`** is a seven-value `pgEnum`, `NOT NULL` with no default (the workspace-local Zod variant supplies `none`; the compendium variant makes the admin answer): `botanical`, `fungal`, `zoological`, `mineral`, `chemical`, `unknown`, `none`. It names _which naming system_ a formal name belongs to, not which rank within that system: `Quartz var. amethyst` and `Lapis lazuli` are both `mineral`. `unknown` and `none` are both answers, not the absence of one. `unknown` means a formal name exists in some system but which one is not settled (§5 says why that earns a value of its own). `none` is the positive claim that no naming system names this thing at all (graveyard dirt, moon water, black salt). A CHECK ties the kind to the name, `nomenclature = 'unknown' OR (nomenclature = 'none') = (canonical_name IS NULL)`, in both directions, so `none` never carries a formal name and a named kind never lacks one, while `unknown` takes either. Zod enforces it too, so the CHECK is never what a user sees.

**`identity_key`**, the generated identity column, is DESIGN.md §5's `GENERATED ALWAYS AS (lower(coalesce(canonical_name, name))) STORED`: the lower-cased formal name, or the label where there is none, and never the form. Both functions in it are IMMUTABLE, which Postgres requires of anything inside a generated column or an expression index; a cast to an enum type raises an immutability question a plain `text` column does not, which is also why a form is never a `pgEnum` in a key. The generated column's expression and the finder's comparison come from one builder (`identityKeyOf`), so the key has one spelling. The expressions are written as literal SQL rather than interpolated Drizzle columns, because the generated column names columns of the table whose column object is still being built (the limitation is Drizzle's, not Postgres's), and the text is the migrations' own byte for byte, so `db:generate` sees no change. GENERATED ALWAYS means Postgres refuses a direct write, and Drizzle omits generated columns from `$inferInsert`, so TypeScript refuses first.

**Two CHECKs hold the table's names**: `ingredients_nomenclature_declares_canonical_name` (above) and `ingredients_canonical_name_not_blank`. The non-blank check exists because `canonical_name = '   '` satisfies "not null" while contributing nothing to the identity key. A variant's form has its own, `ingredient_variants_form_not_blank`.

**Three partial unique indexes, not two, and indexes rather than constraints.** `ingredients_compendium_identity_key_unique` on `identity_key` in the compendium tier, and `ingredients_workspace_identity_key_unique` on `(workspace_id, identity_key)` and `ingredients_workspace_label_unique` on `(workspace_id, lower(name))` in the workspace tier. All three carry `WHERE deleted_at IS NULL`, per the [partial-index convention](soft-delete.md): deleting a row must not permanently reserve its identity or its label (CLAUDE.md rule 4). The label index is workspace-tier only: inside one workspace an ambiguous label is a mistake, but the compendium deliberately allows several rows to display the same label (four unrelated "Cat's Claw" entries) as long as they are different identities; the formal name that keeps them apart is in the slug too (["Ingredient slugs"](ingredient-slugs.md)). They are indexes because Drizzle's `nullsNotDistinct()` exists only on constraints, and a constraint cannot carry a `WHERE` predicate. Two indexes over the two tiers rather than one over `(workspace_id, identity_key)`: without `NULLS NOT DISTINCT`, every compendium row's null `workspace_id` would be distinct from every other's and a single index would reserve nothing there. The workspace tier's slug index carries no tier predicate, as DESIGN.md §5 writes it, because a null `workspace_id` collides with nothing in a btree.

**A variant's `form` is `text`, and deliberately not a foreign key to `ingredient_forms`.** To a coven the curated table is an autofill vocabulary, not a constraint: a foreign key would make an uncurated value like `rhizome` unwritable until a keeper curates it first. The ingredient's own foreign keys are its workspace and nothing else, which the whole free-text design rests on.

**A pick is recorded beside the text.** A variant's `form_id` is a nullable foreign key to `ingredient_forms`, set only when a member picked a curated row, never resolved from typed text. A variant's `form` is `NOT NULL`, so a pick always stands beside its text and needs no CHECK of its own. The pick is outside `ingredient_variants_form_unique`, which folds the text, so two forms of one ingredient, one picked as each Wax, still fold to one form, and a link to a soft-deleted form reads as no link, the text staying. A save writes a pick only of a curated form, live under a live group, beside text folding to its name and written in its spelling; anything else is refused beside the variant's `formId` or `form`, and a save sending no `formId` clears the column and keeps the text. The deities take the same model in `ingredient_deities`.

**The compendium tier is held to the vocabularies, by the service.** Each of a compendium entry's forms and each of its deities is a pick of a live curated row (a form under a live group, a deity under a live tradition), so a curated value typed rather than picked is refused as an uncurated one is. Its `celestialBodies` and `zodiacSigns` each name one, matched as the suggestions fold, `lower(btrim(value)) = lower(name)`. Every value is stored in its row's own spelling. `createCompendiumEntry` and `updateCompendiumEntry` enforce it after the parse, the picks through `resolvePicks` and the celestial bodies and signs through `curatedSpellings` in `vocabulary`, and refuse a value as a `ValidationError` at `['variants', i, 'form']` or `['variants', i, 'formId']`, or `['celestialBodies', i]`, `['zodiacSigns', i]` or `['deities', i]` ([`../validation.md`](../validation.md), "The two ingredient variants"). It is not Zod, since the check reads the database, and not a key or a CHECK, since the columns are shared with the coven tier, which keeps free text. Deleting a curated row a live entry holds (a form or deity it picks, or a celestial body or sign's last live spelling) is refused, and renaming one carries onto the entries, so the rule holds after the write as well ([`ingredients.md`, "The compendium holds curated values alone"](../design-decisions/ingredients.md#the-compendium-holds-curated-values-alone)). A form rename is carried onto the entry's variants that picked the form and moves no slug, a form being no part of the entry's identity or address.

**Folk names have their own table because `array_to_string` is STABLE.** On this repo's PostgreSQL, `array_to_string` is **STABLE** (`pg_proc.provolatile = 's'`), not IMMUTABLE, so it is legal in neither a generated column nor an expression index; a trigram index over a `text[]` would have needed a hand-written IMMUTABLE wrapper. As a table, `ingredient_folk_names` carries a plain `gin_trgm_ops` index on `name` directly. Uniqueness is per ingredient, not global, since several unrelated ingredients claiming the same common name is what is being documented, not an error. `lower`, `btrim` and `similarity` are IMMUTABLE and used freely.

**Celestial bodies, zodiac signs and colours are lists.** DESIGN.md §5 gives an ingredient several of each, so they are `celestial_bodies`, `zodiac_signs` and `colors`, nullable `text[]` with no default (native arrays, which SQLite could not have run: [`process.md`, "Stack choices that were weighed and rejected"](../design-decisions/process.md#stack-choices-that-were-weighed-and-rejected)). The shared schema trims each entry, drops a blank one, refuses a repeat but for case and spacing (at the repeat) and turns a list left empty into null ([`../validation.md`](../validation.md), "The two ingredient variants"), so no row holds `{}` or a blank entry, and no CHECK repeats that. An array keeps its order, and each list's order is the member's, so nothing sorts one on write or read.

- **Arrays, not child tables, unlike folk names.** Folk names became a table so a trigram index could reach them. No single column carried one (the celestial body and zodiac autofill reads the in-use values of the compendium and one workspace with no index behind them), so a list loses no index, and a table per list would buy three joins for nothing.
- **Changing a column's type is a new column (rule 10).** A column cannot turn from `text` to `text[]` under a deployed reader, so the list is added and filled beside the single, the code switches to the list, a migration rederives the list from the single for whatever the live deploy wrote meanwhile (writing only a row that disagrees, so `updated_at` moves on no other; `generate --custom`, which copies the last snapshot rather than diffing, so the later `db:generate` still emits the drop), and the single is dropped, with its `.ack.md` sidecer, once a release carrying the switch has reached production (["Expand/contract"](expand-contract.md)). **The drop fills nothing first**: a single that disagrees with its list may hold the previous deploy's write or the stale value of a list a member has edited since, and the row cannot say which; copying it in would overwrite that member's edit (the `.ack.md` sidecars' "What is lost"). The same path made `elements` a list.
- **The in-use scan unnests.** Tier 2 of the celestial body and zodiac autofill reads entries rather than a column: `cross join lateral unnest(…)` gives one row per entry before anything trims or folds it, so a value counts once however many lists hold it (["The member's autofill"](member-autofill.md)). The deity autofill reads `ingredient_deities`' live rows.

**Elements are a list.** `elements` is a nullable `ingredient_element[]` with no default, declared in Drizzle as `ingredientElement('elements').array()`. The array's type refuses anything but the `pgEnum`'s five, so no CHECK says it again. The shared schema refuses a repeat and turns a list left empty into null, so no row holds `{}` or one element twice; comparing an array's entries with each other would need a subquery or a hand-written function, so no CHECK repeats it. The array keeps the order chosen, and nothing sorts it. The `ingredient_element` type stays, since the list is of it. **The element filter reads containment**: a row whose list holds the element chosen, among others or alone (Drizzle's `arrayContains`, `@>`, not an equality). No index stands behind it, as none stands behind any list; it ANDs onto the compendium read's other predicates over one tier.

**Identity is the formal name alone, and each form is a variant.** DESIGN.md §5 keys an ingredient on `identity_key`, unique per tier, and holds each form it comes in as a row of `ingredient_variants` beneath it, one live row per ingredient and folded form, so Rosemary the herb and Rosemary the oil are one entry with two variants, and _Valeriana officinalis_ root and leaf are one entry, not two identities. A variant adds to its ingredient and never overrides it, and carries its own description, safety notes, correspondences, categories, substitutes and references, while deities and folk names stay on the ingredient ([`ingredients.md`, "An ingredient and its forms"](../design-decisions/ingredients.md#an-ingredient-and-its-forms)). A write of a second form as an entry of its own is refused by the identity-key index, which the compendium and coven services map.

Fuzzy matching, the one index and the rule every caller is bound by: [`fuzzy-matching.md`](fuzzy-matching.md). Ingredient slugs: [`ingredient-slugs.md`](ingredient-slugs.md).

**The variants table** (`src/modules/ingredients/schema/ingredient-variants.ts`). `form` is text, non-blank by `ingredient_variants_form_not_blank`; `form_id` is the curated pick; the row has its own `set_updated_at` trigger. It is an ingredient's child, so the unscoped finders refuse it at compile time.

- `ingredient_variants_form_unique` holds one live row per ingredient and `lower(btrim(form))`.
- `ingredient_variants_id_ingredient_id_unique` on `(id, ingredient_id)` is the one unique index on a soft-deleted table that is not partial. It is the target of the composite foreign keys below, which a partial index cannot be, and reserves nothing the primary key does not. `tests/db/partial-unique-indexes.test.ts` names it as rule 4's exception and fails any other.
- `ingredient_variants_form_id_idx` (partial) and `ingredient_variants_unaccent_trgm` (a trigram index over the folded form and description) serve the in-use reads and the search.

**Identity as every reader and writer uses it.** `findCompendiumEntryByIdentity({ name, canonicalName })` and its coven twin, `findWorkspaceIngredientByIdentity` under the proof, compare `identity_key` through `identityKeyOf`, and `IngredientIdentity` carries no form. Both services' `refuseCollision` map the identity-key indexes to `canonicalName`, or to `name` for an entry with no formal name, naming the entry already holding it through `describeEntry` and pointing at adding the form to it. Postgres names the first index it finds broken, and the address index and a coven's label index are older than the identity one, so an oil written under the herb's own label meets one of them first: each of those branches looks for an identity holder before its own message, so the refusal is the formal name's whichever index spoke. `ingredientSlug` takes the label and the formal name.

**Merging a group.** A database holding two live rows of one `identity_key` in a tier cannot take the identity indexes; the pre-flight query, which must return no row, is `select workspace_id, lower(coalesce(canonical_name, name)), count(*) from ingredients where deleted_at is null group by 1, 2 having count(*) > 1`, and the procedure is "Merging a group" in [`ingredients.md`, "An ingredient and its forms"](../design-decisions/ingredients.md#an-ingredient-and-its-forms).

**What names a variant.** Four tables hold a `variant_id` tied to their `ingredient_id` by a composite foreign key, `(variant_id, ingredient_id) → ingredient_variants (id, ingredient_id)`, declared with Drizzle's `foreignKey` against the non-partial `(id, ingredient_id)` index, so no row pairs one ingredient with another's form. The key is `MATCH SIMPLE`, which skips the check when either column is null, so a CHECK closes the gap wherever the ingredient may be null.

- `inventory_items.variant_id`, NOT NULL; one live row per coven and variant.
- `spell_steps.variant_id`, set exactly when `ingredient_id` is; one live layer per jar and variant.
- `ingredient_categories.variant_id`, nullable: two unique indexes, one on the parent's pairs and one on a form's ([`ingredient_categories`](categories.md)).
- `ingredient_substitutes.variant_id`, the form a row stands in for, and `substitute_variant_id`, the linked ingredient's form, under its own composite key against `substitute_id` and a CHECK that it has one beside it. `ingredient_substitutes_not_itself` forbids the same ingredient _and_ the same form, so a sibling form may stand in, and the link and name uniqueness split by whether `variant_id` is set.
- `reference_links.ingredient_variant_id`, one entry in the `SOURCED` registry ([References](references.md)).

The stock service writes `variant_id` on stock; the grimoire writes it on layers; the ingredient services write a form's categories, substitutes and references.

**Trigram indexes.** `ingredients_trgm` is one multicolumn `gin_trgm_ops` index over `name` and `canonical_name`; it serves a predicate on either column alone and is not partial ([`fuzzy-matching.md`](fuzzy-matching.md)). A match must be written `name % $1` under a per-transaction `pg_trgm.similarity_threshold`, never `similarity(name, $1) > 0.4`, which no trigram index can answer. The folded twin, `ingredients_unaccent_trgm`, goes through `unaccent_immutable` for the compendium search's accent-insensitive `<%` ([The compendium read](compendium-read.md)); only an expression index lets a fold reach a trigram index. It sits beside the raw one because the fuzzy finders still match the raw columns.

### Workspaces and membership

`src/modules/coven/schema/workspaces.ts` holds DESIGN.md §5's two workspace tables and the `workspace_role` enum (`viewer`, `member`, `owner`). The declaration order reads as a hierarchy and is not one: each role has its own permission statements, so nothing compares two roles (["The Membership proof"](membership-proof.md)).

- **`workspaces`** is `id`, `name`, `slug`, + audit, and **nothing else**. There is no `kind` column and no automatically created workspace: every workspace behaves identically, taking members and being deleted by a steward. A test pins the whole column set, so a later `kind`/`type`/`personal` column turns it red. The entity is `workspaces` even though it routes under `/coven/[slug]` (§5's naming note).
- **`workspaces_slug_unique`** is partial on `deleted_at IS NULL`, per the [partial-index convention](soft-delete.md): the slug is what `/coven/[slug]` routes on, so a plain unique constraint would let a deleted workspace hold a name hostage forever.
- **`workspace_members`** has a composite primary key on `(workspaceId, userId)` and no surrogate `id`: the pair _is_ the membership's identity, and a surrogate key would let the same user join the same workspace twice with two rows disagreeing about their role. Columns: `role`, `joinedAt`, `invitedBy` (nullable), + audit.
  - `joinedAt` is distinct from `created_at`: a role change rewrites the row without changing when the person joined.
  - `invitedBy` references `users.id` and holds the sender of the invitation that seated the person. It is not `created_by`, which is the person who accepted, since acceptance runs under their session. It is written at the moment of seating, not worked out later from `invitations`: a person removed and invited back has several accepted invitations, and the database clock (`accepted_at`) and the app clock (`joined_at`) need not order them the same way. Revival overwrites it, a role change leaves it, a creator has null, and the name resolves through the co-member finder, which still names someone removed since.
- **`owner` is a role here but not an invitable one.** That narrowing lives on `invitations`, whose check constraint rejects it (["Invitations"](invitations.md)). The Steward role is granted afterwards by an existing steward on the members page.
- Both tables carry the full six-column audit spread, and every `*_by` column references `users.id`. `workspace_members` keeps all six despite being a join table: two other join tables hard-delete, and this is not one of them, because who removed whom, and when, is worth keeping.

### The provisional-account delete

`deleteLapsedProvisionalUser(userId, lifetimeSeconds, capSeconds)` is the one hard delete of a table carrying `deleted_at`, and it is a named export rather than a loosening of `write.delete`'s type. It removes the one `users` row named, if it is unverified, holds at least one `accounts` row, and has an `updated_at` older than `now()` minus the lifetime or a `created_at` older than `now()` minus the cap, and answers whether it did. Both cutoffs are the database's clock. The `EXISTS` over `accounts` is `existsIn`'s, so the delete builds no read of its own.

`accounts` and `sessions` follow by their `ON DELETE CASCADE`, as do the account's rows in `user_access_pauses`, `workspace_member_pauses` and `support_timeouts`. A pause or a support time-out sanctions the account it names and records nothing else, so unlike the privilege ledger below it neither keeps the account nor blocks the delete.

`provisionalSecondsLeft(userId, ...)` is its read-only partner: how long until the row lapses, or null when it will not (it is verified, vouched for, has no provider account, or is gone). The expiry job's step calls the two in turn.

It skips a row holding any `user_privilege_changes` row, as `not(existsIn(...))`, the negation `citesNothing` uses. Such an account is one a keeper has vouched for, and the ledger references it with a plain foreign key, so deleting it would fail. The rows are not deleted with it either: `forbid_rewrite` refuses that, and the ledger is the history.

It is hard for a reason outside this layer: Better Auth reads `users` by address with no `deleted_at` filter, so a tombstone would keep refusing the owner's sign-in. It runs outside `withAudit` because no surviving row is left to stamp, though its caller is a job whose other writes would run as the System actor. Two partial indexes serve it, one per half of the `OR`: `users_provisional_updated_at_idx` and `users_provisional_created_at_idx`, each `WHERE email_verified = false`. The rest is [`auth/admin-bootstrap.md`](../auth/admin-bootstrap.md), "Provisional accounts".
