### Developer tooling (Wave 11)

**M11.23 — Pre-Commit Checks Only the Files a Commit Changes** · 1.5h

_Story:_ As a developer, I want the pre-commit hook to check only the files I'm committing, so that a one-line change doesn't pay for linting, formatting and typechecking the whole repo.

The hook (the `pre-commit` package, configured by the `"pre-commit"` array in `package.json`) and `npm run pre-commit` both run `oxlint .`, stylelint, `prettier --check .` and `tsc --noEmit` over everything. This task adds `lint-staged`, which works out the changed files, passes them to each check, and sets unstaged edits aside while the hook runs, so the check sees the copy being committed. Its configuration lives in `lint-staged.config.mjs`. `tsc` can't be limited to files (a changed exported type can break files nobody touched), so it stays whole-project and runs only when a TypeScript file, `tsconfig.json`, `package.json` or the lockfile changed. When a check's own config changes (`.oxlintrc.json`, `lint/`, `.prettierrc`, `.prettierignore`, the stylelint config), that check reruns over the whole repo, since a narrowed run would miss what the new rule flags. `lint`, `format:check` and `typecheck` stay as the whole-repo commands, and CI's `checks.yml` stays the whole-repo gate. The plan, with the options weighed, is [`design-decisions/m11.23-plan.md`](../design-decisions/m11.23-plan.md).

_Acceptance criteria:_

- The hook runs lint, format and stylelint on the staged files only; a lint error in a staged file refuses the commit and names that file alone
- A bad unstaged edit in another file doesn't fail the commit, and is restored untouched afterwards
- `npm run pre-commit` checks every tracked file changed since HEAD, staged or not, so the same unstaged edit fails it
- A commit with no TypeScript, `tsconfig.json`, `package.json` or lockfile change doesn't run `tsc`; one with a `.ts` change runs it once over the whole project
- Changing a check's own config reruns that check over the whole repo
- Files `.prettierignore` excludes (`src/gql/`, `src/graphql/schema.graphql`) are not flagged when staged

### Test harness (Wave 11)

**M11.18 — Faster Playwright runs on the same CPU and RAM** · 8h

_Story:_ As a developer, I want the e2e suite to finish in the time its work needs rather than the time its longest file needs, so that a local run and a gate run each cost less waiting on the hardware we have.

Minted on request during MB.119, from a measured look at where an e2e run's time goes. The plan, with the measurements and the order, is [`design-decisions/m11.18-plan.md`](../design-decisions/m11.18-plan.md); this entry is its summary. Neither CPU nor memory can grow: the devcontainer has 12 cores and 32 GB, and CI runs on GitHub's 4-vCPU runner.

The last local run (6 workers, 109 tests) took 55.9 s of wall time for 165 s of test work, whose even spread would be 27.5 s. The reason is that every db-touching spec file opens with `test.describe.configure({ mode: 'serial' })`, so each file runs on one worker in order, and `tests/e2e/admin.spec.ts` alone is 36.6 s: five workers idle behind it. The rule was written for a race on one shared database that MB.112's database-per-slot ended, as `claude-docs/testing/e2e.md` says. On CI the same file is 74 s of a 125 s test span, and the Playwright step is 137–163 s against the 55 s `claude-docs/ci/runner-budget.md` still lists.

Six levers, each its own PR under this task (`Refs` until the last closes it), each measured before and after on the same tree with the recipe in the plan: (1) a baseline that profiles a cold and a warm run and corrects the stale CI row; (2) dropping serial mode from every file whose tests are independent of what an earlier test wrote, since `fullyParallel` is already on and `beforeAll` reseeds per worker, with a split along the chains as the fallback and the doc's serial paragraph rewritten; (3) no video recording on local runs, trace kept as the evidence; (4) JS coverage collected only under `E2E_COVERAGE=1`, which CI sets; (5) a way to leave the slot servers up between local runs so `reuseExistingServer` skips the build, only if the baseline shows the build dominating; (6) the local worker default measured at 6, 9 and 12 once the critical path is gone. Levers 2, 3, 4 and 5 change a rule or a developer-facing default and are put to the owner in their PRs. Postgres write settings, fewer axe scans and CI sharding were weighed and set aside in the plan.

_Acceptance criteria:_

- `claude-docs/testing/e2e.md` has a "Where a run's time goes" section with the measured breakdown and the measurement recipe, and `claude-docs/ci/runner-budget.md`'s Playwright row matches a current run
- Every spec file whose tests are independent runs without serial mode, and the doc states serial as the choice for a file whose tests chain, with the reason
- A warm local `npm run e2e` is within a few seconds of its ideal span plus startup, shown by three runs' median in the PR body
- A local failure still leaves a trace under `.reports/test-results`
- CI's coverage artifact and summary are unchanged, and a local run makes no coverage report unless asked
- Each lever's PR body carries its before-and-after table, three runs each
