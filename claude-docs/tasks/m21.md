## M21 — Billing and memberships

_20 tasks · 93 hours_

**Sequencing** — [Wave 21](../waves/wave-21.md). The proof of concept (M21.1) comes first, because it chooses between the plugin and the SDK and captures the fixtures. The mock server (M21.2) and the scheduled run (M21.3) follow it, then the tables (M21.4), which every behaviour task needs, then the service (M21.5), the webhook route (M21.6) and the checkout page (M21.7). The discount (M21.8), the exemption (M21.9), the curator coven and trial (M21.10) and the payer mode (M21.11) build on the service. The four pages (M21.12 → M21.15) follow the behaviour they show, and the picker (M21.16) follows the pricing page. The support-load task (M21.17), the pay ratio (M21.18) and security.txt (M21.19) have no code dependency and may run at any time; the support-load task must land before billing opens. The stories (M21.20) come last.

These tasks were minted by M17.1 on 2026-11-06 from [`ingredients.md`, "Subscription Billing Scope"](../design-decisions/ingredients.md#subscription-billing-scope). That record is the reasoning behind every task below: the chosen model, the payer modes, the pause, lapsed-member and switch rules, the data model, the membership views and the billing test plan. Every task's criteria name the tests it ships from the test plan, over and above CLAUDE.md's rules.

**M21.1 — Prove the Stripe Integration on a Throwaway Branch** · 8h

_Story:_ As the owner, I want both candidates run against Stripe's test mode, so that the plugin-or-SDK choice rests on what the spike showed and not on the documentation.

This task is the proof of concept the record frames. It is the only task that may touch a throwaway branch. It needs a Stripe test key in `.env.local`.

_Acceptance criteria:_

- A decision section in `design-decisions/process.md` names the choice between `@better-auth/stripe` and a thin service over the Stripe SDK, and states what the spike showed for each of the five wants under model (i), following the proof-of-concept brief in the M17.1 record
- The record says whether `@better-auth/stripe` supports a site-hosted checkout page, chooses between Stripe Elements and embedded Checkout for that page, and names the peer-range bump the plugin would force
- The record says whether Stripe's coupon rules allow the R5 discount as a line on the payer's own subscription, whether `pause_collection` behaves as the pause rule needs, and whether a test clock covers a renewal
- Webhook events are captured from real test mode, replayed signed locally, and saved as fixtures for M21.2; the record names where they are kept
- The throwaway branch `spike/m17-stripe` is named in the record and is never merged; `STRIPE_SECRET_KEY` (test) is named in `claude-docs/secrets.md` by name only
- The merged diff touches only Markdown and `claude-docs/`; no dependency is added and no code under `src/` changes

**M21.5 — Build the Billing Service and the Entitlement Check** · 8h

_Story:_ As the owner, I want one place to ask whether a coven may use the site, so that billing rules are enforced in services and nowhere else.

Needs M21.4. Table-driven tests dominate this task.

_Acceptance criteria:_

- A billing service under `src/modules/` (the module M21.1's record names) holds the entitlement check, opens with `import 'server-only'`, and is the only importer of the processor SDK; a guard test fails if any other file imports it
- The check reads the exemption first, then the pause state, then the subscription state, then the trial, and returns an explicit result for each; the pause rule (stop collection for a site pause and a coven pause), the lapsed-member rule (refused until they pay; the seat and content stay and are visible read-only to the coven) and the switch rule (at the next renewal) are each pinned by a test
- Entitlement is tested both ways, by direct id: the paying coven reaches the feature, and the lapsed, paused, cancelled, exempt-then-cleared and never-subscribed coven is refused, each asserting the precondition that would have let it succeed
- Taking a copy of a coven's data never depends on billing: the entitlement check does not guard `requestCovenCopy`, `requestDataCopy` or their downloads, and a test proves a steward of a lapsed, cancelled, trial-ended and never-subscribed coven can still request and download the whole coven, and a member of each can still take their own copy
- A guard test fails if a resolver or a page touches a billing table
- Money is held as integers in the smallest unit, with a table-driven test that no float reaches a billing column or calculation
- Every billing write goes through `withAudit`, asserted by a test that checks the actor, and a catalogue-introspection test proves the billing tables carry audit columns and partial unique indexes
- Tests run once for coven pays and once for each member pays, plus the switching case and the lapsed member
- No test is skipped or flaky

**M21.6 — Add the Stripe Webhook Route and Event Replay** · 5h

_Story:_ As the owner, I want Stripe's events to update the billing tables safely, so that a repeated, late or unknown event never corrupts a coven's access.

Needs M21.2 and M21.5.

_Acceptance criteria:_

- A plain route receives Stripe's events (the one route Stripe calls, added to CLAUDE.md rule 1's list of routes outside `/api/graphql` in the same PR, carrying no application data), verifies the signature on the raw body, and starts a durable job
- A bad signature is refused, tested with a tampered body and a missing header
- Every event handler is idempotent: a fixture replayed twice leaves one write, tested for every event type the service handles
- Out-of-order delivery converges on the same state, tested with the fixtures in shuffled order
- An unknown event type is logged and acknowledged, never an error
- A handler failure is retried by the job and never charges twice, tested with an injected failure
- The handlers write as the seeded System account through `withAudit`
- No test is skipped or flaky
