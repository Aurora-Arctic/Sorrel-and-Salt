## M16 — More login options

_10 tasks · 27 hours_

**Sequencing** — [Wave 16](../waves/wave-16.md), ahead of Wave 15 (Launch), in id order: the scoping doc first, so the rules the code is reviewed against are already corrected; then email and password, its reset and change, the lockout's table and behaviour; then passkeys; then two-factor's table and behaviour.

These tasks bring first-party sign-in into v1, on the owner's call (2026-10-16): an email address and a password, passkeys (a key stored on the person's device, unlocked by a fingerprint, face or PIN), and an optional second factor for password sign-ins. Until now `DESIGN.md` §2 argued for OAuth only and §13 deferred all three to v2; M16.1 records the change and corrects those sections before any code is written.

The password policy below is the requirement for M16.2, M16.3 and M16.5. It was researched from these sources, and each acceptance criterion names the one it comes from:

- National Institute of Standards and Technology. _Digital Identity Guidelines: Authentication and Authenticator Management_. NIST Special Publication 800-63B-4. Gaithersburg, MD: NIST, 2025. https://pages.nist.gov/800-63-4/sp800-63b.html. Cited as **NIST**, §3.1.1.2 for passwords and §3.2.2 for rate limiting.
- OWASP Foundation. "Authentication Cheat Sheet." OWASP Cheat Sheet Series. https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html. Cited as **OWASP Auth**.
- OWASP Foundation. "Password Storage Cheat Sheet." OWASP Cheat Sheet Series. https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html. Cited as **OWASP Storage**.
- Hunt, Troy. "API v3: Pwned Passwords." Have I Been Pwned. https://haveibeenpwned.com/API/v3#PwnedPasswords. Cited as **HIBP**.
- Better Auth. "Email & Password," "Passkey," "Two-Factor Authentication" and "Hooks." Better Auth documentation. https://www.better-auth.com/docs; and the installed `better-auth`, read in `node_modules`. Cited as **Better Auth**.

The record says so, and names the way out for a later task: a custom `password.hash` and `password.verify` pair using Node's built-in Argon2id (Node 24.7 and later), verifying old hashes by their shape. Nothing in this wave changes it.

### Email and password

**M16.2 — Email and password sign-in and sign-up** · 4h

_Story 70:_ As a person without a Google, Discord, Facebook or Microsoft account, or who would rather not use one, I want to sign up and sign in with my email address and a password, so that I can use the site.

Turns on Better Auth's `emailAndPassword` in `src/lib/auth.ts` with `minPasswordLength: 15`, `maxPasswordLength: 128`, `requireEmailVerification: true` and `autoSignIn: false`, and adds the `haveIBeenPwned()` plugin, which checks a password against the Have I Been Pwned list of breached passwords by sending only the first five characters of its SHA-1 hash (a k-anonymity range query: the service never sees the password or its full hash). The `accounts.password` column already exists and is null today.

Sign-up mails the existing verification link (MB.61's `verify-email` template), and the account reaches nothing until it is verified, as for a provider sign-in whose address is unverified. The account earns nothing else: the invite gate is unchanged (`canCreateWorkspace` stays false).

`SignInPanel` gains an email and password form beside the provider buttons, with a link to switch to sign-up. The password field has a show-password toggle and, on sign-up, a strength meter from `@zxcvbn-ts/core`, shown as guidance and never a gate. `lastLoginMethod` already records `email`, so the panel's "last used" hint covers it.

Each criterion names its source; the sources are listed in full at the head of [`tasks/m16.md`](m16.md).

_Acceptance criteria:_

- A password shorter than 15 characters is refused on sign-up (NIST §3.1.1.2 item 1: 15 when the password is the only factor; two-factor here is offered, not required)
- A password of 64 characters is accepted, and of 129 refused (NIST item 2: at least 64)
- A password of spaces, punctuation and non-Latin letters is accepted, with no rule demanding a digit, capital or symbol (NIST items 3 and 5; OWASP Auth)
- A password that differs only after its first 72 characters does not sign in (NIST item 9: never truncate)
- A password on the breached list is refused with a message saying why, and the request to the breached-password service carries only a five-character hash prefix (NIST §3.1.1.2 blocklist; HIBP)
- Sign-up is refused, not waved through, when the breached-password service is unreachable, and the form says to try again later
- Sign-in with a wrong password and sign-in with an unknown address return the same error (OWASP Auth)
- Sign-up with an address that already has an account returns the same success as a new one, and mails the holder instead (OWASP Auth; Better Auth `onExistingUserSignUp`)
- An unverified email-and-password account reaches only `/account/email`, as an unverified provider account does
- The password fields use `autocomplete="current-password"` and `"new-password"`, and nothing blocks paste (NIST §3.1.1.2)
- No password hint and no security question exist (NIST items 7 and 8)
- A new account has `canCreateWorkspace` false
- An acceptance test names Story 70; a Playwright spec signs up, verifies, and signs in, tagged `@story-70`, with axe clean on the panel

**M16.3 — Password reset and change** · 4h

_Story 71:_ As someone who signs in with a password, I want to reset it when I forget it and change it when I choose, so that I am never locked out of my account and can replace a password I no longer trust.

Wires `sendResetPassword` to `src/lib/mail.ts` with a new template, `src/emails/reset-password.tsx`, and its Ladle story, in the shape of `verify-email.tsx`. Adds `/forgot-password` (asks for an address, always answers the same way) and `/reset-password` (takes the token from the link and a new password, with the same toggle and meter as sign-up). Adds a Password section to `/account`: set a password for an account that has none (a provider-only account adding one), or change it, which asks for the current password and signs out every other session.

Sets `resetPasswordTokenExpiresIn` to 15 minutes, since Better Auth stores the reset token unhashed in `verifications` and a short life limits what a copy of that table is worth, and `revokeSessionsOnPasswordReset: true`. An `onPasswordReset` hook mails "your password was changed" to the account's address, so that a reset the holder did not make does not go unnoticed.

Each criterion names its source; the sources are listed in full at the head of [`tasks/m16.md`](m16.md).

_Acceptance criteria:_

- A reset request for an unknown address returns the same answer as for a known one (OWASP Auth)
- The reset link works once, and not after 15 minutes
- A reset signs out every session the account held (OWASP Auth)
- A changed password signs out every other session, and the current one stays signed in
- A new password at reset or change obeys every M16.2 rule: length, the breached list, refused while that list is unreachable
- A reset or change mails a notice to the account's address
- Change asks for the current password; a provider-only account can set one without it, from a session
- No rule forces a periodic change (NIST item 6)
- The reset template has a Ladle story; an acceptance test names Story 71; a Playwright spec walks forgot, mail, reset and sign-in, tagged `@story-71`, with axe clean on both pages

**M16.5 — Per-account lockout of password sign-in** · 3h

_Story 72:_ As someone who signs in with a password, I want repeated wrong guesses at it to slow down and then stop, so that nobody can try passwords against my account until one works.

Better Auth's rate limiter counts per client address and path, so someone guessing from many addresses is not slowed; NIST §3.2.2 asks for a limit per account. Two hooks on `/sign-in/email` in `src/lib/auth.ts`: a `hooks.before` that looks up the address's account and its `sign_in_failures` row and, while locked, refuses with the same `INVALID_EMAIL_OR_PASSWORD` a wrong password gets; and a `hooks.after` that adds one when the endpoint returned that error and deletes the row on a successful sign-in. (Better Auth puts a thrown error on `ctx.context.returned` and runs the after hooks before rethrowing it, read in `dist/api/dispatch.mjs`.)

The schedule, exponential as OWASP Auth suggests: 5 failures lock the password for 1 minute, 10 for 5 minutes, 20 for 1 hour, and 100 disable it until a reset (NIST's limit, after which the authenticator must be bound again). A provider or passkey sign-in stays open throughout, and a reset clears the row.

The counter is a write outside `withAudit`. Name it in `CLAUDE.md` rule 3 beside the sign-up hook and the seed, as the third identity bootstrap, with its reason: a failed sign-in has no session to audit.

Each criterion names its source; the sources are listed in full at the head of [`tasks/m16.md`](m16.md).

_Acceptance criteria:_

- The fifth wrong password locks the account for a minute: the right password is refused within it, and accepted after (OWASP Auth)
- The 100th disables the password until a reset, and a reset signs in (NIST §3.2.2)
- A lock on one account does not lock another, and does not lock the same account's provider sign-in
- A locked sign-in returns the same error as a wrong password, so a lock does not reveal that the address has an account (OWASP Auth)
- A successful sign-in clears the count
- Each test shows the guard is what refuses: the same password signs in once the row is removed
- `CLAUDE.md` rule 3 names the counter

**M16.7 — Sign in with a passkey** · 4h

_Story 73:_ As someone who has added a passkey, I want to sign in with it, so that I need no password and nothing a site breach could leak.

Registers `passkey({ rpID, rpName, origin })` on the server, and `passkeyClient()` beside the two existing client plugins. The base URL in `src/lib/auth.ts` is resolved per request across three hosts (production, staging and hotfix previews), so `rpID` (the domain a passkey belongs to) and `origin` must follow it too: leave `rpID` to the plugin's fallback and pin `origin` to the request's host in a hook, and test both hosts with `NODE_ENV=production`. The fallback reads `options.baseURL` only when it is a string, and the app's is the `allowedHosts` object; it still follows the host because Better Auth hands every endpoint, `auth.api` calls included, a per-request copy of its options whose `baseURL` is the resolved origin as a string (`resolveRequestContext` in `better-auth/dist/context/helpers.mjs`). The plugin's `rpID` option is one fixed value, so passing it would pin every host to one domain. `tests/db/passkey-hosts.test.ts` fails if the fallback ever gives `localhost` on a deployed host, so a Better Auth upgrade that changes this is caught. A passkey is bound to the domain it was made on, so staging's and production's are separate. The sign-in panel gains a "Sign in with a passkey" button and, where the browser supports it, offers saved passkeys in the email field's autofill (`autocomplete="username webauthn"` with `signIn.passkey({ autoFill: true })`), behind `PublicKeyCredential.isConditionalMediationAvailable()`, an enhancement past the browser floor with the button as its fallback (`.claude/rules/components.md`). The plugin ships no rate rule, so add a `customRules` entry for `/passkey/*` (sign-in ends at `/passkey/verify-authentication`) at 3 per 10 seconds, matching sign-in's.

_Acceptance criteria:_

- `rpID` matches the host the request came to, on production and on staging
- A passkey enrolled on the account signs it in, and the session carries `lastLoginMethod` `passkey`
- A passkey for one account cannot sign in another, and a passkey removed from the account no longer signs in
- Autofill is offered only where the browser supports it; elsewhere the button works and nothing breaks
- The rate rule refuses a fourth request inside 10 seconds in production mode
- Sign-in by passkey earns nothing beyond what any sign-in earns (the invite gate holds)
- An acceptance test names Story 73; a Playwright spec signs in with Chromium's virtual authenticator, tagged `@story-73`, with axe clean

**M16.10 — Two-factor for password sign-ins** · 4h

_Story 75:_ As someone who signs in with a password, I want to add a second step from an authenticator app, so that a stolen password alone does not open my account.

Registers `twoFactor({ issuer })` with the site's name as the issuer, and `twoFactorClient()`. The account page's Password section offers to turn two-factor on: it asks for the password, shows a QR code for an authenticator app and the backup codes once, and turns on only when a code from the app is entered (`skipVerificationOnEnable` stays false). Sign-in with a password then asks for the app's code or a backup code on a second step of the sign-in page, with "trust this device for 30 days" as the plugin's cookie. A provider or passkey sign-in is not asked: the plugin covers password sign-ins, and those methods carry their own second factor.

Two-factor is offered, not required, so the 15-character minimum of M16.2 still applies to every password.

_Acceptance criteria:_

- Turning two-factor on needs the password and a valid code; turning it off needs the password
- With two-factor on, the right password alone does not sign in; the right code completes it; a wrong code does not
- A backup code works once
- A trusted device skips the second step for the trust period, and another device does not
- Wrong codes count towards the lockout of M16.5 or a lockout of their own, the choice recorded in §8
- An acceptance test names Story 75; a Playwright spec enrols and signs in with a code computed from the shown secret, tagged `@story-75`, with axe clean
