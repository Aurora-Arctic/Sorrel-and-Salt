**M9.5 — unitConvert() within a single dimension** · 2h

_Story 24 — As a workspace member, I want quantities compared across units of the same kind, so that a recipe in teaspoons can be checked against a jar measured in millilitres._

Pure function converting only within one dimension: weight to weight, volume to volume. Cross-dimension conversion is refused outright rather than attempted — grams to teaspoons depends on what is being measured, and a wrong answer here silently doubles or halves an ingredient in a working. Count converts to nothing at all; three pinches is not a quantity of millilitres. The refusal is an explicit result the caller must handle, never a null or a best guess.

**Amended by MB.215 (2026-10-11):** the stock and layer quantities it compares each name a variant, so a comparison is always of one form: teaspoons of rosemary oil in a jar are checked against millilitres of the oil, never against grams of the herb ([`design-decisions/mb.215-ingredient-variants.md`](../design-decisions/mb.215-ingredient-variants.md)).

**Amended 2026-10-13 after the Wave 11 review:** the task named a function but not its home, its factors or its result. (1) It lives in `src/modules/ingredients/units/convert.ts` and is exported from `@/modules/ingredients` as `unitConvert`. It imports only `schema/units.ts`, never the database layer ([`db/stock.md`](../db/stock.md), "One module owns the units"). (2) The factors. Weight: 1 oz is 28.349523125 g and 1 lb is 453.59237 g. Volume: 1 tsp is 5 ml, 1 tbsp is 15 ml, 1 cup is 250 ml, 1 `fl_oz_uk` is 28.4130625 ml and 1 `fl_oz_us` is 29.5735295625 ml. The owner chose these on 2026-10-13: metric kitchen spoons and cups, as a British kitchen measures them, and both fluid ounces, since the UK and US ones differ by about four per cent and a recipe's origin decides which it means. (3) A value is converted through a base unit for its dimension, milligrams for weight and millilitres for volume, and rounded to three decimals only at the end, the scale of the column's `numeric(12,3)`. Rounding at each step would let the error grow. (4) The result is a union the caller must test: `{ ok: true, value }` or `{ ok: false, reason: 'dimension' | 'count' }`. (5) It depends on M11.17, which renames the stored unit `fl_oz` to `fl_oz_uk` and adds `fl_oz_us`. Its consumers are M9.3's default threshold and M10.19's comparison of a recipe against a jar.

_Acceptance criteria:_

- Weight to weight and volume to volume convert exactly, to a defined precision
- Every factor above is tested, each pair of units within a dimension, including both fluid ounces
- The defined precision is three decimals, applied once at the end and not at each step
- Weight to volume is refused, in both directions
- Any conversion involving count is refused
- Refusal is a distinguishable result the caller must handle, not null or NaN
- Round-tripping a value returns the original within the defined precision
- No density table exists anywhere in the codebase
- Unit tested across every pair within each dimension, and a sample of refused pairs

**M9.17 — E2E specs tag the stories they walk** · 2h

_Stories 1–64 — As the product owner, I want to see which stories also have a browser flow, so that the launch wave’s seven flows aim at the stories without one rather than repeat what the service tests prove._

The acceptance suite in `tests/acceptance/` is the definition of done (§11), and Playwright keeps to what only a real server can prove: navigation, server render, cookies, mail, the cache, the production build and one axe scan per page (layer-ownership rule 9, MB.224). Both held when the owner asked, on 2026-10-12, whether the stories should have Playwright tests too. The answer was to trace rather than duplicate: no story gains a browser test for its own sake, but every Playwright test whose steps are a story’s flow says which story, with Playwright’s own tag option, `@story-N`, so the checklist can show where a browser proof exists and where it does not ([`design-decisions/m9.17-plan.md`](../design-decisions/m9.17-plan.md)).

The stories checklist (`npm run test:stories`) scans `tests/e2e/**/*.spec.ts` for those tags, marks each story that has one with ` · browser`, and tallies them; a tag naming a number §10 does not list is reported under "Not a v1 story", as a stray describe is. The column reports a tagged spec on disk, not a Playwright run’s result: the Playwright job’s own summary lists the stories its run walked and whether they passed. A tag goes only on a test whose own steps are the story’s flow; visiting a story’s page is not walking it. ### Admin modals (Wave 9)

**M9.18 — Admin modals open at once, with a loading state** · 6h

_Story 18 — As an admin, I want an Edit or Add press to open its modal at once, so that the page does not seem to ignore me while the form loads._

Every admin Edit pencil and Add button was a plain link to `?edit=<slug>` or `?new`, and nothing showed until the server had rendered the whole page again with the modal in it. The owner asked for the modal to open on the press and show a loading state, as the filters (`ListFrame`) and tabs (`TabSwitchProvider`) already do. A `RouteModalProvider` in the admin layout holds the opening in a transition around the soft navigation. Each page renders its one `RouteModal` in a fixed place, so the same dialog shows the form's skeleton and then the form, fading in once. The form's data still comes with the navigation from the server page's existing reads, so no GraphQL query is added (CLAUDE.md rule 1), and a direct request to `?edit=` still renders on the server with the modal open ([`design-decisions/m9.18-plan.md`](../design-decisions/m9.18-plan.md)).

_Acceptance criteria:_

- Pressing Edit on any admin list, or Add beside any admin heading, opens the modal before the page's response arrives, its head as the loaded modal's, its body a skeleton with a status for screen readers
- The form replaces the skeleton in the same dialog element, which fades in once, and the focus moves to its first field
- Closing the modal while it loads keeps it closed when the response lands, and leaves no `?edit=` or `?new` in the address
- A modifier-click or middle-click on Edit, or a press before the page's script loads, still follows the link
- A direct request to `?edit=` or `?new` renders the modal on the server, with no skeleton
- A row gone since the list was drawn closes the modal and shows the missing notice, as before
- The loading modal passes an axe scan
- The Modal, IconTip and admin page docs say so, and the Modal stories hold a Loading story

**M9.19 — Admin user modal, with the user's covens and Impersonate** · 4h

_Story 19 — As an admin, I want to see which covens a user owns or belongs to, with their role, so that I know what someone holds before I approve, revoke, grant or impersonate them._

An admin approving coven creation, revoking it, granting admin or impersonating a user could not see what that person already held, because `membershipsOf` refused an admin asking after anyone but themselves. The owner narrowed story 19: "private data" is now a workspace's contents, and which covens a user belongs to, by name and role, is readable by a site admin. Pressing a user's name on `/admin/users` opens a modal at `?user=<id>`, showing the row's facts, a list of the user's covens and an Impersonate button, built on M9.18's `RouteModal`, so this task depends on M9.18. The modal links to no coven and the service hands over a workspace's `id`, `name` and `slug` and nothing beneath ([`design-decisions/m9.19-admin-sees-user-covens.md`](../design-decisions/m9.19-admin-sees-user-covens.md)).

_Acceptance criteria:_

- On `/admin/users`, pressing a name opens a modal at once, headed by the name with the email beneath, showing the row's facts, with the row's Promote or Revoke and Approve or Revoke beside the facts they change, above a Covens list naming every live coven the user belongs to with the role and joining date, owners first; Close returns to the list with the filter and page kept and no `?user=`
- A `?user=` that is malformed, unknown or soft-deleted shows the missing notice over the list and no dialog; a direct request to a live `?user=` renders the modal on the server
- The modal offers Impersonate, asking first inside the modal, for a non-admin user where impersonation is registered, and sends through the one path the list's button uses; the role and creation controls ask inside the modal too, never in a second dialog, and go through the row's own mutations; it links to no coven
- `membershipsOf` answers a site admin for any user and still refuses any other caller asking after anyone but themselves, both asserted with their preconditions; E is shown refused X's contents by direct id in the same test that shows E reading D's membership of X
- GraphQL's `User.memberships` resolves for an admin asking about a listed user, through the loader, with no SDL change
- The e2e flow is tagged `@story-19` and passes an axe scan with the modal open
- Story 19, CLAUDE.md, DESIGN.md §7–§10, the auth, GraphQL and component docs say so, and the decision is recorded
