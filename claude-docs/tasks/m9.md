**M9.4 — workspace ingredients query and stock mutations** · 2h

**M9.5 — unitConvert() within a single dimension** · 2h

_Story 24 — As a workspace member, I want quantities compared across units of the same kind, so that a recipe in teaspoons can be checked against a jar measured in millilitres._

Pure function converting only within one dimension: weight to weight, volume to volume. Cross-dimension conversion is refused outright rather than attempted — grams to teaspoons depends on what is being measured, and a wrong answer here silently doubles or halves an ingredient in a working. Count converts to nothing at all; three pinches is not a quantity of millilitres. The refusal is an explicit result the caller must handle, never a null or a best guess.

**Amended by MB.215 (2026-10-11):** the stock and layer quantities it compares each name a variant, so a comparison is always of one form: teaspoons of rosemary oil in a jar are checked against millilitres of the oil, never against grams of the herb ([`design-decisions/mb.215-ingredient-variants.md`](../design-decisions/mb.215-ingredient-variants.md)).

_Acceptance criteria:_

- Weight to weight and volume to volume convert exactly, to a defined precision
- Weight to volume is refused, in both directions
- Any conversion involving count is refused
- Refusal is a distinguishable result the caller must handle, not null or NaN
- Round-tripping a value returns the original within the defined precision
- No density table exists anywhere in the codebase
- Unit tested across every pair within each dimension, and a sample of refused pairs

**M9.8 — Low and out-of-stock badges with a sensible default threshold** · 1h

_Story 23 — As a workspace member, I want low and empty stock flagged, so that I know what to replace before I start a working._

Compare quantityOnHand against lowStockThreshold and render the appropriate badge, with a filter for low stock. Nobody wants to set a threshold on every one of two hundred jars, so supply one at add time by dimension: 3 for count, 10 g for weight, 15 ml for volume, converted into whatever unit the row uses. A flat number across dimensions would be useless — 5 is a reasonable count of candles and an invisible quantity of dried herb. Write the default onto the row when it is created rather than leaving the column null and applying a constant at read time: it stays visible and editable, and changing the constant later does not silently reinterpret every existing row.

_Acceptance criteria:_

- Low stock triggers at or below the threshold
- Zero renders as out of stock, distinctly from low
- A new row gets a dimension-appropriate default without the member choosing one
- The default is written to the row, not applied at read time
- The threshold is visible and editable on the row
- Setting a threshold of zero disables the warning rather than meaning 'always low'
- Meaning does not depend on colour alone
- Story 23 acceptance test passes

**M9.14 — Change a member's role** · 2h

_Stories 9 and 11 — As a workspace owner, I want to change a member's role among viewer, member and owner, so that each person's access matches what they do, without the workspace ever being left with no owner._

The `updateMemberRole` service and its GraphQL mutation, which every role change goes through. Before this task nothing changed a role: M6.8 is only the guard, M6.13 renders role controls and a promote-to-owner action, M6.16 promotes a successor before the last owner leaves, and a demotion had no home at all. The `member: update` permission existed with nothing to use it.

The service checks `member: update`, which only owners hold, and allows every move between viewer, member and owner, in either direction. A demotion from owner runs M6.8's last-owner guard, so the only owner cannot be demoted, by themselves or anyone. It changes an existing member's row and nothing else: a pending invitation is not a member, and ownership is never granted through one (§5). A role change leaves `joinedAt` alone, since the person joined when they joined.

Lands after M6.8, whose guard it calls, and before M6.13, which renders its controls.

_Acceptance criteria:_

- An owner can move a member between any two of viewer, member and owner, in either direction
- A member or a viewer calling it is refused with Forbidden; the test shows the caller's membership exists, so it fails if the check is removed
- An owner of another workspace is refused for a member of this one, by direct id
- Demoting the only owner is refused by M6.8's guard, with the remedy it carries
- The target must be a live member of this workspace: a pending invitation, a removed member or someone from another workspace is refused, and no row is inserted
- A role change leaves `joinedAt` unchanged
- The mutation is in the committed SDL and calls the service, which holds every check

### Story traceability (Wave 9)

M9.17 is numbered M9 for the same reason: minted for Wave 9 on the owner’s call (2026-10-12), though its subject is the test harness rather than workspace ingredients. [Wave 9](../waves/wave-09.md) runs it after M6.7.

**M9.17 — E2E specs tag the stories they walk** · 2h

_Stories 1–64 — As the product owner, I want to see which stories also have a browser flow, so that the launch wave’s seven flows aim at the stories without one rather than repeat what the service tests prove._

The acceptance suite in `tests/acceptance/` is the definition of done (§11), and Playwright keeps to what only a real server can prove: navigation, server render, cookies, mail, the cache, the production build and one axe scan per page (layer-ownership rule 9, MB.224). Both held when the owner asked, on 2026-10-12, whether the stories should have Playwright tests too. The answer was to trace rather than duplicate: no story gains a browser test for its own sake, but every Playwright test whose steps are a story’s flow says which story, with Playwright’s own tag option, `@story-N`, so the checklist can show where a browser proof exists and where it does not ([`design-decisions/m9.17-plan.md`](../design-decisions/m9.17-plan.md)).

The stories checklist (`npm run test:stories`) scans `tests/e2e/**/*.spec.ts` for those tags, marks each story that has one with ` · browser`, and tallies them; a tag naming a number §10 does not list is reported under "Not a v1 story", as a stray describe is. The column reports a tagged spec on disk, not a Playwright run’s result: the Playwright job’s own summary lists the stories its run walked and whether they passed. A tag goes only on a test whose own steps are the story’s flow; visiting a story’s page is not walking it. The existing specs are tagged in the same task, since the column proves nothing until they are, and M11.1 to M11.7 each gain the criterion for the flows they add. No test of the harness and no guard: MB.224 retired the harness’s tests, and review holds the tags as it holds the describe names.

Lands after M6.7, early in the wave, so the specs the wave adds tag their stories as they land, and before Wave 15 aims its seven flows.

_Acceptance criteria:_

- `npm run test:stories` marks every story a spec under `tests/e2e/` tags `@story-N` with ` · browser` and tallies them, read from the spec files rather than from a Playwright run
- A tag naming a number §10 does not list is reported under "Not a v1 story" with its file
- The Playwright CI summary lists the stories its run walked, and a story is failing when any spec tagged with it failed
- Every existing test whose steps are a story’s flow carries its tag, and no test is tagged for a page it merely visits
- `npx playwright test --grep @story-N` runs the tagged tests alone
- DESIGN.md §11, the testing docs, the testing rule and M11.1 to M11.7 say so
- No test of the harness itself and no new guard (MB.224)

### Admin modals (Wave 9)

**M9.18 — Admin modals open at once, with a loading state** · 6h

_Story 18 — As an admin, I want an Edit or Add press to open its modal at once, so that the page does not seem to ignore me while the form loads._

Every admin Edit pencil and Add button was a plain link to `?edit=<slug>` or `?new`, and nothing showed until the server had rendered the whole page again with the modal in it. The owner asked for the modal to open on the press and show a loading state, as the filters (`ListFrame`) and tabs (`TabSwitchProvider`) already do. A `RouteModalProvider` in the admin layout holds the opening in a transition around the soft navigation. Each page renders its one `RouteModal` in a fixed place, so the same dialog shows the form's skeleton and then the form, fading in once. The form's data still comes with the navigation from the server page's existing reads, so no GraphQL query is added (CLAUDE.md rule 1), and a direct request to `?edit=` still renders on the server with the modal open ([`design-decisions/m9.18-plan.md`](../design-decisions/m9.18-plan.md)).

_Acceptance criteria:_

- Pressing Edit on any admin list, or Add beside any admin heading, opens the modal before the page's response arrives, its head as the loaded modal's, its body a skeleton with a status for screen readers
- The form replaces the skeleton in the same dialog element, which fades in once, and the focus moves to its first field
- Closing the modal while it loads keeps it closed when the response lands, and leaves no `?edit=` or `?new` in the address
- A modifier-click or middle-click on Edit, or a press before the page's script loads, still follows the link
- A direct request to `?edit=` or `?new` renders the modal on the server, with no skeleton
- A row gone since the list was drawn closes the modal and shows the missing notice, as before
- The loading modal passes an axe scan
- The Modal, IconTip and admin page docs say so, and the Modal stories hold a Loading story
