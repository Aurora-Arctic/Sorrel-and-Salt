## N6 — Operations and vendor ethics

_17 tasks · 50.5 hours_

**Sequencing** — [N · Wave 06](../../waves/v1-next/wave-06.md). The free tasks come first (N6.1 → N6.14) and the paid tasks after (N6.15 → N6.17). The alert helper (N6.6) comes before the three tasks that call it: the database check (N6.7), the Resend webhook (N6.8), and the uptime task (N6.17). The visit counts table (N6.12) comes before the counting (N6.13), which comes before the keeper page (N6.14). The Vercel Pro move (N6.15) comes before tracing (N6.16). The letters (N6.2), the vendor settings (N6.3), the runbooks (N6.4, N6.11), and the security checks (N6.5) have no code dependency and may run in any order.

These tasks were minted on 2026-11-11 from [`support.md`, "Vendor check against the code of ethics and the operations wave"](../../design-decisions/support.md#vendor-check-against-the-code-of-ethics-and-the-operations-wave). That record holds the vendor findings and their sources, the owner's choices, and the approved plan. Every task follows CLAUDE.md's Testing rules: a wording-only or runbook task runs `format:check` and `lint` and no tests, an authorisation test asserts that direct-id access is refused and shows why it could have succeeded, and no task is met by a skipped or flaky test. A task that changes what the site stores or who handles it updates `documents/privacy.md` in the same PR.

**N6.1 — Make the Privacy Policy Promise Only What Its Processors Commit To** · 2h

_Story:_ As a visitor, I want the Privacy Policy to promise only what the services handling my data have agreed to, so that nothing it says is stronger than what can be kept.

No dependency. The policy sentence "none is given it for any other purpose" in `documents/privacy.md` promises more than the written terms of Vercel, Neon, Resend, and, later, Stripe commit to (vendor check of 2026-11-11, recorded in `design-decisions/support.md`). Editing the file does not change production, because the seed skips a document that already has a version; a keeper publishes the text at `/keepers/documents/privacy`.

_Acceptance criteria:_

- The sentence in `documents/privacy.md` about processors using data for no other purpose, and the "Does Not Do" line about sharing, are rewritten so that each claim matches the documented commitment of the processor it names, and no claim is stronger than a processor's own terms
- "How Long It Is Kept" gives the log retention of the Vercel plan the site is on today
- The PR body carries the full replacement text, so the keeper can publish it at `/keepers/documents/privacy`
- Every changed sentence has its source recorded in `design-decisions/support.md`, in the privacy policy's working notes
- The diff touches only Markdown; the PR runs `format:check` and `lint` and no tests

**N6.9 — Require DMARC and Read the Free Mail Reports** · 1h

- `claude-docs/secrets.md` (Resend setup) and `claude-docs/email.md` say what the records are and how to read the reports, naming no address

**N6.12 — Add the Visit Counts Table** · 2h

_Story:_ As the site keeper, I want a table that counts visits by day and page pattern, so that the counting task has a reviewed schema to write to.

No dependency. This is the table task, per the "table task, then a behaviour task" rule. The counter holds a count per day and route pattern, such as `/coven/[slug]`, never the raw path: a raw path such as `/coven/hedge-witches` would show keepers a coven's name, and keepers have no access to workspace data. It holds no IP address, no user agent, and no visitor identifier, so it holds no personal data. The `rate_limits` table, which counts by route, is the nearest pattern.

_Acceptance criteria:_

- A migration adds the visit counts table with one row per day and route pattern, a partial unique index on that pair, and no column that could hold an address, a user agent, or an identifier of a visitor
- `claude-docs/modules.md` records which module owns the table
- The catalogue-introspection test and the audit-column test cover the table, or the task states why the table is exempt, as `rate_limits` is
- The migration is expand-only and passes `npm run check:destructive-ddl`
- No test is skipped or flaky

**N6.13 — Count Each Page Visit on the Server** · 6h

_Story:_ As the owner, I want the site to count its own visits in its own database, so that I know which pages are used without any script running in a visitor's browser.

Needs N6.12. The count is taken after the response through the existing `after()` wrapper in `src/lib/background-tasks.ts`, keyed by route pattern. `src/proxy.ts` sees every path but may not import the database (CLAUDE.md rule 2), so the choice is between a service the proxy calls and a call from each page. The task decides where the count is taken, and the PR body records the decision. A signed-out visit has no session, so the write needs a named exception outside `withAudit`.

_Acceptance criteria:_

- A visit increments the row for its day and route pattern after the response is sent, and a slow or failed count never delays or fails the response
- A test proves two visits to different coven pages add to one `/coven/[slug]` row and that no stored row holds a slug
- Bots are filtered out by user agent, the user agent is never stored, and a test proves a bot visit adds nothing
- The write is a named write outside `withAudit` in `.claude/rules/database.md`, Rule 3, added in the same PR
- `documents/privacy.md` gains a "Visit Counts" section in "What Is Stored", and its line that the site runs no tracking script stays true
- No test is skipped or flaky
