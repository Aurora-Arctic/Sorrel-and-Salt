**M15.1 — Scope a support form reviewed by admins** · 3h

_Story: As a person using the site, I want to send a question, a problem or a bug report — an accessibility bug included — to whoever runs it from inside the site, so that I am not left searching for an address; and as an admin, I want those messages in one list I can work through, answer, and hand to a curator or another admin, so that nothing is lost in a mailbox._

A scoping task, in the shape of MB.175's: it decides, records and mints, and builds nothing itself. The site has no way to be contacted today. The shape the owner asked for is a form whose submissions are rows in a database table, reviewed by admins on the admin section rather than mailed to them. The record it produces is `claude-docs/design-decisions/m15.1-support-form.md`, and each decision below is answered there, with its reason, before the build tasks are minted.

The decisions to make:

- **Who can submit.** The compendium is the one public surface (MB.80), so a signed-out reader may have a question too. Decide whether the form takes submissions from a signed-out visitor, with the spam exposure that brings, or only from a signed-in account, which is what every other write here requires.
- **The kinds of request.** A question, a bug, and an accessibility bug at least, added on the owner's call (2026-10-15) so that the code of ethics (M15.4) can point to this form as the way an accessibility bug is reported. Decide whether the kind is a column the sender picks, and whether an accessibility bug is listed ahead of the rest.
- **Data requests (an option, not decided here).** Requests under GDPR, the EU's data protection law, such as a copy of one's data or its deletion, may be one more kind on this form. The GDPR scoping task decides whether they are, or have a path of their own; this record notes the option and leaves the kind out until that task chooses.
- **The table.** Its name, and its columns: the sender (an account, or an address when signed out), the kind, a subject, the message, the page it was sent from, a status (open or resolved), who it is assigned to, whether curators may see it, who resolved it and when, and the audit columns every table spreads. Whether replies are rows of their own table, which would be a table task of its own. Soft-deleted or hard-deleted, and whether a resolved row is kept. A support row is written by the person sending it, so decide how it goes through `withAudit` (rule 3) when the sender holds no session.
- **The form.** A modal, the owner's call (2026-10-15), opened from the account menu and the shared footer, and already set to a kind when the link that opens it says so. Decide whether the modal also has an address of its own, so that a link to it works when shared or opened without JavaScript, and what it asks for; the length limits; and whether it says anything back beyond "received".
- **The admin list.** A page under `/admin`, paged through the M3.6 helper (rule 8), newest first, open requests ahead of resolved ones, with the actions an admin needs: reply, assign to a curator or an admin, mark viewable by curators, and mark resolved. The owner settled that an admin replies (2026-10-15); how the reply reaches the sender — mailed, shown on the site, or both, and what a signed-out sender receives — is the decision.
- **The curator view.** A curator (M11.20's role) sees only the requests an admin has marked viewable by curators or assigned to them, the owner's call, and never the rest, refused by direct id as well as absent from the list. Decide whether a curator can reply and resolve what is assigned to them, and whether this is the admin page filtered or a page of its own, since M11.20 keeps curators out of the people page.
- **Abuse.** A limit on how many submissions one account or address may make in a period, and whether a signed-out submission is held for a check before it is listed.
- **What it is not.** Not the help and FAQ articles MB.175 scopes, and not a notes or moderation system (§13). Not a way to request a correction to a compendium entry either: the owner deferred corrections with compendium suggestions (2026-10-15), so the form names no entry and the ingredient detail page carries no link to it.

Then mint the build, each task its own PR, in the order the rules fix: the table task first (`CREATE TABLE` and its migration, nothing else), then the service and mutation under rule 1 and rule 3, then the form modal, then the admin page, then the curator view, with the component docs and stories each page needs. Place them in Wave 15's row before M11.8, whose axe sweep scans every page, and before MB.124, the last design review, so that both cover them. Update `DESIGN.md` in the same PR: the table in §5, the mutation in §8's SDL, the routes in §9.

**M15.2 — A Public Privacy Policy Says What Is Kept and Who Sees It** · 4h

_Story:_ As a person using the site, signed in or not, I want to read what personal data Sorrel & Salt keeps, who processes it, how long it is kept and who can see it, so that I can decide whether to trust the site with it.

The site has no privacy policy today, and no place for documents like it. This task builds that place: a public page layout for documents, reachable without an account and linked from the footer of both the signed-out and the signed-in layouts (the public shell and `AppShell`). The later document tasks (legal disclaimers, the code of ethics and the terms of use) reuse it. It then publishes the privacy policy on it.

The policy's text is drafted from the code and `DESIGN.md`, and the owner reviews it. Every claim traces to a file, so the policy describes what the site does rather than what a template says. It covers:

- **What is stored:** the account fields from the sign-in provider, the address the site writes to, session rows (including the IP address and browser details Better Auth records), the audit columns recording who wrote what, and what a coven holds.
- **Who processes it:** the hosting, database, mail and sign-in providers, each named, never a configured value.
- **How long it is kept:** soft deletes, where a deleted row is marked rather than removed, so "deleted" does not mean erased today.
- **How to ask for removal:** until the GDPR scoping task's builds land, by contacting whoever runs the site.
- **Who can see what:** a table for coven owners, members, viewers, curators (as M11.20 defines them), site admins and developers with database access. Each cell is taken from the authorization rules in the services, not from the screens.

The page may be indexed by search engines, but the site's own search does not list it. It runs after M11.20, so the curator role it describes exists.

**M15.6 — Switching Theme Doesn't Freeze the Page** · 3h

_Story:_ As anyone using Sorrel & Salt on a slow phone, I want switching between light and dark to respond straight away, so that the page doesn't freeze for half a second each time I change the theme.

Today, switching theme makes about 300 elements each run their own 400ms colour fade (the `theme-transition` mixin in `src/scss/_mixins.scss`, timed by `$theme-transition-duration`). We profiled a production build in Chromium with the processor slowed 6× (2026-10-20). The switch to dark took 464ms to respond at phone width and 480ms at desktop width, against about 72–104ms with the fades turned off. This task replaces the many fades with one cross-fade of the whole page through the browser's View Transitions API (`document.startViewTransition`). That API is not yet Baseline Widely Available, so it's used only when the browser has it, behind an `in` check. Other browsers swap the theme instantly. The colours themselves don't change.

_Acceptance criteria:_

- The theme toggle calls `document.startViewTransition` to swap the theme when the browser has it, and swaps the theme straight away when it doesn't. Component tests prove both paths, and prove the theme ends up set either way
- With `prefers-reduced-motion: reduce`, the theme swaps with no cross-fade
- No element runs a colour transition when the theme changes: the `theme-transition` mixin and `$theme-transition-*` are gone, and nothing replaces them
- Each theme's colours are unchanged, and the design-token snapshot is unchanged
- Measured the same way as the 2026-10-20 profile (production build, Chromium slowed 4× and 6×, at 390px and 1280px wide), the switch responds within 200ms at 6× at both widths. The before and after figures are in the PR body
- `claude-docs/components/theme-toggle.md` and `claude-docs/styling.md` describe the cross-fade and its fallback

**M15.7 — Pages Respond Quickly on Slow Devices** · 10h

_Story:_ As anyone using Sorrel & Salt on a slow phone, I want a tap, a keystroke or a dialog to respond as soon as I use it, so that the app doesn't feel frozen while it loads or redraws.

The 2026-10-20 profile was a production build in Chromium with the processor slowed 6×. Its figures are relative, not absolute: it ran on localhost with no network delay, an unthrottled graphics processor and Chromium only. It found three costs:

1. **After a page loads,** React spends 300–570ms attaching itself to the server's HTML. A tap during that time waits: opening Quick Look took 432–648ms straight after load, against 136ms once the page had settled. `/compendium` sends 399 KB of HTML, about 59% of it React's data, plus 1.4 MB of scripts (413 KB compressed).
2. **Add Ingredient and Quick Look** each open in a single redraw of about 190ms and 140ms.
3. **Each keystroke in search** does 100–150ms of work straight away, then a further redraw of about 140ms. Next Page and Clear freeze the page for 150–280ms while the cards are drawn.

The network lookup is already delayed until typing stops (`useDebouncedValue`, `src/lib/debounce.ts`); the cost is the redraw on every keystroke.

This task:

- loads the dialogs and menus only when first opened (`next/dynamic`);
- passes the cards less data from the server;
- skips drawing off-screen cards (`content-visibility: auto`);
- shows each dialog's frame before its contents;
- keeps each keystroke to updating the search box. The list update becomes low priority (`useDeferredValue` or `startTransition`), so React can drop a half-finished redraw when the next key arrives.

It starts by measuring how much of each keystroke's cost is the search box and how much is the list below it.

_Acceptance criteria:_

- Quick Look, Add Ingredient and the Account menu load their code only when first opened. A spec opens each one and finds it working
- `/compendium`'s HTML and first-load scripts are smaller than the 2026-10-20 figures (399 KB of HTML; 413 KB of scripts, compressed). The before and after sizes are in the PR body
- Opening Add Ingredient or Quick Look shows the dialog frame before its contents. Focus, closing with Escape and the existing tests behave as before
- A keystroke in search updates the box at once, and the list follows it as a low-priority update. Next Page and Clear draw their cards the same way
- Measured the same way as the 2026-10-20 profile, at 6× and at both widths, each of these flows responds faster than it did then, and the before and after figures are in the PR body: a tap straight after load, opening each dialog, typing, Next Page and Clear
- Behaviour on a fast device is unchanged: the existing component, story and e2e suites pass, and the axe checks still pass
- `claude-docs/components/modal.md`, `compendium-list.md`, `compendium-cards.md` and `ingredient-search.md` describe what loads on first open and what draws at low priority

**M15.8 — Pages Download Only the GraphQL Queries They Use** · 2h

_Story:_ As anyone using the site, I want each page to download only the GraphQL queries it uses, so that pages load less JavaScript.

Browser code builds its GraphQL queries and changes with `graphql()` from the generated client in `src/gql/`, in 37 files (for example `src/components/IngredientEntry/add-cupboard-entry.ts`). Codegen's `client` preset makes that function look each one up in `src/gql/gql.ts` (94 KB), a map from every document in the app to its parsed form in `src/gql/graphql.ts` (149 KB). A bundler cannot drop the entries a page does not use, so any page that runs one query probably downloads them all.

The usual fix is codegen's compiler plugin for the client preset, which rewrites each `graphql()` call at build time to import only its own document. `next.config` uses none today. The task first checks that the plugin runs under this Next.js version's bundler, Turbopack (`node_modules/next/dist/docs/`); if it does not, it says so and proposes codegen's `documentMode: 'string'` instead, before building either.

Measure with a bundle analysis before and after, building into its own `NEXT_DIST_DIR` and never `.next`.

_Acceptance criteria:_

- A browser page that runs a GraphQL query or change ships only the documents it uses: the built client chunks of a page using one document hold no other document's text
- Every query and change still works and is typed as before: `npm run codegen` leaves `src/gql/` clean, and the type check, component, story and e2e suites pass
- `npm run build` succeeds with the plugin running under Turbopack, and `npm run dev` still serves the app
- The PR body gives the first-load script sizes, compressed, of `/compendium` and one coven page, before and after
- `claude-docs/graphql/` describes the plugin, and DESIGN.md §7's client paragraph says each document is compiled into its caller

_Story:_ As a site admin, I want to search the invitation card batches by batch, status, minted date and expiry date, so that I can find one batch among many without paging through them.

Builds on M15.19 and M15.22. The Invitation Cards tab takes the shared `FilterForm` layout the other People tabs use (Privilege Changes, Invitations), held in the URL: Batch, a search box matching the start of the batch number; Status, a dropdown of All, Live, Revoked, Expired and Used up; Minted From and Minted To; and Expires From and Expires To. Every field is optional and any combination applies together. The `invitationCardBatches` connection takes the filter and applies it in SQL (rule 7), the status included, worked out from the batch's counts and expiry the way `batchStatus()` does, and still pages through `findPage`.

_Acceptance criteria:_

- Repository tests prove each filter alone and two combined, each with a batch the filter must leave out, and that a date range includes both of its end days
- A test proves the SQL status agrees with `batchStatus()` for a batch in each of the four states
- Authorization tests prove a curator, a member and a signed-out caller are each refused the filtered connection by direct call
- The filtered connection still paginates (`tests/guards/pagination.test.ts` passes)
- Component tests, by role and label queries, prove each field writes the URL and the table shows what the URL holds, and that clearing the filter shows every batch
- Playwright's axe check passes on the tab with a filter applied
- `claude-docs/components/admin-cards.md` describes the filter

**M15.24 — An Admin Searches Card Sign-Ups** · 2h

_Story:_ As a site admin, I want to search the card sign-ups by the account's name or email and by batch, so that I can find who arrived by a given card batch or whether one person did.

Builds on M15.19. The Card Sign-Ups tab takes the same `FilterForm` layout, held in the URL: Name or Email, one search box matching part of either, as the Privilege Changes tab does; and Batch, a search box matching the start of the batch number. Both apply in SQL, the list still paginates, and the CSV download carries the same filter.

_Acceptance criteria:_

- Repository tests prove a name match, an email match, a batch match and both fields together, each with a sign-up the filter must leave out
- A test proves the CSV holds only the filtered rows
- Authorization tests prove a curator, a member and a signed-out caller are refused the filtered list by direct call
- Component tests, by role and label queries, prove each field writes the URL and the list shows what the URL holds
- Playwright's axe check passes on the tab with a filter applied
- `claude-docs/components/admin-cards.md` describes the filter
