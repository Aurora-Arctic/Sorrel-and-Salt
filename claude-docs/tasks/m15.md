**M15.6 — Switching Theme Doesn't Freeze the Page** · 3h

_Story:_ As anyone using Sorrel & Salt on a slow phone, I want switching between light and dark to respond straight away, so that the page doesn't freeze for half a second each time I change the theme.

Today, switching theme makes about 300 elements each run their own 400ms colour fade (the `theme-transition` mixin in `src/scss/_mixins.scss`, timed by `$theme-transition-duration`). We profiled a production build in Chromium with the processor slowed 6× (2026-10-20). The switch to dark took 464ms to respond at phone width and 480ms at desktop width, against about 72–104ms with the fades turned off. This task replaces the many fades with one cross-fade of the whole page through the browser's View Transitions API (`document.startViewTransition`). That API is not yet Baseline Widely Available, so it's used only when the browser has it, behind an `in` check. Other browsers swap the theme instantly. The colours themselves don't change.

_Acceptance criteria:_

- The theme toggle calls `document.startViewTransition` to swap the theme when the browser has it, and swaps the theme straight away when it doesn't. Component tests prove both paths, and prove the theme ends up set either way
- With `prefers-reduced-motion: reduce`, the theme swaps with no cross-fade
- No element runs a colour transition when the theme changes: the `theme-transition` mixin and `$theme-transition-*` are gone, and nothing replaces them
- Each theme's colours are unchanged, and the design-token snapshot is unchanged
- Measured the same way as the 2026-10-20 profile (production build, Chromium slowed 4× and 6×, at 390px and 1280px wide), the switch responds within 200ms at 6× at both widths. The before and after figures are in the PR body
- `claude-docs/components/theme-toggle.md` and `claude-docs/styling.md` describe the cross-fade and its fallback

**M15.7 — Pages Respond Quickly on Slow Devices** · 10h

_Story:_ As anyone using Sorrel & Salt on a slow phone, I want a tap, a keystroke or a dialog to respond as soon as I use it, so that the app doesn't feel frozen while it loads or redraws.

The 2026-10-20 profile was a production build in Chromium with the processor slowed 6×. Its figures are relative, not absolute: it ran on localhost with no network delay, an unthrottled graphics processor and Chromium only. It found three costs:

1. **After a page loads,** React spends 300–570ms attaching itself to the server's HTML. A tap during that time waits: opening Quick Look took 432–648ms straight after load, against 136ms once the page had settled. `/compendium` sends 399 KB of HTML, about 59% of it React's data, plus 1.4 MB of scripts (413 KB compressed).
2. **Add Ingredient and Quick Look** each open in a single redraw of about 190ms and 140ms.
3. **Each keystroke in search** does 100–150ms of work straight away, then a further redraw of about 140ms. Next Page and Clear freeze the page for 150–280ms while the cards are drawn.

The network lookup is already delayed until typing stops (`useDebouncedValue`, `src/lib/debounce.ts`); the cost is the redraw on every keystroke.

This task:

- loads the dialogs and menus only when first opened (`next/dynamic`);
- passes the cards less data from the server;
- skips drawing off-screen cards (`content-visibility: auto`);
- shows each dialog's frame before its contents;
- keeps each keystroke to updating the search box. The list update becomes low priority (`useDeferredValue` or `startTransition`), so React can drop a half-finished redraw when the next key arrives.

It starts by measuring how much of each keystroke's cost is the search box and how much is the list below it.

_Acceptance criteria:_

- Quick Look and Add Ingredient load their code only when first opened. A spec opens each one and finds it working. The Account menu's panel loads with the page, so a press opens it at once
- `/compendium`'s HTML and first-load scripts are smaller than the 2026-10-20 figures (399 KB of HTML; 413 KB of scripts, compressed). The before and after sizes are in the PR body
- Opening Add Ingredient or Quick Look shows the dialog frame before its contents. Focus, closing with Escape and the existing tests behave as before
- A keystroke in search updates the box at once, and the list follows it as a low-priority update. Next Page and Clear draw their cards the same way
- Measured the same way as the 2026-10-20 profile, at 6× and at both widths, each of these flows responds faster than it did then, and the before and after figures are in the PR body: a tap straight after load, opening each dialog, typing, Next Page and Clear
- Behaviour on a fast device is unchanged: the existing component, story and e2e suites pass, and the axe checks still pass
- `claude-docs/components/modal.md`, `compendium-list.md`, `compendium-cards.md` and `ingredient-search.md` describe what loads on first open and what draws at low priority

**M15.8 — Pages Download Each GraphQL Query Once, as Text** · 6h

_Story:_ As anyone using the site, I want each GraphQL query to download once, as text, so that pages load less JavaScript, and none of the server's.

Browser code builds its GraphQL queries and changes with `graphql()` from the generated client in `src/gql/`, in 37 files (for example `src/components/IngredientEntry/add-cupboard-entry.ts`). Today codegen writes each document twice: as a parsed tree in `src/gql/graphql.ts`, which one 194 KB chunk carries for every page, and as query text in its caller. This task sets codegen's `documentMode: 'string'`, so each document is written only as its query text and the browser downloads it once. Codegen's compiler plugin, which would also have split the documents per page, did not split them under Turbopack; see [`graphql.md`, "Each GraphQL document ships as its caller's text"](../design-decisions/graphql.md#each-graphql-document-ships-as-its-callers-text). Splitting per page is not built by that plugin.

On 2026-11-07 the owner widened the task, because the string documents saved about 3 KB compressed. The documents weigh 11.8 KB compressed on `/compendium`, and two server packages weigh more: `@pothos/core` (10.6 KB), the schema builder, and `graphql` (13.2 KB), which Pothos imports. They reach the browser because client files such as `src/components/CompendiumList/params.ts` import `src/lib/search-params.ts`, which imports `decodeCursor` from `src/lib/pagination.ts`, and that file imports Pothos. This task cuts that path, splits the documents so each page downloads only its own, and checks the first-load scripts for any other package the browser does not need.

Measure with a bundle analysis before and after, building into its own `NEXT_DIST_DIR` and never `.next`.

_Acceptance criteria:_

- Codegen writes every document as its query text (`documentMode: 'string'`), so the browser no longer downloads the documents as parsed trees as well as text
- Every query and change still works and is typed as before: `npm run codegen` leaves `src/gql/` clean, and the type check, component, story and e2e suites pass
- Everything that reads a document still works on the string form, including the fetch helper and the guard on how deeply a query may nest, and each has a test that proves it on a string document
- No file the browser loads imports `@pothos/core` or `graphql` at runtime. A guard test fails when one does, and it fails with the cut undone
- Each page downloads only the documents its own code uses, not all of them
- A bundle analysis lists every package in the first-load scripts of `/compendium` and one coven page. Each one the browser does not need is cut, or `claude-docs/design-decisions/graphql.md`, "Each GraphQL document ships as its caller's text", says why it stays
- The PR body gives the first-load script sizes, compressed, of `/compendium` and one coven page, before and after
- `claude-docs/graphql/` describes the string documents, and DESIGN.md §7's client paragraph says each document ships once, as text

**M15.83 — Typing Into a Suggestion Field Writes Only What Changed** · 3h

_Story:_ As anyone typing into a suggestion field on a slow phone, I want each key I type to appear at once, so that the field doesn't lag behind my typing.

M15.82's trace of one keystroke on `/compendium` (2026-11-07) found two costs inside the shared suggestion field, `src/components/Combobox/`, which every form with suggestions uses. First, on every key the field rewrites its input's `name` and `aria-busy` attributes, even when the values are unchanged. The page has `:has()` style rules, so every change to an attribute makes the browser re-check them. Second, Floating UI, the library that places the suggestion dropdown under the input, reads the input's size and position on every key. That read makes the browser finish its style and layout work mid-keystroke instead of once at the end. Together the two cost about 20–25 ms of browser work per key at 6× CPU slowdown. This task finds why each happens and removes the work that changes nothing. It is built on PR #1610's branch.

_Acceptance criteria:_

- `claude-docs/design-decisions/ui.md`, "The suggestion field writes only what a keystroke changes", records why the field rewrites `name` and `aria-busy` on a keystroke, and when Floating UI reads the input's size and position
- A keystroke writes `aria-busy` only when its value changes, and writes the dropdown's width and `--combobox-list-room` only when they change. A component test proves it by watching the input and the dropdown for attribute changes, and the test fails with the fix removed. React rewrites the input's `name` on every keystroke from its own input update code, which the field cannot stop while React renders the input, so the test does not watch `name`, and the record says why
- When the dropdown closes only because a lookup is pending, Floating UI keeps its subscription, so the reopen does not measure the input again; and each position computation reads the bottom bar once
- Measured as M15.7 was measured (production build, Chromium at 6× slowdown, 390 px and 1280 px, Event Timing), a keystroke's event time on `/compendium` is no higher than before, and the browser's style and layout time per keystroke is lower, at both widths. The before and after figures are in the PR body
- Every form that uses the field behaves as before: its suggestions, its keyboard handling and what a screen reader is told. The existing Combobox component tests, and the e2e and story specs of the forms that use it, pass, and the axe checks still pass
- `claude-docs/components/combobox.md` describes what a keystroke writes to the page

**M15.74 — Erase an Account in Place When Its Holder Asks** · 8h

_Story:_ As a keeper answering a privacy request, I want to erase everything that identifies the person behind an account while keeping the account, so that the site honours erasure under the rule that an account is paused, never closed.

Builds on M15.73's column and M15.46's request anonymiser. A request counts as verified when the account sends it while signed in: the account's own sign-in (password, passkey or a provider, plus two-factor where it is on) is the identity check. The `privacy` subject on `/support?support=privacy` records the sender as `created_by`, and a paused account can still sign in and reach support, so pausing never stops anyone from asking. A signed-out request carries only an address the sender typed, which proves nothing, so it is not acted on directly. The admin replies asking the person to sign in and send the request from their account. If the person cannot sign in any more, the admin mails the address held on the account, never the typed address, and acts once that mailbox replies. The site never asks for an identity document. The one-month clock (GDPR article 12(3)) starts once identity is confirmed; M15.58's scope confirms this against the ICO's guidance before the privacy policy cites it.

Builds after the Wave 18 tasks it may reuse ([`support.md`, "A way for people to take their own writing with them"](../design-decisions/support.md#a-way-for-people-to-take-their-own-writing-with-them), "Built for reuse by erasure"): the classification map and its catalogue test (M18.3), the subject-scoped finders and the "fill every table" test fixtures (M18.3), the `privacy_requests` table (M18.1), the link-and-code confirmation (M18.6) and the keeper action that names a support request (M18.7). This task chooses how far to use them; the scope decides nothing about erasure.

_Acceptance criteria:_

- It is refused, each with an explaining error, when:
  - the request was not sent while signed in by that same account (the identity rule above)
  - the account is the System account or the signed-out sender account
  - the account holds a keeper or curator role, which must be removed first so the ledger records it
  - the account owns a coven where it is the only steward
- In one `withAudit` transaction it:
  - sets `name`, `image`, `former_email` and `pending_email` to null or a placeholder

  - sets an open-ended site pause whose note names the request

  - clears a working-participant name that is the account's
- A pause on an erased account cannot be lifted, and the refusal explains why
- Content the account wrote in shared covens stays with each coven, credited to no name, and the privacy policy says so
- The person can sign up again with the same address and gets a new, empty account
- An Erase Account button with a confirmation dialog sits in the People page's user modal, admin only
- The privacy policy's "How to Ask for Removal" and the Terms of Use's "Leaving" section describe exactly this, and the policy gains a paragraph on how a person's identity is checked
- The privacy policy and the Terms of Use state how erasure fits the rule that an account is paused, never closed
- The privacy policy (M15.2) is corrected wherever the M15.58 scope finds it wrong, and gains the GDPR sections it lacks: who runs the site, the lawful basis for each kind of data, a person's rights, transfers and the processors' agreements, and how to complain to a supervisory authority. _Story:_ As a visitor, I want the site to remember which way I sign in only if I ask it to, so that it stores nothing on my device I did not agree to and never needs a consent banner.

The `better-auth.last_used_login_method` cookie (`src/lib/sign-in.ts`) shows a "last used" hint on the sign-in page. It is a convenience, not strictly necessary, so the EU rule (ePrivacy Directive article 5(3)) needs consent before it is set. The UK's rules from 5 February 2026 (PECR Schedule A1 paragraph 6) might exempt it, but the EU's do not. The owner chose on 2 November 2026 to keep the cookie and ask for consent on the sign-in page itself, where the cookie is used, rather than remove it or add a site-wide banner (`design-decisions/support.md`, "Decisions for the owner"). The `theme` and `card-density` local-storage items stay as they are, stated in the policy under the UK exemption (same file, "Cookies and browser storage").

_Acceptance criteria:_

- The sign-in page has a "Remember My Sign-In Method on This Device" checkbox, unticked by default and labelled for assistive technology
- Signing in with the box unticked sets no `better-auth.last_used_login_method` cookie and clears one already set; signing in with it ticked sets it
- The box shows ticked when the cookie is present, so a person can withdraw consent by unticking it and signing in
- The "last used" hint shows only when the cookie is present
- A test asserts that signing in with the box unticked sets no cookie outside the authentication set
- The privacy policy names the cookie as set only when the person ticks the box, says how to withdraw, and names every other item the site stores on a device: the short-lived sign-in handshake and two-factor cookies, the 30-day two-factor trust cookie, `admin_session`, and the `theme`, `card-density` and `autosave:*` local-storage items, each with its purpose
- The policy says a person can object to the preference items and how
