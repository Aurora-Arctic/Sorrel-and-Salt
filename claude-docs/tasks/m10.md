**M10.3 — Spell visibility column and the service rule** · 1h

_Story:_ As a workspace member, I want to keep a spell to myself, so that I can record a working that is nobody else's business without leaving the workspace.

Add `visibility` (`private` | `workspace`) to spells, defaulting to workspace, and filter private spells to their author in the finder — in SQL, under rule 7, so a private spell never reaches a resolver.

**Re-scoped by MB.29.** MB.24 had left this task half policy; with RLS deferred it is the column plus the service rule, and the filtering happens where every other workspace-scoped predicate now happens — inside the finder, which already takes M6.3's `Membership` and ANDs its own `workspace_id` clause. The author id joins the proof as an argument rather than arriving through a session variable.

The MB.24 finding it keeps: `spell_ingredients` and `spell_categories` reach their spell by FK and carry no `workspace_id` of their own. Whatever this task does to `spells`, a private spell's _ingredients_ must not remain readable through the join tables, or the visibility rule holds for the spell and leaks its contents. Those two tables cannot self-scope, so their finders load the parent spell under the proof and derive visibility from it — the gap CLAUDE.md rule 5 names, closed here by test rather than by the type.

_Acceptance criteria:_

- Column added with a default of workspace and no nulls
- The spell finder admits a private spell only to its author, filtering in SQL rather than after fetching
- A private spell's rows in `spell_ingredients` and `spell_categories` are refused to everyone but its author — **by direct id**, not merely absent from a list
- Each denial test asserts why the read could have succeeded: the row exists, the fixture is populated, and the same call as the author returns it
- Widening `private → workspace` is allowed and `workspace → private` is refused with an explaining error, not a bare `Forbidden` (the service half of M10.6's rule)
- Existing seeded spells migrate to workspace visibility — asserted against a row written before the column existed, not only against the default a fresh insert takes
- ~~The PR carries the M1.5 destructive-DDL acknowledgement line: this adds NOT NULL to a table that now holds seeded rows~~ — **struck.** `ADD COLUMN … DEFAULT … NOT NULL` in one statement is not destructive DDL and the check does not flag it, so there is nothing for a sidecar to acknowledge. See [`TASKS.md`](../TASKS.md)'s "Breaking the M1.23 ↔ M10.3 cycle"

**M10.24 — Browser floor: Baseline Widely Available, held by lint and a guard** · 4h

_Story:_ As a developer, I want one written browser floor that the build and the checks enforce, so that nobody ships CSS or JavaScript a supported browser cannot run, and a newer feature never breaks a core flow.

Until now the only statement was one bullet in `claude-docs/styling.md`: Next's default targets, Chrome, Edge and Firefox 111 and Safari 16.4, frozen on 2025-10-01. Nothing enforced it, and the code had already passed it: `:has()` needs Firefox 121, `URL.canParse()` (reached in the browser through the reference form) needs Chrome 120 and Safari 17. The owner chose, on 2026-10-12: the floor is Baseline Widely Available, a feature in all four engines for 30 months; below it the app degrades and never breaks; CI stays Chromium only; and enforcement is a `browserslist` entry with a stylelint rule, a guard test and a design-review line. The floor rolls forward each month, and today it resolves to Chrome and Edge 123, Firefox 124 and Safari and iOS Safari 17.4. The argument and the options are `claude-docs/design-decisions/m10.24-plan.md`, which also lists the CSS and JavaScript the code uses today.

_Acceptance criteria:_

- `package.json` holds `"browserslist": ["baseline widely available"]`, and a build into a scratch `NEXT_DIST_DIR` still lowers `light-dark()`, since Safari 17.4 is below the 17.5 it needs
- `stylelint-plugin-use-baseline` runs in `npm run lint:css` with `available: "widely"`, and every report is resolved by `@supports` with a fallback, by a disable comment naming what is lost and the date the feature becomes widely available, or by removing the feature; a scratch rule past the floor fails the lint, shown and then deleted
- `tests/guards/browser-floor.test.ts` fails on a listed web API in client-reachable source that has no `typeof` or `in` check, reads each entry's date from the `web-features` package, and fails with "delete this entry" once the feature is widely available, so the list prunes itself; it checks a precondition so an empty scan cannot pass
- `CLAUDE.md` carries the rule as one line, `.claude/rules/components.md` the long form (the floor, the three allowed shapes for a feature past it, the disable comment's wording), `claude-docs/styling.md` replaces the frozen-target bullet and the "oldest browser supported" line, "Designing a section" gains the review line, and `claude-docs/agent-skills.md` and `claude-docs/commands.md` say so
- The decision is recorded in `claude-docs/design-decisions/m10.24-browser-floor.md`
