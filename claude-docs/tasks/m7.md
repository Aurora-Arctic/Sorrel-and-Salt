### Invitations

**M7.1 — workspace_invitations schema** · 1h

_Story:_ As an owner, I want invitations stored safely so that a leaked database row cannot be redeemed.

Add the table with id, workspaceId, email, role, tokenHash, expiresAt, acceptedAt, acceptedBy, revokedAt and audit columns. Only the hash is stored. The role column accepts `viewer` or `member` only — owner is deliberately not invitable, and the constraint lives in the database so no future code path can widen it by accident.

**Folded into MB.201 (2026-10-10):** `workspace_invitations` was copied into the one two-tier `invitations` table, whose workspace tier it is, undeclared by MB.202 and dropped by MB.203; the criteria below hold of that table ([`design-decisions/mb.201-two-tier-invitations.md`](../design-decisions/mb.201-two-tier-invitations.md)).

_Acceptance criteria:_

- No column holds the plaintext token
- A check constraint rejects an invitation with role owner
- Expiry has a sensible default
- Indexed for lookup by token hash
- Full audit spread present

**M7.2 — Token generation and hash-only storage** · 1h

_Story 4 — As a workspace owner, I want an invitation link stored only as a hash and handed to the mail sender once, so that a leaked database row cannot be redeemed._

Service generating an invitation token, storing only its hash, and returning the plaintext exactly once to the caller. Generate it with a CSPRNG — a cryptographically secure pseudorandom number generator, meaning `crypto.randomBytes()` from Node's crypto module, never `Math.random()`. The difference matters: `Math.random()` is a fast, predictable generator, so anyone who collects a few tokens can work out the internal state and compute the next ones. A CSPRNG draws from the operating system's entropy pool and gives no such foothold. Unit tests cover generation, hashing and single-return.

**Amended by MB.202 (2026-10-10):** the hash is taken in the repository, by `hashToken`, inside the named `insertInvitation(membership, values)`, which takes the token and never a hash and fills the workspace from the owner's `Membership`; the service generates the token and hands it over ([`db/invitations.md`](../db/invitations.md), "Written and read by tier"). **Amended 2026-10-12 after the Wave 10 review**, on the owner's call (re-estimated from 2h): the token generator already exists. `newToken()` (`randomBytes(32).toString('base64url')`) is a private function in `src/modules/identity/services/admin-invitations.ts`, and the hash is already taken by `hashToken` in `src/db/repository/tokens.ts`, inside the repository's `insertInvitation`. So this task does one thing: it extracts `newToken` into a single shared helper that both tiers of `invitations` call. Services may not import the repository's internals, so the helper does not live beside `hashToken`; the implementer picks its home, `src/lib/` or the identity module. The story line no longer says "shown once", which contradicted MB.61: no link is ever rendered, and the plaintext is handed to the mail sender once and goes to no response and no query.

_Acceptance criteria:_

- Token is generated with crypto.randomBytes(), not Math.random(), by one helper both tiers call (the extracted `newToken`)
- Token carries at least 128 bits of entropy
- Only the hash reaches the database
- The plaintext goes to the mail sender once and to no response or query, and is never retrievable afterwards (MB.61)
- Holding one token gives no way to guess another
- What a CSPRNG is, and why `crypto.randomBytes()` rather than `Math.random()`, is explained once in [`db/invitations.md`](../db/invitations.md), so the next reader need not look it up

**M7.3 — createInvitation mutation that mails the link** · 3h

_Story 4 — As a workspace owner, I want to invite someone by email with a chosen role, so that I control what a new member can do before they arrive and only the holder of that address can accept._

Owner-only mutation returning the `Invitation`. The link is sent to the invited address through `mail.send` (MB.65) and appears in no response body and no query, ever. The invitable roles are viewer and member, never owner, for §14's reason, and acceptance is bound to a verified matching address (M7.5). A failed send is logged, not thrown: the row stays pending and the owner can revoke and re-invite, the same degradation the verification mail has ([`design-decisions/mb.61-email-verification-and-delivery.md`](../design-decisions/mb.61-email-verification-and-delivery.md)). **Amended by MB.202:** the service is `coven`'s `createInvitation`, writing through the repository's `insertInvitation(membership, values)` on the workspace tier of `invitations`. **Amended 2026-10-12 after the Wave 10 review**, on the owner's call: the estimate rises from 2h because the earlier text left out several pieces. (1) A coven invitation mail template in `src/emails/`, beside `admin-invitation.tsx` and `verify-email.tsx`, with its `.stories.tsx` and a test under `tests/emails/`; every mail is rendered twice by `renderParts` in `src/emails/parts/layout.tsx`, as HTML and as plain text, and the plain-text part carries the link, because story 4's acceptance test reads the token from it with `/\/invite\/([A-Za-z0-9_-]+)/`. (2) A `workspaceInvitation` method on `InvitationSender` (`src/modules/identity/types.ts`, which has only `siteInvitation(to, token)` today), built in `src/lib/invitation-mail.ts`, and on the test double. (3) In GraphQL, an `InvitableRole` enum and the `Invitation.workspace` and `Invitation.role` fields, added from `coven`, since the `Invitation` type in `src/modules/identity/graphql/invitations.ts` has neither (identity cannot name `Workspace`) and its comment says this task adds them; there is no `createInvitation` mutation yet either. (4) The address is normalised and validated as `createAdminInvitation` does, with `normaliseEmail` and `validateEmailAddress`. (5) The service checks the `member: invite` permission, which only owners hold (`src/modules/coven/services/access-control.ts`). (6) The signature is the one the story scaffolds in `tests/acceptance/01-accounts.test.ts` (stories 4 to 7) pin: `createInvitation(session, workspaceId, { email, role }, sender)`, exported from `@/modules/coven`, with the sender typed `ReturnType<typeof invitationSender>`. Two decisions: a second pending invitation to an address already invited is not refused, the admin tier's answer (`claude-docs/auth/admin-users.md`, "Inviting"); and inviting an address that already belongs to a live member of the workspace is refused with an explaining error. `mail.send` (`src/lib/mail.ts`) never throws and logs failures with `console.error`, which is what lets a failed send leave the row pending.

_Acceptance criteria:_

- Only owners can call it
- Role must be viewer or member; owner is rejected with a clear error
- Role is chosen at creation and honoured on acceptance
- The link reaches the invited address through the mail transport, asserted against the transport's test double, and is absent from the mutation response and from every query
- A send failure leaves the invitation pending and the mutation succeeds, asserted with the transport failing
- Any workspace can be invited into, including a user's first one
- Rejection happens at the service, not only in the schema enum
- `createInvitation(session, workspaceId, { email, role }, sender)` is exported from `@/modules/coven` with the signature story 4's scaffold uses
- The coven invitation mail has its template, story and test; its plain-text part carries the `/invite/<token>` link, which story 4 reads the token from
- `InvitationSender` has a `workspaceInvitation` method, on the real sender and the test double
- GraphQL has an `InvitableRole` enum (viewer, member) and `Invitation.workspace` and `Invitation.role` fields, added from `coven`
- The address is normalised and validated as `createAdminInvitation` does; a malformed address is refused
- A second pending invitation to an address already invited is accepted, not refused, asserted
- Inviting an address that belongs to a live member of the workspace is refused with an explaining error, asserted with the member present so the refusal is the check's and not an absence

**M7.7 — Reject expired, revoked and reused tokens** · 2h

_Story 7 — As a workspace owner, I want expired, revoked and already-used links rejected, so that an old link in someone's inbox is not a way in._

The redeemer-facing half: everything that can make a link unusable, checked in one place on the acceptance path. Three separate conditions, three distinct messages — expired (the clock ran out), revoked (the owner withdrew it, the state M7.6 creates), and already accepted (someone used it). One generic 'invalid link' would leave the recipient unable to tell whether to ask for a new invitation or check whether they are already a member. Messages must not name the workspace, since the reader is by definition not a member of it. **Amended by MB.202:** the checks run in the one accept service M7.5 builds, so they hold on both tiers of `invitations`, and MB.70's site-tier invitation takes the same three rejections rather than its own. **Corrected 2026-10-10, on the owner's call**, since MB.70 runs in Wave 8 and M7.5 and M7.7 in Wave 10 (re-estimated from 2h): MB.70 builds the three checks, before the tier branch; this task asserts each on the workspace tier, that no message names the workspace, and story 7's acceptance test. **Amended 2026-10-12 after the Wave 10 review**, on the owner's call (re-estimated from 1h): the closing criterion is an end-to-end spec. No e2e spec walks a workspace invitation today; `tests/e2e/invite.spec.ts` is the site tier (`@story-62`), and `DESIGN.md` §11's e2e line expects "B accepts, signs in, and lands in W". Story 7's acceptance test in `tests/acceptance/01-accounts.test.ts` asserts the `invitationStanding(...).reason` codes `'expired' | 'revoked' | 'accepted'`.

_Acceptance criteria:_

- Expired token rejected, with a message saying so
- Revoked token rejected, distinctly from expired
- Already-accepted token rejected, distinctly from both
- A token that is both expired and revoked reports one reason, deterministically
- No message reveals the workspace name to a non-member
- Story 7 acceptance test passes
- An e2e spec walks stories 4 to 7, tagged `@story-4` to `@story-7`: A invites B by mail, B signs in from the link and lands in W, and a revoked link and a used link are each refused with their own reason, no message naming the coven
