### Spell steps

**M13.1 — Spell steps: the recipe is one ordered list of steps** · 4h

_Story 80:_ As a workspace member, I want a spell's steps recorded in one order, each an instruction, an ingredient, or both, so that the ritual is kept beside what goes in the jar.

Table task, the first of the spell steps and workings plan (2026-10-16, the owner's call; the plan is copied to [`design-decisions/m13.1-plan.md`](../design-decisions/m13.1-plan.md) in this task's PR). A spell's recipe becomes one ordered list of steps, where a step is an instruction, an ingredient, or both. The step is a row in the existing ordered table, not a second table beside it, by MB.40's own argument that one ordered list cannot span two tables ([`design-decisions/mb.40-custom-spell-ingredients.md`](../design-decisions/mb.40-custom-spell-ingredients.md), "Why not the alternatives"). "Layer" survives only as the word for a step that lays an ingredient.

The migration is `0083` (staging's latest is `0081_compendium-seed-state-expand.sql`, and `0082` is taken by a branch in flight): one expand migration, written with `drizzle-kit generate --custom` and a hand-edited snapshot as `0067_celestial-bodies-expand.sql` was ([`db/expand-contract.md`](../db/expand-contract.md)): `spell_ingredients` is renamed `spell_steps`, its indexes, CHECKs and foreign keys renamed with it, and a `spell_ingredients` view left under the old name for the deploy still running (MB.252). Renaming a table renames none of its constraints or indexes, so the migration renames each: the unique indexes `spell_ingredients_spell_id_layer_order_unique`, `spell_ingredients_spell_id_variant_id_unique` and `spell_ingredients_spell_id_custom_name_unique`; the CHECKs `spell_ingredients_ingredient_or_name`, `spell_ingredients_form_only_on_custom`, `spell_ingredients_variant_with_ingredient`, `spell_ingredients_name_not_blank` and `spell_ingredients_form_not_blank`; the composite foreign key `spell_ingredients_variant_fk`; the foreign keys the migrations created (`spell_ingredients_spell_id_spells_id_fk`, `spell_ingredients_ingredient_id_ingredients_id_fk`, and the `created_by`, `updated_by` and `deleted_by` `_users_id_fk` ones); and the `set_updated_at` trigger (added in `0016`). The table keeps `auditColumns`, so it stays soft-deleted. **The view is created after the `ADD COLUMN`s, or names its columns:** `0067` created its `planets` view with `SELECT *` before its `ADD COLUMN`s, which was harmless there because the new columns went on other tables (`ingredients`, `ingredient_variants`, `reference_links`), not on the renamed one. Here the renamed table itself gains `position` and `body`, so a `SELECT *` view made before the adds would lack them. The lesson of `0068_celestial-bodies-refill.sql` is separate: the deploy still running writes the old columns only, so the new ones need a refill before the contract. This migration says in its header whether a refill is needed for rows an old deploy writes through the view (the old deploy writes `layer_order` and not `position`, so a row written that way needs `position` filled from it). The view is listed in `tests/db/schema-drift.test.ts`'s `PENDING_DROPS` as kind `view`, and the old column `layer_order` and `spells.instructions` as kind `column`; M13.9 empties them. `position integer` is added and backfilled from `layer_order` in the same migration, because `layer_order` is `NOT NULL` and `position` replaces it; `position` stays nullable, because the deploy still running writes only `layer_order` and a `NOT NULL` `position` would refuse its inserts, and has its own live unique index on `(spell_id, position)`; `NOT NULL` arrives in M13.9. The code writes both columns until M13.9 drops the old one, per the column-rename rule in `db/expand-contract.md` and `.claude/rules/database.md`, which lists RENAME as destructive DDL. `body text` is added, nullable and non-blank: the instruction. The exactly-one CHECK `spell_ingredients_ingredient_or_name` is replaced by two, `num_nonnulls(ingredient_id, name) <= 1` and `num_nonnulls(ingredient_id, name, body) >= 1`: at most one identity, never an empty step. A new CHECK keeps `quantity`, `unit` and `note` null unless the step carries `ingredient_id` or `name`. `spells.note text` is added and backfilled from `instructions`, the single free-text note on a spell; the code writes both until M13.9. Everything else stays: the variant unique index, the custom-name unique index, the variant composite foreign key, the form and variant CHECKs, the `updated_at` trigger. The `.ack.md` sidecar (MB.48) follows `0067`'s format: the `Destructive DDL acknowledged:` line, then the findings table naming each RENAME and the DROP CONSTRAINT.

The schema file becomes `src/modules/grimoire/schema/spell-steps.ts`, exporting `spellSteps`. In the repository, the layer writers `spellLayerWrites` (`lockLayersOfVariants`, `moveLayers`) in `src/db/repository/spells.ts` and `SpellLayerRow` in `src/db/repository/types.ts` are renamed to say steps. `findManyOfSpellIngredientsIncludingSoftDeleted` is **not** renamed: it reads the categories and folk names of the ingredients used in readable spells, not step rows. `findManyInSpell` keeps its shape, and `existsIn` (in `src/db/repository/select.ts`) is unchanged. Seed types in `src/db/seed/types.ts` (`SeedLayer` becomes `SeedStep`, with `body`) and the demo scenario in `src/db/seed/demo.ts` change, the demo gaining an instruction step or two between its ingredient steps. The test support (`tests/support/db/table-metadata.ts`, `insert-spell.ts`, `tests/support/fixtures/spell.ts`, `fixtures/types.ts`) and every test naming the old table, column, index or CHECK are updated: `tests/modules/grimoire/schema/spell-ingredients-schema.test.ts`, `spells-schema.test.ts`, `tests/db/partial-unique-indexes.test.ts`, `schema-drift.test.ts`, `repository/spells.test.ts`, `repository/finders.test.ts`, `spell-visibility.test.ts`, `workspace-isolation.test.ts`, `tests/modules/grimoire/schema/types.ts`, `tests/db/seed/demo.test.ts`, `tests/db/migrations/0072-fluid-ounces.test.ts` (it runs an `ALTER TABLE` by the old name; both files were deleted later, by M14.27), and the three ingredient-service tests that select from the table: `tests/modules/ingredients/services/convert-compendium-to-local.test.ts`, `compendium-entries.test.ts` and `workspace-ingredients.test.ts`. `tests/db/migrations/0063-variant-children.test.ts` runs 0063's SQL against the live schema and breaks on the rename: it is retired, as MB.226 retired the earlier shipped-migration tests.

Carries `claude-docs/design-decisions/m13.1-spell-steps.md`: why one table, why the rename now (nothing above the schema is built), and the two-step column renames (`.claude/rules/database.md`). **M13.2 — Step units must convert to the jar's** · 1.5h

_Story 77:_ As a workspace member, I want a step's unit to be one the jar can be measured against, so that making the spell can take it out of stock.

A new rule in the spell service's save path, the `createSpell` and `updateSpell` that M10.10 builds, and not in the Zod schema, which cannot see stock. The schema itself lives in `src/modules/grimoire/validation/`, which MB.8 creates and this task extends. This is wholly M13.2's story 77 (step units convert). A step linking a variant the coven holds a stock row for must carry a unit that `unitConvert` (M9.5) accepts into that row's unit: the same dimension. `unitConvert` (`src/modules/ingredients/units/convert.ts`) refuses every `count` conversion, including count to count, so a step in `count` is decided by equality instead: it saves when the jar's unit is also `count`, and deduction (M13.5) subtracts it without calling `unitConvert`. Anything else is refused as a `ValidationError` whose issue path is the array `['steps', i, 'unit']` (see `ValidationError` in `src/lib/errors.ts`; `src/graphql/errors.ts` maps it to `fieldErrors`), not the string `steps.0.unit`, which MB.43's `fieldErrors` shows inline in the builder. A custom step, and a step whose variant has no stock row, are unchecked. A stock row whose unit changes after the spell was saved does not invalidate the spell: that drift is reported as a warning on the working (M13.5), which saves anyway and deducts nothing for that step. Plan: [`design-decisions/m13.1-plan.md`](../design-decisions/m13.1-plan.md), "Comparable units at save time".

_Acceptance criteria:_

- A weight step against a volume jar, and a `pinch` step against a `piece` jar, are refused at the step's path and never written
- A `tsp` step against a `ml` jar saves; a `count` step against a `count` jar saves by equality and deducts without `unitConvert`
- A step whose variant has no stock row saves with any unit
- A stock row whose unit changes after the save does not invalidate the spell; the working's warning reports it (asserted in M13.5)
- The authorization precondition is proved: the check runs under the caller's proof against that coven's stock only
- Docs corrected: the spell service's rules in `claude-docs/`, story 77's line in `DESIGN.md` §10 and its row in `tests/support/story-sections.ts` (section `'Coven - Spells - Ingredients'`). Story 77's browser flow stays `test.fixme` here, because the builder does not exist yet; M10.15, which adds the quantity and unit fields, unskips it; M13.4 owns the rest of the §10 list and the story counts

**M13.11 — Delete a spell** · 2h

A new hook, `useLeaveGuard(dirty, ask)`, in `src/lib/navigation/leave-guard.tsx`:

- While `dirty` is true it adds a `beforeunload` listener (the browser event that fires when a tab is about to close or reload). The listener calls `event.preventDefault()` and sets `returnValue`; the browser shows its own wording, because custom text is ignored (MDN). The listener is removed the moment `dirty` is false, since a page that always listens can lose the browser's back-forward cache.
- It takes an optional `onHide` callback, called when the tab becomes hidden (`visibilitychange` to `hidden`). That is the one moment that is reliable on phones, where `beforeunload` often never fires. M13.16's autosave uses it to save at once.
- It registers with a new `LeaveGuardContext` slot that `NavigationProvider` (`src/lib/navigation/provider.tsx`) owns. `navigate()` is "the one way the site navigates": `PendingLink` and every programmatic navigation go through it. Before it starts, it asks the registered guard. Clean: it goes. Dirty: it calls `ask(proceed)`, holding the navigation the way `useDiscardGuard` holds a close, until the person chooses Discard or Keep Editing.

`useDiscardGuard` calls `useLeaveGuard(dirty, request)` inside itself, so the seven forms that already call it (IngredientForm, GroupedValueForm, GroupForm, StockDialog, CupboardEntryForm, InviteDialog, AdminInvitations' invite form) gain tab-close protection in one change, and draw the same `DiscardQuestion`. A form inside a modal does not hold in-app navigation: the page behind is inert, and the only navigations from a modal are the form's own, after a save or after Discard Changes. A page form holds both. `CreateWorkspaceForm`, a page form with no guard today, adopts `useDiscardGuard`.

**M13.16 — Autosave Module** · 4h

_Story 81:_ As a coven member, I want nothing I type into a spell to be lost, so that I can build it over several sittings and devices.

Mechanism task of the autosave plan (2026-10-25; [`design-decisions/m13.14-plan.md`](../design-decisions/m13.14-plan.md)). It follows M13.15 (the `revision` column) and M13.14 (the leave guard's `onHide`), and precedes M10.10 so the mutations are written with `expectedRevision` from the start. It has no consumer yet: mechanism first, the builder adopts it in M13.17. Nothing in it names a spell, so ingredient drafts can adopt it later without restructuring.

**`useAutosave`** (`src/lib/autosave/use-autosave.ts`) takes `value` (the form's current values), `dirty`, `enabled` (false until the adapter has a target), `save(value, { revision, force })` returning `{ revision, savedAt, id }`, `delay` (default 3 s after the last change, as GitLab Pajamas does), `maxWait` (default 30 s during continuous typing, as Confluence saves drafts) and an optional `mirror` key. It returns `status` (`idle | pending | saving | saved | failed | conflict`), `savedAt`, `error`, `conflict`, `flush()`, `retry()` and `resolveConflict('reload' | 'keep-mine')`.

- At most one save is in flight; a change during a save queues exactly one follow-up.
- A failed save retries after 2 s, then 5 s, then 15 s, then stops at `failed` with a manual Retry. The form keeps its state, and the mirror keeps the copy.
- A `StaleWriteError` from the adapter sets `conflict`; autosave pauses until it is resolved. `keep-mine` sends again with `force: true` (the adapter then passes the server's current revision); `reload` lets the caller reset the form from the server and clears dirtiness.
- It flushes on `visibilitychange` to hidden (through `useLeaveGuard`'s `onHide`), on `blur` of the form root, and on an explicit `flush()` (Mark Complete and the Save button use it).
- The hook stores the last returned `revision` and passes it on the next save.
- Polling is not here, and nowhere else: M13.19, which would have added the app's one poll, was retired 2026-10-28.

**Mirror** (`src/lib/autosave/mirror.ts`): a localStorage copy under `autosave:<entity>:<id|new>:<userId>`, value `{ value, at }`, written on every change and cleared only after the server confirms (Gerrit's bug was clearing early). Entries older than a day are ignored. Every access is in `try/catch`, and absent storage means no mirror. `readMirror(key)` serves recovery: when `mirror.at` is later than the server's `updatedAt`, the consumer shows the recovery banner (M13.17).

**`SaveStatus`** (`src/components/SaveStatus/`): inline beside the form's primary action, never a toast. An `<output role="status">` rendered empty first, then "Saving…", then "Saved 2:02 pm" (or "Draft saved 2:02 pm" while the status is draft), then "Couldn't save." with a Retry (`role="alert"`, stays until a save succeeds), then a `Notice` of kind `caution`, "This spell was changed elsewhere.", with Reload Latest and Keep My Version. The live region announces the first save after a burst only, not every save; the visible text always updates. It reuses `Spinner`, `Notice` and `LastEdit`'s time formatting, and has a Storybook story per state.

**Server side:** `updateRevisioned(tx, table, where, expectedRevision, set)` in `src/db/repository/write.ts` runs `UPDATE … WHERE … AND revision = $expected RETURNING revision`; zero rows with the row present throws `StaleWrite { currentRevision }`, and `expectedRevision: null` writes unconditionally (the `force` path). A GraphQL mutation input gains `expectedRevision: Int`, its payload returns `revision: Int!`, and `StaleWrite` maps to the error code `STALE_WRITE` with `extensions.currentRevision` (`src/graphql/errors.ts`). `readGraphqlFailure` in `src/lib/graphql-client.ts` surfaces it as `StaleWriteError`. The convention is written into `.claude/rules/graphql.md` and `.claude/rules/database.md`.

**Amended 2026-10-27 by M13.16:** the write is `write.updateRevisioned(membership, table, id, expectedRevision, values)`, a by-id writer under the `Membership` proof like `updateByIdInWorkspace`, not `updateRevisioned(tx, table, where, …)` as written above; a row the proof cannot reach answers `[]`, never `StaleWrite`. The client's wrapper `send()` throws `StaleWriteError`, a `GraphQLClientError` subclass, and `readGraphqlFailure` is unchanged. `save` also receives and returns the row's `id`, so a new row's second save updates it. The hook calls `useLeaveGuard` itself ([`components/autosave.md`](../components/autosave.md)).

What this task does not build: no history (no `record_revisions`, snapshots, timeline or restore) and no spell adapter; a past-state read, `restore` and pinning an ingredient revision from a step are v2's. It does not use `useDebouncedValue` (300 ms, type-ahead only), which has no maximum wait and no flush.

_Acceptance criteria:_

- Fake-timer unit tests for `useAutosave`: saves 3 s after the last change; saves within 30 s during continuous change; one save in flight with exactly one queued follow-up; retries at 2 s, 5 s and 15 s then `failed`; pauses on conflict; `keep-mine` sends `force`; flushes on hidden and blur
- The mirror is written on change, survives a failed save, and is cleared only after the server confirms; with storage throwing, the hook still works

**M13.5 — Working service: record, complete and deduct, update, delete** · 4.5h

_Stories 76 and 78:_ As a workspace member, I want to record a working, and complete it so that the stock it used is taken out of the coven's jars, so that the grimoire tracks what was made and the stock stays true. A permission is a per-role statement, never a rank, so the service asks for `working: ['create']` and does not compare roles. The input shapes (`recordWorking`'s and `updateWorking`'s date, note, participants and visibility) are validated by a Zod schema in `src/modules/grimoire/validation/` (the directory MB.8 creates), which M13.6's `WorkingInput` mirrors.

A spell that has been reopened to a draft takes no new working: the service refuses it with an explaining error, not a bare `Forbidden`. Existing workings keep their records and their deductions when a spell is reopened (the UI side is M10.20), and they come back into play when the spell is complete again.
- `completeWorking`: in one `withAudit`, a pure function `planDeductions` decides what is taken, and the service applies it. `planDeductions`, in `src/modules/grimoire/`, takes the working's live steps and the coven's stock rows and returns, for each step, an amount to take in the jar's unit, a shortfall, or a refusal reason. It is the one function that computes both this completion and M13.7's preview, and a test proves the two agree for the same inputs. For each live step with a linked ingredient it finds the coven's stock row for the step's variant and converts the step's quantity into the row's unit with `unitConvert` (M9.5), except for a count unit, which deducts when the step's unit and the row's unit are the same unit and is a refusal otherwise: `unitConvert` refuses every count conversion, so a count is compared by equality of unit and never passed to it. An instruction-only step (no ingredient) deducts nothing and is not a warning, asserted.
- The decrement is a new repository-level writer in `src/db/repository/` that takes the caller's write handle and is called inside the working's `withAudit`, subtracts the amount from the stock row, floors it at zero, and returns what was actually taken so the shortfall can be recorded. It is the only decrement path: `updateStock` in `src/modules/ingredients/services/stock.ts` opens its own `withAudit` and takes absolute values, so it cannot join the working's transaction, and a read-modify-write through it would also race. A deduction row is written with the amount taken and the shortfall. A step that is custom, unstocked, has no quantity, or whose conversion is refused (drift since the spell was saved) writes no deduction and comes back as a warning naming the step and the reason. Returns the working and a per-step report.
- `updateWorking`: date, note and participants; visibility widens only, under the one-way rule M10.6 sets on `setSpellVisibility` and its explaining error, applied to the working's own column. Under `working: ['update']`.
- `deleteWorking`: a soft delete by its recorder, under `working: ['delete']`; stock is untouched.
- `deleteSpell`, which M13.11 builds, is extended here to soft-delete the spell's workings in the same `withAudit`, since the table exists from M13.4. Participant and deduction rows have no `deleted_at` (M13.4): they stay as written and are reached only through their working, so a soft-deleted working hides them.
- Finders in `findManyInSpell`'s shape, ANDing the working's own visibility: a `private` working reaches `created_by = membership.userId` or a participant row with that user id. A count finder over a batch of spell ids counts the visible complete workings. A working keeps its own visibility when its spell widens: widening the spell does not widen its existing workings.
