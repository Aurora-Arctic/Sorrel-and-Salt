### Spell steps

**M13.1 — Spell steps: the recipe is one ordered list of steps** · 4h

_Story 80:_ As a workspace member, I want a spell's steps recorded in one order, each an instruction, an ingredient, or both, so that the ritual is kept beside what goes in the jar.

Table task, the first of the spell steps and workings plan (2026-10-16, the owner's call; the plan is copied to [`design-decisions/m13.1-plan.md`](../design-decisions/m13.1-plan.md) in this task's PR). A spell's recipe becomes one ordered list of steps, where a step is an instruction, an ingredient, or both. The step is a row in the existing ordered table, not a second table beside it, by MB.40's own argument that one ordered list cannot span two tables ([`design-decisions/mb.40-custom-spell-ingredients.md`](../design-decisions/mb.40-custom-spell-ingredients.md), "Why not the alternatives"). "Layer" survives only as the word for a step that lays an ingredient.

The migration is `0081` (the latest is `0080_astrology-position-expand.sql`): one expand migration, written with `drizzle-kit generate --custom` and a hand-edited snapshot as `0067_celestial-bodies-expand.sql` was ([`db/expand-contract.md`](../db/expand-contract.md)): `spell_ingredients` is renamed `spell_steps`, its indexes, CHECKs and foreign keys renamed with it, and a `spell_ingredients` view left under the old name for the deploy still running (MB.252). Renaming a table renames none of its constraints or indexes, so the migration renames each: the unique indexes `spell_ingredients_spell_id_layer_order_unique`, `spell_ingredients_spell_id_variant_id_unique` and `spell_ingredients_spell_id_custom_name_unique`; the CHECKs `spell_ingredients_ingredient_or_name`, `spell_ingredients_form_only_on_custom`, `spell_ingredients_variant_with_ingredient`, `spell_ingredients_name_not_blank` and `spell_ingredients_form_not_blank`; the composite foreign key `spell_ingredients_variant_fk`; the foreign keys the migrations created (`spell_ingredients_spell_id_spells_id_fk`, `spell_ingredients_ingredient_id_ingredients_id_fk`, and the `created_by`, `updated_by` and `deleted_by` `_users_id_fk` ones); and the `set_updated_at` trigger (added in `0016`). The table keeps `auditColumns`, so it stays soft-deleted. **The view is created after the `ADD COLUMN`s, or names its columns:** `0067` made its view with `SELECT *` before its adds, so the view lacked the new columns and `0068_celestial-bodies-refill.sql` had to refill rows. This migration must not repeat that, and says in its header whether a refill is needed for rows an old deploy writes through the view (the old deploy writes `layer_order` and not `position`, so a row written that way needs `position` filled from it). The view is listed in `tests/db/schema-drift.test.ts`'s `PENDING_DROPS` as kind `view`, and the old column `layer_order` and `spells.instructions` as kind `column`; M13.9 empties them. `position integer` is added and backfilled from `layer_order` in the same migration, because `layer_order` is `NOT NULL` and `position` replaces it; `position` stays nullable, because the deploy still running writes only `layer_order` and a `NOT NULL` `position` would refuse its inserts, and has its own live unique index on `(spell_id, position)`; `NOT NULL` arrives in M13.9. The code writes both columns until M13.9 drops the old one, per the column-rename rule in `db/expand-contract.md` and `.claude/rules/database.md`, which lists RENAME as destructive DDL. `body text` is added, nullable and non-blank: the instruction. The exactly-one CHECK `spell_ingredients_ingredient_or_name` is replaced by two, `num_nonnulls(ingredient_id, name) <= 1` and `num_nonnulls(ingredient_id, name, body) >= 1`: at most one identity, never an empty step. A new CHECK keeps `quantity`, `unit` and `note` null unless the step carries `ingredient_id` or `name`. `spells.note text` is added and backfilled from `instructions`, the single free-text note on a spell; the code writes both until M13.9. Everything else stays: the variant unique index, the custom-name unique index, the variant composite foreign key, the form and variant CHECKs, the `updated_at` trigger. The `.ack.md` sidecar (MB.48) follows `0067`'s format: the `Destructive DDL acknowledged:` line, then the findings table naming each RENAME and the DROP CONSTRAINT.

The schema file becomes `src/modules/grimoire/schema/spell-steps.ts`, exporting `spellSteps`. In the repository, the layer writers `spellLayerWrites` (`lockLayersOfVariants`, `moveLayers`) in `src/db/repository/spells.ts` and `SpellLayerRow` in `src/db/repository/types.ts` are renamed to say steps. `findManyOfSpellIngredientsIncludingSoftDeleted` is **not** renamed: it reads the categories and folk names of the ingredients used in readable spells, not step rows. `findManyInSpell` keeps its shape, and `existsIn` (in `src/db/repository/select.ts`) is unchanged. The test support (`tests/support/db/table-metadata.ts`, `insert-spell.ts`, `tests/support/fixtures/spell.ts`, `fixtures/types.ts`) and every test naming the old table, column, index or CHECK are updated: `tests/modules/grimoire/schema/spell-ingredients-schema.test.ts`, `spells-schema.test.ts`, `tests/db/partial-unique-indexes.test.ts`, `schema-drift.test.ts`, `repository/spells.test.ts`, `repository/finders.test.ts`, `spell-visibility.test.ts`, `workspace-isolation.test.ts`, `tests/modules/grimoire/schema/types.ts`, `tests/db/seed/demo.test.ts`, `tests/db/migrations/0072-fluid-ounces.test.ts` (it runs an `ALTER TABLE` by the old name), and the three ingredient-service tests that select from the table: `tests/modules/ingredients/services/convert-compendium-to-local.test.ts`, `compendium-entries.test.ts` and `workspace-ingredients.test.ts`. `tests/db/migrations/0063-variant-children.test.ts` runs 0063's SQL against the live schema and breaks on the rename: it is retired, as MB.226 retired the earlier shipped-migration tests.

**M13.2 — Step units must convert to the jar's** · 1.5h

_Story 77:_ As a workspace member, I want a step's unit to be one the jar can be measured against, so that making the spell can take it out of stock.

A new rule in the spell service's save path, the `createSpell` and `updateSpell` that M10.10 builds, and not in the Zod schema, which cannot see stock. The schema itself lives in `src/modules/grimoire/validation/`, which MB.8 creates and this task extends. This is wholly M13.2's story 77 (step units convert). A step linking a variant the coven holds a stock row for must carry a unit that `unitConvert` (M9.5) accepts into that row's unit: the same dimension. `unitConvert` (`src/modules/ingredients/units/convert.ts`) refuses every `count` conversion, including count to count, so a step in `count` is decided by equality instead: it saves when the jar's unit is also `count`, and deduction (M13.5) subtracts it without calling `unitConvert`. Anything else is refused as a `ValidationError` whose issue path is the array `['steps', i, 'unit']` (see `ValidationError` in `src/lib/errors.ts`; `src/graphql/errors.ts` maps it to `fieldErrors`), not the string `steps.0.unit`, which MB.43's `fieldErrors` shows inline in the builder. A custom step, and a step whose variant has no stock row, are unchecked. A stock row whose unit changes after the spell was saved does not invalidate the spell: that drift is reported as a warning on the working (M13.5), which saves anyway and deducts nothing for that step. Plan: [`design-decisions/m13.1-plan.md`](../design-decisions/m13.1-plan.md), "Comparable units at save time".

_Acceptance criteria:_

- A weight step against a volume jar, and a `pinch` step against a `piece` jar, are refused at the step's path and never written
- A `tsp` step against a `ml` jar saves; a `count` step against a `count` jar saves by equality and deducts without `unitConvert`
- A step whose variant has no stock row saves with any unit
- A stock row whose unit changes after the save does not invalidate the spell; the working's warning reports it (asserted in M13.5)
- The authorization precondition is proved: the check runs under the caller's proof against that coven's stock only
- Docs corrected: the spell service's rules in `claude-docs/`, story 77's line in `DESIGN.md` §10 and its row in `tests/support/story-sections.ts` (section `'Coven - Spells - Ingredients'`), so the story-sections guard passes on the day this lands; M13.4 owns the rest of the §10 list and the story counts

### Workings

**M13.4 — `spell_workings`, participants and deductions tables** · 3h

_Story 76:_ As a workspace member, I want to record that we made a spell, when and with whom, so that the grimoire shows how many times it has been worked.

**M13.5 — Working service: record, complete and deduct, update, delete** · 4.5h

_Stories 76 and 78:_ As a workspace member, I want to record a working, and complete it so that the stock it used is taken out of the coven's jars, so that the grimoire tracks what was made and the stock stays true. (Story 78: As a workspace member, I want completing a working to deduct what it used from the coven's stock, so that the jars stay true.)

A new `working` permission statement is added to `src/modules/coven/services/access-control.ts` with its tests: `['read', 'create', 'update', 'delete']` for member and owner, and `['read']` for viewer. A permission is a per-role statement, never a rank, so the service asks for `working: ['create']` and does not compare roles.

- `recordWorking(session, workspaceId, spellId, input)`: `assertMembership(session, workspaceId, { working: ['create'] })`, so owners and members record and viewers are refused; the spell must be visible to the caller and `complete`; the working's visibility is capped at the spell's, enforced here because a CHECK cannot read the parent row; participants are written in order, the caller first by default; the drift warnings are computed and returned. A spell that has been reopened to a draft takes no new working: the service refuses it with an explaining error, not a bare `Forbidden`. Existing workings keep their records and their deductions when a spell is reopened (the UI side is M10.20), and they come back into play when the spell is complete again.
- `completeWorking`: in one `withAudit`, a pure function `planDeductions` decides what is taken, and the service applies it. `planDeductions`, in `src/modules/grimoire/`, takes the working's live steps and the coven's stock rows and returns, for each step, an amount to take in the jar's unit, a shortfall, or a refusal reason. It is the one function that computes both this completion and M13.7's preview, and a test proves the two agree for the same inputs. For each live step with a linked ingredient it finds the coven's stock row for the step's variant and converts the step's quantity into the row's unit with `unitConvert` (M9.5), except for a count unit, which deducts when the step's unit and the row's unit are the same unit and is a refusal otherwise: `unitConvert` refuses every count conversion, so a count is compared by equality of unit and never passed to it. An instruction-only step (no ingredient) deducts nothing and is not a warning, asserted.
- The decrement is a new repository-level writer in `src/db/repository/` that takes the caller's write handle and is called inside the working's `withAudit`, subtracts the amount from the stock row, floors it at zero, and returns what was actually taken so the shortfall can be recorded. It is the only decrement path: `updateStock` in `src/modules/ingredients/services/stock.ts` opens its own `withAudit` and takes absolute values, so it cannot join the working's transaction, and a read-modify-write through it would also race. A deduction row is written with the amount taken and the shortfall. A step that is custom, unstocked, has no quantity, or whose conversion is refused (drift since the spell was saved) writes no deduction and comes back as a warning naming the step and the reason. Returns the working and a per-step report.
- `updateWorking`: date, note and participants; visibility widens only, under `resolveSpellVisibility`'s rule and its explaining error. Under `working: ['update']`.
- `deleteWorking`: a soft delete by its recorder, under `working: ['delete']`; stock is untouched.
- `deleteSpell`, which M13.11 builds, is extended here to soft-delete the spell's workings and their participants in the same `withAudit`, since the tables exist from M13.4.
- Finders in `findManyInSpell`'s shape, ANDing the working's own visibility: a `private` working reaches `created_by = membership.userId` or a live participant row with that user id. A count finder over a batch of spell ids counts the visible complete workings. A working keeps its own visibility when its spell widens: widening the spell does not widen its existing workings.
