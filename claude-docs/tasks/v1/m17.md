**M17.14 — Help Article Services and GraphQL** · 8h

_Story:_ As a site keeper, I want to write and edit help articles through the API, and as any visitor I want to read them without an account, so that the pages built on top have one place to ask.

_Acceptance criteria:_

- Create, update and delete run under `assertSiteAdmin` alone, through `withAudit`; a curator, a practitioner and a signed-out caller are each refused, asserted by direct id as well as by list, with the keeper accepted as the precondition
- The slug is always `slugify(title)` (`src/lib/slugify.ts`), derived on create and on every title change; the input and the patch hold no slug. A title that makes no address, one of the reserved addresses `glossary`, `staff` and `search`, or an address a live row of the same kind holds is refused on `title` with an explaining error naming the title, for every kind, on create and on rename; the same address on a row of another kind is accepted
- `position` is a whole number, 0 or more; anything else is refused on `position`, in the input's validation and so in the service
- A parent must be a live row of kind `article`, nesting is one level deep, and a `term` takes neither a parent nor a position; each is refused with an explaining error
- A child's `audience` is equal to its parent's or narrower (public, then staff, then keeper); a child set wider than its parent is refused, and so is making a parent narrower than any of its live children, each with an explaining error; changing a parent's audience moves no child
- A parent with children cannot be deleted until its children are moved or deleted, with an explaining error
- An article's input and patch take an optional `childIds`, applied in the same `withAudit` transaction as the parent's own fields: each listed article becomes a child, positioned 1, 2, 3… in list order and moved from any other parent, and each live child left out goes to the top level, positioned after the last top-level article. A non-article, a missing or deleted row, the article itself, an id listed twice, an article with live children of its own, an article wider than the parent, and `childIds` on a row that is not a top-level article are each refused on `childIds`, and a refused save writes nothing. A `childIds` save is checked on the children it names, so it may narrow the parent in the save that releases a wider child
- `shown` hides a row from every reader, the keeper included: every reader finder (the FAQ, the index, the glossary, one article by slug, children, the staff list, the sitemap paths and both arms of the search) filters `shown` in SQL, and a child whose live parent is hidden is hidden with it, its own flag kept. A hidden row asked for by its slug answers not found, publicly and on the staff routes alike. `setHelpArticleShown(id, shown)` runs under `assertSiteAdmin` through `withAudit` and revalidates the tag; a body's `[[Term]]` mark is still checked against hidden terms, so hiding a term never makes a body unsaveable
- `keeperHelpArticles` lists every live row of every kind and audience, shown and hidden, A to Z, through the M3.6 cursor helper, narrowed by a listing (`shown`, `hidden` or `all`, the default), words in the title, a kind and an audience; it runs under `assertSiteAdmin`. `readKeeperHelpArticle(id)` answers one live row, shown or hidden, with every live child in position order, for the editor
- A public finder takes no session and reads the FAQ, the article index, one article by slug (a lookup by slug reads kind `article` only, with its children) and the glossary terms in A-to-Z order; it filters `audience = 'public'` in SQL, children included, and is cached under its own tag, and every write revalidates that tag

A curator asking by direct slug for a `keeper` row, and a practitioner, an observer and a signed-out caller asking by direct slug for a `staff` row, are each refused, with a keeper and a curator accepted as the preconditions
- `searchHelp(session | null, query)` matches through `websearch_to_tsquery('english', q)` ranked by `ts_rank`, falls back to a trigram match on the title (the compendium's `word_similarity` mechanism) when the full-text search finds nothing, searches all three kinds, and applies the audience scope in SQL; a staff row's words never surface for a signed-out caller or a practitioner and do for a curator, and a keeper row's words surface for a keeper only

- Search results page by score through the M3.6 cursor helper, following `findPageInTiers` in `src/db/repository/ingredients.ts`
- Every list is paginated through the M3.6 cursor helper; the glossary read is paginated too, and `tests/guards/pagination.test.ts` stays green

**M17.19 — Keep Only the Latest Drizzle Snapshot** · 2h

_Story:_ As a developer, I want the migration folder to hold only the files a migration needs, so that `src/` is not 80% generated schema snapshots that nothing reads.

`src/db/migrations/meta/` holds one Drizzle snapshot per migration, 137 files and about 740,000 lines — 80% of every line under `src/`. `drizzle-kit generate` reads the folder, checks each file's format and that no two share a parent, then diffs the schema against the newest one only; `drizzle-kit migrate` reads `_journal.json` and the `.sql` files and never opens a snapshot. Nothing else in the repo reads them: `scripts/check-migration-order.ts` and the PR gate read `_journal.json`. The only thing the old snapshots give is a historical diff, which git history gives anyway.

Two parts, in one PR: the one-off drop, and the mechanism that keeps the folder at one snapshot from then on. `npm run db:generate` becomes a wrapper (`scripts/db-generate.ts`) that runs `drizzle-kit generate` and then deletes every `meta/*_snapshot.json` except the one the newest `_journal.json` entry names. A guard asserts the invariant so a bare `drizzle-kit generate` cannot reintroduce old snapshots unnoticed.

_Acceptance criteria:_

- `src/db/migrations/meta/` holds `_journal.json` and exactly one `*_snapshot.json`, the one for the newest journal entry
- `npm run db:generate` runs `drizzle-kit generate` and then prunes every snapshot but the newest; run on an unchanged schema it produces no migration and leaves one snapshot
- `npm run db:generate` on a changed schema produces the migration, its snapshot and its journal entry, and the previous snapshot is gone after the run
- `npm run db:migrate` on a fresh database applies every migration, proving the drop broke nothing
- `tests/guards/migration-order-check.test.ts` (or a sibling guard) fails when `meta/` holds more than one snapshot, or when the one snapshot is not the newest journal entry's
- `.claude/rules/database.md` and `claude-docs/db/` state the one-snapshot invariant and that the wrapper, not bare `drizzle-kit generate`, is the command
