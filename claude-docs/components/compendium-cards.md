# CompendiumCards

`src/components/CompendiumCards/` is the public compendium's list (M8.18; MB.80): the search and its filters, one `IngredientCard` per entry in an `IngredientCardList`, and the pager beneath. A page holds `CARD_PAGE_SIZE` (24) entries, which the page asks its read for, so the grid ends on a full row at one to four columns. It is the card-shaped sibling of the admin's `CompendiumList` table. Both are render-only: the page reads one page of entries under the address's filter and hands it over.

## Props

| Prop                                                    | What it does                                                                                   |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `entries`                                               | One `CompendiumCardEntry` per card: name, slug, formal name, categories, forms, safety notes   |
| `filter`, `facets`, `categories`, `vocabulary`, `total` | The same filter state the admin list takes; see [`compendium-list.md`](compendium-list.md)     |
| `previousHref`, `nextHref`, `position`                  | The pager's links and "Page X of Y"                                                            |
| `action`                                                | The foot of each card: `add` or `none`                                                         |
| `workspaceId`                                           | The default coven, which the plus adds to; `add` with none draws no plus and no check          |
| `covens`                                                | The covens the viewer may write in, as `{ id, name }`, for the menu when there are two or more |
| `entries[].held`                                        | Every writable coven holds the entry, and the check shows (M9.12)                              |
| `entries[].heldIn`                                      | The ids of the writable covens that hold the entry, which the menu shows disabled              |
| `entries[].editHref`, `entries[].editHeading`           | A curator's Edit on the card, and the head of the dialog it opens (M8.17)                      |

## Contracts

- Each card is a plain link to `/compendium/ingredients/<slug>`. The Quick Look eye at its bottom left, when the entry carries `details`, opens the entry's details modal over the results instead (M12.5). Two entries sharing a label are told apart by the formal-name line the card draws.
- The list is regular density, never compact, and sits in `ListFrame` through `IngredientSearch shape="cards"`, so a page on its way draws `ListBody shape="cards"`.
- The filter is `CompendiumListFilter audience="public"`: no Classification facet and no No Refs or No Form control. Those are the curators' to-do lists ([`compendium-list.md`](compendium-list.md)).
- The foot of a card is one row, chosen by the page from the visitor. The add icon (or the check) and Edit share the card's right end (`actions` on `IngredientCard`), the plus or check first and a curator's pencil after it. The left end (`startActions`) is left to the Quick Look eye (M12.5). Where each sits is layout, so no test asserts it.
  - `add` with a `workspaceId` draws, for an entry not held, a **plus** (`PlusIcon`) button named and tipped Add to My Ingredients (`AddIcon`, `src/components/AddIcon/`, a client component shared with the entry page; the cards stay a server component). With one writable coven at all (`covens` of length one or none) it adds there directly, with no quantity, until M9.12's second PR puts the quantity dialog behind it: it sends `addCupboardEntry(workspaceId, ingredientId)` through `/api/graphql`, then reads the page again, which draws the check in its place. It is busy (the shared spinner in the icon's place, `aria-busy`) from the press until the page has been read again, and uses `aria-disabled` rather than `disabled` so the focus stays; a refusal is said in a callout under it ([`click-feedback.md`](click-feedback.md), M12.31). With two or more writable covens it is always a menu instead (below), however many hold the entry: the owner's call of 2026-10-20 that the plus adds at once only where there is one coven, not one coven left. For an entry every writable coven holds (`held`), it draws a **check** (`CheckIcon`, `held-mark.tsx`'s `HeldMark`): a status mark, not a link, the owner’s call of 2026-10-20. It is a `role="img"` named In My Ingredients by its `aria-label`, takes no focus and has no tip, since a tip opens on hover or focus and one on a mark the keyboard cannot reach would show to the pointer alone (WCAG 2.1.1). The details modal’s In Your Covens list carries the links to each coven’s copy.
  - **The menu** (the owner's call, 2026-10-20, over the modal picker it first had): with two or more writable covens, the plus is a standard [`MenuButton`](menu-button.md) with the plus as its `icon`, still named and tipped Add to My Ingredients. Its items are every writable coven, by name; a coven in `heldIn` is shown, not left off, as a disabled item (`aria-disabled`, still reached by the arrow keys, doing nothing when chosen) with the note Already in My Ingredients as its description, the words the Edit menu's Add dialog uses (the owner's call, 2026-10-20). The menu therefore keeps its shape as covens take the entry. Choosing one sends `addCupboardEntry` for that coven at once, with no question after it. The button is busy, its name Adding, from the choice until the page has been read again; a refusal is said in the same callout under the plus, and the focus is handed back to the plus, since the item that had it went with the menu. The public entry page draws the same `AddIcon` just left of its pencil, the same menu, animation and announcement, with no check once every coven holds the entry ([`ingredient-entry.md`](ingredient-entry.md), "On the public page"). Tests: `tests/components/CompendiumCards/add-icon.test.tsx`; e2e: `tests/e2e/compendium-add.spec.ts`.
  - **After an add** (the owner's call, 2026-10-20): when the add succeeds, the spinner in the plus draws into a check, which stays for `ADDED_HOLD_MS` (1s) and then cross-fades back to the plus (`useFade`, [`click-feedback.md`](click-feedback.md)). The check also stays while the page is still being read again. If the add left every writable coven holding the entry, the check stays and does not fade, since the read again draws `HeldMark` in its place. A refusal shows no check. The success is said once through the page's status region, "Added to <coven>.", and the button's name stays Add to My Ingredients throughout. While the check shows, the button is `aria-disabled` and does nothing when pressed. Its `data-state` is `added` while the check holds and `returning` during the fade; the motion is `$arrive-duration` and none under reduced motion, which swaps the glyphs at once. The coven just added to counts as holding the entry, a disabled item in the menu, before the page has been read again.
  - `none`, or `add` with no `workspaceId`, draws neither, for an account that only views and for a visitor with no account, who signs in through the header (the owner's call, 2026-10-19).
  - Edit, an `EditLink` named for the entry's name and formal name, sits at the right when the entry carries an `editHref` and an `editHeading` (M8.17). The page gives them to a curator alone.
- With no entries it draws the filter's empty sentence (`emptyText`) instead of a list.

## The page

`src/app/(public)/compendium/page.tsx` draws it per request over the cached reads in `src/app/compendium-reads.ts`, which the admin page shares. The reads take no session, so every card and link is in the server HTML. The page asks for the viewer to choose `action` and the coven: `add` when any of the viewer's coven memberships `canWrite` (the per-role statement in `viewerFor`, never a comparison of role names), `none` otherwise, with no session included. The coven, passed as `workspaceId`, is the first such membership in the switcher's order: `/compendium` names no coven in its address, so the page takes M8.16's choice for a page without one (`destinationsOf`).

**Held (M9.12).** For every coven the viewer may write in the page also asks which of the page's entries each already holds, through `heldCompendiumEntryIdsIn` (the ingredients module), which runs `heldCompendiumEntryIds` once per coven, one after another: each is one read of `workspace_compendium_entries` for the page's ids, scoped by that coven's membership proof. It gives each entry `held` (every writable coven holds it) and `heldIn`. The read is per viewer and sits beside the cached ones, never inside them (rule 6). A visitor, an account that only views and one in no coven are asked nothing and get neither field. A refusal reads as nothing held, so the plus shows and the add itself says no.

**A curator's Edit (M8.17).** An admin or curator (`canCurate`) gets Edit on each card: the search's own address with `?edit=<slug>`, which opens the admin Compendium's edit dialog (`CompendiumDialog`, given `path="/compendium"`) over the results, headed Edit Compendium Entry. Close or a save comes back to the same search, the query and page kept, inside a `RouteModalProvider` so a press opens the dialog at once. `?edit=` is read only once the viewer is known to curate, through the admin page's own `readEditPlace` and `readCompendiumEntry`: an old slug redirects to the new one, and a slug naming nothing shows `MissingNotice` over the list. For a visitor or any other account there is no Edit, and `?edit=` opens nothing and reads nothing. The list's reads are unchanged, cached and sessionless, keyed by the address alone, whoever asks (rule 6).

**Quick Look (M12.5).** Every card, for anyone, a visitor with no account included, carries `details`: the search's own address with `?entry=<id>`, which opens the entry's details modal over the results ([`ingredient-entry.md`](ingredient-entry.md), "The details modal"), read by `readCompendiumDetails` with no session. An id that names no compendium entry, a coven's own included, opens nothing and says nothing: the page is the page without it, so the address tells nobody a coven's entry exists. A curator's Edit pressed inside the details opens the edit dialog over them.

`?withoutReferences=1` and `?withoutForms=1` are dropped before the address is read, so it lists what the unfiltered page lists. `generateMetadata` marks a filtered view `noindex` with the canonical address `/compendium`; the unfiltered list and its pages stay indexable.

Stories: `Can Add`, `In Several Covens`, `Held`, `Can Add And Edit`, `Curator Can Edit`, `Viewer Only`, `Mid List`, `Empty`. Tests: `tests/components/CompendiumCards/index.test.tsx` and `tests/app/(public)/compendium/page.test.tsx`; the browser flow is `tests/e2e/public-compendium.spec.ts`.
