# SupportSenderRequest

`src/components/SupportSenderRequest/` — the body of the sender's dialog over `/account/support`, opened by `?request=<id>` ([`SupportList`](support-list.md) holds the `RouteModal`, with the eyebrow "Support · " and the kind, the subject as the title and the status badge beneath it; the close control is the dialog's).

It reuses the parts of the staff dialog ([`SupportRequests`](support-requests.md)): `facts.tsx` (Sent, then Page on a row of its own, then Error; the grid's gaps are unchanged), `thread.tsx` and the `support-detail` rules. It differs from the staff dialog in what it leaves out and how it names people:

- **The Error fact shows the status code alone.** The error reference (the crash digest) is staff-only: the sender's reads return none, the GraphQL field is curator-only, and the staff dialog keeps it with its Copy button (2026-10-31, the owner's call).
- **No** issue panel, settings column, time-out panel, assignment or Resolve. There is no From fact: the sender knows who they are.
- **Tags and site name, not people.** The sender's own message is named "You" and tagged "You"; every reply is named for the site (`SITE_NAME`, "Sorrel & Salt") and tagged "Staff", whether a curator or an admin wrote it. A staff member's name is never read for this dialog. Each entry's meta line is who, the tag and when, with the time short (`30 Oct, 2:01 pm`).
- **The thread is the whole conversation.** The sender's first message, then each public reply in order. A sender's follow-up is named and tagged "You", a staff reply is named for the site and tagged "Staff". Internal notes never reach the page: the sender's read (`repliesForRequests`) leaves them out in SQL, and a test reads what the page receives to prove none is there.
- **The reply box** (`reply-box.tsx`, a client component) is present while the request is open, waiting on the sender or resolved. It is a "Your Reply" textarea and a Reply button, sent through `/api/graphql` (`sendSupportMessage`), then the page is read again. A reply to a resolved request opens it again. Typed text asks before it is lost, as the staff reply form does.
- **A time-out shuts it.** While the sender is timed out, the textarea and button are disabled and a notice above them says "You cannot reply until <time>.", the time in the UTC-minute form (`utcMinute`). `sendSenderMessage` refuses the same reply with the same words.
- **A closed request has no box.** It shows "This request is closed." and a link, "Open Your Follow-Up", to the request a later message opened from it (`getMySupportFollowUpId`), or the line "Write a new request from Support to follow it up." where there is none.
- **Status words** come from `senderStatusLabel` (`status.ts`): Received (open, staff not yet written last), Replied (open, staff wrote last), Waiting for You, Resolved, Closed. The list rows and this dialog's heading use it.
- **Spacing.** The thread column keeps the staff dialog's totals: facts to Thread 4, Thread heading to first entry 2, last entry to the reply's hairline 4, and 5 of padding beneath the hairline.
