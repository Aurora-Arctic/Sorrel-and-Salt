# SupportSenderRequest

`src/components/SupportSenderRequest/` — the body of the sender's dialog over `/account/support`, opened by `?request=<id>` ([`SupportList`](support-list.md) holds the `RouteModal`, with the eyebrow "Support · " and the kind, the subject as the title and the status badge beneath it; the close control is the dialog's).

It reuses the parts of the staff dialog ([`SupportRequests`](support-requests.md)): `facts.tsx` (Sent, then Page on a row of its own, then Error; the grid's gaps are unchanged), `thread.tsx` and the `support-detail` rules. It differs from the staff dialog in what it leaves out and how it names people:

- **The Error fact shows the status code alone.** The error reference (the crash digest) is staff-only: the sender's reads return none, the GraphQL field is curator-only, and the staff dialog keeps it with its Copy button.
- **A Resolve button** (`resolve-button.tsx`) shows while the request is open or waiting on the sender. It resolves the sender's own request without a reply (`resolveMySupportRequest`), allowed on an open request too so a sender who has their answer need not wait for staff; the admin side then reads "Resolved by Sender".
- **No** issue panel, settings column, time-out panel or assignment. There is no From fact: the sender knows who they are.
- **Tags and site name, not people.** The sender's own message is named "You" and tagged "You"; every reply is named for the site (`SITE_NAME`, "Sorrel & Salt") and tagged "Staff", whether a curator or a keeper wrote it. A staff member's name is never read for this dialog. Each entry's meta line is who, the tag and when, with the time short (`30 Oct, 2:01 pm`).
- **The thread is the whole conversation.** The sender's first message, then each public reply in order. Internal notes never reach the page: the sender's read (`repliesForRequests`) leaves them out in SQL, and a test reads what the page receives to prove none is there.
- **The reply box** (`reply-box.tsx`, a client component) is present while the request is open, waiting on the sender or resolved. It is a "Your Reply" `PlainTextField` (multiline, soft limit of `MESSAGE_MAX_LENGTH`; Reply is disabled while the text is over it) and a Reply button, sent through `/api/graphql` (`sendSupportMessage`), then the page is read again. A reply to a resolved request opens it again. Typed text asks before it is lost, as the staff reply form does.
- **The mailed-link page** (`/support/request/[token]`) draws this same body for a request opened by its view token, passing its own `reply` form (`SupportViewReplyForm`, a "Your Reply" textarea and a Reply button, which sends `replyToSupportRequestByViewToken`) in place of the reply box and leaving out the Resolve button, which needs a session. It has no page or error code to show, and no follow-up link.
- **The Thread heading’s level** is the `headingLevel` prop (2 or 3, default 3), passed on to the Thread. The dialog keeps the h3 under its title; the mailed-link page passes 2, because its only heading above is the h1. An h2 Thread keeps the h3 size (`support-detail__thread-title`).
- **The mailed-link page waits behind a busy skeleton.** While it reads the request it draws a `page` skeleton (eyebrow head) in a `page-with-nav` wrapper with `aria-busy="true"`, so a scan or a test that waits for no busy element waits for the request.
- **A time-out shuts it.** While the sender is timed out, the textarea and button are disabled and a notice above them says "You cannot reply until <time>.", the time in the site's long form in the viewer's time zone (`LocalTime long`), or "You cannot reply: you are timed out with no end date." `sendSenderMessage` refuses the same reply with the same words, except that its time is in the UTC-minute form (`utcMinute`), since the server does not know the viewer's zone. The page passes `timedOut` (`{ until }`, `until` null for no end date), null when none stands.
- **A closed request has no box.** It shows "This request is closed." and a link, "Open Your Follow-Up", to the request a later message opened from it (`getMySupportFollowUpId`), or the line "Write a new request from Support to follow it up." where there is none.
- **Status words** come from `senderStatusLabel` (`status.ts`): Received (open, staff not yet written last), Replied (open, staff wrote last), Waiting for You, Resolved, Closed. The list rows and this dialog's heading use it.
- **Spacing.** The thread column keeps the staff dialog's totals: facts to Thread 4, Thread heading to first entry 2, last entry to the reply's hairline 4, and 5 of padding beneath the hairline.
