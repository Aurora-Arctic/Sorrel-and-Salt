# FilterForm

`src/components/FilterForm/` is a list's filter form, a toolbar that applies as it changes: the fields the caller supplies, the search box first, and a Clear link at the row's end while the page shows a filter. A select or a switch applies on its change, a type-ahead once a choice settles, and the search from the magnifier or Enter. Each opens the filtered list from its first page as a soft navigation. CompendiumList, GroupedValueList, UserList, PrivilegeLedger, GroupList and AdminInvitations all use it. It renders inside its list's [`ListFrame`](list-frame.md), which runs its navigation.

A list with three filter fields or fewer, its search counted, keeps them inline in this form. A list with more takes the Filters drawer ([`FacetPanel`](facet-panel.md)'s `FacetShell`) with only its search left in the row, because the drawer keeps the row to a search box and one button however many fields the list adds.

## Contracts

- **Props that carry a rule.** `action` is the page itself, the path its list's `href.ts` exports: what the form submits to natively before hydration, and the unfiltered first page Clear opens. `searchHref` builds the address the search's submit opens: the filter shown with the search box's text, trimmed, from the first page, usually through `listHref`. `shown` holds each value of the filter the page shows. `sorrel` (`IngredientSearchForm` turns it on) draws the layer a sticky row fills itself with, so the corner sorrel shows through it ([`ingredient-search.md`](ingredient-search.md), [`backdrop.md`](backdrop.md), "The copy in the search row"). `children` are the fields, a `SearchField` first (or `IngredientSearch`'s box), each with the `name` the page reads.
- **`useApplyFilter()`** returns `apply(href)`: it opens `href` softly through the list's `ListFrame` and marks the row's focus to be given back once the list arrives. A filter's field handlers call it; FilterForm calls it for the search and Clear. It is a hook rather than a context FilterForm provides, since the filter's own handlers render FilterForm and sit above it; `ListFrame`'s context is already above them. Soft on every list, the admin ones too, since every page under `/curator` or `/keepers` runs its own guard.
- **It applies on change.** The caller builds each field's address itself, from the filter shown with the one field changed and the search box's text typed but not yet sent carried along, so a select changed after typing a name applies both. Typing in the search box applies nothing until it is submitted, and typing in a type-ahead nothing until a choice settles (`onSettle`, [`combobox.md`](combobox.md)): a pick, the clear, or leaving the box, applied when the settled choice differs from the one shown. Only the search text is the caller's state; a select, `FilterSelectField`, starts from `defaultValue`, and a switch takes `defaultChecked` ([`field.md`](field.md)), since the new list draws the filter again from what it shows.
- **The search carries its own submit**, `SearchField`'s magnifier ([`field.md`](field.md)); `IngredientSearch`'s box draws the same one. It is the form's one submit button, so Enter in any text box submits natively. It is always offered: the same text again reads the list again, which is harmless, where a submit disabled until something changed read as dead. There is no Filter button.
- **It works before hydration.** The form is `method="get"` to `action`, so a press on the magnifier before the script loads still submits, each field under its own `name`. A field must therefore submit something the page reads as the same filter: a blank `<select>` option as `role=`, a switch (a native checkbox beneath) as `awaiting=` or `withoutReferences=1`. A field that is a script's control (every select once hydrated, the select-only box or the type-ahead) is drawn as a native `<select>` by the server and swapped once hydrated (`FilterSelectField`, `src/lib/hydrated.ts`). A select or a switch changed before hydration applies nothing until the magnifier is pressed.
- **While the new list reads, the row is off and the list is a skeleton.** The frame's body shows the tabs' skeleton in place of the table and the pager, its one status, so a filter has the same loading state as a tab. Meanwhile the form is `aria-busy` and every control in it is `aria-disabled`: Clear by its own prop, the caller's fields by a layout effect that marks them and unmarks them after. It is `aria-disabled` rather than `disabled`, as the tabs use it, so a focus in a field stays where it was rather than falling to the page. The same effect refuses, in the capture phase, every key but Tab, every press, edit, paste and drop, and a submit, Enter included, is refused while a list is on its way, so there is no second request. No control shows a spinner of its own: the skeleton is the loading state, and its status the one a screen reader hears.
- **The focus comes back once the list arrives.** The list keys its filter by the filter shown, so the row that applied is thrown away and a new one drawn. As the old row goes, FilterForm notes the place of the focused control among the row's controls (`-1` for none), and the new row focuses the control at that place; a type-ahead left by Tab hands it to the control Tab reached. It goes by place rather than by id because `useId` numbers a row drawn in the browser afresh, while the controls stand in the same order, Clear, the one that comes and goes, last. A module-level slot holds it, because the filter's handlers sit above the FilterForm a context would come from; one list navigates at a time, so one slot is enough.
- **Clear is drawn only while the page shows a filter**: while any of `shown` is a non-blank string, a non-empty list or `true`, so a blank name, an "All …" choice and a switch that is off count as none. With nothing to clear nothing is drawn, not a disabled placeholder; at the row's end its coming and going moves nothing else. It is a plain link, not a submit: its address is `action`, the page itself with no query, so every filter parameter and the cursor go, and so does a modal's (`?edit=`, `?new`). It works before hydration as an address; a click for a new tab or window is left to the browser.
- **The fields are the caller's.** Their labels, addresses and what each applies stay in the list that knows them.
- **It is one landmark: the `<search>`**, named by `label`, so a screen reader lists it beside the page's other regions. The `<form>` inside is not named, as a named form is a second landmark for the same row. jsdom's role table predates `<search>`, so a component test finds the form through `filterForm(name)` in `tests/support/filter-form.tsx`, and an e2e spec by `getByRole('search', { name })`.

## Styling

The form has no stylesheet of its own: it is `.filter-row` in the primitives ([`styling.md`](../styling.md), "Form fields").

- **The row runs edge to edge with the table beneath it**, so its boxes reach the bands' edges; a label stands a cell inset left of the heading text under it. The row is a size container, so it follows its own width, not the screen's.
- **A choice takes one width.** A plain select's field and every `FilterSelectField` (which puts `filter-row__choice` on its `.field`) stand at `$filter-choice-width`: most names fit, and the longest seeded one, "Anglo-Saxon & Continental Germanic", runs on inside the box while its option in the list is drawn whole. A native select sizes itself by its longest option and a type-ahead by its few letters, so without it two selects would differ and hydration, which swaps the server's select for a Combobox box, would move the row. The field opts in by class since once hydrated it holds no select. A choice marked `fit` is as wide as its longest option instead. A choice keeps its width beside the search, whose grow factor dwarfs its own, but grows to fill a line it wraps onto alone. The clear inside the type-ahead keeps its room while hidden ([`combobox.md`](combobox.md)), so typing does not change the width either.
- **On a phone** two choices do not fit one line, so each takes a line, and the search the first. A switch (`SwitchField`) is a column at desktop width, its track level with the boxes, and a row on a phone, level with the Filters button; with Clear All showing it wraps beneath.
- **The row while a list is on its way** is `.filter-row[aria-busy='true']`, under `body` so it outweighs the fields' own hover: every child, Clear included, faded and greyed as the tab row's tabs are, with a field's hover changing nothing.

## Tests

No test file of its own (claude-docs/testing/layer-ownership.md, "What a test may assert", rule 6). A filter's loading state, focus and Clear are tested once, in `CompendiumList`. What every list must do with its own wiring is written once, as `FILTER_ROWS` in `tests/support/filter-form.tsx`, which each of the six lists' tests runs with `it.each` on a subject of its own: the form a GET to the page itself with no Filter button, sending the filter shown under the names the page reads; the search opening its first page on the magnifier or Enter, trimmed, carrying the rest; each value shown alone drawing Clear to the page, and none with no filter; and the row starting again from a filter shown anew, which proves the list's key. A subject names what the form sends as an address query, as a native submit would. Each list asserts the rest itself: the address each of its other fields applies, a select's options, a type-ahead's pick and clear. The lists assert only that a type-ahead is one, drawn as a native select by the server (`drawnOnServer`); the narrowing as it is typed is Combobox's. Where the row's fields stand is presentation, the workshop's (rule 4).
