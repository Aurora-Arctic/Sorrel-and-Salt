# StockDialog

`src/components/StockDialog/` — the Edit Stock button on a coven's ingredient and the dialog it opens (M9.9). The dialog lists the jars the coven keeps of the ingredient, one for each form, and shows the chosen jar's quantity, unit and low-stock threshold beside the list. It can add a jar for a form the coven does not yet hold, and remove a jar. Everything done in it is saved together, as one `saveStock` request.

It replaces the one-jar `EditStock` dialog of the first build (the owner's call, 2026-10-20): editing one jar at a time from each jar line meant a pencil per line and no way to add a form, so the button moved to the card's foot and the dialog took the whole ingredient.

## Props

`workspaceId`, `ingredientId`, `ingredientName`, `forms`, `jars` and, optionally, `openOn` (`types.ts`).

- `ingredientName` is the name the coven gives the ingredient, the dialog's title and the button's name.
- `forms` is every form the ingredient comes in, each `{ variantId, label }` with the label ready to show (`formLabel`, Title Case), in the order Add Form offers them.
- `jars` is the jars held, `{ id, variantId, quantity, unit, threshold }`, at most one for a form.
- `openOn` (M12.29) is a form's variant id to open on. The dialog opens with that form chosen instead of the first jar. If the coven holds no jar of that form, a new row for it is added first, as Add Form would, and its Quantity is focused. The row is among the form's opening values, not appended after mounting, so the dialog opens unedited: Save stays off and Cancel closes quietly until an amount is entered (the owner, 2026-10-29, replacing a dialog that opened dirty). An id that is not one of `forms` is ignored. Left out, nothing changes.

## Where it is mounted

`covenCardActions` (`CovenCards/actions.tsx`, [`coven-cards.md`](coven-cards.md)) draws it in the card's foot when the entry carries `stock` (the forms and jars), so the Ingredients list and the Quick Look window, which calls the same function, show the same button, first in the foot, ahead of Edit or Annotate. The page gives `stock` only to a role that may update stock, `rolePermits(role, { inventory: ['update'] })`, so a viewer gets no Edit Stock. Hiding it is courtesy: the service refuses a viewer and a non-member whatever the page shows ([`../db/stock.md`](../db/stock.md)).

The entry page's Stock section carries the same dialog behind the same button in its heading (M12.29). Each jar of its shelf ([`jar-shelf.md`](jar-shelf.md)) opens it too, through `StockJarButton`.

**`StockJarButton`** (M12.29) is a second export of the same file: the same dialog behind a button of the caller's own. It takes the dialog's props, a required `ariaLabel` (the shelf names it "Edit Stock, <entry name>, <Form>"), an optional `className`, and `children` as what the button shows, with no icon and no tip. An optional `onSaved` runs once after a save has closed the dialog and refreshed the page (Record a Working reads its preview again there). It wraps the one `StockDialogForm` the default export uses, with the same eyebrow and title, so there is a single implementation of the dialog and the shelf only chooses where it opens.

**From the compendium's three dots** (M9.12; the owner's call, 2026-10-21) the dialog opens without its own button. A compendium card, the Quick Look window and the public entry page list **Edit Stock** first in their dots, and choosing it mounts `StockDialogModal`, the same `StockDialogForm` inside a `Modal` with the eyebrow "Edit Stock" over the ingredient's name, opened at once and closing back to the dots. `EditStock` (`IngredientEntry/edit-stock.tsx`) holds the choice: one coven opens it, several ask which first. The forms and jars come from `readEntryStock` (`src/app/entry-stock.ts`), read per viewer in one batch and mapped by `stockDialogOf` (`src/app/coven-stock.ts`), the mapping the coven's own pages use too, and a save reads the page again as it does here. The forms of a compendium entry are read per coven through that coven's proof (`heldFormsOf`), so an entry the curators have retired still lists them for a coven whose cupboard names it, and a coven that does not hold it reads none (the owner's call, 2026-10-21). The coven's own pages are unchanged. Because these pages are not a coven's, the dialog names the coven it writes to (the owner's call, 2026-10-21, changed from a qualifier the same day): `EditStock` passes `namesCoven`, and `StockDialogModal` puts the coven in the eyebrow, "Edit Stock for Whitethorn Coven" over the ingredient's name. Modal names a dialog by its eyebrow then its title, so the coven is heard in the dialog's name, "Edit Stock for Whitethorn Coven, Testwort". The coven's own pages (the Ingredients cards' pencil and the dots on the coven's entry page) pass no coven, the eyebrow stays "Edit Stock" and their dialog is still named "Edit Stock, Testwort".

**Over Quick Look**, the dialog opens centred, as any modal does. `ModalButton` draws its `<dialog>` beside the button, so in Quick Look it sits among the details window's `formalActions`, and Modal's rule zeroing those actions' margins (`.modal-dialog__naming > .modal-dialog__formal-actions > *`) took the dialog's own `margin: auto` with them, which is what centres a dialog in the top layer; it opened at the window's top left. The rule now skips a dialog (`:not(dialog)`, [`modal.md`](modal.md)). Layout is not something jsdom computes, so the fix was checked in the browser, on `DetailsWithStockDialog`.

## The button and the dialog

A `ModalButton` ([`modal.md`](modal.md#modalbutton)). The button is a jar with a cloth tied over it (`StockIcon`; the owner's pick, 2026-10-20, since Edit beside it in the foot already wears the pencil) in `.icon-tip__edit`, the accent green (the owner's call, 2026-10-20: the foot's Edit and Annotate went to the plain text colour), with an `IconTip` reading "Edit Stock", passed as `ModalButton`'s `tip` so the tip wraps the button and never the dialog ([`icon-tip.md`](icon-tip.md)). It is named "Edit Stock, Rosemary" (`ariaLabel`), so the buttons down a list never share a name. The dialog's head is the eyebrow "Edit Stock" over the ingredient's name.

The dialog is the `listed` size (`ModalButton`'s `size="listed"`, [`modal.md`](modal.md#styling)): half the default 32rem column again, plus a step of gap, so the fields keep the 32rem they would have in a dialog of their own and the list takes the rest. That comes to 49rem of body, capped at the window as every size is. Its body is a react-hook-form form around two columns and a `FormActions` row (Save, Cancel). The form is a child of the modal so its discard guard reaches Close, Escape and the backdrop. Every jar is a row of the form's values (`rows.<i>`), drawn or not: react-hook-form keeps a value when its field is not on screen, so what was typed into one jar survives choosing another.

## Layout: a list and the chosen jar

The layout is option E of the stock-editing mocks, the owner's pick of 2026-10-20: a list of forms down the left, the chosen jar's fields at full size on the right. It replaced a dialog of compact rows, one per jar, all on screen at once.

- **The columns** split the body one third to the list and two thirds to the fields (`grid-template-columns: 1fr 2fr`; the owner's call, 2026-10-20, giving a long form name more room than the first build's fixed 11rem list). A rule down the list's side divides them. The grid's cells stretch to the row, so the rule runs the height of the taller column: past a short list beside the fields, and down the fields' side of a long list.
- **The list** has a button per jar, named by its form, with its amount beneath ("250 g", or "Unmeasured") and the card's `StockBadge` (Low Stock or Out of Stock) at the top right, on the name's line (the owner's call, 2026-10-20; it sat at the end of the amount's line before). The badge moved by CSS alone, so the spoken order is unchanged. Its parts are read as one name with commas heard and not seen (`.spoken-separator`), "Flower, Edited, 250 g", so they never run together. The badge is a button of its own, for its tip, so it sits beside the list's button inside the list item rather than inside the button. The chosen button carries `aria-current="true"`: the list says which jar the fields are for, and is not a set of toggles (`aria-pressed`) that could each be pressed off. Every state is a tint of the accent green, with no grey (the owner's call, 2026-10-20): the chosen button `$fill-highlight` (12%), a touch stronger under the pointer (18%), and an unchosen one halfway there (6%) under the pointer. Each hover rule names whether its button is chosen, so neither depends on the other's order in the sheet. The tint fades in over `$motion-short` (150ms), and not at all under `prefers-reduced-motion`. Keyboard focus draws the shared focus ring inside the button, since the button fills its row and an outside ring would be clipped (`focus-ring($placement: inset)`; MB.121, where the keyboard pass found the browser's default ring on it).
- **The chosen jar** is a `fieldset` named by its form alone (`aria-labelledby`), headed by an `h3` with the form's name, under the dialog's `h2` title. The heading keeps the small-caps heading font every `h3` wears (the owner's call, 2026-10-20). A Remove bin sits at the heading line's end (`BinButton`, tipped "Remove", named "Remove <form>"). Beneath are [`StockFields`](stock-fields.md) at full size under the prefix `rows.<i>`, one under another: Quantity, then Unit, then Low Stock At, each the full width of the fields' column (the owner's call, 2026-10-20). Each field's label row is at least an icon tall (`$icon-size`), so Quantity, which has no ⓘ hint, starts as far below its neighbour as Unit and Low Stock At do below theirs.
- **Opening**, the jars are listed by form from A to Z, whatever order they arrive in, and the first is chosen (the owner's call, 2026-10-21), and the modal's first-field focus lands in its Quantity. With no jar, the list says "There is no stock yet. Add a form to start." over the Add row, and the fields' column holds their place shut (`NoJar`; the owner's call, 2026-10-20, replacing a list alone at the dialog's width): the same two columns and divider, so the dialog keeps its size when the first form is added. The heading's line is there, holding the plain word "Form" at the heading's own size and weight, in `$text-placeholder`, the ink an input's placeholder wears and a step quieter than `$text-muted` (`.stock-dialog__placeholder`; the owner's call, 2026-10-21: "pretty muted", after a blank line, a dashed box and dashed lettering were tried and dropped). No new token. It is `aria-hidden`, decorative, since the legend names the state. The line is as tall as a jar's because the h3's own line box sets both heights, not Remove's button (`.stock-dialog__head.is-blank`, with a `$icon-size` minimum that never binds), so the fields stand where a jar's do; Quantity, Unit and Low Stock At are drawn empty and disabled, with their labels and InfoTips, and no Remove. They live in a throwaway `useForm` of their own, so nothing there is registered with the dialog's form: they never reach its values, its dirty check or the batch, and Save stays off. A screen reader hears the group as "No Form Chosen", described by a hidden "Add a form to enter its stock." On a phone the same column stacks below the list. Adding a form puts its own fields in their place.
- **Narrow**, below 30rem of dialog width, the list stacks above the fields. This is a container query on the dialog's body (`container: stock-dialog / inline-size`), so it follows the dialog's width rather than the screen's; container size queries are Baseline Widely Available.

**Edited.** A form whose amounts differ from when the dialog opened shows "Edited" in its list button (`changed` in `batch.ts`, the same test the batch uses for an update). A form added in this dialog counts as edited, and its heading also says "New". The mark is the accent green of the Edit Stock button (`$accent`, as `icon-button-edit` paints it; the owner's call, 2026-10-20), except on the chosen button, where it takes the accent's hover ink (`$accent-hover`): the same green a step further from the ground in each theme, darker in light and lighter in dark. On the chosen button's tint `$accent` fell below WCAG's 4.5:1 for small text in light (4.43:1 at rest, 4.08:1 under the pointer), and the owner chose the darker green for that text alone (2026-10-20). No new token: `$accent-hover` already clears every state. Contrast at the caption size, computed from the tokens over `$surface-card` with the tint mixed in sRGB as `color-mix()` does: unchosen 5.20:1 light and 7.22:1 dark at rest, 4.81:1 and 6.55:1 under the pointer (in `$accent`); chosen 7.24:1 light and 7.22:1 dark at rest, 6.66:1 and 6.39:1 under the pointer (in `$accent-hover`). A jar waiting to be removed shows no Edited mark: its strike says more.

**Remove waits for Save.** A jar held is not deleted on the press. Its list item is struck through and its badge hidden, its fields are put away (what was typed stays in the form) with a line saying it goes when the dialog is saved, and the heading's bin becomes an Undo button, named "Undo Remove <form>", which takes it back. The delete is sent only on Save. A form added in this dialog and then removed was never saved, so it simply goes from the list, and the first jar is chosen.

## Add Form

Under the list: a `ComboboxSelect` in a compact field (`.field--compact`), labelled "Add Form" (placeholder "Choose form") offering the forms the list does not hold, and an Add button, off until a form is picked. Add puts the form in the list with empty amounts, chooses it, focuses its Quantity (`setFocus` once its fields are drawn) and empties the box. A form waiting to be removed still holds its place in the list, so it is not offered again; Undo brings it back instead. With every form in the list the Add row is gone, since there is nothing left to add. The open list's options take the caption size the compact box's own text has (`Combobox/index.scss`, under `.field--compact`), so the choices read as the box does.

## Saving

`batch.ts` turns the rows into the `SaveStockInput` the mutation takes, `{ create, update, delete }`, and sends **only what changed**:

- a new row is a `create` of `{ variantId, input }`;
- a staged removal is a `delete` of the jar's id, whatever was typed into it first;
- a held row whose amounts differ from how the dialog opened is an `update` of `{ id, input }`;
- an untouched row is in no list. So no jar is in two lists, which the service refuses ("Each jar can be saved once").

Save is off until something differs from how the dialog opened (`isDirty`) and off again if the change is undone. Amounts go as numbers, `null` for an emptied box (`stockAmountsOf`). A unit changed with the numbers left as typed is sent as it is: nothing converts. While the request is in flight Save is busy ("Saving").

The service holds the guards and the atomicity: the whole batch is saved or none of it, in one audited transaction ([`../db/stock.md`](../db/stock.md)). The dialog adds nothing to them.

Success closes the dialog through the modal's own close, then reads the page again (`usePendingNavigation().refresh()`), once however the button was pressed. There is no optimistic update: the card shows the stock as it was until the answer arrives.

## A refusal

The dialog stays open with everything as typed and marked, and the card unchanged. `placeServerIssues` places each issue by its path in the batch, through `rowFieldOf`. Every form with an issue gets a mark in its list button, a "!" whose accessible name is "Needs a Fix", and the first such form in the list is chosen, so its error is on screen:

| Path                                                                      | Shown                                                    |
| ------------------------------------------------------------------------- | -------------------------------------------------------- |
| `update.<i>.input.<field>`                                                | Beside that jar's box                                    |
| `create.<i>.input.<field>`                                                | Beside that jar's box                                    |
| `create.<i>.variantId`                                                    | On the jar as a whole: the coven already holds this form |
| anything else (a delete, the batch, Forbidden, NotFound, a network fault) | One `Notice` of kind `error` above the fields, an alert  |

A message on a jar is a plain `field__error` paragraph under its heading, linked to the jar's `fieldset` by `aria-describedby`; it has no alert role. Only the root Notice is an alert, and it is drawn only for an issue no field holds: a refusal placed wholly on fields shows the marks and the field errors, with no summary alert (the mock drew one; it is left out).

## How the dialog works

The stock button on a coven card is a `ModalButton` that opens a dialog. The coven's jars of the ingredient are listed down one side, and the chosen jar's fields sit beside them. A form is added from the list's foot, and a jar's Remove waits for Save. The whole dialog is sent as one `saveStock`. The service is the guard, and the dialog says its refusal. Nothing on the page changes until the save has answered: the page reads again once the dialog has closed.

The shelf's door and the pencil's door open one dialog, so what is saved and how it is refused cannot differ between them. A dialog opened by something other than its pencil, such as a menu item on a compendium card (Edit Stock), has an owner that holds the question of whether it is open. Modal restores nothing itself, so `returnTo` names where the focus goes on close.

The `coven` prop puts the coven in the eyebrow ("Edit Stock for Whitethorn Coven" over the ingredient's name), and so in the dialog's name. It is for a dialog opened from a page that is not a coven's, where nothing else says whose jars these are. A coven's own pages leave it out, as the address and the shell already say.

## What is sent

`batch.ts` sends only what changed. A jar left as it opened is in no list. A staged removal is a delete whatever was typed into it first. A row added and then removed was never a row. So no jar is ever in two lists, which the service refuses ("Each jar can be saved once"). A jar held is staged, to be sent as a delete; a form added here was never sent, so it simply goes.

## Which jar is chosen

The chosen form is held by its variant, because a row's index moves when an added row before it goes. The jars arrive in no fixed order, so the first form from A to Z is chosen as the dialog opens. When the chosen row has gone (an added form removed before Save), the first is used again. The list's form button is named by the form, its marks and its amount, and the chosen one is `aria-current`: the list says which form the fields are for, and it is not a toggle that could be pressed off. The badge is a button of its own (its tip), so it sits next to the list's button rather than inside it.

Opened on a form the coven holds no jar of, the dialog starts with a new row, as Add Form would add it, but among the opening values. The dialog thus opens unedited and Save waits for its amounts. Appended after mounting, the row would mark the form changed.

The chosen jar's fieldset is named by the form alone, so "New" is not part of the group's name. Quantity and Unit share a row, with Low Stock At beneath at Quantity's width. With no form yet, the fields' place has the chosen jar's layout, its heading empty and its three fields shut, so the dialog keeps its shape when the first form is added. Those fields sit in a throwaway form of their own, so nothing typed or registered there can reach the dialog's values, its dirty check or its batch, and there is no Remove.

## Refusals

A refusal's errors go to the place their path names. An issue's path names a row field: an amount (`update.0.input.unit`) goes beside its box, and a new jar's form (`create.0.variantId`, a form the coven already holds) goes on its row as a whole. Anything else, a delete's or the batch's own, goes to the alert above the fields. Every jar's errors show at once, and what was typed and staged stays. The first form with an error is chosen, so its error is in view.

## Layout and states

The dialog is a container of its own, so it is the dialog's width and not the screen's that stacks the list above the fields: below 30rem, two thirds is too narrow for the fields. A container query styles what is inside the container, never the container itself, so the grid is the box within. Its cells stretch to the row, so the list's rule runs the height of the taller column. The dialog is the `listed` size (Modal), with a third of the body for the list and two for the fields, so a long form name has room. A narrow dialog (a phone) stacks the list above the fields.

A form in the list is positioned for its badge, which sits beside the button at the end of the name's line, the top right. The space before a mark is its own margin rather than a column gap, because the spoken commas between the parts are flex items of no size and a gap would stand either side of each.

The pointer's answer comes at its own pace, not the theme's 400ms fade. Every state is in the accent's green, a step apart: a hovered form is halfway to the chosen look, and the chosen one is a touch stronger under the pointer. Each hover names whether it is chosen, so neither rests on the other's order in the sheet. The shared focus ring is inside, since the button fills its row.

The Edited mark is in the edit pencil's green (`icon-button-edit`), so it reads as the edit it records. On the chosen form the accent is also its wash, and light-theme `$accent` fell below 4.5:1 against it, so the chosen form's mark takes the accent's hover ink. The mark on a form the refused save named is drawn as a warning and read as "Needs a Fix" in the list button's name. A form on its way out is struck through and muted until Save or Undo. Add Form and its Add button sit on one line, under the list.

In the fields, the form's name has Remove (or Undo) at the line's end, and Quantity, Unit and Low Stock At are one under another, each the column's full width. The label row is as tall as a hint's ⓘ whether or not the field has one, so Quantity, which has none, stands as far below the heading as the others.

With no form yet, the heading's line is held so the shut fields stand where a jar's will. Its height is the h3's own line box (a jar's too, which Remove's 32px button does not exceed), so the minimum never binds and only keeps the line from collapsing. The word "Form" in that line is plain text at the heading's own size and weight, in the ink an input's placeholder wears, so it reads as not yet an answer.
