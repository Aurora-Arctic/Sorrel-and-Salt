# GroupedValueForm

`src/components/GroupedValueForm/` is the admin's form for a curated value, grouped or flat. Grouped, the value is filed under a group: a category, a curated ingredient form or a curated deity (whose group is its tradition). Flat, it is filed under nothing: a celestial body or a zodiac sign. One component serves every such vocabulary through `kind: 'category' | 'form' | 'deity' | 'celestialBody' | 'zodiacSign'`, as [`GroupForm`](group-form.md) serves the groups, so a new vocabulary is a kind rather than another copy.

A value has a name, a description and, for a grouped kind, its group. A deity also has Other Names. It saves through the kind's create or update mutation (`createCategory`, `updateIngredientFormValue`, `createCelestialBody` and so on). On an existing value it offers a delete behind a confirmation. It holds no modal of its own: the page puts it in one. The props are in `types.ts`.

The form kind is named for the GraphQL type, `IngredientFormValue`, because `IngredientForm` is the ingredient entry form (DESIGN.md §7). The copy calls a row a "form": Add Form, Save Form. A zodiac sign is "Zodiac Sign" on every button: Add Zodiac Sign, Save Zodiac Sign, Delete Zodiac Sign.

## Kinds

Everything that tells one kind from another is its entry in `index.tsx`'s `KINDS`, declared through `defineKind`, so a new kind is an entry there and its three mutation documents, and nothing else. `defineKind` holds the mutations to the kind's input and hides the input type from the record, so kinds whose inputs differ sit in one `KINDS`.

- **Copy** (`GroupedValueCopy` in `types.ts`). `noun` is the title-case word the buttons say. `group.hint`, the group field's info tip, is set only where it gives a rule the label does not (a deity's Tradition: a god several peoples honour is filed under one). `descriptionHint` is set only on the kinds whose suggestions match the description as well as the name (form, deity, celestial body, zodiac sign), since that flow is not in the label ([`info-tip.md`](info-tip.md), "When a field gets a tip"). `renameNote` is set on every kind but the category, `otherNamesHint` on the deity alone.
- **Schema and input.** The form's values are always `{ name, description, groupId, folkNames, drafts }`, the last two a deity's other names and the box they are typed in. For the category and form kinds the schema is the shared one itself (`CategoryInput`, `IngredientFormValueInput`, in `src/modules/vocabulary/validation/`) and `toInput` keeps the name, description and group. A kind whose input names the group otherwise supplies its shared schema with that key renamed to `groupId`, a `toInput` that renames it back, and `inputKeys`, which says where the server paths it, so its refusal still lands beside the group field. The deity is one: `DeityInput` calls the group `traditionId`, so its schema swaps that for `groupId` and its `inputKeys` is `{ groupId: 'traditionId' }`. Its `otherNames` is swapped for `folkNames`, the list of `{ value }` entries the field keeps, and `toInput` sends their texts back as `otherNames`.
- **No group, for a flat kind.** A celestial body or a zodiac sign has no `group`, so the form draws no group field. Its values still carry `groupId`, always `''`, so every kind has one shape; its schema (`CelestialBodyInput`, `ZodiacSignInput`, `src/modules/vocabulary/validation/astrology-value.ts`) parses the name and description alone, and `toInput` leaves the group out.

## Contracts

- **The shared schema runs first.** react-hook-form runs the kind's schema through the Zod resolver before any mutation is sent, so a blank name, a blank description or an unchosen group never reaches the server. The service runs the same schema again (DESIGN.md §7, "Errors").
- **A server field error lands beside its field.** A `VALIDATION` error's `fieldErrors` go to `setError` by path: `name`, `description`, the group's input key (`groupId`, or a deity's `traditionId`), and an other name's `['otherNames', i]` on that entry. Anything else renders above the fields in a `Notice` with `role="alert"` ([`notice.md`](notice.md)). The slug collision is pathed to `name`, since the slug is derived from the name and has no field of its own. The request is read by the shared `readGraphqlIssues` (`src/lib/graphql-failure.ts`), which gives every field error at once where `readGraphqlFailure` answers only the first; `placeServerIssues` places each under its field and joins the rest into the alert. A refusal that is not `VALIDATION` is one issue carrying the server's sentence, or `GENERIC_FAILURE` when there is none.
- **The group, where the kind has one, is a closed set typed into**, on the combobox's type-ahead box (`ComboboxTypeahead`, through `SelectField`'s `typeahead`) with the kind's placeholder. Typing narrows the list to the groups whose name holds the text, the first highlighted, so Enter takes it. Only a listed group is ever the value: text naming none leaves the group blank, so Save shows the schema's error beside the field, as for a group never chosen. It is named by the kind's label ("Group"; a deity's "Tradition") and its list is "Group choices" ("Tradition choices"). The list floats over the modal rather than stretching it. For a form, each group's row and the chosen value draw its [`FormIcon`](form-icon.md) before the name, the generic spoon for a group with no icon; the icon is decoration, outside the option's accessible name. Category groups and traditions carry none.
- **A deity's Other Names** is the ingredient form's [`ListField`](ingredient-form.md): a box labelled "Other Name" with an Add Other Name button, each name shown as a chip inside it. It sits under Name and opens on the deity's names, alphabetically. A save sends the whole list, and the service brings the stored names to it (DESIGN.md §5, `deity_other_names`). The field keeps its entries under the ingredient form's keys, `folkNames` and `drafts.folkNames`, because `ListField`'s paths are that form's; so the box refuses, as a folk name's does, a name already listed in any case and the deity's own name. The service refuses a name another deity of the tradition holds, naming that deity, and the refusal lands on the entry. Every other kind draws no list and sends none.
- **Every field but Other Names is required**, and each label carries an asterisk in the error red. The asterisk is hidden from the field's name: a screen reader hears "Name" and the control's `aria-required`.
- **Save is offered only when there is something to save.** It is disabled on a new value until something is typed, and on an existing one until something changes (react-hook-form's `isDirty`); putting a value back disables it again. From the press to the answer it is a [`BusyButton`](busy-button.md), named "Saving Category", "Saving Form" and so on, with `aria-busy`. The confirmation's Delete does the same, as "Deleting".
- **A rename of any kind but a category says it carries onto the compendium.** Renaming a form rewrites every live compendium variant that picked it ([`mb.162-compendium-holds-curated-values.md`](../design-decisions/mb.162-compendium-holds-curated-values.md)); renaming a deity rewrites the name on every live compendium entry's `ingredient_deities` row that picked it ([`mb.132-admin-deities.md`](../design-decisions/mb.132-admin-deities.md)); a celestial body's or a zodiac sign's rename reaches every entry listing it the same way. None is part of an entry's identity or address, so no address moves. On an existing value of a kind with a `renameNote`, whose trimmed name differs from the saved one, a `.field__hint` sits above the actions ("Saving renames it on every compendium entry that uses it."), and Save's `aria-describedby` points at it. Putting the name back removes it. A new value never shows it, nor does a change of group, which moves no entry.
- **No rename asks to end a redirect.** A rename moves no address, so the question is not asked here. The compendium's admin form still asks it, of an entry's own save ([`db/ingredient-slugs.md`](../db/ingredient-slugs.md)).
- **A delete asks first, and says what it does.** Delete Category, Delete Form, Delete Deity, Delete Celestial Body or Delete Zodiac Sign asks `Delete "<name>"?` and the kind's `deleteNote`, beside Delete and Cancel, on a card over the form, which is dimmed and held until it is answered, the focus on Cancel ([`modal.md`](modal.md), "Asking over the form"). Cancel puts it away, the focus back on the delete button pressed. A category's note: "Covens' ingredients and spells filed under it stay in their lists, but can no longer be filtered by it." Deleting a category removes nothing of a coven's: an entry filed under it keeps its link and stops reading the category ([`deleteCategory`](../../src/modules/vocabulary/services/categories.ts)). Every other kind's note: "You can't delete it while a compendium entry uses it. Covens' ingredients keep what they wrote, as their own value." A refusal comes back as a `FORBIDDEN` naming the compendium entries filed under the category ([`db/categories.md`](../db/categories.md), "Category writes"), or as a plain message naming the entries that pick the form or the deity. It is shown in the alert notice, the form stays open and the confirmation is withdrawn. A refusal that names its remedy is not a bad value in a box, so it gets no field (DESIGN.md §7).
- **Unsaved changes are asked about.** The form hands `formState.isDirty` to the shared guard ([`modal.md`](modal.md#unsaved-changes)); Discard Changes calls `onDone`.
- **Buttons are title case**: Save and Delete with the kind's `noun`, Cancel, Delete, Cancel, Discard Changes, Keep Editing. Save is solid; Cancel and Keep Editing are quiet, since they change nothing; the two deletes and Discard Changes are destructive.
- **Undo and redo** ([`field.md`](field.md#undo-and-redo)). The form calls `useFormHistory` on its `<form>` and provides it to `FormHistoryButtons`; the hook listens for its chords on the form itself. It is off while the unsaved-changes or the delete question is up. The form does not reset after a save (a save closes it), so nothing calls `clear()`.

## On the admin pages

`/curator/categories`, `/curator/forms`, `/curator/deities`, `/curator/celestial-bodies` and `/curator/zodiac-signs` are one page, `ValuePage` in `src/app/(shell)/curator/value-page.tsx`. Each route's `page.tsx` keeps its tab title and hands its kind and address over. `value-kinds.ts` holds each kind's readers from `@/modules/vocabulary` (its list, count, value by slug and, for a grouped kind, its groups), each mapped onto the page's own names, so the deities' `traditionId` and the astrology services' leading vocabulary stop there.

The page opens the form in a `RouteModal` ([`modal.md`](modal.md)) from its address, or at once from a press on an Edit or Add ("Opening at once" in `modal.md`). `?new` opens an empty form, titled "Add Category"; `?edit=<slug>` opens the value at that slug, under an eyebrow ("Edit Category") with the value's saved name as its title and a deity's tradition after it (`editHeading`; [`modal.md`](modal.md), "An edit dialog's head"). `value-dialog.tsx` is the client edge between the server page and the form, since a server component cannot hand `RouteModal` the function its contents take. The page always renders it, with `opened` (`{ heading, value }`) only when the address opens a modal, so a press's skeleton and the form that replaces it are one dialog; the form is keyed by the value's id. Closing, saving or deleting fades the modal out, then `router.replace`s the page it opened over, filter and cursor kept (`closeHref`, from `groupedValuesHref`), so Back does not reopen it, and `router.refresh()`es so the list re-reads.

A form's slug is its name and its group's (`wax-substance`), a deity's its name and its tradition's (`hecate-greek`, from `deitySlug`), and a celestial body's or a zodiac sign's its name, so a save can move the address; closing after every save means the modal never sits on a stale one. A deity's address also moves when its tradition is renamed, or deleted and its deities moved ([`group-form.md`](group-form.md); [`mb.132-admin-deities.md`](../design-decisions/mb.132-admin-deities.md)), so an old `?edit=` link can go stale without the deity changing. An `?edit=` naming no live value opens nothing and says so above the list in the shared `MissingNotice`, which names the kind by the list's `noun`. Why a modal on a URL rather than separate pages or intercepted routes: [`design-decisions/m5.6-admin-categories.md`](../design-decisions/m5.6-admin-categories.md).

## Styling, stories and tests

The form is the shared pieces on the form primitives ([`styling.md`](../styling.md), "Form fields"): Name and Description are [`TextField`](field.md)s in a `FormProvider`, the group a `SelectField`; Save is a `BusyButton` in a `.form__actions` row with Delete pushed to the far end by `.form__aside` ([`FormActions`](field.md)); the confirmation is the modal's [`ConfirmQuestion`](modal.md) card over the form. Its one rule of its own, `.grouped-value-form__note`, sets the rename note a step above the actions. The workshop has no API, so a story's save answers with the generic error. Stories: `index.stories.tsx`. Tests: `tests/components/GroupedValueForm/`, with the nine tests every kind shares run once, on the category, as rows of `tests/support/grouped-value-form.tsx` (a kind shares that code path, so another kind's run would prove nothing more); `tests/app/(shell)/curator/value-page.test.tsx` for the pages ([`grouped-value-list.md`](grouped-value-list.md#testing)); and `tests/e2e/admin.spec.ts` through the real server.
