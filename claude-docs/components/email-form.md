# EmailForm

`src/components/EmailForm/` is the `/account/email` page's form: the account's address, its verification state, and the one field that changes it. The server component `src/app/(shell)/account/email/page.tsx` reads the session, `getMe`, and `?next=`/`?error=`, and hands the results down as props. This component renders them and runs the `setEmail` mutation. With `embedded` set it is also the account page's Email section: the same field, mutation, cooldown and field errors, with no `<h1>` (the section's `<h2>` "Email" heads it) and never the confirmed view, which stays the email page's. A change link asked for there lands on the email page's confirmed view ([`auth/admin-bootstrap.md`](../auth/admin-bootstrap.md), "The account page"). Props are in `types.ts`.

## Contracts

- **The props carry decisions the page makes; the component never guesses them.**
  - `email` is `''` when the provider shared none. The page maps a placeholder (`isPlaceholderEmail`, `@/modules/identity`) to `''`, and the form never shows one.
  - `confirmed` is set when a followed link landed here (`?verified` on a verified row, with no `?error=`). The confirmed view is the verified line, the address and "Continue", with no field and no button.
  - `waitSeconds` is `verificationWaitSeconds` of the row's `verification_sent_at`, so the countdown starts where it stands.
  - `next` has already run through `safeReturnPath()` (`src/lib/sign-in.ts`), the guard `/sign-in` uses. Continue goes there.
  - `landing` is where Continue goes with no `next`: `signedInLanding()` of the session. That is `/keepers` for a keeper, `/curator` for a curator, the first coven for a member, and `/coven` for someone in none.
  - `accountPath` gives a verified account on the standalone page a quiet "Continue to Account" button (`.btn--quiet`) inside the card, beside "Continue" on the confirmed view and under the form otherwise. An unverified account reaches no other page, so it gets none.
  - `error` is a readable sentence from `verifyErrorMessage()` (`src/lib/account-email.ts`), never a raw `?error=` code, shown as an alert on mount.
- **Outside the confirmed view the field is always editable, whatever `verified` is.** The page is how any user changes the address at any later time. A verified account that comes back sees neither the verified line nor "Continue", since nothing was just proved. It sees the field, prefilled, and "Enter a new email address and we'll send it a confirmation link."
- **The status line is one sentence per state, each exported from `index.tsx`** so a test reads the state from the component and does not restate its words: `NO_EMAIL_STATUS` ("No email address yet. Enter the one we should write to."), `UNVERIFIED_STATUS` ("Your email address isn't confirmed yet. Open the link we sent you, or send a new one."), `CHANGE_STATUS` (the verified account's sentence above) and `VERIFIED_STATUS` ("Your email address is confirmed. We'll send your emails here."). Each says "email address" at its first mention and "address" after.
- **The success message names the typed address.** `setEmail` mails a link and returns the row as it is, because the address changes only when the link is followed, so the returned `email` is still the old one. The confirmation (an `<output>`, which carries the status role) names what was typed, trimmed and lower-cased for display, the service's own normalisation. The typed value goes to the server untouched: normalising is the service's job, and doing it twice would let the two drift.
- **The link carries `next`.** Every submit sends `next` beside the typed address, and `setEmail` hands it to the sender, so the resend or change link lands on the confirmed view with the same `next` ([`auth/admin-bootstrap.md`](../auth/admin-bootstrap.md), "The email page"). A refused link lands here with `next` still beside its `?error=`, so a link sent again from there carries it too. The component sends it as given, and the sender guards it again where it builds the link. With no `next` it sends none, and Continue takes the role's landing.
- **Two error surfaces.** A failed mutation rejects with `GraphQLClientError`, whose `errors[0].extensions` carries the code and, for `VALIDATION`, the field errors ([`graphql/errors.md`](../graphql/errors.md), "Errors"). The component reads it through `readGraphqlFailure(error, ['email'])` (`src/lib/graphql-failure.ts`).
  - A `VALIDATION` entry whose path starts at `email` lands inline beneath the input (`.field__error`), which the input references through `aria-describedby`, with `aria-invalid` set.
  - Any other `VALIDATION` issue, `FORBIDDEN`, `NOT_FOUND` or a masked error lands in the `role="alert"` region with the error's own message, or `GENERIC_FAILURE` when there is none or the rejection is not a `GraphQLClientError`.
  - Both are cleared, with the last success, when a new submit starts, so the page never shows two outcomes at once. The alert element does not exist in the DOM without a message, rather than being an empty live region, as in SignInPanel.
- **The submit is disabled only while the value, trimmed and lower-cased, equals `email` and `verified` is true**, since a verified, unchanged address has nothing to send, and while the mutation is pending. An unverified, unchanged address stays submittable: the service resends its link.
  - The row is the shared `FormActions` with `label` and `busyLabel` given, so the button is a `BusyButton` ([`busy-button.md`](busy-button.md)) that carries `aria-busy` and the `.spinner` and reads "Sending Confirmation" while in flight ([`styling.md`](../styling.md), "Buttons").
  - It is a real `disabled` attribute, not `aria-disabled`, because a submit with nothing to send is fine to skip in the tab order. `.btn` greys out under either, so the component styles neither.
- **The cooldown.** After a send succeeds the submit stays disabled for `RESEND_DELAY_SECONDS` (sixty), its label counting down as "Send Again in Ns", and a form submitted by other means in that time is ignored. It also starts from `waitSeconds` on mount, because an unverified sign-in lands here with the sign-up mail just sent and its first sight would otherwise be a refusal. It is timed off `Date.now()`, not counted in ticks, so a tab left in the background waits the real minute. This is a courtesy: the rule is the service's, which refuses a second mail within the minute with a `VALIDATION` field error naming the wait ([`auth/admin-bootstrap.md`](../auth/admin-bootstrap.md), "The email page"), and that lands beside the input like any other. The test fakes the clock with `shouldAdvanceTime` so MSW's fetch and `waitFor` still see time pass.
- **No native validation.** The form is `noValidate` and the input is not `required`: an empty or malformed field goes to the server, whose sentence lands beside the input like every other refusal, not in the browser's own bubble, which is styled by nobody and read by no screen reader consistently. `type="email"` stays for the keyboard it summons on a phone.
- **A controlled input is the whole form.** It is not react-hook-form; DESIGN.md §7's resolver pattern arrives with the shared Zod schemas, and this component is expected to move to it then.

## Styling

Built on the form primitives in `_primitives.scss` ([`styling.md`](../styling.md), "Form fields"): `.form` and `.form__actions`, one field drawn by the shared `FieldShell` ([`field.md`](field.md)) around the form's own `.input`, and [`Notice`](notice.md) for the alert and the sent message.

- On the email page the `<h1>` and the status line are a `PageHeader` ([`page-header.md`](page-header.md)), the status line its `lede`. Embedded, the status line is a `.lede` on its own, under the section's head.
- Send Confirmation and Continue are each the view's one primary action, so both are `.btn--solid`. Continue is `.btn` on an anchor, which `.btn` keeps from underlining or taking the visited ink.
- The width is the page's: `/account/email` is a `.page-frame--narrow` ([`styling.md`](../styling.md), "The page frame"), and the account page's section sits in the same frame. Both stand the form on a `.panel`, so the two pages share one ground. The way back to the account page sits below the email page's panel.
- The component's own stylesheet is the column's gap and the address's weight.

## Not here

Stories: [`index.stories.tsx`](../../src/components/EmailForm/index.stories.tsx), "Account / Email Form". `States` is drawn in the app shell and has a control choosing Ready To Resend, Countdown, No Email, Confirmed, Change Later and Failed (reading `verifyErrorMessage`, not a copied sentence). `Embedded` sits inside the account page's frame and section. Every other state renders inside the page's own `<main className="page-frame page-frame--narrow">` and its `.panel`. The TanStack Query client comes from the workshop's global provider (`.storybook/components.tsx`), never from a story's own `QueryClientProvider`, since a second would split the cache. Nothing is mocked, because the component reaches the network only on submit.

Tests: `tests/components/EmailForm/index.test.tsx`, in the `dom` project, answers `SetEmail` through MSW (`mockGraphQLMutation` for the row, `mockGraphQLError` for a refusal, so the error body is the route's own mapping). Role and label queries only.
