# Support Requests

`src/components/SupportRequests/` — the support page, `/admin/support`, for an admin (M15.30) and, narrowed, a curator (M15.31).
A page of the requests people have sent, open ahead of resolved and newest first, with a filter, the shared
[`Pager`](pager.md), and one request opened to its message in a modal at `?request=<id>`. Render-only: the page reads the
filter and cursor off its address (`support/filter.ts`), one page and its count through `listSupportRequests` and
`countSupportRequests`, the people named on them through `usersNamedOnRequests`, and the opened request with its replies
and its sender's time-outs (`support/reads.ts`). The support services are the guard; the page and GraphQL end at the
same ones.

## Contracts

- **A row shows** what it is about, subject (a link that opens the request), status, sender, who it is assigned to, whether
  curators can see it, and the error number. `href.ts`'s `supportHref(filter, cursor, request?)` builds every address,
  carrying `?view=` (omitted for the default, Needs Staff), `?about=`, `?error=`, one cursor and `?request=`.
- **Six views** (`views.tsx`, `SupportViews`): Needs Staff (all open, beta testers first, then oldest sender activity first), Mine (open, assigned to me), Unassigned (open, no assignee), Waiting on Sender, Resolved and Closed. They are a tab pattern (`role="tablist"`, roving tabindex, arrow keys, Home and End), each tab a link carrying its count from `countSupportViews`; the list sits in the selected tab's panel. The counts honour the About and Error filters and a curator's scope. The Status select is gone, since the view implies the status. A row's Status cell adds "Sender Replied" and "Beta Tester" text labels.
- **The composer has two modes**: Reply (the default) and Internal Note, chosen in a "Send As" group. A note goes through `addSupportInternalNote`, which takes no notifier, so no email is sent, and it shows with a "Staff · Internal" tag. Senders never receive it.
- **A curator is shown no sender's email** (2026-10-31). The From fact shows the name alone for an account, and "Signed-out sender" with no address for a signed-out request; an admin sees the address beside either. The service withholds it (`asRead` nulls `senderEmail`, `usersNamedOnRequests` blanks other people's addresses for a curator), and the GraphQL `User.email` is self-or-admin already. A curator is shown the linked issue address as a read-only link, with no pencil and no address form.
- **The sender's name** (the Sender column and the From fact) is, for an admin, a link that opens the sender's user modal over this page, at `?user=<id>` beside the filter, the cursor and any open `?request=<id>`, so the browser does not leave `/admin/support`. The page reads it as the Users page does (`readOpenedUser`) and draws the same `UserDetail` dialog, Support Time-Out section included, in a second `RouteModal` place named `user`, after the request's. Both are native dialogs shown in turn, so the later one stacks above the earlier, which stays open beneath; Escape and Close act on the top one. Close of the user modal goes to the same address without `user`, which returns to the request (or the list). The modal's own links (covens, Impersonate) work as on the Users page. A curator has no user modal, so the name stays text and a hand-written `?user=` is ignored; a deleted account stays "Deleted account". The email beside it stays muted text.
- **The filter** is [`FilterForm`](filter-form.md): an Error Number search and a Kind select.
- **The opened request** is a wide dialog of two columns, stacked on a phone with the settings after the reply. Its head is
  an eyebrow ("Support · " and the kind), the subject and a status badge. The left column holds the facts (From on a row of its own, also `.support-detail__fact--wide`, then Sent with Resolved beside it, then Page on a row of its own as `.support-detail__fact--wide` (`grid-column: 1 / -1`, so a long path stays on one line and breaks anywhere only past the full width, and never sits beside a date), then Error; the grid's gaps are unchanged;
  and one Error line with the reference in monospace and an icon-only copy button, when the request has one), then the
  Issue section (below), then the
  thread (the sender's message first, tagged Sender, then each reply, tagged Staff) and the reply form. The controls are:
  - **Waiting on Sender**, a switch beside the reply box on an open request in Reply mode (never in Internal Note mode): on, the reply moves the request to waiting on the sender. While the sender has a standing time-out (`request.timeouts`, not lifted, ending in the future) a notice beside it says "The sender cannot answer until <time>.", and the reply still sends. A sender's follow-up is tagged "Sender" in the thread.
  - **Reply** (a "Your Reply" field; Reply is disabled until there is a body) with **Resolve** opposite it (open requests
    only), for an admin or a curator the request is assigned to. The internal-note mode (M15.42) is open to a curator on any request they can read, not only an assigned one: the service allows it (`addSupportInternalNote` reads the request as the curator's own visible read), so the form needs no assigned-to gate. A curator who cannot answer a request (shared with them, or assigned to someone else) is shown a note-only form: "Your Note" and Add Note, with no mode choice, no reply field, no Resolve and no Waiting on Sender control (`ReplyForm`'s `noteOnly` prop).
  - A right column for an admin alone: **Assigned To**, **Shared With Curators** and **Time-Out**, a
    fold closed by default that says "none", or a "Timed Out" badge and "until" the end of the standing time-out.
- **Resolve asks first** (2026-10-31): it goes through `ConfirmedAction` (`inModal`), titled "Resolve This Request?", saying the sender sees it as resolved on their support page, can reopen it by replying, and that it closes by itself after seven days without a reply. The confirm is plain (`btn btn--solid`), not red, since resolving is not destructive. No mail is sent on resolve. The page has no Close control, so none was given a confirm.
- **The Issue section sits in the left column above the thread, for both roles** (2026-10-31): the linked issue as repository and number, preceded for an admin by a pencil icon button named "Change Issue Address", or the address field at once while none is linked; a curator sees the link alone, and nothing while none is linked. Spacing: the facts to its hairline, and its last line to the Thread heading, are each the column gap, `space(4)` (before, the facts to the Thread was `space(4)`); its own `space(3)` of padding sits below its border, and its margin stays zero. A curator's read-only Issue (`support-detail__issue--plain`) drops the hairline and the padding and stands `space(6)` from the facts and from the Thread heading: before, facts to hairline `space(4)` (column gap) and Issue to Thread `space(4)`; after, each is the column gap `space(4)` plus a `space(2)` margin on the section, two contributors, since the gap is shared with every other section in the column.
- **There is no Create Issue link.** The admin makes the GitHub issue by hand, so nothing from the request is copied
  into GitHub: the message could hold private information (the owner, 2026-10-31). The "GitHub Issue" field takes either of two
  shapes and stores both as the plain issue link, `https://github.com/Aurora-Arctic/Sorrel-and-Salt/issues/<number>`: that link itself, or a link from any project board of the `Aurora-Arctic` organisation (`github.com/orgs/Aurora-Arctic/projects/<n>/...`), such as
  `https://github.com/orgs/Aurora-Arctic/projects/1/views/1?pane=issue&itemId=…&issue=Aurora-Arctic%7CSorrel-and-Salt%7C<number>`, whose `issue` parameter is `owner|repo|number`, URL-encoded. `normaliseIssueLink` in `src/lib/support-path.ts` does it, for the form and the service alike; anything else, or an issue of another repository, is refused beside the field with "Paste a GitHub issue link, like github.com/Aurora-Arctic/Sorrel-and-Salt/issues/1409, or a link opened from the project board."
- **Time-outs** (2026-10-31, the owner's call on reviewing the PR) have no heading of their own beyond the fold. While one stands, the form is hidden and a card shows a "Timed Out" badge, "until {end}", the note in muted text, "Set by {name}, {date}" and **Lift** beneath, which asks first ("Lift the Time-Out?", a red "Lift Time-Out" confirm like Time Out Sender's). Otherwise the form asks **For** first (1 Day, 1 Week, 1 Month or Until a Date; only Until a Date shows an **Until** day field, and the end is the end of that day in the admin's own zone), then **Note** ("Seen by staff only."). **Time Out Sender** is a quiet button that asks first (heading "Time Out {name}?", body "They cannot send a support request until {end}. You can lift it sooner."), with a red confirm. The request dialog keeps no ledger: when the sender has earlier time-outs it draws a history icon link beside the Time-Out heading (the fold's `info` slot), named "Earlier Time-Outs", to the sender's user modal over this page, where the ledger is (the owner, 2026-10-31). The panel (`timeout-panel.tsx`) is shared with the user modal, keyed by the user.
- **Thread dates** (2026-10-31, the owner's call) sit flush right in each card's head (`margin-inline-start: auto` on the `<time>`), with the name and tag at the left; when the head wraps on a phone the date stays at the right. The thread is shared by the admin dialog and the sender's dialog on `/account/support`.
- **The page announces itself.** A visually hidden `<output>` in the list gives the result count ("3 Requests") after a filter change, and one in the dialog gives each save's outcome ("Reply sent.", "Request assigned.", "Time-out lifted."). Each row link is named subject plus sender ("Wobbling Cauldron from Ada Wortley"). The Shared With Curators column draws a check or cross with its text, the Subject cell wraps long unbroken text inside a capped width, and the dialog opens with the focus on its title. Dates use `LocalTime` long, as the account page does. The GitHub Issue and Time-Out forms ask before discarding typed input.
- Every action is a GraphQL mutation (`use-support-action.ts`) and refreshes the page on success; a refusal shows as a
  notice, or beside its field where it names one.
- A curator reaches the page through `requireCuratorSession()` and is shown the admin-only controls by none: the `viewer` prop hides them, the services refuse them regardless, and the page gives a curator no assignee list. A request neither marked nor assigned to the curator shows the same "no support request has that address" notice as an unknown id. `tests/e2e/admin-support-curator.spec.ts` proves it.
