# Support Requests

`src/components/SupportRequests/` is the support page, `/keepers/support`, for a keeper and, narrowed, a curator. It is render-only: the page reads the filter and cursor off its address (`support/filter.ts`), a page and its count through `listSupportRequests` and `countSupportRequests`, the people named on them through `usersNamedOnRequests`, and the opened request with its replies and the sender's time-outs (`support/reads.ts`). The support services are the guard; the page and GraphQL end at the same ones. What a viewer may not do is not drawn, and the services refuse it regardless.

## Contracts

- **`supportHref(filter, cursor, request?, user?)`** in `href.ts` builds every address. The default view (Needs Staff) is omitted from it.
- **Six views** (`supportViewTabs`): Needs Staff (all open, oldest sender activity first, for everyone), Mine (open, assigned to me), Unassigned, Waiting on Sender, Resolved and Closed. There is no Status select, since the view implies the status. Each tab keeps the other filters, and its count honours About, Error, Sender and a curator's scope.
- **The Sender facet** (`sender=<group>`, applied in SQL) has one option per entry of `SUPPORT_SENDER_GROUPS` (`src/lib/support-path.ts`), each with its own icon (`SENDER_ICONS`) and SQL condition (`senderArm` in `src/db/repository/support.ts`). A further group is another entry.
- **A curator is shown no sender's email.** The service withholds it (`asRead` nulls `senderEmail`; `usersNamedOnRequests` blanks other people's addresses for a curator), and GraphQL `User.email` is self-or-admin already. A keeper sees the address beside a name, and beside "Signed-out sender".
- **The sender's name opens the user modal for a keeper only** (`?user=<id>` beside the filter, the cursor and any open `?request=<id>`). It is a second `RouteModal` place named `user`, drawn after the request's; both are native dialogs, so the later one stacks above the earlier, which stays open beneath, and Escape and Close act on the top one. A curator has no user modal: the name stays text and a hand-written `?user=` is ignored.
- **A curator reaches the page through `requireCuratorSession()`.** A request neither marked for nor assigned to the curator shows the same "no support request has that address" notice as an unknown id (`tests/e2e/admin-support-curator.spec.ts`). The page gives a curator no assignee list.
- **Every action is a GraphQL mutation** (`use-support-action.ts`) that refreshes the page on success. A refusal shows as a notice, or beside its field where it names one. A visually hidden `<output>` gives each save's outcome. A trailing no-break space on every other call lets a repeat be spoken, since a live region speaks only a change.

### The opened request

- **Left column** holds the facts (From, Sent, Page, Error with the reference and its Copy button, and Error Details, the error's name and message, on a row of its own when the request has them), Issue, thread and reply form; **the right column, Request Settings, is a keeper's alone**: Assignee, Shared With Curators and Time-Out. The dialog is shared with the sender's page: `facts.tsx` and `thread.tsx` and the `support-detail` rules are reused by [`support-sender-request.md`](support-sender-request.md).
- **From and Page take a row of their own** (`support-detail__fact--wide`), so a long path never sits beside a date. The crash reference is staff only.
- **Resolved reads "by the sender"** when `resolved_by` is the request's sender (`resolvedBySender`).
- **Internal Note is the opening mode**, so a reply is always chosen. A note goes through `addSupportInternalNote`, which takes no notifier, so no email is sent and senders never receive it.
- **A curator may note on any request they can read**, not only an assigned one: the service reads the request as the curator's own visible read, so the form has no assigned-to gate. A curator who cannot answer a request (shared with them, or assigned to someone else) gets the note-only form (`noteOnly`).
- **Reply and Resolve** are for a keeper or the curator the request is assigned to. Resolve is offered on open requests only. Its confirm is plain, not red, since resolving is not destructive. No mail is sent on resolve, and the page has no Close control.
- **Waiting on Sender** is offered on an open request in Reply mode only. While the sender has a standing time-out (`stands`: not lifted, with no end or an end ahead), a notice says they cannot answer, and Reply asks before it sends. An internal note never asks.
- **An anonymised request** (`anonymised`: its sender is the System account) shows no sender. `reads.ts` decides it on the server and loads no name for the System account, so the row's `sender` is null. The sender's message and follow-ups are emptied, and a keeper sees what a curator sees: the issue read-only, no settings, and a notice in place of the reply form. The service refuses each change (`refuseAnonymised`). Anonymised requests come last in every view and filter, each group in the view's own order; the repository orders it (the first key of `orderOf`, through the cursor helper).
- **Issue spacing.** For a keeper, the facts to its hairline and its last line to the Thread heading are each the column gap, `space(4)`, with `space(3)` of padding below its border and no margin. A curator's read-only Issue (`--plain`) has no hairline or padding and stands `space(6)` from both neighbours (the gap plus a `space(2)` margin).
- **There is no Create Issue link.** The keeper makes the GitHub issue by hand, so nothing from the request is copied into GitHub: the message could hold private information. The "GitHub Issue" field takes that issue's link, or a link from any project board of the `Aurora-Arctic` organisation (`github.com/orgs/Aurora-Arctic/projects/<n>/...`), whose `issue` parameter is `owner|repo|number`, URL-encoded. Both are stored as `https://github.com/Aurora-Arctic/Sorrel-and-Salt/issues/<number>`. `normaliseIssueLink` in `src/lib/support-path.ts` does it, for the form and the service alike. Another repository's issue is refused beside the field.
- **Time-outs** use one panel (`timeout-panel.tsx`) for the request dialog and the user modal, keyed by the user, so a repeat sender is seen as one. It is a thin wrapper giving the time-out's words and writes to `PausePanel` (`UserDetail/pause-panel.tsx`), the panel the site and coven access pauses are too. The fold is closed by default.
  - Setting one needs a note and a message to the user, both required; Until a Date ends at the end of that day in the admin's own zone.
  - A signed-out sender has no account to time out, so the panel is keyed by the request (`timeOutSignedOutSender`) and named by the address the sender wrote from. It shows only when the request carries that address.
  - The request dialog keeps no ledger. When the sender has earlier time-outs, a history icon link beside the heading goes to the sender's user modal over this page, where the ledger is.

## Request lifecycle

Server behaviour the component only shows (claude-docs/design-decisions/support.md, "A resolved request closes on its own, and a closed one is anonymised").

- **Transitions.** open to waiting_on_sender (a staff reply marked waiting, `reply.ts`); open or waiting to resolved (staff, `staff.ts`, or the sender on their own request, `resolveMySupportRequest`); open, waiting or resolved to closed (staff, `closeSupportRequest`); waiting or resolved to open (the sender's public message, which keeps the assignee); resolved to closed (the request's job, seven days after resolving, `retention.ts`); closed to a new request (the sender's message opens one linked to it). Staff replies and internal notes change nothing else. Each move is one guarded update, so a refused move writes nothing.
- **Retention** runs once a day as the support-retention job, as the System account: a closing-soon notice from day 5, close on day 7, and anonymising on the twelfth month after the close. Anonymising keeps the row, topic, status and dates so counts survive and drops everything the sender wrote or is known by. The job reads due ids per stage a page at a time and hands each page to a batch; each batch re-reads its rows' status and dates before writing, so a batch run twice, two at once, or after a reopen changes nothing.
- **The sender's own reply:** an open request adds to the thread; a waiting or resolved one reopens, clearing `resolved_at`; a closed one opens a new request carrying topic and assignee, linked to the closed one. Time-outs refuse it as they refuse a send. Only the new request counts toward the daily limit.
- **The reply notice** carries no reply text (it is read on the sender's support page behind sign-in). A signed-out sender, with no such page, is mailed the reply whole. Either goes out through a retried job that stamps the reply once the mail is taken.
- A status change sends no mail.
