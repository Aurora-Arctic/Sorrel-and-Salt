# Sorrel and Salt — Work Breakdown

Every task is one PR, sized to one sitting and reviewable in one. Task IDs are immutable: they identify a task, they do not schedule it. Execution order is the wave order in the next section.

The GitHub issue tracker of `Aurora-Arctic/Sorrel-and-Salt`, with the org Projects **Sorrel & Salt** and **Sorrel & Salt V1.Next** over it (`scripts/task-projects.mjs` names them), is the source of truth for what to work on (see [`CLAUDE.md`](../CLAUDE.md)). This file is the reasoning behind the breakdown — corrected in place when it is wrong, never re-scoped to chase the board. It is the index: the milestone sections are in [`tasks/`](tasks/) and the reasoning for each open wave in [`waves/`](waves/) (**The milestone files**, below).

Story references point at the numbered user stories in §10 of the design doc. Infrastructure tasks carry developer-facing stories instead.

## Deferred to v2

Notes are out of scope for v1. That removes stories 35–46 and the whole notes data layer, UI and visibility model — 17 tasks and 29 hours. Two consequences carried into the tasks below: observers are now strictly read-only, since their own private notes were the sole exception; and the ingredient detail page (M8.19) is built so a notes section can be added beneath it without restructuring the page.

Also deferred: edit history, viewer spell approval, compendium suggestions and merge tooling, GraphQL response caching, a workshop-viewer role that opens the staging workshop without keeper rights (M2.10), and linking a coven's own ingredient to the compendium. A coven can annotate a compendium entry and make it its own in v1; the other direction (the Link dialog, This Is It, splitting an entry across compendium entries) waits for v2. Its drafts, M12.38–M12.41, are retired; M12.42 removes the conversion already built (DESIGN.md §13, "Link to the Compendium").

Two editing experiences wait for v2. A better editor for ingredients and spells, so that changing an entry does not mean working through a long modal form, is scoped in M17.5, retired with its scope kept ([`tasks/v1/m17.md`](tasks/v1/m17.md)). An upload experience for help screenshots is unscoped: how a keeper adds a screenshot's light and dark pictures from the help editor, where they are stored, and how they stay paired and sized, in place of capturing them with `npm run help:screenshots` ([`components/help-pages.md`](components/help-pages.md), "Screenshots").

A tarot and rune journal, where a member records readings, is a v2 idea and unscoped.

**Spell kinds.** A spell has a kind: jar, another kind of working (candle, sachet, bath, incense, …), or no container at all. In the builder the Jar section becomes the kind's own section, with its own fields and drawing, and a spell with no container has no vessel section; the ordered steps, categories, timing, notes and visibility are the same for every kind. The kind is chosen at creation and may change while the spell is a draft; the recipe page and the grimoire card show it and the grimoire filter narrows by it. Every spell that exists today is a jar. In Coven Inventory and the supply verdicts are unchanged for a kind with no container. Who defines the list of kinds (code, curated vocabulary, or free text) is undecided. Estimated at a sitting (owner, 2026-10-28).

## Execution order

The milestone numbers below are **identifiers, not a schedule**. Tasks are executed in the wave order in this section; a task keeps its ID wherever it runs. M1.21 stays `M1.21` even when it runs eighteenth.

**Why the original order does not work.** The breakdown was written feature-first: each milestone creates its own tables. But every table spreads `...auditColumns`, whose three `*_by` columns reference `users`, created in M2.3. An FK target must exist before the FK, so `users` is the first node of the only valid creation order — and in the original numbering it sits behind ten other tables. That is not a narrow edge case: it already forced three workarounds into shipped code (M1.9 clones an empty template, M1.11 reseeds because `seed()` throws for every scenario, and M1.15 shipped `auditColumns` without the FKs §5 mandates). The wave order below retires all three, and costs no rework, because `src/db/schema/` still contains only `.gitkeep` — no table exists yet, so no retrofit migration is needed.

### The core move: land the DDL early, the policies late

|            | **DDL** (moves early)                                                              | **Policies and behaviour** (stays late)                                           |
| ---------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Statements | `CREATE TABLE`, columns, types, NOT NULL, CHECK, FKs, indexes, PKs                 | The membership check, the `Membership` proof, and the finder predicates they gate |
| Answers    | _What shape is the data?_                                                          | _Who may see and change which row?_                                               |
| Tasks      | M6.2, M4.1, M4.1a, MB.35, M4.2, M4.2a, M4.4, M4.4a, M4.6, M7.1, M9.2, M10.2, M10.4 | M6.3, M6.6, M10.3                                                                 |

They separate cleanly because they are already different migrations and different tasks. Postgres will happily create a table in one migration and attach a policy in a later one, and nothing about creating `spells` commits you to a visibility model.

The DDL is safe early because §5 already specifies every column, type, enum set and index predicate — writing it in Drizzle is transcription, not design. Additive DDL is inert: a table nobody queries yet changes no behaviour, and under expand/contract this is the free direction. Empty tables are also the cheapest moment for constraints, so land every constraint §5 specifies at **full strength** — NOT NULL, CHECK, enum sets, three partial unique indexes on `ingredients`, composite PKs. Tightening later needs a backfill, an M1.5 acknowledgement line, and can fail on rows that already exist.

The authorization rules must not come early for the opposite reason. A rule written before its service tends not to match it: the `Membership` proof M6.3 threads through every workspace-scoped finder mirrors the permission statements `assertMembership` checks in the same task, and the two-layer design only works if both layers agree. Behaviour is also where the real uncertainty lives — whether a steward can read a member's private spell is worth deciding with the service in front of you; column types are not. The wave order follows: tables (W3), then seeds run against them (W4), then the service rules land and are proved against real seeded rows (W5).

**MB.29 removed the second half of this argument**, which used to be that RLS interferes with seeding — a policy on a table you are about to seed will filter your seed. With policies deferred to the public launch there is no seed interference to dodge, and the wave order stands on the first reason alone. When policies do land, that constraint comes back with them: [`auth.md`, "RLS role split, `FORCE`, and identity on the read path"](design-decisions/auth.md#rls-role-split-force-and-identity-on-the-read-path) answers it with `BYPASSRLS` on the seeding role.

### Ordering rules

Three rules shape the order, and each is stated once in [`CLAUDE.md`](../CLAUDE.md), "Conventions":

- **The sweep-task rule.** A sweep over database objects lands once, after the last object; a sweep over code lands as a mechanism plus a guard, early. M6.17 is the one exception: a census rather than an enforcer, so it closes at Wave 14 ([wave-14.md](waves/v1/wave-14.md)).
- **A table task, then a behaviour task.** M9.2 is the one bundle: it carries `inventory_items` and the shared unit-to-dimension module.
- **Document as you go.** The scheduled compression pass is retired: `MW.1` and `MW.2` ran, `MW.3` to `MW.14` are retired, and `MW.15` is the v1 close-out.

## The milestone files

The `## M… —` sections that followed the execution order live in [`tasks/`](tasks/), and the reasoning for each open wave in [`waves/`](waves/), each in one directory per Project, named by its `slug` in `scripts/task-projects.mjs`: `tasks/v1/` and `waves/v1/` for Sorrel & Salt, `tasks/v1-next/` and `waves/v1-next/` for Sorrel & Salt V1.Next. A milestone with tasks on both Projects has a file in each directory, and a task's entry sits in its own Project's file. Together with this file they are one document: `scripts/tasks-md.mjs` reads this file first, then each Project's directory in config order, so a range in the table (`M3.3 → M3.10`) is the headings between its ends across that sequence, and a new milestone file needs no registering. Read a task by its `**<ID> — ` heading, to the next heading, and, for an open wave, its wave file — never a whole file.
