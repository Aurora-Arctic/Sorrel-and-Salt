## The build, in three lanes

### Lane A — the shell button and its target (Sonnet)

**What it accomplishes:** the shell's Add Ingredient button comes alive on every page. It works out _where_ a new ingredient should go without asking — the coven whose page the viewer is on, their only coven otherwise, or the compendium when a curator is on an admin page — and opens the right dialog for that target. A viewer who may write nowhere never sees the button, and someone in several covens gets a Coven select with their view-only covens shown but disabled. After a save the dialog closes and a status announces what was saved, naming any jars M12.8 carried onto the new entry. Story 28 and the shell half of story 29 depend on this lane.

1. `ShellWorkspace` (`src/lib/types.ts:250`) gains `id` and `canWrite`, built in `viewerOf` (`src/lib/viewer.ts:42-47`) from the membership role with `rolePermits`, beside the existing `canReadMembers`. The mutation needs the id; the select needs the permission.
2. A new client component `AddIngredientButton` (`src/components/AppShell/add-ingredient-button.tsx`) replaces the disabled button. It reads `usePathname()` and applies the entry's rule:
   - `/admin/*` and `viewer.canCurate` → a `Link` to `/admin/compendium?new` (the admin dialog, by address — see decision 2).
   - Otherwise the target coven is `covenSlugOf(pathname)`, else the viewer's only writable coven. With one writable coven and no coven on the address, that coven.
   - No writable coven and not on an admin page → the button is not rendered.
3. Elsewhere the button is a `ModalButton` (label "Add Ingredient", `title` "Add Ingredient") whose body is a Coven select (only when `workspaces.length > 1`) above `<IngredientForm workspaceId={target.id} key={target.id} …/>`. A view-only coven is listed, disabled, and never preselected. Changing the coven remounts the form through `key`, so a half-filled form is lost — the select is therefore the first control and the dirty guard already covers a change made later (judgement; cheap to do, see decision 1 for the control).
4. After `onSaved(saved, 'open')` the modal closes and the button renders a `role="status"` region beside itself: "Saved {name}" plus, when `saved.jars` is non-empty, which jars came with it (B3). The form's own Saved notice cannot be used here because the form unmounts on close.
5. Tests: `tests/components/AppShell/` — the target rule by pathname and memberships (one coven, several, none writable, admin page), the select present only with more than one coven, the disabled view-only option, the status region after a save (mocked mutation), axe with the dialog open at 375px. `tests/lib/viewer.test.ts` for `canWrite`. Guards: `browser-floor` list if a new client file reaches it.

### Lane B — the form (Sonnet)

**What it accomplishes:** the shared `IngredientForm` meets the two criteria it does not meet yet, for the coven dialog and the admin compendium dialog at once. Errors appear beside a field as soon as the person leaves it, not only on submit (story 31), and the save's result carries the jars that moved onto the new local, so Lane A has something to announce. It also makes sure the unsaved-changes prompt starts on the safe choice, Keep Editing. No new component and no schema change: a form option, three lines on a GraphQL document, codegen, and tests.

1. **Blur validation.** `useForm({ resolver, mode: 'onTouched', reValidateMode: 'onChange' })` (`IngredientForm/index.tsx:140`). `onTouched` validates a field the first time it is left and on every change after; before that, submit only. One caveat from the sources: Smashing says not to flag an _empty_ untouched field on blur, and `onTouched` would flag Name when a person tabs straight through it. Decision 3 picks between accepting that (standard, zero code) and a thin wrapper that skips the first blur of an empty field. Story 31's wording, "errors show beside their fields on leaving one and on submit", is met either way.
2. **Both tiers get it.** The form is shared, so the admin compendium form gains blur validation too. This is a feature, not a regression, but it is named in the PR body.
3. **Carried jars.** The `createWorkspaceIngredient` document (`index.tsx:77-96`) selects `jars { form quantityOnHand unit }` as well as `id name slug`. A brand-new local has no jars of its own, so whatever `jars` holds is what M12.8 moved. No schema change, no new field, `npm run codegen` regenerates `src/gql/`. `SavedIngredient` widens by derivation. The admin's `createCompendiumIngredient` document is left alone.
4. **Discard prompt focus.** Check `DiscardQuestion` puts initial focus on Keep Editing (APG: focus the least destructive action). If it already does, assert it; if not, fix it, since the question is shared with every modal.
5. Tests: `tests/components/IngredientForm/index.test.tsx` gains blur cases (a wrong value flagged on leaving; a fixed value cleared on change; untouched fields silent until submit), and a case that `onSaved` receives `jars`. The compendium test file gets one blur case so the admin tier is covered too.

## Decisions for the owner

1. **The Coven select: native `<select>` or `ComboboxSelect`?** Native is simplest and has a native disabled option; the switcher uses `ComboboxSelect`, so the two would look alike. The e2e helper was written for a combobox-with-listbox and says M8.16 may correct it. **Recommend native** — one control, no new component, and a disabled option needs no custom code.
2. **On an admin page: plain link, or open at once?** `RouteModalProvider` is mounted in `src/app/(shell)/admin/layout.tsx`, below the shell, so the shell's button cannot use `useOpenModalClick` and a press is a full navigation to `/admin/compendium?new` (which renders the dialog server-side, so it works). Moving the provider up into the shell layout lets the button open the skeleton at once like `AddAction` does. **Recommend the plain link for this task**; a later sub-hour fix moves the provider if the delay is felt.
3. **Blur validation: plain `onTouched`, or skip the first blur of an empty field?** GOV.UK says validate on submit only; Smashing says on blur but never an empty untouched field. **Recommend plain `onTouched`** — react-hook-form's standard mode, and the Name field is the only one a person is likely to tab past empty.
4. **Carried jars through `Ingredient.jars` on the mutation's return** (no schema change) rather than a new `carriedJars` field. **Recommend `jars`.**

## Review: DRY and UX in what exists

What the survey found, with a recommendation each. None of these is in M8.16's PR unless marked "rides along".

**DRY**

- **The four `RouteModal` wrappers** (`group-dialog.tsx` 42 lines, `value-dialog.tsx` 39, `compendium-dialog.tsx` 58, `user-dialog.tsx`) repeat `RouteModal closeHref content={opened && { heading, body: (done) => <Form key=… /> }}`. MB.115 already folded the eight originals into `RouteModal`; what remains is one call each. **Leave it** — a further helper would save under ten lines per file and hide which form each page opens.
- **`ShellWorkspace` and `SwitcherWorkspace`** are two near-identical types for one list. Lane A adds `id` and `canWrite` to `ShellWorkspace`; the switcher could take the same type. **Rides along** if the switcher's change is a type import only; otherwise a follow-up.
- **The Saved notice lives inside the form**, so any consumer that closes the form on save has to announce the save itself (Lane A4). M8.17's edit modal closes on save too, so it will meet the same gap. **Follow-up option:** the form takes an `announce` callback, or the notice moves to the caller — decide in M8.17, when there are two consumers.
- **The compendium mutation documents** are declared inside `IngredientForm/index.tsx` rather than beside the other `src/gql` documents. Fine as is; noting only that codegen picks them up there.

**UX, from the sources read** (NN/g "Modal & Nonmodal Dialogs"; WAI-ARIA APG "Modal Dialog"; Smashing "Inline validation in web forms" 2022; GOV.UK "Validation" and "Question pages"). Two points asked for — "Save & Add Another" conventions and destination selects inside a create dialog — have no authoritative source the researcher could find; what is said about them is judgement.

- **Modal vs page.** NN/g: a long multi-step task "probably justifies dedicating a full page". The ingredient form is at the upper edge; the entry page (M8.19) is the long-form home and the modal is the quick add. **No change**; keep the form's sections collapsed by default in the dialog, as they are.
- **Focus on open.** APG: first focusable element, or the title when the content is long enough to scroll it away. `Modal` focuses the first field. With the Coven select present, that is the select, which is right (it decides where the entry goes). **No change.**
- **Focus on close.** APG: return to the opener. `ModalButton` does this. **Asserted.**
- **Validation timing.** Hybrid (Smashing) as Lane B1; GOV.UK disagrees, and the entry already chose blur. **Decision 3.**
- **Error summary on submit.** GOV.UK puts a summary at the top and focuses it; the form instead focuses the first invalid field (`useFocusFirstInvalid`). For a form whose sections collapse, a summary that names fields hidden in a closed section would help. **Follow-up task candidate**, not this one.
- **Unsaved-changes prompt.** Labels are already "Discard Changes" / "Keep Editing"; APG says focus the least destructive action. **Lane B4 checks it.**
- **Save & Add Another.** Judgement, no source: keep the Coven select's value between adds (it is outside the form, so it already persists); announce the saved name (the form does); a running "added this session" list is a nicety the owner may want later. **No change** beyond what is built.
- **Required-field marking.** GOV.UK marks optional fields; the project marks required only (the owner's standing rule). Noted as a deliberate divergence, **no change**.

## Models and effort

Lanes A and B in parallel on Sonnet, from the one worktree on two short-lived branches or sequential commits (A touches `AppShell`, `viewer.ts`; B touches `IngredientForm`; no shared file). Lane C on Opus after both land. The main session reviews each lane's diff and test output, merges, and runs nothing itself beyond `git`. Estimate for the three lanes: within the entry's 4h of agent time; this plan took the two survey agents about 130k tokens.
