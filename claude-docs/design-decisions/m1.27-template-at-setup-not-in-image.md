# M1.27 — The seeded test template is built at test-run setup, not baked into the Postgres image

**Status:** decided · **Date:** 2026-09-19

TASKS.md specified M1.27 as "bake migrations and the standard seed into the
database image": extend M0.18's `Dockerfile.postgres` so `sorrel_template`
ships with the full schema and the `standard` scenario, closing the
dependency M0.18 left open and making M1.9's per-worker database a clone
rather than a setup routine. The story behind it — _no environment spends
time migrating or seeding before it can run a test_ — is what this task
delivers. The mechanism it names is not.

## Decided

**The template is built once per test run, at setup, from the checkout.**
`tests/support/seeded-database.ts` clones M0.18's extensions-only
`sorrel_template` into `sorrel_test_template`, spawns `npm run db:migrate`
and `SEED_SCENARIO=standard npm run db:seed` against it — the same two
scripts `Docker/docker-compose.yaml`'s `db-init` runs — and the Vitest
`globalSetup` clones one database per worker slot from that.
`tests/support/db-setup.ts` re-clones the slot's database from the template
before **every test file**. Playwright does the same with
`sorrel_e2e_template` → `sorrel_e2e`. `Dockerfile.postgres` is unchanged in
substance and its contents no longer depend on anything under `src/`.

## Why

The measurement, taken in the devcontainer against the compose `postgres`
service before deciding:

| Step                                         | Time    |
| -------------------------------------------- | ------- |
| `db:migrate`, 18 migrations                  | 0.54 s  |
| `db:seed` `standard`                         | 0.43 s  |
| Clone from the empty template                | 29 ms   |
| Clone from the migrated + seeded one (9 MB)  | 31 ms   |
| Re-clone with a lingering connection (FORCE) | ~120 ms |

So the entire cost the bake would have removed is **about one second, once
per run**, and cloning stays free whether or not the template carries data.
Against that, baking would have cost:

- **A Node toolchain inside the Postgres image build.** The seed is
  TypeScript and the migrator is `drizzle-kit`; `postgres:18` has neither. A
  builder stage with `npm ci` (hundreds of MB, minutes) to save one second.
- **A DB image rebuild on every migration PR**, since `src/db/**` would
  have to be in the build context as well as the tag hash.
- **A new class of bug: a stale template.** `docker-compose.yaml` builds the
  image locally and never rebuilds it on `up` — so after `git pull` brought a
  migration, every local test run would have used the old schema until
  someone remembered `make docker-rebuild`. A template built from the
  checkout at setup cannot disagree with the checkout.
- **Non-reproducibility masquerading as a criterion.** "Local and CI clones
  are byte-identical" was unachievable as written — `applyAudit` stamps
  `new Date()` on every seeded row, and local and CI would have baked at
  different times — and would have needed the seed's clock pinned. Built at
  setup, both run the same migrations and the same seed, which is the
  property the criterion was reaching for.
- **Unverifiable here.** `docker` is not in the devcontainer, so the image
  half of the task could only have been checked in CI.

The template primitive itself is right and stays: `CREATE DATABASE …
TEMPLATE` is a file-level copy, and it is what makes per-file re-cloning
affordable. Only what fills it, and when, moved.

## What this reworked

Every file under `tests/db/` had been written against an empty template and
built its own tables — stubbing parents to a bare `id`, applying one
migration's statements, dropping everything in `afterAll`, and carrying a
comment about not leaving `__drizzle_migrations` behind for the next file.
All twenty were reworked in M1.27's PR, because a template that carries the
schema breaks every one of them and a red intermediate state has nowhere to
hide on one branch: the schema dance is gone, invented parent ids are bound
to the seed's (`FIXTURE_USERS.A`, workspace W), `beforeEach` truncates
(`cascade`) rather than deletes, and the files that are _about_ seeding
truncate every table first. Three tests met a constraint from a migration
later than their table's own for the first time — a partial unique index on
identity per workspace, an ordering the old hand-picked ids had guaranteed —
and were given data that respects it, not a weaker assertion.

The task's revised size is recorded in its TASKS.md entry: what was estimated
at 2 h as an image change was ~6 h as a harness change plus that rework.

## Rules this sets

- **Nothing about the schema or the seed is ever baked into the Postgres
  image.** `Dockerfile.postgres` carries extensions and roles; `src/db/**` is
  not in its tag hash and must not return there.
- **The two npm scripts are the one path.** Compose's `db-init`, the Vitest
  harness and the Playwright harness all migrate and seed by running
  `db:migrate` and `db:seed`; a third mechanism (importing the migrator, a
  hand-rolled SQL applier) is a divergence, not a shortcut.
- **A db test file starts from the full schema and the `standard` scenario,
  and builds neither.** See the M1.27 amendment to
  [`m1.9-test-db-isolation.md`](m1.9-test-db-isolation.md) for the per-file
  rules that follow.
- **A later task that wants a different baseline** (`demo`, an empty
  schema) seeds on top or truncates within its own file. It does not ask
  the harness for a second template.
