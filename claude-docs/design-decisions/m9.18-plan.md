# Admin modals open at once, with a loading state

## Context

Today every admin Edit pencil and Add button is a plain `Link` to `?edit=<slug>` or `?new`. Nothing appears until the server has re-rendered the whole page, list and all, with the modal in it, so a press feels dead for the length of a round trip. The owner wants the modal to open the moment it is pressed, showing a loading state until its form arrives. That is the same shape as the filters (`ListFrame`) and the tabs (`TabSwitchProvider`): a soft navigation inside a `useTransition`, with a skeleton showing while it is pending.

The form's data still arrives with the navigation, from the server page's existing reads. That keeps CLAUDE.md rule 1 intact: a read that comes with a navigation belongs to the server component, so no new GraphQL queries are needed. A direct request to `?edit=` still renders on the server with the modal already open, and no skeleton.

**Scope (the owner's answers):** both Edit and Add, on the compendium and on every grouped-value and group page. Tracked as a newly minted **wave 9 task** (the next free `M9.n`, expected M9.18; re-check the board and `TASKS.md` first).

## Design

**One dialog from the press to the form.** The modal fades in through `@starting-style` when `showModal()` runs, so a loading dialog swapped for a separate server-rendered one would fade twice and could blank for a frame. Instead, each page renders its one `RouteModal` at a fixed place every time. It shows the skeleton while an opening is pending and the form once the page has the data. Because it is the same component at the same position, React keeps the same `<dialog>` element open throughout.

### 1. `RouteModalProvider`: the opening, held in a transition

New file `src/components/Modal/route-modal-provider.tsx` (client). It is modelled on `TabSwitchProvider` (`src/components/TabbedPage/tab-switch.tsx`), including keeping a provider already above it, as the workshop's is.

- State: `opening: { heading: ModalHeading } | undefined`, plus `useTransition`.
- `open(href, heading)`: sets `opening`, then `startTransition(() => router.push(href))`.
- `cancel()`: clears `opening`.
- It exposes `loading`, which is `opening` while the transition is pending and `undefined` otherwise.
- It is mounted once in `src/app/admin/layout.tsx`, around `AdminNav` and `children`, so the Add actions in the `@action` slots, the lists' Edit links and the page's modal all share it.
- A hook, `useRouteModalOpener()`, gives the links access; it returns `undefined` outside a provider, so a link there stays a plain link.

### 2. `RouteModal` becomes the page's modal place

Changes to `src/components/Modal/route-modal.tsx` and `types.ts`:

- `RouteModalProps` becomes `{ closeHref, size?, content?: { heading: ModalHeading; body: (done) => ReactNode } }`.
- It renders `content` when the page has it, the provider's `loading` heading over `<ModalLoading />` while an opening is pending, and `null` otherwise. Both branches render the same `<Modal>`, so the dialog stays mounted.
- Closing during loading calls `cancel()` and then the existing `router.replace(closeHref)` + `refresh()`. Next marks the pending push as discarded (`app-router-instance.js:149`), so the modal does not reopen when that push would have landed.
- A row that is gone (`missing`) lands with no `content`, so the dialog goes and `MissingNotice` shows, as now.

### 3. `Modal` learns `loading`

Changes to `src/components/Modal/modal.tsx`:

- A `loading?: boolean` prop sets `aria-busy` on the body.
- When `loading` turns false, the focus moves to the first field (`firstShownField`), but only if it is still on the dialog itself. While loading there is no field, so the focus starts on the dialog, which reads the dialog's name, and Tab reaches Close.

### 4. `ModalLoading`: the form's skeleton

New file `src/components/Modal/loading.tsx`, modelled on `TabbedPage/panel-loading.tsx`:

- A visually hidden `<output>Loading</output>` announces the loading state.
- `aria-hidden` placeholder shapes: four label-and-field pairs and a row of buttons.
- It reuses the tab skeleton's shimmer. If that shimmer is written inline in `TabbedPage/index.scss`, it is moved into a mixin, and both skeletons use the mixin.
- Reduced motion turns the shimmer off, as the tab skeleton already does.

### 5. Links that open through the provider

- **`EditLink`** (`src/components/IconTip/edit-link.tsx`) becomes a client component and takes a new `heading: ModalHeading` prop. A plain primary click calls `preventDefault()` and then `open(href, heading)`. A click with a modifier key or the middle button, a press made before the page's script has loaded, and a link outside a provider all keep the native link.
- **`AddAction`** moves out of the `server-only` `src/app/admin/list-page.tsx` into a client file (`src/app/admin/add-action.tsx`) and opens with `{ title: 'Add …' }` the same way. Its callers (`value-page.tsx`, `group-page.tsx`, `compendium/page.tsx`) pass the heading.
- **List entries** carry the edit heading that the server builds for each row. A field `editHeading: ModalHeading` is added beside `editHref` in `GroupedValueListEntry`, `GroupListEntry` and `CompendiumListEntry`. Each list passes it to `EditLink`, so the loading head matches the loaded one exactly, including a deity's tradition or a binomial set in italics.
- **Reuse the existing heading builders.** These are `editHeading` in `value-page.tsx` and in `compendium/page.tsx`; the compendium's is narrowed to `Pick<…, 'name' | 'canonicalName' | 'nomenclature'>` so the list row fits. The group pages' heading is `{ eyebrow: \`Edit ${label}\`, title: name }`, extracted to a small function the page and the rows share.

### 6. One modal per page

- **`ValuePage` and `GroupPage`.** Each folds its two conditional dialogs into one `ValueDialog` or `GroupDialog`, always rendered and given `content` for add, edit or neither. The `key` moves from the dialog onto the form inside it (`key={value?.id ?? 'new'}`), as the compendium already does, so a fresh form per row no longer remounts the dialog.
- **`CompendiumDialog`.** It is likewise always rendered, with `content` built from `adding`/`editing`.
- **`value-dialog.tsx`, `group-dialog.tsx` and `compendium/compendium-dialog.tsx`** take an optional `content` in place of their required props. Types are updated in `src/app/admin/types.ts` and `compendium/types.ts`.

## Tests (TDD, failing first)

Component tests go under `tests/components/`, using role and label queries and asserting state, never copy.

- **`RouteModal`** under a provider with a pending opening shows a `dialog` holding a `status`, and no form fields. When it is re-rendered with `content`, it is the **same dialog element** (`toBe`), the status is gone, and the first field has the focus.
- **Closing while loading** calls `cancel` and `router.replace(closeHref)`.
- **`EditLink` and `AddAction`:** a plain click calls `open` with the href and heading and prevents the default; a meta-click and a click outside a provider do not.
- **Existing tests:** the page tests in `tests/app/admin/**` that assert the dialogs' props are updated to the new `content` shape.

Playwright (`tests/e2e/`), with the spec tagged with the story it walks:

- On `/admin/categories`, `page.route` holds the RSC request for `?edit=`. Pressing Edit shows the dialog and its `status` while the request is held. Releasing it brings the form's Name field, which has the focus, and the URL carries `?edit=`.
- The same check runs for Add, and for the compendium's modal.
- Closing while the request is held leaves no dialog once it is released, and no `?edit=` in the URL.
- An axe check runs on the loading dialog.

## What the build changed

- **The compendium modal is not wide.** The plan's "wide modal" was a slip: `compendium-dialog.tsx` passes no `size` and never did, since MB.115 took the compendium back to the default column (`claude-docs/components/modal.md`, Styling).
- **Invite Admin was included.** The Invitations tab's Add opens its modal at once through the provider too: `InviteAdmin` uses it, and `InviteForm` takes `open: boolean` and is always rendered.
- **`AddAction` takes `heading` apart from its label.** The group pages label the button "Add Group" while the dialog says "Add Category Group", so one string could not serve both.
- **The minting docs rode in M9.15's PR**, as planned: the `M9.18` entry in `claude-docs/tasks/m9.md` and its row in `claude-docs/waves/wave-09.md`.
- **The links use `useOpenModalClick(href, heading)`**, which wraps `useRouteModalOpener()` with the plain-press check, so `EditLink`, `AddAction` and Invite Admin share one click handler.
- **The dialog wrappers take `opened`**, the heading and the row, rather than `content`; each builds `RouteModal`'s `content` from it.
- **The admin layout imports `RouteModalProvider` from `route-modal-provider.tsx`**, not the Modal index: the index re-exports modules a server component cannot import, which the production build refused.
- **The e2e spec checks `aria-busy` rather than the status's absence** once the form arrives, since a form's combobox holds a status of its own.
