# M2.9 — Granting and revoking admin

**Decided 2026-09-24.** Scoping only; nothing here is built. There are two
kinds of admin, both holding the same `role`:

- **The primary admin** is the account whose email matches
  `ADMIN_BOOTSTRAP_EMAIL`, promoted by a verified Google or Discord sign-in.
  It cannot be revoked or deleted by anyone, including itself. Changing who it
  is means changing the variable and redeploying.
- **Every other admin** is granted by an existing admin from MB.52's
  `/admin/users`, and any admin can revoke one.

Every change is appended to its own ledger. The work is four tasks, and four
new user stories (58–61) in DESIGN.md §10:

- MB.60 fixes the bootstrap promotion.
- MB.58 adds the ledger table.
- MB.59 adds granting and revoking.
- MB.61 scopes first-party email verification, which does not block the other
  three but changes several things around them (see "Email verification").

MB.58 and MB.59 are separate because CLAUDE.md puts a table and the service
that governs it in separate tasks.

## Where things stand

`users.role` is `user | admin`. The only thing that sets it is
`src/lib/auth.ts`'s sign-up hook, which promotes a new user whose email
matches `ADMIN_BOOTSTRAP_EMAIL`, compared case-insensitively. The seed's
bootstrap user is written straight to the database. Four properties of that
hook, all describing the code as it stands today and none of them kept, bound
what follows:

- **Today it runs on create only.** Changing the variable later promotes
  nobody who already has an account, so today the variable can name the first
  admin and nothing after that, and a second admin means an `UPDATE` in
  `psql`. After this decision a second admin is made by the first from
  `/admin/users`; the variable names only the primary admin.
- **It matches the email string and ignores `emailVerified`.** Discord maps
  `emailVerified` from `profile.verified`, and Facebook always reports `false`
  (`@better-auth/core/dist/social-providers/`). Until the real owner has an
  account, whoever first signs up carrying that address is made admin. That
  includes an address typed into MB.54's form. On a freshly reset database the
  gap opens again.
- **An unverified account squatting the address locks the real owner out.**
  Better Auth links a new provider to an existing user by email only if the
  existing row is verified (`accountLinking.requireLocalEmailVerified`
  defaults to `true`, `better-auth/dist/oauth2/link-account.mjs`). So once an
  unverified account holds the address, the owner's verified Google sign-in is
  refused with `account_not_linked`, and nobody is ever promoted. This is a
  denial of the primary admin, not just a wrong promotion. MB.60 fixes the
  promotion; the squat waits for MB.61 (see "What is simplified").
- **`role` is read on every request.** M2.7's `getSession` asks Better Auth,
  which reads the `users` row, and `session.cookieCache` is not configured. A
  revocation therefore takes effect on the revoked admin's next request.
  Turning the cookie cache on would open a window as long as its TTL, so MB.59
  pins the current behaviour with a test.

## The approaches

### A. An admin grants admin, from the user list

This is a `setUserRole(userId, role)` service behind an admin-only GraphQL
mutation, with a control on each row of `/admin/users`. It sits beside M5.8's
approval control and has the same shape.

- **Failure: one compromised admin mints more admins.** An attacker holding an
  admin's OAuth account can promote a second account they control, and that
  second account survives revoking the first. Nobody else approves the grant.
  The ledger makes it visible after the fact; it does not prevent it.
- **Failure: admins can remove each other.** Any admin can revoke any other,
  except the primary admin, who therefore can always undo the damage.
- **Failure: a mis-click.** The control sits on a list M5.8 also acts on, so
  the grant needs a confirmation that names the user. It must not be a checkbox
  next to "may create a workspace".
- **Cost:** it reuses surfaces that are already scheduled: MB.52's list,
  M5.7's two-layer admin gate, and M3.6's pagination.

### B. An invitation to become admin

An admin generates a single-use link, and whoever accepts it is promoted.

- **Failure: the link is a bearer token for the site's highest privilege.**
  Anyone who sees it can use it: in a chat history, a forwarded email, or a
  screenshot. Workspace invitations accept that risk because the worst case is
  one coven's data. Here the worst case is every global vocabulary. Binding
  acceptance to an email fixes the leak, but it depends on the provider's
  verification, the same problem MB.60 fixes.
- **Failure: it cannot reuse what exists.** `workspace_invitations` is scoped
  to a workspace, and a check constraint rejects every role but `viewer` and
  `member`. B would need its own table, token hashing, expiry and revocation,
  plus an acceptance route: a second invitation system for about three people.
- **What it would buy:** the grantee opts in, and someone can be promoted
  before they have signed in. Under A they sign in first and then appear in the
  list, which costs nothing in practice.

**Resolved: B is built once email verification exists.** The invitation
names an address, the link is mailed to it, and acceptance requires a
signed-in account whose verified email matches, which removes the
bearer-token failure. MB.61's follow-ups mint the task, since it needs the
delivery MB.61 chooses (story 62).

### C. A break-glass command

An `npm run admin:grant -- --email …` script runs against a database URL. In
deployment it would run through a `workflow_dispatch` job like `migrate.yml`.

- **Failure: it is a third identity bootstrap.** CLAUDE.md rule 3 allows
  exactly two writes outside `withAudit`. A script has no session. The real
  actor would be recorded only in the workflow run, which the database never
  sees.
- **Failure: whoever can run it is effectively an admin.** That is already
  true of `psql`. The script makes that power documented and easy.
- **Failure: it is the everyday path in disguise.** If it is the only way to
  grant admin, every grant is a CI run: the friction the story removes, made
  slightly shorter.
- **What it would have bought:** recovery when no admin can sign in. The
  primary admin now covers that case (see "The primary admin").

### D. More of the env var (not pursued)

This means a list in `ADMIN_BOOTSTRAP_EMAILS`, one variable per admin. Every
admin would be a redeploy, which the story rules out.

### E. Better Auth's `admin` plugin, `set-role` (rejected)

`/api/auth/admin/set-role` writes through the adapter, so it is outside
`withAudit` (rule 3). It is also a browser-initiated mutation outside
`/api/graphql` (rule 1). MB.52 turned down the plugin's `listUsers` for the
same reason.

**This binds MB.53.** MB.53 registers the plugin outside production for
impersonation. That also mounts `set-role`, `update-user`, `remove-user` and
the rest. On staging and previews this would be a second grant path: it would
skip the ledger, and `remove-user` could hard-delete the primary admin.
MB.53 is therefore scoped so that only `impersonate-user` and
`stop-impersonating` are reachable. Its test checks the mounted endpoints
against those two names, so an endpoint added by an upgrade fails the test.
`allowImpersonatingAdmins` stays at its default, off.

## Decision

A is the everyday path now, B follows email verification (below), and C is
not built. A wins because the
surfaces it needs are already scheduled, and because its main failure, a
compromised admin minting another, is no better under B or C. Every option
lets someone holding an admin session act as that admin. Two things limit the
damage:

- admin is a narrow role, with no workspace access (DESIGN.md §5, asserted by
  M6.6);
- the primary admin is out of reach, so they can always revoke whoever was
  wrongly made admin.

The ledger is what brings misuse to light.

**The trust root is the variable.** Whoever can set `ADMIN_BOOTSTRAP_EMAIL`
on the Vercel project chooses the primary admin. That is already true of
`DATABASE_URL`, which grants everything; this adds no new power.

## The primary admin

**Who it is.** The live admin whose email matches `ADMIN_BOOTSTRAP_EMAIL`,
compared case-insensitively. It is read from the variable at the time of each
check, not stored on the row. So the protection always follows whatever the
variable currently names, and changing it needs no migration and no data fix.
Better Auth lowercases every email it writes and looks up, so at most one live
row can match; MB.60's test asserts that, since the partial unique index is on
the raw column and a hand-inserted mixed-case row would otherwise make two.

**How it becomes admin (MB.60).**

- **Promotion happens at sign-in, not only when the account is created.**
  After every OAuth callback, a user whose email matches, who is still `user`,
  and whose sign-in just came through a provider that vouches for the address
  is promoted.
- **Only Google and Discord vouch for an address.** Google marks an email
  verified only for a domain its owner has proved to Google, and Discord only
  for an address it has mailed a code to. Facebook never reports an address as
  verified in Better Auth's mapping, so it can never promote. Microsoft is
  excluded deliberately: with `tenantId: 'common'`, an attacker's own Entra
  tenant can issue an id token carrying any `email`, and Better Auth reads
  `email_verified` and the `verified_*_email` claims off that token
  (`microsoft-entra-id.mjs`). Those claims are meant to be Microsoft's own,
  but this is the surface the 2023 "nOAuth" attack used, and the safe default
  is not to rely on it. The decision is made on the provider's fresh profile at
  the callback, not on the stored `users.emailVerified`, so a later feature
  that sets that column (MB.61) cannot widen who qualifies.
- **The address can still be squatted until MB.61's follow-ups land.**
  Refusing to create an account holding the address unverified would close it
  today, and was in MB.60's first draft; it came out because first-party
  verification settles squatting for every address, not one, and lands before
  launch. What that leaves open is stated under "What is simplified".
- **A non-qualifying match** (Microsoft, Facebook, or a Google/Discord
  profile arriving unverified) on an existing account signs in as an ordinary
  user. The reason goes to the server log, with the user id and not the
  address, because a sign-in screen should not reveal that an address is
  special.
- **Verification is required here and only here.** A grant through A does not
  check it. What the granting admin is trusting is the OAuth account behind the
  row, not the address on it, so `/admin/users` shows each user's linked
  providers and whether the email is verified (MB.52), and confirming who
  someone is before granting them admin is the granting admin's job.
- **One address is one account, and that account can be both.** Site admin is
  a column on the account; workspace roles are rows in `workspace_members`,
  and the two are independent (DESIGN.md §5). So the same account can be a
  site admin and an owner, member or viewer of any number of workspaces at
  once. What admin never does is add workspace access: an admin who is also a
  member reads and writes that workspace as the member they are, and nothing
  else. `users_email_unique` holds one live row per email and Better Auth
  lowercases on every write and lookup, so an address cannot have two
  accounts, one admin and one not; it has one account that several providers
  can be linked to, verified or not as a whole. Better Auth marks the row
  verified the first time a verified provider links to it.

**It costs nothing per request.** The check runs in Better Auth's
after-callback hook, where `ctx.context.newSession.user` is already loaded.
That makes it one comparison per sign-in and no query. Sessions last days, so
it runs a few times per user per week. It writes only on the one sign-in that
promotes. Better Auth's session-create hook would be the other place to put
it, but it receives only a `userId`, so it would cost one extra lookup per
sign-in.

**The promotion writes through `withAudit`, with no new exemption.** At the
callback the user is authenticated, so the hook builds an ordinary `Session`
from the row it already holds and calls the same service MB.59 builds, stamped
as the user. CLAUDE.md rule 3's two identity bootstraps stay two; the
create-time promotion that used one of them goes away.

**It cannot be revoked or deleted, by anyone, including itself.**

- **The service** refuses with an explaining `Forbidden`.
- **On `/admin/users`** the row carries a "Primary admin" label. The revoke
  control stays visible but `aria-disabled`, with the reason written beside it
  in plain language, naming no variable: _"This is the primary admin and can't
  be removed. Changing who the primary admin is takes a change to the site's
  configuration."_ A user who tries anyway is told the same thing. The service
  refusal carries the same wording. How to make that change (the variable and
  the redeploy) lives in `auth.md`, not in the UI. "Owner" is not used, because
  it is already a workspace role.
- **Future deletion paths:** v1 has no path that deletes a user. Any path
  added later that soft-deletes a `users` row must refuse the primary admin
  too.

**Changing the variable demotes the old primary admin to an ordinary admin
and does not revoke them.** They keep `role: 'admin'`. Because protection
follows the variable, they simply become revocable like any other admin. The
new address is promoted, and becomes the protected admin, at its first
qualifying sign-in. This is also the recovery path if the primary admin loses
their OAuth account.

**The last admin is normally the primary admin, and a count guards the rest.**
While the primary admin exists, revoking any other admin always succeeds and
cannot leave zero admins. But between changing the variable and the new
address's first qualifying sign-in, nobody is protected, and if the new
address can only sign in through Microsoft or Facebook, nobody ever will be.
So the revoke service also refuses, with an explaining `Forbidden`, any change
that would leave zero live admins. It locks the live admin rows `for update`
before counting, so two admins revoking each other at the same moment cannot
both succeed. The count is a fallback: with the primary admin in place it is
never reached, and MB.59's test proves that by removing the primary admin from
the fixture.

**A deployed environment refuses to start without the variable.** Everything
above holds only while it is set, so MB.60 makes the app refuse to start
without it in production, staging and every hotfix preview. The check keys on
`NODE_ENV=production`, as `BETTER_AUTH_SECRET`'s does, and not on
`VERCEL_ENV`. `next build` and `next start` always run at
`NODE_ENV=production`, so this single condition covers all three deploy
targets. It also covers CI's `build` leg and the Playwright runs, which set a
fixed placeholder on the reserved `.invalid` domain, the same way they set
`BETTER_AUTH_SECRET`. `next dev` and Vitest are exempt, and an unset variable
there promotes nobody.

**Three Better Auth options stay off, pinned by test**, because each would let
the local email change under the primary admin and move the protection to
someone else:

- `user.changeEmail.enabled` (default off; `update-user` already rejects
  `email`). It stays off for good: MB.54's verified flow is how an email
  changes.
- `overrideUserInfoOnSignIn` on every provider (default off; on, a sign-in
  rewrites the local email from the provider's profile).
- `accountLinking.trustedProviders` (default empty; a trusted provider skips
  the verification check when linking).

**The seed's bootstrap user is not an admin.** Every seed, including the
category and form seed that runs on staging and production, needs a creator
row, because every `created_by` is `NOT NULL` and references `users.id`. That
row (`admin@seed.sorrelandsalt.com`) cannot be removed, but nothing needs it to
be an admin: no OAuth account is attached, it is unverified, so linking to it
is refused, and nobody can sign in as it. MB.58 demotes it to `role: 'user'`
as a named rider, so it neither appears on `/admin/users` as a revocable admin
nor gets a ledger row. `minimal` becomes one system user and one user.

## Granting

- An admin may grant admin to any live user, verified or not. Granting to an
  existing admin is refused with a message and writes no ledger row.
- The grantee must already have an account. There is no promotion in advance
  by email; that would be B.
- Admin carries no workspace access and implies no membership, so a grant
  never touches `workspace_members`. Memberships the person already holds are
  untouched too; they go on being a member where they were a member.
- **Admin changes can be paused (MB.62, MB.63).** The primary admin can
  switch granting and revoking off for every other admin, so a rogue admin
  can neither mint admins nor remove the good ones while the switch is on.
  The primary admin itself is exempt, so it can clean up without unpausing;
  the exemption protects nothing a rogue admin could reach, since the
  primary admin is set by the variable and cannot be revoked. The switch is
  a one-row `site_settings` table, since a variable would need a redeploy
  to flip and a column on the primary admin's own row would move with the
  variable. Only the primary admin may flip it, the flip is audited on the
  row, and a change refused while paused says so and names no one.
- Granting admin also sets `canCreateWorkspace` to `true`. Admins may create
  workspaces regardless of the flag (DESIGN.md §5), so the flag is not what
  lets them; it is set so the row states what the person may do without a
  reader knowing that rule. Revoking admin leaves it, as revoking the flag
  itself leaves existing workspaces (M5.8).

## Revoking

- Any admin may revoke any admin except the primary admin, including
  themselves. There is no hierarchy beyond the primary admin.
- A revoke that would leave zero live admins is refused (see above).
- Revoking does not delete anything the admin wrote. Rows are stamped with a
  person, not a role.
- The revoked user's next request sees `role: 'user'`. Their sessions stay
  valid, since they are still a user; only `/admin` and the admin mutations
  close to them.
- `canCreateWorkspace` is not cleared; the grant was a vouching too.

## What the audit trail records

`users.updated_by` and `updated_at` are not enough, because the next update to
the row overwrites them. M5.8's approval control is the first such update. So
each change to `role` appends a row to `admin_role_changes`:

| Column             | Records                                                          |
| ------------------ | ---------------------------------------------------------------- |
| `user_id`          | The user whose role changed                                      |
| `change`           | `bootstrap`, `grant` or `revoke`                                 |
| `note`             | Optional free text                                               |
| `created_by`       | Who made the change, from the session, never the request body    |
| `created_at`       | When                                                             |
| rest of the spread | Carried like every table; nothing in v1 updates or deletes a row |

- **Append-only by the repository, not by grant.** `sorrel` owns its tables,
  so a `REVOKE UPDATE` would not bind it. The repository exposes an insert and
  a read, and nothing else.
- **`bootstrap` rows** are written by the sign-in promotion (MB.59 adds this
  to MB.60's hook), through the same service and `withAudit`, stamped as the
  promoted user. The `standard` seed writes one for fixture E, and MB.58's
  migration backfills one for each existing admin.
- **This is not the v2 edit history.** Edit history records every column of
  every content table. This ledger records a single privilege, and it would
  stay the readable account of why even once the v2 trigger records that
  `role` changed.
- **Readable by admins only**, on `/admin/users`, through a service that
  asserts admin.

## Email verification (MB.61)

First-party verification is coming before launch, and it changes enough
around this decision that the decision was re-cut for it. Today an address is
verified only if a provider says so, and only Google and Discord say so in a
way that can be trusted. Mailing a link the user follows would let us vouch for
the address instead. What that simplifies:

- **The primary admin** could sign in through any provider, since we would
  vouch for the address rather than the provider.
- **Squatting** closes for every user, not only the bootstrap address. An
  account created with an unverified address, including one typed into MB.54's
  form, proves it or does not block the owner's sign-in. MB.61 decides which:
  verification before the account exists, or an unverified account that a
  verified sign-in may claim.
- **MB.54 becomes the email flow.** The provider's address is prefilled and
  editable, and takes effect once verified; reached again later, the same flow
  is how a user changes their email (story 59). So there is no separate
  change-email task, and Better Auth's `changeEmail` stays pinned off.
- **Invitations go by email.** The link is mailed to the invited address and
  accepted only by an account whose verified email matches it; nothing is
  shown to copy. This is decided now, for M7 and story 4, and MB.61's
  follow-ups rewrite M7.3–M7.5 and §7's `InvitationResult` before Wave 10
  opens. Copy-link stands until then.
- **Option B is built.** An admin invitation by email is bound to a verified
  address rather than to whoever holds a link, which was B's failure: the
  invitation names an address, the link is mailed to it, and only a signed-in
  account whose verified email matches can accept. Accepting is a grant, so it
  writes the ledger row, sets `canCreateWorkspace`, and is refused while
  changes are paused; creating one is refused for a non-primary admin while
  paused. The token is single-use, expiring, revocable and stored hashed, like
  a workspace invitation's. MB.61's follow-ups mint the task, since it needs
  the delivery MB.61 chooses; it is the way to promote someone who has not
  signed in yet, which A cannot do (story 62).
- **Notifying admins of a grant** becomes possible.

It needs email delivery, which v1 has none of. Several providers have a free
tier sized well past what this site would send (a few mails a week), and one
of them, Resend, is on the Vercel Marketplace. So MB.61 is a **scoping task in
M2.9's own shape**: it does the discovery, weighs the free tiers against what
the site actually sends, checks Better Auth's own `emailVerification` hooks
against the rules here (rule 1's transport boundary, rule 3's audit, and that
the verification token is stored hashed like an invitation's), and ends with a
decision doc and follow-up tasks ready to schedule. It writes no code.

## What is simplified, and the hole it leaves

Because verification lands before launch, MB.60 is cut to what only it can do:
promotion at sign-in, Google or Discord only, the startup refusal, the pinned
options, and the count fallback in MB.59. Two things came out of its first
draft and go to MB.61's follow-ups instead: refusing to create an account that
holds the bootstrap address unverified, and mapping the `account_not_linked`
code a refused link redirects to. MB.54, the easy way to squat, now follows
MB.61.

**The hole until then:** an unverified Discord or Facebook sign-up carrying
the bootstrap address, made before the owner's first sign-in or after a
database reset, blocks the owner's verified sign-in with a generic error, and
nobody is promoted. It is recoverable by hand (`psql`), and pre-launch the site
has no such users. The Google-or-Discord rule stays because it is a few lines
and the Microsoft exposure is real either way.

## Out of scope

- **Approving a second admin (two-person grants).** Worth revisiting once
  admins are no longer people who know each other.
- **Notifying existing admins of a grant.** There is no email delivery in v1;
  MB.61 may change that.
- **M5.8's `canCreateWorkspace` provenance** has the same overwrite problem.
  That is M5.8's question.
- **Squatting other users' addresses**, for the same reason as the primary
  admin's: an unverified account holding someone's email locks that person's
  verified sign-in out. MB.61 decides how it is resolved, for every address.

MB.58 through MB.63, written into `TASKS.md` with their acceptance criteria,
and stories 58–62 in DESIGN.md §10 (58 and 59 for MB.61's follow-ups and
MB.54, 60 and 61 for MB.59, 62 for the admin invitation MB.61's follow-ups
mint; story 4 reworded for email invitations).

- **MB.60** is live the moment MB.12 sets `ADMIN_BOOTSTRAP_EMAIL` in a
  deployed environment, so it lands in Wave 6 before MB.12. It writes no ledger
  row, since the table does not exist yet; MB.59 adds that.
- **MB.61** lands in Wave 6 before MB.54, which waits for its follow-ups.
- **MB.58 and MB.59** need MB.52's list, M5.7's admin gate and the GraphQL
  layer, so they go in Wave 8 after M5.8.
- **MB.62 and MB.63**, the pause switch's table and behaviour, follow MB.59 in
  Wave 8. Two tasks because CLAUDE.md puts a table and the service that
  governs it in separate tasks; the table is the first `site_settings` row in
  the schema, so it is worth landing alone. Two rejected shapes: an
  `ADMIN_GRANTS_PAUSED` variable, because flipping it would be a redeploy, the
  friction this whole decision exists to remove; and "only the primary admin
  may grant", which needs no switch but makes the primary admin the only
  grantor for good.
