# M0.18 — build and publish the base Postgres image to GHCR

**Status:** decided · **Date:** 2026-09-09

The task: one Postgres 17 image, built by CI and published to GHCR, that
every environment — CI's `services:` block (M0.19), docker-compose
(M0.13/M0.19), and eventually Vitest's per-worker template clone — starts
from. `resume-2026` has no database at all (`m0.13-postgres-service.md`
already established that), so unlike the other M0 CI tasks this one has
nothing to port from. `DESIGN.md` names exactly one extension (`pg_trgm`,
§5's fuzzy duplicate warning) and no schema exists yet (`src/db/schema` is
still `.gitkeep`-only) — M1.27 is the task that bakes migrations and the
seed into this same image, once there's something to bake.

## Decided

- **A new `Docker/Dockerfile.postgres`, `FROM postgres:17`**, matching the
  major version DESIGN.md §11 pins and the plain `postgres:17` this replaces
  in `docker-compose.yaml` (that replacement is M0.19's job, not this one's —
  this task only has to make the image exist and publish correctly).
- **Extensions and the empty `sorrel_template` database are created by
  running the official image's own first-boot initialization
  (`docker-entrypoint.sh`) during the `docker build`, not by leaving a
  `docker-entrypoint-initdb.d/*.sql` script for a container's first start.**
  "Enabled at build time, not at container start" is the acceptance
  criterion verbatim, and it matters for real: `docker-entrypoint-initdb.d`
  only runs the first time a container starts against an _empty_ volume — on
  `docker-compose.yaml`'s named `postgres_data` volume that means the first
  `make docker-up` after a fresh clone pays initdb + extension setup, not
  image pull. Baking it into the image instead means Docker populates a
  fresh, empty named volume straight from the image's `PGDATA` the first
  time one is mounted over it (verified against `docker-library/postgres`'s
  own `docker-entrypoint.sh` source at
  `repos/docker-library/postgres/contents/17/bookworm/docker-entrypoint.sh` —
  its `_main` already does exactly initdb → temp server → run
  `/docker-entrypoint-initdb.d/*` → stop server → `exec "$@"`, so the only
  thing needed is to run that flow during `docker build` and stop it before
  the final `exec` into a foreground server, which would otherwise hang the
  `RUN` step forever).
- **The `exec "$@"` neutering is a `sed` round-trip in one `RUN`,** not a
  patched/vendored copy of `docker-entrypoint.sh`: disable the exact final
  line, run `docker-entrypoint.sh postgres` (which now returns instead of
  hanging), restore the line, then `grep` for it as a build-time assertion —
  if the restore ever silently fails to match (e.g. a future `postgres`
  base image reformats that line), the build fails loudly instead of
  shipping an image whose containers can never actually start postgres.
  This is the same technique the official image's own docs point to for
  "preloading a database" and that images like `postgis/postgis` use.
- **`Docker/postgres-init/enable-extensions.sql` holds exactly one
  statement, `CREATE EXTENSION IF NOT EXISTS pg_trgm`.** Nothing else is
  named anywhere in the design — CLAUDE.md's own "no density table exists
  anywhere in the codebase" caution about not inventing unrequested data
  applies just as much to inventing unrequested extensions.
- **The workflow tags the image with a hash of everything that determines
  its contents — `src/db/**`, `Docker/Dockerfile.postgres`, and
  `Docker/postgres-init/**` — via `hashFiles()`, plus `latest`.** Content
  addressing makes "tag changes when src/db changes and does not when it
  does not" true by construction rather than something to separately check,
  and it means the tag is branch-agnostic: a PR branch and `staging`
  producing identical `src/db` content get the identical tag and the
  identical image, so building on `pull_request` is reuse, not throwaway
  work.
- **The same path list gates the workflow's trigger.** "Rebuild is skipped
  for PRs that do not touch `src/db`" is read as the workflow never running
  for such a PR, not as a job that runs and no-ops — matching every other
  path-filtered check ported so far (`build-audit-check.yml`,
  `lint-format-typecheck-check.yml`).
- **`latest` only moves on `push` to `staging` or `main`,** never from a
  `pull_request` build. The hash tag is safe to publish from any branch
  (it's content-addressed, so it can never point at the wrong content), but
  `latest` is the floating tag other workflows will default to once M0.19
  wires it up, and a PR's WIP content should never be able to repoint it.
- **No "does this tag already exist" check before building.** Unnecessary:
  the tag is a hash of exactly the paths the trigger filters on, so a run
  only ever fires when that hash is about to change anyway. `docker/
build-push-action`'s own GHA cache (`cache-from`/`cache-to: type=gha`) keeps
  a same-content rebuild (e.g. a manual `workflow_dispatch`) fast without an
  extra existence check to maintain.
- **No `checkout-to-app`.** This job runs `docker buildx` directly against
  the checkout on the bare `ubuntu-latest` runner — it never runs code
  inside the `testing` container image the way `lint`/`format`/`typecheck`/
  `build`/`audit` do — matching `build-audit-check.yml`'s own `build-image`
  job, which does the same plain `actions/checkout@v7`.

## Verified

- `npx js-yaml .github/workflows/build-db-image.yml` parses with no errors.
- `docker-library/postgres`'s `17/bookworm/docker-entrypoint.sh`, fetched via
  `gh api`, confirmed the exact target line (`\texec "$@"` — one leading tab,
  appearing exactly once in the file, at the true end of `_main`) that the
  `sed` pair disables and restores.
- **Not verifiable pre-push:** the actual `docker build`/`buildx` run and the
  image it produces — this sandbox has no `docker` daemon. Opening the PR
  (path-filtered on `Docker/Dockerfile.postgres`, `Docker/postgres-init/**`,
  and this workflow) triggers `build-db-image.yml` for real, which is the
  first thing that can confirm the image builds, publishes, and that a
  container started from it already has `pg_trgm` in `sorrel_template`
  without running any init step.

## Rules this sets

- **M0.19** replaces `docker-compose.yaml`'s `image: postgres:17` and the
  future CI `services:` block's tag with this workflow's `latest` (or a
  pinned hash) tag, from one shared place, and caches the pull between jobs.
- **M1.27** extends `Docker/Dockerfile.postgres` (or adds a script run in the
  same build-time-init step) to also apply migrations and the `standard`
  seed scenario into `sorrel_template`, once `src/db/schema` has content.
- Any future extension the schema actually needs goes into
  `Docker/postgres-init/enable-extensions.sql`, named in DESIGN.md first —
  not added speculatively here.
