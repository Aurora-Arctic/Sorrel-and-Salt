# M9.19 — Admin user modal, with the user's covens and Impersonate

## Context

The owner wants a site admin to see which covens a user owns or belongs to. Today nothing shows it, and the code refuses it on purpose:

- `membershipsOf(session, userIds)` in `src/modules/coven/services/memberships.ts` answers a `Forbidden` for any id but the caller's own, "a site admin included, since an admin reaches no workspace". `tests/modules/coven/services/memberships.test.ts` pins that refusal ("refuses a site admin asking after anyone else").
- `User.memberships` in GraphQL resolves through that service, so an admin's `users { … memberships }` fails too (DESIGN.md §7, line 1071: "the caller's own only").
- Story 19 (DESIGN.md §10, line 1314) reads "As an admin, have no special access to any workspace's private data", and `claude-docs/auth/admin-users.md` lines 11–15 say `/admin/users` "reads nothing below `users` and `accounts`".

**The owner's decisions (2026-10-12, this session):**

1. **A modal over `/admin/users`, not a page.** The user's name in the list opens `?user=<id>` over the list, at once with a skeleton, the way every other admin list's Edit does since M9.18. Heading: eyebrow "User", title the name, qualifier the email. Body: a Covens table and, where impersonation is registered and the user is not an admin, Impersonate. (A separate `/admin/users/[id]` page was the first choice and was dropped for this.)
2. **Story 19 narrowed, recorded as a design decision.** "Private data" becomes a workspace's contents (its ingredients, grimoire and members page). Which covens a user holds, and with what role, is admin-readable, read-only. An admin still reaches no coven: the modal links to no `/coven/[slug]` (a 404 to a non-member), and the service hands over a workspace's `id`, `name` and `slug` and nothing beneath.
3. **Stacked on M9.18.** The modal uses M9.18's `RouteModal` (`content` prop, one modal place per page) and `useOpenModalClick` (a press opens the modal at once). M9.18 sits unmerged in `/home/node/worktrees/m9.18`, branch `feature/m9.18-admin-modals-open-at-once`, two commits, no PR yet. This task branches off that branch; its PR targets `staging` once M9.18 has merged, or M9.18's branch if it is still open. M9.18 touched neither the users page nor `UserList`, so there is nothing to merge by hand.

**Minted as M9.19** (next free id in `claude-docs/tasks/m9.md`; M9.18 is the last, M9.13 retired). Re-check with `node scripts/task-board.mjs find M9.19` right before minting. Estimate **4h**. Wave 9, right after M9.18 in the execution order, which it depends on.

**Where the work happens:** a worktree, since `/app` holds M9.15's uncommitted work: `/home/node/worktrees/m9.19-admin-user-covens`, branch `feature/m9.19-admin-user-modal-covens`, off `feature/m9.18-admin-modals-open-at-once`. Nothing in `/app` or in M9.18's worktree is touched.

## Scope

### 1. The service: a site admin may ask after anyone

`src/modules/coven/services/memberships.ts`, `membershipsOf`:

- A key is permitted when it is the caller's own **or the caller is a site admin**, read as `session.role === 'admin'`, the same read `identity`'s internal `isSiteAdmin` makes (`src/modules/identity/services/admin-changes.ts`; not exported, and `coven` imports only `@/modules/identity`'s index). Anyone else's key is still a `Forbidden` in its slot. Still two queries whatever the batch size; `findMembershipsOfUsers` already excludes soft-deleted memberships and workspaces.
- Rewrite the doc comment: a user lists their own; a site admin lists anyone's, by name and role only, and reaches none of them (decision record below). Same for the comment beside `User.memberships` in `src/modules/coven/graphql/workspace.ts`.

Tests, `tests/modules/coven/services/memberships.test.ts`:

- Replace "refuses a site admin asking after anyone else" with **"answers a site admin asking after anyone, each with its workspace"**: keep its preconditions (E's role is `admin`; D holds a membership in X that D's own call finds) and add the one that matters now, that E is **not** a member of X (`assertMembership(asUser(E), WORKSPACE_X_ID, …)` throws `Forbidden`). Answer: `[{ role: 'member', workspaceId: WORKSPACE_X_ID }]` with `workspace.name` and `slug` present. Add a mixed batch `[D.id, E.id]` for E: both answered, E's empty.
- Keep "refuses another member's key in its own slot" (A asking after B): the admin branch is the only widening.

Unchanged: the loader test (`tests/modules/coven/loaders/memberships-by-user.test.ts`, A asking after B) and `tests/db/impersonation.test.ts` (E asking after E).

GraphQL: no SDL change (the field carries no description), so no `codegen`. One case in `tests/modules/identity/graphql/users.test.ts`: E's `users { edges { node { memberships { role workspace { name } } } } }` resolves a listed user's memberships through the `membershipsByUser` loader.

Story 19's suite, `tests/db/workspace-isolation.test.ts`: one `it` pairing the two halves of the narrowed story: E reads D's memberships (name and role of X) **and** is still refused X's ingredients by direct id, in the same test, so it fails if either half changes.

### 3. The component: `UserDetail`

To keep one wording and one send, move the list button's question, refusal sentence, landing and send into `src/components/UserList/impersonation.ts` and have `impersonate-button.tsx` and this component both import them.
