# M15.82 — What One Keystroke in Compendium Search Costs

Production build, `/compendium`, a remote Chromium with the CPU throttled to 4x and 6x, one key at a time (a Chromium trace with invalidation tracking, plus a log of every DOM change).

## What the trace showed

- **The browser redoes style for the page on every key, and the cost is `:has()`.** Many rules in the stylesheet read `:has(...)` over a changing subtree, such as the radio segment and radio card rules (`:has(input:checked)`) and the shell's `.app-shell__main:has(...)` rules. The trace tags the ancestors and siblings of each DOM change "Affected by :has()", so each change re-checks every such rule above it. With the page's `:has` rules removed, the style total for one key at 6x and 1280 px fell from about 220 ms to about 16 ms. The cost is not the sum of single rules: removing one rule at a time showed no clear winner, so the fix cuts the DOM changes, not the rules.
- **Source of the page changes outside the card list and the dropdown:** the facet panel. `PanelFacets` read the typed text through a React context that changes on every key, so it redrew the whole panel on every key. React then rewrote `name` and `type` on every radio and checkbox, with the same values. Writing a radio's `name` makes the browser re-check its radio group and `:checked`, which is what the `:has(input:checked)` rules watch. The writes changed nothing a user sees or hears.
- The search box's own Combobox also rewrites `name` (22 writes over four keys on the search input, 4 on each of the others), `aria-busy` and the option ids. These alter nothing visible or audible. They were not removed (see below).
- The Combobox's position code (Floating UI) reads computed style while placing the list, which forces a style flush of about 20 to 25 ms at 6x each time the list is mounted or re-subscribed. Not changed (see below).

## A fix tried and dropped

The typed text was moved from a context value into a small store in `IngredientSearch/form.tsx`, read through `useSyncExternalStore`, so the facet panel asked for it only while its facets differed from the filter shown. A component test proved a keystroke then wrote nothing to the panel's radios and checkboxes.

A second measurement on a quiet machine (every pass started under a load average of 2.0, two passes each, 40 keystrokes per figure) showed no gain. At 6x, fast typing took 32 ms before and 24 ms after at 390 px, one 8 ms step of Event Timing, and 56 ms before and 64 ms after at 1280 px. The first measurement's gain came mostly from the higher machine load during its before run. The owner dropped the change on 2026-11-07, and the task stays open.

The trace's other finding led to M15.83: the shared Combobox's attribute rewrites and Floating UI's style reads, which M15.83 removed.

## Not done

- Changing or scoping the `:has()` rules. Scoping the `.app-shell__main:has(.app-shell__pause)` rules to a class on the shell was tried and gave no measured gain, so it was reverted.
