# M11.18 — Faster Playwright runs on the same CPU and RAM

_The plan as approved on 2026-10-13, kept beside the decision records; M11.18 is the task that carries it out, one lever per PR._

## Context

The owner asked how to make the e2e suite faster without more cores or memory. The devcontainer has 12 cores and 32 GB, fixed; CI is GitHub's 4-vCPU runner. This plan is the answer: what the last run measured, where its time goes, and the levers that shorten it without new hardware, each as its own task and PR, with the measurement that proves it.

Every number below comes from the last local run's report (`.reports/playwright-report/index.html`, 2026-10-13 04:41, 6 workers, 109 tests, all passed) or from `claude-docs/`. Anything else is marked as an estimate.

## Where the time goes

1. **The critical path is one serial file.** Twelve db-touching files open with `test.describe.configure({ mode: 'serial' })`, so each runs on one worker in order. `admin.spec.ts` alone is 36.6 s; the other five workers sit idle at the tail. Wall time is roughly startup plus that one file, not the 27.5 s the work would take spread evenly. The doc gives the rule's origin as a race on one shared database, which MB.112's database-per-slot ended; the doc itself says so (`claude-docs/testing/e2e.md`, the serial paragraph).
2. **Startup.** The 55.9 s minus the 36.6 s critical path leaves about 19 s for seeding the template, starting the worker processes and, on a cold run, `next build` plus eight `next start`s. The report cannot say whether this run rebuilt; CI's warm build-and-start is 29 s on 4 vCPU (`claude-docs/ci/runner-budget.md`).
3. **Per-test overhead recorded then thrown away.** Locally `video: 'retain-on-failure'` and `trace: 'retain-on-failure'` record every test and discard the result on pass, and the video is encoded on the browser server, which shares the host's cores. The `coverageAutoFixture` starts JS coverage on every page and feeds monocart after every test, locally and on CI alike. Size unmeasured; estimated at 10–25% of test time together, to be measured in the first task.
4. **CI is slower than the doc says, and critical-path-bound there too.** `claude-docs/ci/runner-budget.md` still lists 55 s for 56 tests on 2 workers. The six most recent successful gate runs on 2026-10-13 show the Playwright step at 137–163 s (`gh api` on the pr-gate runs). The job log of run 38339732424 (106 tests, 4 workers, step 163 s) breaks down as:

   | Phase                                   | Seconds |
   | --------------------------------------- | ------- |
   | `next build` (warm cache) and 8 servers | 26      |
   | Template seed, clones, spec load        | 11      |
   | Tests (one flaky retry included)        | 125     |

   Per-file sums from that log's list reporter: `admin.spec.ts` 74 s, `shell.spec.ts` about 38 s (the log prints its lines twice, 77 s raw), `admin-compendium.spec.ts` 36 s, total about 300 s. So on CI's slower cores the serial admin file is 74 s of a 125 s test span, and the ideal span of 300 s on 4 workers is about 75 s. Trace, video and the build cache are already handled on CI, and coverage has to stay, so the CI saving comes from lever 2 alone.

## Estimated saving on GitHub

Lever 2 is the one that moves CI. Estimate, from the log above: the test span falls from about 125 s toward the 75 s ideal, say 80–90 s with scheduling slack and the 36 s compendium flow as the floor, so the Playwright step goes from about 160 s to about 115–125 s, roughly 40 s or a quarter of the step, and the whole job from about 210 s to about 170 s. The gate's critical path is this job (`runner-budget.md`), so a gate run finishes about 40 s sooner. Lever 6 may add a little on CI (6 workers on 4 vCPU, since a test waits mostly on the browser), unmeasured and probably 5–15 s; the rest of the levers save nothing there. Sharding across more free runners costs about 48 s of image pull per shard against the 40 s it would save, so it is not worth it at this suite size. Locally the same lever saves more, since 6 workers idle behind one file.

## Recommended levers, in order

Each is one task and one PR (CLAUDE.md, one task per PR), minted as `M<wave>.<n>` ids, each measured before and after on the same tree: three runs, median, wall time from `time` around `flock /tmp/sorrel-e2e.lock npx playwright test`, and the per-file sums pulled from the report with the extraction below. Local runs reuse servers already up, so a measurement states whether the servers were warm.

### 1. Baseline and profile (no code change)

- Record three cold runs and three warm runs (servers left up by a prior `npm run e2e:ui` session, so `reuseExistingServer` attaches), and one run each with `video: 'off'`, with coverage disabled by hand in `fixtures.ts`, and with `E2E_WORKERS=12`. Nothing is committed but a measurements table in `claude-docs/testing/e2e.md` under a new "Where a run's time goes" heading.
- This decides levers 3, 4, 5 and 6 on numbers rather than estimates, which is the owner's standing rule.
- The same PR corrects the stale Playwright row of `claude-docs/ci/runner-budget.md` (55 s for 56 tests) to the breakdown above, and lever 2's PR corrects it again after.

### 2. Let independent tests run in parallel (the big one, locally)

- **Change:** drop `mode: 'serial'` from every file whose tests are independent of what an earlier test in the file wrote. With `fullyParallel: true` already set, Playwright spreads the file's tests over the workers; `beforeAll` runs once per worker that takes any of the file's tests, re-cloning that worker's own slot database and rebuilding the file's setup rows there, which is safe since MB.112 and costs tens of milliseconds a time.
- **Audit first, per file:** a test is independent when it signs in its own user and reads only seed rows or rows its own `beforeAll` wrote. `admin.spec.ts` already fits: 19 of 22 tests call `signInAs` with their own address, and `primaryAdminId()` falls back to creating the primary admin when no earlier test did. `shell.spec.ts` builds its `users` in `beforeAll`, which is per worker, so it fits too. A file whose tests chain stays serial and is split along the chains instead (the fallback, which keeps the rule as written).
- **Expected:** wall time falls toward the ideal span plus startup. Estimate: 56 s to about 40 s locally on 6 workers, more with lever 6; on CI little, since CI is throughput-bound.
- **Rule change, flagged to the owner:** `claude-docs/testing/e2e.md` states serial as a must. The PR rewrites that paragraph: serial is for a file whose tests chain, and the reseed hazard it was written for is gone. The e2e paragraph in `.claude/rules/testing.md` is checked for the same statement.
- **Verification:** the full suite three times locally and once on CI with retries, since a retried test lands on a fresh worker whose `beforeAll` reruns, which is exactly the independence the audit proves.

### 3. Stop recording video on every local test

- **Change:** `playwright.config.ts`, local branch of `use`: `video: 'off'`. Trace stays `retain-on-failure`, so a first failure still carries its own evidence (the trace holds screenshots and DOM snapshots per action, which is what a failure is read from).
- **Owner decision:** losing the video on a local failure. Recommended default: off, revertable by one line.
- **Expected:** measured in lever 1; estimated 5–10% of test time, and less load on the browser server.

### 4. Collect JS coverage only when asked

- **Change:** `tests/e2e/fixtures.ts` skips `startJSCoverage`, `stopJSCoverage` and `MCR.add` unless `E2E_COVERAGE=1`; `global-setup.ts` and `global-teardown.ts` skip `cleanCache` and `generate` the same way. `.github/workflows/playwright.yml` sets `E2E_COVERAGE: 1` so CI's coverage artifact and `summarize-playwright.mjs` are unchanged. `claude-docs/testing/coverage.md` and `e2e.md` say how to get the local report (`E2E_COVERAGE=1 npm run e2e`).
- **Owner decision:** local runs no longer write `.reports/coverage-e2e` by default.
- **Expected:** measured in lever 1; estimated 5–15% of test time, and a faster teardown.

### 5. Keep the slot servers warm between local runs, if the build dominates

- Only if lever 1 shows a cold run paying tens of seconds in `next build`. The standard mechanism already exists: `reuseExistingServer: !CI` attaches to servers that are up. What is missing is a way to leave them up: an `npm run e2e:servers` script that starts the slot, providers and cache servers over the existing `.next-e2e` build with the same env `playwright.config.ts` computes (the server list moves to `tests/e2e/servers.ts` so the config and the script share one definition). A run then skips the build and the eight server boots. Staleness is the developer's: the doc says to restart after a code change, the same contract `npm run dev` has. No file watcher, no hash check.
- Flagged as a decision because it adds a developer-run process the owner may not want beside `npm run dev`.

### 6. Use the cores already here: more workers once the critical path is gone

- After lever 2 the suite is throughput-bound locally too, so workers matter. `tests/e2e/slots.ts` defaults to half the cores (6). MB.236 found a test mostly waits on the browser, not on a core, which is why CI runs one worker per vCPU. Measure `E2E_WORKERS` at 6, 9 and 12 (each extra slot is about 180 MB and half a second of startup, `claude-docs/testing/e2e.md`) and set the default in `slotCount()` to the winner, documented with the numbers. 12 servers is about 2.2 GB, well inside 32 GB; the browser server's load is the unknown the measurement answers.

## Not recommended now, and why

- **Postgres `fsync=off` and friends** for the test instance: clones are tens of milliseconds and each test writes a handful of rows, so the saving is estimated at 1–3 s of summed test time, under a second of wall. Revisit only if lever 1's profile shows database waits.
- **Trimming the double-theme and double-width axe scans:** they are the accessibility gate (CLAUDE.md, Testing). A quarter fewer scans would save about 2 s of wall at 6 workers, estimated. Not worth the coverage.
- **Splitting the 12.9 s compendium flow:** it becomes the floor once lever 2 lands (no run can be shorter than its longest test plus startup), and 12.9 s is under the 27.5 s ideal span, so it is not on the critical path.
- **CI sharding, `--only-changed`, project dependencies:** sharding pays more in pulls than it saves; `--only-changed` does not fit a gate that must run everything; the seeding already lives in `globalSetup`.
- **A smaller build** (`productionBrowserSourceMaps` off): shared with the coverage report CI needs, and a change to the production bundle, so out of scope here.

## Measurement recipe (used by every lever)

```sh
# wall time, servers' state noted beside it
time flock /tmp/sorrel-e2e.lock npx playwright test

# per-file sums and slowest tests from the html report's embedded report.json
node -e '
const fs=require("fs");const {unzipSync,strFromU8}=require("fflate");
const html=fs.readFileSync(".reports/playwright-report/index.html","utf8");
const b64=html.match(/id="playwrightReportBase64"[^>]*>data:application\/zip;base64,([^<]+)</)[1];
const rep=JSON.parse(strFromU8(unzipSync(Buffer.from(b64,"base64"))["report.json"]));
console.log("wall ms",rep.duration,"tests",rep.stats.total);
for(const f of rep.files.map(f=>[f.fileName,f.tests.length,f.tests.reduce((a,t)=>a+t.duration,0)]).sort((a,b)=>b[2]-a[2]))console.log(f.join("\t"));'
```

The recipe goes into `claude-docs/testing/e2e.md` with lever 1 so later tasks measure the same way.
