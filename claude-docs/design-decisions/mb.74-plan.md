# MB.74 — Better Auth plugins: what to add now, what waits for v2

## Context

`src/lib/auth.ts` configures Better Auth 1.7.5 with **no plugins**: four OAuth providers, first-party email verification (MB.66), the provisional-account sweep (MB.67), and the primary-admin promotion hooks. The only plugin-module import anywhere is `createAccessControl` from `better-auth/plugins/access` (M6.3). Two plugins already have a recorded decision: `organization` is rejected (MB.30), and `admin` is scheduled for impersonation only, allowlisted to two endpoints, outside production (MB.53).

The user asked for a review of the rest of the roster and a recommendation of what to adopt before launch and what to leave for v2, and chose the deliverable: a decision record plus minted tasks, in the M2.9 / MB.61 shape (a scoping task ends in a record and tasks, no code). Everything below was read from `node_modules/better-auth/dist` and `@better-auth/core/dist`, not from the docs.

**The frame that decides most of it:** the site is OAuth-only and invite-gated (DESIGN.md §2, §14). Most of the roster exists to secure a _first-party credential_ (a password, an email code) or to serve a _non-browser client_. This app has neither, so a plugin has to earn its place against a rule that already excludes it, against rule 1 (every plugin mounts routes under `/api/auth/*`) and rule 3 (plugin writes go through the adapter, outside `withAudit`).

## Findings that change the answer

- **Two-factor never challenges an OAuth sign-in.** `plugins/two-factor/index.mjs:245` intercepts only `/sign-in/email`, `/sign-in/username`, `/sign-in/phone-number`. Registered today it adds a `two_factors` table and `users.two_factor_enabled` and protects nothing.
- **Rate limiting is already on in every deploy, and per-instance.** `context/create-context.mjs:172` defaults `enabled` to `NODE_ENV === 'production'`, which every Vercel build is; storage defaults to `memory` (a module-level `Map`), so on Fluid Compute each instance counts alone. Sign-in paths get 3 per 10 s, `/send-verification-email` 3 per 60 s. If the client IP cannot be resolved (`x-forwarded-for` absent or multi-valued with `advanced.ipAddress.trustedProxies` unset), every request on that path shares **one bucket** (`api/rate-limiter/index.mjs`, `NO_TRUSTED_IP_KEY`): 3 sign-ins per 10 s site-wide. Nothing pins any of it. Database storage is built in: a `rateLimit` model (`key` unique, `count`, `lastRequest` bigint) with atomic increment through the adapter and background pruning.
- **OAuth tokens sit in `accounts` in plaintext.** `account.encryptOAuthTokens` (off) encrypts access/refresh/id tokens under `BETTER_AUTH_SECRET`; `oauth2/utils.mjs:10` decrypts only values that look encrypted, so existing plaintext rows keep working. Nothing in the app reads the tokens.
- **The OAuth proxy plugin fixes a gap the docs currently accept.** `secrets.md` ("Hotfix previews still can't complete a real sign-in") and `auth.md` state that a hotfix slug has no pre-registered redirect URI. `oAuthProxy` sends the provider callback to a fixed `productionURL` and forwards the encrypted profile to the preview's `/callback/:id/oauth-proxy` (`plugins/oauth-proxy/index.mjs`). The forward target must be a trusted origin; `getTrustedOrigins` (`context/helpers.mjs:60`) derives them from `baseURL.allowedHosts`, which already lists `hotfix-*.sorrelandsalt.com`. MB.53 impersonation is only usable on a preview an admin can sign in to, so this is MB.53's missing prerequisite on hotfix previews.
- **Passkeys are a separate package**, `@better-auth/passkey` 1.7.6 with peer `better-auth ^1.7.6`; installed core is 1.7.5. Not in the tree.
- **Last-login-method is cookie-only** unless `storeInDatabase` is set: a non-`httpOnly` cookie carrying the provider id, set on `/callback/:id` (`plugins/last-login-method/index.mjs`). No schema, no query.

### Rejected for this app

- **`user.deleteUser`** (core): it is a hard `DELETE` on `users` (`api/routes/update-user.mjs:340`), and every `created_by`/`updated_by` in the schema references `users.id` with `NO ACTION` (`src/db/audit.ts`), so it fails for anyone who has authored a single row. The soft-delete alternative is unsafe too, for the reason MB.67 found: Better Auth looks a user up by address with no `deleted_at` filter, and a verified tombstone would take an implicit link from any provider vouching for its address, reviving the account. If v2 adds an account-deletion story it is our own service under `withAudit`: tombstone the row, rotate its email to `<id>@deleted.invalid` so nothing can match it, hard-delete its `accounts` and `sessions` rows (adapter tables, cascade already), refuse the primary admin (MB.59). Recorded as the shape, no task minted.
- **`jwt`**: there is no reason to move off the cookie. The plugin does not replace the session; it issues a token _beside_ it (`/token`, and a `set-auth-jwt` header on session responses) for a separate service to verify against a JWKS, and this app has no such service. Its one "instead of cookie" mode, `sessionCookieCache`, requires `session.cookieCache.strategy = 'jwt'`, which is exactly what MB.59 pins off so that a revoked admin is refused on the next request rather than after a cache TTL. The cookie plus one session read per request is the accepted cost.
- **`bearer`, `oneTimeToken`, `deviceAuthorization`, `oauthPopup`**: for non-browser or cross-origin clients; the app has one cookie-authenticated GraphQL client per origin.
- **`multiSession`**: several accounts per browser; one address is one account (M2.9) and no story asks for switching.
- **`username`, `anonymous`, `phoneNumber`, `siwe`, `oneTap`, `genericOAuth`, `openAPI`, `customSession`**: no fit. One Tap would load Google's script on the public `/` for a frictionless sign-up an invite-gated site does not want. `genericOAuth` is the mechanism if a provider outside the built-in roster is ever wanted; none is.
- **`admin`** beyond MB.53's two endpoints, and **`organization`**: already decided (M2.9 option E, MB.30); unchanged.
