# Move task tracking from Asana to GitHub Issues and Projects (MB.89)

## Context

The Asana workspace is on the free Personal plan, and MB.56 (6h) rebuilt the board around what that plan allows: no custom fields, no search, no rules, no dependencies. The task id and status live in the task **name** (`◔ M2.6 — …`), lookup is a two-call walk over wave-card notes, and `Type` was dropped. The question is whether moving the tracker to GitHub restores those features, and what the move costs.

**Short answer: yes, it restores all four, and for free.** GitHub Projects (v2), issue types, sub-issues and issue search are on every plan, including the free org plan this repo already sits on. The tooling is already here: `gh` 2.97 in the devcontainer has native `--parent`, `--add-sub-issue` and `--type` flags, and the org already has `Task` / `Bug` / `Feature` issue types. No MCP server is needed, which is the "standard tool over bespoke mechanism" answer.

**The one real change is visibility.** `Aurora-Arctic/Sorrel-and-Salt` is **public**, and issues and comments inherit the repo's visibility. `TASKS.md` is already public, so task titles and notes are not new exposure, but the 395+ progress comments would be. Decision point below.

**Status.** Approved 2026-09-27 as MB.89: public issues in the code repo, waves as milestones. The Phase 0 spike found the pre-existing fine-grained PAT refused on `createProjectV2`; a new token owned by the org, carrying the Projects permission, fixed it, and the Project was created as number 1 the same day. `gh issue edit` carries `--add-blocked-by`/`--add-blocking`, so dependencies need no API call.

## Decision 1 — where the issues live: **public issues in this repo (decided)**

The pros and cons that led there are kept for the record. Two real options were weighed. Making the code repo private is a third, but it would take the public compendium's repo out of view for a tracker's sake, so it is not argued here.

### What the comments actually contain (evidence)

Two threads read in full. MB.76 (5 stories): branch name, file paths, test counts, a note that the session had no Vercel access. MB.12 (13 stories): which secrets were confirmed set in which Vercel environment, that stale `GITHUB_CLIENT_ID`/`SECRET` were still in Preview, that staging's `DATABASE_URL` pointed at a different Neon account and left the app querying an unmigrated database, a Neon snapshot id, the Facebook scope fix, and "ADMIN_BOOTSTRAP_EMAIL in Production not yet confirmed" until it was. **No secret values anywhere**, and the variable names are already public in `secrets.md`. What is new is the _operational narrative_: a dated timeline of what was misconfigured, where, and for how long.

### (a) Public issues in `Aurora-Arctic/Sorrel-and-Salt`

Pros

- **One repo, no plumbing.** `gh issue` and `gh pr` share a repo, so no `--repo` on every call. Milestones are per-repo, and the Project's auto-add filter watches one place.
- **The merge Action works with `GITHUB_TOKEN`.** Closing an issue on a staging merge needs `issues: write` on the issue's repo; the workflow token has that for its own repo and for no other.
- **Hotfix PRs into `main` close their issue natively**, and the PR shows on the issue's Development sidebar. Neither works cross-repo.
- **The public repo's PR bodies stop pointing into a private tracker.** Every merged PR opens with an Asana permalink nobody outside can open; `#N` resolves for any reader.
- **Same register as what is already public.** TASKS.md, DESIGN.md, secrets.md, the transcripts and every PR body are public; the comments are the same content one notch more candid.
- **Reversible per issue, imperfectly.** `gh issue transfer` moves an issue with its comments to a private repo in the org; caches, notification mail and search indexes keep whatever was there before the move.

Cons

- **The operational timeline becomes public and indexed.** The MB.12 thread is the shape of it: a map of which environment was misconfigured when. Not a secret, but it is more than a reader of `secrets.md` gets today.
- **An accident is public instantly.** Skills post comments automatically; a comment that quotes an `.env` line or a token is indexed before anyone reads it. Asana contained that. Mitigation is a rule in the skills' comment steps ("names, never values") and the pre-publication scan in Phase 1, neither of which is as strong as a private repo.
- **Anyone can open issues and comment.** A public repo cannot restrict issue creation to collaborators; interaction limits are temporary (up to six months, renewable) and blunt. The Project's auto-add filter (`label:tracked` or `type:Task`) keeps strangers' issues out of the board, and an issue template plus a `triage` label keeps them out of the way. The tracker becomes a mixed inbox regardless.
- **Work cadence is visible.** Comment timestamps show when the work happens, which the Asana board did not expose.
- **395 historical comments need a review pass before they go public.** A pattern scan (tokens, `postgres://`, addresses, dashboard URLs) plus a skim of the credential-touching tasks: MB.12, M2.4, M2.5, MB.46, MB.65, M0.27. Budget ~1h inside Phase 1.

### (b) Private sibling repo `Aurora-Arctic/Sorrel-and-Salt-tracker`

Pros

- **Comments stay private**, so the automatic-comment risk and the timeline exposure both go away, and no historical review pass is needed.
- **Issue creation is collaborators-only**, which a public repo cannot get.
- **Sub-issues and the Project span repos** (both confirmed in GitHub's docs), so the board looks identical.
- **One-way door in the safe direction.** An issue can be transferred to the public repo later; the reverse cannot un-publish.

Cons

- **No PR ↔ issue link ever renders.** Manual linking on the Development sidebar is same-repo only, and cross-repo closing keywords fire only on the default branch. The body line `Closes Aurora-Arctic/Sorrel-and-Salt-tracker#N` is the whole link, as the Asana permalink is today.
- **The merge Action needs a PAT.** `GITHUB_TOKEN` cannot close issues in another repo, so the workflow carries a fine-grained PAT with `issues: write` on the tracker as a repo secret, which is one more credential in the secrets matrix and one more thing that expires.
- **Hotfix PRs into `main` also need the Action**, since the native close is same-repo. One path instead of two, at least.
- **Every `gh issue` and `gh project` call takes `-R Aurora-Arctic/Sorrel-and-Salt-tracker`**, and the skills carry the repo name beside the Project number. `GH_REPO` cannot be set globally because `gh pr` must keep working in the code repo.
- **Milestones live in the tracker**, so a wave's progress bar is one click away from the code rather than on its Milestones tab.
- **The public repo keeps pointing at a private tracker**, exactly as now.

### Decision

**(a), the public repo**, chosen on the evidence that the comments carry names and narrative but no values, and that everything else about this project is already public by choice. Three conditions are written into the task: the pre-publication scan of the 395 comments, a "names, never values" line in every skill step that posts a comment, and the Project's auto-add filter so strangers' issues never reach the board.

## Migration shape (MB.89)

Effort a little above MB.56: ~7h for the data move including the comment scan, ~4h for the skills, the close-on-merge Action and the docs.

**Phase 0 — spike (30 min, disposable).** Create the org Project; confirm the PAT can write Project fields (`gh project field-create`, `gh project item-edit`) and org issue types, since fine-grained PATs need an explicit org `Projects` permission; create one throwaway issue with a sub-issue, a type, a milestone and a `blocked by` link; delete it. If Project writes fail, the fix is the PAT's permissions, not the plan.

**Phase 1 — data move, scripted and idempotent.** A Node script (no Python here) in the scratchpad, reading Asana through a personal access token the user mints (MCP would be ~600 calls: wave cards, 290 `get_task`, 290 `get_stories`) and writing through `gh`. Idempotency key is the id segment in the title, so a rerun updates rather than duplicates. Order:

1. Milestones: one per wave from TASKS.md's execution-order table, description = the wave card's notes.
2. Issues in TASKS.md order (so issue numbers roughly follow task order): title `ID — title`, body = Asana notes, type (`Bug` for `MB.*` unless the notes say otherwise, `Task` else), `hotfix` label where the notes call it one, milestone, and closed-as-completed for ticked tasks, closed-as-not-planned for RETIRED.
3. Comments, each opening with the original `[YYYY-MM-DD HH:MM UTC]` bracket (the migrated ones already carry it; system stories are skipped as MB.56 did). The script first writes every comment to a local file and runs the pattern scan (tokens, `postgres://`, addresses, dashboard URLs); publication waits on a skim of the credential-touching threads: MB.12, M2.4, M2.5, MB.46, MB.65, M0.27.
4. Add every issue to the Project; set `Status` from the marker / checkbox and `Estimate` from TASKS.md's `· Nh`.
5. Sub-issue and dependency links where TASKS.md names them.

**Phase 2 — repoint the tooling** (same PR):

- `CLAUDE.md`: replace "Asana task tracking" with a GitHub section: the title convention, the one-call exact-match lookup, Status values and when each is set, `Closes #N` as the completion mechanism, the Project number and field names.
- Skills: `start-task`, `create-feature`, `create-hotfix` (lookup + `Status → In Progress` + comment), `create-pr` and `reference-hotfix.md` (`Closes #N` line, `Status → In Review`, comment; for a hotfix, one comment listing every PR), `project-progress` verify mode (`gh issue list --state all --json title,state,milestone` and compare). `tally.mjs` changes only its comment.
- `.github/workflows/close-task-on-merge.yml`: on `pull_request` closed with `merged == true` and base `staging`, read `Closes #N` lines from the body and `gh issue close` each; `permissions: issues: write` on `GITHUB_TOKEN`, no PAT. PRs into `main` close natively.
- The Project's auto-add workflow filters on `type:Task` or `type:Bug` plus a `tracked` label the script applies, so an issue opened by a stranger stays off the board until triaged.
- Every skill step that posts a comment gets the line "names, never values": no env values, tokens, connection strings or addresses in a comment.
- `.mcp.json`, `.claude/settings.local.json`: remove Asana. Add the `gh issue`/`gh project` read commands to the allowlist instead.
- Live docs: `TASKS.md` l.5, `README.md`, `agent-skills.md`, `docker.md`, `debugging.md`, `secrets.md`. Design-decision plans and transcripts stay as history (MB.50/MB.31: history that is still true is not cut).
- TASKS.md gets the new task's entry; `tests/guards/doc-citation.test.ts` must stay green.

**Phase 3 — cut over.** Set `Status` on the in-flight tasks to match reality; rename the Asana project to `… (archived — moved to GitHub Issues <date>)`; leave the workspace alive for permalinks.

## Verification

- Counts: issues = Asana tasks (290), closed = completed, comments = 395, milestones = 15 (+1); the script prints all four against the Asana source.
- Spot-check five tasks across waves: title, body, milestone, type, status, first comment's bracket date.
- Each skill run once against a throwaway issue on a throwaway branch: lookup finds exactly one issue for `M2.1` and a different one for `M2.10`; `create-pr` writes `Closes #N` and flips Status to `In Review`.
- The close-on-merge Action: run under `act` from the host (`make act-check`) with a synthetic merged-PR event first; then the first real feature merge into `staging` after cut-over is the live check that the issue closes and the Project workflow marks it `Done`.
- The pattern scan reports zero hits before any comment is published, and the six credential-touching threads have been read.
- `/project-progress` verify mode agrees with the local tally.
- `npm run format:check`, `npm run lint`, and the `vitest` guards (doc-citation, test-location) green. No coverage run: nothing under `src/` changes.
