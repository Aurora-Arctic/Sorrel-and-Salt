# M1.1 — Neon branch strategy: persistent staging vs. ephemeral hotfix branches

**Status:** decided · **Date:** 2026-09-10

The task as written only asks for two Neon branches, `production` and
`staging`, with the Vercel integration injecting `DATABASE_URL` per
environment. In practice the project's default branch was never renamed off
Neon's own default (`main`) — every reference below to a `production` Neon
branch is actually `main`; only the Vercel environment is called
`production`. That undersells a real conflict: the Neon Vercel integration can
also automatically create a branch for every Vercel Preview deployment and
delete it when that deployment is torn down. `staging` and the per-PR hotfix
previews (`DESIGN.md`, "Configuration") are **both** Preview-environment
deployments, so the integration's automatic branching does not distinguish
between them by default — left as-is, it would try to mint (and eventually
reap) a throwaway branch on every `staging` deploy too, orphaning the
hand-created `staging` branch.

## Decided

- **`main` and `staging` are created by hand**, `staging` as a child
  branch of `main`. The task names the primary branch `production`; in
  practice it was created under Neon's own default name, `main`, and never
  renamed. These are permanent; nothing automated deletes them.
- **Hotfix previews get ephemeral, automatically-created Neon branches.** The
  integration's automatic branch-per-preview-deployment feature is left on,
  scoped to Preview deployments generally — this is what gives each
  `hotfix/<slug>` PR its own disposable database, deleted when the PR closes.
- **`staging` is shielded from that same automation with a branch-scoped
  environment variable**, added via the CLI (the dashboard's equivalent
  control is inconsistent across UI revisions):

  ```
  vercel env add DATABASE_URL preview staging
  ```

  This ties a `DATABASE_URL` value to Preview deployments from the `staging`
  git branch specifically. Vercel resolves a branch-scoped variable ahead of
  the environment-wide one the integration injects, so a `staging` deploy
  gets the pinned, persistent connection string while a `hotfix/*` deploy
  falls through to the integration's auto-created branch.

- **Add the integration first, then the override.** The branch-scoped
  variable is only meaningful once the integration has already injected a
  Preview-wide `DATABASE_URL` to override.

## Rules this sets

- Only `main` and `staging` are permanent Neon branches; any other
  branch existing in the project is an ephemeral hotfix preview and safe to
  ignore or manually delete if orphaned.
- A `staging` deploy's `DATABASE_URL` must always be the branch-scoped
  override, never the integration's generic Preview injection — if that
  override is ever removed, `staging` silently starts sharing (or losing)
  its database with the next hotfix branch's ephemeral one.
- Verify this exact behavior in the live dashboards before trusting it: a
  `staging` push must not spawn a new Neon branch, and a hotfix PR must both
  get one and lose it on close. Not yet verified as of this record — the
  project doesn't exist yet.

## Correction — MB.27 (2026-09-19)

Nothing asked for the override. `deploy.yml` and `migrate.yml` both ran
`vercel pull --environment=preview` with no `--git-branch`, and Vercel resolves
a branch-scoped variable only for a pull that names the branch — so a staging
deploy would have pulled the Preview-wide `DATABASE_URL` the integration
injects, whatever was configured. That is the failure the rule above warns
about ("if that override is ever removed…") arriving by a route the rule did
not anticipate: not removed, never requested. Both workflows now pass
`--git-branch`, guarded by `tests/guards/vercel-pull-git-branch.test.ts`.

**Superseded in part by MB.45 (2026-09-19):** "both workflows now pass
`--git-branch`" was true of every pull, and one pull too many. Branch-scoped
overrides are a Preview-only Vercel feature; passing the flag with
`--environment=production` is rejected outright —
``Invalid request: `target` must be "preview" when specifying a `gitBranch` ``
— so from the first push to `main` after MB.27 merged, every production deploy
failed at the pull. Each workflow now pulls through two steps selected by the
resolved environment: preview with the flag, production without. The guard
checks both halves rather than only the presence of the flag.

The asymmetry is not arbitrary. Preview has a branch-scoped value to resolve
and silently reads the wrong database without the flag; production has no such
value, so it has nothing to miss and loses nothing by omitting it. The two
failures are opposite in character, which is why one needs a guard and the
other announces itself: dropping the flag on preview fails nothing and
corrupts the target, passing it on production fails everything and corrupts
nothing.

The deploy needed the same fix from the other side. A deployment resolves its
runtime environment from its branch association, and the CLI infers that from
the checkout — which `actions/checkout` leaves detached, so a CLI deployment
from this repo had no branch at all. `vercel deploy` therefore now carries
`--meta githubDeployment=1 --meta githubCommitRef=<branch>`. The two halves fix
different reads: `--git-branch` the build's, `--meta` the running app's, which
is the one `src/db/connection.ts` makes.

Whether the override itself exists is a separate, still-open question:
`claude-docs/secrets.md` records the branch-scoped form as an instruction for
whoever sets the row, not as a confirmation that it was set that way.

The verification this record asks for above is **partly** answered now, and the
rest is owed. That paragraph used to say the deploy workflow's secret guard
(`VERCEL_SCOPE`, MB.12) skipped every real step so nothing had run: both halves
were wrong. The guard checks `VERCEL_DEPLOY_TOKEN` / `VERCEL_ORG_ID` /
`VERCEL_PROJECT_ID` and never mentioned `VERCEL_SCOPE`, all three are set, and
deploys have been running since well before v0.2.0.

What the live runs establish: `vercel pull` retrieves project settings on both
targets, and the production pull fails on the flag alone (MB.45). What they do
**not** establish: whether the branch-scoped `staging` override exists, and
whether its value is usable — the staging pull returns a `DATABASE_URL` that
does not parse as a URL, and CI masks it before anything can print it, so the
logs cannot say whether it is Vercel's `[SENSITIVE]` placeholder or a malformed
value. MB.47 owns that question and needs a look at the dashboard to answer it.
The behaviour this record asks for — a `staging` push spawning no Neon branch, a
hotfix PR getting one and losing it on close — is still unverified.

## Cross-task impact

- **M1.4** (migrations workflow) runs against whichever branch a deploy
  targets; it must resolve `DATABASE_URL` the same way `deploy.yml` does, so
  it inherits this same branch-scoping requirement rather than assuming a
  single staging connection string.
