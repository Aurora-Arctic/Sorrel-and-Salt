# M0.13 — add the `postgres` service to `docker-compose.yaml`

**Status:** decided · **Date:** 2026-09-08

`resume-2026` has no database, so there was nothing to port — the service is
built from DESIGN.md §11 ("Test database: local Postgres, not Neon, not
SQLite"). The task: a `postgres` service with a named volume and a health
check, wired to the image tag CI will publish in M0.18, plus `DATABASE_URL`
for the app (and the future devcontainer).

## Decided

- **`image: postgres:17`, plain upstream.** DESIGN.md §11 pins the major
  version and nothing more. M0.18 publishes a preseeded Postgres 17 image
  (extensions enabled, empty `sorrel_template`) to GHCR; M0.19 is the task
  that repoints this service **and** the CI `services:` block at that one tag
  "from one place, not two literals". Introducing that indirection now would
  be doing M0.19's job with no image to point at, so this ships the literal
  and a comment naming its successor.
- **Named volume `postgres_data` at `/var/lib/postgresql/data`.** Survives
  `docker compose restart` and `make docker-down`; only `make docker-rebuild`
  (`down -v`) clears it — same lifecycle contract as the `node_modules_*`
  volumes, stated in the same place in the file.
- **Health check is `pg_isready -U sorrel -d sorrel`**, `interval: 5s`,
  `timeout: 5s`, `retries: 10`, `start_period: 10s`. `pg_isready` ships in the
  image, needs no shell-level credentials, and returns non-zero until the
  server accepts connections — which is exactly the gate `app` waits on.
- **`app` gets `depends_on: { postgres: { condition: service_healthy } }`.**
  `make docker-up` (`docker compose up -d`) then blocks on the health check
  before starting `app`, so "starts Postgres 17 and reports healthy" is
  observable in the `up` output (`postgres Waiting` → `postgres Healthy` →
  `app Starting`), not just eventually true.
- **`DATABASE_URL: postgres://sorrel:sorrel@postgres:5432/sorrel` on `app`.**
  Host `postgres` is the compose service name (acceptance: "app container
  connects using the service name"). Credentials are the throwaway
  `sorrel`/`sorrel` set via `POSTGRES_USER` / `POSTGRES_PASSWORD` /
  `POSTGRES_DB` — local-only, no secret. The devcontainer (M0.14) sets the
  same value; there is no `devcontainer` compose service to put it on here.
- **Port `5432:5432` published.** The Vitest `db` project runs on the host and
  connects over `localhost:5432`; inside the compose network, services use the
  `postgres` hostname. resume-2026 has no Postgres, so nothing on 5432
  collides with it.
- **`workshop` gets neither `DATABASE_URL` nor `depends_on: postgres`.** It
  serves static component stories and never touches a database; making it wait
  on Postgres would only slow `make docker-workshop`.

## Verified

- `make docker-up` from a clean state: compose output shows
  `postgres Started` → `postgres Waiting` → `postgres Healthy` →
  `app Starting`; `docker compose ps` then shows `postgres` `Up (healthy)` and
  `app` `Up`. `select version()` → `PostgreSQL 17.11`.
- From inside `app`: `printenv DATABASE_URL` is the `postgres://…@postgres…`
  URL, and a Node TCP connect to `postgres:5432` succeeds — the app resolves
  and reaches the database by service name.
- Persistence: `create table … insert 42`, `docker compose restart postgres`,
  wait healthy, `select` still returns `42`. The `postgres_data` volume also
  survives `docker compose down` (no `-v`).
- No Neon: the whole stack comes up with no external database configured or
  reachable.
- `docker compose config` validates; `--services` lists `postgres` and `app`,
  `--volumes` lists `postgres_data` and `node_modules_app`.

## Rules this sets

- **M0.18** builds the GHCR Postgres 17 image (extensions + empty
  `sorrel_template`) that replaces `image: postgres:17` here.
- **M0.19** replaces the `postgres:17` literal and the CI `services:` tag with
  a single shared reference, and caches the pull between jobs.
- **M0.14**'s devcontainer sets `DATABASE_URL` to the same value and adds
  `depends_on: postgres` with the health condition; there is no `devcontainer`
  service in this file to carry it.
- The Vitest `db` project (M0.7) connects over the published `localhost:5432`,
  not by service name.
