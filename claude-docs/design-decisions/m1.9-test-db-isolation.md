# M1.9 — Test database isolation: per-worker clone vs. rolled-back transaction

**Status:** decided · **Date:** 2026-09-10

Two ways to give parallel Vitest `db`-project workers isolated Postgres
state were on the table: give each worker its own real database, or run
every test inside a transaction that starts before the test and rolls back
after, so nothing a test writes is ever actually committed.

## Decided

**Each worker gets its own real database**, cloned from `sorrel_template`
with `CREATE DATABASE sorrel_test_<n> TEMPLATE sorrel_template` in a Vitest
`globalSetup` (`src/test/db-global-setup.ts`), and dropped (`DROP DATABASE
IF EXISTS` first, so a crashed prior run self-heals) in that same setup's
returned teardown. Postgres copies a template's files directly rather than
replaying anything, so this clone is fast — no further optimisation (e.g.
skipping the drop-first when nothing is there to drop) is needed.

## Rejected: rolled-back transactions

Wrapping each test in a transaction that starts before the test body and
rolls back after reads cleaner — no `CREATE`/`DROP DATABASE` plumbing, no
per-worker naming scheme — but it breaks specifically because of how
`withAudit` (CLAUDE.md's non-negotiable rule 3) works: it opens its own
transaction and issues `SET LOCAL app.current_user_id = '<uuid>'` inside it.

`SET LOCAL` scopes to the current transaction. If a test's own wrapper
transaction is the outer one and `withAudit` opens a nested
transaction/savepoint inside it, `SET LOCAL`'s value is transaction-local to
that savepoint by Postgres's own rules — but only until the savepoint
releases back into the outer transaction, at which point later statements
in the _same outer transaction_ (i.e. the rest of that test, or code that
runs after `withAudit` returns) can still observe it, since the outer
transaction is what the rollback-based harness never actually commits or
opens fresh per assertion. Concretely: two calls to `withAudit` for two
different users inside what the harness treats as "one test's transaction"
can leak the first call's `app.current_user_id` into the second — precisely
the audit-identity attribution this test suite exists to verify is correct.
A real, separate database per worker has no such nesting: every transaction
any test opens, `withAudit`'s included, is a top-level transaction against a
connection nothing else is sharing.

## Rules this sets

- **Never wrap a `db`-project test in a rolled-back transaction.** Use the
  per-worker database as-is; open and commit real transactions.
- A test that needs a clean table between assertions truncates or deletes
  explicitly — there is no ambient rollback to rely on.
- This applies to `src/db/**` and `src/services/**` tests specifically
  (anything that can reach `withAudit`). It has no bearing on `unit`-project
  tests, which never touch Postgres at all.
