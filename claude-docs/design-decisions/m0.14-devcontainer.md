# M0.14 — port `.devcontainer/` against the `development` stage

**Status:** decided · **Date:** 2026-09-08

`resume-2026/.devcontainer/` is a single `devcontainer.json` pointing at a
`devcontainer` service in `Docker/docker-compose.yaml`, which in turn built a
dedicated `devcontainer` Dockerfile stage (`FROM testing`, adding zsh +
oh-my-zsh, `gh`, nano, socat, …) and injected Claude / GitHub tokens. M0.11
deleted that Dockerfile stage and M0.12 deleted that compose service. The
task: bring the devcontainer back pointed at the surviving `development`
stage, with Postgres (M0.13) attached through its health check and both web
ports forwarded.

Mid-task the project owner asked, for the same PR, to also port
resume-2026's devcontainer conveniences: a pre-authenticated Claude Code CLI
via `update-token.sh`, a `gh` CLI authenticated from
`GITHUB_PERSONAL_ACCESS_TOKEN`, and a persisted `claude-home` so Claude's
context survives container shutdown.

## Decided

- **Two files: `.devcontainer/devcontainer.json` + `.devcontainer/docker-compose.yml`.**
  The JSON's `dockerComposeFile` lists `../Docker/docker-compose.yaml` first,
  then the sibling overlay.
- **Relative paths in the overlay resolve against `Docker/`, not
  `.devcontainer/`.** The VS Code Remote-Containers extension
  (`devContainersSpecCLI.js`) runs `docker compose -f <files> up -d` with **no
  `--project-directory`**, so Compose falls back to the first `-f` file's
  directory — `Docker/`. Verified against the bundled extension source and by
  `docker compose config`. Consequences, all deliberate: `context: ..` is the
  repo root (same as `app`); `./claude-home` is `Docker/claude-home` (the same
  path resume-2026 used, already in `.gitignore`/`.dockerignore`); and
  `Docker/.env` is auto-loaded for `${...}` interpolation — the mechanism
  resume-2026 relied on, ported unchanged.
- **The overlay adds one service, `devcontainer`, mirroring `app`.** Same
  `build.target: development`, same `..:/app:cached` bind mount, same
  `DATABASE_URL`, same `depends_on: { postgres: { condition: service_healthy } }`.
  It does **not** publish any ports — port exposure is the editor's job (see
  `forwardPorts`). It lives in `.devcontainer/`, not
  `Docker/docker-compose.yaml`, so a bare `make docker-up` stays free of
  editor-only services (M0.12's rule).
- **No `devcontainer` image stage.** `build.target` is `development` — the
  same stage `app`, `testing`, and CI use. resume-2026's `devcontainer` stage
  is not recreated; its interactive tooling is added at devcontainer-create
  time instead (below).
- **Own `node_modules_devcontainer` volume.** Not `node_modules_app`. A fresh
  named volume is populated from the mounting image on first use; two services
  sharing one fresh volume race to write it (observed in M0.12). This mirrors
  resume-2026's `node_modules_development` / `node_modules_devcontainer`
  split.
- **`command: ["sleep", "infinity"]` with `overrideCommand: false`.** The
  `development` stage's `CMD` is `npm run dev`; without an override the
  devcontainer's lifecycle would be pinned to the dev server. Idling PID 1
  instead lets the editor open shells and start `npm run dev` (8000) or
  `npm run start` (8001) on demand. resume-2026 got the same effect implicitly
  (its `devcontainer` stage had no `CMD`, so the base image's `node` REPL held
  it open under `tty: true`); an explicit `sleep infinity` is the idiomatic
  compose-devcontainer form.
- **`forwardPorts: [8000, 8001]`.** resume-2026 forwarded only 8001. Both are
  forwarded now (the task's "forward ports 8000 and 8001"): 8000 is `next dev`,
  8001 is the production build (`npm run build && npm run start`, DESIGN.md
  §"playwright.config.ts"). `portsAttributes` labels them in the editor UI.
- **zsh comes from the `common-utils` devcontainer feature, not the image.**
  resume-2026 installed zsh + oh-my-zsh in the deleted `devcontainer`
  Dockerfile stage; the slim `development` stage is bare
  `node:26.6.0-alpine` + `libc6-compat`, no zsh, no bash. Rather than
  re-bloat the shared app/CI image for an editor-only need,
  `ghcr.io/devcontainers/features/common-utils:2`
  (`installZsh` / `installOhMyZsh` / `configureZshAsDefaultShell`, `username:
node`) layers it on at create time only. The `terminal.integrated`
  zsh profile in `devcontainer.json` is kept — the feature installs zsh at
  `/bin/zsh` on Alpine.
- **`gh` is installed by a `postCreateCommand`, not the `github-cli`
  feature.** The feature was tried first (same reasoning as zsh — keep the
  shared `development` image untouched) but
  `ghcr.io/devcontainers/features/github-cli:1` is **Debian-only**: its
  `install.sh` has no `apk` branch and runs `wget`/`dpkg` unconditionally, so
  on `node:26.6.0-alpine` it dies with exit 127 ("command not found") during
  the feature build. Alpine's `community` repo already carries `gh` as the
  `github-cli` package, so `postCreateCommand: "sudo apk add --no-cache
github-cli"` installs it at create time instead — same "no shared-image
  change" outcome. `sudo` is passwordless for `node` because the
  `common-utils` feature configures it. `common-utils` itself is kept: it has
  a real Alpine path and installs zsh + oh-my-zsh fine.
- **Claude Code CLI is pre-authenticated via `Docker/.env`.** Ported from
  resume-2026 verbatim: `Docker/update-token.sh` (run on the host by
  `make docker-update-token`) does `claude setup-token`, scrapes the
  `sk-ant-oat…` token, and upserts `CLAUDE_CODE_OAUTH_TOKEN` into git-ignored
  `Docker/.env`; the overlay passes `CLAUDE_CODE_OAUTH_TOKEN: ${…:-}` through
  to the container. `Docker/.env.example` is the committed template. The `:-`
  default keeps `docker compose config` quiet when `Docker/.env` is absent —
  the CLI then just falls back to `/login`. `Docker/.env` is auto-loaded
  because it sits in the Compose project directory (see the path-resolution
  note above), so no `env_file:` and no `--env-file` is needed.
- **`gh` is authenticated from `GITHUB_PERSONAL_ACCESS_TOKEN`.** Set by hand in
  `Docker/.env` (not by `update-token.sh`, matching resume-2026). The overlay
  maps it to `GH_TOKEN` (what `gh` actually reads) and also passes it under its
  original name for anything else that expects it (the `create-pr` skill).
- **`claude-home` is bind-mounted, not a named volume.** `./claude-home`
  (→ `Docker/claude-home`, git-ignored) mounts at `/home/node/.claude` so
  Claude's session history, plans, and settings persist across
  `make docker-rebuild` (`docker compose down -v`) — a named volume would be
  wiped by the `-v`. `devcontainer.json`'s `initializeCommand` does
  `mkdir -p Docker/claude-home` on the host first, so Compose does not
  auto-create it root-owned. Docker Desktop's virtiofs maps the host owner to
  the in-container `node` (uid 1000), so it is writable with no `chown` step.
- **Extension list ported as-is**, minus the accidental duplicate
  `ms-playwright.playwright` entry in the source. `Anthropic.claude-code` and
  `github.vscode-github-actions` stay.

## Verified

- `docker compose -f Docker/docker-compose.yaml -f .devcontainer/docker-compose.yml config`
  validates; the `devcontainer` service resolves `context` to the repo root,
  `dockerfile: Docker/Dockerfile.node`, `target: development`,
  `depends_on.postgres.condition: service_healthy`, and the
  `node_modules_devcontainer` volume. `workshop` stays excluded (its profile
  is not passed).
- `… up -d --build devcontainer` from a clean state: compose output shows
  `postgres Started` → `postgres Waiting` → `postgres Healthy` →
  `devcontainer Starting` — the health gate holds.
- Inside the container: `whoami` → `node`, `node -v` → `v26.6.0`, `pwd` →
  `/app`, `printenv DATABASE_URL` → the `postgres://…@postgres:5432/sorrel`
  URL. `node_modules` has 359 entries with `.bin/next` and `.bin/tsc`;
  `require('next/package.json').version` → `16.3.4` — the image's `npm ci`
  result is present through the volume.
- `node -e 'net.connect(5432, "postgres")'` connects — Postgres is reachable
  by compose service name, no Neon.
- `devcontainer.json` parses as strict JSON.
- `make docker-up` is unaffected: its `COMPOSE` variable names only
  `Docker/docker-compose.yaml`, so the overlay never enters that path.
- With a throwaway `Docker/.env`
  (`CLAUDE_CODE_OAUTH_TOKEN=…`, `GITHUB_PERSONAL_ACCESS_TOKEN=…`):
  `docker compose config` interpolates both; inside the running container
  `printenv` shows `CLAUDE_CODE_OAUTH_TOKEN`, `GH_TOKEN`, and
  `GITHUB_PERSONAL_ACCESS_TOKEN` all set. Without `Docker/.env` they resolve
  to `""` and `config` is warning-free.
- `/home/node/.claude` is the bind mount; `touch` there as `node` succeeds and
  the file appears in host `Docker/claude-home/` — persistence path confirmed.
- **Not verifiable without the editor:** the `common-utils` feature, the
  `postCreateCommand`, and `initializeCommand` only run under the devcontainer
  CLI / VS Code, not plain `docker compose`. zsh-as-default, `gh` on `PATH`,
  and host-side `mkdir` of `claude-home` are checked on first "Reopen in
  Container".
- **Editor run, 2026-09-08:** first "Reopen in Container" failed in the
  `github-cli` feature build with exit 127 — the feature is Debian-only. Fixed
  by dropping the feature and installing `gh` via `postCreateCommand`
  (`sudo apk add --no-cache github-cli`); see the amended decision above.

## Rules this sets

- The devcontainer tracks the `development` stage. A change to that stage in
  `Docker/Dockerfile.node` reaches the devcontainer with no `.devcontainer/`
  edit.
- New interactive CLI tooling for the devcontainer goes in `features` (or a
  `postCreateCommand`), never a new Dockerfile stage — the image stays the one
  `app` / `testing` / CI share. **Vet a feature for Alpine support first** —
  the base image is `node:*-alpine`, and Debian-only features (e.g.
  `github-cli`) fail the build with exit 127. When there is no Alpine-capable
  feature, `postCreateCommand: "sudo apk add …"` is the fallback.
- Secrets for the devcontainer live in git-ignored `Docker/.env` (template:
  `Docker/.env.example`), read only through Compose `${…}` interpolation of the
  auto-loaded project-dir `.env`. Only the `devcontainer` service reads them.
- `make docker-update-token` is the only way the Claude token is refreshed;
  `make docker-up` deliberately does **not** depend on it (resume-2026 did),
  because `make docker-up` no longer starts the devcontainer.
- **M0.18** publishes the preseeded `sorrel-node` image; when M0.19 repoints
  `app` at it, the `devcontainer` overlay's `image:` / `build:` follow the
  same reference.
