# One loading standard for the site

## Context

When you switch covens, nothing happens on screen. The switcher calls a bare `router.push` ([WorkspaceSwitcher/index.tsx:36-43](src/components/WorkspaceSwitcher/index.tsx#L36-L43)), the coven layout and page block on several uncached reads, and Next keeps the old coven's page up until the new one is ready. The same silence covers the site nav, the section navs (Ingredients, Members…), the account menu, the brand link, the coven home's Contents links, about ten other bare `router.push` calls, signing in with a provider, linking and unlinking a sign-in method, and the Combobox while it searches.

The site already has good pieces, but nothing ties them together. There are three loading tiers, and only some places use them:

- **Region skeletons:** `TabPanelLoading`, `ModalLoading`, and the duplicate-name and facet-count shimmers.
- **Control pending looks:** `BusyButton`, `MenuButton`'s own copy of the spinner, `.field__busy` and `LinkHint`.
- **The fade-in on arrival:** the `arrived` mixin.

Three places own a navigation transition: `ListFrame`, `TabSwitch` and `RouteModalProvider`. The timings are literals (0.8s spin, 1.4s shimmer, 150, 200 and 300ms fades). Under reduced motion they behave three different ways: the spinner slows, the skeleton stops, and `.field__busy` loses its delay.

Two constraints apply:

- **No `loading.tsx` and no route-level `<Suspense>`.** That would turn the guards' 404, 403 and 308 into 200s and break rendering without JavaScript ([tabbed-page.md:77-80](claude-docs/components/tabbed-page.md#L77-L80), [ingredient-entry.md:71](claude-docs/components/ingredient-entry.md#L71)). So every pending state is a client transition: `router.push` inside `useTransition` stays pending until the new page has rendered. `tab-switch.tsx` already proves this works.
- **No styling past the tokens before a design review** (`.claude/rules/components.md`).

## The standard (owner's calls, 2026-10-19)

Every wait has the same three parts. Each part does one job, and none of them repeats another's.

| Part        | What it looks like                                                                                                                                                                       | Says to a screen reader                                                          | When                                                        |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Control** | The pressed thing answers at once: the switcher shows the picked coven's name, a tab's pill moves, a button keeps its label and gains a spinner, and a link shows the `LinkHint` dot.    | `aria-busy` on the control, and a button's busy label.                           | At once. Spinners and the dot appear after **100ms**.       |
| **Region**  | The skeleton of what is coming replaces the area that changes: cards, table, form or page blocks. The new content fades in over it.                                                      | The skeleton's one `<output>` status ("Loading"). This is the only announcement. | At once. Skeletons are not delayed (the existing tab call). |
| **Page**    | A thin indeterminate bar along the bottom edge of the global bar, on **every** navigation: coven switch, site and section links, tabs, filters, pager, route modals and full page loads. | Nothing. It is `aria-hidden` and only adds a visual cue.                         | After **100ms**.                                            |

- **Reduced motion:** the spinner, the shimmer and the bar all become **one slow opacity pulse**, never a still mark. This replaces today's slowed spinner and still skeleton.
- **Coven switch:** the old coven's page is taken away at once, so nobody acts on the wrong coven's data. The **destination section's** skeleton takes its place. `pathInCoven` already knows the section: cards for Ingredients, the tabbed table for People, page blocks for the coven home, a form for Create Coven. After the switch, focus returns to the switcher. The `[slug]` layout remounts, so focus would otherwise drop to `<body>`. This last part is my inference, not sourced, and will be checked in the design review.
- **Optimistic UI** stays out of scope. Every mutation keeps a pending state.

The research, with sources (NN/g, Primer, Carbon, GitLab Pajamas, React and Next docs, WCAG 4.1.3, MDN), goes into the standard's doc. Each claim names its source, and inferences are marked as inferences.

## Examples

**Coven switch, Hollow Oak → Willow Hall, on Ingredients:**

```
│ Sorrel & Salt   Compendium  Your Covens        ☰ │
│▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│  page: bar
│ [Willow Hall ⟳ ▾]  Ingredients  Members          │  control: picked name + spinner, aria-busy
│ ┌────────┐ ┌────────┐ ┌────────┐                 │  region: the Ingredients card skeleton,
│ │░░░░░░  │ │░░░░░░  │ │░░░░░░  │                 │  <output>Loading</output>
│ └────────┘ └────────┘ └────────┘                 │
```

**More examples:**

- **Section link (Members):**
  - Page: the bar.
  - Control: the Members tab shows the dot.
  - Region: the coven body shows the table skeleton.
- **Site link (Compendium):**
  - Page: the bar.
  - Control: the dot.
  - Region: `#main` shows the page-blocks skeleton.
- **Filter or pager:** unchanged, plus the bar.
  - Control: the filter row greys (`busy-faded`).
  - Region: the list skeleton holds its height.
- **Save in a modal:** unchanged, with no bar, because nothing navigates.
  - Control: `BusyButton` shows "Saving Ingredient" and a spinner.
  - Its `router.refresh()` afterwards runs through the same navigation hook, so the bar shows if the refresh is slow.
- **Sign in with Google:**
  - Control: the provider button becomes busy ("Signing In") with a spinner.
  - Page: the bar stays up until the browser leaves.
- **Combobox search:**
  - Control: the visible `.field__busy` spinner appears in the input. Today there is only a hidden status.
- **Substitute summary:**
  - Region: a one-line skeleton replaces the plain "Loading…" text.

## The task

**One task, one PR** (the owner's call). It is minted with `/create-feature-task` before any code.

- **Input:** the owner's own words: "Switching covens has no loading state. Also there are lots of other places where there's no clear loading state. Can we come up with something and make cohesion for loading in the site?"
- **Questions the skill still asks:** audience, area, milestone, the user story and the criteria. It follows its own approval gates.
- **Id:** `M<wave>.<n>` for the chosen wave, checked against the board and `TASKS.md` for the next free number.
- **After minting:**
  - The entry's acceptance criteria are the three-part standard above, the coven-switch behaviour, the guard, and the gaps listed under lanes D and E.
  - `sync <ID>` updates the issue.
  - `reorder` runs as a dry run, then `--apply`.

**Where the minting's doc edits go:** to `/app` (the owner's call), and they are committed with the work already there. Those edits are:

- the entry in `claude-docs/tasks/m<wave>.md`
- the wave-table row in `TASKS.md`
- the id in the milestone description, which lives on GitHub

`sync <ID>` and `reorder` run from `/app`, the checkout holding the edit. They are not copied into the task branch.

**Branch:** `feature/<id>-loading-standard`, off fresh staging, in the worktree `/home/node/worktrees/<id>`. The code goes there, along with the task's own docs (lane G: `loading.md`, the decision record, the component docs), so they land in the PR that makes them true.

- Each lane gets its own worktree, `/home/node/worktrees/<id>-<lane>`, on a lane branch from the task branch.
- Each lane messages main with every commit hash, and main merges each lane commit into the task branch as it lands.
- **Status:**
  - The first lane brief's first step sets the task to `In Progress`.
  - It moves to `In Review` when the PR opens.

**Lane T details**

- The gate e2e spec:
  - Slow the RSC (React Server Components) response with `page.route`, then switch covens.
  - The switcher is `aria-busy`.
  - A status is present, and the old coven's cards are gone.
  - The new coven renders.
  - Focus is on the switcher.
  - Axe passes during the wait.
- The same check for a section link and a site link.
- A `reducedMotion: 'reduce'` run.
- Component tests for the store, `PendingLink` (the modifier-click fall-through), the bar's delay (fake timers), the switcher and `CovenBody`.
- Every assertion checks state and roles, never copy.

**Lane A details**

- `src/lib/navigation/`: the external store, `usePendingNavigation`, `refresh`, `reportLeaving`, `PendingLink`, and `NavigationBar` (behaviour only, with styling from B).
- Mounted in `providers.tsx`.
- The store's `target` type is the interface C and D build on. **A merges first.**
- `tests/guards/navigation.test.ts`, with today's offenders as its baseline.

**Lane B details**

- The `loading-motion` mixin and the reduced-motion pulse.
- `.field__busy` uses the shared delay, and `.filter-row` uses `busy-faded`.
