# M15.83 — Typing Into a Suggestion Field Writes Only What Changed

M15.82 traced one keystroke on `/compendium` and found that the shared suggestion field, `src/components/Combobox/`, writes attributes and reads layout on every key. This record says why each happens and what was changed. The measured figures are in the PR body.

## Why the input's `name` is rewritten, and why it is left alone

React DOM writes it, not the Combobox. React's `updateInput` (`node_modules/react-dom/cjs/react-dom-client.development.js`, the function at line 1833; the production build's copy is at line 1269) first sets `element.name = ""`, then sets the name back. With no `name` prop, it adds `name=""` and removes it again. Each run therefore makes two writes to `name`, even when the value ends where it started. React runs `updateInput` in two places:

- **After every input event.** The change event queues the input for React's restore step (line 3700), and `restoreStateOfTarget` (line 3360) calls `updateInput`. This happens whether the input is controlled or not.
- **On every commit of the input** (line 22565). React commits a host element whenever its props object is new (line 12965), and Downshift's `getInputProps` builds a new one on every render.

The field cannot stop either while React renders the `<input>`. Setting `name` from a ref instead does not help, because `updateInput` would remove it on the next run. The only way out is an input React does not own: the Combobox would create it, set its attributes and attach its listeners itself, and keep it in the server-rendered page so the search form still works before hydration. The owner judged that too large and risky a change to a field every form uses, so `name` is left to React, and the component test does not watch it.

## Why `aria-busy` is written

React writes an ordinary attribute only when its value changes, so `aria-busy` is never rewritten unchanged. The writes M15.82 saw are real changes. The search box marks itself busy on a key whose text differs from the query it last looked up (`src/components/IngredientSearch/search-box.tsx`, its `pending`), and clears the mark when the answer arrives. Nothing is changed here. The component test proves a key that leaves the lookup in flight writes no `aria-busy`.

## When Floating UI reads the input's size and position

`useListPosition` (`src/components/Combobox/position.ts`) places the list with Floating UI and follows it with `autoUpdate` only while the list is open.

- **While closed:** one computation, when the hidden list first mounts. Nothing after that.
- **While open:** a computation whenever the ResizeObserver sees the input or the list change size, for example when the rows change the list's height. Each computation measured the phone's bottom bar three times (once in each of `flip`, `shift` and `size`), and the `size` step wrote the list's `width` and `--combobox-list-room` even when they were unchanged.
- **On each reopen:** `autoUpdate` subscribes again. It reads every scrolling ancestor's style and the input's position, then computes. React runs that effect straight after a keystroke's render, so the reads land inside the keystroke. On `/compendium` the list closes and reopens while a lookup is pending with no rows to keep, for example when the typed text first reaches the search floor.

## What changed

- **The subscription outlives a close that only a pending lookup causes.** The list is followed while it is open, or while it is wanted and a lookup is in flight. So the answer's reopen subscribes nothing again. A close by Escape, a pick or a blur still ends the subscription.
- **Each computation measures the bottom bar once,** and the three steps share the result.
- **The `size` step writes `width` and `--combobox-list-room` only when they change.**
- **Kept:** the ResizeObserver and the layout-shift tracking. The list's own size decides whether it flips above the box, and a page that shifts moves the box.

`tests/components/Combobox/keystroke.test.tsx` holds the proofs: no `aria-busy` write on a key that leaves it as it was, no unchanged style write on the list across a key and a pending close, and one subscription across that close.
