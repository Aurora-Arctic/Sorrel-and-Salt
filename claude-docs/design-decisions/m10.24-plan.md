## Context

The project has no declared browser target. The only statement is one bullet in
`claude-docs/styling.md` ("Binding rules", line 88): Next's default modern
targets, Chrome, Edge and Firefox 111 and Safari 16.4, which Next computed as
"Baseline Widely Available" on 2025-10-01 and froze. Nothing enforces it:
there is no `browserslist` key, no `.browserslistrc`, no compatibility lint,
and Playwright runs Chromium only (three projects, all `Desktop Chrome`;
`Docker/Dockerfile.e2e` installs Chromium alone since MB.237).

The code has already moved past that frozen floor. `:has()` (six Sass files)
needs Firefox 121, `URL.canParse()` (reached in the browser through the
reference form's resolver) needs Chrome 120 and Safari 17, `<search>` needs
Safari 17, `inert` needs Firefox 112, `color-mix()` on `var()` tokens needs
Firefox 113. None of this was caught, because nothing could catch it.

**Decisions the owner made on 2026-10-12:**

1. **The floor is Baseline Widely Available**: a feature may be used unguarded
   once it has shipped in Chrome, Edge, Firefox and Safari for 30 months.
2. **Below the floor the app degrades and never breaks.** Core flows work
   without the newer feature; a feature past the floor needs a fallback or must
   be a pure enhancement.
3. **CI stays Chromium only.** WebKit, Firefox and a phone profile are an
   occasional local audit, never a gate.
4. **Enforcement** is a `browserslist` entry plus a stylelint rule, a guard test
   over the source, and a line in the design-review checklist.

## What the floor resolves to

`browserslist` 4.28.9 (installed, with `baseline-browser-mapping` 2.11.21) understands
the query `baseline widely available`. It is rolling: the mapping package takes
today's date minus 30 months, against data pinned by the lockfile. The floor
only ever rises, so a build or lint that passes today still passes tomorrow.

| Browser    | Query today (2026-10-12) | Next's frozen default |
| ---------- | ------------------------ | --------------------- |
| Chrome     | 123                      | 111                   |
| Edge       | 123                      | 111                   |
| Firefox    | 124                      | 111                   |
| Safari     | 17.4                     | 16.4                  |
| iOS Safari | 17.4                     | 16.4                  |

Verified with `npx browserslist "baseline widely available"` and
`… on 2025-10-01` (which reproduces Next's list exactly).

**Against the new floor, the current code is compliant** except for pure
enhancements, which the degrade rule allows: `@starting-style` (Modal, IconTip
fade-ins; Firefox 129, widely available about 2027-02), `scrollbar-gutter` and
`scrollbar-width` (Modal, TabbedPage; Safari 18.2, about 2027-06), `light-dark()`
(Safari 17.5; Lightning CSS lowers it for the browserslist, so it never reaches
a browser), and unprefixed `line-clamp` beside its `-webkit-box` fallback. The
dates are my estimates from release dates; the stylelint rule in step 2 reports
the authoritative ones.

Pinning the date (`baseline widely available on YYYY-MM-DD`) is possible and
rejected: it is the version list the owner chose not to maintain, under another
name. Lightning CSS, Turbopack's default and the only CSS pipeline here, reads
the same browserslist, so one line drives both lowering and lint.

## The rule, in one paragraph (for `CLAUDE.md`)

> **The browser floor is Baseline Widely Available, and below it the app
> degrades, never breaks.** `package.json`'s `browserslist` is the one
> statement of it; Lightning CSS lowers to it and `npm run lint:css` refuses
> CSS past it. A feature past the floor is allowed only as an enhancement whose
> absence changes nothing a person needs, inside `@supports` with a fallback,
> or in JS behind a `typeof` check, and says so in a comment naming the
> Baseline date. Client-reachable JS is held by `tests/guards/browser-floor.test.ts`.
> Playwright gates on Chromium; WebKit, Firefox and a phone profile are a local
> audit (`npm run e2e:audit`). Long form: `.claude/rules/components.md`.

### Task A: the floor, its two mechanical guards, and the rule (est. 4h)

**1. Declare the floor.** Add to `package.json`:

```json
"browserslist": ["baseline widely available"]
```

Next's docs (`node_modules/next/dist/docs/03-architecture/supported-browsers.md`)
name this key as the override. Confirm Lightning CSS picks it up: build with a
non-default `NEXT_DIST_DIR` (never a bare `npm run build` in `/app`) and check
`light-dark()` is still lowered in the emitted CSS, since Safari 17.4 is the
floor and `light-dark()` needs 17.5.

**2. Lint CSS against it.** Add `stylelint-plugin-use-baseline` (1.4.7, peer
`stylelint ^16 || ^17`, data from `web-features`) to devDependencies and to
`.stylelintrc.json`:

```json
"plugins": ["stylelint-plugin-use-baseline"],
"rules": { "plugin/use-baseline": [true, { "available": "widely" }] }
```

It reports properties, values, at-rules, functions, units, pseudo-classes and
pseudo-elements past the floor, and skips anything inside `@supports`. Run
`npm run lint:css` and resolve every report one of three ways, in this order:
`@supports` with a fallback; a `/* stylelint-disable-next-line plugin/use-baseline -- enhancement: <what is lost>, widely available <date> */`
for a pure enhancement; or remove the feature. Expected reports are the
enhancement list above and nothing else; anything more is a finding to fix in
this PR and name in its body. The plugin's SCSS behaviour is undocumented: Sass
variables in values may produce false positives, handled by `ignoreProperties`
on the specific property with a comment, and if it proves unusable on SCSS the
fallback is to lint the compiled output (compile with `sass`'s `compileString`
as `tests/scss/tokens.test.ts` does, then run stylelint on plain CSS). CI's
`lint` leg (`checks.yml`) already runs `lint:css`, so no workflow change.

**3. Guard client-reachable JS.** `tests/guards/browser-floor.test.ts`, in
the pattern of `tests/guards/no-tracked-books.test.ts`: a header comment with
the constraint and its doc, a `describe` named by the task id, a precondition
so an empty scan cannot pass. It holds a short hand-kept list of web APIs that
are past the floor today, each as `{ pattern, feature }` where `feature` is a
`web-features` id (add `web-features` as a direct devDependency; the lockfile
pins its data). For each entry the test reads `features[id].status.baseline`
and `baseline_high_date`:

- if the feature is now widely available, the test fails with "delete this
  entry", so the list prunes itself;
- otherwise it greps `src/**/*.{ts,tsx}` except `src/db/**`, `src/modules/*/services/**`
  and the GraphQL layer (server-only by rules 1 and 2), and fails on a match
  not on a line that also carries `typeof` or `in window`/`in navigator`.

Seed list, from the inventory: `structuredClone`, `.at(`, `Object.hasOwn`,
`findLast`, `toSorted`/`toReversed`, `Promise.withResolvers`, `AbortSignal.any`,
`Set.prototype.union` and friends, `startViewTransition`, `requestIdleCallback`
on Safari, `navigator.share`. Several of these are already past the floor and
will be rejected by the test's own first rule, which is the point: the
`web-features` data decides, not the list. `tsconfig`'s `lib` stays at
`es2020`, which already stops the ES2022+ built-ins at typecheck.

**4. Write the rule down, one home per fact.**

- `CLAUDE.md`, Conventions: the paragraph above, as one bold line.
- `.claude/rules/components.md`, Styling: the long form. Floor, the three
  allowed shapes for a feature past it, the disable-comment wording, what the
  guard test holds, the audit command. Its `paths:` already cover `src/scss/**`,
  `src/components/**` and `src/app/**/*.tsx`.
- `claude-docs/styling.md`, "Binding rules" line 88: replace the frozen-target
  bullet with the Baseline rule and the argument (rolling floor, Lightning CSS,
  why not pinned); "Designing a section" line 905: add the review line, "each
  review checks the CSS it adds against `npm run lint:css` and looks at the
  section in Safari and Firefox, the audit profiles when a layout changed".
  Fix line 850's "Safari 16.4, the oldest browser supported".
- `claude-docs/commands.md`: `e2e:audit` row (from Task B) and the plugin in
  the `lint:css` row.
- `claude-docs/design-decisions/m10.23-browser-floor.md`: the decision, the

### Task B: the local cross-browser audit (est. 3h)

Not a CI gate. The devcontainer has no browsers and must never install any;
its runner connects to the `playwright-server` compose service, built from
`Dockerfile.e2e`'s `headed` stage, Chromium only.

**1. A browser source with WebKit and Firefox.** Add a `playwright-audit`
service to `Docker/docker-compose.yaml` on a new `audit` profile, image
`mcr.microsoft.com/playwright:v1.63.0-noble` (the lockfile's `@playwright/test`
is 1.63.0; the image ships all three engines with their libraries, which is why
MB.237 removed it from CI's path), command
`npx playwright@1.63.0 run-server --port 4445 --host 0.0.0.0`, no repo mount
and no `npm ci`. A `make playwright-audit-up` target beside
`playwright-server-up` (Makefile line 186). The pull is a one-time local cost.

**2. Audit projects in `playwright.config.ts`.** Add `webkit`, `firefox` and
`phone` (`devices['iPhone 15']`, so `isMobile`, `hasTouch` and the safe-area
inset are real, unlike the 375px viewport loops in `shell.spec.ts`) projects
that exist only when `E2E_AUDIT=1`, with `testIgnore` for the two
provider/cache specs. Coverage already runs only under the `chromium` project
(`tests/e2e/fixtures.ts:24-38`). `wsEndpoint` reads `PLAYWRIGHT_AUDIT_WS_ENDPOINT`
(`ws://playwright-audit:4445/`) for these projects.

**3. `npm run e2e:audit`** = `E2E_AUDIT=1 playwright test --project webkit --project firefox --project phone`,
wrapped on `flock /tmp/sorrel-e2e.lock` like every e2e run.

**4. Run it once and record the result.** Expect failures: the suite was never
run on WebKit or Firefox. Each failure becomes a line in the PR body and, where
it is a real bug, its own MB task; the audit PR does not fix them. Document in
`claude-docs/testing/e2e.md` ("E2E") and `claude-docs/debugging.md`.
