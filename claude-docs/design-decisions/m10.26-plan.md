# M10.26: Invited By on the coven members table, scoped

_Recorded on 2026-10-12 from the scoping plan. The owner approved minting the task; the build is M10.26 itself, on its own branch._

## Context

The owner wants each row of the members table at `/coven/[slug]/members` to show who invited that member. Today the database knows this, but only indirectly: an invitation's `created_by` is the inviter and its `accepted_by` is who accepted it. The membership row has no link back to the invitation, and its own `created_by` is the person who accepted, because acceptance runs under their session.

Working the inviter out at read time, by joining `invitations` on `workspace_id` plus `accepted_by`, gets four cases wrong:

1. **Coven creators** joined without an invitation, so they have no inviter. That is correct, but the join can't tell it apart from a lost link.
2. **Someone removed and invited back** has several accepted invitations. Taking "the latest" means comparing `accepted_at` (the database's `now()`) with `joined_at`, which `reviveMembership` sets from the app's clock (`new Date()`). The two clocks aren't guaranteed to order the same way.
3. **Accepting while already a member** stamps the invitation (`acceptInvitation` runs whatever `seated` is) but leaves the membership alone. The join would name an inviter who didn't bring them in.
4. **Duplicate pending invitations** to one address are allowed (`createInvitation`, src/modules/coven/services/invitations.ts:41). Any one of them can be accepted, including while the person is already a member, which is case 3 again.

**Approach: record the inviter on the membership at the moment it's written, not afterwards.** Add a nullable `workspace_members.invited_by` column. Acceptance sets it from the stamped invitation's `created_by` whenever it inserts or revives a membership. Each case above then falls out of the write instead of a guess:

| Case                                 | `invited_by`                                                               |
| ------------------------------------ | -------------------------------------------------------------------------- |
| Creator (`workspace-creation.ts:74`) | null, so the cell is empty                                                 |
| Fresh accept (insert)                | the invitation's `created_by`                                              |
| Removed, then re-invited (revive)    | overwritten with the new inviter                                           |
| Accepting while already a member     | untouched, because no membership write happens                             |
| Duplicate invitations                | whichever one was accepted, and only if it seated them                     |
| Role changed or made owner later     | untouched, because `updateMembershipRole` doesn't set it                   |
| Inviter since removed or deleted     | still named: they once held a seat, so the MB.10 name finder resolves them |

**No backfill.** Acceptance (M7.5, PR #917) is on staging but not on `main`, whose latest release is 0.7.0. So no production membership came from an invitation. Staging rows accepted before the migration stay empty. Seeds and fixtures leave the column null unless a test sets it.

**Why a user id and not an `invitation_id`.** An invitation's `created_by` never changes, so copying it loses nothing. A user id keeps the read path at one column, batched into the page's existing `displayNamesOf` call, with no join onto a `namedWrites` table and no new rule 4 question about soft-deleted invitations.

## Branch and acceptance criteria

- Base its branch on M7.6's once M7.6 is committed, or on staging if M7.6 has merged by then. M7.6 moves the members page to `(people)/members/`.
- Acceptance criteria for the entry:
  - A member who accepted an invitation shows its sender
  - A creator's cell is empty
  - Someone invited back shows the latest inviter

  - Names resolve without an N+1 query
  - A viewer still can't read the list

## Changes

### Schema and migration

- `src/modules/coven/schema/workspaces.ts`: add `invitedBy: uuid('invited_by').references(() => users.id)`, nullable, with a one-line comment saying it is written once at acceptance and is not `created_by`.
- `npm run db:generate` writes the next migration (0070): a column add plus a foreign key, expand only, so no `.ack.md`. Run `npm run check:destructive-ddl`.

### Repository (`src/db/repository/memberships.ts`, `types.ts`)

- `insertMembership(workspaceId, userId, role, invitedBy?: string)` and `reviveMembership(workspaceId, userId, role, invitedBy: string | null)`. Revival always sets the column, so an old inviter can't linger.
- `findMemberPage` already returns the row, so `invitedBy` comes back with no finder change.

### Service (`src/modules/identity/services/invitation-acceptance.ts:157-176`)

- Pass `stamped.createdBy` (the `InvitationRow` that `write.acceptInvitation` returns) to the revive and insert calls. The value comes from the database row inside `withAudit`, never from the request.
- `workspace-creation.ts:74` stays as it is, so creators keep a null `invited_by`.

### GraphQL (`src/modules/coven/graphql/workspace.ts:26-38`)

- Add `invitedBy: t.field({ type: CoMemberRef, nullable: true, resolve: (m) => m.invitedBy ? { id: m.invitedBy } : null })`. `CoMember.name` already batches through `loaders.usersById` (src/modules/identity/loaders/users-by-id.ts), so there's no new loader.
- Regenerate the SDL snapshot (`src/graphql/schema.graphql`) and run `npm run codegen` (`src/gql/`).

### Page and component

- `(people)/members/page.tsx`: add `node.invitedBy` to the `ids` batch passed to `displayNamesOf`, and map it to `invitedBy: node.invitedBy ? editorOf(node.invitedBy) : null`.
- `src/components/MemberList/types.ts`: add `invitedBy: string | null` to `MemberListEntry`.
- `src/components/MemberList/index.tsx`: add an "Invited By" column between Joined and Updated. It shows the name and is left empty when the value is null, following the Updated column's pattern.
- `index.stories.tsx`: fill in the out-of-date `MEMBERS` fixtures with `updatedBy`, `updatedAt` and `invitedBy`, including one creator row with no inviter.

### Docs

- `claude-docs/db/workspaces-and-membership.md`: add the column.
