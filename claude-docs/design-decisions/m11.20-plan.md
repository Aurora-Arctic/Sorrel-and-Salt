# M11.20 — A Curator Role: the Compendium Without the People Page

Issue #962 · branch `feature/m11.20-editors-curate-compendium-without-people-page` · worktree `/home/node/worktrees/m11.20` (off `origin/staging` at `99435190`) · 6h.

## Context

Today the site role is `user` or `admin`, and one check, `role === 'admin'`, opens every admin screen. The owner wants to hand out curation (the Compendium, its vocabularies and the references) without also handing out the people page (who is an admin, who may create a coven, impersonation, invitations). This adds a third role, **`curator`**. A curator passes a new curator-or-admin check on every curation screen and fails the admin-only check on everything under the people page. An admin gives and takes away the role on the user screen, and each change lands in the privilege ledger like any other.

### Who sees what

| Visitor     | `/admin` index & nav | Curation pages | People section in nav | `/admin/users`, a user's details, invitations, privilege ledger |
| ----------- | -------------------- | -------------- | --------------------- | --------------------------------------------------------------- |
| User        | 403                  | 403            | no                    | 403                                                             |
| **Curator** | yes                  | yes            | **no**                | **403**                                                         |
| Admin       | yes                  | yes            | yes                   | yes                                                             |

**The user screen is the admin's tool, not the curator's.** The Change Role dialog lives on `/admin/users` and the user modal, under the People section. Only admins see that section, and only admins use the dialog. A curator never needs the People item: they never set roles, and their own role is shown to them nowhere but in what `/admin` lets them open. So the People item is shown to admins and hidden from curators, and the dialog is the only place the curator role is granted or taken away.

**Out of scope here:** the backlog's "V Fast Follow" item, "Allow editors to view some of other editors/admins info so they can collaborate" (`claude-docs/backlog.md`). Curators get no access to People in M11.20, and no task is minted for the item now (the owner's call, 2026-10-16). The backlog line stays as it is, apart from saying _curators_ where it says _editors_.

### Decisions (2026-10-16, with the owner)

- **The role is called `curator`** ("Curator" on screen), not `editor`. The task entry and issue title are corrected to match, along with the slug in the decision record's file name. The branch name stays as created.

## Design

### The two proofs (rule 5, on the site role)

In `src/modules/identity/services/site-admin.ts`:

- **`Curator`** is `{ userId }` under a `curator` brand the file doesn't export. `assertCurator(session, reason?)` returns it when the role is `curator` or `admin`, and otherwise throws `Forbidden`.
- **`SiteAdmin`** becomes `Curator & { [adminBrand]: true }`. Every admin is a curator, not every curator an admin. A caller holding an admin's proof never needs to ask for both. `assertSiteAdmin` is unchanged.
- `admin-changes.ts` gains an `isCurator(session)` beside `isSiteAdmin`. It is the one place the set of curating roles is written down.

Repository (`src/db/repository/types.ts`, `write.ts`):

- **Take `Curator`:** the compendium-tier writer methods (`insertInCompendium`, `updateByIdInCompendium`, `softDeleteByIdInCompendium`, `deleteLapsedSlugRetirements`, and the three `carry*Rename`s).
- **Keep `SiteAdmin`:** the people-page methods (`lockLiveAdmins`, the pause and its resume, the user-list and ledger finders in `users.ts`, and the site-tier invitation insert, revoke and list).

Services:

- **Switch to `assertCurator` / `Curator`:** the curation services, `ingredients/services/{compendium,references}.ts` and the `vocabulary/services/*` (astrology, categories, category-groups, curated-writes, deities, deity-traditions, ingredient-form-groups, ingredient-form-values). In `references.ts`, `'admin' in proof` becomes `'curator' in proof`.
- **Unchanged:** every identity people-page service, `workshop-access.ts`, and `coven/services/memberships.ts` `membershipsOf`. The last one widens only for `role === 'admin'`, so a curator reads no one else's covens.

### Database: one migration, `0073_curator-role`

1. `ALTER TYPE user_role ADD VALUE 'curator' AFTER 'user'` and `ALTER TYPE user_privilege ADD VALUE 'curator'`.
2. Replace the CHECK. `users_admin_can_create_workspace` (`role <> 'admin' or …`) gives way to `users_privileged_can_create_workspace` (`role = 'user' or can_create_workspace`). The new CHECK doesn't name the new enum value, which avoids Postgres's "unsafe use of new value" inside the migration's transaction. Both are drop-and-add, so a `0073_curator-role.ack.md` sidecar is needed (MB.48); 0072 is the precedent.
3. `CREATE OR REPLACE FUNCTION record_privilege_change()`. `admin` changes when `(OLD.role = 'admin') IS DISTINCT FROM (NEW.role = 'admin')`, and `curator` the same way, so curator→admin writes a `curator` revoke and an `admin` grant at one instant. The insert trigger's WHEN becomes `NEW.role <> 'user' OR NEW.can_create_workspace`. The update trigger already fires on any change to `role`.
4. Schema files follow: `userRole` gains `curator`, `userPrivilege` gains `curator`, and the check is renamed. I'll run `db:generate` for the enum and check parts, then hand-append the function and trigger, as 0056 was written. `check:destructive-ddl` is then run on it.

### Role writes (`identity/services/user-role.ts`, `workspace-creation.ts`)

`setUserRole(session, userId, role, note?)`, still behind `assertAdminChangesOpen`, so the primary admin's pause covers it:

- Asking for the role the user already has is refused with a `Forbidden` naming them, and nothing is written.
- Leaving `admin`, to `curator` or `user`, runs today's revoke guards: the live-admin lock, the primary-admin refusal and the last-admin refusal.
- To `admin`: `writeAdminGrant`, unchanged.
- To `curator`: a new `writeCuratorGrant` writes `{ role: 'curator', canCreateWorkspace: true }` in one update. That covers becoming a curator setting the flag in the same write.
- `curator` → `user` leaves the flag set, as revoking admin does.
- A move between curator and admin keeps the flag; the CHECK guarantees it.

`revokeWorkspaceCreation` refuses any role but `user`, and the refusal says which role to take away first.

The admin-invitation accept (`invitation-acceptance.ts`) already grants when `role !== 'admin'`, so a curator accepting one becomes an admin. A test pins the two ledger rows that writes.
