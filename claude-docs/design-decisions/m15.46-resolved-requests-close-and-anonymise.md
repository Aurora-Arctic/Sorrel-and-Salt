# M15.46: a resolved request closes on its own, and a closed one is anonymised

## Decision

A support request that staff or its sender resolve gets one durable job run (claude-docs/design-decisions/m15.49-job-mechanism.md). The run sends the closing-soon notice on day 5, closes the request on day 7, and anonymises it twelve calendar months after the close. A request staff close straight from open or waiting gets the same run, which only anonymises it. Readers do not wait for the job: a `resolved` row whose seven days have passed reads as `closed`, closed on its seventh day.

## Shape

- **Files.** `src/modules/support/jobs/support-lifecycle.ts` is the workflow, and `support-lifecycle-steps.ts` holds its steps. The steps call `src/modules/support/services/retention.ts`. The services start runs through `services/retention-start.ts`, which is a separate file so that a job never imports itself.
- **Which services start a run.** `resolveSupportRequest` (staff), `resolveMySupportRequest` (the sender) and `closeSupportRequest` each start one after their move is saved. A failed start is logged and never undoes the move. `resolveMySupportRequest` now takes the notifier, so that it can read the origin from it.
- **One run per request.** A run holds a hook token named for the request. A second start while a run is waiting ends at once as `duplicate`. The waiting run re-reads the row each time it wakes, so it picks up a newer resolution. A run ends when it finds the request open, waiting or already anonymised.
- **The step loop.** `advanceStep` reads the row and does whatever is due as the System account, the close and the anonymising included. It then answers `wait n seconds`, `send the notice` or `done`. Sleeps are computed from the row, so a reopen and a second resolve move the deadlines.
- **The notice.** The run receives the notice already rendered, from the service that started it. The step re-reads the row and sends the notice only while the request is still `resolved` with `closing_notice_sent_at` null. It stamps the marker only when the transport accepted the mail. A transport failure throws, so the SDK retries the step (three retries). A notice that fails every retry is given up for that resolution: the run remembers the resolution's timestamp and goes on to close the request on day 7 without the notice. A reopen clears the marker.
- **The close.** `closed_at` is set to `resolved_at` plus 7 days, never to the moment the job ran. A late run or the sweep therefore gives the same date the readers already showed.
- **What anonymising empties.** Subject, message and path become empty strings, and `sender_email` becomes null. `created_by` passes to the System account, and `resolved_by` too when the sender resolved it. Every reply's body is emptied, and a sender-authored reply's `created_by` passes to the System account. **What it keeps:** topic, status, error code, the dates, staff ids and the issue link, so the counts per topic and per month do not change. A `created_by` equal to the System account marks a row as done, because no request is otherwise created by it. The audit writer strips `created_by` from an update, so this one statement is written on the transaction directly. One statement changes both the address and `created_by`, so the one-sender CHECK never sees an address without the signed-out sender.
- **The fallback.** Every admin visit to `/admin/support` starts one sweep run (`support-retention-sweep.ts`), after the response is sent (Next's `after`). The sweep closes every lapsed resolved request and anonymises every request closed twelve months or more ago. It sends no notice. A curator's visit starts none. There is no daily chain, because readers already treat a lapsed row as closed, and only the anonymising needs to happen without a visit.
- **Readers.** In the repository, `asOfNow` maps a lapsed resolved row to `closed`. The status filters and the view arms treat it as closed too, and `moveSupportRequest` refuses to move it. So a sender's message on it opens a linked follow-up, and staff can no longer resolve, close or set waiting on it.
- **The migration.** 0118 adds nullable `closing_notice_sent_at timestamptz`, expand-only.

## Why the run gets the notice already rendered

The email templates are JSX. The Vitest workflow builder bundles a step's local imports with esbuild's `jsx: 'preserve'` and loads the bundle in Node with nothing compiling it afterwards. A step that imported `src/lib/support-mail.ts` broke every workflow test, the existing provisional-account ones included, with `SyntaxError: Unexpected token '<'`. Under `next build` the bundle passes through Next's compiler, so production would probably have worked. The test project would not have. So the starting service renders the notice, and the step only hands it to `deliver`.

The cost is that the rendered mail is a run argument: the sender's address and the request subject sit in the workflow event log for as long as the run's events are kept. The owner's question is in the report: keep this, or move the templates to non-JSX rendering so a step can render from ids.

## Why not a daily job

The provisional cleanup chains itself daily because nothing else removes a lapsed account. Here, a lapsed resolved request already reads as closed, and the per-request run covers the anonymising. The admin-visit sweep is enough for a run that was lost.

## Things not done

- `support_send_counts` keys rate-limit rows by address and is not anonymised. It is a different table with its own window, so it is outside this task.
- The closing-soon mail says the request closes in two days. A run that wakes late, for example a notice sent on day 8 just before the close, sends the same words.
- A twelve-month sleep is pinned to the deployment that started it. The admin-visit sweep is what anonymises a request whose run was lost.
