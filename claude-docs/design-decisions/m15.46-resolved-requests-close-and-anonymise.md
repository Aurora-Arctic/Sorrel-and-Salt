# M15.46: a resolved request closes on its own, and a closed one is anonymised

## Decision

A support request that staff or its sender resolve gets one durable job run (claude-docs/design-decisions/m15.49-job-mechanism.md). The run sends the closing-soon notice on day 5, closes the request on day 7, and anonymises it twelve calendar months after the close. A request staff close straight from open or waiting gets the same run, which only anonymises it. Readers do not wait for the job: a `resolved` row whose seven days have passed reads as `closed`, closed on its seventh day.

## Shape

- **Files.** `src/modules/support/jobs/support-lifecycle.ts` is the workflow, and `support-lifecycle-steps.ts` holds its steps. The steps call `src/modules/support/services/retention.ts`. The services start runs through `services/retention-start.ts`, which is a separate file so that a job never imports itself.
- **Which services start a run.** `resolveSupportRequest` (staff), `resolveMySupportRequest` (the sender) and `closeSupportRequest` each start one after their move is saved. A failed start is logged and never undoes the move. `resolveMySupportRequest` now takes the notifier, so that it can read the origin from it.
- **One run per request.** A run holds a hook token named for the request. A second start while a run is waiting ends at once as `duplicate`. The waiting run re-reads the row each time it wakes, so it picks up a newer resolution. A run ends when it finds the request open, waiting or already anonymised.
- **The step loop.** `advanceStep` reads the row and does whatever is due as the System account, the close and the anonymising included. It then answers `wait n seconds`, `send the notice` or `done`. Sleeps are computed from the row, so a reopen and a second resolve move the deadlines.
- **The notice.** The run receives only the request id and the origin, the site the request was resolved on, which the notice links to. The step re-reads the row and sends the notice only while the request is still `resolved`, with `closing_notice_sent_at` null and its seven days not yet over. It builds the mail then, from the row: the address a signed-out sender gave or the account’s current address, the subject as it stands, and the time left until `resolved_at` plus 7 days, rounded to hours under a day and to days above it. It stamps the marker only when the transport accepted the mail. A transport failure throws, so the SDK retries the step (three retries). A notice that fails every retry is given up for that resolution: the run remembers the resolution's timestamp and goes on to close the request on day 7 without the notice. A reopen clears the marker.
- **The close.** `closed_at` is set to `resolved_at` plus 7 days, never to the moment the job ran. A late run or the sweep therefore gives the same date the readers already showed.
- **What anonymising empties.** Subject, message and path become empty strings, and `sender_email` becomes null. `created_by` passes to the System account, and `resolved_by` too when the sender resolved it. Every reply's body is emptied, and a sender-authored reply's `created_by` passes to the System account. **What it keeps:** topic, status, error code, the dates, staff ids and the issue link, so the counts per topic and per month do not change. A `created_by` equal to the System account marks a row as done, because no request is otherwise created by it. The audit writer strips `created_by` from an update, so this one statement is written on the transaction directly. One statement changes both the address and `created_by`, so the one-sender CHECK never sees an address without the signed-out sender.
- **The fallback.** Every admin visit to `/admin/support` starts one sweep run (`support-retention-sweep.ts`), after the response is sent (Next's `after`). The sweep closes every lapsed resolved request and anonymises every request closed twelve months or more ago. It sends no notice. A curator's visit starts none. There is no daily chain, because readers already treat a lapsed row as closed, and only the anonymising needs to happen without a visit.
- **Readers.** In the repository, `asOfNow` maps a lapsed resolved row to `closed`. The status filters and the view arms treat it as closed too, and `moveSupportRequest` refuses to move it. So a sender's message on it opens a linked follow-up, and staff can no longer resolve, close or set waiting on it.
- **The migration.** 0118 adds a nullable `closing_notice_sent_at timestamp`, without a time zone like the table's other timestamps, expand-only.

## Why the step renders the notice itself

The step bundler that the workflow SDK uses (its esbuild step, `jsx: 'preserve'`, with no way to override it) leaves JSX uncompiled, and the Vitest workflow builder then loads that bundle in Node with nothing compiling it. A step that reached a `.tsx` template failed with `SyntaxError: Unexpected token '<'`. A first version of this task worked round that by rendering the notice in the starting service and passing the rendered mail as the run argument. That put the sender’s address and the request subject in the workflow event log, and the owner turned it down (2026-11-02).

**What was done instead:** every template and the shared layout are plain TypeScript (`src/emails/*.ts`), built with `createElement`. A test in `tests/emails/parts/layout.test.tsx` fails on any `.tsx` under `src/emails` other than a story.

**Alternatives turned down:**

- **A JSX transform in the step bundle**, by a custom builder or an esbuild plugin. The SDK exposes no hook for it, so it would mean patching the package.
- **Precompiling the templates to `.js`** in a build step. That adds a generated file and a build step to keep in sync with the source, for a gain plain TypeScript gives without either.
- **Rendering in a route the step calls over HTTP.** A third access path, which CLAUDE.md rule 1 forbids.

The cost is that the templates read less like markup than JSX did. They are short, and the stories still render them for the eye check.

**The origin as a run argument.** The site has more than one origin (production, staging and each hotfix preview) and no setting that names the current one, so a step cannot work out the link on its own. The origin is neither personal data nor a secret, so it stays in the run argument. Storing it on the row instead was the alternative; the owner chose (2026-11-02) to keep it in the run argument.

## Why not a daily job

The provisional cleanup chains itself daily because nothing else removes a lapsed account. Here, a lapsed resolved request already reads as closed, and the per-request run covers the anonymising. The admin-visit sweep is enough for a run that was lost.

## Things not done

- A run that wakes after the seven days are over sends no notice, since the request has already closed.
- A twelve-month sleep is pinned to the deployment that started it. The admin-visit sweep is what anonymises a request whose run was lost.

## The reply's "sent" marker (owner's call, 2026-11-02)

A staff reply's mail is sent by its own job, `supportReplyNotice(replyId, origin)` (`src/modules/support/jobs/support-reply-notice.ts`), started by `replyToSupportRequest` once the reply is saved. Its step (`services/reply-notice.ts`) reads the reply, the request and the sender's address when it runs, builds the notice for a signed-in sender or the reply in full for a signed-out one, and stamps `support_replies.notice_sent_at` as the System account only once the transport took it. Migration 0119 adds the column, a nullable `timestamp` without a time zone, expand-only. A reply already stamped, an internal note, a sender's own message and a request already anonymised send nothing. When the run cannot be started, the service tries the step once itself, as `send` does for a failed start. The notifier lost its `replyWaiting` and `signedOutReply`, which nothing calls any more.

The run carries the reply id and the origin and nothing else, for the reason the closing-soon notice does: the run's arguments are kept in the job's event log, and a signed-out sender's mail holds the reply text.

## The signed-out send counts hold no address (owner's call, 2026-11-02)

`support_send_counts.key` is an HMAC-SHA256 (a keyed hash) of the address, never the address. `src/lib/send-count-key.ts` builds it: `addressCountKey` hashes the email after `normaliseEmail`, so the limit still counts a change of case or spacing as the same address, and `clientCountKey` hashes the trimmed, lower-cased client address. The client address is hashed as well, though the owner's call named only the email: an IP address is personal data too, and the counter needs only to tell one apart from another.

The key is `BETTER_AUTH_SECRET`, with a fixed development fallback outside production, so no new variable exists. A rotation of that secret starts every count afresh, which loosens the limit for at most one 24-hour window. A plain hash without a key was set aside: an email address is guessable, so an unkeyed hash of one can be reversed by hashing candidates.

Migration 0120 deletes every row, since the rows written before it hold addresses. A count lives 24 hours, so the loss is at most one window's limit. `check:destructive-ddl` does not flag a `DELETE`, so the migration has no sidecar. `tests/modules/support/services/support-signed-out.test.ts` proves no row holds either address, and `tests/db/migrations/0120-support-send-counts-drop-address-keys.test.ts` that the migration leaves none.

## Secret links through a job (owner's call, 2026-11-02)

The owner chose that the six secret-link mails go through a retried job, with a run that holds ids alone and a step that gets the token when it runs, by minting one, re-signing one or reading one Better Auth stored. Three are built; three are not.

**Built.** `secretLinkMail(link)` (`src/modules/identity/jobs/secret-link-mail.ts`) takes a `SecretLink`: the kind, the account id, the request's `/api/auth` base, and for a verification where the account was going, for a lockout its length in minutes. Its step (`services/secret-link-mail.ts`) reads the account's address when it sends.

- **The sign-up and resend verification link** is re-signed in the step with `createEmailVerificationToken`, under `verificationSigningSecret()` (`src/lib/auth-secrets.ts`), which picks the secret as Better Auth picks `ctx.secret`. The link is good for the full lifetime from the moment it is sent. A row verified meanwhile gets nothing.
- **The password reset link** carries the newest unexpired `reset-password:` token Better Auth stored in `verifications` for the account (`findNewestResetToken`). Better Auth already stores that token unhashed, which is why it lasts 15 minutes; nothing new is stored.
- **The lockout mail** still mints its reset token in the hook, as Better Auth's own reset does, and its step reads it back the same way.

`scheduleSecretLinkMail` (`services/secret-link-start.ts`) starts the run. While `MAIL_TRANSPORT` is unset, or when the run cannot be started, it builds the mail in the request and tries it once through `send`.

Tests: `tests/workflows/secret-link-mail.test.ts` (a verification mail refused twice is retried and goes to the address the row holds when the step runs, signed with a token Better Auth's secret verifies; the newest live reset token; the lockout link; every attempt failing logs without the token and returns false; nothing to send). `tests/db/secret-link-start.test.ts` (sign-up, reset and lockout start the run with ids alone, and no address or stored token is in it; a failed start tries the mail once). `tests/db/email-verification.test.ts` holds the signing secret to Better Auth's, and its link-following cases follow a re-signed link. `tests/lib/auth-secrets.test.ts` covers the secret's choice.

**Built afterwards (owner's calls, 2026-11-02).**

- **The change-of-address link.** The address asked for is held in `users.pending_email` (migration and behaviour in [`auth/admin-bootstrap.md`](../auth/admin-bootstrap.md), "The email page"), so the step reads it and signs the change link when it sends. Only the newest change's link is honoured, and the job clears the column once its link has lapsed. Putting the address in the run was turned down because it is personal data in the event log; leaving the mail tried once was turned down because it loses a refused mail.
- **The admin and coven invitations.** The step gives the invitation a fresh token through `rotateInvitationToken`, a named exception to rule 5 ([`m15.50-invitation-token-rotation.md`](m15.50-invitation-token-rotation.md)).
- **Every run holds ids alone.** `startJob` refuses a run argument that is not an id, a kind, a site origin, a return path, a number, a boolean or null (`src/lib/jobs/run-arguments.ts`), so an address, subject, body or token cannot enter an event log ([`m15.50-mail-through-a-retried-job.md`](m15.50-mail-through-a-retried-job.md)).
- **The notice to the address a completed change left.** The swap holds that address in `users.former_email`, and the account-notice job's step mails it and clears it ([`m15.50-mail-through-a-retried-job.md`](m15.50-mail-through-a-retried-job.md), "The notice to the address a change left").
