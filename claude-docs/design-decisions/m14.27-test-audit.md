## 8. CI: splitting the Vitest job

Facts checked: Vitest 5.0.4 has `--project`, `--shard i/n`, `--reporter=blob` and `--mergeReports <dir>`, and `--mergeReports` merges coverage maps from blobs (node_modules/vitest/dist/chunks/cli-api.*.js: `coverages: blobs.map((blob) => blob.coverage)` and `coverageMap.merge(coverage)`), so the 80% thresholds can be applied once over the whole tree after split jobs. A container job's fixed overhead in run 40340661432 was 40–50 s (set-up 3 s, image and Postgres pull 34–42 s, checkout 2–4 s). Minutes are free on a public repo. The required check is named "vitest / vitest" (the Staging ruleset 22612558 did not show its required checks to this token, so the owner must confirm the name there). M11.18 set sharding aside for Playwright because the image pull cost more than it saved at that scale; that reasoning does not transfer to a 6.5 min job.

### Option A: one job per Vitest project family, one merge job (recommended)

```
vitest-dom   : vitest run --project dom                      --reporter=blob --coverage   (no Postgres service)
vitest-node  : vitest run --project unit --project rsc       --reporter=blob --coverage   (no Postgres service)
vitest-db    : vitest run --project db --project db-mocking  --reporter=blob --coverage   (Postgres service)
vitest       : download the three blobs; vitest run --mergeReports .reports/blobs --coverage
               applies the 80% thresholds, writes the JSON the PR comment reads, and is the required check
```

- Each job keeps its own flock-free run (CI has no lock); locally `npm run test:coverage` stays as it is.
- The merge job is small (no tests run) and keeps summarize-vitest.mjs and slowest-files.mjs unchanged, reading the merged JSON.
- Wall: the dom job is about 86% of CPU, so A alone takes the wall from ~6.5 min to ~5.5 min. Its value is feedback and isolation: a backend PR's db and node jobs finish in about 1.5 min, and a dom timeout no longer fails the db run.
- Do not path-skip the individual jobs: thresholds are over the whole src tree, so a skipped job breaks the merge. Keep today's whole-vitest skip for doc-only PRs.
- Cost: three container starts instead of one (about +90 s of runner time, free), and the db job alone pulls Postgres.

### Option B: A plus sharding the dom job

`vitest-dom` becomes a matrix over `--shard 1/2` and `--shard 2/2` (or 1/3..3/3), each writing a blob; the merge job already handles any number of blobs. Vitest shards by file, so no test changes. Wall falls to the slowest shard: about 3 min at two shards, about 2 min at three, before any test cuts. The db job cannot be sharded cheaply, because each shard builds its own template database; it does not need to be, at about 80 s of CPU.

### Option C: frontend and backend

The same as A with dom as "frontend" and unit, rsc, db and db-mocking as "backend". It is A with two jobs instead of three; the only difference is that the backend job then needs the Postgres service for its unit half too. I recommend A over C for that reason.

### What I recommend

Take A now and B after the first test cuts land, with the shard count set from a measured run (two shards is the right first guess). Keep the merge job as the one required check so the ruleset needs one name change at most. Record the shape in claude-docs/ci/runner-budget.md. This is a task of its own (a CI change, not a test cut), and it is independent of every cut above.

Things I measured that argue against other levers: a 4th worker, unisolated dom, the Vitest cache and the FILE_COPY clone were all tried and dropped by M11.24; `isolate: false` for dom would save about 19 s of start-up but failed on pre-paint-scripts last time.
