# M5.6 — The admin categories page: the delete, the list query, the modal

**Status:** decided · **Date:** 2026-10-07

M5.6 is the first admin CRUD page, and M5.6a, M5.6b, MB.95 and MB.132 reuse
its shape. Scoping it, three questions had no answer in DESIGN.md or the task
entry. The owner settled each one. [`db/categories.md`](../db/categories.md),
"Category writes", carries the delete rule as built, and
[`components/grouped-value-form.md`](../components/grouped-value-form.md),
"On the admin pages", carries the modal.

## Deleting a category that is in use

The criterion asks only that it be "handled explicitly, not by cascade
surprise". A category reaches an ingredient through `ingredient_categories`
and a spell through `spell_categories`. Both are hard-deleted join tables
(MB.34), and both hold covens' rows as well as the compendium's.

**Decided: refuse while a live compendium entry is filed under the category,
naming the entries. Otherwise soft-delete it and leave every link in place.**
The refusal is the one M5.6a gives a form a compendium entry picks (MB.162),
and the admin takes the category off the entries first. A coven's links never
block the delete and are never removed. Every read already drops a deleted
category, so the coven's chip disappears and its link stays for v2's restore.

Weighed:

- _Ask for confirmation, then soft-delete, whatever holds it._ Simple, but the
  compendium would silently lose a tag from entries the admin never opened.
- _Soft-delete and hard-delete every link in the same transaction._ The data
  stays exact, but it is an admin write reaching covens' rows, which M6.6
  forbids, and it cannot be undone.

## The list read

DESIGN.md's rule 1 has a server component read a service, and the browser read
GraphQL. MB.126, not yet built, owned the public `categories` query that its
picker and M8.11's filter read.

**Decided: M5.6 builds `listCategories` and the public, paged `categories`
query.** The admin page reads the service on navigation, and MB.126's picker
reads the query from the browser. MB.126's entry is amended to consume the
query rather than build it. Caching the query under the `compendium` tag is
still M8.6's.

Weighed: _service only_, which leaves the task's "reads go through GraphQL"
unmet and the query to MB.126; and _an admin-only `adminCategories` query_,
two queries over the same rows.

## The page shape

The first proposal was three routes: a list, `/new` and `/[slug]`. The owner
asked whether a modal suited a three-field form better, opened by an address.

**Decided: one route, `/admin/categories`, with the form in a modal that the
address opens — `?new`, or `?edit=<slug>`.** The server renders the list with
the modal already open. Closing it, after a save, a delete or a Cancel,
replaces the address with the list's, the page's cursor kept, so Back does not
reopen it. A link to a category's modal works from anywhere.

The modal is `Modal`, the project's first: the native `<dialog>` in modal
mode, which gives the focus trap, Escape and the inert page without building
them. M8.16, M8.17 and M7.4 reuse it.

Weighed: _intercepted and parallel routes_ (`@modal/(.)new`), where a click
inside the app gets a modal and a pasted link a full page. That is two
renderings of every form, with known quirks on refresh, for no gain here. And
_separate pages_, which suit a long form better than a short one.
