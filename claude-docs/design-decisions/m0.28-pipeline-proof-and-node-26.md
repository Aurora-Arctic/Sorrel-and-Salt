# M0.28 — end-to-end pipeline proof; deploy.yml on Node 26

**Status:** in progress · **Date:** 2026-09-09

M0.28 exists to run the whole deploy pipeline once while the app is a trivial
page, so deploy problems surface before any feature work. The first run did
exactly that.

## What M0.28 found

M0.26's `deploy.yml` merged to `staging` (PR #40) and its first real run
([run 34388520913](https://github.com/Aurora-Arctic/Sorrel-and-Salt/actions/runs/34388520913))
**failed at `npm ci`**, before Vercel was ever contacted:

```
npm error `npm ci` can only install packages when your package.json and
package-lock.json … are in sync.
npm error Missing: typescript@5.9.3 from lock file
```

### Root cause

`deploy.yml` ran `actions/setup-node@v4` with `node-version: 22` — the only
place in the repo not on Node 26 (`Docker/Dockerfile.node` pins `26.6.0`;
local dev is 26.x; `@types/node` is `^26.1.2`). It was a carry-over default
from the port, not a considered choice.

- Node 22 bundles **npm 10.9.8**; Node 26 bundles **npm 11.19.0**, which is
  what generated the committed `package-lock.json`.
- `typescript@^7.0.2` (the new Go-based compiler) ships ~20 per-platform
  optional dependencies (`@typescript/typescript-darwin-arm64`, …) plus a
  `typescript@5.9.3` JS fallback. npm 11 records that tree in a shape npm 10
  reads as incomplete, so npm 10's `npm ci` sync check rejects the lockfile.
- Reproduced in Docker: `npm ci` fails on `node:22-slim`, passes clean on
  `node:26-slim` against the same committed `package.json` + lockfile.

### Fix

Both `Set up Node` steps in `deploy.yml` (the `deploy` job and the `teardown`
job) pinned to `node-version: 26.6.0`, matching `Docker/Dockerfile.node` and
local dev. No lockfile change — the lockfile is correct; the runner was wrong.

This supersedes the "Node 22, npm cache" detail in
[`m0.26-disable-previews-and-alias-staging.md`](m0.26-disable-previews-and-alias-staging.md)
("Bare runner" bullet).

## What M0.28 found next — `vercel pull` could not read the project

With `npm ci` green (PR #41 on `staging`, run
[34390137712](https://github.com/Aurora-Arctic/Sorrel-and-Salt/actions/runs/34390137712)),
the pipeline reached `vercel pull` and failed:

```
Retrieving project…
Error: Could not retrieve Project Settings. To link your Project, remove
the `.vercel` directory and deploy again.
```

### Root cause

Reproduced locally against the live project. The canonical link for
`aurora-arctic/sorrel-and-salt`:

| Value               | Canonical                          |
| ------------------- | ---------------------------------- |
| `VERCEL_ORG_ID`     | `team_YA8GrwB8bqvQ1sOemBC9H9T7`    |
| `VERCEL_PROJECT_ID` | `prj_TNdoYllyiKqxkWrnZAE4qFQeQAoz` |
| `VERCEL_SCOPE`      | `aurora-arctic`                    |

The exact CI call — `vercel pull --yes --environment=preview` with only
`VERCEL_ORG_ID` + `VERCEL_PROJECT_ID` exported, no `.vercel/` directory, no
`--scope` — **succeeds** with valid credentials. The workflow shape is
correct. Mapping the error messages:

| Condition                                         | CLI says                                   |
| ------------------------------------------------- | ------------------------------------------ |
| invalid / expired token                           | `token … is not valid`                     |
| wrong `VERCEL_PROJECT_ID`, or org slug for org id | `Project not found (…)`                    |
| **valid token without access to the team**        | **`Could not retrieve Project Settings…`** |

So the token was valid but minted against the wrong Vercel scope (a personal
account rather than the Aurora Arctic team).

### Fix

The deploy-token secret is renamed **`VERCEL_TOKEN` → `VERCEL_DEPLOY_TOKEN`**
and re-issued scoped to Aurora Arctic — a distinct name so it is never
confused with credentials the Vercel GitHub integration manages. All eight
references in `deploy.yml` (both `Check secrets` guards,
`pull`/`build`/`deploy`/`alias`, the teardown `alias rm`) and the doc
mentions (`DESIGN.md` §12 secrets row, `ci.md`, the M0.26 decision doc) move
with it. `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` / `VERCEL_SCOPE` keep their
names; the table above is the value set to hold.
