# Autosave, leave warning and edit conflicts for spells — plan

Planned 2026-10-25. Written for the owner to approve, then copied to `claude-docs/design-decisions/<id>-plan.md` in the first PR.

## Context

Nothing in the app saves a spell before the user presses Save, and the spell builder (M10.12, M13.3, M13.10) is not built yet. Its tasks describe one explicit save of the whole form, a `draft | complete` status that is itself set by hand, and a Cancel guarded by `useDiscardGuard`. Closing the tab, reloading, or using the browser's Back would lose everything typed; no `beforeunload` listener exists anywhere in `src`, and no task covers autosave, draft recovery, or two people editing one spell.

The owner's decisions (2026-10-25):

1. **Real autosave to the server draft row**, with a localStorage mirror for failures and recovery.
2. **Autosave always**, on drafts and on complete spells alike. When spell history lands (DESIGN.md's v2 `record_revisions`, line ~1789), edits to a complete spell must be able to go into a draft revision instead — so the save adapter takes a _target_, and nothing in the mechanism assumes "the row".
3. **Conflicts:** revision check (the counter v2 history will reuse); on a stale write the builder offers **Reload Latest** or **Keep My Version**.
4. **Cancel goes, Save stays:** a draft is always saved, so the builder shows a Back link and the save status, not Cancel. An explicit **Save** button stays beside the status (NN/g: autosave does not replace the explicit action): it flushes the pending autosave at once and is **disabled when there is nothing to save** (the repo's form save rule), so it reads as the "I'm done with this edit" action. Mark Complete is separate and flushes first. Deleting a draft is M13.11's Delete.
   4a. **Live refresh and presence:** while the builder is open on a visible tab, it polls the spell every 10 s. Fields the user has not touched update from the server silently; another member whose save is under 2 minutes old is shown as editing.
5. **Title becomes nullable on drafts**: a CHECK requires it only when `status = 'complete'`; a blank one shows as "Untitled Spell".
6. **`beforeunload` on every long form**, not just the builder.
7. **Modular**: the mechanism is entity-agnostic so ingredient drafts can adopt it later without restructuring.

Research findings this plan rests on (agent report, sources read): GitLab Pajamas autosaves 3 s after the last keypress and on blur, inline status near the content and never a toast, failure as an inline alert with retry; Confluence saves drafts every 30 s; NN/g says autosave does not replace an explicit action; MDN says attach `beforeunload` only while there are unsaved changes, call `preventDefault()`, custom text is ignored, Chrome needs a user gesture, and flush state on `visibilitychange` because `beforeunload` is unreliable on mobile; Gerrit's bug — clear the local copy only after the server confirms; WordPress recovery wording "There is an autosave … more recent than the version below / Restore"; Next 16 `<Link onNavigate>` can cancel a client navigation, there is no official API for back/forward or `router.push`, and patching `history.pushState` is bug-prone (vercel/next.js discussion #50700).

## The mechanism (entity-agnostic)

### 1. Leave guard — `src/lib/navigation/leave-guard.ts(x)`

`useLeaveGuard(dirty: boolean, ask: (proceed: () => void) => void)`:

- While `dirty`, adds a `beforeunload` listener that calls `event.preventDefault()` and sets `returnValue = true`; removed the moment `dirty` is false (MDN). Also calls an optional `onHide` on `visibilitychange → hidden` so autosave can flush.
- Registers with a new `LeaveGuardContext` slot that `NavigationProvider` owns. `navigate()` consults the registered guard before starting: clean → go; dirty → `ask(proceed)`, holding the navigation the way `useDiscardGuard` holds a close. Back/forward and address-bar edits are not intercepted (no reliable API; see research) — autosave itself is the protection there.
- `useDiscardGuard` calls `useLeaveGuard(dirty, request)` internally, so **all seven existing forms get tab-close and in-app-navigation protection in one change** and draw the same `DiscardQuestion`. `CreateWorkspaceForm` (page form, no guard today) adopts `useDiscardGuard`. `NameForm`/`EmailForm` are single-field and short: left alone, said so in the task.
- Mechanical guard (sweep-over-code rule): `tests/guards/leave-guard.test.ts` — every component that renders `FormActions` or calls react-hook-form's `useForm` must call `useDiscardGuard` or `useLeaveGuard`, allow-list for the two short forms.

### 2. Autosave hook — `src/lib/autosave/use-autosave.ts`

```ts
useAutosave<TValue, TResult>({
  value: TValue;            // the form's current values (RHF `watch()`)
  dirty: boolean;           // RHF isDirty, or a hash compare against last saved
  enabled: boolean;         // false until the adapter has a target, or when the owner says so
  save: (value, ctx: { revision: number | null; id: string | null; force: boolean }) => Promise<{ revision: number; savedAt: Date; id: string }>;
  delay?: number;           // 3000 ms after the last change (GitLab)
  maxWait?: number;         // 30000 ms during continuous editing (Confluence)
  mirror?: MirrorKey;       // localStorage copy; see §3
}): {
  status: 'idle' | 'pending' | 'saving' | 'saved' | 'failed' | 'conflict';
  savedAt: Date | null; error: Error | null; conflict: { currentRevision: number } | null;
  flush(): Promise<void>; retry(): void;
  resolveConflict(choice: 'reload' | 'keep-mine'): Promise<void>;
}
```

- One save in flight at most; a change during a save queues exactly one follow-up.
- Failure → retry with backoff 2 s, 5 s, 15 s, then `failed` with a manual Retry; the form keeps its state; the mirror keeps the copy. `error` stays `null` through the retries and is set only at `failed`.
- `StaleWriteError` from the adapter → `conflict`; autosave pauses until resolved. `keep-mine` re-sends with `force: true` (the adapter passes the server's current revision); `reload` lets the caller reset the form from the server and clears dirtiness.
- Flushes on `visibilitychange → hidden`, on `blur` of the form root, and on explicit `flush()` (used by Mark Complete and by Back).
- Revision-tracking is the hook's: it stores the last returned `revision` and `id` and passes them on the next save, so a new row's second save updates it.
- The hook calls `useLeaveGuard` itself: the browser asks before closing the tab while a change is not yet on the server, an in-app link is not held (the mirror keeps the copy), and the tab going hidden saves at once.

### 3. Mirror — `src/lib/autosave/mirror.ts`

Key `autosave:<entity>:<id|new>:<userId>`, value `{ value, at }`. Written on every change, **cleared only after the server confirms** (Gerrit), entries older than a day ignored. Every access in `try/catch`; absent storage = no mirror. `readMirror(key)` for recovery: when `mirror.at > server updatedAt`, the consumer shows the recovery banner.

### 4. Save status — `src/components/SaveStatus/`

Inline, near the form's primary action, never a toast. `<output role="status">` rendered empty first. Texts (title case where labels, sentence case in prose): "Saving…" → "Saved 2:02 pm" (or "Draft saved 2:02 pm" while status is draft) → "Couldn't save. [Retry]" (`role=alert`, stays until a save succeeds) → conflict `Notice kind="caution"` showing the `conflictMessage` prop (the spell builder passes "This spell was changed elsewhere.") with **Reload Latest** and **Keep My Version**. Live region announces the first save after a burst only, not every one; visible text always updates. Reuses `Spinner`, `Notice`, `LastEdit`'s time formatting, on a 12-hour clock with am or pm. One Storybook story, `States`, shows every state.

### 5. Server contract — revisioned writes

Built so that v2 history (DESIGN.md "One generic revisions table", `record_revisions.revision int`, one PL/pgSQL trigger reading `to_jsonb(NEW)`) is an extension, not a rework. **No history is built now**: no `record_revisions` table, no snapshots, no timeline. What is built is the counter history will key on and the one trigger function history will grow.

- `revisionColumn()` beside `auditColumns` (`src/modules/identity/schema/users.ts` is where `auditColumns` lives; the helper goes beside `auditStampColumnsReferencing`): `revision integer NOT NULL DEFAULT 1`. One shared PL/pgSQL function `bump_revision()` BEFORE UPDATE sets `NEW.revision = OLD.revision + 1` — the same shape as `set_updated_at` ([0016_updated-at-trigger.sql](src/db/migrations/0016_updated-at-trigger.sql)): one function, a trigger per table added by that table's own migration. In v2 the same function also inserts the `record_revisions` row from `OLD`/`NEW`, so the two counters cannot disagree — the reason it is one function and not a per-table expression.
- Repository writer `write.updateRevisioned(membership, table, id, expectedRevision, values)`, a by-id writer that takes the `Membership` proof first like `updateByIdInWorkspace`: `UPDATE … WHERE id AND workspace_id AND deleted_at IS NULL AND revision = $expected RETURNING revision`; zero rows with the row present → throws `StaleWrite { currentRevision }`, and a row the proof cannot reach answers no row, never `StaleWrite`. `expectedRevision: null` = unconditional (the `force` path). In `src/db/repository/write.ts`, used by the spell writer; later by an ingredient writer unchanged.
- GraphQL: a mutation input gains `expectedRevision: Int`, its payload returns `revision: Int!`; `StaleWrite` maps to error code `STALE_WRITE` with `extensions.currentRevision`. The GraphQL client's `send()` throws it as `StaleWriteError`, a `GraphQLClientError` subclass, for the hook; `readGraphqlFailure` is unchanged. Convention documented in `.claude/rules/graphql.md` and `.claude/rules/database.md`.
- Reserved for v2, not built: a `revision` read of a past state, `restore` as a new revision, pinning an ingredient revision from a spell step. The plan only guarantees that `spells.revision` will equal `record_revisions.revision` for the same change once the table exists.
- Spell adapter (`src/components/SpellBuilder/autosave.ts`): `target: { kind: 'new' } | { kind: 'spell', id, revision }`; `new` → `createSpell` once, then the hook carries the id; otherwise `updateSpell(id, expectedRevision)`. When history exists, a `{ kind: 'revision' }` target is the only addition.

### 6. Live refresh and presence — `src/lib/autosave/use-live-row.ts`

One TanStack query per open builder: `spell(id) { revision updatedAt updatedBy { id name } …fields }`, `refetchInterval: 10_000`, `refetchIntervalInBackground: false` (visible tab only), `staleTime: 10_000` with `refetchOnWindowFocus: true` — so a tab that was hidden and comes back fetches again at once if its last result is 10 s or older (the owner's call, 2026-10-25), and does nothing if it is fresher; paused while a save is in flight. Workspace-scoped, so never cached server-side (rule 6). Nothing in the app polls today; this is the first and the hook is the one place it is allowed, so a later ingredient builder reuses it rather than adding a second timer.

On each result, if `revision` is newer than the one the hook holds:

- **No overlap** (no field the user has dirty changed remotely): the untouched fields are reset to the server values (RHF `resetField` per untouched field; the `steps` array counts as one field), the held revision becomes the new one, and `SaveStatus` shows "Updated from <name>" for a few seconds. The next autosave then sends the merged form with the new `expectedRevision`, so it overwrites nothing of theirs.
- **Overlap** (a field both touched): autosave pauses and the §4 conflict banner shows, naming the fields: "<Name> changed Title and Steps while you were editing." with **Reload Latest** / **Keep My Version**. The server `STALE_WRITE` path stays as the backstop for the race the poll misses.

Presence: `updatedBy.id !== me && now - updatedAt < 2 min` → a line under the heading, "<Name> is editing this spell", with their `LastEdit` time; it clears when the window lapses. It is a hint derived from saves, not a lock — the plan says so in the UI copy's InfoTip, because a reader who stopped typing 90 s ago still shows.

`updated_by` already exists in `auditStampColumns` and the SDL exposes `updatedBy`, so no new column; the `User` resolved from it gives the name through the existing loader.
