# M5.3 — Plan, as approved

**Status:** approved · **Date:** 2026-09-30

The scoping plan for M5.3 as widened in review, copied here as approved. The decision it records is [`m5.3-spells-keep-deleted-ingredients.md`](m5.3-spells-keep-deleted-ingredients.md).

**Amended while building.** The children's finder is not one statement: it
reaches its parents through `findIngredientsInSpellsIncludingSoftDeleted`, two
statements, because a deleted parent's tier cannot be tested through
`existsIn` and a raw subquery is what MB.100 removed. Spells are seeded through
a new shared inserter, `tests/support/db/insert-spell.ts`, on
`insertIngredient`'s terms. The "custom layer contributes nothing" test was
dropped: both finders take ingredient ids, which a custom layer does not have.

### Context

M5.3 as tracked proves one thing: an admin's soft delete of a compendium entry
takes it out of every read and frees its formal name. That half is written and
green on `feature/m5.3-soft-delete-compendium-entry-prove-name-reused`
(uncommitted: `compendium-entries.test.ts` "a deleted entry", `db.md` paragraph).

You widened it in review:

1. **A coven member deletes one of their own ingredients** — service _and_
   GraphQL mutation now. Nothing builds this today: M8.8 made create/update
   only, M9.10 (the confirm dialog) assumes a delete exists, and there is no
   delete mutation anywhere in the schema.
2. **A spell keeps the ingredients it holds after they are soft-deleted**, and
   they still count toward its derived categories and safety warnings. The
   spell stays editable; its edit history is v2. CLAUDE.md rule 4 ("no exported
   finder can return a deleted row") is wrong for this case and is corrected,
   not routed around. The finder is built now, ahead of its Wave 13 caller.
3. **A layer leaves a spell only by a user's choice, and even then softly** —
   `spell_ingredients` gains `deleted_at`. A schema change reversing MB.34 for
   that one table, so it is minted as its own table task, **MB.110**, straight
   after M5.3 (Part D); this PR only mints it.
4. **v2 direction, recorded not built:** a layer references the exact revision
   of its ingredient; the spell indicates when the ingredient has been modified
   since, and the user can pull that precise modification in.

At the data level (2) already holds — `spell_ingredients` has no `deleted_at`,
its FK is `NO ACTION`, and a soft delete touches no layer. What loses the
ingredient is every _read_: `findOneIngredient`, `findManyByIds` and
`findManyOfIngredients` (via `existsIn`) all filter a deleted parent.

### Part A — a coven member's delete

**Writer** — `src/db/repository/types.ts` + `write.ts`: add
`softDeleteByIdInWorkspace(membership, table, id)`, typed
`PgTable & SoftDeletable & WorkspaceScoped & Identified`, built as
`softDelete(table, and(scopedTo(membership, table), eq(table.id, id)))`. A
service cannot build `id = $1` itself (MB.33), which is why the by-id twins
exist. Parity with `updateByIdInWorkspace`: no `NotVisibilityScoped`, so a
future spell delete still reads `findOneSpell` first, as `spell-visibility.ts`
does — noted in db.md rather than typed.

**Service** — `src/modules/ingredients/services/workspace-ingredients.ts`:
`deleteWorkspaceIngredient(session, workspaceId, id): Promise<void>`, shaped as
`deleteCompendiumEntry` (`services/compendium.ts:249`):
`assertMembership(…, { ingredient: ['delete'] })` (owner, member; not viewer),
`RowId` check → `NotFound`, `withAudit` → `softDeleteByIdInWorkspace` → no row →
`NotFound('No such ingredient in this coven')`. Folk names, category links and
its stock row stay: only a spell reads past a deleted parent (Part B), and
stock reads go through a live ingredient (criterion added to M9.3 — `inventory`
has no `delete` permission and no reader yet).

**Mutation** — `src/modules/ingredients/graphql/workspace-ingredients.ts`:
`deleteIngredient(workspaceId: ID!, id: ID!): ID!`, `authScopes: { signedIn }`,
returning the deleted id. Not the entity, though §7 says mutations return one:
a deleted `Ingredient`'s `folkNames`/`categories` would resolve empty through
the loaders, and a client evicting a list row needs only the id. First delete
mutation in the schema, so the convention is recorded in graphql.md and §7.
Then regenerate `src/graphql/schema.graphql`
(`npm run test -- tests/graphql/schema-snapshot.test.ts -u`) and `npm run codegen`.

### Part B — a spell's reach past a tombstone

Two finders in `src/db/repository/spells.ts` (beside the private
`readableSpells`), each named `…IncludingSoftDeleted` so the guard pins them:

- `findIngredientsInSpellsIncludingSoftDeleted(membership, ingredientIds)` —
  the ingredients among `ingredientIds` that a spell this member may read
  links, deleted or not. The DataLoader key M10.9 needs: layers come from
  `findManyInSpell`, their `ingredientId`s batch into this.
- `findManyOfSpellIngredientsIncludingSoftDeleted(membership, table, ingredientIds)`
  — `ingredient_categories` / `ingredient_folk_names` of those ingredients, on
  the same reach, so derived categories stay whole. The child's _own_ tombstone
  still filters (a removed folk name stays removed); only the parent's is
  skipped.

Both are `selectFrom(…, and(inArray(id…), or(inCompendium(ingredients),
scopedTo(membership, ingredients)), existsIn(spellIngredients,
and(eq(spellIngredients.ingredientId, ingredients.id),
existsIn(spells, and(eq(spells.id, spellIngredients.spellId), readableSpells(membership)))))))`,
with deliberately no `notSoftDeleted(ingredients)`. The spell's own filter
(`readableSpells` carries `notSoftDeleted(spells)`) and visibility are kept.
The layer is read through `existsIn(spellIngredients, …)`, which ANDs the
table's own `deleted_at IS NULL` whenever it has one — so once MB.110 adds the
column, a layer the user removed stops reaching its ingredient with no change
here.
The tier clause keeps a W spell from surfacing X's ingredient — the FK does not
prevent that link, and M10.10's validation does not exist yet.

### Part D — mint MB.110 (entry and issue only; no code)

**MB.110 — Make spell layers soft-deletable** · 3h, Bug, Wave 08, straight
after M5.3. Table task, landing while `spell_ingredients` is still empty in
production. The entry carries:

- `deleted_at`/`deleted_by` — the table takes the full `...auditColumns`;
  `ingredient_categories` and `spell_categories` stay hard-deleted, so "the
  three join tables" becomes two everywhere (CLAUDE.md rules 3–4, DESIGN.md §5
  "Why those three", db.md "Hard delete on the three join tables",
  `tests/support/db/table-metadata.ts`, `audit-columns.test.ts`'s `STAMPED`).
- A surrogate `id` primary key; `(spell_id, layer_order)` becomes a live-only
  partial unique index, since a removed layer must not hold its slot; the two
  existing partial indexes gain `deleted_at IS NULL`. Destructive DDL (PK and
  index drops, `NOT NULL` column) — an `.ack.md` sidecar, and the task decides
  whether the index swap needs MB.107's two-PR split.
- Criteria: a removed layer vanishes from `findManyInSpell` and from M5.3's
  finders; its `layer_order` and ingredient can be reused in the same spell;
  soft-deleting an ingredient never touches a layer; the catalogue test for
  the new predicates; the demo seed and spell fixtures still write.

Minting follows CLAUDE.md's recipe, re-checking the next free id first:
the TASKS.md entry, the Wave 8 execution-order row and the milestone
description, then `gh issue create … --type Bug --label tracked --milestone
"Wave 08 — Compendium and admin"`, `task-board.mjs estimate MB.110 3`,
`reorder --apply`. Any `gh` write auto mode refuses — this, the M5.3 issue-body
refresh — is handed to you as the exact command.
