# M11.25 — The component tests run on happy-dom

Decided 2026-10-16 by the owner, on the measurement below. The task entry is in [`tasks/m11.md`](../tasks/m11.md); this file holds the evidence behind it. Every figure comes from runs on one tree, recorded during M11.24's follow-up investigation (three happy-dom runs and one jsdom run of the `dom` project, three workers, coverage on, `CLAUDECODE` unset, under the shared Vitest lock).

## What was asked

The `dom` Vitest project runs every component test (94 files, 1,049 tests). It takes about 60% of the suite's CPU, and Vitest credits about a fifth of that to the test environment itself, the library that stands in for a browser. Could a lighter library do the same job without weakening any test?

happy-dom averages 28.2 s of wall time and 94.9 CPU-seconds against jsdom's 46.3 s and 167.9: 39% less wall time and 43% less CPU. The happy-dom runs started under the higher load, so the gap is if anything understated. jsdom has one run only; an earlier session saw 41 to 45 s at lower load, so the saving is probably nearer 35 to 39%. (Each run exits non-zero only because `--project dom` alone misses the 80% coverage line, as it always has.)

The CPU figure is user plus system time, so it is the number that the gate's 4-vCPU runner pays too. The wall-time and CPU figures for the `vitest` job on the gate are in the PR body, measured after the merge target is known.

## The four problems, and the fix for each

Switching the library alone failed tests. Each cause was found and fixed in a way that also passes on jsdom (the jsdom run J1 above is on the tree with the fixes applied), so none is a happy-dom workaround.

1. **Modal's fade (about 28 tests).** `Modal` closes at once if `matchMedia` is missing or reports reduced motion; otherwise it fades and waits for the browser's `transitionend` event. jsdom has no `matchMedia`, so the tests had been taking the "no fade" path by accident. happy-dom has one that answers "no preference", so the modal waited for an event that nothing in a test environment fires. It is not a product hang: `Modal` has a 400 ms fallback timer (`FADE_LIMIT_MS`, already tested). Fix: `tests/support/setup-dom.ts` declares a `matchMedia` that reports reduced motion and nothing else, which is true of an environment that draws no transitions, and is the path the tests already took. Rejected: firing `transitionend` in 28 tests, which would add noise and make each test about the fade instead of what it is about.
2. **Dialog accessible names (about 15 tests).** happy-dom's computed style leaves an inline element's `display` empty (its issue [#2467](https://github.com/capricorn86/happy-dom/issues/2467), opened 2026-10-06, no maintainer reply at the time, reported against 20.14.5 and still present in 21.0.3). The accessible-name library puts a space between parts whose `display` is not `inline`, so names came out with spaces inside words. No happy-dom setting changes this. Fix: a default stylesheet in the setup, `:where(a, abbr, b, …) { display: inline; }`, the browser's own default for the HTML rendering section's inline elements, as real CSS the library already honours. `:where` gives it zero specificity, so a test's own styles win. An earlier attempt wrapped `getComputedStyle` in a Proxy; it was dropped because it patched every read for the whole run and hid the cause.
3. **31 act() warnings.** All were in `tests/components/IngredientForm/lookups.test.tsx` (15 tests, two each), from the combobox's positioning code updating outside `act`. The file imported Testing Library's `waitFor` rather than the shared `waitFor` in `tests/support/ingredient-form.tsx`, which settles inside `act` first for exactly this. The warning was latent: happy-dom's faster DOM shifted the timing and exposed it. Fix: import the shared helper (two lines, no assertion changed).
4. **`{ ...window.location }` (four files).** A spread copies the fields only where they are own properties, which is jsdom's doing; on happy-dom they are prototype getters and the spread is empty, while the GraphQL client needs `origin`. Fix: `stubLocationAssign(assign)` in `tests/support/location.ts` names the fields a test needs, used by the ImpersonationBanner, UserList, Pager and UserDetail tests.

The setup test (`tests/support/setup-dom.test.tsx`) pins the two setup declarations: it names a dialog from inline parts and checks the reduced-motion answer, and fails if either declaration is removed.

## Alternatives ruled out

- **Staying on jsdom.** jsdom 30.1 already carries its own performance release and is the version in the tree. A profile of the slowest file put the remaining cost in working out accessible names and hidden elements for every role query, which faithful queries have to pay, so more tuning of the same library would not move it far.
- **linkedom.** Built for server-side rendering without the computed styles that role queries need.
- **Vitest's browser mode.** Found slower, not faster, and beyond a devcontainer that reaches browsers only through a remote server.
- **Per-file opt-in to happy-dom.** Would keep two DOM libraries and need environment detection in the setup; the fixes are small and library-agnostic, so the whole project switched, with no environment variable.

## Stability assessment

happy-dom is the risk, not the speed.

- **Release cadence.** About 25 releases from 2026-08-26 to 2026-10-08 (20.11.8 to 20.14.6), then 21.0.0 to 21.0.3 from 2026-10-11 to 2026-10-15 (`npm view happy-dom time`).
- **Maintenance.** One maintainer; last push 2026-10-15; 522 open issues and about 4.7k stars (GitHub API for `capricorn86/happy-dom`).
- **Open issues that touch us.** #2467 (the `display` bug above); #2488 (computed style returns an empty string for properties nothing sets, opened 2026-10-11); #2422 (draft pull request: the `hidden` attribute should compute to `display: none`). All are gaps in computed style. `claude-docs/testing/layer-ownership.md` already bans presentation assertions in the `dom` project, so only accessible-name and visibility checks (the accessible-name library, jest-dom's `toBeVisible`) are exposed.
- **Libraries on top.** The suite does not use `@testing-library/user-event`, whose README says it works with both jsdom and happy-dom. jest-dom has no happy-dom-specific problem that was found, and its 1,049 tests pass.
- **Guards.** Nothing in `tests/guards/` pinned jsdom.

Sources: the three issues above on GitHub, the GitHub API's issue search and repository metadata, `npm view happy-dom time`, the user-event 14.6.7 README, and happy-dom's own source in `node_modules` (`CSSComputedStyle.js`, `CSSComputedStyleElementDefault.js`, `BrowserWindow.js`) together with `dom-accessibility-api`'s `accessible-name-and-description.js`.

## Safeguards

- **An exact pin.** `package.json` pins `happy-dom` to `21.0.3` with no caret, so a new release arrives as a Dependabot pull request and runs the whole `dom` project before it lands. Expect each major to need a look.
- **The setup test as a tripwire.** If a release changes what the environment reports (a fixed #2467 leaves the stylesheet redundant but harmless; a changed `matchMedia` default is covered by the declaration), `tests/support/setup-dom.test.tsx` fails first, with a name that says which declaration is at issue.
- **jsdom is removed.** Nothing but the `dom` project used it, so it leaves `package.json`. Reverting is a one-line environment change and an install; the fixes above pass on both.
