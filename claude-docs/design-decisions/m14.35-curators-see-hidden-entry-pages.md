# M14.35 — A curator or admin still sees the page of a hidden entry

**Status:** accepted · **Date:** 2026-10-31 (the owner's call)

## What changed

`CLAUDE.md` said the compendium read takes no session. That stays true of the public read: `readCompendiumEntry` is cached, takes no session and excludes hidden entries in SQL. What is new is a second read, `readCompendiumEntryAsCurator(session, slug)` in `src/modules/ingredients/services/compendium.ts`. It opens with `assertCurator` (an admin passes), is not cached because its answer depends on who asks, and returns the entry shown or hidden. Soft-deleted rows stay out, in the repository finder.

The entry page (`/compendium/ingredients/[slug]`) calls the public read first. Only when that finds nothing does it ask for a session, and only a curator or admin gets the second read. A signed-out visitor, or a signed-in user who is not a curator, gets the 404 as before, so the public path stays cheap.

For a hidden entry the page:

- sets robots `noindex, nofollow` in its metadata;
- shows a plain `Notice` under the heading: "Hidden in the Compendium. Only curators and admins can see this page.";
- carries the shown switch after Reviewed, which flips with the normal `refresh()`; showing the entry removes the notice.

The public list, search, `llms.txt` and `.well-known` files keep excluding hidden entries for everyone.

## Why

The owner wants a curator to keep the page of an entry while it is hidden, so hiding it from the page does not throw the curator onto a 404.

## Rejected

- **A notice and no refresh on the flip.** It left the page showing an entry that a reload would 404.
- **Sending the curator to the entry's Quick Look in the admin compendium.** It moves the curator away from the page they were on.
- **Leaving the 404.** Hiding from the page would have ended the visit.
