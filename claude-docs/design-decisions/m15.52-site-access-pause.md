# M15.52 — How the site access pause refuses a sign-in, and what it decides along the way

**Status:** decided · **Date:** 2026-11-02

M15.52 lets a site admin pause a user's access to the site, until a time or with no end date, and lift it early.
DESIGN.md §8, "An admin can pause a user's access", carries the rule; [`../auth/admin-bootstrap.md`](../auth/admin-bootstrap.md),
"Pausing a user's access", carries the mechanics. This record carries the choices the task left open, each with its reason.
The owner was away while it was built; the coordinator decided the first one, and the rest were chosen to fit DESIGN.md and
the existing code.

## A user already paused is refused, not re-paused

The coordinator's decision. `pauseUserAccess` on a user with a standing pause answers a validation error,
"This user is already paused; lift the pause first". The repository's writer could replace a standing pause in one step
(DESIGN.md §5, `user_access_pauses`), but the service does not use that: an admin who pauses a user should see the pause
already there, and changing it is a lift followed by a new pause, two rows on the history. A run-out pause does not stand,
so a new pause over it goes ahead, and the writer lifts the run-out row first as §5 says.

## One session hook refuses every way of signing in

Better Auth makes every session through one internal call, and `databaseHooks.session.create.before` runs inside it. The hook
(`refusePausedSession` in `src/lib/auth.ts`) therefore covers a provider callback, a password, a passkey, the two-factor step
and the verification link without a check in each endpoint. The alternatives were a hook per endpoint, which a new sign-in
method would have to remember, and a check in `requireSession()`, which would let the session be made and then ignore it.

The hook runs only after the credential is proven. So a wrong password still answers 401 and is counted as a failed sign-in,
and the refusal tells nobody who does not hold the credential that the account is paused. A paused right password is not
counted as a failure: the counter counts the wrong-password code only.

## Redirect for a page load, 403 for a fetch

A provider's callback is a browser navigation, so the hook answers it, and any other GET, with a redirect to
`/access-paused`. A password, passkey or two-factor request is a fetch from the sign-in panel, which cannot follow a redirect
into a page, so the hook answers 403 with the code `ACCESS_PAUSED` and `until`, and the panel loads the page itself
(`src/components/SignInPanel/paused.ts`). The code and the path are spelt once, in `src/lib/access-paused.ts`, which both
sides import.

## The paused page reads only its own address

The page learns the pause's end from `?until=`, written by the refused sign-in, and reads nothing from the database. It has
no session to read one with, and a lookup by address or user id would tell any visitor whether an account is paused. Reading
only its own address, it can tell a visitor nothing the address does not already say. The cost is that anyone can open
`/access-paused?until=` with any date and see that date printed back, which reveals nothing about any account. A past
`until` says the pause has ended and links to Sign In, since the page may be reopened from history after the end. The end is
printed in UTC (`inUtc` in `src/lib/utc.ts`), labelled as such, so the server's and the reader's zones agree.

## Ending the sessions is part of the pause's own write

`setUserAccessPause` deletes the user's `sessions` rows in the same transaction as the pause row, inside `withAudit`. A pause
that committed without its session delete would leave the user signed in until the session expired. The rows have no audit
columns and no `deleted_at`, the same as when Better Auth's own sign-out deletes them, so a hard delete is right.

## An impersonation session is refused

An admin impersonating a paused user is refused like any other session for that user: the hook answers the impersonation
request 403 with `ACCESS_PAUSED` and the pause's end, makes no session, and leaves the admin's own session as it was. The
users list and the user modal show the refusal under Impersonate, naming the pause and its end, rather than sending the admin
to `/access-paused`, since the admin is not the one paused. Once the pause is lifted or runs out, impersonating the user works
again.

The task first let an impersonation session through, since it is the admin's and not the user signing in. The owner reversed
that on 2026-11-02: impersonation is never built on production (`claude-docs/auth/impersonation.md`), so letting it through a
pause served no purpose.

## Pausing another admin waits on admin changes

While the primary admin has paused admin changes (MB.62), pausing another admin is refused for every admin but the primary
admin, through the same `assertChangesOpen` a revoke of admin uses. That pause exists to stop a rogue admin acting against the
others, and pausing an admin's access would be another way to do it. Pausing a user or a curator is not affected. Lifting is not
gated: it only restores access.

## Lifting with nothing standing answers NotFound

`liftUserAccessPause` returns the lifted row, so it is non-null in the schema, as the scope registry
(`tests/db/graphql-query-scopes.test.ts`) requires of every admin write. A user with no standing pause, a run-out one
included, answers `NotFound`, "No pause stands on this user", rather than a quiet success, so the admin is told the lift did
nothing.

## Where the compendium proof sits

The criterion "a paused user still reads `/compendium` as a signed-out visitor" is proved in
`tests/db/access-pause-sign-in.test.ts`: the old cookie reads as no session through `sessionFromHeaders`, which every page
reads the viewer through, and the proxy lets both compendium routes through with and without it. The compendium page's own
signed-out view is already proved by its page test. M15.53's Playwright spec walks a refused sign-in in a browser.
