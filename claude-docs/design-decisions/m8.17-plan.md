# M8.17: Editing a Coven's Own Ingredient

## Context

Today a coven member can't edit an ingredient their coven made: nothing passes Edit to the coven's own entries, and `IngredientForm` only edits compendium entries. M8.17 adds the edit dialog (stories 33 and 34) in two places: the coven entry page and each row of the coven's Ingredients list. The dialog also gets **Link to the Compendium**, which swaps the coven's entry for a compendium entry and moves its jars and spell layers onto that entry (the conversion M12.21 built).

The work happens in the worktree `/home/node/worktrees/m8.17` (branch `feature/m8.17-edit-ingredient-modal`, cut from staging). The Opus agent that drafted this plan builds it, by TDD. It doesn't touch the Wave 12 places app-9a is reordering: TASKS.md's Wave 12 row and description line, wave-12.md's ordering paragraphs, and M12.5's entry. It also leaves alone M12.32's list readers in `src/db/repository/`.

## Decisions (owner, 2026-10-19)

- **Who gets Link:** every owner or member on any of their coven's own entries, formal name or not. The page works out `rolePermits(role, CONVERT_PERMISSION)` itself, as it already does for Make It Ours, and passes the answer to the dialog. The search reaches every live compendium entry. `canConvert`, and the Similar block that reads it, stay unchanged.
- **After a save:** the dialog closes, and the page or list shows the new values.
- **Where Link sits:** in its own section at the foot of the dialog, below the form and outside it. `IngredientForm`'s props don't change for it.
- **Unsaved edits when Link is pressed:** the Link confirm question adds one sentence saying unsaved changes won't be kept.
- **Taken as recommended, not raised with the owner:**
  - The value read becomes `entryValues(entry, session)`, moved to `src/app/entry-values.ts`.
  - A form an admin has renamed blocks the save, with an error at that variant's Form field, until the member picks a name.
  - The dialog has no Delete; that stays M9.10's.
  - On the list, a `?edit=<id>` that isn't the coven's own entry, or comes from a viewer, opens nothing.

## Giving the focus back (owner, 2026-10-19)

Stories 33 and 34 ask that a closed dialog puts the focus back on what opened it. Four owners had built that return by hand, each its own way (`ModalButton`, Add Ingredient, `ConfirmedAction`, `CupboardActions`), and a dialog opened by the page's address had none. The owner chose **option B**: one mechanism in `Modal`, built inside M8.17 rather than as its own task, with **the page's `<h1>` as the last place** when nothing opened the dialog.

**What was built:**

1. **`Modal`** notes the focused element before `showModal()`. As it unmounts it focuses that element again, if it is still on the page and the focus is on nothing; otherwise it asks its owner's new `returnTo` prop. It tells a real unmount from React Strict Mode's rehearsal by whether the `<dialog>` is still attached.
2. **`RouteModal`**, when the opener is gone, focuses a link to the address the dialog opened (outside any dialog), then its owner's `returnTo`, then the page's `<h1>`, which it gives `tabindex="-1"`. The provider notes the address on a press, as `RouteModalOpener.opened`.
3. **The four hand-built returns are deleted**; each owner names its trigger through `returnTo`. Their tests stayed green unchanged.
4. **`tests/guards/focus-return.test.ts`** refuses a `.focus()` in a file that draws a dialog, outside `modal.tsx` and `route-modal.tsx`. It failed against the four old returns before they were deleted.

**Choices the owner's brief did not name, taken as recommended:**

- **`returnTo` on `Modal` and on `RouteModal`.** An owner names its trigger there. It keeps WebKit working, where a click focuses no button, and covers `CupboardActions`' Annotate dialog, opened from a menu that is gone by the close.
- **The return never steals the focus.** It acts only when the focus is on the page's body, so a dialog that moved the focus elsewhere (a page it navigated to) keeps it there.
- **A save or a confirmed action returns the focus too**, where the opener still exists. Before, only Cancel did.
- **A gone link's own address is used** where there is no provider, as on the coven list's plain Edit link. Links inside a dialog never match.
- **A third exception in the guard:** `ConfirmedAction` keeps one `.focus()`, which puts the focus on the confirm as its question opens. That is the focus going in, not back. The guard counts calls per file, so an exception can only shrink.
- **The e2e proof is a small gate spec**, `tests/e2e/route-modal-focus.spec.ts`, on `/admin/categories` with the seeded Protection category: a close by Back lands on the Edit link, and a dialog reached by a pasted address lands on the `<h1>`.

## Three additions (owner, 2026-10-19)

Added after the build, each its own commit:

1. **Annotate on the coven list.** A member who may update ingredients gets Annotate on each card for a compendium entry the coven holds, retired ones included. `?annotate=<id>` opens the entry page's Annotate dialog over the list, through one `AnnotateDialog` the entry page now shares, and a close or a save comes back to the list as it was.
2. **A curator's Edit on the public search.** An admin or curator (`canCurate`) gets Edit on each card at `/compendium`, opening the admin Compendium's edit dialog over the results from `?edit=<slug>` and closing back to the same search. For anyone else there is no Edit, and `?edit=` opens nothing and reads nothing. The list's reads stay cached and sessionless (rule 6): the page already asked for the viewer on every request.
3. **A notice on the compendium's edit form,** above its fields, saying it edits the compendium. An add and a coven's edit carry none.

The owner chose the Annotate icon and the notice's wording, each kept in one place: `AnnotateIcon` in `src/components/IconTip/icons.tsx`, an open book with lines on its left page and a filled pencil, at stroke width 1.25 rather than the set's 1.5; and `COMPENDIUM_EDIT_NOTICE` in `src/components/IngredientForm/compendium-notice.ts`, "Changes are made to the Compendium, for everyone."

**Choices the brief did not name, taken as recommended:**

- Story 33 walks a coven's own entry, so Annotate on the list is proved by a gate spec in `tests/e2e/coven-ingredients.spec.ts`, and the curator's Edit by one in `tests/e2e/public-compendium.spec.ts`, rather than by a story.
- The notice shows on a compendium edit only, not on the admin add (`?new`), reading "the edit dialog" literally.
- The public page reuses the admin page's helpers from the `(shell)` route group: `CompendiumDialog` (given a `path` prop), `readEditPlace`, `MissingNotice`, and `readCompendiumEntry`, moved out of the admin page into `read-entry.ts` so both read `?edit=` one way.
- The public search's dialog is headed Edit Compendium Entry, as on an entry's page, not the admin list's Edit Ingredient.
- The public page is wrapped in a `RouteModalProvider`, as the admin layout is, so a press opens the dialog at once.

## Changes

1. **`src/components/IngredientForm/`**
   - `types.ts`: the props allow `entry` with a coven's `workspaceId`.
   - `index.tsx`: a new `UpdateWorkspaceIngredient` document calls `updateIngredient(workspaceId, id, input)`. `mutationFn` branches on coven update, coven create, compendium update and compendium create, in that order. Run `npm run codegen` and commit `src/gql/`.
   - `variants.tsx` and `values.ts`: build the **renamed-form prompt**. A variant whose picked form's `name` no longer folds to its `form` text offers two choices: "Use '<new name>'" or "Keep '<text>'", which unlinks the pick. The save is refused until the member picks. This prompt is new: the code has none today, although the task says it "stays".
2. **The coven-tier value read:** generalise `src/app/(shell)/admin/compendium/entry-values.ts` into `src/app/entry-values.ts`, as `entryValues(entry, session)`. It reads through the existing services, which check the coven's proof. It has four importers to update, one of them `tests/db/admin-compendium-entry-values.test.ts`, which is renamed to `tests/db/entry-values.test.ts`.
3. **The entry page** (`src/app/(shell)/coven/[slug]/ingredients/[id]/page.tsx`): an owner or member gets Edit on their coven's own entry. It opens the dialog under `?edit`, with `mayPromote` and the Link permission computed from the role. A viewer gets no Edit. Remove the "no Edit until M8.17" comment.
4. **`src/components/IngredientEntry/`**
   - `IngredientEntryEdit` gains `coven: { workspaceId, mayPromote, convert? }`.
   - `entry-dialog.tsx`: with `coven` set, it mounts the coven form and, on save, replaces the address with `savedHref` and refreshes.
   - The Edit button's accessible name becomes "Edit {name}, {formal name}", from hidden text, as `EditLink` already does.
   - The heading above the dialog's title follows the tier: "Edit Ingredient" for a coven's entry, "Edit Compendium Entry" for a compendium entry.
   - The Similar block's confirm question moves out into its own component, `link-confirm.tsx`, so the Similar block and the edit dialog share one copy.
   - New `link-search.tsx`: a "Compendium Entry" search box over `useCompendiumSubstitutes`, then Link, which opens the shared confirm question.
5. **The list** (`src/app/(shell)/coven/[slug]/ingredients/page.tsx` and its `reads.ts`/`types.ts`): reads `?edit=<id>` and draws the same dialog. Closing or saving goes back to the list's own address, query kept. Each own row the viewer may edit gets an Edit link: `CovenCards` gains `editHref` and `editHeading` and draws `EditLink` in the card's foot, with a story case added.
