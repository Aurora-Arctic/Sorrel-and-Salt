# MB.61 — Scope first-party email verification and email invitations

## Context

MB.61 is a scoping task in M2.9's shape: a decision record in `claude-docs/design-decisions/`, follow-up tasks in `TASKS.md` and on the Asana board, and no code. Today an address is verified only when Google or Discord say so (MB.60). Mailing a link we issue lets the site vouch for an address itself, which is what closes address squatting, lets MB.54 collect and change an email, moves workspace invitations to email (already decided for M7 and story 4), and makes the admin invitation of story 62 buildable.

Exploration established facts that correct the task's own premise, and the user has decided the forks:

| Decision                          | Chosen                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Verification token                | Accept Better Auth 1.7.5's stateless HS256 JWT (`expiresIn` 3600s, `autoSignInAfterVerification: false`). It is never stored, so it cannot be hashed, and is not single-use; replay is bounded by the early return once the row is verified. TASKS.md's "stored hashed like an invitation's" is corrected. Invitations keep their own hashed tokens.                                                                                                                                                                          |
| Squatted address                  | Unverified rows are provisional: swept once older than one token lifetime from the last verification mail, in a Better Auth `hooks.before` on `/callback/:id`, together with their `accounts`/`sessions` rows. `requireLocalEmailVerified` stays at its default. The owner blocked inside the window sees why and when to retry.                                                                                                                                                                                              |
| Session for an unverified account | Issued. No per-provider `requireEmailVerification`. Everything that matters already needs a verified address: invitations, promotion, workspace creation.                                                                                                                                                                                                                                                                                                                                                                     |
| Delivery                          | Resend's HTTP API in production. Mailtrap Email Sandbox's HTTP API in staging and hotfix previews: it captures and never delivers, so no preview can reach a real inbox. Mailpit's HTTP API in compose for local dev and e2e. One `src/lib/mail.ts` with three HTTP transports chosen by an explicit `MAIL_TRANSPORT` env, fail-closed: production accepts only `resend`, a preview accepts only `mailtrap-sandbox`, unset logs and sends nothing. No SMTP anywhere: Vercel functions are unreliable over SMTP (user's note). |
| CLAUDE.md rule 3                  | Corrected in this PR: the seed publishes the GUC; the sign-up hook self-stamps and cannot publish one, because Better Auth's adapter gives it no transaction.                                                                                                                                                                                                                                                                                                                                                                 |

Preconditions, now met: MB.64 (PR #168) and MB.12 (PR #169) are merged to `staging`; `/app` sits clean on the MB.12 branch. The secrets matrix is the pattern for a mail key, and real providers are live.

## Facts the record cites (verified against `node_modules`, 1.7.5)

- Token: `better-auth/dist/api/routes/email-verification.mjs:14-19` signs `{email, updateTo}` as HS256 with the secret; verified at `:178`; early return when already verified `:287-293`; the write is `internalAdapter.updateUserByEmail(email, {emailVerified: true})` `:294-296`, wrapped by `beforeEmailVerification`/`afterEmailVerification`, and it passes through `databaseHooks.user.update.before/after` (`db/internal-adapter.mjs:614-622`, `db/with-hooks.mjs:53-60`). The `before` hook sees only the patch plus the endpoint context and may merge columns, which is how `updatedBy` gets stamped. No `onEmailVerification` exists in 1.7.5.
- OAuth register with an unverified provider email creates `users` + `accounts` first (`oauth2/link-account.mjs:214-229`), mails when `sendOnSignUp ?? provider.requireEmailVerification` (`:253`), send failures are logged and swallowed (`:282-300`).
- Squat: `link-account.mjs:59` finds the row by email; `:78-85` refuses `account not linked` when the local row is unverified; `validateUserInfo` runs only after that (`:88`, `:132`), and `hooks.before` on the callback runs before the code exchange, so no hook of ours sees the profile at the refusal. The browser gets `?error=account_not_linked` (`api/routes/callback.mjs:243-245`), which `src/lib/sign-in.ts` does not map today.
- Provider mapping: Google `email_verified`, Discord `profile.verified`, Facebook `false`/`email_verified ?? false`, Microsoft `email_verified` or the `verified_*_email` claims (the nOAuth surface). Every provider spreads `...mapProfileToUser(profile)` after its own `emailVerified` (`@better-auth/core/dist/social-providers/google.mjs:124-131`, `microsoft-entra-id.mjs:118-126`), so `mapProfileToUser: () => ({ emailVerified: false })` forces a provider unverified.
- App: `src/lib/auth.ts` has no `emailVerification` or `accountLinking` config; `changeEmail`, `overrideUserInfoOnSignIn`, `trustedProviders` pinned off by `tests/lib/auth.test.ts:267-298`; `databaseHooks.user.create.before` (`:170-189`) self-stamps and publishes no GUC; no `user.update` hook, so a Better Auth `emailVerified` write leaves `updated_by` stale. `src/services/admin-role.ts` decides promotion on the fresh profile via `validateUserInfo` + request state.
- Schema: `users.email` not null, `emailVerified` default false, partial unique `users_email_unique`, `users_email_lower_case` check; `verifications` unaudited (adapter table, `auth.md` L78-80); `workspace_invitations` with `token_hash`, 7-day default expiry, `accepted_at/by`, `revoked_at`, viewer|member check, six audit columns; no invitation service; `/invite/*` public in `src/proxy.ts`.
- No mail code or provider anywhere. Env precedent (MB.60, commit 4a616af): a build-time variable touches `checks.yml`, `playwright.yml`, compose `e2e`, `deploy.yml --require`, `tests/guards/pulled-env-assertion.test.ts`, `secrets.md`, `auth.md`, `ci.md`. A key read only at send time needs the `secrets.md` row and Vercel env only (`secrets.md` L129-132).
- Delivery free tiers (re-verify with sources at execution; 2026 figures): Resend 3,000/mo, 100/day, one verified domain, pauses at the cap, on the Vercel Marketplace; Brevo 300/day; Mailtrap 4,000/mo, 150/day; Postmark 100/mo; Amazon SES sandbox limited to verified recipients until production access is granted, domain required. Site volume: a few mails a week.

- **Where things stand** — the facts above, grouped: Better Auth's flow, the squat and why no hook sees it, provider mapping and the `mapProfileToUser` lever, the app today, schema, no mail.
- **The approaches** — four questions, lettered options with `**Failure:**` / `**Cost:**` bullets and a `**Resolved:**` line each: (1) token: Better Auth JWT vs own hashed table; (2) squat: provisional-and-swept vs `requireLocalEmailVerified: false` (failure: a merge, the squatter's account stays linked; deprecated) vs verify-before-the-row-exists (failure: second provider round trip, replaces Better Auth's flow); (3) delivery: Resend, Brevo, Mailtrap, Postmark, SES on monthly cap, daily cap, domain requirement, behaviour at the cap, Marketplace presence, plus SMTP-everywhere rejected; (4) when verification is required: withheld session vs issued-and-gated vs both.
- **Decision** — one paragraph per question. The trust statement: `users.emailVerified` true now means Google, Discord, or we vouched, because Facebook and Microsoft are pinned unverified via `mapProfileToUser`. What stays off: `changeEmail`, `overrideUserInfoOnSignIn`, `trustedProviders`.
- **The token** — lifetime, not single-use and why acceptable for a write that flips one boolean, `autoSignInAfterVerification` off, `verifications` unused by this flow, a resend re-issues rather than revokes. **Verification completes only in a browser holding a session for that account**: `beforeEmailVerification(user, request)` refuses when the request's session is not that user's. This is what stops the pre-account attack where an attacker registers the victim's address unverified and the victim clicks the mail they did not ask for; state it as the reviewable claim.
- **What an unverified account can and cannot do** — has a session, can reach the email page, resend, sign out; cannot accept any invitation, be promoted, or create a workspace; is provisional until verified.
- **Provisional accounts and the sweep** — expiry from the last send (keyed on `updated_at`, so the resend service touches the row through `withAudit`), the sweep predicate and its partial index, removal of `accounts` and `sessions` with the row (else Better Auth resolves a soft-deleted user through a live account row), soft vs hard delete decided in MB.67 under rule 4's `write.delete` escape hatch, actor = the row's own id, argued as the create bootstrap's mirror in the same file, not a third exception; the `account_not_linked` message during the window.
- **The audit trail (rules 1 and 3)** — `beforeEmailVerification` records the user id in MB.60's request-state store; `user.update.before` merges `updatedBy` into the same statement; why the after-hook `withAudit` alternative (a second transaction for one column) is rejected. Rule 1: `/api/auth/verify-email` and `/send-verification-email` are the existing transport exception; the app's own writes (set email, resend touch) go through `/api/graphql`. Rule 3's corrected wording.
- **Delivery** — the comparison table: Resend, Brevo, Postmark, Mailgun, Mailtrap Sending, SES on monthly and daily caps, sending-domain requirement, behaviour at the cap, non-delivery mode, Marketplace presence (SES has no free tier for accounts created after July 2025; Brevo is a marketing-suite account with a contacts database and a paid branding add-on; Postmark is 100/mo with account approval; Mailgun 100/day with 1-day logs). Chosen: Resend in production (3,000/mo, 100/day, one verified domain, pauses at the cap, native Marketplace integration).
- **Keeping mail away from real people outside production** — previews (`VERCEL_ENV=preview`, staging and hotfix) send to the Mailtrap Email Sandbox, which captures and never delivers: free plan 50 test mails/mo, one sandbox, 10 stored messages, 1 per 10s; `POST https://sandbox.api.mailtrap.io/api/send/{sandbox_id}` with `Api-Token`; messages read at `GET https://mailtrap.io/api/sandboxes/{id}/messages?search=` and `…/messages/{id}/body.html`. Local and e2e send to Mailpit in compose (the maintained MailHog successor: single binary, Docker image, `:8025` UI and REST API, `POST /api/v1/send`), and Playwright reads the link from that API. A `MAIL_TRANSPORT` guard pinned by test: production refuses anything but `resend`, a preview refuses anything but `mailtrap-sandbox`, so a misconfigured environment sends nothing rather than something. Rejected: one nodemailer SMTP transport per environment (one code path, but SMTP from a Vercel function is the stated problem); a preview recipient allowlist with redirect (still delivers to someone); Brevo's sandbox header and Postmark's sandbox server (provider-bound, and the Sandbox already covers previews).
- **`mail.ts`** — `send({to, subject, text, html})`, three HTTP transports, `MAIL_FROM`, the sending domain and its DNS records as a one-time manual step in `secrets.md`, send failures logged not thrown, the caps (Resend 3,000/mo or 100/day pauses; Sandbox 50/mo fails and logs; volume never reaches either), keys runtime-only so no CI copy and no startup refusal.
- **MB.54's flow** — `/account/email` (protected), current address and state, change via a `setEmail` mutation → service under `withAudit` (refused when a live verified row holds it), resend through Better Auth's server API; a provider returning no address yields a sentinel `<providerAccountId>@pending.invalid` from `mapProfileToUser` so the row and session exist and the page can ask; the sentinel is never mailed and is swept like any provisional row.
- **Invitations by email** — what M7.3/M7.4/M7.5 become; §7's `Invitation` type, `acceptInvitation`/`revokeInvitation` mutations, `InvitationResult` and `url` removed; acceptance matches the session's `users.email` case-insensitively with `emailVerified` true; copy-link gone.
- **The admin invitation (story 62)** — `admin_invitations` table, hashed `randomBytes` token, mailed link, `/admin-invite/[token]`, acceptance as a grant through MB.59's `setUserRole` (ledger row naming the invitation, `canCreateWorkspace`, pause check on create and accept), revocation from `/admin/users`, M7.7-style distinct rejections.
- **Which of MB.60's restrictions each follow-up lifts** — MB.67 lifts "have the owner sign in first" and the squat; MB.66 lifts "an address is verified only when a provider says so" for every ordinary purpose; MB.68 adds a second promotion event, verification of the bootstrap address, safe only because of the session binding above. Kept: the fresh-profile Google-or-Discord rule on the sign-in path, Microsoft and Facebook never vouch, the three pinned options.
- **What is simplified, and the hole it leaves** — the window of `account_not_linked` for the real owner (one token lifetime), JWT replay within the hour, the phishing residual is closed by session binding.
- **Out of scope** — notifying admins of a grant, resend rate limits beyond Better Auth's, a mail log table, email/password sign-in, DMARC beyond what Resend's domain setup asks.
- **The follow-up** — the list below with wave placement and the one-line reason for each position.

## Risks

- The session-binding claim in MB.66 is the security argument the whole "lift the provider restriction" rests on; if review rejects it, MB.68 is dropped and the primary admin stays Google-or-Discord.
- The sweep must key on last-send time and remove `accounts`/`sessions`, or a resend deletes its own row mid-window and a soft-deleted user signs in through a live account row.
- Free-tier figures are re-verified with sources at execution; Resend's pause-at-cap behaviour and the Sandbox's 50/mo (shared by staging and every hotfix preview) are the two that matter. If the Sandbox cap proves too tight, the fallback is a second sandbox on a paid tier, not delivery.
- The transport guard is what keeps a preview from ever mailing a stranger; it must be pinned by test in MB.65, not left to configuration.
- `doc-citation` fails the PR on a section name off by one character.
- Better Auth facts are 1.7.5's; MB.66 re-checks hook signatures before building.
