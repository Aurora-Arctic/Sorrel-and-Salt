# M15.48 — A signed-out sender keeps a provisional session

Plan: `m15.48-plan.md`. This file records what was decided and what was left.

## Decision

A visitor who sends a support request while signed out is given an anonymous account and a session, through Better Auth's `anonymous` plugin. They can then read their own requests at `/account/support` and reply, without an account. This reverses the earlier decision to leave the plugin out (`mb.74-better-auth-plugins.md`, MB.80). The plugin is used for this one purpose; try-before-sign-up stays in v2.

- The anonymous session acts as itself only on `/support`, `/account/support` and below, and for the support GraphQL operations plus `sendSignedOutSupportRequest`. Everywhere else it reads as signed out.
- `/` and `/compendium` set no cookie.
- The sign-up hook skips an anonymous account: no demo-coven seat, no `canCreateWorkspace`.
- When the sender signs in to a real account, the plugin links the requests across. A request whose `sender_email` matches that account's verified address is claimed too.
- The daily provisional cleanup removes an anonymous account that holds no request and no standing time-out 7 days after creation (a request is handed to the System account when it is anonymised; a time-out goes with its account, so a standing one keeps the account).
- The People list, the access-pause check and the keepers' support sender names leave anonymous accounts out of "people".

## The proxy limit

`src/proxy.ts` checks only that a session cookie exists. An anonymous cookie therefore passes it on every protected path. The secure layer (`requireSession()`, `getShellSession()`, the GraphQL context) is what refuses it. The proxy was not changed.

## The two-factor link gap

The plugin's link hook does not match `/two-factor/verify-*`. A sender who signs in through two-factor from an anonymous session is not linked, and the anonymous account then expires under the cleanup rule. Known and accepted.

## The mailed link and the signed-out reply

Each mail about a request carries a view link holding a fresh token (32 random bytes, base64url; only its SHA-256 is stored in `support_requests.view_token_hash`; only the newest mailed link works). The page `/support/request/[token]` shows the request, and `replyToSupportRequestByViewToken` adds a reply as the request's own sender. Neither is the mailed sign-in link that DESIGN.md §13 defers: the link opens no session and no other data, and the page sets security headers that stop the token leaking through a referrer.

## Time-outs bind the anonymous account

A keeper’s support time-out names the anonymous account, so it holds as it does for a signed-in sender. A returning visitor’s send (`sendSignedOutSupportRequest`) and a reply through the mailed link (`replyToSupportRequestByViewToken`, after the token is valid) are refused with the signed-in wording. Claiming requests by address (`claimSupportRequestsByEmail`) moves the time-outs of the anonymous accounts whose requests were claimed to the claiming account, as `adoptAnonymousAccount` does. The keeper’s request detail reads `anonymousSender` and shows the Time-Out panel for it; the shared stand-in account (`SIGNED_OUT_SENDER_ID`) has no panel, since a time-out on it would bind every old signed-out request.

## Time-outs also bind the address

A time-out on an anonymous account would be escaped by clearing cookies, which mints a new account. So `support_timeouts.address_key` (nullable text, with a partial index `WHERE lifted_at IS NULL`) holds the HMAC key of the address the sender wrote from. `timeOutSupportSender` records `addressCountKey` of the address on the account's newest request that carries one; a signed-in sender's requests carry none, so the column is null. It holds the HMAC, keyed by `BETTER_AUTH_SECRET` like `support_send_counts`, and never the address, so the table gives away no address to anyone holding it. The migration only adds, so it needs no acknowledgement sidecar.

A time-out standing on a key (not lifted, and no end date or one still ahead) is checked in four places, each reading it from the repository in SQL:

1. The signed-out send, before the limits are counted and before any account is minted, for a new and a returning visitor. A refusal writes no request and mints nothing.
2. The reply through the mailed link, against the request's `sender_email`.
3. The claim by email: `claimSupportRequestsByEmail` moves the standing time-outs that bind the claimed address to the claiming account, even when their account holds none of the claimed requests.
4. The expiry sweep: it keeps an anonymous account while it holds any standing time-out. A lifted or run-out time-out no longer keeps it.

Each refusal uses the signed-in wording.

## Left for a later drop task

`support_requests.sender_email` and the seeded signed-out sender account (`SIGNED_OUT_SENDER_ID`) stay, since existing rows use them. Removing them is a separate drop task, in two PRs.
