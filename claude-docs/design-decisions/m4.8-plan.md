# M4.8 — `categoriesByIngredient` and `folkNamesByIngredient` loaders

## Context

M4.8 asks for three things: the loader factory, `categoriesByIngredient`, and
`folkNamesByIngredient`. **The factory is already built.** M3.2 landed
`defineLoader`, `buildLoaders`/`createLoaders`, the per-request test and the
lint pin, and `membershipsByUser` uses it. The acceptance criterion "Loaders are
per-request" is met by that base. This PR adds the two loaders, the
service and repository read behind them, and a query-count test, and corrects
TASKS.md to say the base came from M3.2.

Their first caller is M8.5 (`Ingredient.categories`, `Ingredient.folkNames`),
and one design fact from it shapes everything below. **A batch can mix tiers.**
The public compendium (MB.80) resolves these fields with **no session**, and a
coven page resolves compendium and workspace ingredients side by side. So
`membershipsByUser`'s shape, where a null session gets `Forbidden` everywhere,
is wrong here.

## What it will never return

A workspace ingredient's folk names or categories never reach anyone outside
that workspace. That holds even when the caller knows the ingredient's id, and
even when the key lies about which workspace the ingredient is in. Three layers
stop it, and any one of them is enough on its own:

1. **The check.** A workspace ingredient's key costs an
   `assertMembership(session, workspaceId, { ingredient: ['read'] })`. If the
   caller is not a member of that coven (**D** for W, or the admin **E**), the
   key's slot answers `Forbidden`. A signed-out caller gets the same.
2. **The SQL.** The read's `EXISTS` admits a child row only when its parent is
   in the compendium or in a workspace a proof was minted for. The scope comes
   from the proofs and never from the key. So a key for X's ingredient that
   claims `workspaceId: null` (compendium) or claims W gets **zero rows**. Its
   slot is `[]`, and the filtering happens in the database, not after the
   fetch (rule 7).
3. **The type.** `NotIngredientScoped` makes `findMany(ingredientFolkNames, …)`
   and its siblings a compile error, so a later service cannot read these
   tables around the scoped finder.

What it _does_ return:

- A **compendium** entry's children, to anyone, signed out included. This is
  MB.80's one public surface.
- A **workspace** entry's children, to any member of that coven, viewers
  included. Ingredients belong to the coven, not to the member who created
  them, so B sees A's.

The tests assert each refusal with its precondition. The row exists, it has
children, and a member reads them through the same key. That way a refusal
cannot pass merely because the fixture was empty.

## The authorization gap this closes

`ingredient_categories` and `ingredient_folk_names` carry `ingredient_id` and
no `workspace_id`. By shape they are `Unscoped`, so `findMany(ingredientCategories, …)`
compiles today and would return a workspace ingredient's children with no proof.
That is the gap M10.3 closed for `spell_*` with `SpellScoped`/`NotSpellScoped`,
and it is open here only because nothing has read these tables yet. M4.8 adds
their first reader, so it closes the gap in the same shape:

- `shapes.ts`: `IngredientScoped = { ingredientId: AnyPgColumn }`, plus
  `NotIngredientScoped = { ingredientId?: never }` on the **unscoped** finders
  (`findMany`, `findOne`, `findOneById`, `findManyByIds`, `findPage`,
  `findManyIncludingSoftDeleted`). `inventory_items` and `spell_ingredients`
  are unaffected: they are already workspace- or spell-scoped and never reach
  those finders.
- The one existing call, `findMany(ingredientCategories)` in
  `ingredient-categories-schema.test.ts:273`, switches to the test's raw `sql`
  client.

## The read

**New finder** `findManyOfIngredients(memberships, table, ingredientIds)` in
`src/db/repository/ingredients.ts`:

- `table` is `IngredientScoped & Unscoped` (the two child tables).
- It returns the live rows whose `ingredient_id` is in the ids, filtered by a
  correlated `EXISTS` on the parent: the parent is live **and** either
  `workspace_id is null` or `workspace_id` is one of the proofs' workspaces.
  This is `sql`, not a subquery builder, for the reason `findManyInSpell`
  gives: `selectFrom` stays the only select builder.
- `memberships: readonly Membership[]` may be empty, which means compendium
  only. The scope therefore comes from the proofs and nothing else.
- It reads both tiers in one statement, so it goes into `TIER_SEAM`. It also
  goes into the pinned `EXPORTED_FUNCTIONS` and into the index.

**New service** in `src/modules/ingredients/services/ingredient-children.ts`
(`import 'server-only'`): `categoriesOf(session | null, keys)` and
`folkNamesOf(session | null, keys)`. The key is `{ id, workspaceId }`, the
parent `Ingredient` row the resolver already holds.

1. For each distinct non-null `workspaceId` among the keys, call
   `assertMembership(session, ws, { ingredient: ['read'] })`. If the call
   throws `Forbidden`, or there is no session, those keys get `Forbidden` in
   their own slots and the rest of the batch stands (as in `membershipsOf`).
2. Run one `findManyOfIngredients(proofs, table, ids)` over the remaining keys.
   A key that lies about its `workspaceId` gets no rows, because the `EXISTS`
   checks the parent's real tier, not the key's claim.
3. Categories only: one `findManyByIds(categories, …)` for the rows the
   join table points at.
4. Answer one slot per key in key order. Children are sorted by name, so the
   output is deterministic. Folk names come back as `string[]`, because §7
   exposes `folkNames: [String!]!` flattened.

**Query count:** one read for folk names and two for categories, plus one
`findWorkspaceRole` per distinct coven in the batch. A 50-ingredient page is at
most 1 + 2, so the count is bounded by the number of covens in the batch, not
the number of ingredients. A signed-out compendium batch needs no role lookup.

**Loaders** in `src/modules/ingredients/loaders/`: `categoriesByIngredient` and
`folkNamesByIngredient`, each built with `defineLoader` and a
`cacheKeyFn: key => key.id`. They are exported through the module index and
spread into `LOADERS` in `src/graphql/loaders/index.ts`.

## Tests (written first)

`tests/modules/ingredients/loaders/ingredient-children.test.ts` (one file for both loaders, mirroring `loaders/ingredient-children.ts`),
in the `db` project. They mock the repository the way
`memberships-by-user.test.ts` does and count every repository call the path
reaches (`findManyOfIngredients`, `findManyByIds`, `findWorkspaceRole`):

- They seed 50 ingredients (compendium plus W) with categories and folk names.
  All 50 are loaded, the tests assert the exact call counts, and each slot is
  checked against its own ingredient, so the ordering is correct.
- Loading keys in reverse order returns each ingredient's own children.
- With a null session, a compendium ingredient resolves and a W ingredient is
  `Forbidden`.
- Authorization: **D** (member of X), passing a W ingredient **by direct id**,
  gets `Forbidden`. A key claiming `workspaceId: null` for a W ingredient gets
  `[]`. The preconditions are asserted first: the row exists and has children,
  and **B** sees them through the same key. **E** (admin) gets W's refused.
- A soft-deleted ingredient or folk name is excluded.
- An `@ts-expect-error` probe shows that `findMany(ingredientCategories)` no
  longer compiles.

The guard updates are `TIER_SEAM` and `EXPORTED_FUNCTIONS`.
