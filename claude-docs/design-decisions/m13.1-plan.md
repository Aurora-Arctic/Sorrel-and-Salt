# Plan: spell steps and workings

Two backlog lines, now one model. Nothing is written to the repo until each task is minted with `/create-feature-task`; this file is what those runs mint from, and what the existing Wave 13 entries are corrected against.

## Context

The backlog asks for two things: "spell recipes and spell jars completed" (how many times a spell was made, reducing stock, with notes and private/coven visibility) and "steps to spells so the order of combination and any ritual can be recorded". The grimoire is entirely unbuilt (all 22 Wave 13 tasks open), so the shape can still be set before anything is retrofitted.

Decisions taken in this conversation (2026-10-15/16), the owner's:

| Topic                 | Decision                                                                                                                                                                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Noun for one making   | **Working.** A spell is the recipe for a working; a working is the record of one time it was made. The docs' phrase "a spell is a record of a working" (about 19 places) is corrected.                                                          |
| Recipe vs steps       | **One interleaved list.** A step is an instruction, an ingredient, or both, in one order. "Layer" survives only as the word for a step that lays an ingredient.                                                                                 |
| Only finished recipes | A working needs `status = complete`. A complete recipe stays editable (M10.20 keeps completion reversible); v2's edit history pins each working to the recipe revision it was made from.                                                        |
| Participants          | A working names several participants: coven members (viewers included) picked from the coven, plus typed names for anyone else. A member named on a private working can read it.                                                                |
| Comparable units      | A spell may only use units that convert to the stocked ingredient's unit: saving refuses anything else. The one exception is drift after the save: saving or completing a working warns that it drifted, allows it, and deducts nothing for it. |
| Stock running short   | Deduct down to zero, record what was taken and the shortfall, never negative, never refuse.                                                                                                                                                     |
| Draft workings        | A working is created as a draft and deducts nothing; completing it deducts. Deleting a complete working does not restore stock.                                                                                                                 |
| Notes                 | One free-text `note` on the spell and one on the working, the layer note's shape. The notes subsystem stays v2. The per-ingredient note is kept.                                                                                                |
| Table name            | `spell_ingredients` becomes `spell_steps`, following MB.252's rename precedent (compatibility view, later contract task). `layer_order` becomes `position` and `instructions` becomes `note` in two steps, per the expand/contract rule.        |
| Milestone             | Wave 13 — Grimoire, ids `M13.1` onward, MB.123's design review covering it all.                                                                                                                                                                 |

## The model

### Steps: the existing table, widened

`spell_ingredients` already holds an ordered list keyed on a surrogate id, soft-deleted, with `layer_order` unique among live rows and MB.40's one-of check between an ingredient link and a custom name. MB.40's own argument (one ordered list cannot span two tables: `claude-docs/design-decisions/mb.40-custom-spell-ingredients.md`, "Why not the alternatives") decides this too: the step is a row in that table, not a second table beside it.

Expand (M13.1), one migration written with `drizzle-kit generate --custom` and a hand-edited snapshot, exactly as `0067_celestial-bodies-expand.sql` was (`claude-docs/db/expand-contract.md`, "the rename needs no second table"):

- `ALTER TABLE spell_ingredients RENAME TO spell_steps`; indexes, CHECKs and foreign keys renamed with it (`ALTER INDEX … RENAME`, `ALTER TABLE … RENAME CONSTRAINT`); `CREATE VIEW spell_ingredients AS SELECT * FROM spell_steps`, listed in `tests/db/schema-drift.test.ts`'s `PENDING_DROPS` as a view.
- `position integer` added nullable and backfilled from `layer_order`; the new live unique index on `(spell_id, position)`; the code writes both columns until the contract. `layer_order` keeps its index until then.
- `body text` nullable, non-blank CHECK: the instruction.
- `num_nonnulls(ingredient_id, name) <= 1` and `num_nonnulls(ingredient_id, name, body) >= 1` replace `spell_ingredients_ingredient_or_name` (the DROP CONSTRAINT is acknowledged in the sidecar).
- `quantity`, `unit` and `note` null unless the step carries `ingredient_id` or `name`.
- `spells.note text` added; `instructions` backfilled into it; the code writes both until the contract.
- Everything else stays: the variant unique index, the custom-name unique index, the variant composite FK, the form/variant checks, the `updated_at` trigger.

Contract (M13.9, a later release): drop the `spell_ingredients` view, `layer_order` with its index, and `instructions`, under one acknowledgement.

Reads and writes keep their shape: `findManyInSpell` (`src/db/repository/spells.ts`) reads the list in order, the reorder moves live rows through a scratch offset (`claude-docs/db/grimoire.md`, "Position is the identity"), a removed step is a tombstone (MB.110), derived categories and stock comparison read only the steps with an ingredient. `findManyOfSpellIngredientsIncludingSoftDeleted` is not renamed: it reads the categories and folk names of the ingredients used in readable spells, not step rows.

The owner's later note, that v2 steps should reference layers, is met by the model itself: a step carries its ingredient. §13 gets one line, that a working pins the spell revision.

### Workings: three new tables

- `spell_workings`: `id`, `spellId`, `status` (`draft` | `complete`, new enum `working_status`), `workedOn` (date, when it was made), `completedAt` (timestamptz, null while draft), `note` (nullable, non-blank), `visibility` (`spell_visibility` enum, default `workspace`), full `...auditColumns`, soft-deleted. `createdBy` is who recorded it. Index `(spell_id, worked_on DESC) WHERE deleted_at IS NULL`.
- `spell_working_participants`: `id`, `workingId`, `userId` (nullable, FK users), `name` (nullable, non-blank), `position` (order entered, as deities keep theirs), full audit, soft-deleted. `CHECK (num_nonnulls(user_id, name) = 1)`, the MB.40 idiom. Partial uniques on `(working_id, user_id)` and `(working_id, lower(name))`. Member names read through MB.10's co-member finder so a removed member still shows.
- `spell_working_deductions`: `id`, `workingId`, `spellStepId`, `inventoryItemId`, `quantity`, `unit` (the stock row's unit), `shortfall` (numeric, 0 when fully met), `...auditStampColumns`, written once at completion and never edited (a pairing with a value, argued in the decision record). Index on `working_id`.

Visibility: a working is never wider than its spell, enforced in the service (a CHECK cannot read the parent); a `private` working is read by its recorder and its member participants. Widening is one-way with the spell's explaining error.

Completion, in one `withAudit`: for each live step with a linked ingredient, find the coven's stock row for the variant; `unitConvert` (M9.5) the step's quantity into the row's unit; subtract through M9.3's stock writer, floored at zero; write a deduction row with the amount taken and the shortfall. A step not stocked, a custom step, a step with no quantity, or a refused conversion (drift since the spell was saved) writes no deduction and comes back as a warning naming the step and the reason. The same warnings are computed when a draft working is saved, so the recorder sees drift before completing. The count on a spell is its visible complete workings.

### Comparable units at save time

New rule in the spell service (not Zod, which cannot see stock): a step linking a variant the coven holds a stock row for must carry a unit `unitConvert` accepts into that row's unit (same dimension; a count unit must be identical, since `unitConvert` refuses every count). Refused as a `ValidationError` at the step's path, so the builder shows it inline. A step with no stock row is unchecked; drift after the save is the working's warning, not the spell's error.

### M13.2 — Step units must convert to the jar's · 1.5h

_Story 77:_ As a workspace member, I want a step's unit to be one the jar can be measured against, so that making the spell can take it out of stock.

The rule under "Comparable units at save time", in the spell service `createSpell`/`updateSpell` path M10.10 builds, refused with a `ValidationError` at `steps.<i>.unit`, surfaced inline by MB.43's `fieldErrors`. A custom step and an unstocked variant are unchecked.

Acceptance criteria:

- A weight step against a volume jar, and a `pinch` step against a `piece` jar, are refused at the step's path and never written
- A `tsp` step against a `ml` jar, and an identical count unit, save
- A step whose variant has no stock row saves with any unit
- A stock row whose unit changes after the save does not invalidate the spell; the working's warning reports it (asserted in M13.5)
- The authorization precondition is proved: the check runs under the caller's proof against that coven's stock only

### M13.5 — Working service: record, complete and deduct, update, delete · 3.5h

_Stories 76 and 78:_ record a working · complete it and have stock deducted, warned where it cannot be · note how it went · keep it private or share it, one way.

`recordWorking(session, workspaceId, spellId, input)`: `assertMembership` with a write permission (owner and member; viewer refused); the spell visible to the caller and `complete`; visibility capped at the spell's; participants written in order, the caller first by default; the drift warnings computed and returned. `completeWorking`: the deduction under "Workings", one `withAudit`, returning the working and a per-step report (taken, shortfall, or not deducted and why). `updateWorking`: date, note, participants, widen visibility only through `resolveSpellVisibility`'s rule and error. `deleteWorking`: soft, by its recorder; stock untouched. Finders in the `findManyInSpell` shape, ANDing the working's own visibility: `private` reaches `created_by = membership.userId` or a live participant row with that user id. A count finder over a batch of spell ids counts visible complete workings.

Acceptance criteria:

- Direct-id refusals, each with its precondition proved: D (non-member) on every call; C (viewer) recording; B reading A's private working unless named on it; recording against a draft spell; recording against a private spell B cannot see
- Completing deducts exactly the converted amount per stocked step, floors at zero and records the shortfall; a draft deducts nothing; completing twice is refused
- A custom step, an unstocked step, a step with no quantity, and a refused conversion each write no deduction and are named in the report with their reason, at save and at completion
- One transaction: a failing deduction leaves no `completedAt` and no deduction rows
- Narrowing visibility is refused with the explaining error; a working cannot be wider than its spell
- A removed member stays a participant, read under their last name (MB.10)
