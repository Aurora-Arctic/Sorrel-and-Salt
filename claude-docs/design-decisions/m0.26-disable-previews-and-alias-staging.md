# M0.26 — CLI-driven Vercel deploys, staging aliased

**Status:** decided · **Date:** 2026-09-09

The task as written: turn deploy previews off, give `staging` a URL that is
fixed across redeploys, and confirm the production alias tracks `main`. The
domain in hand is `sorrelandsalt.com`, and the story also wants a stable
naming schema for hotfix deployments.

The plan behind it assumed a named `staging` environment on
`staging.sorrelandsalt.com`. That needs Vercel **Pro** — Custom Environments
are Pro/Enterprise only (`/docs/deployments/environments`: "Pro and Enterprise
teams can create Custom Environments"). Rather than settle for the bare
`…-git-staging-<scope>.vercel.app` alias as the staging origin, this task
**switches the deploy model from Vercel's Git integration to CLI-driven
deploys from CI**. That is a larger change than the 1h estimate and it
supersedes M0.25's approach; it was taken deliberately (see the cross-task
notes below).

## Decided

- **Deploys run from `.github/workflows/deploy.yml`, not the Git
  integration.** It triggers on a **push** to `main` / `staging` and on a
  **`pull_request` into `main` from a `hotfix/**` head**, and does, on a bare
  `ubuntu-latest` runner:

  ```text
  npm ci
  npm i -g vercel@59
  vercel pull  --yes --environment=<production|preview> --token=$VERCEL_DEPLOY_TOKEN
  vercel build [--prod]                                 --token=$VERCEL_DEPLOY_TOKEN
  url=$(vercel deploy --prebuilt [--prod]               --token=$VERCEL_DEPLOY_TOKEN)
  vercel alias set "$url" <target-domain> --token=$VERCEL_DEPLOY_TOKEN --scope=$VERCEL_SCOPE
  ```

  This is Vercel's own documented CI pattern
  (`/docs/cli/deploy`, `/kb/guide/how-to-alias-a-preview-deployment-using-the-cli`).
  `main` skips the alias step — `vercel deploy --prebuilt --prod`
  auto-assigns the production domains. Target domain: `staging` →
  `staging.sorrelandsalt.com`; a hotfix PR → `hotfix-<slug>.sorrelandsalt.com`
  (see below). A second `teardown` job runs `vercel alias rm` when a hotfix
  PR closes.

- **The Git integration is turned off in `vercel.json`.** M0.25's allow-list
  becomes a blanket off switch:

  ```json
  { "$schema": "…", "git": { "deploymentEnabled": { "**": false } } }
  ```

  `"**": false` disables an automatic deployment for every branch, so CI is
  the only path that ships code even if the Git integration stays connected
  in the dashboard. Disconnecting it there is optional and not scripted from
  here. This directly meets acceptance criterion one — "deploy previews are
  off" — for every branch, not just the non-allow-listed ones.

- **Staging is aliased to `staging.sorrelandsalt.com` by `vercel alias`.**
  The `vercel alias` docs call this out as the intended path when you are
  **not** using the Git integration: "If you're not using the Git
  Integration, `vercel alias` is a great solution if you still need to apply
  custom domains based on Git branches." The target is a plain custom domain
  added to the one Vercel project with **no** preview-branch binding — which
  is what the Pro gate was actually on (branch⇄domain assignment in project
  settings, and Custom Environments). `deploy.yml` re-points it at the newest
  `staging` deployment on every push, so the URL is fixed across deploys —
  acceptance criterion two. This is the canonical staging origin; M0.27's
  matrix and both OAuth apps' redirect URIs point here.

  DNS: one `CNAME` `staging` → `cname.vercel-dns.com` (exact value from the
  Vercel dashboard). Until it resolves, `vercel alias` can target
  `staging-sorrel-and-salt.<scope>.vercel.app` as an interim.

- **Production: `main` → `sorrelandsalt.com`.** On a push to `main`,
  `deploy.yml` runs the deploy with `--prod`, and Vercel assigns the
  production domains (`sorrelandsalt.com`, `www`) to that deployment —
  acceptance criterion three. The domains are added to the project once, in
  the dashboard; that is the only required manual Vercel step.

- **Hotfix: a per-PR domain, deployed on the PR.** A `hotfix/**` branch does
  **not** deploy on push. Instead `deploy.yml` also triggers on a
  `pull_request` into `main` whose head is `hotfix/**`, deploys a Preview,
  and aliases it to `hotfix-<slug>.sorrelandsalt.com` where `<slug>` is the
  branch name after `hotfix/`, lowercased and reduced to a DNS label. The
  alias URL is posted to the PR with the `pr-comment` composite action, and a
  `teardown` job removes the alias (`vercel alias rm`) when the PR closes so
  stale domains don't accumulate against the Hobby 50-per-project cap.

  - **Why the PR, not push.** An urgent fix wants a preview its reviewers can
    click while reviewing, and it reaches production through its own `main`
    PR anyway — deploying on push would be a second, redundant deployment.
    The `create-pr` skill opens a hotfix PR into `main` _and_ `staging`;
    `deploy.yml`'s trigger is `branches: [main]`, so only the `main` PR
    deploys and a hotfix deploys once. `pull_request` (not
    `pull_request_target`) is safe — hotfix branches are always in this repo,
    never a fork, so the run gets the `VERCEL_*` secrets with no untrusted
    checkout.

  - **Why a per-PR domain needs a wildcard.** `hotfix-<slug>.sorrelandsalt.com`
    is a _different_ hostname per hotfix, so it can't be a single
    pre-registered project domain. The clean way is one wildcard
    `*.sorrelandsalt.com` on the project: Vercel then answers every
    `hotfix-*.sorrelandsalt.com` with an auto-provisioned cert and DNS, and
    `vercel alias set` to a fresh name Just Works with no per-hotfix setup.
    Wildcard domains are **available on Hobby** but require the domain to use
    **Vercel's nameservers** (`/docs/domains/working-with-domains/add-a-domain`:
    "If using your custom domain as a wildcard domain, you must use the
    nameservers method"). Moving `sorrelandsalt.com` to Vercel nameservers is
    the one manual prerequisite for the hotfix path; `main`/`staging` work
    with plain `CNAME`/`A` records regardless.

  - **Branch naming.** `hotfix/<task-id>-<slug>` — e.g.
    `hotfix/m4-7-spell-visibility-leak` — so the branch, the Asana card, the
    deployment logs, and now the preview hostname
    (`hotfix-m4-7-spell-visibility-leak.sorrelandsalt.com`) share an
    identifier. A **recommendation for the `create-hotfix` skill**, its own
    task; not an M0.26 acceptance criterion.

- **`--prebuilt` caveat.** With `--prebuilt`, System Environment Variables
  are absent at build time. This app does not read them at build time (Next
  reads its own env at runtime; nothing in the build depends on `VERCEL_*`),
  so `--prebuilt` is safe and keeps the build on GitHub's runners where the
  rest of CI already is.

- **Secrets are deferred to M0.27.** `deploy.yml` needs `VERCEL_DEPLOY_TOKEN`,
  `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, and `VERCEL_SCOPE` (the team/username
  slug `vercel alias` wants) as **GitHub Actions** secrets. They are added to
  M0.27's env/secrets matrix. Until they exist the workflow's first step
  sees no token, emits a `::warning::`, and skips every real step — the job
  still completes green, the same stub-now/wire-later shape `pr-gate.yml`
  uses for its `vitest`/`playwright` jobs.

- **Bare runner, not the `testing` GHCR image.** `deploy.yml` needs the
  Vercel CLI and writes `.vercel/output`; the shared test image is not built
  for that. `composite-actions-check.yml` already set the precedent that a
  bare `ubuntu-latest` runner is fine when the container image is not the
  right fit. It uses `actions/setup-node@v4` (Node 22, npm cache) and the
  repo's `timer-start` / `timer-elapsed` / `job-summary` composite actions;
  `pr-comment` (`success-mode: comment`) posts the preview URL on hotfix PRs,
  and the workflow takes `pull-requests: write` for it.

## Cross-task impact

- **M0.25** — its `git.deploymentEnabled` allow-list (`main`/`staging`/
  `hotfix/*` → `true`) is replaced by `{ "**": false }`. Its decision doc's
  "Rules this sets" is partly superseded; it stays as the historical record
  of why the catch-all form is needed.
- **M0.28** ("deploy hello-world from staging and promote to production") —
  now runs through `deploy.yml`: a push to `staging` is the preview deploy +
  alias; `release/0.0.1` merging to `main` is the `--prod` deploy. The task's
  "confirm the Preview deploy" wording wants a refresh when it is picked up.
- **M1.1** ("wire the Neon Vercel integration") — still needed. The
  integration populates the Vercel project's per-environment variables;
  `vercel pull` fetches them into the CI build, and runtime reads them from
  the project. "Injected per environment" becomes "fetched by `vercel pull`".
- **M1.4** (`migrate.yml`) — migrations must complete before `deploy.yml`
  ships the new deployment. Wire it as a `needs:` job inside `deploy.yml` or
  a `workflow_run` predecessor when M1.4 lands.

  (`actionlint` is not available via `npx` in this environment; `js-yaml` is
  the check M0.24's decision doc used for the same reason).
- `vercel.json` is valid JSON; `npx prettier --check` clean on it and every
  touched `.md`.
- `npm run lint` / `format:check` / `typecheck` / `check:stories` all exit 0
  (YAML + JSON + docs only).
- Command sequence in `deploy.yml` checked line-by-line against
  `/docs/cli/deploy`, `/docs/cli/alias`, and
  `/kb/guide/how-to-alias-a-preview-deployment-using-the-cli` (all 2026-08).
- **Not verifiable pre-merge** (needs the `VERCEL_*` secrets from M0.27, the
  live project, and `*.sorrelandsalt.com` on Vercel nameservers):
  - push to `staging` → `deploy.yml` deploys a Preview and
    `staging.sorrelandsalt.com` serves it; re-push → same URL, new build;
  - push to `main` → `--prod` deploy; `sorrelandsalt.com` serves it;
  - a `feature/*` push triggers no `deploy.yml` run and no Vercel deploy;
  - a `hotfix/** → main` PR → Preview at
    `hotfix-<slug>.sorrelandsalt.com`, URL commented on the PR; closing the
    PR removes the alias; the sibling `hotfix/** → staging` PR does not
    deploy.

## Rules this sets

- **Deploys are CI-only.** `deploy.yml` — push to `main`/`staging`, or a
  `hotfix/** → main` PR — is the sole deploy path; `vercel.json` keeps the
  Git integration off. A new deploy target means editing `deploy.yml`'s
  trigger and target resolution, not `vercel.json`.
- The stable staging origin is `https://staging.sorrelandsalt.com`, held by
  `vercel alias`. M0.27's matrix and both OAuth apps point there.
- Per-hotfix preview domains (`hotfix-<slug>.sorrelandsalt.com`) rely on a
  wildcard `*.sorrelandsalt.com` on the project, which requires the domain to
  use Vercel's nameservers. That is a prerequisite for the hotfix path only.
- Hotfix preview aliases are cleaned up by `deploy.yml`'s `teardown` job on
  PR close — nothing else prunes them, and Hobby caps a project at 50 domains.
- `deploy.yml` references `VERCEL_DEPLOY_TOKEN` / `VERCEL_ORG_ID` /
  `VERCEL_PROJECT_ID` / `VERCEL_SCOPE`; the guard step keeps the job green
  until M0.27 sets them.
- Hotfix branches should be named `hotfix/<task-id>-<slug>` — a follow-up for
  the `create-hotfix` skill.
- `migrate.yml` (M1.4), when it lands, runs ahead of the deploy step in
  `deploy.yml`.
