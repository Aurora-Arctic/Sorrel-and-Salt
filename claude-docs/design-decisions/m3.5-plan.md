# M3.5 — graphql-codegen and the staleness check

## Context

M3.5 was written before Pothos, the server read path (M3.8) and M3.4's SDL
snapshot existed. Before starting it, the question was whether it still earns
its place.

**What it buys.** Pothos types the _server_. Nothing types the _browser_: every
mutation (§7's sketch has about 13) and every read made without a navigation
(M5.10a's suggesting combobox, "load more" through M3.6's cursor helper, modals)
is a GraphQL document sent through `graphql-request`. Without something tying
those documents to the schema, each call is `request<HandWrittenType>(doc)`, a
hand-kept type that drifts silently when a field is renamed. That is the failure
§2 rejected SDL-first for, and §14's "GraphQL kept" row names "a single typed
contract" as what makes the transport worth its cost. Dropping client typegen
would keep the cost and remove half the contract.

**What was stale in the task as written.**

1. "Codegen produces typed documents **and hooks**." graphql-codegen's current
   recommendation is `client-preset`: a typed `graphql()` function returning a
   `TypedDocumentNode`, with no generated hooks. With TanStack Query the hook is
   `useQuery({ queryKey, queryFn: () => request(doc, vars) })`, which is M3.7's
   request function. The hooks plugin (`typescript-react-query`) is
   community-maintained.
2. "Add `codegen.yml` to CI." M3.4 already commits `src/graphql/schema.graphql`
   and fails when it drifts, so codegen reads that file rather than booting the
   schema, and staleness is one guard in `tests/guards/` running in CI's existing
   `vitest` job, with no new leg.

## Decision

Keep graphql-codegen, re-scoped:

- `@graphql-codegen/cli` and `@graphql-codegen/client-preset`, from The Guild,
  the maintainers of Yoga: the standard tool.
- The schema source is M3.4's committed SDL. The chain is Pothos →
  `schema.graphql` → generated types, so one reviewable file carries every
  contract change first.
- Output is committed under `src/gql/` (client-preset's own convention, and
  outside `src/graphql/`, which is the server layer M3.9 fences), and ignored by
  Prettier beside `schema.graphql`, since the generator owns the layout.
- `npm run codegen` replaces the placeholder. The staleness guard regenerates in
  memory and compares.
- No hooks. M3.7 owns running a `TypedDocumentNode` through TanStack Query.

**Weighed and not taken.**

- **gql.tada:** no generated file per operation, with types inferred in the
  editor from one generated `graphql-env.d.ts`. Fewer files, but still a
  generated artefact to keep fresh, a TypeScript-plugin dependency for good
  diagnostics, and an inference cost that grows with the number of documents. A
  legitimate choice, but not preferred over the standard tool.
- **No typegen** (hand-written result types, optionally checked with Zod at
  runtime): the browser half of the contract drifts silently.

The doc corrections landed in M3.5's own PR rather than on M3.4's branch, so each
PR carried one task.

## Verification

`npm run codegen` is clean on a fresh checkout. The guard fails when a committed
file is edited by hand, when a document selects a field the schema lacks, and
when a custom scalar has no mapping. `npm run test:coverage` passes.
