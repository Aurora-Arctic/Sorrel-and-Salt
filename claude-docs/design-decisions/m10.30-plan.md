# Dependency audit, 2026-10-12: what can move, and the work to move it

## Context

`npm i` prints twenty "Package no longer supported" warnings, one per `@react-email/*` package. That prompted a full audit of the 69 direct dependencies (34 runtime, 35 dev): what is behind, what has a major, what is blocked upstream, and what `npm audit` is really saying. Part 1 is the catalogue. Part 2 is the work: five tasks, one PR each, written as briefs a Sonnet agent can run from the text alone.

What is already automated: `.github/dependabot.yml` opens weekly npm, GitHub Actions and Docker PRs into `staging`, grouping React and Better Auth. It handled 10 bumps in the last fortnight. It does **not** swap a deprecated package for its successor, take a major that needs code changes, move a pinned package, or explain an advisory with no fix. The CI `audit` leg (`checks.yml`) is non-blocking and only comments; the repo already answers a downgrade-only "fix" with No.

Everything here was read from the registry, the lockfile, the installed packages and the upstream trackers today. Hour figures are my estimates.

Owner's calls so far: tasks mint into Wave 10; the refresh is one `npm update` PR, not Dependabot's twenty; graphql-request is not needed and goes (task 5); the doc work runs in a worktree and opens a PR when done.

### B. Deprecated, successor available: React Email

`@react-email/components@1.0.12` and its 19 component packages are deprecated on npm at every version. React Email 6.0.0 (April 2026) folded them into `react-email`; 6.11.1 (6 October 2026) is current. One import site: `src/emails/parts/layout.tsx:14`. ### C. Major available, code changes needed: msw 2.15 → 3.0.3

Peers met: Node ≥ 22.12 (26.6.0), `graphql >= 16` (16.14.2), `vite >= 6` (8.3.2). The repo already uses the v3 model (`graphql.link('/api/graphql')` with `.query`/`.mutation`) and never used the removed top-level `graphql.query`, `setupWorker`, `passthrough`, `bypass` or `delay`. What changes: `http`/`HttpResponse` move to `msw/http`, `graphql` and its types to `msw/graphql` (`msw/node` is unchanged); `onUnhandledRequest` becomes `onUnhandledFrame`, same `'error'` string; `graphql` becomes a peer instead of msw's own dependency.

### D. Major available, blocked upstream: graphql 16 → 17.0.2

Yoga, Pothos (all four), graphql-scalars, codegen and the typed-document-node core accept 17. Two do not: `graphql-request@7.4.0` (peer `14 - 16`) and `@escape.tech/graphql-armor@3.2.0` (`^16.10.0`, open issue #885 "Support graphql v17", September 2026).

**Do we need graphql-request at all? No.** The project was renamed Graffle and `graphql-request` is "the old version", kept on a branch with occasional releases (last 7.4.0, December 2025); a 17 range is unlikely to come from it. The repo uses two things from it, `request()` and the `ClientError` class, in two source files and two tests. `request()` is a `fetch` POST of `{ query: print(document), variables }` that throws when the answer carries `errors`; `ClientError` is read for `response.status` (the retry rule) and `response.errors[0].extensions` (the form readers). Neither batching, `gql`, `rawRequest` nor a custom fetch is used. A wrapper of about forty lines replaces it (task 5). The armor blocker remains, so graphql 17 itself still waits on #885.

## Brief M10.31 — A fetch wrapper replaces graphql-request

**Goal.** Remove `graphql-request`: it is the old, branch-maintained name of Graffle, pins `graphql` to 16, and the repo uses only a POST and an error class from it.

**Worktree.** `m10.31`, branch `feature/m10.31-fetch-wrapper-replaces-graphql-request`. Needs `.env.local` for e2e and the build check.

**What it uses today.** Read `src/lib/graphql-client.ts` and `src/lib/graphql-failure.ts` in full before writing anything. `send()` calls `request({ url, document, variables, signal })`; `shouldRetry` reads `ClientError.response.status`; `readGraphqlFailure` and `readGraphqlIssues` read `ClientError.response.errors?.[0]?.extensions`. The tests build the error directly: `tests/lib/graphql-client.test.tsx` (`clientError(status)`, and `rejects.toBeInstanceOf(ClientError)`) and `tests/lib/graphql-failure.test.ts` (`refusal(fieldErrors)` with `status: 200` and an `errors` array). Three docs describe the behaviour the wrapper must keep: `claude-docs/graphql/client.md` ("A GraphQL error rejects"), `claude-docs/graphql/errors.md` (the error shape), `claude-docs/testing/where-tests-live.md` (the request is resolved against jsdom's location and matched by msw's link; `window.fetch` is looked up on every request so a story or test can stand in for it).

**Steps.**

1. Before uninstalling, read how graphql-request 7.4.0 serialises and sends (`node_modules/graphql-request/build/`): it posts `JSON.stringify({ query: print(document), variables })` with `print` from `graphql`, and sets `content-type` and `accept` headers. Note the exact `accept` value and keep it, so Yoga's status codes stay as they are.
2. In `src/lib/graphql-client.ts`, replace the import and `send()`:
   - `export class GraphQLClientError extends Error` with readonly `status: number` and `errors: readonly GraphQLFormattedError[] | undefined` (the type from `graphql`), constructed as `new GraphQLClientError({ status, errors })`; the message is the first error's message or the status.
   - `send()` keeps its browser guard and its `new URL(ENDPOINT, window.location.origin).href`, then calls the global `fetch` (looked up at call time, never captured at import) with `method: 'POST'`, the two headers, the body above, and `signal`. Parse the JSON; if the response is not `ok`, or the body carries a non-empty `errors`, or has no `data`, throw `GraphQLClientError`; otherwise return `data`. A partial answer never resolves, as today.
   - `shouldRetry`: `error instanceof GraphQLClientError` and `error.status >= 500`.
   - The type lives in `src/lib/types.ts` only if it is a type; a class is code and stays in the client file (CLAUDE.md, "A type lives in a type-only file").
