# M0.22 — port gitflow workflow and branch rulesets

**Status:** decided · **Date:** 2026-09-09

The task: copy resume-2026's `gitflow.yml`, wire it into `pr-gate.yml` and
`merge-queue.yml` (both of which have been carrying "gitflow doesn't exist
yet" comments since M0.20/M0.21), mirror its branch rulesets onto `main` and
`staging`, add a `release/*` ruleset, and configure Dependabot to target
`staging` with the author-based exemption `gitflow.yml` itself provides.

## Decided

- **`gitflow.yml` ported byte-for-byte.** Unlike the composite actions
  (`checkout-to-app`'s hardcoded repo path) or the per-check workflows
  (`build-image.yml`'s eventual `uses:`), this file has no repo-specific
  reference to fix — it only reads `github.event.pull_request.*` and calls
  the four composite actions by their generic relative path.
- **`pr-gate.yml`/`merge-queue.yml` gain a `gitflow` job each, and
  `needs: gitflow` on every other job**, exactly as both files' own
  M0.20/M0.21 comments promised: `pr-gate.yml`'s job passes the real PR
  number (`should-run` defaults `true`); `merge-queue.yml`'s passes
  `should-run: false`, matching upstream, since `merge_group` events only
  expose a synthetic head ref
  (`refs/heads/gh-readonly-queue/<base>/pr-<n>-<sha>`), not the PR's actual
  source branch — there's nothing real to validate there, but the job still
  has to report success under the "gitflow / gitflow" name or a queued merge
  stalls forever. `audit` is excluded from `needs: gitflow` in both files,
  matching upstream — it's PR-only and never a required check, so gating it
  on Gitflow validation buys nothing. The `vitest`/`playwright` stub jobs
  also gained `needs: gitflow`, even though they're still bare `echo` steps,
  so the dependency graph doesn't reshape itself when M1 swaps in the real
  `uses:`.
- **Discovered undocumented pre-existing ruleset state and stopped to ask
  rather than guess.** Before starting the ruleset work, the repo already
  had three rulesets — `Deploy Branches` (covering `main`+`staging`
  together) plus separate, near-duplicate `Main`/`Staging` ones, all created
  the day before this task and none carrying required status checks. None
  of this is mentioned anywhere in `claude-docs`; the M0.21 design doc,
  written one day earlier, explicitly says "no branch ruleset exists yet."
  This doesn't match resume-2026's shape (`Main`, `Staging`,
  `Release Branches` — no combined ruleset) and modifying/deleting live
  GitHub branch protection is exactly the kind of hard-to-reverse,
  shared-state change this project's operating rules say to confirm before
  touching. Asked the user via `AskUserQuestion` rather than assuming either
  "match upstream exactly" (which would mean deleting `Deploy Branches`, a
  ruleset the user might have just been trying out) or "leave it alone"
  (which would mean skipping the task's own acceptance criteria).
  - The user had already deleted `Deploy Branches` and added a
    `Release Branches` ruleset (`refs/heads/release/**`, delete/
    force-push-only, matching resume-2026's exactly) before answering, and
    asked to leave `Main`/`Staging` otherwise untouched.
  - On required status checks, the user chose "gitflow only" over
    upstream's full list (`build`, `build-image`, `format`, `gitflow`,
    `lint`, `playwright`, `typecheck`, `vitest`) — `build-image.yml` doesn't
    exist yet (M0.24) and `vitest`/`playwright` are still no-op stubs (M1),
    so requiring them now would permanently block every merge on checks that
    can never truly pass/fail meaningfully.
- **Ruleset write blocked by token permissions — reported, not worked
  around.** `gh api -X PUT repos/.../rulesets/<id>` (the only way to add a
  rule to an existing ruleset without also resending its full body) returned
  `403 Resource not accessible by personal access token` for both `Main` and
  `Staging`. Read access works; this session's fine-grained PAT lacks the
  `Administration` repository permission rulesets require to write. Did not
  attempt a workaround (e.g. asking for broader token scope, or trying the
  classic-PAT-shaped `branches/.../protection` API instead of rulesets) —
  escalating a token's permissions is itself a decision for the user to
  make, not something to route around silently. Reported as a manual
  follow-up instead: add `gitflow / gitflow` as a required status check to
  both rulesets via the GitHub UI.
- **`.github/dependabot.yml` created new** (didn't exist before this task).
  Ported verbatim from resume-2026: three ecosystems (`npm`, `github-actions`,
  `docker` at `/Docker` — same directory name/location in this repo, no path
  fix needed), all `target-branch: staging`, weekly schedule. The
  "exempt by author" half of the acceptance criteria isn't a Dependabot-side
  setting — it's `gitflow.yml`'s own `dependabot[bot]` actor check
  (`ACTOR = github.event.pull_request.user.login`), already covered by the
  workflow port.

## Verified

- `npx js-yaml` parses `gitflow.yml`, `pr-gate.yml`, `merge-queue.yml`, and
  `dependabot.yml` with no errors.
- `grep -rn 'resume-2026|mjoynes-wombat-web' .github/` finds nothing new (the
  one `resume-2026` hit is this task's own prose in `pr-gate.yml`'s header
  comment, not a workflow reference).
- `npm run lint` / `format:check` / `typecheck` / `check:stories` all exit 0.
- **Not verifiable pre-push:** a live PR actually failing `gitflow / gitflow`
  for a branch mismatch, or a Dependabot PR exercising the author exception
  — both need a real PR against the pushed branch.
- **Not verifiable until the manual ruleset step is done:** a feature-branch
  PR into `main` being _blocked from merging_, specifically. The check will
  report failure regardless; only the required-status-check wiring (blocked
  above) makes that failure actually gate the merge button. This is a real
  gap against this task's own acceptance criteria ("a feature branch PR
  targeting main is rejected") that depends on a manual step outside this
  session's access.

## Rules this sets

- **Live GitHub settings (branch rulesets, protection) are confirmed with
  the user before being created, modified, or deleted** — even when a task's
  acceptance criteria implies a specific end state, discovering the current
  state doesn't match what the docs say should be true is a stop-and-ask
  moment, not a silent reconcile.
- **A blocked write (permissions, scope) is reported as a manual follow-up,
  not routed around** — this session doesn't ask for broader credentials or
  reach for an adjacent API on its own judgment when the direct one is
  refused for a permissions reason.
- Required status checks are added incrementally, matching what's actually
  real: a stub job or a workflow that doesn't exist yet doesn't get required
  just because upstream requires its eventual counterpart.
