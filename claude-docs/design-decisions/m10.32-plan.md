# M10.32 — Pending coven invitations on the /coven landing

## Context

An invitation reaches the invited person one way today: the mailed link. The row
stores only the token's hash, the link appears in no response, and `/invite/[token]`
accepts it only for a signed-in account whose verified address matches. The owner
asked whether a signed-in user could **see invitations addressed to them inside the
app**, so a lost or spam-filtered mail does not block them, and what that costs in
security. Answer given and accepted: a small task, coven invitations only, admin
invitations stay mail-only.

Decisions taken in the conversation:

- Build it as one wave-10 task, **M10.32** (M10.27–M10.31 are on staging; re-check
  with `node scripts/task-board.mjs find M10.32` before minting, expecting zero).
- **Coven (workspace-tier) invitations only.** The site tier is never listed and
  cannot be accepted by id: m2.9-granting-admin.md calls that link "a bearer token
  for the site's highest privilege" and accepts the risk for covens because the worst
  case is one coven's data.

## Security assessment (the reasoning behind the shape)

Both the link and `emailVerified` prove mailbox control; they differ in _when_. The
link proves the person could read the mailbox at invitation time; a verified flag
proves Google, Discord or our own mail vouched at some past moment (MB.61), and
nothing re-verifies. DESIGN.md §14 already ranks them: the link "only proves receipt
and can be forwarded"; the verified-address binding is what stops it being a bearer
token. The one case this feature reopens is a **stale verified address** passed to
someone else; keeping the site tier mail-only bounds it to one coven's seat.

Kept: no token in any response, nothing to copy, list filtered by the session's own
verified address in SQL, by-id accept answers NotFound for any id not addressed to
the session, single use (pending predicate), the MB.63 pause irrelevant (site tier
excluded), deleted-coven check, unverified accounts fenced by `requireSession()`.

Widened, and recorded: the invitee reads the inviter's name without sharing a
coven (the mail already carries it; `claude-docs/auth/display-names.md` gains a row);
two more proof-less reads of workspace-scoped rows, justified as
`findInvitationByToken` is (the invitee holds no proof yet; the session row is the
scope).

## Design

**No GraphQL list query.** The landing is a server component; rule 1 sends only
browser-initiated reads through `/api/graphql`. The two existing pending lists (owner's,
admin's) read the service directly and page with `readNumberedPage`. Follow that.
Only one new mutation, `acceptInvitationById(id: ID!): Invitation!`, next to
`acceptInvitation` in `src/modules/identity/graphql/invitations.ts`, rather than
widening the token mutation (two optional args, blurred site-tier rule, SDL churn).

**Members who already have a coven get nothing new** in this task: `/coven` still
redirects them. Doing it right needs a Decline write and a place to show it; flagged as
a follow-up for the owner, not built here.

### Repository — `src/db/repository/invitations.ts` (export via `index.ts`)

Private helpers: `onWorkspaceTier()` (`isNotNull(workspaceId)`), `inLiveWorkspace()`,
`receivedBy(session) = and(onWorkspaceTier(), heldVerifiedBySession(session))`.

| Function                                       | ANDs                                                                                                                                  |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `findReceivedInvitationPage(session, page)`    | `findPageInScope(invitations, receivedBy(session), PENDING_INVITATION_ORDER, page, pendingInvitation(inLiveWorkspace()))`             |
| `findReceivedInvitationCount(session, start)`  | same, through `findPageCountInScope`                                                                                                  |
| `findReceivedInvitation(session, id)`          | `selectOne(invitations, and(notSoftDeleted, eq(id), receivedBy(session)))`, any state so the service can say accepted/revoked/expired |
| `findReceivedInvitationCovens(session, ids)`   | live `workspaces` by `existsIn(invitations, …receivedBy…)`; id, name, slug only                                                       |
| `findReceivedInvitationInviters(session, ids)` | live `users` (aliased, since `heldVerifiedBySession` nests `users`) by the same exists; id and name only                              |

New named write in `invitationWrites` (and `AuditWriter` in `types.ts`):
`acceptReceivedInvitation(id)` = the token write with `eq(invitations.id, id)`,
`onWorkspaceTier()`, `heldVerifiedBySession(session)`, `inLiveWorkspace()`.
The token write stays untouched. Every new finder body passes the soft-delete guard
(`notSoftDeleted(` or a `find*` pager).

### Service

`src/modules/identity/services/invitation-acceptance.ts`:

- Extract `checkInvitation(session, row | undefined)` from `standingOf`; `standingOf`
  becomes `checkInvitation(session, await findInvitationByToken(token))`.
- `standingById(session, id)`: malformed id (`RowId.safeParse`) → `invalid`; else
  `checkInvitation(session, await findReceivedInvitation(session, id))`. The site
  branch is unreachable (excluded in SQL).
- Extract the `withAudit` body into `acceptChecked(session, check, stamp, recheck)`;
  `acceptInvitation(token)` and the new exported `acceptInvitationById(session, id)`
  both call it, keeping seat/revive, `invited_by` (M10.26), the flag grant via
  `'invitation'`, and the post-race recheck.
- By id: `NotFound` (own wording, not "open the whole link") for another address,
  unverified match, site-tier id, deleted row, deleted coven, malformed id;
  `Forbidden` with the existing words for accepted / revoked / expired.

New `src/modules/identity/services/received-invitations.ts`, exported from the
module index: `listReceivedInvitations(session, page)` (page, then covens and
inviters over the page's ids in parallel: three statements per page) and
`countReceivedInvitations(session, start)`. Flat `ReceivedInvitation` type in
`src/modules/identity/types.ts`: id, covenName, covenSlug, role (typed from the row,
identity cannot import coven), inviterName | null, expiresAt, note | null.
