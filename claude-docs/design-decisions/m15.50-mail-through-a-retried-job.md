# M15.50: mail is sent through a retried job

## Decision

`send(message)` in `src/lib/mail.ts` stays the one way the site mails, and its signature is unchanged. With a transport set, it starts one run of a durable job, `mailDelivery` (`src/lib/mail-delivery.ts`), and returns. The job's step calls `deliver` (`src/lib/mail-transport.ts`), which throws when the transport answers with an error or cannot be reached. The Workflow SDK then retries the step with its default policy: the first try and three retries. The run returns true once the transport took the mail. If every attempt fails, a second step logs it and the run returns false.

## Shape

- **The split.** `src/lib/mail-transport.ts` holds one attempt at a transport (`deliver`, `MailNotSent`) and imports nothing from the job adapter, so a job step can import it. `src/lib/mail.ts` holds `send`, which decides whether a mail goes through the job.
- **A refusal is not retried.** A recipient under `.invalid`, a transport the environment may not use, or a missing variable makes `deliver` return false without throwing, because no retry would change the answer. It is logged once.
- **A failed start.** If the run cannot be started, `send` logs it and tries the transport once itself, so a queue outage costs the retries, not the mail.
- **The marker.** A caller that records a mail as sent does it in its own job step, after `deliver` returned true. Two callers do: the support closing-soon notice (`closing_notice_sent_at`) and a staff reply's mail (`support_replies.notice_sent_at`, migration 0119), each sent by its own job, whose step renders the mail from the rows and carries only ids (M15.46).
- **Vitest.** Every test that reads mail mocks `@/lib/mail`'s `send`, so the capture inbox still sees every mail. While `MAIL_TRANSPORT` is unset, which is how Vitest runs, `send` logs the mail and starts no run, because there is nothing to retry. Real retries are tested in the `workflow` project (`tests/workflows/mail-delivery.test.ts`).

## What skips the job, and why

A run's arguments are stored in the job's event log for as long as its events are kept. A link that proves something must not be copied there: CLAUDE.md says an invitation token "appears in no response and is never copied", and a reset or verification link is the same kind of secret.

The owner then chose (2026-11-02) that the secret-link mails go through a retried job too, with a run that holds ids alone and a step that gets the token when it sends (M15.46's record, "Secret links through a job"). Three now do: the sign-up and resend verification link, the password reset link and the lockout mail, through `secretLinkMail`. Three are still sent with `send(message, { carriesSecret: true })`, tried once, as before:

- the change-of-address link, because the new address is stored nowhere a step could read it;
- the admin invitation and the coven invitation, because only the token's hash is stored, and minting a new one in the step needs a write no proof covers.

Every other mail goes through `mailDelivery`: the account-exists mail, the password-changed notice, the email-change notice, and the support mails not sent by a job of their own.

## Compared

| Option                                       | For                                   | Against                                                           |
| -------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| Every mail through the job (task as written) | One path; every mail retried          | Tokens and signed links copied into the event log                 |
| Token-free mails through the job             | Retries where the log holds no secret | Six mails still tried once                                        |
| The step renders the mail from ids (chosen)  | Nothing sensitive in the log          | Three mails have no stored value a step can rebuild the link from |
| Retry inside `send`, in the request          | No job                                | Lost when the function ends; delays the response                  |
