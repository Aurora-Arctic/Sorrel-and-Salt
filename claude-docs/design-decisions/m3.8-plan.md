# M3.8 — React cache() wrapper and the server read path

Branch `feature/m3.8-react-cache-wrapper-and-server-read`, stacked on M3.7's head (PR still in review) with `origin/staging` merged in. Asana task `1218815062811222` is `▶ In Progress`.

## Context

M3.8 fixes the project's access boundary — server components read through `cache()`-wrapped services, everything the browser initiates goes through `/api/graphql`, both end at the same service — and proves it on one representative service. The task as written assumes a workspace read service exists to wrap; none does (`src/services/` holds `assertMembership`, admin promotion, spell visibility, provisional accounts). The user chose **cached membership, M3.8 alone**: no new finder, no production GraphQL field, no reach into M6.10.

Three facts checked this session change the design from the earlier proposal:

1. **`cache()` keys object arguments by identity** (`react.react-server.production.js`: objects go in a `WeakMap`, primitives in a `Map`). A wrapper taking `(session, workspaceId)` dedupes only if both callers pass the _same_ `Session` object — true via `getSession()`, false for `asUser()` and for any caller that rebuilds the session. So the cache key must be **primitives**: the cache goes around the role lookup _inside_ `assertMembership`, keyed on `(userId, workspaceId)`, not around a new `(session, workspaceId)` export. Every current and future caller of `assertMembership` then gets the dedupe with no per-task adoption, whatever permission it asks for.
2. **Route Handlers have no React cache dispatcher.** Nothing under `next/dist/server` calls `getCacheForType`; only the Flight renderer does. Without `ReactSharedInternals.A`, React's `cache()` is `fn.apply` — a pass-through. On the GraphQL path `cache()` is therefore inert and DataLoader (rule 9) is the dedupe. The doc must say this rather than claim memoisation on both transports.
3. **Dedupe is only observable inside a Flight render**, and loading the Flight server needs the `react-server` export condition. A probe (since deleted) proved it works under Vitest with `ssr.resolve.conditions/externalConditions: ['react-server']`: one render → one call, second render → second call, and fails without the condition ("The `react-server` condition must be enabled"). The `db` project cannot take the condition globally: `react-dom/server` resolves to a file that throws under it, and `tests/db/email-verification.test.ts`, `tests/services/admin-role.test.ts`, `tests/services/provisional-accounts.test.ts` import `@/lib/auth` → react-email → `react-dom/server`. So a small third project, `rsc`, carries the render test.

## Changes

### 1. The cached read — `src/services/membership.ts`

- Module level: `const workspaceRole = cache(findWorkspaceRole);` (`cache` from `react`). `assertMembership` calls `workspaceRole(session.userId, workspaceId)` in place of `findWorkspaceRole(...)`. The permission check below it still runs on every call — cheap and uncached — so a layout asking `workspace: ['read']` and a page asking `spell: ['create']` for the same workspace cost one query.
- Comment (conclusion only, argument in the doc): keyed by the two ids because `cache()` compares objects by identity; scoped to one server render, a pass-through in the GraphQL route handler where DataLoader batches instead.
- No lint change: nothing bans `react` in `src/services/`, and `src/lib/request-session.ts` already sets the precedent.

### 2. Guard — `tests/guards/no-server-actions.test.ts`

"Mutations never take the server read path" has one mechanical hole lint cannot see: a `'use server'` directive is not an import, so M3.9's `no-restricted-imports` rules will never catch a server action. This guard scans `src/**` (tracked and untracked, `slug-rule.test.ts` style since it reads contents) and fails on `'use server'` / `"use server"`. Precondition assertion: the scan found `src/app/api/graphql/route.ts` (so an empty scan cannot pass).

### 3. The `rsc` Vitest project — `vitest.config.mts`

- Third project: `name: 'rsc'`, `environment: 'node'`, `globals: true`, `include: ['tests/rsc/**/*.test.{ts,tsx}']`, with `ssr: { resolve: { conditions: ['react-server'], externalConditions: ['react-server'] } }` (the minimal form the probe needed; re-verify when the config is written — try `resolve.conditions` alone first and keep whichever is the least that passes). `unit` gains `'tests/rsc/**'` in its `exclude`. No `dbHarness`: the test mocks the repository, so no template rebuild and no pool-group coupling.
- `react-server-dom-webpack` as a devDependency pinned **exactly** `19.3.0` (the lockfile's `react`), per the "prefer the standard tool" preference; if npm has no matching build, fall back to `next/dist/compiled/react-server-dom-webpack/server.edge`, which the probe used. `tests/vitest-env.d.ts` gains `declare module 'react-server-dom-webpack/server.edge'` (the package ships no types).
- Why the count is of `findWorkspaceRole` calls, not of Postgres statements: `src/db/repository.ts` is the only importer of the client (rule 2), so a repository call _is_ a Postgres round trip; the render test can therefore mock the repository and stay off Postgres.

### 4. Render test — `tests/rsc/services/membership.test.tsx`

`vi.mock('@/db/repository', importOriginal → { ...actual, findWorkspaceRole: vi.fn(async () => 'owner') })`. Components are plain async functions calling `assertMembership` and rendering the role; render with `renderToReadableStream(tree, {}, {})` and read the stream to a string. Write these first and watch them fail against the current uncached `assertMembership` (the mock is called twice):

- **One render, one query.** Layout and Page both ask about W using **two distinct `asUser(A)` objects** (proves the key is the ids, not the session object). Precondition: the output contains the role twice. Assertion: the mock was called once.
- **Different permissions, same lookup.** Layout asks `workspace: ['read']`, Page asks `spell: ['create']`: one call.
- **Different workspaces, different lookups.** W and X: two calls (the key includes the workspace).
- **Nothing persists across requests.** A second `renderToReadableStream` of the same tree: the mock's count rises by one.

### 5. Two-transports denial test — `tests/services/two-transports.test.ts` (db project, real Postgres)

A throwaway schema from `createBuilder()` (its stated purpose) with `Query.workspaceRole(workspaceId: ID!): String!`, `authScopes: { signedIn: true }`, resolving `(await assertMembership(ctx.session, id, { workspace: ['read'] })).role`. Execute with `graphql({ schema, source, contextValue: { session, loaders: createLoaders(session) } })` — the transport minus cookie parsing, which `tests/graphql/context.test.ts` already covers. `tests/graphql/builder.test.ts` has the pattern.

- Precondition (why it could have succeeded): D on X resolves `'member'` through **both** paths — the field works and the finder is reached.
- D on W: direct call rejects `Forbidden`; GraphQL path answers `data: null` with `errors[0].originalError instanceof Forbidden` (asserting on the original error, not the message — MB.43's mapping is not landed and Yoga's masking is not in play under `graphql()`).
- E (site admin, in no workspace) on W: the same pair, so the "admin is not an exception" line is asserted rather than stated.

### 6. Docs
