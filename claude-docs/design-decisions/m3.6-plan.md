# M3.6 — Cursor pagination helper with a hard maximum page size

## Context

Rule 8 and DESIGN.md §7 say every list paginates through one shared cursor
helper: default 25, hard max 100, and cursors that encode sort key + id, never
an offset. No list query exists yet, so this lands the **mechanism plus a
mechanical guard** (the sweep-task rule for code). Each later list task
(compendium, workspaceIngredients, grimoire, the admin user list) then adopts it
in its own PR.

Branch `feature/m3.6-cursor-pagination-helper-with-hard-maximum` is stacked on
M3.5's head (PR #183), because this task moves the SDL and M3.5's codegen guard
reads that SDL. Rebase onto `staging` once #183 merges.

### What was stale in the task as written

**"Cost limit accounts for the requested page size" cannot hold under M3.3's
cost limit, and that limit also breaks the silent clamp.** graphql-armor's cost
rule (read in `graphql-armor-cost-limit` 2.4.3) runs at validation, before
variables are bound. It multiplies a subtree only by a _literal_ `first`/`last`:

| Request           | armor multiplier | rows the server returns |
| ----------------- | ---------------- | ----------------------- |
| `first: 100`      | ×100             | 100                     |
| `first: $n` (100) | ×1               | 100                     |
| no `first`        | ×1               | 25 (default)            |
| `first: 1000`     | ×1000 → refused  | 100 (clamped)           |

The second and third rows undercount by up to 100×, so two nested variable
pages are 10 000 rows at the price of 1. The fourth row contradicts "requesting
more than the maximum returns the maximum, silently and consistently":
`things(first: 1000) { edges { node { id } } }` costs about 12 900 and is
refused, while the same request with `$n = 1000` is answered.
`claude-docs/graphql.md` already flags the variable case as "has to be argued
separately".

## Decision

### 1. Standard tools: `@pothos/plugin-relay` and `@pothos/plugin-complexity`

Both are stable 4.x majors, peer `graphql ^16.10`, and maintained with `@pothos/core`.

- **Relay plugin** supplies `t.connection`, and with it `*Connection`/`*Edge`
  types, `PageInfo`, and `first/after/last/before`. Its options:
  `nodeQueryOptions: false` and `nodesQueryOptions: false`, so there is no
  `node`/`nodes` root field and no `Node` interface (confirmed in a scratch
  schema), and edges/nodes are non-null, matching `defaultFieldNullability`.
  The shape is the Relay spec's. Relay's own `resolveOffsetConnection` and
  `resolveArrayConnection` are offset-based and are **not** used.
- **Complexity plugin replaces armor's cost limit**, so cost has one owner.
  `EnvelopArmorPlugin` gets `costLimit: { enabled: false }` and keeps depth 7,
  aliases, directives, tokens and field suggestions. The complexity plugin
  checks before any root resolver runs, with variables bound. A connection field's
  multiplier is the **effective** page size, `min(first ?? last ?? 25, 100)`,
  set once through relay's `defaultConnectionFieldOptions.complexity`. In a
  scratch schema: absent → ×25, `$n = 1000` → ×100, literal `1000` → ×100.
  `edges` gets multiplier 1, so the page is not counted twice by the list
  default of 10. The limit gets a new constant sized in Pothos units, so that
  M3.3's "two nested pages of 100 refused, of 10 answered" still holds.
- The armor cost tests in `tests/app/api/graphql/armor.test.ts` become
  complexity tests over the same throwaway schema: `children` becomes a
  connection, and a variable-`first` case is added. Depth tests are unchanged.
  The refusal is now an execution-time error (200 with `errors`) rather than a
  validation `Syntax Error`. The doc records that.

### 2. The helper, in three layers (each respects rules 1, 2 and 4)

- **`src/lib/pagination.ts`** is pure, with no drizzle and no graphql, so both
  sides import it. It holds `DEFAULT_PAGE_SIZE = 25` and `MAX_PAGE_SIZE = 100`,
  and `pageRequest(args)`, which wraps `@pothos/core`'s exported
  `parseCursorConnectionArgs` with those sizes. That function silently
  `Math.min`s to the max and rejects a negative size. It also holds the
  `PageRequest` type (`{ after?, before?, limit, inverted }`) and the cursor
  codec: base64url of `{"k": <sort key as text>, "i": <id>}`. A malformed
  cursor is refused with a user-facing error, never read as "from the start".
- **Repository:** `findPage(table, sortColumn, page, where?)` and
  `findPageInWorkspace(membership, table, sortColumn, page, where?)`. Keyset:
  `(sort, id) > (k, i)` (or `<` when `inverted`), `ORDER BY sort, id` (desc
  when inverted), `LIMIT limit` (which is already the page size + 1). The soft-delete and
  workspace predicates are ANDed exactly as in `findMany`/`findManyInWorkspace`.
  The sort key is selected as `sort::text` in SQL and compared back in SQL, so
  a `timestamptz` keeps its microseconds. A JS `Date` would truncate to
  milliseconds and repeat or skip rows. `sortColumn` is typed to NOT NULL
  columns, because a NULL breaks row comparison. The query still goes through
  the one private `selectFrom` (extended with optional order/limit/key), so
  `soft-delete-finder-guard.test.ts`'s single-select invariant holds. Its
  pinned export list gains the two finders, and `findPageInWorkspace` joins
  `SCOPED_FINDERS`. A spell page (`findManySpells`' counterpart) is left to
  the grimoire task that needs it: adopted per PR, not speculated.
- **`src/graphql/pagination.ts`:** `pagedConnection(t, { type, resolve })`
  wraps `t.connection`. Its `resolve` receives a parsed `PageRequest` rather
  than raw args, and returns the repository's `{ cursor, node }[]`. The
  wrapper trims the extra row, reverses when inverted, and builds `edges` and
  `pageInfo`. A resolver never sees the raw `first`, so the clamp cannot be
  skipped.

### 3. Guards (the "no future list query can forget" half)

- **`tests/guards/pagination.test.ts`** walks the built schema. Any `Query`
  field whose type is a list fails, and every `*Connection` field must carry
  `first`/`after`. **This covers vocabularies too** (categories, form values),
  per rule 8's "every list" and the task's "every list query". Nested lists on
  an object (`Ingredient.categories`) are bounded by their parent and stay
  bare, as §7 sketches them.
- The same file text-scans `src/` (untracked included, as `slug-rule.test.ts`
  does): `.connection(` appears only in `src/graphql/pagination.ts`, so a hand-built
  connection that bypasses the clamp fails in its own diff.

### 4. Docs, in this PR

- `claude-docs/graphql.md`: a new "Pagination" section. "Protections" is
  rewritten: the cost row moves to the complexity plugin, and the literal-only
  paragraph is replaced.
- `claude-docs/db.md`: the keyset finders.
- DESIGN.md §7: the SDL sketch's root lists become connections
  (`compendium(first: Int, after: String, …): IngredientConnection!`, and the
  same for `workspaceIngredients`, `grimoire` and the vocabularies). Its
  pagination paragraph names the effective-size cost.
- TASKS.md M3.3 and M3.6: a line on the cost re-scope, with a link to the plan
  record.
- CLAUDE.md rule 8: add "cost is priced at the effective page size".
- This plan is stored as `claude-docs/design-decisions/m3.6-plan.md`.

## Tests (TDD: each written first and watched fail)

- **Unit** (`tests/lib/pagination.test.ts`):
  - A missing size gives 25. 100 gives 100, and 101 and 10 000 give 100 with
    no error.
  - A negative size is refused.
  - A cursor round-trips, and decodes to `{k, i}` with no numeric offset field.
  - A malformed or tampered cursor is refused.
- **DB** (`tests/db/pagination.test.ts`), over invented-name fixture rows in a
  table the seed does not fill for this test's filter:
  - Walk all pages at size 25, then at `first: 7`, across 3+ pages. No row is
    skipped or repeated, and the order equals `ORDER BY sort, id`.
  - Mid-traversal, insert rows before and after the cursor and soft-delete an
    unseen row. Every row that existed throughout is seen once. The deleted
    row is not seen, and a cursor pointing _at_ a deleted row still resumes.
  - Backward traversal (`last`/`before`) gives the mirror image.
  - A `timestamptz` sort with microsecond-distinct values in one millisecond
    loses no row.
  - A workspace-scoped page returns no row from X. The precondition is that X
    has rows, and the direct-id case stays covered by the existing
    `workspace-isolation.test.ts`.
- **GraphQL** (`tests/graphql/pagination.test.ts`), over a throwaway
  `createBuilder()` schema:
  - Literal 1000 and variable 1000 both return 100 edges without error.
  - Complexity scales with the literal, the variable and an absent `first`,
    and the one over the limit is refused.
- **Guard:** show it red by adding a scratch list field and a scratch
  `.connection(` call, then remove them.

## Where the implementation departed from the plan

- **`t.pagedConnection` is a method, not a function `pagedConnection(t, …)`.**
  Inferring the parent shape through a field builder passed as an argument
  gave TypeScript an instantiation it could not finish ("excessively deep"),
  for an object field. So the helper is added to `RootFieldBuilder.prototype`,
  the way the Relay plugin adds `t.connection`. The guard still scans for
  `.connection(`.
- **`MAX_COST` moved from `armor.ts` to `builder.ts`**, beside the complexity
  plugin that now enforces it. It stays at 5000, and is now counted in the
  plugin's units.
- **The route-level cost tests use two nested connections from the root**,
  which reach exactly depth 7, because a connection spends two levels on
  `edges` and `node`.
- **`InvalidCursor` joins `src/lib/errors.ts`.** The repository throws it for a
  cursor that will not cast to the sort column's type (SQLSTATE class 22),
  and `t.pagedConnection` turns it into an `Invalid cursor` GraphQL error.
