# MB.54 — Set the account's email: prefilled from the provider, editable, verified before it counts

Branch `feature/mb.54-accounts-email-prefilled-from-the-provider` off `origin/staging` (d4a5d90). Asana `1218815062887579` is `▶ In Progress`.

## Context

Stories 58/59. A provider that shares no address currently dead-ends the OAuth callback at `?error=email_not_found`; one that shares the wrong address leaves the user no way to change it. The task builds `/account/email`, protected: it shows the provider's address and whether it is verified, lets the user change it through a `setEmail` mutation, and resends the verification mail — the address counting only once MB.66's link is followed from a session holding the row.

### The conflict this plan resolves

The task's second criterion says changing the address "marks the row unverified … and touches `updated_at` so MB.67's window restarts". **That would destroy established accounts.** MB.67's sweep (`deleteProvisionalUsers`) hard-deletes every row with `email_verified = false` and a provider `accounts` row whose `updated_at` is older than an hour **or whose `created_at` is older than three hours** — and it runs on every OAuth callback by anyone. A user who signed up months ago and changes their email becomes an unverified row far past the cap: the next callback tries to delete it, and either succeeds (their account, memberships and spells' authorship gone) or — because every other audit FK is `NO ACTION` — the whole sweep statement fails on every callback from then on, which is the seeded-admin failure mode MB.67 already had to design around. The criterion was written before the cap existed; the sweep is right, the criterion is wrong.

**Resolution: the row's address never changes until the new one is proven.** A change request writes nothing to `users.email`. It mints Better Auth's own change token — the same HS256 JWT `/verify-email` already accepts, with `updateTo: <new address>` and `requestType: 'change-email-verification'` — mails the link to the new address, and `/verify-email` swaps `email` and sets `emailVerified: true` in one adapter write when the link is followed from a session holding the row. So:

- a **verified** account stays verified and keeps its address throughout; the sweep never sees it;
- a **provisional** account (provider address unverified, or the placeholder) also keeps its row's address. Its window is restarted through `extendVerificationWindow` at each request, for the reason that function already exists: the mailed link lives an hour, and a row whose `updated_at` is fifty minutes old would lapse forty minutes before the link does — the click would find no user, which is the dead end this task removes. The three-hour cap from `created_at` is untouched, so a squatter still cannot hold an address by re-requesting; Better Auth's own resend does exactly this touch today;
- there is one rule instead of two modes: _an address becomes the account's at verification, never before_. The "unverified" state the spec wanted is carried by the token, not the row.

What this costs: a pending change is not visible on reload (the page shows the row's address; the client shows "we sent a link to X" after submitting). Better Auth's `updateTo` path is also weaker than the plain path — it calls no `beforeEmailVerification`, and with **no session it mints one**, signing the link's opener in — so a `hooks.before` on `/verify-email` applies the MB.66 rule to it: refuse unless a session holds the row, and refuse when a live row still holds the new address (the unique index would otherwise 500). `user.changeEmail` stays pinned off; this flow replaces it and nothing on `/api/auth` is added.

**Placeholder for a provider that returns no address:** `mapProfileToUser` yields `<providerId>-<providerAccountId>@pending.invalid` (RFC 2606 reserves `.invalid`: no mailbox can exist). It arrives `emailVerified: false`, so the row is provisional and lapses like any other. The sign-up mail is skipped for it, and `mail.send` refuses any `.invalid` recipient as the backstop.

**An unverified sign-in lands on the email page.** The callback's after-hook sends every sign-in whose row is `emailVerified: false` — a Facebook or Microsoft address, a Google or Discord address the provider did not vouch for, or the placeholder — to `/account/email?next=<callbackURL>` instead of `next`, with the address prefilled (empty for the placeholder) and editable. A verified sign-in lands at `next` exactly as today. It applies to every sign-in, not only sign-up: an unverified account is provisional and can do nothing else, so the page is where it should be until the address is proven.

### Sequence a user sees

**A verified sign-in lands at `next` as today; an unverified one lands on the email page.** The page is also a standing account setting reached at any later time — by URL now, and from the `/account` page once MB.71 builds it (the sign-in page's `email_not_verified` sentence already names it).

1. **No email from the provider** → callback after-hook → `/account/email?next=/coven`, empty field, "no email yet". Types one → token mailed to it → clicks in the same browser → `/verify-email` swaps the address, verified → back on `/account/email`, "verified", Continue to `next`.
2. **Provider address, unverified** (Facebook/Microsoft, or Google/Discord reporting unverified) → callback after-hook → `/account/email?next=…`, the provider's address prefilled and editable; the sign-up mail has already gone to it. "Send confirmation" resends to it (Better Auth's endpoint, window restarted); editing it requests a change to the new address instead. Every later sign-in lands here too until the address is verified.
3. **Any account, later, wants mail at a different address** (story 59 — the reason the page exists after sign-in) → edits the field → nothing written to the row; the confirmation goes to the **new** address; the row keeps its current address and verified state until the link is followed from this browser, then carries the new one, verified. Every later mail — invitations included — goes to the new address. The sweep never touches an established account. **This is the conflict's regression test.**

### Riding along: Facebook's `#_=_` (sub-hour fix, named in the PR body per MB.31)

Facebook appends `#_=_` to the `redirect_uri` it sends the browser back to. A fragment is never sent to the server, and a browser carries it across every 302 whose `Location` has no fragment of its own, so today the user lands on `/coven#_=_` — and after this task on `/account/email?next=…#_=_`. The server cannot strip what it never receives, so the fix is client-side and page-independent: an inline script in `src/app/layout.tsx` beside `THEME_INIT_SCRIPT`, run before first paint, that does `history.replaceState(null, '', location.pathname + location.search)` when `location.hash === '#_=_'` and nothing otherwise. Exactly that fragment, not any fragment — in-page anchors keep working. Tested in `tests/e2e/smoke.spec.ts`: `page.goto('/#_=_')` → `page.url()` carries no hash; `page.goto('/#top')` keeps its hash. Documented in one line in `claude-docs/auth.md` under "Social providers".

## Amended after approval

- The change mail names no provider: the address is new to the account, so the provider it signs in with tells the reader nothing about whether the request was theirs.
- One verification mail a minute per account, requested during the build: a nullable `users.verification_sent_at` (migration 0021) stamped by every mail sent for the row's own account — which replaces `extendVerificationWindow`, since the stamp is an update and restarts the window the same way — checked by `setEmail` (a field error naming the wait) and by the `sendVerificationEmail` hook (sends nothing inside the minute). The form counts the minute down on its own submit as well.
- From the first manual walkthrough: the page has a confirmed view (`?verified=1`: the address and Continue, nothing to edit) and a change view (the field alone, for a verified account back to change it); the countdown starts from the server's clock, which the verifying write clears; an unverified account reaches no page but the email page (`requireSession()`); a link opened signed out goes to `/sign-in` with a sentence and nothing from the link; `/send-verification-email` answers 401 to anyone but the row's own session; the form uses no native validation; button labels are title case (DESIGN.md §9).
