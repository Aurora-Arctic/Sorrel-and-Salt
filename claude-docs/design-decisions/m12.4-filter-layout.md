# M12.4 — How the search filters sit together

**Status:** pending the owner's sign-off · **Date:** 2026-10-17 · **Amended:** 2026-10-17

The ingredient search is about to hold more filters than one row can carry. This record says what published design guidance says about that, sets out the layouts we considered, assesses each for keyboard and screen-reader use, and recommends one. It settles the layout only. MB.120 reviews the finished design, and the owner agrees this layout from workshop stories before anything is built.

## Context

By the end of Wave 12 an `IngredientSearch` page can filter by:

- a text query;
- categories, with an All/Any toggle (M8.12);
- Forms, a multi-select typeahead (a box that offers matches as you type) with the chosen values as chips inside it, each with its form icon (M12.7);
- Deities, a multi-select grouped by tradition;
- Zodiac signs, Planets and Elements (Fire, Water, Earth, Air and Spirit), each a chip combobox like Forms and Deities (see the amendment below);
- Toxic, a three-way segmented control (Any, Toxic, Not Toxic);
- later, the stock filters (in stock only, low stock only) and a local-or-compendium chip;
- for admins only, Classification and No Refs (no references recorded).

Every value shows a count: how many results choosing it would give (M12.3). Above the results sits one sentence naming every chosen value. Each value in it is a link that removes it, and Clear All ends it.

Laid out as plain rows, that is about eight rows before the first result, on a page that already has a left section nav and an app shell.

### Constraints that hold whatever the layout

1. The sentence names every chosen value.
2. A hidden facet's chosen values stay visible, as chips or in the sentence. A collapsed state never hides an active filter.
3. Every facet applies before hydration (before the page's JavaScript runs) through a GET form. The server renders the page, and a visitor with no JavaScript can still filter.
4. The page works at 375px, a common phone width.
5. All values are in the URL: a repeated parameter per value, so the form writes them itself (M8.13).

### Amended 2026-10-17

The owner chose a chip combobox for the three fixed vocabularies, Zodiac, Planets and Elements, in place of rows of checkbox chips. A chip combobox is one control: the chosen values sit as chips inside it, a dropdown offers the rest with their counts, and a value with a count of zero is listed last and disabled. Forms and Deities already work this way, so every multi-value facet now behaves the same.

What this record can show of the reason is a matter of space. A row of twelve zodiac chips wraps at 375px, so each chip row costs a block of height, while a combobox costs one line wherever it sits. The original draft recommended hiding the tail of the facets behind a disclosure (layout C) partly to save that height. With every facet one line, that reason is weaker, so this amendment adds a layout built on it (E, below), re-measures every layout, assesses all five for keyboard and screen-reader use, and re-evaluates the recommendation. The stories in `.ladle/facet-layout.stories.tsx` were redrawn to match.

## What the sources say

Each point below names the source it comes from. Every source was opened during this task; the dates are in [Sources](#sources).

### Which facets are always visible, and which sit behind a disclosure

- The Department for Work and Pensions (DWP) design system's research says filters should be visible by default. Hiding them behind accordions makes users click into each category to see what is inside, and makes them hard to find again. Its position is a "theory" held for its own services, and it says there is not yet enough evidence for other mobile layouts (DWP, "Filters").
- Maersk's design system says the opposite for rarely used filters: "display and prioritise the most used and essential ones and hide the rest behind a menu or panel" (Maersk, "Filter Patterns").
- eBay's playbook says filters are organised from most to least important, and that a large value set takes a text filter and a long flat list is sorted alphabetically, ideally searchable (eBay, "Filtering Patterns").
- The Ministry of Justice (MOJ) filter component says to "only provide users with filters they really need", to use an accessible autocomplete for long option lists, and to show an option only if it matches what was typed or is already selected. Its own page marks the component "to be reviewed" (MOJ, "Filter").
- Nielsen Norman Group (NN/g) names the cost: each extra facet adds interaction cost, and "a simple filter can often be easier to understand and faster to use" (Whitenton, "Filters vs. Facets"). It gives no number of facets to show.

The sources disagree, and the disagreement is a trade, not an error. DWP is describing a short list of filters. Maersk is describing a long one. We have a long one, so the sources we can lean on are the ones that rank filters and hide the tail.

### How a closed panel summarises what is chosen

- Maersk says to write the number of applied filters into the label of the button that opens the hidden filters, and to show applied filters in their original place as well as in a separate applied-filters section. The user can clear all from that section (Maersk).
- Baymard Institute's research says 28% of benchmarked sites show no overview of applied filters at all, and 72% of its desktop benchmark sites do, so users come to rely on one. It recommends always showing one, on desktop and mobile. It warns against showing only a count of applied filters, because the user then still has to open the panel to see or remove them (Reeves, "How to Design Applied Filters").
- DWP says the user "should not have to remember what they have done to produce the current view", and wants a Clear all that resets to the unfiltered view, plus individual removal so a user can undo the one filter that emptied the list (DWP).
- The MOJ filter puts the selected filters at the top as removable tags, with a "Clear filters" link. Clicking a tag refreshes the page and removes the filter (MOJ).
- eBay says a chip with a value should announce the value and its category, keep its label while selected, and expose applied state to screen readers. It says to avoid a Reset action where a single selected filter can be removed directly (eBay).
- Smashing Magazine says applied filters belong above the results rather than above the filter panel, because the latter pushes content down and shifts the layout (Friedman, "Designing Filters That Work").

### Where the applied-filter summary sits

Baymard found three common places (above the product list, above the filter sidebar, below a horizontal toolbar) and no clear winner: "what matters is that the overview is easy to see" (Reeves). Smashing says above the results (Friedman). The MOJ component puts it at the top of the filter (MOJ). Our sentence is already specified to sit above the results as the `role="status"` region, and that agrees with both Baymard and Smashing.

### Phone width

- NN/g advises against putting facets on a separate screen of their own, because the user then works harder to see how a facet changes the results. It recommends a tray over the results, so results stay visible and change as facets are chosen, with the word "Filter" or "Refine" on the button rather than an icon (Whitenton, "Mobile Faceted Search with a Tray"). The article is from 2015.
- Smashing says a full-page overlay for filters is worth testing, and that a mobile Apply button should stay "sticky at the bottom" (Friedman).
- Baymard's two ways to show applied filters on a phone are a sideways-scrolling row (with a count such as "4 Filters Applied" or a faded edge to show there is more) and stacked rows, which can push the products out of view. A variant shows one or two rows with a "See All Applied Filters" control (Reeves).
- DWP says that where filters sit above the results on mobile and tablet, results may be out of view (DWP).
- eBay says an advanced panel or sheet suits users who "need to make several selections before updating the result set" (eBay).

### Apply on change, or an Apply button

- DWP prefers batch filtering (the results change when the user presses an Update button) over live filtering. Its reasons: stray clicks change the results, several selections in a row distract, and many quick requests cost performance at scale. It also says live filtering is weaker on mobile, where the results may be out of view (DWP).
- Maersk gives a rule: live filtering when a result takes a second or less, batch with an Apply button when it takes more, and batch on mobile because loads there are often slower (Maersk).
- eBay offers both, with explicit apply "when users need to submit criteria before results update", and says an Apply button inside a panel carries the result count (eBay).
- Smashing prefers live updates together with an Apply button, and criticises pure auto-apply that reloads the page and blocks input after every selection (Friedman).
- Baymard found that autosubmitting without an overview of applied filters makes it harder to remove one and easier to lose track (Olah, "Always Allow Users to Combine Multiple Filtering Values").
- The MOJ filter is a plain form with an "Apply filters" button, which refreshes the page. It notes a keyboard cost: users must go to the top of the component to press it (MOJ).

For us, a GET form with no JavaScript is a batch filter by nature: the page reloads when the form is submitted. Live filtering would be an enhancement on top, never the base.

### Counts and zero-count values

- Maersk says to show a count on the button that opens hidden filters (Maersk). eBay says the panel's main button carries the total result count (eBay). Smashing says to show the count as soon as possible, and that it can sit on the Apply button (Friedman).
- Smashing says that when an option stops being available it should be disabled rather than hidden, with a reason, and that a "Hide all unavailable options" control is worth offering (Friedman).
- DWP says the count of results should update as filters change (DWP).
- eBay says that when no result matches, filter controls stay visible and a way forward (such as Reset) is always offered (eBay).
- The MOJ example shows counts beside checkbox options, such as "Blue (18)" (MOJ).
- Baymard's multi-value article says filter values of one type combine with OR and different types with AND, and that users who could pick several values used 5 to 10 filters at once (Olah). That matches M11.22's rule. The article does not cover counts or zero values.

M12.4's acceptance criteria already follow the Smashing line for fixed vocabularies (a zero stays in place, disabled) and sort zeros last in the typeaheads, where eBay and MOJ say a long list should be searchable and ordered.

### Sidebar or top bar on desktop

- DWP says filters on desktop are preferred on the left, and that one of its services found all users, screen reader users included, preferred this. It marks this as a convention, not settled fact (DWP).
- Baymard lists above the list, above a sidebar, or under a horizontal toolbar as all in use, with no winner. It notes that rows of filters can push products down, and suggests truncating extra rows behind a control (Reeves).
- Maersk does not compare the two (Maersk). The MOJ page does not say, and lists "when to use a horizontal layout for filters" as an open question (MOJ).

So the sources give no verdict between a sidebar and a top panel. What decides it for us is that the app shell already uses the left edge for the section nav.

### What the sources do not tell us

- None of the sources addresses a GET form that works with no JavaScript, apart from the MOJ component being a plain form. Whether a closed disclosure still submits its fields is an engineering question for the build to prove with a test.
- None says how many filters is too many. NN/g gives no number.
- Baymard's counts-beside-options and truncation research sits behind its paywall, so it is not used here.

## Layouts considered

All five keep the constraints above. They differ in how much is on screen before the results.

### A. Everything open, as plain rows (the do-nothing option)

Every facet is drawn as its own labelled row above the results, in one GET form with an Apply button.

- For: the simplest build. Nothing is hidden, which is what DWP asks for. No disclosure state to remember.
- Against: about eight rows, then the sentence, then the first result. At 375px the first result is several screens down, which is the crowding the task exists to fix. Baymard names exactly this risk for rows of filters (Reeves). The rarely used facets cost as much space as the common ones. With the chip comboboxes every row is one line, so this layout is shorter than the original draft measured, but it is still the longest on a phone (see the table below).

### B. A filter sidebar beside the results

A column of every facet, open, left of the results on wide screens; stacked above them on a phone.

- For: matches DWP's left-column preference and Baymard's "above a sidebar" pattern. Long lists scroll in the column while the results stay in view.
- Against: the app shell already puts a section nav on the left, so this would be two left columns next to each other, leaving little width for a results table. On a phone it becomes layout A. The comboboxes are wide controls that fit a narrow column badly.

### C. A primary row, and one disclosure for the rest

The few facets people reach for first stay open in a row under the search box. Every other facet sits in one native disclosure (a `<details>` element) headed "More Filters", with the number of chosen values on its button. The sentence sits below the panel and above the results. One GET form wraps the lot.

- For: the first result stays near the top at both widths. It follows Maersk (most-used open, the rest in a panel, count on the button) and Smashing (summary above the results, not above the panel). It needs no JavaScript to open or close.
- Against: DWP's research warns that hiding filters in accordions makes them harder to find. The count on the button and the sentence reduce that cost but do not remove it. The line between "primary" and "more" is a judgement and needs the owner's call.

### D. A trigger button opening a tray or full-page overlay

A single "Filters" button beside the search box opens a tray (NN/g) on a phone and a popover or panel on desktop, with every facet inside and a sticky Apply button.

- For: the strongest match to NN/g and Smashing for phones; the page itself is as short as it can be.
- Against: a tray or overlay is built from a dialog and focus handling in JavaScript. Before hydration there is nothing to open, so the facets would have to be drawn inline as a fallback, which means building two layouts. NN/g and Smashing both assume instant, scripted results. Our sources give no evidence that this beats a disclosure for a list this size.

### E. Every facet visible, as one-line controls in a compact grid

Added in the amendment. Nothing is hidden and nothing opens. Under the search box, Categories and its All/Any toggle take a line of their own. Below that, at the shell's tablet width and above, a grid of two or three columns holds Toxic (the segmented strip), then Forms, Deities, Zodiac, Planets and Elements, then for admins Classification and No Refs, last. Each is a one-line control (a chip combobox, the strip, or a checkbox). Below the tablet width the grid becomes a plain stack. Apply Filters and Clear All sit below the grid, and the sentence sits above the results, as in C. One GET form wraps it.

- For: it is the only layout that honours DWP's research without a caveat, since no filter is hidden, so there is nothing to find again and no accordion to click into (DWP). The constraint that a hidden facet's chosen values stay visible holds without effort, because no facet is ever hidden. There is no disclosure state, no `<details>` behaviour to test, and no question about whether closed fields still submit. The keyboard and screen-reader path has the fewest moving parts (see Accessibility).
- Against: the first result sits lower than in C at desktop width, by 138px in the stories. At 375px it is a stack of every facet, which is layout A's crowding (1474px against 1458px for A and 835px for C). Maersk's advice to hide rarely used filters behind a panel is the position it gives up (Maersk). More tab stops before Apply than C closed (see Accessibility).

## Accessibility

How each layout works for a keyboard user and a screen-reader user, from the sources in [Sources](#sources) and from our own constraints. Where a source is silent, this section says so and names the test the build needs, in place of guessing.

### What the sources set

- **Disclosure** (W3C, "Disclosure"): the control that shows and hides the content is a `button`. Enter and Space toggle it. While the content is visible the button has `aria-expanded="true"`, and `false` when it is hidden. `aria-controls` is optional. The page does not discuss the native `<details>` element, so whether our disclosure exposes the same state to a screen reader is for the build to test.
- **Combobox** (W3C, "Combobox"): the combobox stays in the page's tab sequence and its popup does not. Focus stays on the combobox, and `aria-activedescendant` points at the option being highlighted. Down Arrow moves into the popup, Escape closes it, and Enter accepts the highlighted option. `aria-expanded` says whether the popup is open. The page says nothing about disabled options, and nothing about several chosen values shown as chips. Both are outside the pattern, so how a disabled zero-count option is announced, and whether arrow keys step over it, must be proved with a screen reader in the build.
- **Dialog, modal** (W3C, "Dialog (Modal)"): on open, focus moves into the dialog. Tab and Shift+Tab cycle inside it. Escape closes it. On close, focus returns to the element that opened it, unless that element is gone. The dialog needs a name, ideally from a visible title. `aria-modal="true"` belongs only where the code blocks all interaction outside and the styling visibly obscures it.
- **Focus Order, 2.4.3, Level A** (W3C, "Understanding 2.4.3"): focus order must preserve meaning and operability. It may differ from the reading order, but the best practice is to keep them aligned. A modal dialog makes everything outside it inert while it is open. The page lists "inserting dynamic content immediately after its trigger" and HTML modal dialogs among sufficient techniques, and treats a dialog or menu that is not next to its trigger in the focus order as a failure.
- **Focus Not Obscured (Minimum), 2.4.11, Level AA** (W3C, "Understanding 2.4.11"): a focused component must not be entirely hidden by author-created content. A sticky footer is the named risk, and the page's passing approaches are CSS scroll padding so the footer does not cover content, or a modal.
- **Status Messages, 4.1.3, Level AA** (W3C, "Understanding 4.1.3"): a status message must be programmatically determinable by role, so assistive technology can present it without moving focus. A line such as "18 results returned" counts as one. When a persistent count changes, the whole phrase is marked as the status, so a screen reader does not read only the number. A change delivered by a change of context, such as moving focus or reloading the page, is not what the criterion is about, and the page warns that too many live regions make a page tiresome.
- **Contrast (Minimum), 1.4.3, Level AA** (W3C, "Understanding 1.4.3"): text needs 4.5:1, or 3:1 if large. Text that is part of an inactive component, such as a disabled control, is exempt.

### Common to all five layouts

- **Each removal link names what it removes.** A link reading "Water" says nothing about what pressing it does. eBay asks for a chip that announces its value and its category and exposes its applied state (eBay), so the accessible name is a phrase such as "Remove Element: Water", not the bare value. This holds for the sentence's links and for the chips inside each combobox.
- **A disabled zero-count option must stay perceivable and be announced as unavailable.** Smashing's rule is to disable the option, not hide it (Friedman). Two consequences. First, 1.4.3 exempts disabled text from the contrast minimum, but only for a component that is truly inactive. The stories dim a zero-count row and ignore its click, which is a mock-up. A row that is still operable is not exempt. The build must truly disable it. Second, the exemption lets us dim the text and does not require it. Our own choice, so a low-vision user can still read why a value is unavailable, is to keep a zero-count option's text at 4.5:1 and mark it as unavailable by the "Nothing Matches" note beside the count, not by contrast alone. The announcement itself is untested (see Combobox above).
- **The count is read as part of the option.** Each option's text is the name and the count together, "Water (7)", so a screen reader reads the count with the name, the way the MOJ example writes "Blue (18)" (MOJ). The count must not live only in a badge or a colour.
- **The sentence is the status region, and a reload is not a live update.** Under the no-JavaScript base the Apply button reloads the page, and 4.1.3 does not treat a change of context as a status message. The sentence is then simply the first thing a reader finds above the results. It speaks as a live update only in the JavaScript enhancement where a single click, such as Toxic, applies on change. Marking the whole sentence as the status, not just the count, follows the page, and the build should keep apply-on-change to single clicks so the region does not become chatty.
- **Sticky Apply row (2.4.11).** At 375px the Apply row sticks to the bottom of the screen. A focused field scrolled beneath it would be entirely hidden. The build sets scroll padding on the page equal to the row's height, the technique the 2.4.11 page names, and tests that a field focused by keyboard at the bottom of the form stays at least partly visible. It applies to every layout that sticks an Apply row at that width, and the recommendation does so for all of them.
- **Source order is visual order.** No layout uses CSS `order` or a grid to reorder fields, so the tab order equals the reading order and the visual order (2.4.3).

- **A and E** hide nothing. Their cost is the length of the tab path and the length of the page, not missing access. E is the shorter to scroll at desktop and A and E are equal at 375px.
- **B** is the same as A on a phone. At desktop a keyboard user tabs through the whole sidebar before reaching a result, which is a cost A shares.
- **C** shortens both the page and the tab path while closed, at the price of a disclosure the build must make work: the button's state exposed to assistive technology (untested for a native `<details>`), and the closed fields still submitted by the GET form (already a build test). Removing a value is possible from the sentence without opening the panel. Adding one is not. That is the one case where the sentence does not compensate, and DWP's warning that hidden filters are harder to find and to find again (DWP) is the same point.
- **D** is the costliest. A modal tray needs, and the other four do not:
  1. focus moved into the tray on open, and back to the trigger on close;
  2. Tab and Shift+Tab held inside, and everything outside made inert;

  4. a name from a visible title;
  5. a clash to settle: Escape closes a combobox popup (Combobox pattern) and also closes the dialog (Dialog pattern), so an Escape pressed with a popup open should close the popup only. This is our inference from the two pages, not something either says;

### What this changes in the weighing

- The layouts with nothing hidden (A, B, E) carry no accessibility mechanism beyond the comboboxes everyone has, and none of the disclosure or dialog behaviour that has to be built and tested.
- E and A pay in tab stops and in scrolling past a sticky row at phone width. C closed pays least there, and pays in the one thing the sentence cannot do: let a user add a hidden filter without first opening the panel.
- D is the only one with a hard requirement to build and prove a focus trap, Escape, a scrim and focus return, and it also carries the two-layout cost. Nothing read here supports taking that cost for this list.

## Recommended layout

Layout E from the shell's tablet width (`$shell-tablet-width`) upwards, and layout C's disclosure below it. One `<form method="get">` in both, with the panel inline and no overlay.

### Does E now beat C?

At desktop width, yes. At 375px, no. The reasons:

1. **What C was for.** The original draft chose C to keep the first result near the top, hiding the facets people reach for least. That is Maersk's advice for a long set of filters (Maersk). It is paid for in the way DWP warns about: hidden filters make users click into each one and are hard to find again (DWP).
2. **What changed.** With every facet a one-line control, hiding them saves little at desktop width. In the stories C closed puts the first result 679px down and E puts it 817px down, 138px lower. For that price nothing is hidden, which is DWP's position without a caveat. The sources do not say how many filters is too many (NN/g gives no number), so this is a judgement on a measured cost, and the owner may weigh 138px differently.
3. **The other things E removes at desktop.** There is no disclosure state to get right, no test of whether closed fields reach the query string, and no case where the sentence cannot help: in C a keyboard user can remove a hidden value from the sentence but cannot add one without opening the panel. The accessibility assessment above finds E has the fewest mechanisms to build and prove.
4. **What E costs.** About ten tab stops before Apply against about six for C closed, and the 138px.
5. **Why C wins at 375px.** E there is a stack of every facet: 1474px to the first result against 835px for C, and as bad as A (1458px). Crowding on a phone is the problem the task exists to fix, and DWP notes results may be out of view on mobile (DWP). C's closed state also halves the tab path and the scroll past a sticky Apply row (2.4.11).

The price of the split is two arrangements of one form. We have not shown that a native `<details>` can be open and fixed at one width and closed at another with CSS alone: the server renders the `open` attribute without knowing the screen width. The build proves it with a test, or falls back to one arrangement. If the owner wants one arrangement, this record recommends C at every width over E at every width, because E costs 639px at 375px (1474 against 835) and C costs 138px at desktop. The tray (D) is not recommended at any width: its extra work (a focus trap, Escape, a scrim, focus return, an inline fallback for no JavaScript) is not supported by anything the sources say for a list this size.

### The pieces, top to bottom

1. **Search row.** The text box, with its Search button. On a phone it is full width.
2. **Categories row.** The picker and its All/Any toggle (a segmented strip) on a line of their own. The picker takes the spare width.
3. **The facets.**
   - At the tablet width and above (layout E): a grid of two or three columns, always visible, in this order: Toxic (the segmented strip), Forms, Deities, Zodiac, Planets, Elements, then the stock filters and the local-or-compendium chip when they exist, then for admins Classification and No Refs, last. Every one is a one-line control.
   - Below it (layout C): Toxic stays open under the categories row. The rest sit in one native disclosure headed "More Filters", closed by default, with the number of chosen values on its button, for example "More Filters (3)", as Maersk does. Open, it holds the same facets in the same order, one block each, labelled above its control.
4. **Apply row.** An "Apply Filters" button and a Clear All link after the facets, so Apply follows the controls in the tab order, which avoids the MOJ keyboard cost of travelling back to the top (MOJ). At 375px the row sticks to the bottom of the screen while the form is on screen, as Smashing suggests for a mobile Apply (Friedman), with scroll padding so a focused field is never entirely behind it (2.4.11).
5. **The search sentence.** Directly above the results, below the form, as the `role="status"` region. It carries the count, every chosen value as a removable link, and Clear All. It is outside the disclosure, so it stays visible when the panel is closed.
6. **Results and pager.**

### What the closed state shows (below the tablet width)

Closed, the panel is the search row, the categories row, Toxic and the "More Filters (n)" button. Each hidden facet's chosen values appear in the sentence below. Because that is the only place the user sees them while closed, the sentence is built from the whole filter, not from what the visible fields hold. This is what satisfies "a collapsed state never hides an active filter", and it is Baymard's warning in practice: a bare count is not enough (Reeves), so the count on the button is a pointer to the sentence, not a replacement.

The disclosure starts open when the page loads with any hidden facet already chosen. That follows the Smashing note that users expect state to persist on refresh and back (Friedman). The user can still close it, and the sentence keeps the values.

### Zero-count values

- All five chip comboboxes (Forms, Deities, Zodiac, Planets, Elements): a value with a count of zero is listed last and truly disabled, not merely dimmed (Smashing: disable, do not hide; 1.4.3 exempts only inactive components). Its text keeps its contrast and carries a note beside the count.
- A chosen value with a count of zero is never disabled, so the user can always remove it.
- In the stories the disabled option is a mock-up: a dimmed row that ignores its click, because the shared Combobox has no disabled option yet. The build adds one.

### How the GET form submits every facet

- Every control is a real form field with a name: a hidden input per chosen combobox value, radios for Toxic and for the All/Any toggle. They write the repeated parameters M8.13 specifies.
- At the tablet width and above, every field is visible, so the form submits as any form does. Below it, the disclosure is a native `<details>`, and the build adds a test that a closed disclosure's fields still reach the query string, since the sources do not say and the form must work either way. If that test fails in any browser, the fallback is to render the disclosure open when JavaScript is off.
- Pressing Apply Filters submits the form and reloads the page, the batch model that DWP and Maersk (for slow loads) recommend and that the MOJ filter uses. Each link in the sentence is a plain link to the same filter minus that value, so removal needs no JavaScript either.
- With JavaScript, Toxic and All/Any may apply on change as a pure enhancement, because they are single clicks. The comboboxes still wait for Apply, so several choices cost one reload (Smashing, DWP, Olah).

### Accessibility notes drawn from the sources

- The "More Filters" button states its count in its text, not in a colour or badge alone (eBay), and its open state is exposed to assistive technology: the Disclosure pattern uses `aria-expanded` on the button, and the build proves a native `<details>` does the same (W3C, "Disclosure").
- Every removal link and chip has an accessible name that says what it removes, for example "Remove Form: Oil" (eBay).
- Each option reads its count with its name, and a zero-count option is announced as unavailable. How a screen reader announces a disabled combobox option is not in the Combobox pattern, so the build proves it.
- The other points are in the Accessibility section above.
