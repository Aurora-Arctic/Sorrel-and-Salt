# M0.19 — consume the preseeded image in CI and compose

**Status:** decided · **Date:** 2026-09-09

The task: point `docker-compose.yaml`'s `postgres` service and a CI job at
the preseeded Postgres image M0.18 introduced, instead of the plain
`postgres:17` and "nowhere" they point at today.

## Decided

- **`docker-compose.yaml` builds `Docker/Dockerfile.postgres` locally
  (`build: { context: .., dockerfile: Docker/Dockerfile.postgres }`,
  `image: sorrel-postgres`) rather than pulling the GHCR image
  `build-db-image.yml` publishes.** This compose file is local dev only —
  the same reasoning `app`/`workshop` already follow, building
  `Dockerfile.node` instead of pulling a published image. Pulling from GHCR
  would mean registry auth and a network round trip for something a local
  `docker build` already does directly, for a Dockerfile that's already
  checked out on disk. The GHCR image stays what CI and deployment consume.
- **A pre-existing `postgres_data` volume from the old plain `postgres:17`
  image doesn't get reset by this change.** Anyone who already ran
  `make docker-up` before this task has a volume initialized with the
  `sorrel` role/database (created from `POSTGRES_*` env vars by the _old_
  image's normal first-boot init); switching `image:`/`build:` doesn't
  touch it, so Postgres keeps serving that old data, which has no
  `postgres` role at all. Flagged with a comment rather than silently
  leaving it for someone to debug — `make docker-rebuild` (`down -v`)
  clears the volume so the next start populates fresh from the new image.
  Confirmed while testing: this produces a `FATAL: role "postgres" does not
exist` log line on every health check tick against a stale volume —
  benign, not a failing check. `pg_isready` always names some role in its
  connection attempt (explicitly, or implicitly the invoking OS user) and
  Postgres logs any rejected attempt regardless of role validity; `pg_isready`
  itself only checks that the server responds at all, not that the role is
  real, so the check still passes.
- **The CI side is a new `verify-db-image` job in `build-db-image.yml`,
  `needs: build-db-image`, using `${{ needs.build-db-image.outputs.image }}`
  — the hash tag, not `latest`.** That output is the one place the tag is
  written down; the job never reconstructs the `ghcr.io/<repo>/db` string a
  second time, which is what "reference the same tag from one place, not two
  literals" actually asks for. Using the hash tag (not `latest`) matters on
  a `pull_request` run specifically: `latest` hasn't moved yet, so it would
  verify old, unrelated content instead of what this run just built.
- **It's a literal job-level `services:` container**, the exact pattern
  DESIGN.md §11 names for the future M1 test job ("CI unit + db | Actions
  `services: postgres:17`, reachable by service name from the existing job
  `container:`"). A fancier design (an `actions/cache`-backed
  `docker save`/`docker load` step, avoiding `services:` so a prior step
  could restore a cached pull before the container starts) was drafted and
  rejected as overkill for a 1h task — GitHub Actions pulls a `services:`
  image before any step runs regardless, so there's nothing to intercept,
  and the extra machinery bought nothing a real workflow needs. "Cache the
  pull" is read instead as the build job's existing
  `cache-from`/`cache-to: type=gha` (scope `db-image`) — what actually costs
  time is reconstructing layers on top of the `postgres:17` base, and that
  stays cached across runs already.
- **The health check gates the test step by construction, not by a manual
  wait loop.** Actions blocks every step of a job until its `services:`
  containers report healthy, so `--health-cmd="pg_isready" --health-interval=5s
--health-timeout=5s --health-retries=10` is the entire mechanism.
- **`SELECT 1` runs via `docker exec ${{ job.services.postgres.id }} psql
-U postgres -d sorrel_template -c 'SELECT 1'`, not a TCP connection from a
  step.** `Docker/Dockerfile.postgres`'s build-time
  `docker-entrypoint.sh postgres` run configures `pg_hba.conf`'s `host`
  (network) rules for password auth, using a superuser password that's
  generated randomly and discarded before the image is even pushed
  (`m0.18-build-db-image.md`) — nothing can ever authenticate over TCP with
  a known credential. The `local` (Unix-socket) rule initdb writes stays
  `trust`; `docker exec` uses that socket, so it needs no password. This is
  also why the acceptance criterion says "from inside the job container"
  rather than just "succeeds" — a TCP attempt from outside the container
  would fail on auth, not because anything is broken.
- **`docker-compose.yaml`'s healthcheck changes from `pg_isready -U sorrel
-d sorrel` to `-U postgres -d sorrel_template`.** Neither the `sorrel` role
  nor a `sorrel` database exist in this image — only the baked-in `postgres`
  superuser and the empty `sorrel_template`. `pg_isready` doesn't actually
  validate the user/database it's given (it only checks that the server
  accepts a connection attempt), so the old flags weren't actually broken,
  but they described things that don't exist. Using real ones costs nothing.
- **`POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`/`DATABASE_URL` in
  `docker-compose.yaml` are left as `sorrel`/`sorrel`/`sorrel`, unchanged and
  inert.** Same reasoning as M0.18's own doc: a real container from this
  image ignores every `POSTGRES_*` env var, because `docker-entrypoint.sh`
  only reads them during first-boot init, and PGDATA already exists in the
  image's layers. `app` doesn't query the database yet (`src/db/schema` is
  still empty), so this doesn't break anything today — it's flagged with a
  comment instead of silently left for someone to rediscover.

## Rules this sets

- **`verify-db-image` is scaffolding, the same way `lint-format-typecheck
-check.yml`/`build-audit-check.yml` were (M0.16/M0.17's own docs call this
  out explicitly)** — a stand-in until something real exercises the image.
  Once M1 adds a real `db`/`unit` test job that runs actual tests against
  a `services:` postgres container, that job's own green run already proves
  reachability, auth, and the health check; **delete `verify-db-image` at
  that point** rather than run two jobs proving the same thing on every PR.
- **M1.27** is what has to give the image real, known-password app
  credentials (a `sorrel` role/database with a password baked in on
  purpose, not the random-and-discarded one) once there's a schema to
  connect for — this task deliberately doesn't invent one early.

## Verified

- `npx js-yaml .github/workflows/build-db-image.yml` and
  `Docker/docker-compose.yaml` both parse with no errors.
- **Not verifiable pre-push:** the actual job run — `job.services.postgres.id`
  resolution, the health check, and the `docker exec`/`psql` call, plus
  whether `docker-compose.yaml`'s local build of `Dockerfile.postgres`
  actually starts — this sandbox has no `docker` daemon (same limitation
  M0.18 hit). Opening the PR (path-filtered on this workflow file itself)
  triggers `build-db-image.yml` for real; `docker-compose.yaml` isn't in
  that path filter; and there's no CI job yet that runs
  `docker compose up` for local dev.
