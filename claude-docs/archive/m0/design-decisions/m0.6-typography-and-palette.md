# M0.6 — Typefaces and base colour palette

**Status:** decided · **Date:** 2026-09-07 · **Supersedes:** the resume-2026 values M0.5 ported as a placeholder

This is the decision record M0.6 asks for. It exists because M0.7 (category-group and
safety tokens) and M0.8 (chip, badge and modal-surface mixins) are required to _derive_
from this palette rather than pick alongside it — so the reasoning has to outlive the
commit that set the hex values.

---

## The decision

**Typefaces:** Cormorant Unicase (display) over Lexend (body).
**Palette:** "Parchment and iron-gall ink" — warm near-black grounds, parchment ink,
sorrel-green accent, sealing-wax secondary. **Dark is the default; the system preference
is honoured.**

---

## Typefaces

| Role    | Family            | Licence | Weights loaded    |
| ------- | ----------------- | ------- | ----------------- |
| Display | Cormorant Unicase | OFL 1.1 | 500, 600, 700     |
| Body    | Lexend            | OFL 1.1 | variable, 100–900 |

Cormorant Unicase is a high-contrast old-style serif whose unicase forms all sit at cap
height, so a heading reads as an inscription rather than a sentence — appropriate for a
compendium, and it gives headings a distinct voice without a second display weight doing
the work. It has no variable axis, so weights are enumerated; only the three the type
scale in `_typography.scss` actually uses are requested, since each is another file on
the wire. Headings run at 600 rather than the 500 the port used: at 500 the thin strokes
go weedy against a dark ground.

Lexend is variable across 100–900 in a single file and was drawn for reading fluency,
which suits long ingredient descriptions and safety notes. Body copy sits at 300.

**Licensing.** Both are SIL Open Font License 1.1. Self-hosting, subsetting and
embedding are exactly what the OFL permits, and it requires no attribution in the UI.
Neither family is being sold or redistributed on its own, which is the OFL's only real
prohibition.

**Loading strategy.** `next/font/google` in `src/app/fonts.ts`, applied as CSS variables
on `<html>` in the root layout. Next downloads both families at build time and serves
them from our own origin, so no runtime request reaches `fonts.googleapis.com` or
`fonts.gstatic.com` — that removes a third-party DNS + connect + CSS + woff2 chain from
the critical path, and means nothing about a visitor's page load is disclosed to Google.

**No layout shift.** `adjustFontFallback` is left at its default of `true`, which
synthesizes a local fallback face with `size-adjust` and `ascent-override` matched to
each family's metrics. The fallback occupies the same box as the real font, so
`display: 'swap'` exchanges glyphs without reflowing anything around them. Verified in
the build output: both families emit a fallback face (`size-adjust: 109.91%` and
`111.26%`). **Setting `adjustFontFallback: false` is the change that would reintroduce
the shift** — don't.

Fonts are referenced from Sass through `$font-body` / `$font-heading`, which resolve to
`var(--font-body)` / `var(--font-display)` with the named family and a generic stack
behind them as fallback.

## Palette

Named for materials rather than roles, because a role can change and `#14120e` cannot.

### Hand-picked base — four hues, everything else derived

| Sass         | Hex       | What it is                                     |
| ------------ | --------- | ---------------------------------------------- |
| `$soot`      | `#14120e` | dark page ground                               |
| `$parchment` | `#efe9da` | light page ground                              |
| `$iron-gall` | `#23201a` | light-theme body ink                           |
| `$sorrel`    | `#4a6b34` | accent — the plant the app is half named after |
| `$wax`       | `#8c3b2e` | secondary — sealing wax on a jar               |

The grounds are warm near-blacks, not neutral ones: a herbal contains no pure black, and
a green accent over a blue-grey ground reads cold. `$soot-raised`, `$parchment-raised`
and `$chalk` are picked alongside them for the raised card surfaces and the dark-theme
ink; everything else in the file comes out of `color.adjust()`.

### Contrast — every pairing, both themes

WCAG AA for body text is 4.5:1. Nothing in the palette sits below it, against **either**
surface of its own theme.

**Dark** — page `#14120e`, card `#1f1c16`

| Token               | Hex       | vs page | vs card |
| ------------------- | --------- | ------- | ------- |
| `--text-primary`    | `#ebe4d4` | 14.77   | 13.42   |
| `--text-muted`      | `#c7b487` | 9.18    | 8.34    |
| `--accent`          | `#87b669` | 7.95    | 7.22    |
| `--accent-hover`    | `#99c979` | 9.79    | 8.89    |
| `--secondary`       | `#cb6e60` | 5.29    | 4.80    |
| `--secondary-hover` | `#d9877a` | 6.86    | 6.23    |

**Light** — page `#efe9da`, card `#f9f5ea`

| Token               | Hex       | vs page | vs card |
| ------------------- | --------- | ------- | ------- |
| `--text-primary`    | `#23201a` | 13.41   | 14.91   |
| `--text-muted`      | `#5e5645` | 5.99    | 6.66    |
| `--accent`          | `#4a6b34` | 5.03    | 5.60    |
| `--accent-hover`    | `#375027` | 7.41    | 8.24    |
| `--secondary`       | `#8c3b2e` | 6.24    | 6.93    |
| `--secondary-hover` | `#753126` | 7.80    | 8.67    |

The tightest pairing is `--secondary` on the dark card at 4.80:1. It clears AA, but it
is the value with the least headroom in the palette — if M0.7's safety badges put small
text in that colour on that surface, check the number again rather than assuming the
margin is there.

### Derivation conventions, for M0.7 to follow

- **Hover is punchier, and "punchier" is direction-dependent.** In light mode that means
  darker (`color.adjust($sorrel, $lightness: -8%)`); on a near-black ground darker only
  loses contrast, so dark-mode hovers lighten and add saturation instead.
- **Muted text is the body ink at lower strength**, derived from it, and still clears
  4.5:1 — not a decorative grey that fails it.
- **Shadows are per-theme.** A 0.8-alpha near-black under a card reads as a hole punched
  in parchment, so light mode gets `rgba(35, 32, 26, 0.18)` against dark's
  `rgba(6, 5, 3, 0.8)`.

## Theming: three states, not two

Dark is the default **and** the system preference is honoured, which needs three blocks
(`src/app/globals.scss`):

| Selector                                                            | Applies when                                       |
| ------------------------------------------------------------------- | -------------------------------------------------- |
| `:root`                                                             | always — dark, the baseline                        |
| `html:not([data-theme='dark'])` under `prefers-color-scheme: light` | the system asks for light and nothing overrides it |
| `html[data-theme='light']`                                          | an explicit choice, which beats the system         |

A system with a dark preference or no preference at all falls through to `:root` and
gets dark. The `:not([data-theme='dark'])` guard is what will let a theme toggle pin
dark on a light-preference machine; nothing sets the attribute yet.

Both light blocks `@include theme-light` rather than repeating the values, so the two
spellings cannot drift apart.

### Why custom properties, when the port used Sass variables directly

resume-2026 themed by duplicating every rule under `html[data-theme='light']` with
compile-time Sass values. Adding a system-preference tier to that approach means a
**third** copy of every themed rule in every component stylesheet, forever. Routing
colour through CSS custom properties collapses all three into one rule.

The raw Sass hues are kept anyway — `color.adjust()` needs real colour values, and M0.7
is required to derive from them. So the file has two layers on purpose:

- **raw palette** (`$sorrel`, `$wax-warm`, …) — compile-time, the derivation source;
- **token aliases** (`$accent`, `$text-primary`, …) — thin `var(--token)` wrappers, what
  components consume.

A component writes `color: $text-primary;` and never learns a token's spelling or a
theme's name. **Nothing outside `_variables.scss` and the two theme mixins should name a
raw palette colour** — if a rule needs a hue that isn't a token, the token is the thing
to add.

### Why `src/app/globals.scss` exists

§9 says componentized Sass with no global stylesheet beyond the shared partials, and
that still holds. But two things must be emitted exactly once: `_typography.scss`'s
global element rules, and the theme token assignments. Each component's `index.scss` is
its own compilation unit, so a shared partial that emitted CSS would duplicate it into
every compiled stylesheet — which is why `_variables.scss` and `_mixins.scss` remain
declaration-only. `globals.scss` is that single import point and holds nothing
component-specific.

## Alternatives considered

**Ink-green and parchment** — near-black _green_ grounds instead of warm near-black,
otherwise similar. Rejected as slightly redundant: with a green accent doing the
signalling, a green ground gives the accent less to push against.

**Salt-grey and sorrel** — cool mineral greys, green as the only accent. The most
generous option to M0.7, since nothing warm competes with the eight category-group
colours. Rejected for feeling tool-like rather than like a herbal; M0.7 will have to
work a little harder for it.

**Retuning resume-2026's wine/plum** — visual continuity with the source repo, and it
would have fixed the ported `$wine-stained` link colour that sits at ~3.86:1 against its
card. Rejected: this project should not look like the resume it was ported from.

**Keeping Syne + Lexend** — zero risk, but the display sans reads modern and graphic
rather than herbal, which is the opposite of what the story asks for.

The palettes were compared as rendered specimens — the same compendium entry in both
themes for all three — rather than as swatch lists, which is what surfaced the
ground-versus-accent point that decided it.

---

## What this commits later tasks to

- **M0.7** derives its 8 category-group colours and safety-badge palette from the hues
  above, following the conventions in this document, and re-checks contrast against
  `--surface-card` in both themes.
- **M0.8**'s chip, badge and modal-surface mixins consume tokens, never raw palette Sass.
- A theme toggle, whenever one lands, stamps `data-theme` on `<html>` and needs no
  change to any component stylesheet.
