# M0.36 — Wire check:stories and workshop:build into CI

**Status:** decided · **Date:** 2026-09-09 · **Builds on:**
[m0.33-component-story-gate.md](./m0.33-component-story-gate.md),
[m0.20-pr-gate.md](./m0.20-pr-gate.md)

M0.33 built the gate and deliberately left both `npm run check:stories` and
`npm run workshop:build` as plain npm scripts, on the assumption that the
build job (M0.17) or the PR gate (M0.20) would pick them up when they
landed. Both landed without doing so — `grep -rn "check:stories\|workshop:build"
.github/workflows/` returned nothing, and M0.34 corrected CLAUDE.md and
`claude-docs/workshop.md` to say so plainly rather than continue claiming
enforcement that didn't exist. This task closes the gap.

## Where the two scripts run

Both were added to `.github/workflows/build.yml` — the reusable job
`pr-gate.yml` and `merge-queue.yml` both call — as two more steps right
after `npm run build`, gated by the same `should-run` input the build step
already uses (driven by `pr-gate.yml`'s `changes.outputs.build`, which
includes `src/**`). Not a new reusable workflow: this job already runs on
every push that could touch a component, and a sixth `workflow_call` file
just to host two fast scripts (`check:stories` runs in ~0.1s, `workshop:build`
in ~1s) would cost a `changes` filter category and its own `build-image`
dependency for no benefit `lint-format-typecheck-check.yml` or
`build-audit-check.yml` don't already give it for free.

## The real finding: `ladle build` doesn't fail on a failed build

The task assumed `npm run workshop:build` already does what M0.33's decision
doc claimed it would: fail the run on a story that throws. Verified directly,
it doesn't — for any reason. Three separate cases, all against
`src/components/_GateFixture/` seeded then removed:

1. A story whose render function throws at call time — `ladle build` never
   calls it. Ladle code-splits each story into its own chunk that only
   evaluates in the browser; the CLI's production build is a Vite/Rollup
   bundle, not a render pass. Exit 0.
2. A story that throws at module-eval time (top-level `throw`) — same
   reason, same result. Rollup's bundler doesn't execute module bodies for a
   browser target; it only needs to resolve and transform them. Exit 0.
3. A story importing a module that doesn't exist — this **is** something
   Rollup's bundler must actually do (resolve the specifier), and it does
   fail: stdout shows `✗ Build failed` / `Could not resolve "..."`, Vite's
   own wording. And the CLI still **exits 0.**

Case 3 traces to `@ladle/react` 5.1.1 itself
(`node_modules/@ladle/react/lib/cli/vite-prod.js`):

```js
try {
  await build(viteConfig);
} catch (e) {
  console.log(e);
  return false;
}
```

`build.js` calls `await viteProd(config, configFolder)` and never looks at
the return value — `false` is silently discarded, nothing throws, the
process exits 0 regardless. There's no CLI flag for this (`ladle build
--help` has none), no newer version to bump to (5.1.1 is latest per `npm
view @ladle/react versions`), and no supported way to call the build
function directly — `lib/cli/build.js` isn't in the package's `exports`
map, so `import '@ladle/react/lib/cli/build.js'` throws
`ERR_PACKAGE_PATH_NOT_EXPORTED`.

So case 3 — a story that fails to bundle, the one thing Ladle's static
build step can catch in principle — is exactly the case the CLI silently
swallows. Cases 1 and 2 (an actual runtime throw) are outside what any
static build can catch at all; that needs a render pass, which is Playwright
/ M1 territory, not this task's.

## The fix: `scripts/build-workshop.ts`

A wrapper, not a reimplementation: spawns `ladle build`, relays its stdout
and stderr byte-for-byte (so the real build log is unchanged), and inspects
the combined output for Vite's own `Build failed` marker. If present, it
exits 1 regardless of what the child process itself exited with. On a clean
build the marker never appears and the wrapper passes the child's exit code
through unchanged — so if a future `@ladle/react` release fixes the
upstream bug, this wrapper becomes a no-op rather than a conflicting layer,
and can be deleted then.

`package.json`'s `workshop:build` script now points at the wrapper
(`node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/build-workshop.ts`)
instead of `ladle build` directly. `make workshop-build` is unaffected — it
already just calls the npm script.

**`scripts/check-component-stories.ts` itself is untouched**, per the task's
own acceptance criteria — the missing-file gate needed no fix, only a place
to run.

## Verified

- `npm run check:stories` on the real tree: `1 component, every one with a
story.`, exit 0.
- Seeded `src/components/_GateFixture/index.tsx` with no story →
  `npm run check:stories` prints the missing path, exit 1. Fixture removed →
  back to exit 0. (Same regression M0.33 already ran; re-run here to confirm
  nothing in this task touched the gate's own behavior.)
- Seeded a story importing a nonexistent module → `npm run workshop:build`
  prints Vite's `✗ Build failed` / `Could not resolve` and **exits 1** (was
  exit 0 against bare `ladle build`, confirmed both ways). Fixture removed →
  exit 0, real `./build` output produced (`assets/`, `index.html`,
  `meta.json`), same as before the wrapper.
- `npm run lint` / `format:check` / `typecheck` all pass, including the new
  `scripts/build-workshop.ts`.
- `npx js-yaml .github/workflows/build.yml` parses with no errors.
- **Not verifiable pre-push:** the real CI run. Opening this PR triggers
  `pr-gate.yml`'s `build` job for the first time with these two steps in it
  (this diff touches `src/**`-adjacent files, so the `should-run` filter
  trivially qualifies); confirming `build / build` runs `check:stories` and
  `workshop:build` and stays green is the actual demonstration of acceptance
  criterion 3. A throwaway commit reintroducing the `_GateFixture` story
  fixture should turn that check red before it's reverted.

## What this doesn't do

- No change to `scripts/check-component-stories.ts` (explicit acceptance
  criterion).
- No attempt to make Ladle's build actually _render_ a story — that would
  catch cases 1/2 above too, but needs a real browser/DOM pass
  (`ladle preview` + something like Playwright), which is M1 territory, not
  a CI-wiring task.
- No new reusable workflow file — `build.yml` already ran on the right
  trigger with the right path filter for this.
