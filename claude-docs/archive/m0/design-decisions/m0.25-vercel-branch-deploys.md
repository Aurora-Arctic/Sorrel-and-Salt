# M0.25 — connect repo to Vercel and restrict branch deploys

**Status:** decided · **Date:** 2026-09-08

The task: connect the repo to a Vercel Hobby project and commit a `vercel.json`
so only `main`, `staging`, and `hotfix/*` trigger deployments — feature branches
must not spend build minutes or function meters (§4).

## Decided

- **The Vercel project connection was done in the dashboard, out of band.**
  Connecting a Git repo to a Vercel project is a one-time account action with
  no repo artifact; it can't be scripted from here and isn't checked in. What
  this PR carries is the committed `vercel.json` — acceptance criterion three
  ("configured, not dashboard-only") is about the deploy-enablement rules, and
  those live in the file.

- **`deploymentEnabled` needs an explicit `"**": false` catch-all**, not just
  the allowed branches. Vercel's rule (confirmed against
  `vercel.com/docs/project-configuration/git-configuration`, last updated
  2026-08-25): _"By default, any unspecified branch is set to `true`."_ So the
  `{ "main": true, "staging": true }` snippet in §4 of the design doc would
  have left every `feature/*` push deploying. The committed file is:

  ```json
  {
    "$schema": "https://openapi.vercel.sh/vercel.json",
    "git": {
      "deploymentEnabled": {
        "**": false,
        "main": true,
        "staging": true,
        "hotfix/*": true
      }
    }
  }
  ```

- **`"**"`, not `"*"`, is the catch-all.** Branch keys use minimatch syntax,
  where `*` stops at `/` and `**` does not. This repo's non-deploying branches
  are `feature/*`, `release/*`, `main-sync/*` — all with a slash — so
  `"*": false` would miss them. `"**": false` matches names with and without a
  slash.

- **`hotfix/*` deploys; `feature/*` does not.** A hotfix is an urgent
  production fix and wants a real deployment to verify against before it
  promotes to `main`. `"hotfix/*": true` re-enables just that prefix via the
  same tiebreak the two long-lived branches use. Everyday feature work still
  gets nothing — local dev and CI cover it.

- **`main`, `staging`, and `hotfix/*` win via the "multiple rules" tiebreak.**
  Each matches `"**"` (false) and its own key (true); Vercel's documented
  behaviour is _"if a branch matches multiple rules and at least one rule is
  `true`, a deployment will occur."_ So Production (`main`), the `staging`
  preview alias, and any `hotfix/*` deploy; nothing else does.

- **`$schema` is included** per Vercel's own docs examples — it gives editor
  validation and costs nothing.

- **§4 of `DESIGN.md` was corrected in the same change.** Its config snippet
  showed the two-key form that doesn't actually restrict anything; leaving a
  known-wrong spec snippet behind after implementing it is worse than the
  one-task-per-PR tidiness of not touching it. The prose table there was also
  updated to name `hotfix/*` alongside `main`/`staging`.

- **No `github.autoAlias` / preview settings in the file.** "Deploy previews
  disabled" and the `staging` → stable-alias mapping are dashboard/project
  settings, not `vercel.json` keys worth pinning here; `deploymentEnabled`
  already stops preview builds for every branch that isn't `main`, `staging`,
  or `hotfix/*`.

## Verified

- `node -e "JSON.parse(...)"` — `vercel.json` is valid JSON.
- `npx prettier --check vercel.json` — passes; `npm run lint` / `format:check`
  / `typecheck` / `check:stories` unaffected (JSON + docs only).
- **Not verifiable pre-merge** (needs the live Vercel project, acceptance
  criteria 1–2):
  - a push to this `feature/*` branch produces **no** deployment;
  - a push to `staging` deploys.
    Confirm both in the Vercel dashboard once this merges to `staging`.

## Rules this sets

- Branch-deploy policy lives in `vercel.json`'s `git.deploymentEnabled`, not
  the dashboard. Adding another always-deploy branch means adding its key set
  to `true` alongside `main`/`staging`/`hotfix/*`; the `"**": false` catch-all
  stays.
- New Gitflow branch prefixes are non-deploying for free — they match
  `"**": false` and nothing re-enables them.
