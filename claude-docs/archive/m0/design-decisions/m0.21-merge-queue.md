# M0.21 — port merge-queue.yml

**Status:** decided · **Date:** 2026-09-09

The task (per the Asana board, which supersedes `TASKS.md`'s frozen text):
copy resume-2026's `merge-queue.yml`, wiring it to the same reusable checks
`pr-gate.yml` (M0.20) already consumes. Unlike `TASKS.md`'s original wording,
the live Asana task explicitly says **not** to enable "Require merge queue"
in Settings → Branches as part of this task — solo development gets no
benefit from queue serialization, and flipping it on forces every merge
through the full CI suite. That switch is a separate task, M7.A.1, deferred
until there are other contributors or real PR volume.

## Decided

- **Same three gaps `pr-gate.yml` (M0.20) already had, for the same reason —
  neither exists in this repo yet:**
  - `gitflow` (M0.22) — dropped entirely, not stood in for. Upstream's
    `merge-queue.yml` calls it with `should-run: false` purely so the
    "gitflow / gitflow" required status check (shared with `pr-gate.yml`)
    reports success instead of leaving a queued merge stuck. Since gitflow
    isn't a required check in this repo's branch protection yet either (no
    ruleset exists — that's also M0.22), there's nothing for a stand-in job
    to unblock. M0.22 adds `gitflow` back to every job's `needs:` here the
    same way it will for `pr-gate.yml`.
  - `build-image.yml` (M0.24) — replaced with the same ad hoc, run-scoped
    image build `pr-gate.yml`'s own `build-image` job uses, tagged
    `ghcr.io/.../testing:merge-queue-<run id>` — distinct from `pr-gate`'s
    `pr-gate-<run id>` and the M0.16/M0.17 smoke workflows' `smoke-<run id>`,
    so a queue entry never collides with a concurrently running PR gate on a
    GHCR tag.
  - `vitest`/`playwright` (M1) — bare stub jobs, real job names, one no-op
    `echo` step. Same reasoning as `pr-gate.yml`: M1 swaps in the real
    `uses:` without ever renaming a required status check, and both stubs
    land in the gate and the queue together so neither is missing a check
    the other has.
- **No `audit` job** — matches upstream, which never calls it from
  `merge-queue.yml` either. `pr-gate.yml`'s own comment already establishes
  why: audit is PR-only and deliberately non-blocking, never a required
  status check, so it has no reason to run again once a PR reaches the
  queue.
- **No path filtering (`changes` job).** Upstream's `merge-queue.yml` calls
  `lint`/`typecheck`/`build` without a `should-run` input at all — each
  reusable workflow's own `should-run` input already defaults `true`
  specifically so "merge-queue (no path filtering) is unaffected" (see
  `lint.yml`/`typecheck.yml`/`build.yml`'s own input descriptions, already in
  place since M0.16/M0.17 anticipating this task). Porting a `changes` job
  here would contradict that documented default rather than complement it.
- **No job-level `concurrency:` on `lint`/`format`/`typecheck`/`build`**,
  unlike `pr-gate.yml`'s cancel-on-new-push groups. Those exist in
  `pr-gate.yml` because a PR's `pull_request` trigger re-fires repeatedly as
  new commits land, and an older, now-stale run should yield. A merge queue
  entry doesn't recur the same way — GitHub re-queues rather than re-firing
  this workflow for the same entry — so there's no stale duplicate run to
  cancel. `build-image` keeps its own concurrency group (`cancel-in-progress:
false`) purely for the shared GHA layer-cache safety reasoning `pr-gate.yml`
  already established, which applies regardless of trigger type.

## Verified

- `npx js-yaml merge-queue.yml` parses with no errors.
- `grep -rn 'resume-2026|mjoynes-wombat-web' .github/` finds nothing new.
- `npm run lint` / `format:check` / `typecheck` / `check:stories` all exit 0
  — a YAML-only addition, unaffected by any of the four.
- **Not verifiable pre-push, and not verifiable even once merged in this
  repo's current state:** an actual `merge_group` run. `merge_group` only
  fires once "Require merge queue" is enabled on the target branch's
  ruleset, which this task deliberately does not do (that's M7.A.1). The
  acceptance criteria this task owns are file-level: the workflow exists and
  parses; enabling the switch and confirming a real queued run stays owned
  by M7.A.1.

## Rules this sets

- A workflow ported ahead of a dependency that doesn't exist yet (`gitflow`,
  `build-image.yml`) follows the exact stand-in `pr-gate.yml` already
  established, rather than inventing a second pattern for the same gap.
- Enabling a GitHub setting that changes what triggers fire (branch
  protection's "Require merge queue") is tracked as its own task, separate
  from porting the workflow file the setting activates — ported-but-inert is
  a valid, intentional end state for a task, not a partial one.
