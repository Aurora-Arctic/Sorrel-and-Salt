## The schema

The schema is code-first, built with Pothos in `src/graphql/builder.ts` and assembled in `src/graphql/schema/index.ts`. A type lives in its own file in the `graphql/` directory of the module that owns its rows, and the index loads each module through its `@/modules/<name>` index, never the deep path, for the side effect of registering on the builder. Only the cross-cutting `AuditInfo` stays under `src/graphql/schema/` ([`modules.md`](../modules.md)). The SDL snapshot (see "The SDL snapshot" below) shows every type, field and argument; this file holds the rules the SDL cannot.

- **No ORM plugin.** `@pothos/plugin-drizzle` is deliberately absent (MB.20, DESIGN.md §7). An object type is declared by hand as an `objectRef` over the row type the service returns, such as `typeof ingredients.$inferSelect`, so a column whose type changes still fails `npm run typecheck`. `tests/graphql/builder.test.ts` pins this with `@ts-expect-error` inside a function that is never called.
- **Every Pothos package is a stable major.** A `0.x` plugin entering the tree is a decision to argue for in the diff.
- **Fields are non-null by default** (`defaultFieldNullability: false`). A field that can be null says so with `nullable: true`, which makes the null something the field means rather than an accident of the default.
- **Typed text that narrows a list is `query`.** `compendium` and the autocompletes all take `query: String`, and a blank or absent one is no filter. The same name runs through the filter types and the services to the SQL. The exception is `possibleDuplicates(name: String!)`: its text is a whole name about to be saved, compared as a whole, and stays `name` all the way down.
- **Two date scalars, an instant and a day.** `DateTime` is graphql-scalars' `DateTimeISO` under the plain name (the package's own `DateTime` serializes to a `Date` and leaves the string to `JSON.stringify`). `LocalDate` is for days such as a reference's `modified` and `accessed`: `YYYY-MM-DD` both ways, and a value that is not a calendar day is refused before any resolver runs.
- **`AuditInfo` is defined once**, in `src/graphql/schema/audit.ts`. An audited type exposes `audit: AuditInfo!` (`createdAt`, `createdBy`, `updatedAt`, `updatedBy`), resolved from the row, never as flat fields. `deleted_at` never surfaces, because no ordinary finder returns a soft-deleted row. `createdBy` and `updatedBy` are bare ids. A test walks every object type and fails on any type other than `AuditInfo` with an audit-named field.
- **`ok: Boolean!` stays beside the real fields.** It mirrors Better Auth's `/api/auth/ok`: it answers without a session or the database, which is what the route's tests and the e2e spec probe the endpoint with.
- **An object type is declared over the row, never exposing `identityKey` or `workspaceId`.** A tier is `isGlobal`. A nested list is non-null (`[]` with none), is a bare list rather than a connection (the pagination guard reads `Query` alone, so it is bounded by its parent), carries no `audit`, and reads through a loader keyed by the row ([`loaders.md`](loaders.md)).
- **A delete answers the deleted id, not the entity.** The row is soft-deleted and a list evicts a row by its id; the deleted entity would be a poor answer, since its loader-backed lists read live parents only and would come back empty. An id the caller's tier does not hold live is `NOT_FOUND`.
- **A refusal is an error, never a payload** (["Errors"](errors.md)). A Zod failure is `VALIDATION`, with one `fieldErrors` entry per issue whose path is in the input's own shape, such as `['folkNames', 1]`. A collision is `VALIDATION` on the field that caused it. Either way `data` is null and the transaction wrote nothing. An id that is not a uuid is answered as an id naming nothing (`NOT_FOUND`, or `FORBIDDEN` for a coven id, [`db/membership-proof.md`](../db/membership-proof.md), "What the check asks"), never a masked driver error.
- **A write clears the loaders an earlier root field may have filled.** Root mutation fields run in turn within one request, so each write clears the per-request loader keys it changed before it answers, and the answer is a fresh read. Every keeper write expires the `compendium` tag.
- **An update input is the whole entity and replaces the row.** Every field is non-null, so leaving one out is a schema error rather than a silent clear. GraphQL has no field that is required and also nullable, so a caller clears a text field with `""` and a list with `[]`; the shared Zod schema takes both as absent, as it takes a blank form field. An input never declares a tier, `workspaceId` or an audit column, and GraphQL refuses a field its type does not declare before any resolver runs. An input where a field must be one of two (a substitute's `ingredientId` or `name`) makes both nullable, since GraphQL has no one-of input, and the shared schema holds an entry to exactly one ([`validation.md`](../validation.md)).

### Resolver helpers

A resolver holds only what the transport adds to the service it calls, written once in `src/graphql/context-helpers.ts`. None of it decides who may: that is the service's (CLAUDE.md rule 1).

- **`sessionOf(context)`** is the session, non-null, or `Forbidden` for a signed-out caller and `AccessPaused` for a paused one: the refusal a field scope gives, so the transport maps one shape. `.oxlintrc.json` holds a module's resolvers and loaders to it: its `src/modules/*/graphql/**` and `src/modules/*/loaders/**` override refuses a runtime import of `Forbidden`, since oxlint has no `no-restricted-syntax` to refuse `if (!session) throw new Forbidden()` itself.
- **`definedArgs(args)`** makes each null absent: GraphQL sends null for an optional argument, and a service's filter takes `undefined`. A list passes the fields it names, `definedArgs({ query, groupId })`, never a connection's whole `args`, which also carry `first` and the cursors.
- **`suggestionConnection(name, type, suggest)`** registers a picker's suggestion field as one connection taking an optional `workspaceId` and `query`. `ingredientSuggestions`, whose `workspaceId` is required, is written out.

### `me`, `User` and the account writes

- **`me: User!`** is read through `getMe(session)`, which takes no id, so there is no other user a caller could name. A session whose user row is gone or soft-deleted gets `NotFound`: Better Auth reads the session's user without our filter, so the session can outlive the row.
- **`User`'s private fields.** `email`, `emailVerified`, `role` and `canCreateWorkspace` carry the `self`-or-`admin` scope; `providers` is a keeper's alone. They stay non-null, so a query for another user's email fails with `Forbidden` rather than returning the user without it.
- **`User.memberships`** is registered by `coven`, not `identity`, because `identity` may import no module. The `membershipsByUser` loader's service `membershipsOf(session, userIds)` answers each id with that user's live memberships in live workspaces, or a `Forbidden` in that id's slot for anyone but the caller. A site keeper may list anyone's by name and role and reaches none of those workspaces' contents.
- **`Workspace.members`** is a paged connection (CLAUDE.md rule 8). `listMembers` checks `member: read`, orders by join date, and takes an optional `query` that matches the member's name case-insensitively, with `%` and `_` read literally. It is one coven at a time, not batched by a loader: no page lists two covens' members ([`m6.11-members-without-a-loader.md`](../design-decisions/m6.11-members-without-a-loader.md)).
- **`WorkspaceMember.user` is a `CoMember`** (an `id` and a nullable `name`), never the `User` type, whose email a scope would have to guard. The name resolves through `usersById` ([`auth/display-names.md`](../auth/display-names.md)).
- **`workspace(id: ID!)`** reaches a coven from the query root. Through `me`, a member's name sits one level past the depth limit ([`protections.md`](protections.md)). `workspaceById` checks `workspace: read` and answers the same bare `FORBIDDEN` to a stranger and to an id no coven holds, so the answer says nothing of whether the coven exists. The members page calls `listMembers` directly from a server component.
- **`users(query, awaitingApproval, role)`** is the admin user list: a paged connection of the ordinary `User`, so `email` resolves through its scope and there is no second path. `listUsers` refuses anyone but a site keeper; the query has no scope of its own, because it is a read ([`auth/admin-users.md`](../auth/admin-users.md), "The user list").
- **`privilegeChanges(userId, privilege, query)`** is the privilege ledger: a paged connection of `PrivilegeChange`, newest first, whose `subject` and `actor` are the ordinary `User`, nullable where no live account holds the id. They share the `usersByIdForAdmin` loader, so a page reads its users once. The query carries the `admin` scope and `listPrivilegeChanges` refuses anyone but a keeper again ([`auth/admin-users.md`](../auth/admin-users.md), "The privilege ledger").
- **Account writes.** `setEmail(email, next)` is signed-in only and answers the row as it is: the address changes only once the mailed link is followed ([`auth/admin-bootstrap.md`](../auth/admin-bootstrap.md), "The email page"); a refusal, including an address held by another verified account or a second mail inside the minute, is a `VALIDATION` error on `email`. `next` is where the mailed link's landing goes on to. `setName(name)` renames the session's own row; a blank or over-long name is `VALIDATION` on `name`, and a provisional account is `FORBIDDEN`. `setPassword(newPassword)` gives an account with no password its first one through Better Auth; a refused password, or an account that already has one, is `VALIDATION` on `newPassword` ([`auth/passwords.md`](../auth/passwords.md), "Setting a first password").
- **`grantWorkspaceCreation` and `revokeWorkspaceCreation`** each write `canCreateWorkspace` on a live user and a row in the privilege ledger, answer the row, and carry the `admin` scope. The service refuses anyone but a keeper, a change that changes nothing, and a keeper's flag, as `FORBIDDEN` with a message naming the user ([`auth/admin-users.md`](../auth/admin-users.md), "Approving workspace creation").

### Suggestion fields

`celestialBodySuggestions`, `zodiacSuggestions`, `deitySuggestions` and `formSuggestions` (`vocabulary`) and `commonNameSuggestions` (`ingredients`) are the autofill behind the member fields. Each is a `pagedConnection` over one list with two buckets: curated values first (name matches before description matches), then values in use in the compendium and the named workspace that no live curated row holds. `curated` says which bucket a row came from; the order is the finder's ([`db/member-autofill.md`](../db/member-autofill.md), "The member's autofill").

- **A blank or absent `query` lists the whole vocabulary** and every in-use value, still a page at a time.
- **Celestial body and sign suggestions share one type**, `CorrespondenceSuggestion`; neither carries a group and neither records a pick, so neither has an `id`.
- **`group` tells two same-named forms apart.** `ingredient_forms` is unique on the slug alone, so "Wax" may be an animal part and a substance, and a variant's `form` stores only the string. The pair comes back as two suggestions, in group order, and a client renders "Wax (Substance)". `tradition` does the same for deities ("Hecate (Greek)"); a deity under a soft-deleted tradition comes back as a value in use, with none.
- **`id` is what a pick sends**: the curated row's, as `formId` or `deityId`; null for a value only in use, which is sent as text.
- **A deity is found by its other names too.** A query matching none of the deity's name but one of its live `deity_other_names` finds it in the first tier, and `matchedName` carries the closest such name, so the picker can say "Also called Woden". A pick still sends the deity's `id` and `value`, never the other name.
- **`claimants` names who already holds a form or common-name value**, in the compendium and the named workspace only: formal name first, and a claimant with none by its label, so a `none` entry is not hidden. It is a nested list, bounded by the in-scope ingredients. Deities have none: a deity is no part of an ingredient's identity.
- **A common-name suggestion has one bucket**: there is no curated vocabulary of common names, so no `curated` and no `description`. The in-use names are every in-scope entry's display name and live folk names.
- **Two refusals, one error.** Signed out, the resolver's `sessionOf` refuses with `Forbidden` before the service is reached. Signed in, `assertMembership` refuses a coven the caller does not belong to with the same `Forbidden`, a site keeper included. The field carries no scope, because the resolver's null check is the same early refusal.
- **A null `workspaceId` reads the compendium alone**: the curated rows, then the values in use in the compendium, under no proof, so any signed-in caller is answered. It is the keeper's compendium form, which names no coven. Signed out is still refused, because the public line is drawn field by field and no public page reads these. The form, not the field, keeps a compendium entry to the curated rows ([`components/ingredient-form.md`](../components/ingredient-form.md), "On the compendium").

### `compendiumMatches`

`compendiumMatches(workspaceId, name)` lists the compendium entries whose name or formal name is exactly the typed one, folded to lower case, and no other tier, so no coven's own entry is ever offered. `findCompendiumMatches` asserts read membership of the coven first, so an observer is answered and a non-member gets `FORBIDDEN` by direct id. A blank name answers empty. Its node is the `Ingredient`, whose `inCupboard(workspaceId)` says whether that coven's cupboard holds it, through the batched `cupboardEntryByIngredient` loader. `possibleDuplicates` nodes carry it too; `workspaceId` is nullable there, answering false, so the keeper's call shares the document.

### `possibleDuplicates`

The "did you mean" warning, registered by `ingredients` over `findPossibleDuplicates` ([`db/fuzzy-matching.md`](../db/fuzzy-matching.md), "Fuzzy matching"). Each edge carries the match's `score`.

- **A node is an `Ingredient`**, so a warning links by `slug`, tells the tier by `isGlobal` and shows `canonicalName` beside the label. Without the formal name, "Did you mean Cat's Claw?" could mean five different plants.
- **Compendium entries and the named coven's own, and nothing else.** A match in another coven never comes back, whether by label or folk name. The filter is the finder's, in SQL.
- **The threshold is 0.4 trigram similarity** (`%`), from the one `SIMILARITY_THRESHOLD` in `select.ts`, set per read. It is not the compendium search's 0.5 word similarity: a search finds an entry from a fragment, while this asks whether a whole name is nearly one already there.
- **Best match first.** Pages are keyed `(-score, name, id)`. The score is the best trigram similarity among the label, the formal name and the live folk names; it is never below the threshold, and 1 means that exact name is already there. It sits on the edge because it describes the match, not the entry. A blank `name` gets an empty page, not every entry.
- **Refusals** are the suggestion fields': `Forbidden` from the resolver when signed out, then `assertMembership` for `ingredient: ['read']`. An observer is answered, because every row returned is one a reader of the coven could already list. A null `workspaceId` matches the compendium alone, asking no membership: the admin's compendium form, which drops the entry being edited from what it shows.

### `ingredientSuggestions`

The substitute picker's search, over `suggestIngredients` and `findIngredientSuggestions` ([`db/compendium-read.md`](../db/compendium-read.md), "findIngredientSuggestions"). Picking a node writes a link to it (`ingredient_substitutes`).

- **A node is an `Ingredient`**, because a pick needs the id that the common-name strings do not carry.
- **Compendium entries and the named coven's own, and nothing else**, which is exactly what a coven's substitute may link. A compendium entry's substitute may link only the compendium, so the admin form reads `compendium(query)`, which holds nothing else.
- **It matches as `compendium` does**: word similarity at 0.5 against the label, the formal name, the live folk names and the live variants' forms and descriptions, accents folded, so a typed prefix finds its entry (`mu` is under 0.4 similar to Mugwort and 0.67 word-similar). Best match first under the compendium's weights, with no score on the edge, since a picker ranks rather than reports. A blank `query` lists both groups by name.
- **Each edge carries a `group`**, the `SuggestionGroup` enum, `yours` or `compendium`. `yours` is the coven's cupboard (its own entries and the compendium entries it holds), listed first; `compendium` is the rest. Each group is ranked within itself and starts with up to eight. A coven's own entry and a compendium entry sharing its name both appear, because a name match hides nothing. A held entry's node answers `cupboardEntry(workspaceId)` for the label the coven gave it. `group` is on the edge, not the node, because it depends on the viewing coven. `form` ranks within each group.
- **`categoryIds` keeps entries carrying any of the ids**, on the entry or one of its variants, through the compendium filter's `any` mode. Null or empty is no filter. The list is paged, so a filter applied after fetching would miss matches.
- **Refusals** are `possibleDuplicates'`.

### `compendium`, `ingredient` and `ingredientFormValues`

The compendium's reads, registered by `ingredients`, with the vocabulary types by `vocabulary`. All three are public: no `signedIn` scope, and the list and the vocabulary resolvers pass no session at all. The list's connection adds to the usual one a `totalCount` (the entries under the filter), a `countBefore` (how many precede this page; null on an empty page), and on each edge a `score`.

- **The `compendium` query is the search.** Its filters run in SQL ([`db/compendium-read.md`](../db/compendium-read.md), "The compendium read"; facets in [`design-decisions/m11.22-search-facets.md`](../design-decisions/m11.22-search-facets.md)). The browser never holds more than a page (CLAUDE.md rule 8), so it cannot be the search.
  - `query` must be at least 0.5 word-similar (`<%`) to the label, the formal name, a live folk name, or a live variant's form or description, case- and accent-folded, so a prefix and a transposed pair both find their entry. A query shorter than two characters is no search (one letter would filter and rank by noise), so it lists every entry, unranked.
  - `categoryIds` ANDs the listed categories (with a mode). `forms` keeps an entry holding a live variant whose form, trimmed and lower-cased, is any one of the list. `deityIds` keeps an entry with a live link to any listed curated deity. `zodiacSigns` and `celestialBodies` keep an entry whose own list, or a live variant's, holds any one of the values, folded on both sides. `elements` matches an entry whose `elements`, or those of any live variant, overlap the list, by array overlap in SQL; `workspaceIngredients` takes it too.
  - `toxic` is the `ToxicFilter` enum, `any`, `toxic` or `not_toxic`: `toxic` keeps an entry flagged on itself or on any live form, `not_toxic` one where neither holds, and a retired form's flag counts for nothing.
  - Within one kind the chosen values OR; across kinds the filters AND. An empty list, a blank entry or a value matching nothing is no filter rather than an error.
  - The keeper's to-do lists, for `/curator/compendium`, are public as the rest of the query is: `withoutReferences: true` keeps only entries citing no live compendium reference (an entry whose one link is unlinked, or cites a soft-deleted reference, is on it); `nomenclature` keeps only entries so classified, so `unknown` is the formal names still to look up; `withoutForms: true` keeps only entries with no live form. `false` or leaving one out is no filter, and `totalCount` counts under the same filter.
- **A search is ranked, best match first.** It pages `(score DESC, name, id)`, and each edge carries `score`: the query's word similarity to each field it matched times that field's weight, the best kept. Weights run from 1 for the label down to 0.2 for a description ([`db/compendium-read.md`](../db/compendium-read.md), "The compendium read", holds the weights and how the rank reaches a keyset page). Without a search the list pages `(name, id)` and `score` is null. The score is on the edge because it describes the match, not the entry.
- **The list numbers its pages.** `totalCount` and `countBefore` are `countCompendium`'s, over the same parsed filter as the page, so a search counts at the page's 0.5 rather than the server's 0.6 and never counts fewer rows than its pages hold. The formula is in ["Pagination"](pagination.md). A signed-out visitor reads both.
- **`ingredient` is non-null, and a miss is `NOT_FOUND`**, as `me` answers one: an id that names nothing, a soft-deleted entry, and a coven's own entry asked for without its coven all read the same, since a workspace entry's existence is private. `workspaceId` names the coven whose own entry may be asked for: the service asks `assertMembership(…, { ingredient: ['read'] })`, refusing a non-member, a site keeper and a signed-out caller with `Forbidden`. Without it the read is the compendium alone. A malformed id is a miss, not a driver error.
- **Nested lists** (`folkNames`, `categories`, `substitutes`, `deities`, `references`, `variants`) read through loaders keyed by the row ([`loaders.md`](loaders.md)).
  - `FolkName` inputs take bare strings, since a name typed and not yet saved has no id; the output id is the live row's, so a client can name one to `promoteFolkName`. Sorted by `name`.
  - `Substitute` is a link or a typed name. `ingredient` is null on typed text and on a deleted link, so a client links exactly when it is set. `variant` is found among the linked ingredient's variants, so a form is read beneath its ingredient and never by its id alone. Sorted by `name`. A page reads its substitutes in one statement, the linked ingredients joined in through the hatch ([`db/soft-delete.md`](../db/soft-delete.md)).
  - `IngredientDeity` reads as `Substitute` does: `deity` is null on typed text and once that deity or its tradition is retired. In the order entered.
  - `ReferenceLink` is filed alphabetically by citation less a leading quotation mark and an initial _A_, _An_ or _The_. The service sorts, since the citation exists only in TypeScript. Only a live reference the ingredient's readers may read answers ([`db/references.md`](../db/references.md)).
- **`IngredientVariant` is one form of an ingredient.** A variant's `categories`, `substitutes` and `references` come through `categoriesByVariant`, `substitutesByVariant` and `referencesByVariant`, keyed by the variant row, which carries its ingredient's tier. An ingredient's own lists are its rows with no variant, so nothing appears in both and nothing is merged: a client shows a form's beside its ingredient's (the union rule). `formChoice` is the curated `IngredientFormValue` the variant's `formId` records, null when the form was typed and once the form or its group is retired, so the text stands alone. `Ingredient` has no `form` or `formChoice`: a client reads an entry's forms through `variants`. The four ingredient inputs carry `variants: [IngredientVariantInput!]`, required, and there is no variant mutation ([`design-decisions/mb.215-ingredient-variants.md`](../design-decisions/mb.215-ingredient-variants.md)).
- **`IngredientFormValue`, not `IngredientForm`**: one row is one permitted value of a variant's `form`, and `IngredientForm` is the entry-form component. Only forms whose group is live are listed, and the group is what tells two "Wax" values apart.
- **A sweep holds the signed-out line.** `tests/db/graphql-query-scopes.test.ts` names every `Query` field with the outcome a null session gets, fails on a field it does not name, and runs each. A query added later has to say which side it is on. It does the same for every `Mutation` field, all of which refuse, and for every query taking a `workspaceId` it runs a null one too, so the compendium-only mode is no way round the session. Each table must equal the schema's field list and none may be empty, so no resolver file holds a signed-out test of its own. Every `Mutation` is also named as a keeper write or one any session may reach (["Auth scopes: the second check"](#auth-scopes-the-second-check)).
- **Cost.** A page of 100 with `categories { group { … } }` prices above `MAX_COST`, since a bare list multiplies its selection by 10, and is refused; the chip-decorated list pages at 25 or 50 (["Protections"](protections.md)).

A GraphQL test file holds the transport's half alone: one refusal per error code per field, with the precondition that would have let it succeed, beside what only the transport can show (the SDL's own refusals, an `authScopes` gate, the loaders cleared after a write, one read per page, the edge fields). Which roles are refused at which rows, and every Zod rule, are the service and validation tests' alone ([`design-decisions/mb.180-graphql-transport-half.md`](../design-decisions/mb.180-graphql-transport-half.md)). Every GraphQL test file runs through `tests/support/graphql/run.ts`, Yoga with the route's `maskedErrors`, and reads a refusal as `extensions.code`, never as the thrown type. A test that watches a loader, shares one across operations, or records what a sender was asked to mail hands `run` its own.

### `compendiumSourcingScore` and the `sort` argument

`compendiumSourcingScore(id: ID!)` is a curator's read of one compendium entry's sourcing score. Every fact is listed, zero-point ones too, and the points add up to the score. The field carries the `curator` scope with an `unauthorizedResolver` that answers `null`, so a practitioner, an observer or a signed-out request reads `null` rather than an error, by direct id too. The resolver calls `readSourcingScore`, which checks the curator again (rule 1). `Ingredient` has no score field, so a coven's ingredient, the public read, `llms.txt` and the `.well-known` files never carry one.

`compendium` takes an optional `sort` (`name`, A to Z even under a search, or `sourcing_score`, lowest first) and `order: desc` to reverse either ([`db/compendium-read.md`](../db/compendium-read.md), "The sourcing sort"). The score sort refuses anyone who is not a curator or keeper with `Forbidden`. No edge carries the score itself: the admin list reads it through the service, beside its rows.

### The workspace ingredient mutations

`createWorkspaceIngredient`, `updateIngredient` and `deleteIngredient`, over `services/workspace-ingredients.ts` ([`db/workspace-ingredients.md`](../db/workspace-ingredients.md), "Workspace ingredients"), each taking the coven as `workspaceId`.

- **The coven is an argument.** The service asks the proof for the argument's coven, `{ ingredient: ['create'] }`, `['update']` or `['delete']`, which stewards and practitioners hold and observers, site keepers and non-members do not. All three carry the `signedIn` scope.
- **The four ingredient inputs spread one field set**, `ingredientInputFields(t, { tier, whole })` in `graphql/ingredient-input.ts`. `whole` makes every field non-null, and the compendium tier requires `nomenclature` on a create too.
- **`IngredientInput` is the create's.** Only `name` and `variants` are required, so a one-field stub is `{ name, variants: [] }`. With no formal name, a `nomenclature` left out or sent as `null` becomes `none`.
- **`variants` is required on all four inputs**, the creates included: each a whole form whose every field but `id` is non-null, `""` or `[]` clearing one. A form's refusal is `VALIDATION` pathed to it, `['variants', 1, 'form']`. Both update mutations clear `variantsByIngredient` with the other child loaders.
- **A reference is a `ReferenceLinkInput`**, `{ referenceId, locator }`: an existing reference, created a moment before through `createReference` when it is new. Optional on `IngredientInput`, required on the update input where `[]` clears. The shared schema refuses the same reference twice whatever its locator, so `reference_links_ingredient_unique`'s 23505 is never what a member sees. The service holds a new one to the tier rule (a coven's ingredient cites the compendium's or its own coven's, a compendium entry only the compendium's); anything else, an id naming nothing or a soft-deleted reference included, is the same `VALIDATION` field error on the entry, `['references', i]`. The list replaces the links: a link is matched by its reference, keeps its row and takes the locator sent, and a list that changes nothing writes nothing. A link to a soft-deleted reference is not shown, so the form never sends it back, and the save leaves it in place for a restore.
- **A substitute is a `SubstituteInput`**, `{ ingredientId }` to link (with `substituteVariantId` for one form of it) or `{ name }` for one not entered. The service holds a new link to the tier rule (DESIGN.md §5): a coven's ingredient may link the compendium or its own coven, a compendium entry only the compendium, and never itself. Anything else, another coven's ingredient, a deleted one or an id that names nothing, is the same `VALIDATION` field error on the entry, so a refusal says nothing about what exists elsewhere. A link the ingredient already holds is kept as it is. The list replaces the live rows: a link matched by its ingredient, a name as written, and a list that changes nothing writes nothing.
- **A form's pick is `formId`, a deity an `IngredientDeityInput`.** `formId` sits beside `form` on each variant input, non-null, where `""` means the form was typed. It must name a curated form (live, under a live group) and `form` must fold to that form's name, which is written in its spelling; anything else is a `VALIDATION` field error at `['variants', i, 'formId']` or `['variants', i, 'form']`, never a 23503. A deity entry is `{ deityId }` or `{ name }`, exactly one; a deity picked anew must be curated, and one the ingredient already holds is kept once retired, sent back by id or by name. The list replaces the live rows in the order sent ([`db/ingredient-children.md`](../db/ingredient-children.md)).
- **`categoryMode`** is `all` (default) or `any`, beside `categoryIds` on `compendium` and `workspaceIngredients`. `any` matches an entry holding any of the ids; it changes nothing with fewer than two.
- **The categories are `categoryIds`**: `[ID!]` on the create, `[ID!]!` on the update where `[]` clears. Each must name a live category (an id naming none, or a soft-deleted one, is a `VALIDATION` field error at `['categoryIds', i]`), and a repeat is written once rather than refused, since a chip is on or off. The set replaces the ingredient's pairs in its own transaction: a pair kept keeps its stamps, one dropped is hard-deleted and one added is stamped from the session. A pair whose category is soft-deleted is not shown, so the form never sends it back, and the save leaves it in place for a restore.
- **The answer is the entity as a fresh read gives it**, with `audit` stamped from the session and the loader-backed lists read after the write has committed, so a client reconciles its cache without a refetch. `updateIngredient` first clears the entry from the ingredient loaders and empties the three variant child loaders through `clearIngredientChildren`, which clears every loader `loaders/ingredient-children.ts` defines.
- **An id the coven does not hold live** (the compendium's, another coven's, one already deleted) is `NOT_FOUND` on a delete.

### `workspaceIngredients`

A coven's list over `listWorkspaceIngredients` ([`db/stock.md`](../db/stock.md), "The workspace ingredient list"): its own entries and the compendium entries it holds a jar of, as a `t.pagedConnection` of `Ingredient`. It takes the filters of `compendium` (`query`, `categoryIds`, `forms`, `deityIds`, `zodiacSigns`, `celestialBodies`, `toxic`, `elements`), still under the coven's membership check, plus three arguments the coven alone has:

- `source`, `local` (the coven's own entries) or `compendium` (the compendium entries it holds); left out, both.
- `inStock` keeps an entry only when one of the coven's jars of it is not at 0; a jar with no quantity counts as held, so a local entry with no jar leaves.
- `lowStockOnly` keeps an entry only when one of its jars is at 0 or at or under a threshold above 0 (Out of Stock or Low Stock).

A coven the caller is not in answers `FORBIDDEN`; any practitioner, observers included, may read it. An entry's jars are its `stock` field, so a page reads its stock in one batch. The Ingredients page shows "Page X of Y" from `countWorkspaceIngredients`, which the field does not expose: the connection carries no `totalCount`, because only the server-rendered page counts, and the count is not cached.

### `compendiumFacets` and `workspaceIngredientFacets`

The numbers beside each choice in the search's filter panel: for every value of every filter, how many entries the list would hold with that value picked. `compendiumFacets` takes `compendium`'s filter arguments with no page; `workspaceIngredientFacets` takes `workspaceIngredients`', so a count agrees with the list under the same filter. Each resolver hands its arguments to its service in `services/ingredient-facets.ts` and checks nothing itself. How each value is counted is in [`db/compendium-read.md`](../db/compendium-read.md), `findCompendiumFacets`; which rows a coven's counts read is in [`db/stock.md`](../db/stock.md), "The workspace ingredient list".

- **Each answers one object, not a list**, so neither is a connection, and the pagination guard has nothing to exempt. The seven lists are bounded by the vocabularies and by the forms, deities and categories the counted entries carry. Each item's `value` has the type of the argument it would be sent back as, so a client can put a picked value straight into the next query.
- **`CompendiumFacets` adds** `withoutReferences` and `withoutForms`, each the same whether its switch is on or off.
- **`CompendiumFacets.reviewed`** is a nullable list: how many entries are reviewed (`value: true`) and how many need review (`false`), counted with `reviewed` left out of the filter. It is null, with no error, for anyone who neither curates nor administers, so the public panel learns nothing of the mark. `compendium` and `compendiumFacets` both take `reviewed: Boolean`; anyone but a curator or a keeper sending it gets `FORBIDDEN`, refused by `compendiumFilterFor` ([`db/compendium-read.md`](../db/compendium-read.md), `reviewed`).
- **A coven's `IngredientFacets` adds** `source` (always both values, zeros kept, each counted with the Source setting blanked and everything else, In Stock included, kept), `inStock` and `lowStockOnly` (how many entries the list would hold with that switch on, under the rest of the filter and the chosen Source). A count equals the list's `totalCount` under the same filter. They are non-null on the coven's type alone.
- **`compendiumFacets` is public** like `compendium`: no `signedIn` scope and no session, and its service caches the answer under the `compendium` tag ([`db/compendium-cache.md`](../db/compendium-cache.md)).
- **`covenIds: [ID!]` counts only entries a live `workspace_compendium_entries` row of one of these covens holds** (In My Covens on the public compendium). The resolver hands it to `compendiumFacetsHeldIn` (`services/compendium-held-in.ts`), which deduplicates the ids, keeps the first 20, and asks `assertMembership` for each with `ingredient:read`, which every role holds. An id the caller is not a member of, or that is not a uuid, is dropped without an error, so a foreign coven's id narrows nothing and says nothing about that coven. With no id left, none given, or no session, the answer is the cached public one; with at least one it is read per request and never cached (rule 6). `covensNot: Boolean` turns it to Not In: count only entries none of the proved covens holds, and with no `covenIds` given, none of the caller's covens. If `covenIds` were given and every one dropped, it is the cached answer under Not In too. `compendium` itself takes no `covenIds`: the page reads the narrowed list through `listCompendiumHeldIn` and `countCompendiumHeldIn`, never through the GraphQL list.
- **`workspaceIngredientFacets` refuses as `workspaceIngredients` does** and is never cached.

### Stock

`InventoryItem`, `Ingredient.stock` and the stock writes, in `graphql/stock.ts` over the stock service ([`db/stock.md`](../db/stock.md), "The stock service").

- **`InventoryItem`** is one jar: one form of one ingredient in one coven. Its `ingredient` loads through `ingredientsById`, keyed by the jar's coven, and its `variant` is found in `variantsByIngredient`'s answer, so a page of jars costs one read for each. `quantityOnHand` and `lowStockThreshold` are `Float`: Postgres returns `numeric` as text and the field turns it into a number. The unit enums are built from `src/modules/ingredients/schema/units.ts`, so the schema cannot drift from the one module that owns the units.
- **`Ingredient.stock(workspaceId)`** reads through the `stockByIngredient` loader ([`loaders.md`](loaders.md)), so a page makes one read per coven named. A coven the caller is not in refuses at the field, `FORBIDDEN` with the field's path.
- **`StockInput`** has no `unitDimension`, which the service derives from the unit. On `updateStock` a field left out keeps its value and `null` clears it. The form is the add's own `variantId` argument, never an input field, so a jar cannot move to another form.
- **`addIngredientToWorkspace(workspaceId, variantId, input)`**: a form the coven already holds is `VALIDATION` beside `variantId`; an id naming no form the coven may read, such as an entry with no forms, is `NOT_FOUND`. The API always takes a form; picking the one form of a single-form entry is the page's job.
- **`deleteStock`** soft-deletes a jar and answers its id.
- **`saveStock(workspaceId, ingredientId, input)`** is the stock dialog's one Save, over the three writes' rules in one transaction. `SaveStockInput` is three lists (`create`, `update`, `delete`), so a delete cannot carry a quantity and `StockInput`'s omit-keeps, null-clears reading holds in each row. `ingredientId` scopes the batch: a jar or form of another ingredient or coven, a deleted one, or an id that is not one is `NOT_FOUND` and nothing is written. The answer is the ingredient's live jars after the write. Bad rows give one `VALIDATION` error carrying every bad row's `fieldErrors`, each `path` in the shape of the input (`create.<i>.input.<field>`, `update.<i>.input.<field>`, `create.<i>.variantId` for a form the coven already holds); a jar named twice is `VALIDATION` at `update.<i>.id` or `delete.<i>`. An empty save writes nothing and answers the current jars.

All four writes carry the `signedIn` scope, and the service asks the proof for `inventory: update`, which observers do not hold. The add, the update and `saveStock` clear the changed jar's (or the ingredient's) `stockByIngredient` key; the delete has no row to key by, so it clears the loader whole.

### Cupboard entries

`CupboardEntry` and `Ingredient.cupboardEntry`: a coven's own say over a compendium entry it holds, in `graphql/cupboard-entries.ts` ([`db/workspace-compendium-entries.md`](../db/workspace-compendium-entries.md), "Reading it").

- **`CupboardEntry`** is one row of `workspace_compendium_entries`. A null override means "the compendium's value", and an empty list is one the coven cleared on purpose. `annotated` is true when any override is set. `compendiumName` is read off the parent `Ingredient`.
- **`Ingredient.cupboardEntry(workspaceId)`** is that coven's live row for the entry, or null: for an entry the coven does not hold, and for a coven's own ingredient. It reads through the `cupboardEntryByIngredient` loader ([`loaders.md`](loaders.md)). A coven the caller is not in refuses at the field, `FORBIDDEN` with the field's path, as `Ingredient.stock` does. Any member reads it, observers included.
- **The row sits beside the entry, never merged into it**, so `Ingredient` still answers the compendium's values and `isGlobal` stays true. Forms, folk names, substitutes, categories, references and `toxic` have no override and always read from the compendium.
- **`Ingredient.retired: Boolean!`** is true for a compendium entry the curators have retired, which `ingredient(id, workspaceId)` still answers to a member of a coven whose cupboard names it, through the service's `isRetired`. The entry's child fields read through loaders whose keys carry no reading coven, so they answer nothing for a retired entry; the entry page reads them through `ingredientDetailOf` ([`db/workspace-compendium-entries.md`](../db/workspace-compendium-entries.md), "When the compendium retires the entry").
- **The three writes** answer through the same `nodeOf` as the read, so the loader is cleared and the answer is a fresh read. `addCupboardEntry` answers the new `CupboardEntry` (`input` optional). `annotateCupboardEntry(…, expectedRevision)` answers the row after the change, with its `revision`; a stale `expectedRevision` is `STALE_WRITE`, leaving it out writes over a newer one; a field left out keeps its value, `null` hands it back to the compendium, and a list, even empty, is the coven's own. `removeCupboardEntry` answers the `ingredientId` and is `VALIDATION` while the coven holds a jar of the entry.
- An observer is `FORBIDDEN`, an entry the coven does not hold is `NOT_FOUND`, and a taken label is `VALIDATION` beside `label` ([`db/workspace-compendium-entries.md`](../db/workspace-compendium-entries.md), "Writing it").
- **`convertCompendiumEntryToLocal`** (Make It Ours) makes a held compendium entry into the coven's own and answers a `ConvertedCompendium`: `entry`, the new own `Ingredient`, and `dropped`, in which only `folkNames` can be non-empty (a folk name the new name took). An observer is `FORBIDDEN`, an entry not held `NOT_FOUND`, and a taken label or an own entry of the same identity `VALIDATION` beside `label`, `canonicalName` or `name` ([`db/workspace-compendium-entries.md`](../db/workspace-compendium-entries.md), "Converting a compendium entry into our own").

### The grimoire

`Spell`, `grimoire`, `spell` and the two saves, in `graphql/spell.ts` over `services/spell-reads.ts`. Every read asks the proof for `spell: read`, which every role in the coven holds, and every row comes through the finders that keep a private spell its author's ([`db/spell-visibility.md`](../db/spell-visibility.md)). A private spell never reaches a resolver: it is left out of a list in SQL, and by id it is `NOT_FOUND`, the same answer as a spell that does not exist.

- **`grimoire(workspaceId, orderBy, status, query, first, after)`** is a cursor page of the coven's shared spells and the caller's own private ones, through `t.pagedConnection` and `findGrimoirePage`.
  - `orderBy` is `UPDATED_DESC` (default, by `updatedAt`), `CREATED_DESC` or `TITLE_ASC` (A to Z, untitled last). Each order's cursor key ends in the spell's id, so spells that tie page once each. A draft may go untitled, so `TITLE_ASC` sorts on whether the title is missing first, then on the title read as empty; a cursor compares its key as one row value, which a null part would break.
  - `status`, given, keeps only that status, in SQL; left out, both.
  - `query` searches the title and the intent through the weighted search the ingredient lists use ([`db/compendium-read.md`](../db/compendium-read.md)): a title match counts twice an intent match, the best match first, with `orderBy` breaking a tie. A search under two characters (`MIN_QUERY_LENGTH`, counted in composed code points) is no search; `listGrimoire` and `countGrimoire` both drop it, so the page and its count agree.
- **`spell(id, workspaceId)`** takes the coven as `ingredient(id, workspaceId)` does, so the membership check runs before any read. A spell in another coven, or another author's private spell, is `NOT_FOUND`.
- **`Spell`** has `title` nullable because a draft may go untitled until complete. `revision` is the count a save names. Three lists load through loaders ([`loaders.md`](loaders.md)): `steps` (every live step in recipe order, instructions and one-off rows included), `categories` (what the spell intends) and `derivedCategories` (what it is made of). Each linked step contributes its ingredient's own categories and those of the form it lays, never another form's; a one-off row and an instruction contribute none; an ingredient deleted since still contributes. `categoryGaps` is worked out by `compareSpellCategories` from the two category loaders' cached answers, so it costs no read of its own.
- **`SpellStep`**: `ingredient` is the linked ingredient, kept and answered even once deleted, and `variant` the form it lays, answered too once that form alone has been deleted, through `findFormsInSpellsIncludingSoftDeleted`. `name` and `form` read the linked row's when there is one and the step's own text otherwise.
- **`createSpell` and `updateSpell`** save a spell's fields and recipe over `services/spells.ts`. Both answer the `Spell` and clear that spell's three loaders first, so the answer is what was just written.
  - `steps` is the whole recipe in order: a step with an `id` is kept, one without is new, a saved step left out is removed. On `updateSpell`, leaving `steps` out leaves the recipe as it is ([`db/grimoire.md`](../db/grimoire.md), "Saving a recipe").
  - `categoryIds` is the whole set of assigned categories: one left out is unassigned, `[]` empties the set, and on `updateSpell` leaving it out leaves the set. An id naming no live category is `VALIDATION` at `['categoryIds', index]` ([`db/grimoire.md`](../db/grimoire.md), "Saving its categories").
  - Every other field is nullable. On `updateSpell` a field left out keeps its value and null clears it, except `status`, `visibility`, `steps` and `categoryIds`, which cannot be cleared and read null as left out.
  - `expectedRevision` is the revision the save was written against. GraphQL cannot require a field that may be null, so the schema has a nullable `Int` and the service refuses a save that leaves it out as `VALIDATION`. Null writes whatever the revision is. A revision no longer current is `STALE_WRITE`, with `extensions.currentRevision`.
  - An observer is `FORBIDDEN`; a spell the caller cannot read is `NOT_FOUND`.

A page of spells with all three lists costs the page, then eight batched reads (three for the steps, two for the assigned categories, three for the derived ones), plus one membership check per coven named. A coven the caller is not in refuses at the field, `FORBIDDEN` with the field's path.

### Workings

`Spell.workings`, `workingCount`, the four writes and the preview, in `graphql/working.ts` over `services/workings.ts`. No resolver authorizes or queries: every service asks for `working: read | create | update | delete`, and a private working is its recorder's in SQL, so by id it is `NOT_FOUND`.

- **`Spell.workings(first, after)`** is a cursor page of the workings of the spell the caller may read, newest `workedOn` first, through `t.pagedConnection` and `findWorkingsPage`. The participants and deductions of the whole page are read in one query each.
- **`Spell.workingCount`** counts the complete workings the caller may read, through the `workingCountBySpell` loader (one query per coven for a page of spells; `0` with none). A completion clears it.
- **`SpellWorking`**: a participant is a `userId` or a typed `name`; a member's name is the one their row last held. A deduction is in the jar's own unit. `warnings` is filled only on the answer to a completion.
- **The writes** are `recordWorking`, `updateWorking`, `completeWorking` and `deleteWorking`. `WorkingInput` mirrors `validation/working.ts`; a bad participant lands on `participants.<index>` as `VALIDATION`. `completeWorking` answers `CompleteWorkingResult { working, warnings }`, one warning per step it took nothing for, with a `NotDeductedReason`. `deleteWorking` answers the id. Making a complete working private again is `FORBIDDEN` with its explaining message.
- **`workingDeductionPreview(workspaceId, spellId)`** answers what completing a working would take from each jar and what it would take nothing for, using the same `planDeductions` as completion, and writes nothing.

### The compendium mutations

`createCompendiumIngredient`, `updateCompendiumIngredient` and `deleteCompendiumIngredient`, in `graphql/compendium-entries.ts` over the compendium services ([`db/compendium-writes.md`](../db/compendium-writes.md), "Compendium writes"). What the workspace mutations above say of the inputs' lists, the answer and a refusal holds here, bar the tier.

- **A curator's or the site admin's, twice.** Each carries `authScopes: { curator: true }` and the service's `assertCurator` refuses again; a coven's steward is refused as its observer is. No coven is an argument.
- **`CompendiumIngredientInput` is the create's**: `IngredientInput`'s fields with `nomenclature` required, since every compendium entry declares one (DESIGN.md §5). Leaving it out is a schema error before any resolver runs.
- **`CompendiumIngredientUpdateInput` is the whole entry**, `categoryIds` among its fields, so an update cannot silently unfile the entry. A variant's `formId: ""` means no pick.
- **`endRedirect` answers whether to take over an address.** A write taking an address another entry still redirects from is `VALIDATION` with one `fieldErrors` entry at `['endRedirect']`, naming that entry and when its window closes; the same call with `endRedirect: true` goes through ([`db/ingredient-slugs.md`](../db/ingredient-slugs.md), "Ingredient slugs").
- **A delete is soft**; a spell holding the entry still reaches it. A coven's ingredient, a deleted entry and an id naming nothing are `NOT_FOUND`, so the admin reaches no coven's row by id.
- **`setCompendiumEntryReviewed(id, reviewed)`** sets a curator's review mark on a compendium entry, or clears it so the entry needs review. It carries the `curator` scope and `assertCurator` refuses again; a coven's ingredient, a deleted entry and an unknown id are `NOT_FOUND`. No field of `Ingredient` carries the mark or the reviewer, because the compendium's reads are cached and shared by every viewer (CLAUDE.md rule 6); the keeper's details read the mark on the server through `readCompendiumReview` ([`db/compendium-read.md`](../db/compendium-read.md)). Create, update and promote set the mark in their services ([`db/compendium-writes.md`](../db/compendium-writes.md)).
- **`compendiumEntryUsers(id)`** answers how many covens hold a compendium entry in their cupboard, for the delete confirm. It carries the `curator` scope and `assertCurator` refuses again; an id that is not a live compendium entry is `NOT_FOUND`. It is a count and never names a coven ([`db/workspace-compendium-entries.md`](../db/workspace-compendium-entries.md), "Counting covens").

### Promoting a common name

`promoteFolkName(workspaceId, id, folkNameId)` swaps an ingredient's display name with one of its common names ([`db/workspace-ingredients.md`](../db/workspace-ingredients.md), "Workspace ingredients"). A null `workspaceId` names a compendium entry and carries the `curator` scope, anything else the `signedIn` scope with the membership check deciding. It clears the child loaders as `updateIngredient` does. A common name that is not live on that ingredient is `NOT_FOUND`.

### References

`Reference`, `reference`, `createReference`, `updateReference` and `referenceSuggestions`: a source, kept once and linked from every row it supports (DESIGN.md §5, "References"), over `services/references.ts` ([`db/references.md`](../db/references.md)).

- **`Reference`** never exposes `workspaceId`; the tier is `isGlobal`. The type's text fields and the input's are built from `REFERENCE_TEXT_FIELDS`, the one list of them, so a field added to `CitationFields` reaches the wire too. `citation` is `renderCitation`'s output (`src/lib/citation.ts`) joined plain, so a chip, a sort and a screen reader read one string; a surface that shows italics calls the renderer for its parts.
- **One input, `ReferenceInput`, for both writes.** An update replaces the reference, so a field left out or `null` is cleared: a day has no empty value to send, which is why this input, unlike the ingredient's, is not all non-null. The shared schema validates it per `kind`, each refusal `VALIDATION` on the field that failed (a web page's `url` and `accessed`, a chapter's, article's or entry's `container`, a book's `published`), never a constraint's name ([`validation.md`](../validation.md)).
- **The tier is the `workspaceId` argument.** Null writes the compendium under `assertSiteAdmin` and carries the `admin` scope; a coven's is written under `assertMembership(…, { ingredient: ['create'] })` or `['update']` and carries `signedIn`. A member citing a compendium reference cannot edit it: under their coven the id names nothing there, `NOT_FOUND`, and without a coven the admin check is `FORBIDDEN`. `updateReference` reaches every row citing it, so it clears `referencesByIngredient` whole. There is no `deleteReference`.
- **`reference(id, workspaceId)` reads one source whole**, for the ingredient form's edit panel: a null `workspaceId` the compendium's alone, a coven's its own or the compendium's, never another coven's. `getReference` runs under `ingredient: ['read']`, the picker's tiers and permission. Another coven's id is `NOT_FOUND`, as an id naming nothing is; a coven the caller is not in is `FORBIDDEN`. It carries no scope and refuses a signed-out caller through `sessionOf`.
- **`referenceSuggestions` is the picker's search**: the compendium's references and the named coven's, never another's, matched at the compendium search's 0.5 word similarity against `authors`, `title` and `container`, accents folded, best match first. It cannot match the rendered citation, which would need rule 7's filtering in SQL. A blank `query`, or one under two characters, lists both tiers by title. Refusals are `ingredientSuggestions`'. A null `workspaceId` reads the compendium's alone, asking no membership, which is all a compendium entry may cite.

### Curated vocabularies

Every keeper-curated vocabulary (categories and their groups, forms and their groups, deities and their traditions, celestial bodies and signs) has the same type, input and three writes, so `curatedVocabularyWrites` in `vocabulary/graphql/curated.ts` registers them. Given an unimplemented `objectRef`, it implements the type; registers `<Type>Input` with `name` and `description` required and no slug, which follows the name; and registers `create<Type>`, `update<Type>` and `delete<Type>`, each under the `admin` scope, the delete answering the id. What a vocabulary adds is told to it: `parent` (the field read through its loader, and the id column, which is also the input's required `ID`), `fields` and `input` (the type's and the input's own), `services` (the three exported writes, each calling `assertSiteAdmin` itself; the input reaches them through `definedArgs`), `moveTo` (for a group whose delete moves its rows first: the delete takes an optional `moveTo`, and the list names the loaders the move leaves stale), `clears` (the loaders an update or a delete leaves stale) and `descriptions` (the update's and the delete's). Each vocabulary's list query stays in its own file, since the filters differ.

Rules every vocabulary shares: the writes carry `admin` and `assertSiteAdmin` refuses again in the service, which is the gate. A slug collision is `VALIDATION` on `name`, naming the row holding the address; a retired or unknown parent is `VALIDATION` on its id field; an unknown, deleted or malformed id is `NOT_FOUND`. A delete answers the deleted id and is `FORBIDDEN` while a live compendium entry uses the value, with a message naming the entries and how many more, shown verbatim to the admin. Each list is public, counts its pages (`totalCount`, `countBefore`) unless it is small, and takes an optional `query` (a name holding it, read literally) and its parent's id, where a parent id that is not a uuid gives an empty page rather than an error.

- **Categories** ([`db/categories.md`](../db/categories.md), "Category writes"). `categories` pages the live categories under live groups by group name, own name, id (the picker's order), each group through `categoryGroupsById`. The picker and the filter read it from the browser: one page of the hard maximum holds the 63 seeded categories. `CategoryInput` is `name`, `description` and `groupId`; an update keeps a seeded row's `seedKey`. Both writes clear `categoriesByIngredient`.
- **Forms** ([`db/categories.md`](../db/categories.md), "Form writes"). The type is `IngredientFormValue`. `ingredientFormGroups` is public and carries no count (six are seeded). `IngredientFormValueInput` has no `endRedirect`, since a rename moves no compendium entry's address, and no slug: a form's is its name and its group, `formSlug`, and follows either. A rename that would give a compendium entry two forms of one name is `VALIDATION` on `name`, naming the entry. Update and delete clear `ingredientFormsById`.
- **Celestial bodies and signs** ([`db/astrology-vocabularies.md`](../db/astrology-vocabularies.md), "The admin writes"). Two types, `CelestialBody` and `ZodiacSign`, registered from one table of names so the two cannot drift. A rename carries onto every live compendium entry listing the value. No loader holds either, so neither write clears one.
- **Groups** (`services/category-groups.ts`, `services/ingredient-form-groups.ts`; [`db/categories.md`](../db/categories.md), "Group writes"). There is no new list query: the admin pages read the services on navigation (rule 1). `CategoryGroupInput` adds `color`; a colour under 4.5:1 on its own ground is `VALIDATION` on `colorDark` or `colorLight`, the message naming the theme, the surface and the ratio verbatim. A delete takes an optional `moveTo`: the group's live categories or forms move to the group `moveTo` names, a form re-slugged there, before the soft delete, in one transaction. A group with live rows and no other live group named, or a moved form that would take another's address, is `VALIDATION` on `moveTo`, and a form-group rename that would re-slug a form onto another's address is `VALIDATION` on `name`. A group delete is never `FORBIDDEN` for a compendium entry's pick, since the moved forms stay curated. Loaders cleared: `categoryGroupsById` on a category group's update and delete, `categoriesByIngredient` on its delete, `ingredientFormGroupsById` and `ingredientFormsById` on a form group's update and delete.
- **Deities** ([`db/deity-vocabulary.md`](../db/deity-vocabulary.md), "The keeper's writes"), over `services/deities.ts` and `services/deity-traditions.ts`. `deities` lists each deity under its tradition, by the tradition's name and then its own; `deityTraditions` is the live traditions by name and carries no count. `DeityInput.otherNames` is optional and the whole list, so a save brings the stored names to the list sent and an absent list clears them. A name the list repeats in any case, or another live deity of the tradition holds, is `VALIDATION` on `['otherNames', index]`, naming the deity that holds it. `Deity.otherNames` is non-null, alphabetical, read through `otherNamesByDeity`. There is no slug (a deity's follows its name and its tradition) and no `endRedirect`, since a deity moves no entry's address. A deity's rename carries onto every live compendium entry's link to it. `deleteDeityTradition` takes `moveTo` as a group does: its live deities move first, each re-slugged there; a tradition's rename re-slugs its deities, and one that would collide is `VALIDATION` on `name`. Loaders cleared: `deitiesByIngredient` on every deity and tradition write but a create, `otherNamesByDeity` on a deity's update and delete, `deityTraditionsById` on a tradition's update and delete.

### Auth scopes: the second check

`@pothos/plugin-scope-auth` gives the schema four scopes, all read off the context without a query:

| Scope      | Holds when                                   |
| ---------- | -------------------------------------------- |
| `signedIn` | the request has a session                    |
| `curator`  | the session's role is curator or keeper      |
| `admin`    | the session's role is admin                  |
| `self`     | the user id it is given is the session's own |

A scope is the second check, never the first. The service's own check is the gate (CLAUDE.md rule 1), and a scope on a field is a cheap early refusal in front of it. `User.email`, `role` and `canCreateWorkspace` carry `{ self: user.id, admin: true }`, which holds if either does; every people mutation (roles, creation approval, pause, admin invitations) carries `admin`; every compendium and vocabulary write carries `curator`, which a keeper holds too; `createReference` and `updateReference` carry `curator` when their `workspaceId` is null and `signedIn` otherwise. `ok` and the compendium's queries carry no scope, and the sweep names them so. The private fields' test hands `me` another user's row, standing in for a service that chose the wrong one, which is the bug the scope is behind. A scope refusal throws `Forbidden` from `src/lib/errors.ts`, the same type a service throws, so the transport maps one refusal shape whichever check said no.

**The sweep proves the two checks apart.** `tests/db/graphql-query-scopes.test.ts` names every `Mutation` field as an admin write, with what it governs, or one any session may reach, so a write added later says which it is. It runs each keeper write signed in as A, a coven's steward, the highest workspace role and still no site role, with E admitted past the scope and the service's own refusal as the preconditions in the same case. The code cannot tell the checks apart, since both answer `FORBIDDEN`, but the message can: the scope's refusal is `Forbidden`'s default message, and `assertSiteAdmin` says "Only a site keeper may do this". So a non-keeper hearing the default was refused by the scope before the service ran, and the field fails the sweep the moment its `admin` scope goes. What the service refuses, and to whom, stays its own test's. What a keeper governs is a closed type, `Governed`, beside the sweep, so a keeper write outside it is a visible change. The keeper's reach into no coven is `tests/db/workspace-isolation.test.ts`'s.

### The SDL snapshot

`src/graphql/schema.graphql` is the printed SDL, committed, and checked by `tests/graphql/schema-snapshot.test.ts` through Vitest's `toMatchFileSnapshot`. It is one of the two permitted snapshots, beside the design tokens (DESIGN.md §11), because the schema is a contract and a change to it should show up in the diff.

- **A schema change fails the test until the file is regenerated.** Vitest never overwrites an existing snapshot without `-u`, and under `CI` it does not write a missing one either, so CI fails on a changed schema and on a deleted file alike. Locally, a missing file is written on the first run.
- **Regenerating is the deliberate step:** `npm run test -- tests/graphql/schema-snapshot.test.ts -u`. The rewritten file is committed with the change that moved it.
- **Only a contract change moves it.** Pothos's `toSchema()` sorts types and fields lexicographically, so reordering the imports in `src/graphql/schema/index.ts` changes nothing.
- **Prettier ignores it.** `printSchema` owns the layout, and a reformat would fail the test. `.prettierignore` carries it.
