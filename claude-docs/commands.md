# Commands — summary

Every command the repo runs, and where it runs. `CLAUDE.md` keeps the ten a
task reaches for; this is the rest.

**Two places run them.** `make help` lists every target from the **host**.
Neither `make` nor `docker` is installed in the devcontainer, so a session
running inside it calls the npm scripts directly, and the `make` column below is
the host equivalent. **There is no Python in the devcontainer** either: neither
`python3` nor `python` exists, so quick scripting, JSON munging or arithmetic
goes through Node (`node -e`), the npm scripts, or `jq`, `grep` and `sed`.

**While working, run the individual test files and specs a change touches.**
The full suites run only when the owner says so. When they do, run
`test:coverage`, not `test`: a plain `npm run test` pass can still fail CI on
the 80% threshold (lines, branches, functions, statements) alone.

**`npm run test` and `npm run test:coverage` take the Vitest lock themselves.**
Each runs through `scripts/with-lock.sh /tmp/sorrel-vitest.lock`, so two runs
from different sessions wait for each other instead of colliding on the shared
Postgres. The wrapper skips the lock when a parent process already holds it, so
`flock /tmp/sorrel-vitest.lock npm test` runs instead of deadlocking; a plain
`flock` wrapper does not know that, so never use one in a script. A direct
`npx vitest run …` takes no lock, so wrap that one by hand:
`scripts/with-lock.sh /tmp/sorrel-vitest.lock npx vitest run …`. `test:debug` and `test:ui`
take no lock. [`testing/e2e.md`](testing/e2e.md) explains the locks.

**Every local Playwright run sets `BETTER_AUTH_SECRET` on its command line, to
the placeholder `local-dev-not-a-real-secret`.** This covers `npm run e2e`,
`npm run test:stories`, and a named spec. The Playwright runner signs each
test's session cookie with that secret (`tests/e2e/session.ts` throws without
it), and does not read `.env.local`. The servers it starts get the same value:
Playwright passes its own environment on to them, and Next never lets
`.env.local` replace a variable that is already set. So a made-up value works,
and the real secret is never read for a test run. It is the placeholder CI's
Playwright jobs set too.

```sh
BETTER_AUTH_SECRET=local-dev-not-a-real-secret npm run test:stories
```

A bare `npx playwright test <spec>` takes no lock, so wrap it:
`flock /tmp/sorrel-e2e.lock env BETTER_AUTH_SECRET=local-dev-not-a-real-secret npx playwright test <spec>`.
One `webServer` entry (`scripts/e2e-servers.ts --playwright`) builds once and starts every server together (testing/e2e.md).
Locally a run reuses an e2e server already listening on its port, so a server left running under a different secret
refuses every cookie the run signs: stop it, or pick another `E2E_PORT_BASE`.
A worktree has no `.env.local`, since the file is not committed: copy `/app`'s
in before the run, for the server's other settings.

**Deploys are CI-only (M0.26).** `.github/workflows/deploy.yml` deploys via the
Vercel CLI (`vercel pull`/`build`/`deploy --prebuilt`/`alias`) on a push to
`main` (production) or `staging` (preview, aliased to the staging domain), and
on a `hotfix/** → main` PR (a per-PR preview, commented on the PR and torn down
on close). `vercel.json` sets `deploymentEnabled: { "**": false }`, so Vercel's
Git integration deploys nothing and the workflow is the only path. There is no
local deploy command ([`ci/deploy.md`](ci/deploy.md), "Deploy").

**Seeding an environment by hand (M14.26).** `.github/workflows/seed-environment.yml`
runs the seven reference seeds below on staging or production without a deploy,
in one transaction, through `db:seed:reference`.
A site keeper starts it from the Actions tab, choosing `environment` (`preview`
is staging), `dry-run` (on by default: everything is decided and rolled back)
and `force` (off by default: passes `--force`, which reaches the compendium seed). It
waits for any migration running, and its summary lists every `UPDATED`,
`REFUSED`, `ADOPTED`, `RETIRED` and `PENDING` line ([`ci/deploy.md`](ci/deploy.md),
"Seeding an environment by hand").

**Pre-commit** (M11.23) checks only the files that changed, so a one-line fix
doesn't pay for checking the whole repo. A tool called lint-staged works out
the file list and hands it to each check; `lint-staged.config.mjs` says which
check gets which files. It runs two ways:

| Run                           | Files checked                                                                                                                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The git hook, on `git commit` | The staged files, through `npm run pre-commit:staged`, which `package.json`'s `"pre-commit"` array names. Every unstaged edit is set aside while the checks run and put back afterwards, so the hook checks exactly what is being committed |
| By hand, `npm run pre-commit` | Every tracked file changed since the last commit, staged or not. A new file needs `git add` first                                                                                                                                           |

Three things are not narrowed:

- **Typecheck runs whole or not at all.** `tsc` can't check a single file on
  its own terms: changing an exported type can break a file nobody touched. So
  it runs over the whole project, once, and only when a TypeScript file,
  `tsconfig.json`, `package.json` or `package-lock.json` changed. A commit
  touching only Markdown skips it.
- **A check's own config reruns that check over everything.** Changing
  `.oxlintrc.json` or `lint/` runs `oxlint .`; `.prettierrc` or
  `.prettierignore` runs `prettier --check .`; `.stylelintrc.json` or
  `package.json` (which holds `browserslist`) runs `lint:css`. A narrowed run
  would miss what the new rule now flags.
- **`lint`, `format:check` and `typecheck` stay whole-repo.** They are what
  CI's `checks.yml` runs, so the local narrowing gives up no protection.

Every check runs to the end even when another fails (`--continue-on-error`),
so one run lists every problem. Prettier still honours `.prettierignore` for a
file passed by name, so a staged file under `src/gql/` is not flagged.

**Oxlint** (`.oxlintrc.json`) exits 0 on a warning, so a rule that only warns is a rule nothing enforces. The repo holds 0 warnings and 0 errors. A disable is `// oxlint-disable-next-line <rule> -- <reason>` (`{/* … */}` among JSX children), and the reason is required.

- **Errors**: `no-console` (output goes through a logger; `scripts/**` and a few named files are exempt), `no-unused-vars` (dead code hides mistakes), `no-unsafe-optional-chaining` (it throws on undefined), `react-hooks/exhaustive-deps` (a missing dependency is a stale value), `react/set-state-in-effect` (state set in an effect draws twice), and the `jsx-a11y` rules `click-events-have-key-events`, `no-static-element-interactions`, `no-noninteractive-element-interactions`, `interactive-supports-focus`, `no-noninteractive-tabindex`, `control-has-associated-label` and `anchor-is-valid` (each is a keyboard or screen-reader failure).
- **Warnings**: `jsx-a11y/aria-role`, set to `ignoreNonDOM` so a component with a `role` prop is not judged as an element, and the advisory rules below.
- **Advisory, disabled where deliberate**: the React Compiler rules (`react/refs`, `react/immutability`, `react/preserve-manual-memoization`) because the compiler is off in `next.config.ts`; they are off in `tests/**`, where fixtures write and read freely, along with `react/globals` and `react/incompatible-library`. `jsx-a11y/prefer-tag-over-role` is disabled per site where the native tag would change the layout or the meaning.

**knip** (`knip.jsonc`) lists files no entry point reaches, exports and types nobody imports, and packages `package.json` lists but no file imports (or the reverse). It is not part of `lint` or `pre-commit`. CI runs it as the `checks / unused` leg on every pull request that runs `checks / lint`; the leg never fails (`continue-on-error`), is not a required check, and posts its findings as a PR comment marked "Unused Code (Non-Blocking)". The script supplies a placeholder `DATABASE_URL` when none is set (knip loads `drizzle.config.ts` and `playwright.config.ts`, which throw without one) and unsets `NODE_ENV` (`development`, which the devcontainer sets, makes `withWorkflow` watch the job files and never exit). It also lists an export that only its own file uses: drop the `export`, or, where something reads it by name in a way knip cannot follow (a test reading it off a module barrel), keep it with a JSDoc `@public` tag and the reason. Each exception in `knip.jsonc` carries its reason beside it.

**Stylelint** (`.stylelintrc.json`) refuses, outside `src/scss/_variables.scss`: a hex, a named colour, a colour function with a numeric first argument, and any `font-family`, `font`, `font-size` or `z-index` value that is not a token ([`styling.md`](styling.md), "Binding rules"). A group colour is a hex on its `category_groups` row, set inline from data, so the linter never sees it. `stylelint-plugin-use-baseline` (`available: "widely"`) refuses CSS past the browser floor; an enhancement carries a disable comment saying what is lost and when it becomes widely available. Class names must be BEM (`block__element--modifier`, each part kebab-case), and `number-max-precision` is 5. Blank-line and colour-notation rules are off where Prettier owns the layout or the repo writes the other form on purpose; `.stylelintrc.json` lists each.

## The local review

Tools for reading a change before it is pushed, all inside the devcontainer. The image's `devcontainer` stage holds difftastic, Plannotator, ripgrep (the search tool Plannotator's code navigation runs), and the `dft` alias, which it writes to the system Git config, `/etc/gitconfig`: a `~/.gitconfig` written before VS Code attaches stops it copying the host's name and email in. `postCreateCommand` installs `gh stack` each time the container is created.

The editor extension `bierner.markdown-mermaid` draws the Mermaid block in VS Code's Markdown preview, so `.review/affected.md` opens as a picture.

**How the graph parses the code.** `.dependency-cruiser.cjs` sets dependency-cruiser's `swc` parser, because its TypeScript parser does not support the repo's TypeScript and finds no modules without a warning. `swc` cannot parse a `using` declaration, so the config excludes `src/modules/documents/jobs/document-mailing.ts`, and `tests/dependency-cruiser-config.test.ts` fails when another file stops the parser. If the `swc` route breaks, the fallback is the TypeScript parser with a second, older TypeScript installed beside the repo's ([`review-poc/verify.md`](review-poc/verify.md), Decision 1). The config holds no rules: Oxlint owns the import rules, cycles included.

**How the tools are fetched.** The `review-tools` stage of `Docker/Dockerfile.node` downloads every file through a `fetch` helper that checks a SHA-256 written in the Dockerfile, and checks Plannotator against its release's `.sha256` file as well. Nothing is piped into a shell (guard: `tests/guards/download-checks.test.ts`). difftastic's checksums are the ones GitHub publishes for each release file; the three Debian packages (`libc6`, `libgcc-s1` and `libstdc++6`, about 26 MB unpacked) come from `snapshot.debian.org`, whose URLs never change, and their checksums match Debian's package index. Raising a version means new URLs and new checksums together.

**Why the Plannotator binary is patched.** It is built for glibc and Alpine is musl. Plannotator starts itself again for some commands (`plannotator inbox`), so its own executable path must be the real binary: running it as an argument of the glibc loader makes that path the loader, and the restart fails. The `review-tools` stage instead edits the ELF headers in place, leaving the file size unchanged (a tool that grows the file breaks the bundle appended to it): the interpreter becomes the symlink `/opt/glibc/ld.so`, and `DT_RUNPATH` becomes `$ORIGIN`, with symlinks to the glibc libraries beside the binary. No `LD_LIBRARY_PATH` is set, so the git and shells Plannotator starts keep musl. A new Plannotator release needs the patch step run against it (the build fails if the headers have no room).

**Rebuilding the container.** "Dev Containers: Rebuild Container" in VS Code builds the image and starts a container from it; no separate build is needed first. Without VS Code, `make devcontainer-up` on the host does the same, and the checks in step 2 hold for its container too:

1. Run "Dev Containers: Rebuild Container" in VS Code. To read a failing build in a terminal instead, run `make devcontainer-build` on the host, from the repository root; the devcontainer has no `docker`.
2. Inside the rebuilt container, each of these should work:
   - `difft --version` and `plannotator --version` each print a version.
   - `plannotator annotate README.md &`, then `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:19432/` prints `200`; `http://localhost:19432` opens in the host browser when no other session holds that port; otherwise use the address Plannotator prints. Stop the server afterwards (`kill %1`).
   - `git dft HEAD~1` on a commit that touches a `.tsx` file prints a structural diff with no notice that it fell back to a text diff.
   - `gh stack view` runs.
   - `git config --global --get diff.external` prints nothing.

### Destructive DDL check

check-destructive-ddl file list precedence: DESTRUCTIVE_DDL_FILES (CI changed-file list, JSON or newline-separated; set-but-empty means nothing changed), then positional filenames, then a diff against the Gitflow base; only *.sql scanned. Every ALTER COLUMN ... TYPE is flagged whether or not it narrows, and ALTER INDEX ... RENAME is flagged though it cannot break a rollback. Usage: --base origin/main, --all, <file>..., --self-test (fixtures under scripts/**fixtures**/destructive-ddl/).

### Migration order check

check-migration-order: the branch journal is the working tree's, the base's is the base ref's committed one; base resolves as check:destructive-ddl's does; CI fetches it and passes --base because its checkout is a detached merge commit. Usage: npm run check:migration-order [-- --base origin/main].

### Compendium attribution audit

compendium-audit: --report (default) writes nothing; --apply, only after the curator has read the report, marks each flagged file needs-review and adds one Questions block per citation, idempotent; --all with --apply also writes candidates naming no other formal name; --wiki is a repeatable folder of <Title>.wikitext pages (default every shards/*/wiki folder); --limit n; --resolve writes nameBasis: resolved, headedAs and resolvedBy on each citation Wikipedia settles (the page is, or redirects to, the article the entry cites as stated; never a collision, disambiguation or another taxon); --fetch fetches missing redirect answers, the only network use; --dry-run; --cache is a JSON file outside git, default wiki-lookups.json beside the shards.

### Database seeding

db-seed: the reference-data targets are categories, forms, astrology, deities, sources, compendium, demo-coven, documents and help, what migrate.yml seeds after migrating; Node's type stripping resolves no extensionless relative import, hence tsx. Commands: db:seed (SEED_SCENARIO, default minimal), db:seed:categories|forms|astrology|deities, db:seed:sources after the vocabularies, db:seed:compendium after sources, db:seed:demo-coven after the compendium (seats every account), db:seed:documents (version 1 of each), db:seed:help (FAQ, articles and glossary), -- --dry-run runs then rolls back, db:seed:compendium -- [--dry-run] [--adopt] [--force] (--adopt lists ADOPTED lines as migrate.yml does; --force lifts refusals 1 to 4), db:seed:reference runs the reference seeds in one transaction, db:drop drops the schema only, db:reset drops, migrates, seeds.

### Lighthouse SEO

lighthouse-seo: audits the home page, the compendium list and one current entry, signed out (or the --path entries, which stand in for the entry the script picks, so a sampler picks them, say from /sitemap.xml). Off production the app answers X-Robots-Tag: noindex and robots.txt disallows all, so the not-blocked and robots-valid audits fail, as does every preview; that is the site working. It is no part of CI, test:coverage, test:stories or e2e. <base-url> e.g. http://localhost:8001 (http://devcontainer:<port> from the browser). --port uses a Chrome already listening for DevTools; without it chrome-launcher launches a local Chrome, absent in the devcontainer, whose Playwright servers open no DevTools port, so it uses the lighthouse-chrome container (make lighthouse-up on the host); docker-compose.yml sets LIGHTHOUSE_CDP_HOST and LIGHTHOUSE_CDP_PORT as the defaults. --host defaults to localhost. Chrome builds the WebSocket address it returns from the Host header, and Lighthouse sends the hostname flag as that header, so a name like lighthouse-chrome is refused.
