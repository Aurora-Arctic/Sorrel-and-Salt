# Wave 05 — Authorization

**MB.45, MB.46 and MB.47 open the wave and have nothing to do with authorization.** They are the deploy pipeline, broken in both environments, which outranked everything else here. v0.2.0 was merged and tagged but not deployed: `migrate` failed on the push to `main` and `deploy` is gated behind it, so production still served v0.1.1. That was stale rather than broken, since code and schema still agreed, but nothing else shipped until it was fixed.

- **MB.45 first**: `vercel pull --git-branch` is rejected outright on the production target, so it is what kills `main` earliest, and it needs nothing outside the repo.
- **MB.46 branches off `main` after MB.45 merges**, not alongside it. On a branch still carrying MB.45's bug the production pull fails first and MB.46's new deploy-job validation step never executes, so the guard would merge unverified. The two touch the same two workflows and the same guard test: they are sequential, not parallel.
- **MB.47 needed someone at the Vercel dashboard**, to look at the Preview `DATABASE_URL` row scoped to branch `staging`, so it could not be specified from the devcontainer. MB.45 and MB.46 do not wait for it, and MB.46 is what makes the cause legible if the dashboard check is inconclusive: before it, the value is masked before anything can print it. Their own previews show a red `Deploy` leg until MB.47 lands, which is not a block: `Deploy` is not a required check, and #136 merged with it skipped.
- **MB.49 follows MB.47**, whose follow-up hotfix it was: a failed migration names its cause. It depends on nothing else in the wave; MB.103's reorder is what found it absent from this row.

**M6.3, M10.3 and M6.6 are the wave's subject.** All seven workspace-scoped tables now exist, so M6.3's `Membership` sweep over the finders is complete rather than partial, which is the reason this wave waits on the schema block. Run at its original position, it would have covered whichever tables happened to exist that week, and every finder added later would have been a retrofit rather than an adoption. M6.3 then blocks every workspace-scoped service from M8 on. **M6.4 and M6.5 were on this row and are retired** (MB.29, accepted in Wave 3). RLS is deferred to the public launch, M6.3 carries a type-level proof in their place, and M10.3 carries its column plus a service rule. So the wave is three tasks where it was five, and the risk that once topped the whole re-sequencing, policies landing after the seeds and filtering them, went with them. M6.6 now carries the whole burden of proving isolation, which is why its direct-id denial tests are per-entity rather than a sample. M10.3 lands here, after M1.23's seeded spells, for the reasons in [`TASKS.md`](../TASKS.md)'s "Breaking the M1.23 ↔ M10.3 cycle", which also says why its migration needed no destructive-DDL acknowledgement.

**MB.48, MB.50 and MB.51 clear the ground before M6.3 opens.** MB.48 is the destructive-DDL gate, not the deploy pipeline, and is independent of the other three: it can run in parallel on a feature branch into `staging` whenever there is room. It stopped being urgent once #136 merged. The two migrations that had failed the release check were then in `origin/main`, so the next release would not rescan them, and what remained was the class rather than the instance. **MB.50 follows MB.48** so it is not racing another PR through the same files. It is a repo-wide comment sweep touching nearly every schema, seed, test, workflow and Docker file, so any task open in parallel would conflict with it on merge. It changes no executable code and depends on nothing in the wave, and it merges before M6.3 opens, so M6.3 starts from the trimmed files and from the comment convention MB.50 adds to CLAUDE.md. **MB.51 follows MB.50 for the same reason.** It deduplicates the db-test harness, the seed logic and the image-build workflows, the files MB.50 had just rewritten the comments in, so it is based on MB.50's branch rather than on `staging`. It too lands before M6.3 opens, since M6.3's finder tests are the first that would otherwise be written against the old per-file scaffolding. MW.5 is retired (MB.31).
